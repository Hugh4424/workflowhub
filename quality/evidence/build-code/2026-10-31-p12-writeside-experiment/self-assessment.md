## 2. 我最满意的一条：AC-EFFECT-001 的两层盲判

它要求：绿而错变体先通过该 Phase 的全部契约测试、门禁、判定器、断言和回归，再被独立判定者拒绝；判定者只读验收和原始需求，不读方案；真实消费者在真实场景用一次；每个 Phase 一行，全部行过才算过。

为什么它能判效果：

- 它把「门禁绿」明确排除在通过条件之外：绿而错必须门禁全绿，仍要被拒。
- 它判的是验收的区分力，不是字段齐不齐：判定者要在不知道 A/B 标签时判，并写出用户可观察差异和门禁为何区分不了。
- 它把「验收比方案重要」变成可判动作：判定者不读方案；若必须读方案才知道判什么，验收就不自足。
- 它把「做对」推到「有效」：真实消费者用一次，得到该 Phase 原始需求要求的结果，且不求助作者。
- 它用逐 Phase 行回应原始需求的全称「每个 Phase」，不让试点一行冒充全部。

它仍然不能证明的东西：

- 只证明红队想到的一种错法；不证明所有错法都被覆盖。
- 「效果」被我定义为用户可观察结果 + 下游消费者完成；不是业务指标、长期用户效果。
- 语义判定不能用一条命令重放；Phase 模板的 `Done` 要求一条命令，所以这条 AC 在当前机器合同下只能记 `incomplete`。
- 最终验收 Phase 没写；只交 P1 时，它只证一行，不能证全称。
- 消费者如果是材料的下游作者，而不是产品用户，效果是弱的；对内部 Phase 只能这样。

结论：它能判「这个 Phase 的验收能不能拒绝一个绿而错的交付，并让一个真实消费者完成一次使用」；不能判「产品产生了真实用户/业务效果」，也不能单独判「全部 Phase」。如果原始需求的「效果」指前者，这条够用；如果指后者，不够。

## 3. 模板与标准让我为难、需要猜的地方（逐处）

### A. 形状与机器合同

1. **四标签装不下六要素**：spec 模板 Appendix A 只示范 `验证／通过／失败／证据`；任务要求 `判据／成功／失败／环境与数据／谁判／承接`。模板没有环境数据、谁判、承接的独立位置。我把它们折进 `验证` 与 `证据`，并在「六要素落点」表说明。机器读者能读四标签，但读不出谁判、环境、承接；换一个作者会放别处。
2. **决策日志的验收面是索引，不是讨论**：模板说「本节是 make-decision 到 build-plan 的交接索引」「完整判据的唯一权威在 spec Appendix A」。原始需求要求 make-decision 讨论每个工作包怎么验收；模板把讨论推给 build-plan。我只能在 work package 下自造成功/失败/谁判/环境块；模板没有这个字段。
3. **验收面表没有谁判、环境与数据、判定时点、覆盖上限**：列是 AC/用例/成功/失败/证据/承接负责人/UC；「承接负责人」不是判定者。表本身装不下任务要求的四项，我加了表外说明。
4. **工作包没有验收字段**：模板的工作包是「要交付什么 + 五行过程 + 四字段决定」；没有「怎么验收」。我加了成功/失败/谁判/环境/怎么判/证据/承接；这是自造结构。
5. **decision-log 与 spec 的 AC 所有权冲突**：decision-log 说验收面与 spec Appendix A 同号、spec 是唯一权威；但 decision-log 在 make-decision，spec 在 build-plan。make-decision 写 AC 索引时 AC 还不存在；build-plan 写 AC 后谁更新索引？模板没有单一 writer 和更新规则。我让 Phase 不改 decision-log，回 make-decision owner；索引仍是空的。
6. **「每个 Phase」的全称没有覆盖机制**：spec AC 可以逐 Phase 一行；Phase 文件只写自己一行；最终验收 Phase 的「验收 Phase 才能做的检查」是唯一跨 Phase 的地方，但它是可选的、只给末 Phase、且没有「逐 Phase 行」的表结构。模板没说非末 Phase 怎么声明「我只证一行，别把 AC 判过」。我在边界、覆盖上限、机器字段里自造。
7. **一条命令重放 vs 语义判定**：phase 模板的「怎么验证」完成判据、机器字段 `gate_cmd`、任务卡「完成」都要求没参与实现的人能用一条命令重放。盲判/消费者观察写不出这样的命令。强行写只能写「构造盲包」或「跑门禁」的命令，那正是原始需求说的「只检查有没有做」。我选 `gate_cmd=unavailable`、`Done=incomplete`；本 Phase 因此过不了模板的机器合同。这是最大的结构性冲突。
8. **8 值档位词表不可读**：phase 模板要求档位只引用 `runtime/evidence/acceptance-evidence-validator.mjs` 的 8 值词表；文件不在允许材料里。我用了 `pass/incomplete/unavailable`，很可能是猜的；机器读者可能不认。
9. **`test-asset-governance-rules.md` 不可读**：phase/spec 模板都要求在判定前读该文件的「验收标准可执行形式」节；它不在允许材料里。这恰恰是「什么叫有效验收」的权威，却没给。陌生人只能像我一样自造绿而错/盲判，可能不符合项目标准。
10. **表/长行 vs 80 字**：十一条第 5 条要一句一行 ≤80 字；模板的验收面表、四标签 AC、机器字段都是长行。我优先保四标签和表格，正文尽量折到 80 字内；仍有 7 行 84–101 字（非表格，主要是长路径或代码跨度），四标签已折成多行。标准说校验器只报读数，不拒收；但作者会感到「照模板」与「照标准」冲突。
11. **每份材料恰好一张编号对照表**：标准要求；Phase 的对照表在任务卡「任务 N/任务编号」。本 Phase 不写任务卡（因为语义判定没有 RED/GREEN 命令），所以没有对照表；片段按标准是不完整的。模板要求每张任务卡 18 字段，但没给「语义判定任务」的卡形状。

### B. 验收设计缺槽

12. **「效果」没有定义**：标准与模板都没定义「效果」是用户可观察结果、业务指标、下游消费者完成，还是行为正确性。spec 模板的「效果评测」在末 Phase，讲指标/统计量/正负负载；phase 七槽讲场景/环境/用例；两处不是同一层。我推断为「用户可观察结果 + 下游消费者完成」，并标 `inferred`；如果项目指业务指标，我的 AC 不成立。
13. **绿而错/负控没有位置**：模板的「反向场景」是输入错误/异常，不是「通过所有门禁但结果错」的交付；「效果评测」有正例负例，但只在末 Phase、且是 metrics。我需要红队造绿而错变体；模板没有「谁造负控」这个角色。七槽的「谁判」只有一个判定者；我加了红队和第三方。
14. **独立性的边界**：模板说判定者与实现者不同上下文；没说是否要与 AC 作者不同。我的盲判要求与作者、实现者都不同；这是我加严的。模板也没说「不同 subagent/不同 provider/不同人」哪种算独立。
15. **具名判定者**：模板要求「具名子代理或 provider」，但 spec/phase 写作时不知道将来谁判；我写 role + unknown + owner=主会话。模板没有「何时具名」的规则。
16. **「验收标准比方案重要」没有可判形式**：原始需求说 Phase 最重要的是 AC 不是方案；模板的 Phase 仍有「为什么现在做」「每个文件由谁改」「怎么验证」等大段方案内容，七槽只占一节。我把它操作化为「判定者只读验收和原始需求，不读方案」；模板没有这个要求，也没有「方案可以省/后置」的规则。
17. **「用户在场」歧义**：七槽说真实外部环境产生判据时写用户是否在场；盲判的「人」是判定者/消费者，不是产品用户。模板把「人」混在一起；我区分了「环境用户」与「判定者/消费者」，但这是猜。
18. **数据规模/脱敏 N/A**：七槽的环境与数据写来源、规模、脱敏、构造、清理；本任务判定对象是两份交付+一份需求+一次消费者场景，没有数据集。模板说拿不到时记 unavailable/incomplete，不写 N/A 蒙过去；我写「规模与脱敏不适用 + 理由」，这是对模板规则的偏离。模板没有「非数据型验收」的 N/A 例外。
19. **「效果评测」的位置**：模板的「效果评测」在「验收 Phase 才能做的检查」里，只给唯一末 Phase；普通 Phase 的作者不会读到它。它是模板里最接近「效果」的方法，但被藏在末 Phase、且以指标/统计量为主；对普通 Phase 的语义效果没有指导。
20. **模板示例把作者拉回代码验收**：spec 的 AC 示例是「非法配置报位置+退出码 2」；phase 的示例是 PROCESS_STALLED + RED/GREEN oracle。两者都是代码/状态行为，且没有绿而错负控。陌生人照示例写，会写出「行为断言通过」而不是「效果判据」；这正是原始需求禁止的。模板的好例没有展示效果级 AC。
21. **谁判/承接散在多个字段**：Phase 机器字段有 `消费者`、`Done`，但没有判定者身份、判定时点、独立上下文差异；spec 四标签没有；decision-log 表没有。三份材料的「谁判」分散在不同字段，读者要拼。

### C. 外部依赖与非代码任务

22. **spec 的验收对象只支持 UI/CLI**：模板的 `checkAcceptanceObject` 要 workspace/service/route/state/viewport 或 CLI 五项；本任务是材料/方法，两个都不适用。我记 N/A，checker 会 `ok=false`。模板没有「材料/流程任务」的验收对象形状。
23. **「代码锚点」H3 逐字保留**：spec 模板要求 `## 实现设计（全局权威）` 和四个 H3 名逐字保留；四个 H3 之一是「代码锚点」。本任务无产品代码，我只能写 N/A + 材料锚点。模板假设所有 spec 都有代码；流程/材料任务被套进代码形状。
24. **来源编号/真实任务身份**：模板的 R-001/ADR-001/AC 编号、路径、env、provider 都要求真实值；只给原始需求时，我只能写 unknown + owner。模板允许 unknown，但一个完整材料会有大量 unknown；不知道这算不算「写完」。模板没有「最小可写集」或「哪些 unknown 可接受」的规则。

## 4. 我有没有写成「跑测试通过就算过」？

有，而且不止一处，只是我做了标注：

- **最明显的一处**：Phase 的「怎么验证」表和机器字段。唯一可执行的行是「控制有效：B 通过全部门禁，退出码 0」；语义判定两行写 `unavailable — 只能人读`。我标了「命令不是判定器」，但模板的 `gate_cmd`、`oracle`、`evidence_path`、`Done` 让命令成为重心。一个扫表的人可能看到控制命令通过，就把控制当成验收。
- **第二处**：decision-log 的验收面。成功条件里「绿而错变体通过全部门禁」是一个门禁条件；它不充分，但它是表里最具体的可观察条件，而且表没有判定者/消费者列。读者可能停在这里。
- **第三处**：spec AC 的 `证据` 把「全部门禁原始输出」放在最前；答卷和消费者记录也在，但证据排序会让人先看门禁输出。
- **我有没有把 AC 的 `通过` 写成「测试全绿」？** 没有。`通过` 明确要求判定者理由、消费者结果、控制有效、拆封记录；`失败` 明确写「只写测试通过」算失败。所以 AC 文本本身不是「测试通过=完成」。真正的问题是模板的机器形状把语义判定挤到 `unavailable`，让整个材料看起来像一个「跑命令」的 Phase。
- **最危险的标签**：我写了 `ORACLE-EFFECT-BLIND`，但它不是一个可执行 oracle，只是盲判答卷的判据名。这个标签会制造「有判定器」的错觉；模板的 `oracle` 字段没有说它必须可执行，但 `gate_cmd` 必须可执行，两者放在一起会误导。

如果我是一个更赶时间、或不那么警惕的作者，我会把「控制有效」的命令当成 gate，把 `Done` 写成 `pass`，然后这份 Phase 就变成「门禁绿了就算过」——正好是原始需求禁止的。模板没有机制阻止这件事；它只靠作者自觉。

## 5. 哪些是猜的，哪些是模板直接给的

### 模板直接给的

- spec：章节骨架、Appendix A 四标签的示范、Appendix B 对照表、PFACT/FR/AC 的示例、`## 实现设计（全局权威）` 与四个 H3 名、验收对象 JSON 与 checker、证据计划提示、测试计划提示。
- phase：七槽的提示（判据/成功/失败、正常与反向场景、环境与数据、用例、谁判、失败回修、承接）、机器字段名、任务卡 18 字段、G-2 示例、选节表、`Done`/`gate_cmd`/`oracle`/`evidence_path` 的形状。
- decision-log：任务身份、级别与路线、原始需求、工作包与四字段决定、验收面表、未决、风险、外置事实索引、旧编号对照的骨架。
- 十一条：读者、中文编号、标题即问题、一句一行、术语首现、表格只对照、机器字段位置、不用层号、不滥用黑话、编号对照表。

### 任务书给的（不是三样材料）

- 六要素：判据、成功信号、失败信号、环境与数据、谁判、承接。
- 自评要求、诚实要求、C07 来源说明、三份片段的格式要求。

### 我猜的

- 「效果」= 用户可观察结果 + 下游消费者完成，而不是业务指标。
- 绿而错变体、红队、盲判、第三方拆封、消费者观察这一整套方法；模板只给了「反向场景」「谁判」「环境与数据」的提示，没有给这套方法。
- 判定者要与 AC 作者也不同上下文（模板只要求与实现者不同）。
- 「判定者只读验收，不读方案」作为「AC 比方案重要」的操作化。
- 每 Phase 一行、全部行过才过；非末 Phase 只证一行。
- 具体 judge/provider/env/data/path/task-id；`pass/incomplete/unavailable` 档位；`ORACLE-EFFECT-BLIND` 命名。
- UI/文档/代码三种绿而错示意的具体形态。
- 「每个 Phase」是否含跨任务推广；我按本任务 build-plan 的 Phase 处理，跨任务记不覆盖。
- decision-log 与 spec 的 AC 所有权：我让 Phase 不改 decision-log，回 make-decision owner；模板没说。
- 材料作者作为 Phase 的唯一 writer；模板的 writer 角色更偏代码实施者。

### 额外读到的（污染）

- 整份 `skills/spec-specify/SKILL.md`：四标签的强制性、Appendix A 唯一权威、PFACT 四状态、canonical ID。这些不是十一条，但我的 spec 片段用了。
- 系统提示里的 `AGENTS.md`/`CLAUDE.md`：独立审查、证据、阶段、质量裁决等背景。

## 6. 结论：三样东西够不够？

**够写出形状，不够稳定写出效果判据。**

- 一个仔细的陌生人，拿着三份模板和十一条，能写出结构完整、字段齐全、看起来有场景/环境/谁判/承接的 decision-log、spec、phase。
- 但他不会自动知道：
  - 「效果」指什么；
  - 要用绿而错负控来证明验收有区分力；
  - 负控由谁造、判定者要多独立；
  - 语义判定怎么过「一条命令重放」的机器合同；
  - 「每个 Phase」怎么跨 Phase 覆盖；
  - 决策日志和 spec 谁拥有 AC、谁更新索引；
  - 8 值档位、`test-asset-governance` 的好坏例是什么。
- 模板的示例是代码行为 AC，不是效果级 AC；模板的机器合同奖励「能跑的命令」，不奖励「能判效果的语义判据」。所以陌生人最可能写出两种东西：
  1. 一份「行为断言通过」的 AC，自己以为这是效果；
  2. 一份像我这样自造盲判/消费者协议的 AC，但最后 `gate_cmd=unavailable`、`Done=incomplete`，过不了机器合同。
- 这不是作者不努力，是三样材料里缺了「效果判据的默认方法」和「语义判定的合法位置」。

## 7. 要让下一个陌生人稳定写出来，最少要补什么

1. **定义「效果」**：用户可观察结果、下游消费者完成、业务指标，三者分开；每个 Phase 选一个并写清。
2. **给默认方法**：绿而错负控 + 独立盲判 + 真实消费者用一次；或者项目认可的替代（mutation、metrics、用户观察）。不要只给「反向场景」四个字。
3. **给 AC 记录加一等槽位**：判据、成功、失败、环境与数据、谁判（含独立性与时点）、消费者、承接；不要让作者折进 `验证`/`证据`。
4. **让语义判定合法**：`gate_cmd` 对「只能人读」的 AC 允许 `unavailable` + 结构化答卷，不强迫伪造命令；`Done` 的「一条命令」只对 `机器可判` 的 AC 生效。
5. **加跨 Phase 覆盖**：非末 Phase 声明「只证第 N 行」，末 Phase 逐行收口；模板给一个行表，不要只给「覆盖 AC」ID 列表。
6. **补外部权威**：把 `test-asset-governance-rules.md` 的「验收标准可执行形式」节、8 值档位词表放进允许材料，或明确说不需要。
7. **换示例**：给一条效果级 AC 的好例和坏例，坏例是「所有门禁绿、用户结果错」；不要只给配置报错/PROCESS_STALLED。
8. **解决 AC 所有权**：decision-log 的验收面与 spec Appendix A 谁写、谁改、何时同号；给一个单一 writer。
9. **支持非代码任务**：给材料/流程任务的验收对象、任务卡、证据形状；不要强迫 UI/CLI 或 RED/GREEN。
10. **说明最小可写集**：哪些 unknown 可接受、哪些必须真实；否则陌生人会在几十个 unknown 里不知道算不算写完。

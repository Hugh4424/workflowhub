## 这是什么，给谁用？

给 Phase 作者和独立验收者一条能判效果的验收要求；它约束 Phase 材料怎么写、怎么被判，不改变产品行为。

- **功能名**：Phase 验收的效果判据
- **来源**：R-001，用户 2026-10-30 任务书逐字引用；真实消息未提供
- **状态**：草稿；试点 Phase、环境与判定者未核实

## 一页看懂：谁要什么结果，怎么算通过？

Phase 作者要写出这样的验收：独立判定者只读验收和原始需求，就能拒绝绿而错；真实消费者用一次，得到要求的结果。

- **需求 1**：每个 Phase 的验收要能让没参与实现的人判「做没做对、有没有效果」，不能只以契约测试、门禁命令、判定器、断言、回归通过作为完成。
- **最大影响面**：build-plan 的 Phase 材料、build-code 的独立验收、最终验收 Phase 的逐条结论。
- **验收信号**：盲判中真实交付被接受、绿而错变体被拒绝，理由指出用户可观察差异；消费者得到要求的结果且不需作者解释。
- **非目标**：不改变产品功能；不新增测试框架；不把试点结论当全部 Phase 结论；不证明跨任务长期效果。

**术语**（首现解释，后文同义）：

- **绿而错**：所有已列门禁、契约测试、断言和回归都通过，用户可观察结果却错的交付。
- **盲判**：判定者不知道两份交付哪份是真的，只按验收和原始需求判。
- **红队**：独立构造绿而错变体的人，不看作者写的验收，防止照着验收做错。
- **消费者**：真实使用该 Phase 结果继续工作的人或下一 Phase 的 owner，不是作者或实现者。
- **做对**：交付能通过盲判，绿而错被拒绝；**有效**：真实消费者在真实场景中得到要求的结果。

## 为什么做，给谁用？

默认的「命令绿了就算过」只能证明做了，不能证明做对；读者会在验收记录里看到通过，却拿到错的结果。

### 需求 1：每个 Phase 的验收要能判「做对」和「有效」

Phase 作者在 build-plan 为每个 Phase 写验收时，要写清用户可观察结果、成功信号、失败信号、场景、环境与数据、用例、判定者和消费者；
  独立验收者在 build-code 末期只读这些内容，就能判该 Phase 的原始需求有没有达成。

- **角色与场景**：Phase 作者写验收；独立判定者判「做对」；真实下游消费者判「有效」；两者都在实现完成、审查问题修完后判。
- **真实输入**：该 Phase 的原始需求逐字文本、真实交付、独立红队构造的绿而错变体、真实环境与数据、盲包与答卷、消费者场景与基线。
- **可观察结果**：判定者在不知道标签时正确认出两份交付，并说出用户可观察差异；消费者在真实场景中得到要求的结果，且不需作者解释。
- **失败**：判错、全收、全拒；
    理由只写命令通过或字段齐全；
    需要作者解释；
    绿而错变体过不了门禁；
    消费者是作者或实现者；
    消费者只复述命令；
    改了既有行为却没有基线。
- **消费者**：build-plan 作者、build-code 独立验收者、最终验收 Phase、试用该 Phase 结果的下游 owner。
- **证据类型**：盲判答卷、两份交付与哈希、红队构造说明、全部门禁原始输出、拆封记录、消费者观察记录，各一份原件。

**范围说明**：本条按「本任务 build-plan 产出的每个 Phase」执行；跨任务推广不在本条证据范围，记显式不覆盖。

## 做成什么样？

每个 Phase 的验收都要经一次盲判和一次消费者使用，两层都过才算通过；完整判据在 Appendix A。

## 打算怎么做？

复用现有 Phase 材料与 build-code 独立验收，不新增测试框架；只加效果判据、绿而错对照、盲判和消费者观察。

### 方案 1：在现有七槽上补「做对」与「有效」两层

- **做什么**：Phase 作者在七槽里写清用户可观察结果、成功与失败信号、环境数据、绿而错对照、判定者与消费者；
    build-code 独立验收者按盲判和消费者观察判。
- **为什么这样**：只加字段不改判定，验收仍会退化成门禁检查；加绿而错对照和真实消费者，才能判做对与有效。
- **怎么验**：每个 Phase 一行；红队造绿而错变体，判定者盲判，消费者用一次；两层都过才算通过。
- **失败怎样**：控制无效、盲判泄露、消费者不独立或只复述命令时，记 `incomplete` 并回对应 owner，不用门禁绿冒充效果。

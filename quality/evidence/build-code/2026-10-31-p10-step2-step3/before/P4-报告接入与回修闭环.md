# Phase P4 — 把页面审计接进 build-code 的冻结前与终末，并把报告消费与回修闭环写成可执行契约

读者：本 Phase 的实施者、独立审查者，以及下游的编排与末验收两个 Phase。
读完要能：知道十三个受管路径各改什么、凭什么判红绿、红了交给谁、本 Phase 不签什么。

> 写作标准：用户十条标准，原件指针见「开始前读什么？」表末行。
> 二级标题都是读者问题，第一句直接回答；命令与表格行不受行宽限制。
> 命令、路径、退出码、编号、哈希逐字保留，不因改写而改。

先说明十个会反复出现的词。

页面审计：在真浏览器里打开一个页面，按判据取事实、记四态的那套动作。
冻结：build-code 收尾前把当前审查对象固定下来的那一步。
接线：在方法正文里写一句明确要求，让下游照这句话执行，而不是靠记忆。
四态：一次检查只有通过、失败、未测、不适用四种结果，没有第五种。
身份块：报告开头记工作区、服务、路由、状态、视口等八项身份的那一段。
覆盖边界：报告里列明这次没测到什么、为什么没测的那一组条目。
判定器：一个具名检查，它给出「改之前必须失败、改之后必须通过」的那条断言。
回修闭环：定位、路由、最小修复、独立复验，加一个人工停点。
分流：把报告里失败与未测的行按原件事实分类，给每类一个 owner 和去向。
契约决定：`build-plan` 原件里逐条编号的取舍；正文写「契约决定 n」。

## 这一 Phase 交出什么？

交四件东西，并在四件落定后，在自有样例上真实修一处缺陷。

交付一：build-code 三处接线——触发句、冻结前插入块、终末复核半句。
交付二：触发词扩一处，前端测试条目的适用面加上浏览器可见页审计。
交付三：审查镜头新增一节「页面审计摘要消费」。
交付四：一条静态契约测试，把弱断言加强到同句同块。

这四件之外，本 Phase 另在 C07 自有样例上复现并修一处真实缺陷。
这处修复不占任务卡号，五步与四件产物见「在自有副本上怎么修一处缺陷？」。

本 Phase 不采集页面、不产正式报告、不跑真实审计。
受控演练只做一件事：初始化一份单文件工作副本，等下游真实检出后再修。
工作包声明：本 Phase 对应 decision-log 的工作包 6、7，即回修闭环与报告接入。

改动前：页面审计只写在技能方法里，build-code 没有一句要求冻结前审一次。
审查镜头也没有读审计摘要的规则，摘要容易被当成结论。
改动后：冻结前必须审一次、终末只复核四项，都能在方法正文里逐字读到。
审查者按四态与覆盖边界读摘要，不新增字段；缺陷按五步闭环走。

与相邻 Phase 的边界：P1 先给报告形状与四态，本 Phase 只消费，不改。
本 Phase 把接线措辞交给 P5 读，把终末四项复核交给 P8 取证。

主要风险：把「冻结前审一次」写进终末段，或把四项复核写成全量重跑。
若因此返工，替代走法是触发句只留方法区一句，细节块收回覆盖句之前。

下一步：P5 按这些措辞写编排入口，P8 按终末四项复核取证。

未决事实：受控九类的检出、修源与复验都还没跑，等 P8 原链回本 Phase。

## 这一 Phase 怎么验收？

先答这一问：假设本 Phase 全部实现、所有已设计测试也都通过，还会不会漏掉原始需求？
答不出「不会」之前，任何测试通过都不算达成验收。
自有副本上真修一处缺陷，报告里的失败变成带责任方的条目。
还要看那条失败修完是否由独立角色复验，以及接线是否真让冻结前审一次。
一个 Phase 只有在验收标准真的被满足后才能说开发完成；代码审查通过、测试全绿、结构检查通过，都不是完成条件。
静态契约绿只证文本在场，不证上面任何一件，细节留在「怎么验证？」。

1. **验收标准**：逐条列本 Phase 承接的验收，各写判据、成功与失败三句。
   - 验收 5：判据是一条模糊反馈走完定位、路由、最小修、独立复验四步。
     成功长这样：定位到页面、元素、状态与 owner，原问题消失、受影响面有回归记录。
     失败长这样：修复者自签复验、凭猜盲修，或反改判据让问题消失。
   - 验收 7：判据是资产层、组件层、页面层各有可回读证据，未覆盖不被吞。
     成功长这样：三面各指到原件，无 Figma 或 Storybook 处写不适用加依据。
     失败长这样：用组件故事冒页面，或把 region 关闭、todo 当通过。
   - 验收 3 的修复段：判据是检出后的修复真实发生，修前修后可比。
     成功长这样：修前副本、修后文件、真差异、独立复验四件齐。
     失败长这样：只初始化工作副本，或只改处置字符串没改源码。
   - 验收 5 的终末段：判据是下一次走 build-code 的任务，冻结前真审一次页面。
     成功长这样：执行记录里有这次审计，终末只复核四项、不重跑全量。
     失败长这样：只有方法正文一句话，没有一次真触发；现在正是这一格。

2. **场景**：正常两例、反向三例，每个写输入、动作与预期。
   - 正常（本轮真跑）：输入是样本 A 工作台默认态、视口 640x960。
     动作是原生聚焦「图表」后按右方向键。
     预期：焦点与选中态移到下一项；修前停在原处，修后切换并首尾循环。
   - 正常二（分流）：输入是一份正式审计报告，动作是按失败与未测行做四步分流。
     预期：每行一个类别、一个 owner、一个去向，条数与报告对得上。
   - 反向一（自检会红）：输入是三行样张，动作是清空其中一行 owner 再跑。
     预期：退出非零并报出缺 owner 的那一行；本轮实际退出 1。
   - 反向二（占位修复）：输入是只改处置字符串、源码没动的副本。
     动作是按复验判据看原问题。预期：原问题仍在，判修复不成立。
   - 反向三（插入点错位）：输入是把细节块挪到冻结实现之后的文本副本。
     动作是跑契约测试。预期：被拒收；这一步只证文本，不证执行。

3. **环境与数据**：写环境、数据、谁提供、来源与清理；缺的写 incomplete。
   - 环境：本机静态服务加真浏览器；样本 A 的工作台 route，视口 640x960 与 1440。
   - 构建：改源码后用样本自己的构建脚本重建运行资产；基线构建与原件同字节。
   - 数据：样本数据是 mock，业务结论只到 mock；身份字段取注入值，不用真实账号。
   - 报告：只读正式报告，取失败与未测行；本 Phase 只有三行样张，不产真实分流。
   - 来源：受控工作副本从 P3 的受控页复制，字节与 sha 在修复一节记过一次。
   - 谁提供：样本 A、B 随材料落盘；正式报告由 P5 的生产者出；分流真跑归 P8。
   - 构造与清理：临时起服务，结束关掉；不写 C05 归档，不改别人的浏览器配置。
     改 `move-map.json` 只做两条单条登记，登记完立刻交还写权。
   - 拿不到：真实报告在 P5 之前不存在，这一格记 incomplete，不拿样张冒真分流。
     受控九类的检出、修源与复验没跑，这一格也记 incomplete，负责方是末验收。

4. **用例**：六条用例，逐条给对应验收、操作、预期与判定方式。
   - 用例一（对应验收 5）：按修前、修后同一操作重放，看焦点与选中态。
     判定：修前无效、修后切换且首尾循环；diff 退出 1 只说明有差异，不是判定。
   - 用例二（对应验收 5·分流）：取一份正式报告跑四步，出清单与派生条目。
     判定：报告条数、派生条目数、清单行数三者相等，类别与 owner 齐全。
   - 用例三（负控·自检会红）：三行样张正例一次，清空 owner 的反例一次。
     判定：正例退出 0、反例退出 1 并报出那一行；两次原件都要回读。
   - 用例四（对应验收 7）：三面各取一件可回读证据，核未覆盖项在报告里。
     判定：三面都能指到原件；无资产处写不适用加依据，不写通过。
   - 用例五（验收 5 终末段）：按 build-code 走一次带可见面的任务，读执行记录。
     判定：记录里真有冻结前那次审计；只有正文与契约绿不算，这一条现在未取得。
   - 用例六（负控·文本）：挪插入点、删「四项」、把触发词改回旧词，各跑一次门禁。
     判定：三类各被拒；命令见「怎么验证？」，它只证文本在场与位置，不证执行。

5. **谁判**：修复与分流换两拨上下文，都不与改稿的人同会话。
   - 修复判者：原独立角色，与修源的人不同上下文；本轮它已关闭三具名发现。
   - 分流判者：独立审查子代理，读报告与清单，不读开发者的自述。
   - 时点：开发完成、审查问题改完之后才判；修完就自签的结论不算。
   - 判者不改方法正文、不改判据、不补 region，只按原判据读原件。
   - 本 Phase 只接修复段与接线措辞，七条页面验收的终验仍归末验收。

6. **失败回修与重验**：失败信号、分诊、回 owner、重验与结论更新各一句。
   - 失败信号：修了原问题仍在、复验由修复者自签、清单条数与报告对不上。
     另一类信号是终末被写成全量重跑，或受控九类只有初始化没有检出。
   - 分诊：由独立判者或主会话分；正文问题找方法 owner，口径问题回本 Phase。
   - 回 owner：正文回方法 owner；判据键名回 P1；受控修源回本 Phase 同一会话。
   - 重验：原问题与受影响面重放（两宽方向键回归、被改章节的合同断言）。
     受控链按「发现回本 Phase、最小修源、归还写主、重载」的顺序走，越序不算。
   - 结论更新：只按新原件改档位与 Done；原失败、旧绿与旧 review 都保留。
   - 重报：独立复验者重报，修复者不自签，主会话只核四项。

7. **承接**：结论落在本文件的状态行与具名原件上，下游照这两处读。
   - 状态：写进文末 Done 与「什么时候能说这一 Phase 做完了？」的四项核对。
   - 原件：`quality/evidence/build-code/2026-10-29-155-p4-wiring.json` 与修源差异件。
   - 另三件是修前副本、修后文件与差异记录，第四件是独立复验记录。
     四件都落 `quality/evidence/build-code/`，缺一件按 incomplete 记。
   - 下一消费者：P5 读接线措辞并产正式报告；P8 恢复真检出，发现回本 Phase 修源。
   - 读状态去 Done 与「下一消费者拿什么继续？」，读做法去修复与分流两节。
   - 本 Phase 不把静态契约的绿写成执行效果，也不替末验收签页面结论。

## 为什么现在做，依据是什么？

编排要读到「什么时候必须审」的措辞，末验收要按终末四项取证，所以先落这两处文字。

结果：三句话都能在方法正文里逐字读到。
三句话是：冻结前审一次、终末只复核四项、审查镜头按四态读摘要。
非目标：不改判据正文、不改报告字段、不新增第 13 步，也不替 P8 做终验。
与其它 Phase 的区别：P1 定判据与形状，P5 定编排入口，P8 定终验。
本 Phase 只定三件事的措辞：什么时候必须审、审完怎么读、坏了怎么修。

依据是契约决定 9、10，加规格里的验收 5 与验收 7。
契约决定 9 给九类映射与报告表达，契约决定 10 给审查怎么读摘要。
两份原文都在 `build-plan` 的 004 原件里，读法见「开始前读什么？」。

方法接线依赖 P1 的报告形状。
样例回修另依赖真实构建、静态服务与浏览器观察。
它不等待编排完成，也不把开发观察当独立验收。

## 报告里的失败行怎么变成带责任方的清单？

按原件事实把失败与未测的行分成四类，每类一个 owner 和去向，条数要对得上。

验收 5 要「定位到页面、元素、状态与 owner」。
只写文字不算，这一段给可执行的步骤。
它不改任何判据，也不碰报告生成端。

输入只读正式审计报告 JSON，由 P5 的实际 producer 回执定位原件。
取唯一 `criteria[]` 中 `state` 为「失败」或「未测」的行。
真实环境失败由其依赖判据与 `coverage_limits[]` 承接，保原失败引用。
不把不适用理由混入失败加未测的条数。

四步，按顺序跑。

第一步，定位：先按正式形状核报告，再逐行输出对象与判据事实。

```sh
node -e 'const r=require(process.argv[1]);if(!r.object||!Array.isArray(r.criteria))throw new Error("report shape");for(const c of r.criteria.filter(x=>x.state==="失败"||x.state==="未测"))console.log(JSON.stringify({id:c.id,dimension:c.dimension,criterion_state:c.state,page:r.object.route,page_state:r.object.state,viewport:r.object.viewport,evidence:c.evidence}));' <报告>
```

由各 `evidence[]` 的原件补元素、文件行与根因。
没有观察就写具体未取得，不能从 ref 路径猜事实。
分流的 `items[]` 保上述来源、定位与后续类别、owner、去向。
它是派生清单，不改原报告。

第二步，分类：按原件事实只选一类。
- 一、代码缺陷：原页面失败已定位到代码 owner。
- 二、运行诊断：原件证明 `NOT_STARTED`、`UNREACHABLE`、`TOOL_ERROR` 等执行失败。
- 三、设计源缺口：所需设计源不可读。
- 四、判据或规范缺口：`norms_missing`，或判据正文缺项。
原件不足以定类时保 `incomplete`，写缺证与承接者，不为自检猜类别。

第三步，路由：四类各有一个去处。
- 代码缺陷 → 原代码 owner，在本 Phase 已准副本与必要源补集回修。
- 运行诊断 → 环境 owner，与 P8 的环境就绪、真实执行组。
- 设计源缺口 → 设计 owner 补源。
- 判据或规范缺口 → P1 判据 owner；规范类另给 P5 的未测行任务。

第四步，产出分流清单：用认证普通记录保存 JSON 与 Markdown 原件。
后续引用实际原 ref；Markdown 的列顺序如下。

`id | 类别 | owner | 去向 | 证据 ref | 处置`

`items[]` 条数、清单数据行数与报告失败加未测条数三者相等。
少一条记 `incomplete`。

可核判据三条，缺一条这一段不算做完：
一、条数相等：报告失败加未测条数 = `items[]` 条数 = 清单行数。
二、无人空转：每行 `类别` 是四类之一，`owner` 与 `去向` 非空。
   类别与 owner 的对应要符合第三步那张路由表。
三、自检会红：造一份三行最小报告样张，跑一遍得三行清单。
   三个 owner 各不相同时才算正例；把其中一行的 owner 清空再跑，退出非零。
   样张与两次自检输出都以实际认证原件回读。

本轮三行校准产物是三件，路径见附录 C。

两次都是 3 条判据、3 条派生项、3 行清单。
反例报告 `owner/route gap: CAL-CODE`。

不冒真实报告或页面裁决。

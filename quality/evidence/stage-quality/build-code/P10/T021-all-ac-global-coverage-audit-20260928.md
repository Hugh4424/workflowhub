## 全局唯一验收 Task：最小可行合同

1. **先由 build-plan owner 指定一张全局 Task，不缩成 P10 的三条。** 现有 post 解析器跨所有 indexed Phase 寻找**恰好一张** `acceptance_role=acceptance`、`acceptance_data` 卡；当前一张也没有。它把卡的所有 AC 复制给每个场景，尚不支持逐场景 AC 子集。应在材料中登记全部 19 条的场景与责任来源；多个子场景共同覆盖一条时，必须全核，不准其中一个通过就整条通过。P10/T021 的七行候选只涉及 AC-26/27/33，且独立审查已判不能直接使用。可以把唯一卡放在 P10/T021 承载全局声明，但这**不改变执行时点**，也不能夺走 P6/P7/P11/P12 原责任。
2. **阶段内采可取得的原始执行证据，缺后置事实保持未完成。** 目前每次官方 build-code handler 都读所有 Phase 的验收卡；若声明全局卡，早期运行也会触发。真实 `command/service/browser` 场景只能报告当时可见的事实。子进程 stdout 里的 `expected=actual` 由同一进程自填，须由独立规则/读者从原始业务输入和输出重算，才可采信通过；运行成功不是业务通过。没有来源、旧基线、页面或消费者时保留 `unknown/unavailable`。若改逐场景 AC 子集，解析器、覆盖计算和单叶补源读路都要加失败负控。
3. **阶段发布后再做独立只读核验，确实需要前后两段，但不新增公共 stage、gate 或进度账本。** AC-26 的本次 `stage_end_spec_analyze` 在 handler 返回后才发布，P5 报告又在 `runStage` 返回后产生；同次场景子进程不可能读未来事实。第一段保存执行原件和当时的逐 AC 未完成状态；第二段在正式阶段行、分析事实、报告与必要独立审查实际发布后，按同 Task、材料、树、来源 ref/hash 只读核对，另判断后置场景。必须明确“这次”或“前次同身份”的来源，不可拿旧报告冒充本次。最终全 19 条只在 P1–P12 各自真实场景和 P13 聚合核齐、verify-code 独立审查与授权答复完成后判定。后置读回若要改变先前逐 AC 判决，应由材料 owner 设计并验证现有事实写入顺序；不能先写 `passed`、事后只补一份说明。

**最关键阻塞：** 全局验收 Task 缺失；现有运行器会过早执行且用子进程自报值判断；AC-26 报告只能后读；AC-27 旧字节基线缺独立旧见证；AC-33 大量变化未映射、完整旧失败→新复测链缺失。P11 页面真实消费者和 P5 真实报告也未确认。局部测试或样例不能填这些空。

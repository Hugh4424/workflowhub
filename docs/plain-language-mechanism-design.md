# WorkflowHub 大白话人机交互 + Handoff 累积 · 落地方案

> 目标：解决三个问题——(1) 向人提问全是术语；(2) 人工确认缺大白话总结摘要；(3) handoff 不累积上游。
> 原则：全程不设阻断式质量门（宪法 F3/F4/F5/Q1/Q2/Q3）。质量靠 3rd-review 异源审查 + 人拍板，机器只记事实不卡。

## 一、总体模型：三 gate 两 auto

五阶段分两类：

- **决策 gate（停下等人拍板）**：make-decision、build-plan、verify-code。人看大白话决策摘要，选"继续 / 返工 / 暂停"。
- **自动放行（不停，给人瞄一眼）**：build-spec、build-code。输出大白话进度汇报摘要，自动接受本阶段结果并进入下一阶段。审查结论、测试结果和未解决项原样记录；可自动修复的继续修复，审不了或暂时修不完也不增加中途人工门，而是在下一个决策 gate 集中呈现。

| 阶段 | 人拍板 | 质量把关 | 摘要类型 | 进入下一阶段 |
|---|---|---|---|---|
| make-decision | 是 | 方向审查 | 决策摘要 | 人点继续 |
| build-spec | 否 | 3rd-review | 进度汇报 | 自动接受 |
| build-plan | 是 | 3rd-review | 决策摘要 | 人点继续 |
| build-code | 否 | 3rd-review | 进度汇报 | 自动接受 |
| verify-code | 是（接受验证结论） | 测试 + 3rd-review | 决策摘要 | 人点继续；close 另授权 |

要点：

- 摘要**不是审查门**，纯给人看进度 / 拍板，不判质量。
- 决策 gate 停下等的是**人点头（人工确认，合宪）**，不是"摘要字段缺了机器自动卡"。
- 自动放行阶段：审查 finding 能自动处理就处理并重审；pass/revise_required 等已取得的质量事实如实带到下一个决策 gate，不伪造 pass，也不在中途卡人。若独立审查能力本身不可用，明确记诊断并 blocked；用户点头不能替代缺失的异源审查。

## 二、大白话摘要（问题 1 + 2）

### 2.1 Stage 自包含，两种用法

每个 Stage SKILL 直接写明四项大白话要求：当前状态；下一步和负责人；用户是否需要操作；
需要操作时的问题、推荐选项及每个选项的后果和风险。`docs/human-brief-template.md` 只保留为
维护者参考，不是 Agent 运行时依赖。

- **make-decision**：使用本 Stage 自包含的决策摘要和“请确认”块。
- **其余决策 gate**（build-plan/verify-code）：四项后加“请确认”块（继续/返工/暂停 + 每项后果）。
- **自动放行**（build-spec/build-code）：只写四项，不带"请确认"，结尾说明阶段已完成、将自动进入下一阶段，并原样列出审查事实和未解决项。

硬规则（直接写进各 Stage SKILL）：

- 全大白话中文，高中生能懂。
- 禁止出现内部产物名/字段名/编号。要提就翻成人话。
- 给选项时每个选项写清"什么意思 + 选了会怎样"，并标推荐项。

### 2.2 提问场景（问题 1）

agent 中途要问人时，问题按"请确认"块格式走：大白话问题 + 2–4 个选项（各含含义 + 后果）+ 推荐。禁止甩术语问题。
注意：agent"意识到该问人"这步无法机器强制，靠两手——① SKILL.md 把"哪些情况必须问人"列成明确清单，减少自由裁量；② 3rd-review 抽查"该问没问"，作为事实浮现。

### 2.3 五阶段各改哪一步

- **make-decision**：保留人确认（S9）。结尾按本 Stage 的具体合同输出决策摘要。
- **build-spec**：去掉强确认门。输出进度汇报摘要，自动接受阶段结果并进入 build-plan；审查异常和未解决项作为事实带到 build-plan gate。
- **build-plan**：保留人确认（Step 9）。结尾输出决策摘要。**删掉违宪句**（见 2.5）。
- **build-code**：不设每 Phase 或收尾人工确认。输出进度汇报摘要，自动接受阶段结果并进入 verify-code。
- **verify-code**：保留阶段确认，用来接受验证结论。阶段接受后另行冻结 close 动作计划；commit、push、merge、archive、cleanup 必须取得绑定计划 hash 的独立授权，不能复用 verify-code 确认。

### 2.4 机器事实采集（已推迟，不是本次交付内容）

本方案**不做**机器事实采集脚本。原设想是加一个 cheap 脚本，在每次产出人向摘要时扫"摘要是否存在""有没有漏内部术语"，写进统一执行记录（形如 `facts.human_readability: { summary_present, machine_verdict: "not_judged", ... }`）。

独立异源审查（Codex）发现这个设想在集成时会引入真实 bug（写入的 `facts.human_readability` 被另一个不相关的 metrics 采集器不做合并直接覆盖，外加 CLI flag 缺失、字段归属不清等问题），且用户确认这不是本次直接要的东西（宪法 F5/F10：不预置机器自动化，等真出现复用痛点再加）。

因此本次交付范围只有：大白话摘要模板 + 三 gate 两 auto 模型 + handoff 累积（第一、三节）。机器事实采集列为**明确推迟的非目标**，不在本次落地——若未来出现真实、反复出现的问题（例如摘要经常缺失或反复带术语），可以再单独立项设计采集机制，但需重新解决字段归属和写入合并的问题，不能照搬本节原设想。

### 2.5 要删的现存违宪句

`build-plan/SKILL.md:296` 现有一句"这个摘要是人工放行的依据，必须包含，缺少则 stage 不完整"——这是隐藏的必填门。改成：
> 该摘要用于人工确认。若缺失，在阶段边界显眼提示，由人决定继续/返工/暂停，不因摘要缺失自动阻断 stage-result。

### 2.6 质量归 3rd-review（不新增门）

质量把关全部交给已有的 3rd-review 异源审查（build-spec/build-plan/build-code/verify-code 都挂）。摘要机制**不碰质量判断**。异源审查可顺带在给人的意见里带一句"这段是否够大白话"，但那是审查意见，不阻断。

### 2.7 不新建技能（避免过度设计，S4/F5）

不做 human-brief 独立技能或运行时共享模板依赖。每个 Stage SKILL 只保留上面的四项窄规则，
避免跨宿主打包遗漏；`docs/human-brief-template.md` 仅供维护者查看更完整的写法参考。

## 三、Handoff 累积（问题 3）

固定链，不造累积字段（宪法 F2 窄契约 / F8 简单优先 / F10 不堆基建）。缺口具体、就补具体两处：

- **build-code** `SKILL.md §1 前置读取`：加一步无条件读 `specs/{task-id}/spec.md` + decision-log，作为 plan.md/tasks.md 之外的补充。
- **verify-code** `SKILL.md §1`：加一步读 spec.md 的验收标准 + plan.md + decision-log。
- 顺带修 bug：verify-code 说明称"读 spec 验收标准"但步骤没落实——上面这步正好补上。
- build-spec 已有的"下游必读清单"字段留作参考，不作为主依赖。

现状对照：make-decision→(decision-log)；build-spec 读 decision-log（已对）；build-plan 读 spec+decision-log（已对）；build-code 补读 spec+decision-log；verify-code 补读 spec+plan+decision-log。

## 四、落地顺序

1. 先做问题 3（改 build-code/verify-code 两个 Step 1，独立、最小、顺带修 bug）。
2. 在各 Stage SKILL 内写入四项大白话规则。
3. 改五阶段人向边界：build-spec 去门、build-code 加自动摘要、三 gate 阶段使用各自的自包含规则、删 build-plan:296 违宪句。
三步互相独立，可分批交给 executor，每步独立验证。

## 五、明确不做（守宪法边界）

- 不设"摘要缺失/不合格就卡 advance"的机器门。
- 不给机器 machine_verdict 写 pass/fail。
- 不把摘要必填写进 schema 当硬门。
- 不给每个 phase / 每轮审查都绑大白话 checklist（违 F5 轻量）。
- 不为模板新建技能。

## 附录：大白话摘要示例

### 示例 A：决策 gate 阶段（build-plan，停下等人拍板）

```
给志鹏看的进度汇报 —— 排计划阶段

1. 这阶段做了什么
把"记住我"功能的技术方案拆成了可执行步骤清单，一共 6 步，排好了先后顺序。

2. 审了几次、结论是什么
异源审查（第三方）过了 2 轮。第 1 轮提了 3 个问题（没考虑退出登录时清凭证、没定凭证有效期、少一个测试点），都改完了。第 2 轮通过。

3. 这个 task 要解决什么
用户每次访问网站都要重新登录，很烦。要做到：勾选"记住我"后，30 天内不用重复登录。

4. 准备怎么做
登录成功后发一个 30 天有效的凭证存在浏览器；下次带着凭证自动认；退出登录时清掉。分 6 步，先做凭证生成和校验，再接登录流程，最后补退出清理和测试。

5. 原始需求覆盖情况
你最初要的"记住登录状态""能手动退出""安全不被盗用"三点都覆盖了。额外加了一条"异地登录提醒"，是审查建议加的，你可以要也可以不要。

6. 现在结果
方案和步骤清单都出好了，审查通过，可以开始写代码。

7. 下一步
进入写代码阶段，按这 6 步实现。

请确认：
- **推荐：继续** —— 后果：进入写代码阶段，按这份计划实现。
- 修改后继续 —— 后果：告诉我哪里要改，我改完计划再来找你。
- 暂停 —— 后果：先不往下走，方案和清单都留着。
```

### 示例 B：自动放行阶段（build-spec，不停，给人瞄一眼）

```
给志鹏看的进度汇报 —— 需求规格阶段

1. 这阶段做了什么
把"记住我"功能要满足的具体要求写清楚了，一共 12 条，配了 8 个验收标准（怎么算做好了）。

2. 审了几次、结论是什么
异源审查过了 2 轮。第 1 轮指出漏了"退出后凭证要失效"和"凭证有效期没定死"，补上了。第 2 轮通过。

3. 这个 task 要解决什么
用户每次都要重新登录，很烦。要做到勾选"记住我"后 30 天免登录。

4. 准备怎么做
这阶段只定"要做成什么样"，不写代码。下阶段才排实现步骤。

5. 原始需求覆盖情况
你要的三点（记住状态、能手动退出、安全）全写进要求了，没遗漏。

6. 现在结果
需求规格写好、审查通过。

7. 下一步
自动进入排计划阶段，把这些要求拆成可执行步骤。

本阶段已通过异源审查，自动进入下一阶段。以上仅供你了解进度，无需操作。
```

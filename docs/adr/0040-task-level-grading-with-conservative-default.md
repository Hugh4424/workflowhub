# 任务按四级分级，默认档走重

## Status

accepted（2026-10-14，make-decision 阶段，任务 `skills-framework-redesign-20261014`）

WorkflowHub 此前对所有任务都走同一套五阶段全流程，而实测一个普通任务要 47 步、
23 个必读技能文件（236,253 B）、11 类产出目录、最少 3 次人工确认。我们决定在
`make-decision` 入口把任务分成四级（小改动／普通任务／复杂任务／规划任务），
每级绑定一张技能矩阵；判据**只用入口真实可得的事实**（用户的任务性质声明 + 风险事实），
拿不准时**往上抬一级**。入口**主动给出一个建议档位并高亮推荐项、同时给出建议与理由**，
由用户选择（2026-10-14 修订：不是静默默认，而是可见的推荐；
推荐项按保守原则给出，因此与"默认走重"相容）。

## Considered Options

- **默认走轻 + 风险信号硬性抬级**：省得最多，但外部 8 家主流 agent 框架没有一家在入口做
  自动分级，也全部没有公开误判率——判级可靠性无先例，漏掉一类风险就会误走轻路。
- **不自动判，每次问用户一句**：判得准，但每次任务的交互成本固定增加。
- **用数字阈值机械分档**（如"改 N 个文件即某级"）：可预测，但数字看不出"改动小但影响大"
  （改一处权限判断），且用户明确不接受数字阈值作为判级判据。

## 三项判据

1. **难以反转**：真——它决定每个任务走多少流程，一旦有任务按错误级别做完，
   返工代价落在下游；且本决定**推翻**了
   `specs/archive/workflowhub-thin-core-rebuild-planning-20260919/prd.md:244,251`
   的 FR-03／AC-03「不存在按任务大小的自动分流」。
2. **无背景会意外**：真——后来的读者会问"为什么默认是重的那一档""为什么有四档而不是两档"，
   而代码里只看得到矩阵差异，看不到这个取舍。
3. **存在真实取舍**：真——在"省 token"与"不漏质量事故"之间明确选了后者，
   并接受由此产生的收益天花板。

## Consequences

- 省 token 的收益**不能来自默认降级**，只能来自用户显式声明级别或显式风险信号。
- 级别差异**不靠新增或删除阶段来实现**（阶段集合恒为五个，宪法禁止新增 stage），
  而是由**阶段跳过**（某一级任务不跑某些阶段）与**阶段内技能矩阵／审查档位**共同表达，
  见 `docs/adr/0041-level-differences-via-stage-skip-and-matrix.md`
  （本 ADR 原编号 0038、该件原编号 0039；2026-10-14 基线合并时顺延重编号，见纠错账 C-19）。
  **补正记录**：本行原文是"级别差异**不通过增删阶段实现**（阶段集合不可改），
  **只能**用阶段内矩阵与审查档位表达"——那是把"宪法禁止新增 stage"误推成"禁止跳过阶段"，
  方向审查 F-05／F-18 已判为方向错误（违背 R-007）；当时修了 D-003 与姊妹 ADR，
  **本件此处漏改**，2026-10-14 基线复核时补正。
- 判级依据与理由必须写进 decision-log，使其可回退、可复核。

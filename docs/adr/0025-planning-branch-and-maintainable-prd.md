# ADR 0025 — 独立规划支线与可维护归档 PRD

用户已选择让 make-decision 收敛完整需求后，由 build-prd 独立支线交付任务群 PRD，以免逐任务开发时重复解释规划；规划完成、开发完成与物理交付必须分别表达。本文只记录已选方向，整体内容已由用户批准，机器正式收尾、实施与验证未完成；本ADR保留proposed以避免将内容批准冒作治理已生效，不赋予现行 F7、发布或 close 尚不存在的能力。

依据为当前 `specs/workflowhub-build-prd/decision-log.md` 的 D4、D9、D11、D13–D17、D21、D25–D28、D32、D37、D39–D40、D42、D45–D53。D51 是本阶段最小更新 CONTEXT 与新增 proposed ADR 的明确文档写入窄授权，不是治理实施、Git 操作或整体方案批准。

## 已选边界

- **独立规划而非开发模式**（D4、D16、D37、D40、D42、D45–D47）：build-prd 只做薄编排；单个 spec-prd 拥有模板与单文档内容，先大纲／地图，再真实地图核对、适用设计与确认，最后细节成稿；必要时分组草稿，唯一整合者写正式 PRD。独立调用保持同等内容标准，不伪造平台身份、确认、发布或归档事实。普通五阶段不改，本次开发该能力的任务仍走普通五阶段。
- **确认与完成分开**（D14、D16、D25–D28、D32、D39、D46、D48）：地图核对、适用 UI 的全套高保真分组确认、最终规划确认归 build-prd；实际展示与回复绑定真实版本，旧确认不能挪给新稿。适用质量工作、一次最终独立审查、处置、交接与末尾真实复盘不得因“纯规划”省略；未返回设计、未确认、拒绝或取消保留草稿，质量缺失如实披露。规划完成不代表开发、产品发布或物理交付完成，阶段确认不带 Git 授权。
- **真实材料的物理交付**（D9、D16、D21、D39、D49、D50）：PRD 位于 `specs/<task-id>/prd.md`，随母目录归档到 `specs/archive/<task-id>/prd.md`，实际归档位置须读回。已选范围包括在现物理交付入口窄适配规划任务的真实材料集合与正式规划完成语义，不填假工程 spec/plan/tasks，不伪造五阶段或测试完成，不新增第二 close 入口、永久状态机或双写；物理动作仍独立授权、分别保留真实结果。D53 进一步明确：本次准备交付／读回必须核实新任务接力所需附件存在、可访问、版本对应，不重新做视觉质量审查、不全读背景研究；缺必要附件则报告具体材料缺口，不声称完整交付，不能用旧确认豁免当前可用性。过去真实规划完成、本次接力可用性与实际 Git 动作结果独立保留，不撤销旧事实或将已发生的物理动作伪记为未发生。
- **归档 PRD 的唯一窄维护例外**（D11、D13、D17、D48、D50、D52）：小修可直接做；已归档 PRD 的目标、权限、范围或验收承诺实质变化，由维护主会话澄清并取得此次真实用户确认，在 PRD 现有变更说明区记录新确认、变更前后承诺、来源／版本依据、受影响条款／卡及在途影响，只重核受影响地图、设计与最终稿。不强制新建任务，不回写旧母 decision-log；未归档母任务仍由当前 make-decision 写决定。新任务读取当前 PRD 并记录接纳来源；在途任务保留已接纳来源与自身四材料，不自动覆盖。旧 decision-log、确认版本、review、test、物理交付与失败事实不改；新版不得重写旧 close 的实际归档事实。D52 优先于 D48／D13 中对已归档实质修订一律回旧母日志的解释，PRD 只承载规划修订依据，不成为任意项目决定存储或第五份开发材料。本决定不授权修改旧 UI PRD。

## 后果与待实施责任

选择独立支线会影响完成含义、确认归属、来源接纳与归档读回消费者，反转需重新协调这些契约，因此值得记录；在五阶段及历史只读规则下，这一例外无背景会令人意外，且存在真实取舍，ADR 三项判据均为真。

后续获准的 build-spec/build-plan 必须细化现有 owner 与真实 consumer 的最小适配，build-code/verify-code 实现并针对性验证内容两步、独立调用、最小阅读接力、缺引用反例、UI 取消／错版本、审查及争议分流、规划收尾／复盘、归档维护与旧物理事实相容性、归档实质修订的新旧版本承诺及确认边界、必要接力附件缺失／不可访问／版本错配反例（D49–D50、D52–D53）；未实测保持 unknown，不能仅靠模板存在宣称支线验证完成。归档维护存在小修越界、来源漂移及在途影响遗漏风险，必须保留影响与确认边界，而非建设持续 tracker。

现行 F7 的 UI owner 仍限定 build-spec；本记录不改宪法或宣称该限定已更新。ADR 0013 的 mini-task 仍是不同交付概念；ADR 0014 的根目录 locator 保留历史原文，当前四材料 locator 按现行仓规为 `specs/<task-id>/`；ADR 0020 的普通开发 close 背景与物理／质量／授权分离保留，不据本文追认当前纯规划 close 已可用。历史 ADR 均不修改，也不以新增 ADR 扩大实施范围。

## 未采用的替代

- build-spec 计划模式、只报告文件产出或不集成的独立建议技能：不满足已选独立规划完成与确认责任（D4、D16、D39）。
- 肥 build-prd 本体或拆成两个 PRD 内容技能：前者膨胀上下文，后者割裂单文档模板与作者责任（D37、D40、D42）。
- 只交内容并延期真实材料 close 适配，或填三份假工程材料迎合读取：不满足真实规划交付及不假完成要求（D50）。
- 归档一律只读另开重规划、所有小修都确认、每次恢复全文比对或自动覆盖在途：分别增加不必要任务／确认／读取成本，或破坏已接纳范围；因此选择有依据、承诺变化先确认的窄维护例外（D11、D13、D17、D48、D52）。
- 归档实质修订必须由范围匹配的合法当前任务写 decision-log、否则不落承诺：未采用，D52 选择维护主会话真实确认并记入归档 PRD 变更说明，避免强制新任务；代价是需明确版本适用边界，防止例外扩成通用决定存储。
- 核心文件交付即可称完整、必要附件缺口仅另报：未采用，D53 要求完整交付前核实必要附件可用性；成本限定为必要引用检查，不扩大为全套质量复审。

# 单个技能目录的可搬运判定标准

## Status

accepted（2026-10-16，make-decision 阶段，任务 `n2-skill-catalog-portability-20261016`）

「搬得走」的判定口径定为**单技能目录粒度**：把一个技能目录复制到仓库之外的空目录后（1）指向**外部来源**的引用必须写成「来源仓＋技能名」，不依赖副本内有没有那份外部内容；（2）指向**本仓技能**的引用如果副本内没有，正文必须写明依赖了哪些同仓技能，且与登记一致；（3）没写明、或引用明显指向不存在的文件即判失败。
**不要求技能自足**，**不接受用「按依赖闭包整体复制」替代这条判定**，不为对齐别的仓造空目录，不覆盖宿主的全局技能目录。

## Considered Options

- **要求技能自足**（副本内能解析正文的所有引用）：判定会被抬成「内容自包含」，落地就等于把被引内容都复制进来；用户未选。本仓确实存在跨技能方法引用，正文如实写明同仓依赖同样能满足「读得回来」。
- **按依赖闭包整体复制替代单目录判定**：明文否掉。它把判定对象退回整包粒度，答不出「单独一个技能能不能搬走」；本仓此前唯一的真搬运验证（把发布闭包复制到临时目录再 import）正是整包粒度，不是单技能粒度。
- **为对齐别的仓造空目录、或加宿主的目录映射／专属安装布局**：排除；三仓对照里这类做法属于明确不搬的部分。
- **覆盖宿主的全局技能目录**：排除，本判定只在仓库之外的空目录里读回。

## 三项判据

1. **难以反转**：真——它是本卡「搬得走」这一目标的唯一判定口径；已改正的 8 处坏引用、41 条依赖记录与正文引用对账、以及「技能不绑死单一宿主」的验收动作都以它为准，改口径要连同正文与对账结果一起重做。
2. **无背景会意外**：真——读者会问「为什么指不到本仓的引用不算失败，反而允许依赖留在原仓库」，答案在「只要求引用可解析或如实声明，不要求自足」这一句里，不在代码里。
3. **存在真实取舍**：真——在「要求自足、把依赖一并复制」与「允许写明依赖、只保证逐条读得回来」之间选了后者，代价是这条判定靠人对正文逐条读回，不是一次自动检查。

## Consequences

- **样本区分度有限**：实测按三个具名技能执行（`ui-project-init`、`stage-reflection`、`spec-specify`）；其中 `spec-specify` 自身对外引用只有 1 处，照出的问题面窄，结果里须如实说明，不能拿三个样本称判定已被充分检验。
- **判定前提是引用写法规则**：本仓技能写仓内相对路径，外部来源写「来源仓＋技能名」，不得写成看起来像本地路径的样子；8 处指向本仓不存在技能的坏引用改正之前，判定不可能通过。
- **依赖记录只写在清单里不算数**：判定看的是副本正文；依赖记录须与正文一致（41 条依赖记录改真，并与正文 51 处引用逐条对账），留一次真实对账读回。常驻的机器对账归后续负责检查器接线的卡。
- **写入判定保持人工读回规则**，不新增停机门、机器硬拦截或退出码变化；读不到目标按既有行为规则停手问人。
- 「技能不绑死单一宿主」由修好的宿主守卫测试与本次搬运实测两个真实动作承担，不在本判定里另立门。

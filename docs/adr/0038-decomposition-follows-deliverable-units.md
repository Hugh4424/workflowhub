# 0038 — 分解依据由交付单元决定

原先 Phase 边界由物理文件唯一所有权决定：每个实现路径全任务只有一个所有者，写面互斥被当作拆分的判据。真实计划里这会把一组必须顺序改动、同属一个交付结果的路径强行打散成多个 Phase，并在末端堆出无法并行的大块。决定改为：**Phase 边界由「可独立交付验收单元」决定，写集降级为申报结果**；同一并行批次内同一路径仍互斥，跨批次可以先后写同一路径，前提是依赖图上有真实边固定先后；每个 Phase 在自己的契约头申报写入集，跨批次重叠的路径在与相邻 Phase 的边界处点名先写者、后写者与依据。粒度规则同时补上「何时应当并」的另一半：共享同一条判据、判定必须看到对方的产出、必须一起交给同一真实消费者、拆开后各自无外部可观察变化，任一成立即应当并。

## 否掉了什么

不新增数字阈值或最少 Phase 数校验；不按路径前缀豁免；不新增运行时豁免种类 —— 既有 `serializedPair`（`runtime/stage/stage-content-contracts.mjs:393`，见 [ADR-0036](0036-write-set-governance-exemption-and-serialized-sharing.md)）本已允许依赖祖先—后代关系的 Phase 共享实现文件，本条与该判定同构。

## 后果与风险

失去「全任务静态零重叠」这一可机器验证的强保证，换来更短的关键路径与更少的 Phase。真实并发冲突仍由既有的 `git diff --name-only` 与声明写集的独立审查兜底；串行判定只读取索引里的依赖声明，不能证明实际执行顺序一致。若规则再次只被当作参考而不被执行，本条接受「只靠可见性与既有审查」，不因此新增门禁、校验器或账本。

来源：`design-execution-efficiency-20261014` 的 decision-log D-012／D-013（用户 2026-10-14 裁定），模块设计原件 `module-design/M2.md`。

## 三项判据

- **难以反转**：真 —— 它改变的是 Phase 边界的判定依据；回退会让一批必须顺序改动的路径重新被判成多个 Phase，代价立刻回到末端巨块与长依赖链。
- **无背景会意外**：真 —— 后来者看到一个文件被多个 Phase 先后修改，若不知道「写集只是申报结果、先后由依赖边固定」，会以为写面治理失效。
- **存在真实取舍**：真 —— 放弃了「全任务静态零重叠」这一可机器验证的强保证，换来更短的关键路径与更少的 Phase；替代方案（只放宽到整条链唯一、只改粒度规则、加字段与校验器、设数字区间）已逐条评估并拒绝。

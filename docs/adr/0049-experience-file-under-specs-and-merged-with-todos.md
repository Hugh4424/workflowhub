# 业务仓经验文件放在 `specs/` 下，并把经验与未解待办合成一份

业务仓的阶段经验与未解待办，统一写到**业务仓根下 `specs/Improvements.md`**，一份文件同时承载"能改变下次行动的经验"和"仍需人决定的未解待办"，按该仓自己的模块分节、每节一张小表；文件不存在就创建，存在就追加并读回；仓根旧位置的文件直接删除，不留占位。

这与本仓此前的两种直觉做法不同：一是"写在工具仓根"（旧路线，会让别的项目永远空着），二是"业务仓根"（父任务 D-012 的原始位置）。改成 `specs/` 的理由是位置契约要跨项目一致：本仓已有 `specs/` 放任务材料，业务仓也普遍有 `specs/` 或等价设计材料目录，经验跟设计材料放一起比放仓根更容易被下一个维护者看到。代价是仓根不再有显而易见的入口文件，所以本仓与论文仓都在各自的**项目规则文档**里留一行指针；漏改旧引用会让读者找不到，迁移时先全仓搜旧路径、改完再搜一遍确认零命中。

## Considered Options

- **业务仓根**（父任务原方向）：最容易发现，但与本仓把材料集中在 `specs/` 的现状不一致。
- **工具仓根**（旧路线）：不增加跨仓写入，但别的项目永远没有经验文件，等于没交付。
- **仓内 `docs/` 下**：与项目文档放一起，但 `docs/` 的职责偏规范，经验属于"待复用的事实"而非规范。
- **业务仓 `specs/` 下一份文件**：采纳。

## Consequences

- 经验文件按模块分节，写入方必须知道目标仓的模块名，不能用一个通用分类硬套。
- 判重键是"下次要改的那一步 + 现象"，来源不参与判重；同一事实重复出现只追加一行引用。
- 只有用户明确确认已解决后才清理条目；不按时间自动清理。
- 术语表新增"业务仓经验文件"并修订原"复盘候选与未解待办"条，避免两套说法。

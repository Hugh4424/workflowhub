# 大白话摘要模板（human-brief）

> 用途：workflowhub 五阶段向人输出进度 / 让人拍板时，统一用这个格式。
> 铁律：这是给人看的，不是质量门。缺了只记录、浮现，不自动卡流程。

## 硬规则

1. 全大白话中文，当对方是高中生，不用专业术语。
2. 除验收覆盖表保留 AC 编号并配大白话外，禁止出现内部产物名、字段名、编号（如 spec.md、plan-eng-review.md、escalate_to_human、worktree.json、M11/M10 baseline）。要提就翻成人话。
3. 给选项时，每个选项写清"什么意思 + 选了会怎样"，并标出推荐项。

## 七要素（所有阶段都填）

1. 这阶段做了什么
2. 审了几次、结论是什么（没有审查的阶段写"本阶段不涉及审查"）
3. 这个 task 要解决什么
4. 准备怎么做 / 已经怎么做
5. 原始需求覆盖情况（覆盖了哪些、有没有遗漏、有没有额外加的）
6. 现在结果
7. 下一步

## 质量事实怎么说

- 审查要求修改：说清楚哪里还要改、谁来改、改完会不会再审。
- 测试命令失败：说清楚跑了什么、哪里失败、现在能不能继续。
- 验收证据有缺口：说清楚哪些要求已证明、哪些还没有证据或暂时未知。
- 审查服务没有返回结论：说清楚失败原因、可追溯记录在哪里、由谁重试、何时重试或等待到什么条件，以及用户是否需要操作。
- 审查未通过、测试失败、证据缺失或审查不可用，都不得写成“已通过”。

## 简短交接区

- 阶段结果：一句话说明成功、失败或阻塞。
- 关键决定：只列影响下游的决定。
- 正式产物：列名称和位置，不复制正文。
- 测试和审查证据：列结论及可追溯引用。
- 下一阶段依赖：列下游开始前必须具备的条件。
- 未解决风险：没有就写“无”。
- 下一步：说明由谁做什么，是否需要人处理。
- 可追溯记录：只列引用；不得复制粘贴产物或日志全文。

验收覆盖固定使用下表。每项已接受的验收要求恰好一行，写编号和大白话；
遗漏项必须补成“缺失”或“未知”，不能写成“已覆盖”。

| 验收要求 | 状态 | 证据引用 | 原因 |
| --- | --- | --- | --- |
| 编号 + 大白话 | 已覆盖 / 缺失 / 未知 | 已覆盖必须有引用；其余可写“无” | 缺失和未知必须说明 |

## 两种结尾

### A. 决策 gate 阶段（make-decision / build-plan / verify-code）—— 停下等人拍板

七要素之后，加：

```
请确认：
- **推荐：继续** —— 后果：<继续会发生什么>
- 修改后继续 —— 后果：<会按你的意见重做哪部分>
- 暂停 —— 后果：<不推进，保留什么>
```

### B. 自动放行阶段（build-spec / build-code）—— 不停，给人瞄一眼

七要素之后，加一句：

```
本阶段已完成并自动进入下一阶段。审查结论和未解决项已如实列在上面，
会在下一个人工决策边界集中呈现。以上仅供你了解进度，无需操作。
```

## Close 授权不使用本模板

verify-code 的阶段确认只接受验证结果。后续 commit、push、merge、archive、cleanup
使用独立的 close 授权：逐项列出动作、目标、风险和计划 hash，不能复用阶段确认。

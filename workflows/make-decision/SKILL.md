# Make Decision

## 目标与材料

把原始需求变成用户确认的方向，写入当前任务的 `decision-log.md`。本阶段负责 Talk、必要调研、Grill 与决策正文；后续 build-plan 负责规格澄清和实施设计。读取已有材料和原始来源即可开始，历史任务与旧审查只作背景。当前 post 任务使用 decision-log、spec、独立 Phase 文件及纯指针索引；历史材料只读，不重新启用 pre 工作流。

## 方法

1. 先记录用户原话、痛点、任务类型、已知事实、假设、非目标和未决问题。任务类型不明确或互相冲突时，只暂停依赖它的问题并向用户澄清；不靠文件名或旧记录猜答案。规划任务的问题围绕用户旅程、范围、数据状态、成功失败边界、非目标与延期，工程细节交后续规划；普通任务可追问影响实现的细节。
2. 在同一决策日志整理背景、问题、目标、方案、验收、扩展，以及完整用户旅程、页面范围、数据状态、成功失败、非目标和延期。每项有原始来源或具体缺口原因，不另造一份进度账。模糊需求先比较至少两个角度和有差异的候选，说明证据、取舍和可推翻假设；大部分假设被事实推翻时重新整理方案，保留旧判断和更改理由。
3. 只研究会改变方向的未知问题。读取一手资料和当前项目事实，说明候选来源、推荐或拒绝理由、限制；跳过或无法研究写真实原因，不能把研究当用户决定。
4. 用 wh-review 做独立方向建议：检查候选、问题和来源，不替用户选择。保留原始发现、provider、失败与覆盖限制；不可用不写为空发现或通过，也不冻结同任务讨论。修复未变的建议后不为追空 findings 再派一轮。
5. 主会话把重要方向问题交给用户。一题一个决策轴，选项说明后果和风险；独立问题可合问，有依赖的等真实答复再问。使用真实询问→等待→用户回复→继续，未答、旧答或 agent 推测不当成新答复。问题数量由未决内容决定，零问题合法。
6. 选定方向后用 grill-with-docs 对照当前事实挑战方案。Grill 是交互思考，不替代审查；用户问答由主会话执行，子代理只提供研究或问题建议。把必要决策更新写回原日志。
7. 按未决问题逐模块收敛，说明方案、替代、验收、后果、风险与仍需用户决定的事项。普通细节可用公开的最小假设；方向或验收争议继续交用户，选项空间不足时返回有边界的研究。
8. 写决策草稿，保留原话、派生判断、来源、已确认/待确认/退役处置、偏离理由、风险和延期负责人。历史正文保留，更改追加理由。逐项对照原始需求，不能以索引、文件存在或审查建议代替语义覆盖。
9. 草稿和 Grill 之后用 wh-review 做独立细节建议。逐条处置 fixed、rejected_invalid、accepted_risk 或 needs_human；涉及方向或验收的分歧交用户，其余有效问题在同任务修。严重问题若不修，必须展示具体损失并取得绑定该问题的真实风险选择。正式确认前先用 spec-analyze 对照原始需求、当前决策、真实问答和审查发现，完成一致性准备与必要修复，让用户看到完整、可审查的决策；这项准备不替代确认后的阶段末核对。
10. 展示已完成上述准备的最终方向、范围、非目标、验收、风险、延期与发现处置，取得用户对展示内容的实际确认。拒绝或未答保持草稿，不把审查建议当成用户答复；不重复询问已覆盖的授权。
11. 用户确认后，由 spec-analyze 只读核对原始需求、当前决策、真实问答、完整 Grill/审查发现、本次实际确认和已产生的证据，确认最终材料仍对应用户看到并确认的决定。缺来源、遗漏、冲突和未执行事项如实披露；需要修复的缺口留在当前任务，若修复改变已确认的方向、范围或验收，先完成修复和一致性准备，再展示更改并取得该决定的真实答复。普通核对不增加人工审批、阶段或机器门，也不以旧确认掩盖后续变化。
12. 阶段末由主会话执行 stage-handoff，写人读交接，说明当前材料、已做与未做、证据、风险和下游下一步。缺失交接只披露，不把文档写入或复盘变成工作门。

UI 是否适用依据原始需求、当前项目和计划中的实际前端范围判断；来源缺失或冲突保持 unknown，不能用 caller 标签降成 non_ui。记录目标、范围、方案和验收的真实用户回答；高风险用户可见事项说明真实分类依据，不能把风险藏入普通默认值。

## 使用技能与执行分工

按 `skill-deps.yaml` 的 name/path/trigger 直接读取所需方法。Talk、Grill、方向选择与确认由主会话负责；有边界的研究、草稿与独立审查按项目分工委派，重产物保存原件后回传短摘要和路径。方向/细节建议由独立上下文产生，实施者不自判质量；研究、审查、测试的不可用都保留真实原因。

## 人为门与审查点

- confirm：本阶段、build-plan 和 build-prd 收口时，记录用户对实际展示材料的真实答复；未答不算同意。
- authorize：只在 commit、push、merge、archive、cleanup 等不可逆 Git/交付动作前，使用 `runtime/interface/git-authorize.mjs`，执行前核对授权动作、分支与当前 HEAD；HEAD 不一致时拒绝消费旧记录；已有用户授权覆盖当前动作和范围时，按当前 HEAD 重新记录并消费，未覆盖的新增动作或范围才需用户决定。方向确认不授权这些动作，不能声称尚未发生的授权已经完成。
- 三个必留审查点：build-plan 的 wh-review 合并审查、build-code 每 Phase 的 OCR 审查、verify-code 终末 OCR 审查。本阶段方向/细节及 build-prd 文档建议仍由 wh-review 执行，不另建全 Phase 集成审查。

## 安全写入与收口

改动前用工作区/范围核对工具确认目标；需要写文件时使用安全原子写入，有共享记录冲突时使用记录锁。失败明确暴露，保留原始来源，不覆盖历史原件。当前材料说明做什么，实际执行写既有任务事实与质量记录，二者不互相代填。交接使用 `skills/stage-handoff/SKILL.md`，保存并报告该方法返回的实际不可变绝对路径；执行不是门，不要求固定复盘表或每步机器认证。正式阶段事实由现有公共流程负责，本方法不增加 writer、公共命令或生命周期对象。

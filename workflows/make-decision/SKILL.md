# Make Decision

## 目标与材料

把原始需求变成用户确认的方向，写入当前任务的 `decision-log.md`。复杂路线在本阶段负责 Talk、必要调研、Grill 与决策正文，后续 build-plan 负责规格澄清和实施设计；轻档与规划的职责按下方入口选中的流程执行。读取已有材料和原始来源即可开始，历史任务与旧审查只作背景。当前 post 任务使用 decision-log、spec、独立 Phase 文件及纯指针索引；历史材料只读，不重新启用 pre 工作流。

### 当前材料写入边界

post 任务的当前 decision-log 唯一落点是认证 worktree 的 `specs/<task-id>/decision-log.md`。发布草稿必须经过公共 `run --action=draft --stage=make-decision --name=decision-log.md` 路由；该路由由认证任务身份解析 ArtifactDir，再以安全原子写入发布到上述材料根。不得把 `taskPath` 或 `WORKFLOWHUB_TASK_DIR` 当作当前材料／decision-log 的写入根，也不得以当前 cwd 推断写入位置。

`taskPath` 只用于 `task.json`、`facts.jsonl`、`quality/` 和 `evidence/` 等任务事实与原始证据；它不是当前材料目录。若公共材料写入路由不可用，记录 `unavailable` 并停止该写入路径，不 fallback 到 taskPath；不在任务库 task 目录生成 decision-log 副本或把外置副本冒充当前权威。这是材料归属约束，不新增 stage、gate 或进度对象。

## 入口路由

首次问答前只读本节与当前材料，复用 scripts/entry-evaluation.mjs 的 evaluateEntryRoute 真实返回评估七项入口事实：boundary_clear、single_outcome、limited_impact、major_architecture、migration、permission、security。函数保原风险与缺事实语义；它不是四级自动选择器。按以下顺序推荐，判据只用入口可得的交付、验收、用户故事与风险事实，不使用实施后的 diff 或 Phase 数：

1. 规划性质：目标是梳理任务组、给后续写 PRD 提供方向，推荐规划。
2. 交付或验收范围超过一个任务：建议规划拆分，说明独立交付单元和消费者。
3. 风险硬覆盖：任一架构、迁移、权限、安全风险，或入口评估 paused 的未知风险未解，覆盖轻档建议为复杂；同时给可选拆分路线。
4. 默认复杂：事实不足以明确满足轻档边界、拿不准时保持复杂，先给推荐理由。
5. 普通：一个可独立验收任务，有清楚边界与受控影响，但涉及多个模块或需要方案比较；七项事实完整且无上述风险。
6. 小改动：一个清楚的单点用户故事，一个可观察结果，有限影响，七项事实完整且无上述风险。
7. 事实缺失或用户未答：仍推荐复杂，逐项记录缺事实、未选与待答，不能把未答当同意或默认小改动。

**唯一写入**：把入口评估真实返回的 status、reason、expanded_risks、choices，七项输入判级事实 boundary_clear、single_outcome、limited_impact、major_architecture、migration、permission、security，连同「承诺的独立可交付验收单元数」「是否含需要用户在场或真实凭证的动作」及逐项来源、实际调用命令、返回原 ref 的唯一可回读指向，只写当前 decision-log.md「级别与路线」。原始返回单份沿唯一原 ref 保存，不另存或复制 raw；其它节只引用该节稳定锚与必要决定含义，不重复入口取值。推荐、理由、用户真实选择、覆盖旧新级别/来源/影响仍沿同节原合同保历史，不新增字段或账本。

返回未包含项写“未返回”，不补造值；缺来源写 unassessed 与具名 owner，函数不可用、材料不足或取值缺依据记未评估/未决。paused 时在第8步与第14步同批展示至少一条可选拆分路线，不把建议当许可。原 ref 缺失或不可回读时报告原件不可得、具体缺口与 owner，按复杂处理，不以其它节原值兜底，不另存或复制 raw；未答不当用户授权，其余安全工作继续。

第一次真实问答同批展示 **推荐级别（高亮）**、理由、所用入口事实/来源、可覆盖选项与影响。用户可覆盖；真实答复写回后按新级别执行，未答保留草稿与未选。先将推荐、理由、入口事实与用户选择只写当前 decision-log.md 的「级别与路线」一节；覆盖追加旧/新级别、理由、来源与影响，保历史，不增加 task/facts 字段。

流程步骤、实施/审查、收口、验收四类消费者各自读同一节，不以启动时读过代替后续消费。流程执行者选步骤前读取「级别与路线」；确认后实施与组装审查前读取「级别与路线」；反思与物理交付前读取「级别与路线」；逐 AC 对账前读取「级别与路线」。原 ref 缺失或不可回读、该节或关键事实缺失时记具体缺口与 owner，按复杂路线处理，不冒用户授权，不用另一节重复原值兜底。

开局四级选择：按入口事实推荐一档并说明理由，用户可覆盖；推荐与真实选择沿「级别与路线」记录。

## 方向地图与 fog

五段方向信息写回同一 decision-log，不另建 map 文件、tracker 或第二决策权威；「大纲地图」只是顶层节目录，不承载五段信息。
落点：Destination、Notes、Out of scope 写「这次覆盖什么，排除什么？」的目标／范围／非目标，Destination 的「何时达到目的」另引「验收面」；Decisions so far 写「每个包定了哪些决定？」；Not yet specified 写「还有什么没定，谁来定？」。
方法中的研究、真实答复和草稿更新都写回同一日志：

- **Destination**：当前方向要解决什么问题，何时达到目的。
- **Notes**：真实约束、适用方法和已明确的偏好；不把假设当决定。
- **Decisions so far**：已决定事项的一行含义及原决定指针，理由仍由原决定正文承载。
- **Not yet specified**：fog 中尚不能精确提问的未知边、依赖及其可能后果；已决定、已能精确提问或已排除的事项不混在 fog 中。
- **Out of scope**：明确不做的事项、理由和原选择来源；范围外不是等待实施的 fog。

**复杂与规划路线只规划不做**：方向地图只澄清路线，不交付实现或自动创建实施票。小改动/普通按入口选中的子流程在当前阶段完成材料与授权内实现。fog 不预先切成 ticket 大小；已能精确提问的问题交现有 Talk/Grill frontier，未知依赖等真实答复后重排。本分支每会话最多解一个方向 ticket（即一个方向决策问题，不是 Phase 实施 Task），其它未解问题保原位置；有边界的研究不冒真人决定。HITL 必须询问、等待并消费用户真实回复，agent 不自问自答、不替用户选。取消、未答或来源不足保留原事实和未知，不将它们写成已决定。

## 中途重判

每次取得真实改动与影响证据、准备继续步骤或审查时，对照已选路线承诺的交付物、AC、独立用户故事是否变化；核跨层或层间影响，以及新增架构、迁移、权限、安全等未知风险。真实 diff 与影响证据用于说明变了什么，不凭 diff 大小或 Phase 数量改级或加审。

发现超出原判断的影响就暂停相关路径，按根 SKILL「入口路由」重新推荐并展示证据，回用户真实选择；未答不得改级，保留原选择和待答，其余授权内安全工作继续。已有授权继续有效，分别核对当前授权是否涵盖改动、真实写集是否越界；新增方向或范围未获许可时回用户选择，只停该相关路径，审查建议不能代用户改级。

在同一决策记录 decision-log.md「级别与路线」追加变更，保留旧级别与旧判断，写新推荐、证据原 ref、用户真实选择或未答、理由、新范围与影响；入口取值沿唯一原 ref，不复制原始返回，不改写历史判断。

升级保留已完成的方向、方案、spec/Phase 与实施，只补未做步骤与适用审查，已写代码补一次代码审，不重做调研；按根 SKILL「升级到复杂流程与材料接管」逐项核已有输入和真实缺口后接续。只有用户明确选择才降级，并记录理由与新范围；代理只能建议，不得自动降级。风险未变保持原级别与原路线，风险未变不加审；小改动仍无独立审查，不因“看起来大”改判。

## 升级到复杂流程与材料接管

用户真实选择升级后，实施者先读当前「级别与路线」、原始需求与方向确认、spec/Phase 及纯指针索引、已改代码与写集、测试/审查原件和现有 task facts；已完成方向、方案、spec/Phase 与实施作为已有输入，逐项列保留项、未完成项、证据缺口、原 owner 与接续动作。缺原件写 unknown/unavailable，不把存在、历史通过或升级选择冒当前完成或新的授权。

对照本文件复杂15步及目标路线的实际依赖，复用已完成且仍适用的调研、讨论、确认和材料，只补真实未做步骤与适用审查，不重做调研；不得跳过复杂路线未完成的方向收敛、真实用户决定、build-plan 规格澄清和当前计划确认等前置。若来源是规划路线，原两次确认与任务卡成果保持真实，仅规划授权不允许实施；先核新的执行目标与用户选择，再补目标路线缺项，不能用改级跳过原流程仍适用的前置。

未实施的任务在方向已确认后，从 build-plan 消费已有材料，核其输入、澄清与当前计划确认，补缺而非另起 spec 或重做方向研究。已实施但未验证的任务先核并补齐尚缺的复杂前置与当前计划确认，保留代码与原测试，再补一次代码审后从 build-code 的依赖已满足项继续；已有适用审查只引用原件、补真实覆盖缺口，不按改级次数重复完整审查。是否继续实施仍分别依原授权范围与当前声明写集判断，不能用“已写代码”豁免未完成前置。

build-code 无 phase_progress 游标或游标缺失/过期时，按当前工作区、当前材料与真实交付继续安全工作，在同一决策记录写明无游标或过期事实、所据原件、已完成与待做项；不为续跑新建游标许可或第二进度对象。接续者按原 build-code 方法核 frontier、目标测试和适用审查；材料不代表阶段已执行，轻档历史仍只保实际 make-decision 阶段行，后续阶段仅在真实执行后记录。

接管完成以每个保留项和补做项有真实来源、对应 owner/下一动作及实际依赖满足为准；无用户答复保持未选，只停依赖新选择的路径。P6 文本合同不能证明真实接管、真实重判或用户选择，真实运行与风险未变对照按当前任务验收授权另核；未执行保持 incomplete。

## 方法

以下十五步仅属于复杂路线；轻档和规划按入口表读取对应子流程。复杂路线不因分级删去N6动作或改变slug/产物。

写decision-log前，先读取 `skills/material-writing/SKILL.md` 的「材料写作标准（唯一）」。
再读 `skills/spec-specify/SKILL.md` 的 Q01–Q13 唯一正文，然后调用本流程对应的材料作者。
缺源如实 `unavailable`，保留原问答、确认、权限和失败边界，不复制规范。

全程领域维护：Talk、研究、Grill、写稿或确认中出现已解决的领域术语、含义或边界变化时，按 `skills/grill-with-docs/SKILL.md` 的 `Domain Awareness` 节 就地最小写入 `GLOSSARY.md` 并读回；本步完成前必须有其一——具名写入读回，或本 decision-log 里有来源的 no change 理由；未变保来源充分的 no change，归属或含义冲突交真实 owner 回答。写入方法、懒创建与返回事实归该领域 owner，本阶段只在现 decision-log 记录变化引用、理由或待问来源，逐词核对不延迟成阶段末批量写。

下方两行只显露各步骤原有产物与前提，是可发现性改进，不是新 gate 或审批；细则仍在同一步正文及所指原专业方法。十五步由真实主会话执行，公共 run --action=execute 不会自动执行 make-decision 或代填完成；材料渲染、问题生成与原件保存均不冒真人答复。

每步的完成只认本步自己的原件：优先读 `steps.json` 声明的可读原件（decision-log 节锚点、quality 原件、审查／确认／交接目录）；既有 facts 中带本步 `source` 与 `step_slug` 的步骤级证据只在该步实际存在时用于定位，不假定每个步骤都有该生产者。目录、共用文件和其它步骤的原件只作导航，不能证明本步完成。跳过不使下一步前移：任何一步没有本步原件时，下一步不成为当前步；跳过只能连同具名缺口（原因／负责人／恢复条件）记 `incomplete`，阶段保持未完成，直到本步真实原件出现。检查器 exit 0、材料存在或显式跳过声明都不是完成事实。

讨论批次与 grill 前置：用户新增或修改需求、范围、验收或非目标时，必须新起一个 talk 批次，不得以「前一批已问完」或「当前 chat 消息」替代；新批次记录触发它的需求变化原 ref 与批号。零问题仍合法，但必须写明已问过什么、为什么无问题，不能只写「无问题」。进入逐包收敛前先做一次 grill 检查：方向、范围、验收三项若有未答问题，必须问；三项都已答且无新问题，才可记「无问题」并写理由。

   开工按真实任务问题读取并执行 `skills/knowledge-graph/references/knowledge-reuse.md`：从现项目规范、案例、业务知识和已验证经验取合法原文，完成比较/四判与采用或缺口定位，结论回同一decision-log；原文/权利不足保具体影响，不把链接或调用次数当使用。图导航继续先读取并实际消费 `skills/knowledge-graph/SKILL.md`：以当前认证项目/worktree和本次原始需求为输入，按其入口选择查询现图或缺图建代码图；把内部图调研交独立子代理，主会话只收少数有源结论与对本次方向的影响。现图可读直接查询，不先更新；没有图按该方法免费建代码图，文档另按真实候选数量、字节、prompt/dispatch及估算限制告知并等本次真实范围许可，未答/拒绝只停付费路径。缺工具、坏图、无匹配或歧义保原诊断，回普通文件阅读继续本阶段，不增加准入条件。完成时把实际读取来源、改变的假设/候选/问题或无信号理由消费到同一 decision-log 的相应位置；调用次数、查询日志或历史授权不能代替结论/本次答复。

   先记录用户原话、痛点、任务类型、事实、假设、非目标和未决问题，含范围分诊：区分用户痛点、完整旅程、页面、数据状态和成功失败边界。任务类型不明或冲突时，只暂停依赖它的问题并澄清；不靠文件名或旧记录猜答案。规划任务只问会改变方向的问题，不问具体实现形式：文件路径与文件面、函数名、字段名、算法、schema 形状、命令形态、入口参数形态、行号、代码片段；可问要求覆盖哪些测试与实测面，具体命令、记录形状与实测记录由后续 build-plan 设计，普通任务可问影响实现的细节。
   **入口评估**：普通/规划是任务性质，交付规模与风险另作入口判断。普通任务有实际执行目标时，实际调用 workflows/make-decision/scripts/entry-evaluation.mjs 的 evaluateEntryRoute，七项输入各带真实依据。返回与判级事实只写当前日志「级别与路线」，字段、两项代价事实与来源及调用命令/返回原 ref 沿入口「唯一写入」原合同；「工作包与决定」的一条既有做什么／不做什么／风险／改动四字段决定只引用该节稳定锚和必要决定含义，不复制返回取值或代价事实。返回未包含项写“未返回”，不补造值；缺来源写 unassessed 与具名 owner，函数不可用、材料不足或取值缺依据记未评估/未决。paused 时在第8步与第14步同批展示至少一条可选拆分路线，不把建议当许可。原 ref 缺失或不可回读时报告原件不可得、具体缺口与 owner，按复杂处理，不以其它节原值兜底，不另存或复制 raw；未答不当用户授权，其余安全工作继续。入口事实及真实选择在第8步/第14步按既有展示读回；规划任务仍做方向规划，不自动转换任务。
   用户中途改变任务类型声明时，停止消费旧类型下的问题与产物，直到逐项按新类型重新处理。当前决策保留旧问题引用、重处理原因、新内容位置；只换 hash 或引用不算重处理。不为此新建 schema、控制面、类型状态或记录绑定。
   新日志使用 `skills/decision-log/templates/decision-log-template.md`；先实读模板，再按当前真实来源写内容。主文与原件分工按模板 `## 外置事实索引` 的节级消费者定义；逐字原文、需求索引明细、Talk 批次、grill、调研与审查处置明细只沿唯一原 ref，历史日志保持原文。首次写外置完整 U 原件或主文 OI 之前，读取并执行 `skills/decision-log/SKILL.md` 的「来源与未决问题写法」；覆盖收口前读同节 coverage audit，正文和原件各归该 owner。记录实际读取位置与先后，读了但动作未做仍记未执行；缺来源写具体诊断。

   - U 写入前：用当前 task 绝对基准＋`quality/evidence/decision-log-refs/requirement-change-log.md`（已有原件沿实际唯一 ref）定位真实 U 条目；主文每 U 最小决定、受影响落点与条件 ref 按「来源与未决问题写法」。
   - OI 写入前：定位当前 `decision-log.md#未决项`，按同节 OI 方法写问题与来源、真实状态与处置、解决者及下一步。
   - coverage 收口前：按当前 task 基准定位 `quality/evidence/decision-log-refs/coverage-matrix-5d.md` 或已存在 itemized 唯一 ref，逐 R／U 落点或缺口与真实排除选择沿同节 coverage audit；已有原件不搬移、不复制。

   **Talk 最小内联卡**：首次结构化提问前读取并执行 `skills/talk-with-zhipeng/SKILL.md` 的「问答工具 IO 契约」与「每答重排」，核宿主映射并等待真实回复；无工具或当前模式不可用时发同内容文本卡，记录“本轮降级为文本提问”＋真实原因，不记工具通过或失败。

   **UI 识别与五行卡（仅 UI 任务）**：三源 raw_requirement、project_inventory、planned_or_changed_frontend_fact 任一命中即按 UI 处理；三源都缺记“未知”加负责人，不默认非 UI，真实非 UI 写理由。判定为 UI 时把设计源问题并进第一次真实提问：设计稿从哪来、谁提供、何时可用；不另开一轮问答。同一决策记录「UI 范围与设计基准」节写五行卡：① 是不是 UI 与三源依据；② 页面、路由与组件；③ 设计源、提供者与何时可用；④ 验收基准；⑤ 缺什么与风险。非 UI 任务不写本节、不问设计源。
2. <a id="step-outline-hypothesis-talk"></a>`outline-hypothesis-talk`：
   产出任何大纲前，主会话先在分级真实答复后向用户提问：内部、内部加外部、跳过加理由；展示本次调研范围与代价，等待并消费本题真实答复。未答就保留待答，不产出大纲；级别选择不代调研答复。当前 decision-log 的既有调研记录单写范围、为什么、跳过会缺什么、谁决定与答复原ref。
   **本步产物**：同一 decision-log 的粗粒度大纲：每块问题/边界、方向假设及会推翻它的证据。
   **进下一步前**：大纲明确仍待验证，不冒基线、实施承诺或已定方向；模糊处保原备选/取舍和未知，再据它研究。

   主会话通过真实 Talk 产出粗粒度大纲，含每块的「问题与边界」及「方向假设」。标明可修改假设和什么证据会推翻它；不作基线，不在此承诺范围或成本。模糊需求比较至少两个角度及有差异的候选，说明证据与取舍。

   UI 任务时调研顺带查现有页面、路由、组件与规范；非 UI 跳过。
3. <a id="step-research-and-diverge"></a>`research-and-diverge`：
   调研决策：回读第2步大纲前取得的本题真实调研答复及原ref，按该答复执行内部、内部加外部、跳过加理由；跳过必须给理由，范围、为什么、跳过会缺什么及谁决定沿当前 decision-log 既有调研记录读取；没有本题答复就保留待答，不能代选或倒填。
   **本步产物**：内部查图／读文件的有源结论与外部研究报告及 candidates；方法分别归 knowledge-graph／deep-research 原 owner，decision-log 消费关键结论与唯一原件指针。
   **进下一步前**：内部与外部研究分别给实际执行、原文来源，或真实跳过/不可用理由，不能空白。每个候选的摘要、来源 ref、推荐/拒绝和理由可读；无候选保真实原因，研究不替用户决定。

   内部调研是查项目现图并读项目文件，核当前契约、关系与历史经验；由 `skills/knowledge-graph/SKILL.md` 承接。外部调研是检索并阅读项目外来源，由 `skills/deep-research/SKILL.md` 调用检索工具承接。两边各按自己正文的搜前声明、相关性判据和零结果写法交回，未执行与零结果分开。

   本步内部调研再次按 `skills/knowledge-graph/SKILL.md` 查询与当前未知相关的知识及 `specs/archive/` 历史经验，消费开工结论并按新问题补查，不能只在入口挂链接。先按当前职责/写集/consumer选source，经知识方法有界候选选完整ID解释；当前契约与独立历史两通道不硬排archive，宽query/god仅发现且严格限字段/条数/字符，不拿输出前25当相关性。每条拟使用结论回真实 source_file/origin 原文核命题、条件和位置；关系来源不等于端点定义，缓存同条、raw ID缺失或label命中不证明语义。存在当前图质量报告时，按knowledge-graph方法消费其误边/位置漂移/重放限制，未证实不写成事实。把适用历史经验明确落到“原文结论→本次哪个候选/假设/提问改变→具体新内容与理由”；并说明具体多知道什么；与已有建议等价就标重复/补强，不编新增收益。只报查过图不算影响产出。确无相关历史保有源的“本次无历史经验可挖”，无匹配/歧义/工具不可用仍继续普通研究并写覆盖限制；指定历史正例的独立对照与用户判断不因此被免除。不得为普通调研顺手更新、扩大JSON/忽略路径或触发付费抽取；必要时回知识方法先估范围/成本等真实许可。

   围绕大纲每块会改变方向的未知按上述分工开展研究，输入保留「大纲是待验证假设」。外部研究使用 `skills/deep-research/SKILL.md` 的 R0–R5 契约：R0 生成缺口、R1 读一手文本、R2 受限并行深读、R3 三角验证、R4 写 research-report、R5 独立审查。跳过或不可用写真实原因，研究不替用户决定。每份完成的调研报告必须显式声明 `candidates`；每个候选写摘要、证据绑定来源 ref、推荐（含拒绝）及理由，无候选写真实原因。Talk 从唯一 canonical report 读取这些事实，不用摘要或报告引用冒充候选交付。全文仍留原件；决定作者把会改变方向／范围／验收的结论与被排除候选及原因写进本日志正文，其余只给指针；取舍与逐件找回沿 deep-research「消费与所有权」的既有落点。
   UI 任务时调研顺带查现有页面、路由、组件与规范；只有设计源或还原口径不清才加外部调研，不重复常规调研。设计源固定四路：内部设计稿、外部设计稿、沿用现有页面、无稿。无稿须用户选：没有稿时由你在“先做原型或设计稿”与“直接实现并接受风险”之间选，不默认无稿可做。四路都记来源、负责人、可用时间、验收基准与缺项，信息不足记“未知”加负责人，不默认通过。非 UI 跳过。
4. <a id="step-outline-revision-check"></a>`outline-revision-check`：
   **本步产物**：研究后设计的修订大纲、需求最小索引与独立四查四行结论；两份外置原件是确认输入。
   **进下一步前**：逐块对照研究与假设，保旧判断及更改理由；多数被推翻先重整。四查已确定工作包顺序，太大或太碎时执行者当场改完给用户看。

   方向沟通与全方向调研完成后，才拆需求可核单元并设计大纲。正文每条需求只留编号、原文指针和工作包落点；需求编号永不变，新增在末尾追加，需求与工作包可一对多或多对一，不造主接字段。工作包写目标、边界、与其它工作包的关系、待弄清的问题四样；不适用写理由与依据。只写编号却找不到实际处置不算承接。
   沿当前任务已有 `requirement-index.md` 唯一原件保存完整逐字、按工作包分结构的四类来源（需求原话／选择类答复／文档转述／推断，推断明写“这是推断”）、最后变更批次，以及派生号如 R-002a 的谁接／落在哪／怎么验。原话本不存在与取不到分开；材料复述不冒逐字，原件截断照录不补。逐字答复归该索引，不另开问答原件；已有历史原件只读引用。索引单列“本次任务自己的调研（不是工作包）”，不计交付工作包。`coverage-matrix-5d.md` 保存逐单元归属、落点、验收及来源；两端同号一致。任务库文件是外置事实原件，仓库材料仍只有 decision-log，不新开正文或目录。
   将同原需求、大纲与两份原件交独立助手做前置自检，非质量裁决：覆盖与缺口直接用 `skills/decision-log/SKILL.md` 的 coverage audit；粒度直接用 `skills/spec-plan/templates/phase-template.md` 的拆／并判据，核独立消费者、独立验收、单独删减，同时报应拆与应并，不用工时、行数或验收条数门；原规则管实施边界，此处管大纲工作包，同族不同消费者。依赖沿该模板的单向无环规则。四查正文各一行写结论／依据／缺口，明细只在覆盖表，供 build-plan 与最终验收直接读取；三类缺口（没人接／有承接无落点／有落点无验收）逐条写谁接、何时接。核跨任务牵连并写谁先写谁后写。粒度负例消费归档 `design-execution-efficiency-20261014` 的 P8/T022 真实目标句，不能以单节占比代判。
   完整原文、索引与覆盖表缺任一件时明确缺项，不能仍宣覆盖完整；压缩原话、编号占位、无理由不适用分别报出并恢复受影响内容。

   UI 任务时设计源四路选择与无稿风险并进骨架四查落位；非 UI 跳过。
5. <a id="step-outline-talk"></a>`outline-talk`：
   大纲确认：本步确认骨架；第14步才确认最终方向、范围、验收与风险，两次展示与真实答复分别回读。
   **本步产物**：同一日志中的骨架展示、既有攻击自查原件及用户对此骨架的真实答复或明确待答。
   **进下一步前**：先执行原第6步的轻量攻击自查，再一次展示并等待用户真实回复；未答停草稿，旧答、推荐或模拟不代答。

   主会话先攻击过早锁定、隐藏前提与更小可逆路径，保有来源风险清单，不设否决权。接着一次给用户需求清单及真实来源类型、每工作包四样的大纲、四查四行结论及两份已备外置原件；用户可核结果并确认骨架，工作包次序沿第4步已定顺序，此处不重排。重要问题沿 Talk 一题一个方向轴、后果风险与真实等待；独立问题可合问、依赖题等真实回复，零问题合法但不替代骨架回复，且须写明已问过什么、为什么无问题，不能只写「无问题」。本步只问方向轴与骨架；逐模块方案、字段级取舍留到第 9 步，不在骨架确认时追问模块细节。本步确认的骨架（包划分、依赖与顺序、每包范围边界、非目标、每包初步验收或验收缺口）就是第 7 步方向审查要看的对象，随 `convergence_outline` 交付，不另存第二份。
   打回只改受影响部分，旧答复作废但保留原文，再展示受影响骨架；未答、取消保当前材料与未答项，恢复只消费本题真实新回复，不进入逐包。确认沿现机制保存实际展示与真人答复；字段不支持区分第5/14步用途时如实记 incomplete，不能硬造字段或凭证。第5步只确认骨架，第14步确认最终方向／范围／验收／风险，不重复问同一问题。

   UI 任务时把设计源四路逐路写清触发、负责人与证据：内部设计稿须设计方在具体页面或区块标“可开发”并给注解；外部设计稿须写来源、版本、可用范围与验收基准；沿用现有页面须写页面、路由与版本；无稿须写用户所选路线（先做原型或设计稿／直接实现）与后果，直接实现前须取得“用户明确接受风险”的答复，未取得不进入直接实现。四路都写来源、负责人、可用时间、验收基准与缺项。非 UI 跳过。
6. <a id="step-adversarial-direction-check"></a>`adversarial-direction-check`：
   **本步产物**：第5步已执行攻击自查的原件与结果读回，风险仍留原风险／假设位置。
   **进下一步前**：已回读同一次自查；不重复执行，不把用户骨架答复冒成自查结果。

   同一主会话按第5步先、第6步后串行执行，回读过早锁定、隐藏前提及更小可逆路径检查的事实依据和风险清单。第5步真实骨架确认后，在本步分两次独立调用：先执行现 `tools/cli/check-decision-log-chain.mjs --file <当前任务需求索引绝对路径>`，再执行 `tools/cli/check-decision-log-chain.mjs --file <当前任务覆盖表绝对路径>`，每次只传一个 `--file`，各自保存该时点的实际 warning/exit 给人看，只报告不阻断；未确认不得冒写该时点完成。缺自查原件如实补做并重核受影响展示，不倒填确认前已做；自查不代第7步独立方向审查、不替用户选择或新增机器门。
7. <a id="step-direction-advice"></a>`direction-advice`：
   方向审查时点：在大纲确认后、逐模块收敛前取得并回读独立方向建议；不可用与覆盖限制沿本步原件保真。
   **本步产物**：wh-review 原 owner 保存的方向建议、provider/失败/覆盖事实与实际原件 ref；审查输入是方向包，含原始需求原文（`raw_requirement`）、调研结论与来源（`research_context`，不得含 proposed_solution）、可核对现状与限制（`objective_facts`）、大纲骨架完整结构（`convergence_outline`：包划分、依赖与顺序、每包范围边界、每包验收草案或验收缺口、问题/未知、约束、失败后果、较小可逆选项）、已确认决定与当前选择一句（`current_selection`：方向、范围、非目标、已确认骨架）、被否候选及否决理由（`alternatives`＋`selection_rationale`）、关键假设及会推翻它的证据（`key_assumptions`）、被审大纲的可回读 ref＋sha256；用户答复原话不进包。缺当前选择、备选或否决理由任一项时本步不得记完成；包内缺方向或骨架是本步输入未备，不是已审发现的 finding。
   **进下一步前**：到达本步先读 skills/wh-review/SKILL.md 的现有接口，沿真实公共 review 或裸入口字节规则提交完整允许材料。答复/所选处置/结论不进入包；Kill/Recycle 权限与判据缺失不报通过，不可用不冻结同任务讨论，未变范围不追空 findings。

   用 wh-review 独立审查方向与修订后大纲，不审细节；保留原始发现、provider、失败及覆盖限制，未变范围不为追空 findings 重派。方向审查按四问逐包给结论：① 这张大纲实现之后，能不能保证原始需求被正确实现；② 所有功能是否都有接线——谁调用谁、上游输出是否被下游真读；③ 所有验收标准是否合理、可判、能证伪；④ 范围、风险、依赖是否覆盖。答不出或答「无法判断」就是 finding，写清第几问、缺哪份证据、该谁补；四问都不成问题时不写 finding，把比对范围（审了哪些包、哪些依赖、哪些验收）写进 evidence。这不是判原始需求有没有意义，也不是另给一个更粗的大纲。 Kill 权限是建议停止无效目标或违反硬约束的方向，由用户作停止决定；Recycle 权限是建议把可修补的假设、来源或选择缺口送回对应调研或方向 Talk。两项权限与判据缺失，不记审查通过；不可用不伪装通过，也不冻结同任务讨论。
8. <a id="step-module-breadth-confirm"></a>`module-breadth-confirm`：
   **本步产物**：全部工作包的简单／复杂分诊与入口规模事实展示，保真实回复或未答。
   **进下一步前**：第 7 步方向审查已回读，且其 finding 已逐条处置 `fixed`／`rejected_invalid`／`accepted_risk`／`needs_human` 并写回 decision-log；provider 不可用时保留失败原件，并取得用户对「带缺口继续」的真实答复，「不可用」不自动放行；未取得真实答复或 finding 未处置，未达不开始逐包收敛。分诊仅决定先补调研或直接收敛，保持第4步顺序，不冒细节已收敛。进入逐包收敛前先完成 grill 检查：方向、范围、验收三项有未答问题必须问；三项已答且无新问题才可记「无问题」并写理由。回读时把 provider 不可用与用户选择已具名两件事分开写：不可用保留失败原件并记 unavailable 或 incomplete，用户实际选的那条路写明是哪一条。两者缺一不算本条已回读。

   各工作包命名并写一到三句范围，沿已有风险／优先级、第1步入口规模事实及 Talk 范围五类判定哪些先补调研、哪些直接收敛，不另造判据。向用户展示承诺的独立可交付验收单元数、是否含用户在场或真实凭证动作，以及 入口评估真实返回；缺事实展示缺口，未返回项不补造。返回 paused 时同批展示至少一条可选拆分路线，保用户实际答复或未答。分诊不重新确认或改排已确认骨架的工作包次序。
   按入口路由选用对应流程；本复杂流程内分诊只决定先补调研或直接收敛，保持已确认骨架顺序。四级都先大纲再收敛，沿既有决定格式，不固定问题数或轮数；当前工作包分诊不代替入口用户选择，不把文本存在冒真实执行。派发回传、写作与跨Phase写集分别只指向 `AGENTS.md` 的派发与回传、WR001 与现写集纪律。

   分诊标出 UI 包：三源判定为 UI 的包先补设计源调研再收敛；非 UI 包不标、不加动作。
9. <a id="step-module-convergence"></a>`module-convergence`：
   逐模块台账：在既有收敛原件每包一行，五类分析答复只取已答／事实可定／待你定；收敛原件每行十列固定为 包｜目标｜边界｜方案与取舍｜验收｜风险｜依赖｜消费者｜未决/无｜状态；状态列之后另设五类分析列（目标与成功意图／范围与旅程／数据与状态／成功失败验收／约束非目标与风险），逐类写「已答／事实可定／待你定＋谁定」；「未决/无」列不是「无」时状态必须写「未收敛」。包状态沿原检查器的已收敛语义，三值不填入包状态列。引用本包调研／发散／收敛／就地讨论／定验收五行表与8项证据指针；8项证据均可回读且分析无待定、讨论与验收已确认后才记已收敛，有待你定就保留未收敛。未决列非空的包不得记已收敛；记「已收敛」必须同行给出五段表位置、8 项证据指针（各带 ref 与批次）与五类分析标注，缺一项写「未收敛」并停在第 10 步之前。每包写完立即发布并读回，保留批次与具名未决者。
   **本步产物**：逐模块方案/替代/验收/后果、red/blue 争议清单及每条处置或具名未决项，留现决定/处置原位置。
   **进下一步前**：方向审查属第 7 步，本步不重复方向审；每条 red/blue 争议都已逐项消费，方向或验收分歧交真实用户；新增模块补齐原研究/决定/验收，仅闭包触及的旧决定复评。amend/supersede 保历史，不用泛化摘要冒逐条收敛。 五类分析须逐类标「已答／事实可定／待你定」与谁来定；讨论前展示工作包判断，讨论后用 3–5 句大白话复述并取得用户确认；进入细节审查前完成五类收敛并把工作包骨架给用户看一次。

   按已定顺序逐工作包走调研→发散→收敛→就地讨论→定验收，当前包完成再进入下一包，不攒跨包批次；包内独立问题可合问。简单包消费全方向调研并定向读文件，复杂包补有边界调研。复杂包逐一判断是否需要内部或外部调研；本包调研格引用开局真实调研答复原ref，记录本包内/外部需要判断，与开局选择不同则写差异理由及决定来源，沿现调研格保存，不另建记录；会改变方向、范围、验收或风险的歧义仍按原Talk边界取得真实答复，未答不代选。简单包免扩散仅两理由：只有一个明显合理方向且其它明显更差，或全方向调研已比较过；写理由与原件。其余用 Talk 扩散透镜，外置候选件至少两个关键决策轴不同的候选及取舍理由，非措辞变体。定验收格按「每个工作包的验收怎么谈定」五问逐条谈定，五问答不出就在本格改范围或改验收方式。
   逐包收敛两样东西：「收敛」格写本包的具体需求细节（承接哪几条原始需求、做到什么程度、边界在哪、明确不做什么）。
   「定验收」格按「每个工作包的验收怎么谈定」五问写本包的交付验收标准。
   顺序是先需求细节、后验收标准：验收标准对着收敛后的细节写；细节没收敛就定验收，写出来是空话。
   两样都在本步逐包完成，不在第12步写草稿时补，也不留到 build-plan；第12步只把本步结果写进材料。
   需求细节或验收标准有一项没收敛，该包保持未收敛，不进第10步细节审查。
   每包正文保方向结论与验收，并建五行小表（调研／发散／收敛／就地讨论／定验收）；每格一句结论＋一个原件指针及本包批次号，注明简单／复杂，不适用写理由。讨论与验收分格，不把两件事压成同句；同批不出现两个包名。新增包重走本包五段并建表，不重跑方向审查，随整体细节审查看；若该路线有真实 accepted_risk 决定，只引用其绑定原件，不能自行接受风险或称无问题。旧包回改只 amend/supersede，标需重评并更新受影响验收格，不重走全五段。

   逐模块澄清未决项，说明方案、替代、验收、后果与风险。方案写到可实现的方向与取舍为止：选哪条路、放弃哪条、接受什么代价；坐标、判定阈值、字段级方案与可粘贴代码由后续 build-plan 写入 `spec.md` 与 `phases/P<n>.md`，本步保留全部既有收敛义务。产出 red/blue 争议清单并逐条给处置，辩论未决项，不压成泛化摘要。只有不影响验收判据的措辞级细节可公开最小合理假设；范围、验收、依赖、写集不得以假设代答复；方向或验收分歧交用户，选项不足回有边界的研究。中途新增需求时，在同一决策日志新增大纲模块，补齐调研、决策、方案与验收标准，不新增步骤。默认新增下游人读决策记录；仅新模块上下文传递闭包触及的旧决策记 `requires reassessment`。`context(p) = requirements(p) ∪ ⋃_{q≻p} solution(q)` 的 `≻` 是 `leadsTo` 传递闭包，此法来自单一学术提案；工程上从触及的最高抽象层向下级联。只追加信息用 amend，改变决定用 supersede 加双向人读链接，保留旧正文；不新增 runtime 状态或许可。方向或决定被 supersede 时，在同一决策日志「级别与路线」追加一行 `- 失效步骤：<step_slug 或 step_id>、…；阶段：<stage>；重做范围：…；未失效：…`，列出因此失效、必须重做的步骤；数字编号按「阶段」限定到对应阶段，缺阶段或阶段不明的条目不跨阶段推断；被列步骤按新原件重跑并留下新证据后从该行移除；只重写正文不重跑受影响步骤不算完成。

   **每个工作包的验收怎么谈定（第 9 步）**

   本节是第 9 步逐包收敛的细则：先收敛本包需求细节，再按五问定验收标准。

   每个工作包的验收都在本阶段谈定：复杂路线写进第9步定验收格与第12步验收面同号 AC，轻档写进对应子流程的材料，都不留到 build-plan 才想。
   多条需求聚合成一个包时，验收按包谈；每条需求是否都被方案与验收覆盖由 build-plan 结束时的 spec-analyze 判。

   逐条回答五问，五问都答得上才算谈成：

   - 谁做、做多久：写执行者与预计工时；合计超出本任务预算就换方式或改范围。
   - 靠什么资源、缺了能否就地造：写外部件与来源；造不出或要等外部的，不写成通过条件。
   - 范围只覆盖本包吗：写它证的是这个包承接的哪些需求；别的包与长期指标不当本包判据。
   - 通过或不通过怎么观察：写观察方式、观察者与证据落点；写不出观察方式的不是验收。
   - 读者能不能照着做：这个包验收写完，找没参与的独立执行单元读；不需要用户本人到场。
     问他「下一步为这个包做什么、在哪做、跑什么」。

   三问答不出，就在本格补真实 task-id、落地的 Phase 文件路径或门禁入口。
   补不出就当场改范围或改验收方式，不许带进 build-plan；这一问是作者自查，不新增质量门。

   优先选最简、成本最低的验证方式，并写清为什么不能再简。
   五问答不出，或成本超出本任务预算，当场改需求范围或改验收方式，不许带「以后再说」进 build-plan。
   要用户本人拍板的事项在本阶段就问，并写成「用户独占确认」这一种验收形态。
   定义见 `skills/spec-plan/templates/phase-template.md` 的「Phase 的验收要用户本人来判吗？」。

   最小充分验收：能用既有样本就不新造；能抽检就不全量；能一次就不做两次。
   能用一条命令判就不写人工流程；只要判真伪的能力不降，就必须选更便宜的那种。

   硬规则：在 make-decision 阶段谈不成可执行验收的工作包，不许进入 build-plan。
   轻档不进 build-plan 的，同一条规则落在它自己的规格与 Phase 材料上。
   谈不成的当场改范围或改验收方式；改完仍谈不成，把选项交用户，不留一条永不可能通过的验收。

   这五问与 `skills/spec-specify/SKILL.md`「验收标准怎么写才可实现」是同一套；判据写法与硬规则归该节。
   本节只说本阶段问什么、答不出怎么办。

   **每个包的方案卡与冷读（第 9 步）**

   本步每包除台账行与五类分析外，另写一张十格方案卡；卡写在该包收敛原件行下，不另建文件。
   十格是结果、对应需求、现状缺口、方案与取舍、边界、数据与状态、验收、风险与回退、未决、白话复述。
   每格只写一句结论，细节仍放既有表格与原件指针；十列台账与五类分析列的形状不变。
   本卡是这两处正文的组织方式，不是第五类分析，也不是第二份材料。
   方案与取舍格写选哪条路、放弃哪条被否替代、接受什么代价；把原始需求换个说法填进来不算写卡。
   验收格每条给一个反例；风险与回退格写触发条件、失败后果与恢复路径。
   未决格写真实未决项与谁定，不把「以后再说」当成未决。
   白话复述格用三到五句大白话说清改什么、为什么；出现未解释的黑话或内部编号即未收敛。

   写完由没参与本步骤的人只读这张卡冷读，冷读五问是改什么、为什么、边界、怎么验、还有什么没定。
   五问全答出才算收敛；任一问答不出，或要翻本卡以外的材料才答得出，答不出即未收敛。
   答不出即未收敛的包保持未收敛，停在第 10 步之前，不因写过卡就记已收敛。
   冷读记录写进本包五行表的「收敛」格，记独立读者身份、读的卡与五问答复原文。
   未决不为空仍算未收敛，冷读通过不能把它改成已收敛。
   方案卡对 UI 包与非 UI 包同样适用；卡里不写只对某一类包生效的额外要求。
   以上是方案卡段的全部要求；后续阶段在其后追加各自内容，本步不为它预留格子。

   **UI 包的补充（第 9 步）**：本步只对 UI 包，在“数据与状态”“成功失败验收”两格里补设计源、对照项、通过失败与反例；验收五问加一个子问“设计源和对照基准可用吗”，答不出即保留未收敛并写明谁补。非 UI 包不补格、不加子问。

10. <a id="step-detail-advice"></a>`detail-advice`：
   细节审查前检查：先跑步骤检查器并读回台账；有包未收敛即停在细节审查前，记录缺项与owner，收敛后重跑并核全部包齐再做整体细节审查。
   **本步产物**：整体一次 wh-review 细节建议、全部真实 R/U 全文与条件原件的送达事实、OI 终态及 finding 原处置格；不拆逐模块再整体审。
   **进下一步前**：全部模块收敛；全部真实 R/U 在现工作包与决定/写集或唯一覆盖格各有落点或具名缺口、写集每个路径有定序写主（批内同路径互斥，跨批重叠有真实依赖边及具名先后写者）、同一事实文内只有一个值，三者缺一仍未完成。到达本步读 wh-review 现有接口，保全文/顶层 ref 与多个原件真实 body、实际 delivery 和未证 read-confirmed 边界；下文全部风险/处置/分析义务保持。 五类分析须逐类标「已答／事实可定／待你定」与谁来定；讨论前展示工作包判断，讨论后用 3–5 句大白话复述并取得用户确认；进入细节审查前完成五类收敛并把工作包骨架给用户看一次。

   全部模块收敛后，对整体做一次 wh-review 细节审查，检查模块间一致性，不拆成逐模块审加整体审。先实读当前 decision-log 全文，包括全部真实 R／U，再按模板 `## 外置事实索引` 的取用条件逐件读本次需要的唯一原件全文；全部 R／U 对账沿 `skills/decision-log/SKILL.md#来源与未决问题写法`，不把主文摘要、编号存在或包外指针当全文已读。
    调用者将当前 decision 顶层 ref／sha256 放 `approved_direction`，触发的 U／coverage 等明确原件 ref／sha256 放 detail 合法的 `context_map`／`evidence_map` 顶层成员；现 `resolveMaterialRefs` 按认证 worktree 或当前 task 双 root 读真实 bytes，现 `runSimpleReview` → `buildReviewMaterials` 将完整正文装入 packet。多个原件逐件复用现读取方法，已读全文连同各自基准与原 ref 放合法成员；嵌套 ref 不被 resolver 递归读取，不能算已送达。按实际 delivery manifest 回读送出的完整成员和来源／脱敏事实；只给摘要或包外 ref 时明确 incomplete，缺原件、越界、跨 task 或 symlink 保原 TASK_FILE_INVALID／读失败，不略过。只取本次条件触发的明确原件，不扫目录、不递归解析 Markdown、不放宽 ArtifactDir writer 根、不把 detail 成员混入 phase profile；送出不证明 provider 已读懂，read-confirmed 未证保 unknown。

    每个工作包的四行投影写进 `context_map.proposal_projection`，键为包名，值为 `{scope, plan, acceptance, risk, source_ref}`：`scope` 写承接的需求编号与明确不做；`plan` 写选定做法、放弃的替代与代价；`acceptance` 写 AC 编号、通过／失败信号与至少一处反例；`risk` 写失败后果、恢复回退、外部依赖与未解项；`source_ref` 写该行正文的可回读位置。缺任意一行，该包方案未交审，detail 审查不得记完成。detail 审查按仔细检查设计的深度读：逐包核方案是否成立、接线是否为真（谁调用谁、上游输出是否被下游真读）、验收是否可判且能证伪、风险与依赖是否覆盖；四问（方案成立吗／验收可判吗／范围越界吗／风险覆盖吗）逐包给结论，答不出或答「无法判断」就是 finding，写第几问、缺哪份证据、该谁补；四问都不成问题时不写 finding，把比对范围写进 evidence。不把文件存在、编号或字段齐备当判断。
    本步完成以全部真实 R 与 U 在现工作包与决定／要改哪些文件或唯一覆盖原件的落点或缺口格各有一个落点，且写集表每个路径有定序写主（批内同路径互斥，跨批重叠有真实依赖边及具名先后写者），且同一事实在文内只有一个值为准——三者缺一即本步未完成。采用的发现、风险、OI 仍在其已有唯一处置格逐项保真实处置及未处置缺口，影响 R／U 时覆盖格引用原格，不要求另造“未落项”。detail 审查逐条 OI 核对终态字段（问题/成功标准、方向/范围/取舍、盲审发现/假设、剩余风险、被拒方案与未决项）是否有真实内容。Kill 权限是建议停止整体目标或范围无法成立的任务，由用户决定；Recycle 权限是建议将可修补的模块间缺口送回对应模块收敛。两项权限与判据缺失，不记审查通过。finding 逐项处置 fixed、rejected_invalid、accepted_risk 或 needs_human；方向或验收分歧交用户，其余有效问题在同任务修。严重问题若不修，展示具体损失并取得绑定风险的真实用户选择。正式确认前用 spec-analyze 对决策草稿作只读一致性核对并做必要修复；该核对先于最终确认，不替代最终确认，也不新增审批或机器门。

   **设计审查镜头（仅 UI 包）**：细节审查加一个镜头，核对 UI 需求是否收敛、设计源是否确认、验收是否可判；缺设计源、缺对照项或缺反例都具名报出，写清第几包、缺哪份证据、该谁补。非 UI 包不加镜头。
11. <a id="step-grill-with-docs"></a>`grill-with-docs`：
   领域词表读回：按原领域owner将已解决术语变更就地写入并读回，或在当前日志给有来源的不变理由；冲突保留具名来源，沿本步原方法处理。
   **本步产物**：质询输入的计划草案骨架、原 Grill 方法的最小内存 grill_summary，及写回原日志的必要 decision_updates/GLOSSARY/ADR 结果 ref；不持久化完整 Grill 历史。
   **进下一步前**：按 skills/grill-with-docs/SKILL.md 全文完成五类覆盖、四退出检查、领域 changed/no change 与冲突处置；ADR 三项全部成立才由原 owner 记录。问答由主会话真实执行，Grill 不冒独立审查，后续写稿/确认/核对仍需真实进行。

   以细节决策与计划草案骨架调用 `skills/grill-with-docs/SKILL.md` 全文；五类覆盖、四退出、领域维护与 ADR 判据均由原 owner 承接，主会话执行真实问答，Grill 不冒独立审查，后续写稿／确认／核对／交接照常执行。Grill 的对话范围不再限定「只有仍会改变方向的问题」：进入逐包收敛前的 grill 检查中，方向、范围、验收三项未答必须问；三项已答且无新问题才记「无问题」并写理由；本句覆盖 grill 原方法里「只有仍会改变方向的问题才进对话」的窄口径。

   出现 UI 术语或争议时才质询；非 UI 跳过。
12. <a id="step-write-decision-draft"></a>`write-decision-draft`：
   **本步产物**：当前 decision-log 完整草稿：原话/派生判断/来源、真实已确认或待确认/退役、风险与延期 owner。
   **进下一步前**：所有真实 R/U 在主文必要接口及唯一覆盖原件有落点或有源具名缺口，排除保真人理由/去向；历史与更改理由保留，文件/编号/索引不冒语义覆盖。

   在正文既有整体形态节讲清整件事，让读者不读完整日志也能懂要改成什么样；跨包核对另留一小段，逐条给唯一写者／依赖顺序／边界重叠／口径统一的结论。页面承载整体形态时此处给内容与唯一页面指针，不造第二权威。 需要生成或实质更新该页时调用 `skills/answer-as-page/SKILL.md`，传当前材料与task facts、测试/审查原件和真实改动清单、当前步骤及任务库内页面/同目录节点侧车绝对路径；同一页面owner串行更新，只读派生不反写进度。首次基准缺失据实展示，较大变化才更新；具体样式沿已确认模板，真实效果仍须独立页面读回。全部工作包谈完后，在本步再次分两次独立调用：先执行现 `tools/cli/check-decision-log-chain.mjs --file <当前任务需求索引绝对路径>`，再执行 `tools/cli/check-decision-log-chain.mjs --file <当前任务覆盖表绝对路径>`，每次只传一个 `--file`，各自保存第二时点的实际 warning/exit 给人看，并回读第6步第一次原件；默认仓库扫描不等于读了任务库，只报告不阻断。旧历史时点或事后补件如实记回溯，不能补证当时已备。

   写完整决策草稿，保留原话、派生判断、来源、已确认/待确认/退役处置、风险和延期负责人。先按「来源与未决问题写法」逐项核对全部真实 R 与 U：每条在主文必要接口及唯一覆盖原件有一个落点或具名缺口，用户真实选择的排除保理由与去向；缺项不算完成，每条有可见真实处置。历史正文保留，更改追加理由，不能用文件、索引或审查建议代替语义覆盖。

   UI 任务时写稿引一行「UI 范围与设计基准」；非 UI 跳过。

   **本步产物**：确认前对最终决策草稿、真实问答、Grill/审查与已产生证据的只读一致性核对结果；日志留必要说明/原件引用及领域写入读回或有源 no-change。

## 使用技能与执行分工

按 `skill-deps.yaml` 的 name/path/trigger 直接读取所需方法。Talk、Grill、方向选择与确认由主会话负责；有边界的研究、草稿与独立审查按项目分工委派，重产物保存原件后回传短摘要和路径。方向/细节建议由独立上下文产生，实施者不自判质量；研究、审查、测试的不可用都保留真实原因。

## 人为门与审查点

下列三阶段审查点属于复杂路线；小改动无独立审查轴，普通路线在本阶段逐模块收敛后做一次方案审（detail 轨）、整次实施做一次实现审，规划只审方向与任务卡，分别按子流程执行，不将复杂路线的每Phase审查叠加给轻档。

- confirm：本阶段、build-plan 和 build-prd 收口时，记录用户对实际展示材料的真实答复；未答不算同意。
- authorize：只在 commit、push、merge、archive、cleanup 等不可逆 Git/交付动作前，使用 `runtime/interface/git-authorize.mjs`，执行前核对授权动作、分支与当前 HEAD；HEAD 不一致时拒绝消费旧记录；已有用户授权覆盖当前动作和范围时，按当前 HEAD 重新记录并消费，未覆盖的新增动作或范围才需用户决定。方向确认不授权这些动作，不能声称尚未发生的授权已经完成。
- 三个必留审查点：build-plan 的 wh-review 合并审查、build-code 每 Phase 的 OCR 审查、build-code 终末 OCR 审查。本阶段方向/细节及 build-prd 文档建议仍由 wh-review 执行，不另建全 Phase 集成审查。

## 安全写入与收口

执行纪律：缺失即未完成；跨包不合批；确认与推进分开问，分诊、骨架与最终确认分别问；少打扰不等于跳过步骤。步骤证据位置以本阶段 `steps.json` 为指针（每步 `completion_evidence` 指向该步真实产物：decision-log 节锚点、quality 原件、审查/确认/交接目录）；检查器把可读原件记为已留痕但不判完成。完成由独立角色按原步骤结果判，并在既有记录（confirm/review/appendRecord/capture）写事实与缺口；或由既有 producer 读取合格 human 记录后判 completed。不恢复退役 writer、不造 row、不自述。trace-only 表示完成未知，不等于没做。producer 的 criteria_ref 用可回读节锚点（如 `workflows/make-decision/SKILL.md#方法`），不加“第N步”字面；步骤选择由 observable_result 的判定消费描述承载。研究、审查、确认、测试和问答原件仍放既有位置，不在决策日志新增步骤节；问答原件开头写明批次类型。第9步逐包收敛时，在既有收敛原件逐项更新8项证据指针与包状态；收敛原件文件名必须是 `convergence-checklist.md`，带批次前缀时先建同名指针件再写；第10步细节审查前运行 `node tools/cli/check-stage-steps.mjs --stage=make-decision --task-path=<任务目录> --material-root=<材料目录>`，实际读取模块缺项与状态，有未收敛包就停在细节审查前并在既有原件留记录；收口前再按该命令核步骤证据与缺口；检查器逐包报告状态，5 列状态表点名未收敛包并以非 0 退出；十列状态表（8 字段＋状态列）同样按状态列点名并以非 0 退出，其余只报告，不证明完成；退出码只反映状态列的未收敛包，十列字段缺口只进 complete/gaps，不改变退出码。入口推荐行使用可解析字面，如 `- 推荐级别：复杂`；既有日志不回改，未命中就报“未读到级别事实”。

改动前用工作区/范围核对工具确认目标；需要写文件时使用安全原子写入，有共享记录冲突时使用记录锁。失败明确暴露，保留原始来源，不覆盖历史原件。当前材料说明做什么，实际执行写既有任务事实与质量记录，二者不互相代填。交接使用 `skills/stage-handoff/SKILL.md`，保存并报告该方法返回的实际不可变绝对路径；执行不是门，不要求固定复盘表或每步机器认证。主会话照步骤执行并把本步真实产物存既有位置；正式事实写既有任务与质量记录。本方法不恢复退役 stage writer，不增加 writer、公共命令或生命周期对象。

阶段末统一按收口方法执行一次；交接内容与独立读取沿 `skills/stage-handoff/SKILL.md`「信息来源」「回读结果」「结束条件与边界」，返回其实际不可变路径。局部 Phase 摘要不触发收口，原失败与缺口可见，持续授权不代候选采纳。

## 驾驶舱

到达出页条件时调用 skills/answer-as-page/SKILL.md 原方法：三个以上相关概念、分支、多维对比或层级关系适合出页；没有这些信息形状时记录未触发理由。符合条件才由本流程主会话作为生成 owner 调用，不以示例数据或产物存在冒真实生成。

出页后四类更新时点为：骨架确认后、每细化完一包、方向/范围/验收实质变化、Phase 定稿或收口前；只改措辞或指针不生成。路径由调用者指定，默认任务库证据区 overview-<date>.html 与同名 .nodes.json；同一页面 owner 串行更新，先读旧页/侧车，安全原子写，中断保旧件与真实失败。

页面按原 owner 的7环读取当前材料、task facts、测试、审查、真实改动；缺环标「缺」，未产生写「尚未产生＋到时会填什么」。顶部显示 decision-log 的 sha256/字节/行数指纹、时间与当前步骤。页面是只读派生，不新增进度账本，不反写任务事实；来源、比较基准或工具缺失如实记录。生成/QA 仍沿 answer-as-page 与 isolated-browser-qa 的真实场景；未生成不报页面通过。

## 当前步怎么执行？

主会话从本阶段步骤表投影当前卡，只读本步和必要前置。
调用检查器时显式给任务根、材料根、阶段和当前步；跳过使用可核当前 Phase 或真实 HEAD。

`node tools/cli/check-stage-steps.mjs --stage=make-decision --step=N --card --task-path=<任务根> --material-root=<材料根> --phase=<当前Phase>`

卡给结果、进入与停止条件、最多三个读取位置、具名证据、自查命令和答复要求。
步骤表的稳定锚直达本步正文；前置原件可读只表示留痕，完成仍按本步原判据。
显式跳过用 `--skip-with-gap=N --reason=<原因> --owner=<负责人> --recovery=<恢复条件>`。
跳过后当前步仍是第 N 步并带具名缺口；检查器只在同次回复提示下一步卡，不写进度、不前移。
检查器经现有任务句柄保存普通原件；缺字段或当前身份不可读时不记录、不前进。
Phase 沿现有当前游标、索引、物理任务和材料提交核对；提交必须等于真实工作区 HEAD。
运行编号当前没有可认证的现役权威，写跳过时改用上述身份，不猜默认编号。
当前原件沿 facts 的本阶段 source、step_slug、实际 ref 逐件读回；目录只作导航。
收口读同一报告的 `closeout.gaps`，逐项披露未清缺口和恢复条件，记未完成。
缺口跨 Phase、提交和运行编号持续披露；只有既有完成生产者所引的本步同身份原件可解除。
解除原件还须晚于缺口，当前方向未把本步列为失效；缺证明就保留缺口。
检查器对 5 列与十列状态表逐包点名未收敛并以非 0 退出，其余只报事实；退出码只反映状态列，十列字段缺口只进 complete/gaps；不建立步骤账本、游标或通用退出门。

阅读基线：记录路径、字节、跳步、返工、Phase 时长的前后原始读数；只建立基线，不宣称改善。

### 执行策略什么时候定？

主会话在本阶段逐包收敛与最终确认时，把执行策略写入当前决定材料。
策略说明任务形状（验收、模块、数据量、最长测试、外部输入）、S/M/L 测试数据、
测试选择、事件等待、证据指针、检查点和可并行测试面，并取得真实答复。
缺项或未答就保持草稿，回原问题补齐，不能收口进入 build-plan。
数值来自真实任务，不新增固定机器门，也不降低完整验收。

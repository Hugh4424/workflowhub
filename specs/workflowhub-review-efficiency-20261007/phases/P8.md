## L0 — 结果与变更

文档审查走 wh-review runner → ReviewProviderClient → 3rd-review broker（B-1 G1）。HEAD 上这条路径有三处让「失败」看起来像「通过」：拒审散文经 runner 解析成零问题、无输出的 completed 成员原样计完成、`catch {}` 吞掉解析失败（ADR-030、ADR-031）；另有两处休眠或静默丢弃机制：墙钟超时环境变量（ADR-009）与 600 秒补充窗口（ADR-026）。P8 把这些接到 P1 收紧后的解析口径上，并给每个 provider 写上记账事实（ADR-038）与原件 ref+sha256（ADR-025 / C8）。

- **结果**: 经 `runSimpleReview` 产出的结果里，解析失败或无输出的成员 `status:"failed"`、`error.code:"OUTPUT_INVALID"`，全部如此时整轮 `status:"unavailable"`；成员带 `parse_outcome`、`usage_status`，有原件时带 `raw_output_ref` 与 `raw_output_sha256`；提示词不含 `bundle/review-instructions.md`；`new ReviewProviderClient()` 不受环境变量影响；迟到的补充 findings 并入结果。
- **非目标**: 不改解析函数本身（P1）；不改 record route 与 OCR 适配器（P7）；不接 `onProviderResult`（P9）；不改 vendored broker（C16）。
- **与其它 Phase 的区别**: P8 是 runner 与 provider client 的唯一 owner；它消费 P1、P3、P7 交来的语义，不改这些语义的定义处。

## 任务身份：这是什么任务？

本任务是把“质量优先、砍仪式不砍质量”落成可执行方法的一项复杂任务。
它同时涉及 workflowhub 的写 PRD 方法、写计划方法和 PaperBuilder 的规划 PRD，属于跨仓库、多交付物、要直接动手改的任务。
用户已选择“设计和动手一起做”，按复杂路线执行；本阶段只出决策与交接，实际改动放下游阶段。

## A 组：build-plan

### A1：阶段验收

- 一条验收 = 一小段，写清：目标、怎么操作、什么条件、怎样算通过（含“故意弄坏一处必须失败”）、真跑还是替代、谁判/证据、失败怎么修/什么时候停。
- 不写长跑当每次门；确实需要一次长跑，放任务最后，写清跑多久、看什么、什么时候停。
- 阈值必须有来源或基线，不随便定。
- 不写“谁开发/谁测试/谁审查”；那是 build-code 的事。
- 写完给一个没参与的人，只给他这段，问四件事：第一步做什么？看到什么算过？看到什么算不过？证据放哪、跑一次多久？四问答不出就重写。
- “顺带看之前任务”是建议：发现问题只记录、不阻塞当前任务。

### A2：阶段拆分

- 分清三个词：PRD 任务（用户能看到的交付物，一张卡）；阶段（一个任务里能独立验收的一部分，默认 2–7 个）；阶段内任务（一个阶段里具体要做的工作）。
- 按交付/验收拆：每个阶段交一个不同的、用户能看到的中间结果；每条验收能独立失败；共享同一条验收就并；必须一起交给同一消费者就并。
- 不按文件、步骤、人、代码行数、时间拆。
- 阶段内任务按交付/验收拆；任务卡 8 个 plain 字段：为什么做、交付什么、不做什么、前置、怎么做、怎么验收、证据、下游（含什么时候停）。
- 不设时间盒；不指定“谁”。

### A3：执行建议（含第 0 阶段、测试人数、流程监控员）

- **第 0 阶段**：所有阶段需要同一套测试环境/数据时，统一准备；交付共享环境+数据+脚本+说明；验收=一条命令搭好、每个阶段能用、没有阶段自己重建、清理干净；不需要就跳过并写理由。
- **测试人数**：一个面/一条命令 → 1 个；两个以上独立面 → 2–3 个，各管一面；真实外部/小窗 → 1 个测试 + 1 个见证/复核。
- **流程监控员（建议）**：建议 build-code 考虑一个专门子代理，一个任务一个；只监控长/复杂阶段；30–60 分钟看一次是建议，不是硬定时器；只看进度/证据/命令结果；正常回“在轨”，有问题报“偏离+证据+建议”；不改代码、不跑测试；便宜模型、小上下文。build-plan 只写建议，是否派、频率由 build-code 定。
- 每阶段 1 个开发（唯一写代码）；测试/审查独立上下文；开发修问题复用同一会话；测试/审查在开发就绪后并行；写代码串行；只读可并行。
- 主会话只派发、裁决、对外；不写代码、不跑测试、不查细节 bug。

### A4：build-plan 流程与模板小改

- **流程 1**：读 decision-log、原始需求、PRD 任务卡；查代码现状时，**有知识图谱就用图谱**（模块/接口/消费者/历史决定/失败教训），没有就用现有代码/上下文；不新增外部系统，只读指到的文件。
- **流程 2**：先做“阶段大纲”（2–7 个阶段；每阶段交付/一条验收/依赖/并行/下游），像 make-decision 大纲一样先给用户确认；确认后再写规格。
- **流程 3（建议）**：建议规格作者 1 个（全局规格）、阶段作者最多 3 个（每个阶段一份文件，可并行）、验收设计 1 个（写/校验每阶段验收）、审查 1 个（对原始需求审阶段大纲/规格/阶段文件/验收）；实际派谁、派几个由 build-code 定；主会话只派发/答澄清/裁决。
- **流程 4**：验收设计=每阶段一小段（A1）；实现前冻结；改验收要用户真实答复。
- **模板小改**：
  - spec 加“阶段大纲”（2–7 个阶段 + 需要时的第 0 阶段）；其余不动。
  - phase 的“这一 Phase 怎么验收？”7 个槽删掉，换成“一条验收一小段”；“怎么验证”只留 RED/GREEN/命令/证据执行细节，不重复验收标准。
  - phase 在“下一消费者拿什么继续”加“下游”；执行建议放一句话；不新增节。
  - 第 0 阶段放 spec 的“阶段大纲”，不放 phase 文件。
  - 当前 spec/phase 结构不大改；只加/改上述几处。

## B 组：build-prd

### B1：任务级验收

- 一张卡 4 行一段：目标、怎么操作、什么条件（含真跑/替代）、怎样算通过（含“故意弄坏必须失败”）。
- 一个任务可以有多个强关联结果，每个结果一段 4 行；结果不相关才拆卡，避免拆太碎。
- 不写命令、不写证据；留给 build-plan 阶段验收。
- 不写“意图/等级/风险级”这种黑话。

### B2：任务拆分

- 一个任务 = 一个用户能看到的结果（可多个强关联结果）；一张卡。
- 按交付/验收拆；两个任务共享同一结果/验收就并；一个任务多个独立结果就拆。
- 一个任务可拆 2–7 个阶段（build-plan 做）；超过 7 个先拆任务。
- 任务地图 4 列：任务、结果、依赖、波次；不改卡号。
- 任务卡 6 个 plain 字段：为什么做、交付什么、不做什么、前置/依赖、怎么验收、下游；**不写证据**。
- 流程：读方向/原始需求/现有 PRD/代码现状 → 粗切地图 → 用户确认 → **一个作者写整个 PRD 文件**（不派多个子代理）→ 一次审查 → 交接。
- 审查四件事：拆卡、实现、范围、验收；不审文件格式。

### B3：build-prd 写法/步骤/模板

- 6 步：读 → 任务地图 → 用户确认 → 一个作者写卡（当前波次）→ 一次审查（拆卡/实现/范围/验收）→ 交接。
- 任务卡 6 字段、一页；任务地图 4 列；PRD 章节保留但收短。
- 不写 16 字段散文、状态表、证据字段、命令、判定器、文件行号。
- 写 PRD 前读 `skills/material-writing/SKILL.md` 的「材料写作标准（唯一）」；不复述标准。
- 一个作者写一个 PRD 文件；一个审查；用户先确认地图，再确认终稿。

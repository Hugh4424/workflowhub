## 速读卡（30 秒）

- **一句话需求**：当任务涉及 UI 或前端时，WorkflowHub 要在写代码前把页面流程、状态、设计来源、组件边界和验收证据说清楚，并让新旧项目都能从可读的项目级 `Design.md` 开始。
- **核心改动点**：
  - 自动判断是否涉及 UI；不能由调用方把 UI 任务伪装成非 UI。
  - 新项目和历史项目都先建立可追溯的设计来源与组件边界。
  - build-spec 先用真实组件、固定假数据和预览设计；不满意时生成简短设计提示词，人工确认后仍可继续。

- **最大影响面**：所有新增或修改 Web UI 的 WorkflowHub 任务，以及缺少 `Design.md` 或组件边界的历史项目。
- **验收信号**：build-code 开始前已有可读的交互流程、状态矩阵、设计版本/缺口、组件化计划和可执行的视觉/浏览器验收要求；缺失项被诚实记录，不被伪装成完成。

## 1. 问题与紧迫性

现在的 WorkflowHub 可以约束需求、规格和工程阶段，却没有把 UI 设计和前端组件质量放在正确的时间点。结果是：前期只写 spec 和 plan，build-code 才开始猜页面；设计改动没有交互状态和组件边界；历史项目没有 `Design.md` 时只能临时摸索；组件和 CSS 容易重复、泄漏、缺状态，最后只能靠长时间反复提示和人工补丁收尾。

这不是单个 PaperBuilder 页面的问题，而是 WorkflowHub 的通用交付契约缺失。若不在 build-spec 解决“先看见并确认设计”的问题，后续任何 UI 项目都会把设计成本和返工风险推迟到 build-code，无法稳定复用。

## 2. 背景、目标与范围

### 背景

WorkflowHub 的当前真相由 `decision-log.md`、`spec.md`、`plan.md` 和 `tasks.md` 组成。make-decision 负责冻结用户流程和边界，build-spec 负责产品行为，build-plan 负责组件和工程计划，build-code 负责实现，verify-code 负责消费者、兼容性和视觉/浏览器事实。本需求把 UI 交付需要的事实接入这条既有链路，不新增一套平行历史或状态机。

`Design.md` 是整个项目通用的设计来源，记录可读的视觉规则、组件约束和页面设计原则；它不绑定某一任务的临时状态。任务只引用项目级设计版本、生成当前页面的 Screen Read Map，并记录本任务的 UI Contract、缺口和确认事实。

### 目标

- 让 UI 任务在进入 build-code 前拥有完整的用户流程、页面范围、状态、交互、组件边界和设计证据。
- 让新项目能建立设计与组件基础，让历史项目能先做只读盘点和小范围初始化，不强迫整仓重构。
- 让真实组件、固定假数据、预览/Story、浏览器测试和截图成为可复查的产品证据，而不是“有截图就算完成”。
- 让组件复用、修改、增加状态/变体、新增局部组件、共享抽取和无消费者删除都有真实消费者与状态拥有者依据。
- 保持流程简单：没有设计稿、预览宿主或某项证据时，明确记为 `unknown` / `unavailable` / `N/A`，经人工确认可以继续，不把质量事实变成自动闸门。

### 范围内

- UI 适用性自动判定及 `ui`、`non_ui`、`unknown` 结果。
- 新项目/历史项目的 UI 初始化与项目级 `Design.md` 来源登记。
- Design Source Readiness、Screen Read Map、页面/区域/交互/状态/UI Contract。
- build-spec 的真实组件 + 固定 fixture + viewport 预览环节，以及简短设计提示词回路。
- build-plan 的组件动作、状态拥有者、类型化 ViewModel、CSS/token 归属、前端测试和截图字段。
- build-code 对确认设计的实现边界，verify-code 对消费者、兼容性、CSS 泄漏和视觉事实的检查。
- React/Next 项目的 Vercel MIT `react-best-practices` 作为内部参考规则；不新增独立阶段或闸门。

## 3. 用户场景与状态覆盖

> 场景覆盖正常、边界、失败和权限路径，并说明用户可观察结果。这里的“页面”也包括 WorkflowHub 用来描述目标产品页面的交付记录，不是本任务去实现某个业务页面。

### SCN-001：判断 UI 适用性

- **角色**：WorkflowHub 任务发起者与工作流运行时
- **Given**：已有原始需求、项目盘点和当前计划/变更事实
- **When**：任务进入 make-decision 或后续阶段
- **Then**：系统依据可信事实给出 `ui`、`non_ui` 或 `unknown`；调用方的 UI 标记不能降低已有 UI 事实的结论，`unknown` 记录原因和风险。

### SCN-002：新项目建立 UI 基础

- **角色**：新项目的开发者
- **Given**：项目没有可用的 `Design.md` 或组件/样式边界
- **When**：选择新项目初始化
- **Then**：系统记录项目级 `Design.md` 路径与版本（或明确缺失）、组件和样式边界、fixture 形状、viewport 及预览/截图卡；不把本任务状态写进项目通用设计来源。

### SCN-003：历史项目先盘点再收缩

- **角色**：维护历史项目的开发者
- **Given**：项目已有页面和前端代码，但缺少 `Design.md`、组件消费者或 CSS 归属事实
- **When**：选择历史项目初始化
- **Then**：系统只读盘点现有组件、样式、首个页面和风险，提出最小收缩建议并请求人工确认；不会自动全仓重构，也不会把未查明内容写成已完成。

### SCN-004：读取项目级设计来源

- **角色**：产品/设计/前端协作者
- **Given**：项目有一个当前 `Design.md` 版本或该来源缺失
- **When**：build-spec 读取设计来源
- **Then**：得到当前页面的 Screen Read Map 和 `bindable`、`not_bindable` 或 `unknown` 绑定状态；缺失项带代码、理由和人工待办，不创建第二份设计真相。

### SCN-005：在 build-spec 设计页面与状态

- **角色**：产品/前端协作者
- **Given**：页面范围和用户流程已经在 make-decision 冻结
- **When**：build-spec 设计 UI Contract
- **Then**：默认用真实组件、固定假数据和明确 viewport 做预览/Story，覆盖默认、加载、空、错误、禁用/权限、长内容/溢出和窄视口等状态；设计未满意时不能偷偷把设计工作推到 build-code。

### SCN-006：设计不满意时生成短提示词

- **角色**：需要外部设计工具帮助的开发者
- **Given**：预览不可用、设计结果不满意或需要外部设计工具
- **When**：请求重新设计
- **Then**：得到只包含页面/区域、交互、状态和可见 label 的短提示词；用户可以同时提供修改后的完整 `Design.md` 或新版本，也可以只给设计意见。预览失败、不满意、取消等待、外部设计未返回或版本不一致时，都保留当前事实并显示可恢复动作；缺失的 viewport、fixture、截图或设计稿记录为事实，不被伪装成通过。

### SCN-007：人工确认设计缺口并继续

- **角色**：人工确认者
- **Given**：设计来源或预览存在 `unknown`、`unavailable`、`N/A` 或暂未满意项
- **When**：人工确认当前风险并继续
- **Then**：记录 `approved`、`acknowledged` 或 `not_approved` 的确认结果和当前设计版本引用；三种结果在记录风险后都可以进入 build-plan 和后续实现，`approved` 才能标记设计就绪，`acknowledged`/`not_approved` 保持 `not_ready`/`unknown`。后续计划必须绑定风险，任何结果都不能宣称视觉完成。

### SCN-008：按组件化契约交接实现

- **角色**：前端开发者
- **Given**：UI Contract 和设计版本已确认或缺口已明确
- **When**：build-plan 规划并交接 build-code
- **Then**：每个 UI 阶段说明组件动作（复用、修改、增加状态/变体、新增局部、抽取共享、无消费者删除）、真实消费者、状态拥有者、类型化 ViewModel、单一 CSS/token 归属、测试/浏览器/截图的阶段和所需 viewport、fixture、状态；不能用“做页面”代替这些事实。

### SCN-009：验证实现与回归边界

- **角色**：验证者
- **Given**：实现完成，可能存在新旧组件共存、跨页面复用或设计版本变化
- **When**：verify-code 检查 UI 交付
- **Then**：验证真实消费者、状态覆盖、组件兼容性、CSS 泄漏、浏览器行为和视觉/人工证据；截图只证明某次观察，不单独证明设计完整或质量通过。

### SCN-010：上游流程未冻结或材料互相冲突

- **角色**：build-spec 阶段执行者
- **Given**：make-decision 尚未完成，或当前页面范围、用户流程、状态、非目标与决策日志互相冲突/无法核验
- **When**：build-spec 尝试写入规格
- **Then**：保留 `unknown`、冲突事实和影响，不自行补充用户需求；把方向性缺口交回 make-decision，同时继续完成不依赖该缺口的安全整理。

### 状态覆盖清单

| 状态 | 结论 | 场景 | 处理规则 |
| --- | --- | --- | --- |
| 默认态 | 适用 | SCN-005、SCN-009 | 展示主要内容与核心操作 |
| 空态 | 适用 | SCN-005 | 固定 fixture 明确“没有数据”时的 label 与下一步 |
| 错误态 | 适用 | SCN-005、SCN-009 | 显示可理解错误和可恢复动作 |
| 加载态 | 适用 | SCN-005 | 说明等待中、避免布局跳动与重复提交 |
| 取消态 | 适用 | SCN-006、SCN-007 | 用户可停止外部设计/预览等待，保留未完成事实 |
| 边界态 | 适用 | SCN-003、SCN-005、SCN-009 | 长文本、溢出、窄视口、组件跨页复用需可观察 |
| 权限态 | 适用 | SCN-005、SCN-009 | 禁用、隐藏和无权操作必须有明确 label 与理由 |
| 竞态 | 适用 | SCN-006、SCN-007、SCN-009 | 设计版本、预览结果或状态更新冲突时保留最新来源并标记风险 |

### 页面/区域状态交互契约

状态名称本身不算覆盖。每个页面/区域的每个适用状态，都必须在 UI Contract 或其引用的 Screen Read Map 中写出以下最小字段；不同状态可以共用 fixture，但必须说明共用关系和差异。

- **visible_structure**：用户能看到的结构、主要内容、提示和可见 label。
- **fixture_shape**：固定假数据的形状、关键值、长文本/空数据/错误数据的代表性；没有 fixture 时写 `N/A` 和原因。
- **available_actions**：当前可操作的按钮、链接、输入和它们的可见 label。
- **disabled_actions**：不可用、隐藏或无权限的操作、原因和用户看到的说明。
- **trigger**：进入该状态的用户动作、系统事件或失败条件。
- **recovery_or_exit**：取消、返回、重试、修复或完成后进入的下一状态，以及用户看到的操作 label。
- **permission_result**：允许、拒绝、只读或需人工确认的结果；不适用时写 `N/A` 和原因。
- **preview_browser_screenshot_assertion**：预览、浏览器和截图分别要观察什么；证据缺失时写 `unknown`、`unavailable` 或 `N/A` 和原因。

响应式和无障碍属于同一状态契约：窄视口必须说明重排、溢出处理、操作优先级和触控可达性；适用时必须说明 accessible name、语义角色、焦点顺序、键盘路径、错误提示关联和对比度意图。真正不适用才可写 `N/A`，不能用“窄屏支持”或“有 label”代替这些字段。

### 预览与设计确认状态转移

以下是现有四份材料和阶段技能中需要记录的状态与可见操作 label，不是新增管理页面、后台、第五材料或 runtime 状态机。它们只描述当前 UI Contract 的记录/交接事实；项目若没有对应可见界面，写 `N/A` 和原因。

- `preview_ready`：显示预览和“确认设计 / 需要修改”两个可见动作；状态契约和观察断言随预览保留。
- `preview_unavailable` 或 `design_read_error`：记录原因和“重新读取 / 生成设计提示词 / 继续并记录风险”；重试保留原失败事实，成功后只把新读取结果作为当前版本候选。
- `design_prompt_ready`：记录短提示词；“取消”只结束本次外部设计等待，不删除当前 UI Contract 或失败事实。
- `external_design_pending`：等待用户返回完整 `Design.md` 或新版本；“未返回”保留等待超时/缺失事实，不自动视为满意。
- `external_design_returned`：版本一致时可进入人工确认；版本缺失或不一致时显示“重新读取并确认”，旧版本不能冒充当前设计。
- `human_approved` / `human_acknowledged`：允许交接 build-plan，保留所有未知项和返工风险。
- `human_not_approved`：保持 `design_status=not_ready`/`unknown`，记录缺口与返工风险；人工确认后仍可交接 build-plan/build-code，后续补设计是风险处理，不是推进前置条件。

  - **owner、影响**：由当前项目的 build-plan/人工确认补齐；影响预览证据强度，但不改变继续推进的权利；关联 `RISK-UI-001`、`OPEN-UI-001`
  - **关联**：FR-UI-005、FR-UI-006、FR-UI-007、FR-UI-010、AC-UI-005、AC-UI-006、AC-UI-007、AC-UI-010

## 5. 功能需求

### UI 适用性与项目初始化（UI-APPLICABILITY）

本域让 WorkflowHub 先识别 UI 范围，再为新旧项目建立最小可用的设计与组件事实。初始化产物是项目级来源和风险记录，不是某任务的第二份设计文档。

- **FR-UI-001**：WorkflowHub 必须根据原始需求、项目盘点和计划/变更事实自动判定 UI 适用性，并输出 `ui`、`non_ui` 或 `unknown`。
  - **范围边界**：包含可信事实合并和理由；不包含让调用方用一个标记覆盖事实。
  - **依据**：R-002、D-001、PFACT-UI001
  - **场景**：SCN-001
  - **验收**：AC-UI-001

- **FR-UI-002**：WorkflowHub 必须提供新项目和历史项目两条初始化路径。
  - **范围边界**：新项目建立最小设计/组件基础；历史项目只读盘点、指出首个页面和风险并提出最小收缩建议；不自动整仓重构。
  - **依据**：R-009、D-009、D-010、PFACT-UI003、PFACT-UI004
  - **场景**：SCN-002、SCN-003

### Design.md 与交互契约（UI-DESIGN-SOURCE）

本域把项目级 `Design.md` 变成可读、可复核的来源，并在 spec 中表达交互流程和状态。它不要求每个任务复制整份设计，也不要求必须有外部设计工具。

- **FR-UI-003**：新项目初始化必须记录项目级 `Design.md` 的路径和版本；若来源不存在，必须记录缺失、影响和后续人工动作。
  - **范围边界**：版本是项目设计版本字符串；不要求 SHA-256，也不把任务状态写入来源。Design Source Readiness 还要检查稳定的页面/章节锚点、目标与主操作、状态清单、组件/token 来源、fixture、viewport、响应式与无障碍意图、已有证据的新鲜度、缺项代码和人工待答项。
  - **依据**：R-007、R-009、D-007、D-009、D-013、PFACT-UI002、PFACT-UI003
  - **场景**：SCN-002、SCN-004
  - **验收**：AC-UI-003

- **FR-UI-004**：历史项目初始化必须产出可读的设计/组件盘点、首个页面、风险和最小收缩建议，并由人工确认是否采用。
  - **范围边界**：盘点是事实，不自动改造全部旧代码；允许先只覆盖一个页面或一条流程。
  - **依据**：R-009、R-010、D-010、D-012、PFACT-UI004
  - **场景**：SCN-003、SCN-004
  - **验收**：AC-UI-004

- **FR-UI-005**：build-spec 必须为每个 UI 页面或区域维护交互流程、可见 label、状态矩阵和 UI Contract，并生成基于项目级设计来源的 Screen Read Map。
  - **范围边界**：包含默认、加载、空、错误、禁用/权限、长内容/溢出和窄视口等适用状态；每个适用状态必须填写状态交互契约的八类字段，并补充响应式和无障碍字段；不把设计来源复制成第二份真相。Screen Read Map 是完整性检查，不打分，也不是自动闸门。若上游页面范围、流程或状态未冻结/相互冲突，必须保留 unknown 并交回 make-decision，不得在本阶段补需求。
  - **依据**：R-004、R-007、R-008、R-010、D-004、D-007、D-008、D-012、PFACT-UI002、PFACT-UI010
  - **场景**：SCN-004、SCN-005、SCN-010
  - **验收**：AC-UI-005

### 预览、提示词与人工确认（UI-PREVIEW）

本域把设计问题暴露在 build-spec。默认先用真实组件和固定假数据预览；预览缺失或不满意时，输出最小提示词并保留未知事实。人工确认可以让流程继续，但不会把未知改写为完成。

- **FR-UI-006**：build-spec 必须优先使用真实组件、固定 fixture 和明确 viewport 做可观察预览或 Story，并记录实际覆盖的状态。
  - **范围边界**：预览是设计判断输入，不是最终实现证明；没有可用宿主或 fixture 时允许 `unavailable`/`N/A`。预览、浏览器和截图分别遵守状态契约中的观察断言；没有截图不能阻止继续，但必须保留缺失事实。
  - **依据**：R-008、R-011、D-008、D-020、D-021、PFACT-UI005、PFACT-UI010
  - **场景**：SCN-005、SCN-006
  - **验收**：AC-UI-006

- **FR-UI-007**：预览不满意或不可用时，WorkflowHub 必须生成简短设计提示词，只包含页面/区域、交互、状态和可见 label，并允许用户带回完整 `Design.md` 或新版本。
  - **范围边界**：不在提示词中重复 viewport、fixture、响应式和无障碍长清单；这些约束仍由 UI Contract、Design.md 和验收事实管理。提示词路径必须支持取消、未返回和版本不一致的恢复状态。
  - **依据**：R-011、R-008、D-011、D-013、D-020、PFACT-UI005、PFACT-UI010
  - **场景**：SCN-006、SCN-007
  - **验收**：AC-UI-007

- **FR-UI-008**：人工确认设计缺口后，WorkflowHub 可以继续进入 build-plan，但必须保留设计状态、缺失项、原因、假设、返工风险、预览/fixture/viewport/截图事实、设计版本和当前材料引用。
  - **范围边界**：人工确认是继续依据，不是视觉质量通过；确认结果必须区分 `approved`、`acknowledged`、`not_approved`；只有 `approved` 能标记设计就绪，另外两种结果在记录风险后也可继续进入后续阶段。
  - **依据**：R-010、R-011、D-012、D-013、D-025、D-030、PFACT-UI010
  - **场景**：SCN-006、SCN-007
  - **验收**：AC-UI-008

### 组件化与前端质量（UI-COMPONENT-QUALITY）

本域保证后续实现围绕真实组件和消费者组织，而不是在页面中堆叠一次性 CSS。公共能力以 `frontend-component-quality` 提供；React/Next 参考规则只是其中的内部依据。

- **FR-UI-009**：build-plan 必须为每个 UI 阶段声明组件动作、真实消费者、状态拥有者、类型化 ViewModel、单一 CSS/token 归属和变更后的 Stories/测试要求。
  - **范围边界**：组件动作包括复用、修改、增加状态/变体、新增局部、抽取共享和无消费者删除；共享抽取需至少两个真实消费者；不强制指定 CSS 框架。
  - **依据**：R-011、D-014 至 D-019、D-026、D-025、PFACT-UI006、PFACT-UI008、PFACT-UI009
  - **场景**：SCN-008、SCN-009
  - **验收**：AC-UI-009

- **FR-UI-010**：组件和 CSS 质量检查必须能发现真实消费者缺失、状态遗漏、CSS 泄漏、跨功能覆盖和与设计来源不一致；截图不能替代这些事实。
  - **范围边界**：全局 CSS、`!important` 或跨功能覆盖需要有明确理由；阈值和工具由 build-plan 根据项目事实选择，不在本规格锁死。
  - **依据**：R-008、R-011、D-018 至 D-024、D-026、PFACT-UI006、PFACT-UI007、PFACT-UI009、PFACT-UI010
  - **场景**：SCN-008、SCN-009
  - **验收**：AC-UI-010

### 阶段交接与回归（UI-HANDOFF）

本域把 UI 事实交接给 plan、code 和 verify，确保改动所在阶段有对应的前端测试和截图要求，并保留新旧项目的回归边界。

- **FR-UI-011**：涉及 UI 改动的 build-plan 阶段必须明确前端测试、浏览器检查、截图留存、viewport、fixture 和状态；build-code 只实现已确认的设计范围，verify-code 只根据当前材料和真实事实验收。
  - **范围边界**：没有截图或设计稿可以继续，但必须记录 `N/A`/`unknown` 及原因；不把外部 Figma、Storybook 或某个浏览器工具设为必选。测试和截图计划要能断言状态交互、响应式和无障碍字段，而不是只断言文件存在。
  - **依据**：R-003、R-008、R-011、D-020 至 D-030、PFACT-UI007、PFACT-UI009、PFACT-UI010
  - **场景**：SCN-008、SCN-009
  - **验收**：AC-UI-011

## 6. 模块划分

### UI 适用性与项目初始化

- **负责什么**：依据可信事实判定 UI 范围，并区别新项目与历史项目的最小初始化路径。
- **对外提供什么**：适用性结论、项目设计/组件盘点、首个页面、风险和人工确认事项。
- **依赖谁**：原始需求、项目现状和当前计划/变更事实。
- **测试边界**：能识别 UI、非 UI 和未知；历史项目不会被自动整仓重构。

### Design Source Readiness 与 UI Contract

- **负责什么**：读取项目级 `Design.md` 版本，生成包含页面/章节锚点、目标/主操作、状态清单、组件/token 来源、fixture、viewport、响应式与无障碍意图、证据新鲜度、缺项代码和人工待答项的 Screen Read Map，并生成交互流程、状态矩阵和设计缺口。
- **对外提供什么**：可绑定/不可绑定/未知状态、缺失项、短提示词和人工确认事实。
- **依赖谁**：项目级设计来源、make-decision 冻结的页面范围和用户流程。
- **测试边界**：新版本能重新确认，缺失来源不会被宣称为完整设计；Read Map 缺项可被机器发现并交给人工确认，不打分、不成为自动闸门。

### 前端组件质量与阶段交接

- **负责什么**：表达组件动作、真实消费者、状态拥有者、ViewModel、CSS/token 归属和测试/截图要求。
- **对外提供什么**：可供 build-plan、build-code、verify-code 消费的组件化质量契约和回归事实。
- **依赖谁**：UI Contract、Design Source Readiness 和项目现有组件盘点。
- **测试边界**：复用/修改/增状态/新增/抽取/删除均有消费者与状态依据；CSS 问题和状态遗漏可被发现。

## 7. 关键实体

- **UI 适用性事实**：代表一次任务对 UI 的可信判定；字段包括结论、来源事实、原因、未知项和风险引用；结论只能为 `ui`、`non_ui` 或 `unknown`。
- **项目设计来源引用**：代表项目级 `Design.md` 的路径、版本、绑定状态、缺失代码和人工待办；不包含任务临时状态，也不以 SHA-256 作为必需字段。
- **Screen Read Map**：代表从项目设计来源读取出的页面/区域锚点、目标与主操作、视觉规则、组件/token 来源、状态清单、fixture、viewport、响应式/无障碍意图、证据新鲜度和可绑定关系；缺项带代码和人工待答项。它是派生读图，不是第二份设计真相。
- **UI Contract**：代表当前任务页面/区域的交互、可见 label、状态交互契约、假数据、viewport、响应式/无障碍断言、预览事实和设计状态；引用项目设计版本和当前材料。
- **组件质量映射**：代表组件动作、真实消费者、状态拥有者、ViewModel、CSS/token 归属、测试/Story 和变更影响；一项映射必须能回到 UI Contract。
- **设计确认**：代表人工对当前设计版本和缺口的继续决定；包含确认结果、缺失/未知原因、返工风险和交接阶段，不改变项目级 `Design.md`。

## 8. 数据和生命周期

- **数据粒度**：每条 UI 适用性、项目初始化、设计来源、UI Contract、组件质量映射和设计确认对应一个任务/项目/页面区域或组件变更事实，并带稳定 ID。
- **数据时效**：项目级设计来源版本变化时重新读取；任务的 UI Contract 在 build-spec 冻结，plan/code/verify 只引用和补充各自阶段事实；不覆盖旧事实。
- **缺失或迟到**：没有 `Design.md`、预览宿主、fixture、viewport、截图或外部设计返回时保留 `unknown`、`unavailable` 或 `N/A` 及原因；人工确认后可以继续，但返工风险进入交接。
- **预览与正式**：预览使用真实组件和固定假数据，只表达设计可见性；正式实现由 build-code 依据 UI Contract 及已记录的缺口/风险完成，`not_ready`/`unknown` 不自动阻止实现；verify-code 依据真实消费者和浏览器/视觉事实验收，不能把缺口改写成设计完成。
- **当前与历史**：当前任务只引用当前项目设计版本和当前材料；历史设计/审查/测试事实只读保留，不创建 successor、replacement 或第二份当前投影。
- **归属与清理**：项目级设计来源由项目维护者持有；任务级 UI Contract、质量映射和确认随任务材料保存；无消费者组件可以在有事实依据时标记删除，不清理仍被历史或当前消费者引用的来源。

## 9. 兼容性预留

- **既有消费方**：非 UI 任务继续走原有流程；已有 `Design.md` 的项目只增加版本引用和读图结果；历史项目可先局部初始化，不要求一次迁移全部页面。
- **命名预留**：稳定 ID 使用 UI、SCN、PFACT、FR、AC、RISK、OPEN 前缀；项目设计版本使用项目已有版本表达，不引入哈希作为强制命名。
- **容器预留**：UI Contract 可以容纳页面、区域、状态、viewport、fixture、预览和人工确认；组件质量映射可以容纳复用、修改、增状态/变体、局部新增、共享抽取和删除。
- **状态预留**：适用性保留 `ui`、`non_ui`、`unknown`；设计绑定保留 `bindable`、`not_bindable`、`unknown`；质量事实保留 `unknown`、`unavailable`、`N/A` 而不把它们强转为通过/失败。
- **扩展边界**：允许未来接入 Figma Make、其他设计工具、Storybook 或浏览器工具，但本期不绑定供应商，也不新增独立公共阶段。

## 10. 明确不做与默认必须成立

### 明确不做

- 不修改 F11、F12a 或 PaperBuilder 现有页面和前端代码；来源 `R-006`、`D-006`，交给独立后续任务。
- 不在本任务实现具体产品页面、业务 API、数据库或视觉成品；来源 `R-001`、`D-002`。
- 不复制 AgentHub 的多阶段 manifest、双真相历史状态机、caller UI flag 或 successor/replacement 机制；来源 `R-003`、`R-004`、`R-011`、`D-026` 至 `D-030`。
- 不新增 UI 管理页面、后台服务、第五份当前材料或独立 runtime 状态机；本规格中的预览/确认状态只表示既有材料中的记录和交接事实，来源 `R-004`、`D-010`、`D-026`、`D-030`。
- 不强制 Figma、Figma Make、Storybook、Chromatic、某个 CSS 框架或某个浏览器供应商；来源 `R-011`、`D-011`、`D-026`。
- 不把 Design.md 绑定单个任务的状态，不要求 SHA-256，不把截图存在当成视觉质量完成；来源 `R-007`、`R-010`、`D-007`、`D-012`、`D-025`。
- 不因为没有设计稿、预览或截图而自动阻止推进；来源 `R-008`、`R-010`、`R-011`、`D-012`、`D-025`、`D-030`。

### 默认必须成立

- UI 适用性由可信事实推导，调用方不能降级结论（FR-UI-001、AC-UI-001）。
- `Design.md` 是项目通用来源；任务只引用版本并维护当前页面的 UI Contract（FR-UI-003、FR-UI-005、AC-UI-003、AC-UI-005）。
- build-spec 先做 UI 设计，build-code 不承担临时设计；设计不满意时使用短提示词并保留人工确认（FR-UI-005 至 FR-UI-008、AC-UI-005 至 AC-UI-008）。
- make-decision 未完成、页面范围/流程/状态冲突或来源不可核验时，build-spec 不得自行补需求；保留 unknown/冲突事实并交回上游（FR-UI-005、AC-UI-005）。
- 组件质量必须有真实消费者、状态拥有者和单一 CSS/token 归属；修改或增加状态需要同步 Stories/测试事实（FR-UI-009、FR-UI-010、AC-UI-009、AC-UI-010）。
- 每个 UI 改动阶段要明确前端测试和截图要求；缺失证据必须如实标记并交接风险（FR-UI-011、AC-UI-011）。

## 11. 验收标准

- [ ] **AC-UI-001**：同一组可信 UI 事实会得到稳定的 `ui`/`non_ui`/`unknown` 结论，调用方的降级标记不能把 `ui` 变成 `non_ui`。
  - **需求**：FR-UI-001
验证：用含页面/交互事实、明确非 UI 事实和事实不足的三组任务材料各走一次适用性判断。
  - **通过条件**：三组结论分别可观察且理由指向输入事实；事实不足保留 unknown 与风险。
失败：仅凭调用方 flag 判定、事实被丢失，或 unknown 被写成 non_ui/完成。
  - **证据类型**：`test` / `evidence`

- [ ] **AC-UI-002**：新项目和历史项目初始化都能给出各自的最小结果，历史项目不会自动整仓重构。
  - **需求**：FR-UI-002
验证：分别提供无设计基础的新项目和有遗留页面但缺少设计来源的历史项目材料。
  - **通过条件**：新项目有设计/组件边界及预览卡；历史项目有只读盘点、首个页面、风险、收缩建议和人工确认项。
失败：两类项目共用不可执行的空结果，或初始化直接修改全仓代码。
  - **证据类型**：`manual` / `evidence`

- [ ] **AC-UI-003**：项目级 `Design.md` 能以版本字符串被引用；缺失来源被明确记录而不冒充完整。
  - **需求**：FR-UI-003
验证：分别读取有版本、无来源和返回新版本的项目设计来源。
  - **通过条件**：路径/版本/绑定状态可读；新版本触发重新确认；无来源带缺失原因和人工待办。
失败：把任务状态写回通用来源、强制哈希或把缺失当成通过。
  - **证据类型**：`evidence` / `manual`

- [ ] **AC-UI-004**：历史项目的盘点结果能指导一个小范围页面开始，而不要求一次性清理旧代码。
  - **需求**：FR-UI-004
验证：人工检查盘点、首个页面、风险、最小收缩建议和确认记录。
  - **通过条件**：每项建议都有来源事实和影响；人工可选择采用、延后或继续观察。
失败：建议没有消费者/风险依据，或把未盘点的全仓组件宣称为已治理。
  - **证据类型**：`manual` / `evidence`

- [ ] **AC-UI-005**：每个 UI 页面/区域的 spec 都有交互流程、可见 label、状态矩阵和 Design Source Readiness 结果。
  - **需求**：FR-UI-005
验证：检查当前 spec 的场景卡、状态覆盖、UI Contract 和 Screen Read Map 引用，以及每个适用状态的 visible_structure、fixture_shape、available_actions、disabled_actions、trigger、recovery_or_exit、permission_result、preview/browser/screenshot_assertion、响应式和无障碍字段。
  - **通过条件**：正常、空、加载、错误、权限/禁用、边界/窄视口和竞态均有完整状态契约或 N/A 理由；来源版本、页面/章节锚点、组件/token 来源和缺口可追溯。
失败：只有视觉形容词或页面名，没有交互/状态/恢复/无障碍/响应式；或创建第二份 Design.md 真相。
  - **证据类型**：`evidence` / `manual`

- [ ] **AC-UI-006**：build-spec 默认能用真实组件、固定 fixture 和 viewport 产生可观察预览事实。
  - **需求**：FR-UI-006
验证：对可用预览宿主检查指定状态、响应式和无障碍观察断言，对不可用宿主检查 N/A/unavailable 记录。
  - **通过条件**：预览标明实际组件、fixture、viewport、状态、可见结构、操作和观察结果；不可用时保留原因与风险。
失败：用占位组件冒充真实预览，或只有截图文件没有来源与状态说明。
  - **证据类型**：`evidence` / `manual`

- [ ] **AC-UI-007**：预览不满意时得到短提示词，用户可带回完整 Design.md 或新版本。
  - **需求**：FR-UI-007
验证：模拟预览不满意、预览不可用、取消等待、外部设计未返回和版本不一致路径，人工读取提示词、可见操作、状态转移和版本引用。
  - **通过条件**：提示词只说页面/区域、交互、状态、label；每条失败路径都记录“重新读取 / 生成提示词 / 继续并记录风险”等恢复动作；返回的设计版本可重新读取和确认。
失败：提示词复制长篇工程约束，取消或未返回后丢失事实，或外部结果被当作无版本的隐式真相。
  - **证据类型**：`manual` / `evidence`

- [ ] **AC-UI-008**：人工确认未知项后可以继续，但未知、unavailable、N/A、返工风险和当前材料引用仍可见。
  - **需求**：FR-UI-008
验证：在无设计稿或预览失败的材料上分别执行 `approved`、`acknowledged`、`not_approved` 人工确认，再检查 build-plan 交接事实。
  - **通过条件**：三种结果都可在记录风险后继续；`approved` 才能标记 ready，`acknowledged`/`not_approved` 保持 not_ready/unknown；确认不改变事实状态，不宣称视觉完成。
失败：缺失项或 not_approved 自动阻断推进，或确认被错误转换成质量通过/ready.
  - **证据类型**：`manual` / `evidence`

- [ ] **AC-UI-009**：每个组件动作都有真实消费者、状态拥有者、ViewModel、CSS/token 归属和必要的 Stories/测试更新说明。
  - **需求**：FR-UI-009
验证：抽查复用、修改、增加状态/变体、局部新增、共享抽取、无消费者删除各一项。
  - **通过条件**：共享抽取至少有两个真实消费者；状态变更能回到拥有者；React/Next 参考规则可追溯但不成为额外阶段。
失败：只有页面文件或截图，没有消费者/状态/CSS 归属；或把参考规则当成独立闸门。
  - **证据类型**：`evidence` / `manual`

- [ ] **AC-UI-010**：质量检查能发现组件与 CSS 的边界问题，且不会把截图当成唯一完成信号。
  - **需求**：FR-UI-010
验证：用跨页面 CSS 覆盖、重复组件、遗漏状态和无消费者组件的样例进行检查。
  - **通过条件**：问题指出真实消费者、影响和处理建议；全局覆盖或 `!important` 有理由；阈值可按项目事实解释。
失败：检查只看命名/截图，或无依据地判定所有质量通过。
  - **证据类型**：`test` / `evidence`

- [ ] **AC-UI-011**：每个涉及 UI 的计划阶段都有前端测试、浏览器检查、截图、viewport、fixture 和状态要求，且 build-code/verify-code 按已确认设计交接。
  - **需求**：FR-UI-011
验证：检查一项有 UI 改动的计划交接及其实现、浏览器和视觉回归记录，逐项对照状态交互、响应式和无障碍断言。
  - **通过条件**：测试与截图要求写在对应阶段；缺失证据为 N/A/unknown 并有原因；验证能区分实现事实和视觉完成，且不是只检查文件存在。
失败：测试只在最后补写，或 build-code 临时重新设计并覆盖已确认范围。
  - **证据类型**：`evidence` / `manual`

## 12. 风险、未决与交接

- **RISK-UI-001**：项目没有可用设计来源、预览宿主或固定 fixture，导致 build-spec 的视觉判断不足。
  - **受影响 ID**：PFACT-UI010、FR-UI-005、FR-UI-006、FR-UI-008、FR-UI-011、AC-UI-005、AC-UI-006、AC-UI-008、AC-UI-011
  - **触发条件**：读取失败、历史项目未初始化或外部设计未返回。
  - **后果**：实现可能需要返工，视觉事实不完整。
  - **缓解或 STOP**：记录 unknown/unavailable/N/A、生成短提示词并取得人工确认；不把缺失证据写成通过。只有产品流程本身无法说明页面/交互时才回 make-decision。
  - **处理 Stage**：`build-spec` / `build-plan`
验证：确认记录、版本引用、返工风险和阶段测试/截图要求均可追溯。

- **RISK-UI-002**：Design.md 与代码中的组件规则逐渐漂移，形成双重真相。
  - **受影响 ID**：PFACT-UI002、FR-UI-003、FR-UI-005、FR-UI-009、AC-UI-003、AC-UI-005、AC-UI-009
  - **触发条件**：组件修改未回写项目来源，或任务复制整份设计内容。
  - **后果**：新页面按旧规则实现，审查无法判断哪个版本有效。
  - **缓解或 STOP**：只引用项目设计版本，变更时更新来源并重新确认；禁止任务级第二份通用设计。
  - **处理 Stage**：`build-plan` / `verify-code`
验证：检查当前版本引用、变更后的组件规则和消费者事实是否一致。

- **RISK-UI-003**：重复或伪造组件消费者、旧截图和非 UI 标记掩盖真实质量问题。
  - **受影响 ID**：PFACT-UI001、PFACT-UI006、FR-UI-001、FR-UI-009、FR-UI-010、AC-UI-001、AC-UI-009、AC-UI-010
  - **触发条件**：只检查文件存在、截图存在或调用方 flag，不检查真实消费者和当前材料。
  - **后果**：组件不可复用、CSS 泄漏，非 UI 任务逃过 UI 契约。
  - **缓解或 STOP**：适用性使用可信事实；质量检查绑定真实消费者、状态拥有者和当前版本；旧证据只能作为历史事实。
  - **处理 Stage**：`build-plan` / `verify-code`
验证：消费者、状态、CSS、浏览器和设计版本的事实链完整且没有伪造通过。

- **OPEN-UI-001**：不同项目如何选择 viewport 组合、fixture 规模和 CSS 质量阈值仍需按项目事实确定。
  - **受影响 ID**：PFACT-UI010、FR-UI-006、FR-UI-010、FR-UI-011、AC-UI-006、AC-UI-010、AC-UI-011
  - **owner**：当前项目的 build-plan 与人工确认者
  - **影响**：若不确定，预览和回归证据只能标记为 unknown/unavailable，不能比较不同项目的数值质量。
  - **处理 Stage**：`build-plan`
  - **关闭条件或 STOP**：在计划中写出本项目的 viewport、fixture、状态覆盖和阈值理由；若仍不可得，保留 N/A 和风险，不能宣称完成。

- **DEFER-001**：PaperBuilder/F11/F12a 的真实页面前端重构与历史组件治理。
  - **受影响 ID**：FR-UI-002、FR-UI-009、FR-UI-010、AC-UI-002、AC-UI-009、AC-UI-010
  - **owner**：后续独立 PaperBuilder 任务
  - **影响**：本任务只提供通用交付契约，不改变现有页面质量。
  - **处理 Stage**：后续独立任务的 `make-decision`
  - **关闭条件或 STOP**：新任务重新确认页面范围、设计版本、组件消费者和回归边界后再实施。

## 13. 业务影响与回归范围

### WorkflowHub UI 任务交付流程

- **既有行为**：UI 设计可能延迟到 build-code，组件、CSS 和截图事实分散在提示和临时文件中。
- **本需求影响**：make-decision 冻结流程，build-spec 设计并记录状态/预览/提示词，build-plan 绑定组件和测试，build-code 实现确认范围，verify-code 验证真实消费者和视觉事实。
- **回归路径**：UI 适用性 → 新/历史项目初始化 → Design Source Readiness → UI Contract/状态矩阵 → 真实组件/fixture/viewport 预览或短提示词 → 人工确认 → 组件化计划 → 前端测试/截图 → 实现 → 浏览器与视觉验证。
- **验收**：AC-UI-001 至 AC-UI-011。

- **可能受冲击的业务规则**：四份当前材料仍是唯一产品真相；审查、测试、截图和历史只产生事实，不成为继续工作的许可证；unknown、unavailable、incomplete 不能被改写成完成。
- **明确无影响**：非 UI 任务的原有流程、PaperBuilder/F11/F12a 当前实现、项目的业务 API/数据库，以及用户选择的具体设计供应商不在本期改变范围内。

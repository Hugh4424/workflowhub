# WorkflowHub 原则设计 v2：先定轴，再定模块，最后定原则

2026-11-21 · DeepSeek-V4.1-Flash（`auto/deepseek-v4.1-flash`）

---

## 0. 这一版改了什么

上一版犯了一个方法错误：我把复盘里的"七个方向"（需求收敛、计划设计、项目规范、执行质量、代码质量、验收测试、Agent 执行效率）直接当成了模块，然后为每个方向写原则。

**这七个方向不是一个切法。** 检查后有三个具体问题：

| 问题 | 表现 |
| --- | --- |
| 两个不是模块 | 「Agent 执行效率」是成本，不是被交出去的东西；「执行质量」的五条内容其实是"任务路由（工序层）+ 反馈环 + 状态身份 + 回原场景 + 攻击前提"，后四条分别属于判据和代码，自己没有独立内容 |
| 两处是缺口 | 「交付与交接」整个方向没有——但复盘里"收口把未验成写成通过""授权记录晚于动作四小时""修复重建上下文七次""61/108 条发现无处置"四个症状都落在这里；「流程自身」也没有——而用户此刻正在做的事就属于它 |
| 一处重叠 | 「项目规范」和「代码质量」互为生产者和对象，写在一起必然出现同一条原则两处各写一遍 |

结论：**先论证轴，再切模块，再写原则。** 本版结构是 0–4 章定方向，5–11 章写原则，12–14 章写落点、检验与边界。

材料分工不变：原则主要取自 `../外部调研/`（Lauren Tan 演讲、pstack 固定提交 `4a4f41c`、Matt Pocock 固定提交 `abeeaf95`、以及 05–16 的机制拆解）；`../任务报告/` 只用来确认"现在的错法长什么样"，不用来推导原则。

## 1. 一个切法要满足什么

在写任何原则之前，先把"模块"的定义钉住，否则切法只能靠手感。

### 1.1 四条判据

1. **唯一消费者。** 每一块必须能回答"下一位打开它的人是谁"。答不出，这一块的原则就无法判定"该改哪里"，只能写成"要做好"。
2. **单向关系。** 块与块之间只允许"生产 → 消费"。如果两块互相消费，它们不是两块，是一块。
3. **可判的完成条件。** 这一块能回答"怎么算它做好了"，而且这个回答不是"齐全""完整"这类词。
4. **症状映射全覆盖且不重叠。** 把复盘里的症状逐条放进去，每条必须落到**恰好一个**块。落到零个＝缺口，落到两个＝重叠。

第 4 条是最硬的检验，因为它可以机械执行。第 3 章会给这张表。

### 1.2 四个候选轴

| 轴 | 例子 | 好处 | 致命问题 | 结论 |
| --- | --- | --- | --- | --- |
| 按阶段 / 时间 | 需求 → 计划 → 执行 → 交付 → 复盘 | 和流程一一对应，好排期 | 同一阶段产三份交接物（build-plan 同时产 spec、phases、判定器）；同一份交接物被两个阶段写（spec 在 build-plan 写、build-code 引用并可能失效）。**同一条原则必然在两个阶段各写一遍** | 只适合当"工序层"，不能当模块轴 |
| 按质量属性 | 正确性 / 可维护性 / 效率 / 可追溯性 | 好向人解释 | 属性没有消费者。写"要可维护"无法回答"这条规则放哪、谁在读它"，最终退化成"都要做好" | 不行 |
| 按失败类型 | 目标错 / 顺序错 / 实现错 / 判据错 / 证据错 | 诊断时极好用 | 同一类失败散在多个阶段（判据错既发生在计划期冻结，也发生在执行期自证），无法指派负责流程 | 只适合当故障清单附录 |
| **按交接物 + 消费者** | 决策日志、计划合同、代码、判据与证据、交付与交接 | 每块有唯一消费者，判据①自动满足；生产者矩阵（第 12 章）把工序接回来 | 需要额外一层把"工序"接回来 | **采用** |

### 1.3 为什么原七方向会让人"都说了又都没说"

因为它同时用了两个轴：前三个（需求、计划、执行）是**时间轴**，后四个（规范、代码、验收、效率）是**质量属性轴**。混轴的结果是可以预测的：

- 时间轴上的"执行质量"必然与属性轴上的"代码质量""验收测试"重叠——所以它的内容被吸收掉，自己变空。
- 属性轴上的"效率"没有交付物，所以它只能写成一堆注意事项，无法指派。
- 两个真正贵的交接物（证据底座、交付与交接）在两个轴上都不显眼，于是缺席。

上一版 863 行里，"证据去重""收口把未验成写成通过""授权时机"这三类内容都被塞进了别的模块，读起来像是补充说明。这版把它们各自归位。

### 1.4 采用的轴：交接物

> **交接物 = 下一位在开始工作前必须打开的东西。**

这个定义有一个直接好处：它天然带一个消费者，而且"必须打开"可以验证——下一位如果没有打开它也能干活，说明它不是交接物，是参考资料。

按这条定义，现有流程里有七份：

```
                    ┌─────────────────────────────────────────┐
                    │  H0 规范与知识（作某类决定前必须打开）    │
                    └─────────────────────────────────────────┘
                                    ↓ 约束全部
  H1 决策日志 ──→ H2 计划合同 ──→ H3 代码与结构 ──→ H5 交付与交接 ──→ 用户 / 下一阶段
                        │                                    ↑
                        └──→ H4 判据与证据 ──────────────────┘
                                    ↑
                    ┌─────────────────────────────────────────┐
                    │  H6 流程自身（改 H0–H5 的规则与工具）     │
                    └─────────────────────────────────────────┘
```

一条主链五份（H1→H2→H3→H4/H5），一份贯穿（H0），一个回环（H6）。

### 1.5 被考虑过、但没有成为模块的东西

用户问"有没有更多方向"，所以把淘汰过程交代清楚。下面每一项都真实存在于 WorkflowHub 或外部调研，但按 1.1 的四条判据都不该成为模块：

| 候选 | 为什么不成为模块 | 它应该在哪 |
| --- | --- | --- |
| 失败分诊与调试 | 它的产物是"一个能判红的反馈环 + 一个根因"，分别属于 H4 和 H3，自己没有独立交接物 | H4.2、H4.5、H3.1 |
| 任务路由（新功能 / 修故障 / 重构） | 这是"用哪条工序"，属于工序层 | 第 12 章 build-code 行 |
| 模型与供应商选择（OCR / arena / 盲评） | 是"谁来判"，属于独立性与成本 | V3 视图 + H6.1 |
| UI / 设计源 / 组件库 | 是一个子领域，它的规则分别落在 H0（组件规范）、H2（入口与对照基准）、H4（视觉判定器） | 不单独成模块 |
| 知识图谱 | 是 H0 的一个实现，不是一条独立承诺。现在的问题是"查了就算用了" | H0.5 |
| 指标与度量 | 度量本身不交付任何东西；它是 H6.6 的四个信号 | H6.6 |
| 安全与权限边界 | 是 H0 的一类规则 + H5.3 的授权核对 | H0、H5.3 |
| 并发与共享状态 | 是 H3 的一种结构，不是独立承诺 | H3.1、H3.2 |
| 文档与写作规范 | 是 H0.6 的"指针而不是全文"，不是独立模块 | H0.6 |

反过来说，一个模块必须至少有两个独立的复盘症状落在它上面，否则它就是凑数。第 3 章的表会给出计数。

## 2. 对原七方向的逐条处置

| 原方向 | 判定 | 处置 | 理由 |
| --- | --- | --- | --- |
| 需求收敛 | 保留，改名 | **H1 决策与承诺** | 原名字只覆盖"收敛"，实际还要管承诺的生命周期（谁能改、改了谁失效）。T08 有 4 条被推翻的决定仍在生效，T03 的原要求被写成"重启后自动补写"而用户没这么说——这些不是"收敛没做好"，是"承诺没被管理" |
| 计划设计 | 保留，吸收 build-prd | **H2 计划合同** | build-prd 与 build-plan 产的是同一族交接物（顺序、切片、入口），消费者也是同一批人。Matt 明确建议 spec 与拆票在同一窗口跑完，因为边界很薄 |
| 项目规范 | 保留，改名 | **H0 规范与知识** | 重点从"规范文档写得好不好"移到"规则的落点选择 + 单一权威 + 历史知识的适用性" |
| 执行质量 | **拆掉** | 内容分给 H4（反馈环、回原场景、攻击前提）与 H3（状态身份），"任务路由"进第 12 章 | 它没有自己的交接物。一个模块如果为了容纳"怎么干活"而存在，就会持续吸收别的模块的内容，然后变成一个大而空的块 |
| 代码质量 | 保留 | **H3 代码与结构** | 唯一不变 |
| 验收测试 | **拆分** | 判据设计归 **H4**，"冻结时点与自证前置"归 **H2** | 原方向把"判据怎么写"和"什么时候允许冻结"混在一起。前者是判据质量问题，后者是计划合同的问题——T03 的 0.8 门槛是在计划期冻结的，出错位置在 H2 |
| Agent 执行效率 | **降级为视图** | **V3 成本与上下文** | 它是成本，不是交接物。作为视图，它要过的模块全部要过一遍，反而更有用 |
| — | 新增 | **H5 交付与交接** | 复盘里 6 个症状无家可归 |
| — | 新增 | **H6 流程自身** | 复盘里 3 个症状无家可归，而且它是唯一能让其他六个模块逐步变好的回环 |

**数量仍是七个，但成分不同：两个被拆、一个被降级、两个新增、一个改名。** 这不是巧合，是轴换了之后自然收敛到的粒度。

## 4. 三个质量视图（不是模块）

视图是**每个模块都要过一遍的检查**，不是原则，不占编号为模块。它们存在的理由是：有些问题不属于任何单一模块，但会在所有模块里以不同面目出现。

### V1 真实性：谁产出、谁读、能不能回到原件

三句话：
1. 这个结论是**谁**产生的？产出者和判定者是同一个吗？
2. **谁读它**？读的人有没有能力核它（拿到同一个原件）？
3. 从这条结论出发，**三次点击内**能不能到达它声明的原件？

如果三条都过不了，这条结论是叙述，不是事实。WorkflowHub 现在最贵的教训就是这个：make-decision 任务里需求、计划、测试、门禁、回执都由同一执行系产出，独立审查只能核一致性，核不了"事实是否成立"——于是四张含错的卡全过了计划审查。[make-decision 复盘](../任务报告/workflowhub--make-decision-requirements-design-20261117.md)

### V2 权威与冻结：谁能改、何时冻结、改了谁失效

三句话：
1. 这个东西**谁能改**？改的时候要不要回原决定者？
2. 它**什么时候冻结**？冻结之后，什么条件下允许解冻？
3. 它被改了，**哪些下游事实失效**？谁负责把它们标出来？

这一条在复盘中反复出现，却从没被当成一个统一问题：T04 的修复可以改掉已冻结的语义；T02 有两次冻结判据改判；T08 有 4 条被推翻的决定仍在生效；make-decision 的 decision-log 里有"失效步骤"这一行，但没有被任何下游消费。

### V3 成本与上下文：谁的窗口、重复动作、token

三句话：
1. 这件事**必须在主上下文做**吗？还是可以派出去只收结论？
2. 这一步**之前有人做过相同输入**吗？为什么又要做一次？
3. 这次新增的动作，**替代了哪一次人工动作**？

Lauren 引用的数字是约 70% 的日 token 用于验补丁、20–30% 用于写补丁。[验证成本 12:05](../外部调研/01-Lauren-Tan演讲深读.md) 这说明成本问题的答案不是"少验证"，而是"把验证放到一次建成、反复复用的地方"。同一个检查跑第八次不会更可信。

## 5. H1 决策与承诺

**消费者是谁**：计划作者。
**做好了什么样**：他不需要回来问方向，就能开始写计划。
**现在错在哪**：收敛被做成了填表。make-decision 的 SKILL.md 有 488 行、15 个步骤，一个步骤里就有十格卡、五类分析、十列台账、8 项证据指针、冷读五问、判不合格的十类。结果是一个真正改变用户行为的边界情形（重启后系统自己补还是运维点一下）被埋在材料里，没有任何格子专门问它。

### H1.1｜用"两种做法会让用户做不同的事"来切问题

Matt 的 `grilling` 把设计决策组成带依赖的树，每轮问完所有已满足前置条件的决定，有依赖的留到下一轮；能从代码、文件或工具查到的事实由代理派独立上下文去查，只有真正的取舍交用户。pstack 的 `never-block-on-the-human` 更硬：可逆动作自行决定后说明，产品方向与不可逆动作才留人决。Lauren 的 `experience-first` 把目标定为"由用户、API 调用者、下一位维护者的使用体验来确定"。

**会改变哪个决定**：一个问题属于"问用户 / 代理自己查 / 实现者自选"哪一类。判据从"我拿不准"换成「两种答案会不会让用户做出不同的动作」。

注意现在的做法在两个方向上都偏了：把内部命名、文件路径、schema 形状拿去问用户（这一步已经禁掉了，是对的），却把「无人操作时系统会不会自己补」这种真正改变用户行为的问题留在 fog 里。

**什么情况可以省**：用户已选「沿用现页」，就不再问设计源、不问布局、不问组件结构。T08 就是这样，查现有组件和实际数据就能开始，而计划仍提出做原型，最后用户又重说了一遍只接数据。[T08 复盘](../任务报告/PaperBuilder--strategy-iteration-t08-market-update-20261115.md) 而 T03 的自动 / 人工补写会改变用户要不要采取行动，必须问。[16-从作者原则到三阶段工程约束](../外部调研/16-从作者原则到三阶段工程约束.md)

**检验**：让一个没参与的人只看决策日志，回答一个相邻边界情形。两人答得不同就还有分歧，回去只改那个问题。**撤回**：若所有相邻情形两人都答一样，这个提问动作没有增量，停掉。

### H1.2｜每条承诺带"力度"和"出处"，力度只有三档

Matt 的作者文档记过一个已观察失败：普通回答没有逐项关联到 spec、ticket 和验证，排序保证、负要求和默认值会被下一步概括弱化。pstack 的 `outcome-oriented-execution` 允许计划内迁移有阶段性断点，但结尾必须检真实状态。

| 力度 | 含义 | 谁能改 |
| --- | --- | --- |
| 必须 | 不满足就是没交付 | 只有原决定者，且要重走一次确认 |
| 允许 | 可以做，也可以不做，按成本选 | 实现者 |
| 这次不做 | 明确出界，想改先回方向 | 原决定者 |

**会改变哪个决定**：答复被记录的形状。现在记"用户说了什么"，改成记"这句话是承诺、许可，还是排除"，并写清它在什么条件下可以被新事实推翻。

T02 是最好的例子：用户只确认了"先测哪里、什么时候测"，后来量出的数字仍要按原约定处理，报告里的建议门槛仍待用户接受。这条规则会让"数字"在记录里就挂着一个"待接受"标记，而不是等收口时有人记得。

**什么情况可以省**：已确认且未被新事实触发的承诺不重问。这直接删掉"22 条需求只换来两次总确认"与"每包确认一次"之间的摇摆——需要的是**每条承重承诺一次**。

**检验**：抽三条决定，答出"必须/允许/不做 + 谁说的 + 原话在哪"。答不出就是不可执行。

### H1.3｜决定有生命周期：改、废、以及失效传播

这是上一版缺的一条，也是复盘里最贵的一条。pstack 的 `attack-the-premise` 和 `maintain-formal-verification-skill` 都要求"旧结论不能自动证明新东西"；Matt 的 `writing-for-agents` 要求一个权威源。

具体需要三件事：
1. **改**：追加（amend）还是替换（supersede），旧正文保留、双向链接。
2. **废**：谁有权废，废的理由和新的依据。
3. **失效传播**：这条决定被改/废之后，哪些下游材料（AC、Phase、判定器、交付声明）失效，谁负责标注。

**会改变哪个决定**：任何一次"改方向"，都要同时产出一份失效清单，而不是只改正文。

现在的状况：make-decision 的决策日志里有 `<失效步骤：…>` 这一行格式，但没有任何下游消费它；T08 有 4 条被推翻的决定仍在生效；T04 的修复改掉了已冻结的语义。这不是纪律问题——是因为**失效清单没有消费者**，所以写了也没人读。

**什么情况可以省**：只改措辞、不改判定的修订不触发失效传播。

**检验**：做一次真实的方向修改，看下游有几处被自动标成失效。零处说明这条没落地。

### H1.4｜收敛的产物是"下游能开工"，不是一个状态字段

Matt 的 `writing-for-agents` 要求指针写清"什么时候读、去哪里读"，正文只放每条分支都要读的规则。pstack 的 `minimize-reader-load` 要求缩短追踪层数与需记忆的可变状态。

现在做的是反面：包状态、冷读五问、十格卡、8 项证据指针、五类分析、十列台账。每样都有道理，合在一起的效果是**收敛变成了填表**。make-decision 复盘：八个包里 1 个未收敛、7 个缺机检冷读证据，仍然收口了。

**会改变哪个决定**：包的合格判据。从"格子齐"换成一句可操作的话——**本包的承接者，能不能不回来问一句话就开始写它的 Phase？**

这条会连带删掉：不服务于这个判据的字段、不能被下游消费的状态值、重复表达的同一事实（现在同一件事在十列台账、五类分析、方案卡、覆盖表里各写一遍）。

**什么情况可以省**：单一方向、且全方向调研已比较过的包，只保留"方向和理由"两行，免扩散、免冷读。现在有这个例外，但被"8 项证据指针缺一项就写未收敛"抵消了。

**检验**：统计 build-plan 回头问 make-decision 的次数与类型。目标不是零，是**回问全是"这处代码事实缺失"，没有一条是"这个方向到底要哪个"**。

### H1.5｜未答项挂在具体验收上

pstack 的 `blast-radius` 能显式留下未证明项，`interrogate` 会滤掉无法执行的风险——调用者要先决定需要哪种产物。区别很重要：**"未证明"是可以交付的结论，"没回答"不是。**

现在的状况：未答项被记成 fog / OI，但没有规则要求它挂到某条验收上。于是 T05 里「用户确认两表后」这条承重前提从未发生，终账却判通过、缺口是空数组。[T05 复盘](../任务报告/PaperBuilder--strategy-iteration-t05-metrics-20261118.md)

**会改变哪个决定**：未答项的处置。每个未答项必须写「阻塞哪一条 AC 或哪一段交付」；挂不上任何 AC 的，不许带进 build-plan，当场删掉或降级为"实现者自选"。

改动很小，但它把"用户没确认"从一个供述性的句子，变成验收表上的一个空栏。**空栏比句子难抹平**，因为空栏有一个具体的消费者在数它。

**什么情况可以省**：不影响任何 AC 的内部细节，不问、不记、不挂。

**检验**：收口时看有没有任何一条 AC 的判定来源是"用户确认了 X"而 X 找不到原件。有，就是没落地。

### H1.6｜决策日志的减法清单

这一条不是新原则，是把前五条的减法集中写出来，方便执行时直接用。

不写进决策日志的：
- 能由代码、配置、现有产品回答的事实（派代理查，只记结论与位置）；
- 内部命名、文件路径、schema 形状、算法选择；
- 不影响任何 AC 的未决项；
- 施工级细节（部署、迁移步骤、回滚顺序）——那是 H2 的。

不重复做的：
- 每条承重承诺只确认一次，不按包、不按阶段；
- 已被新事实推翻的旧承诺不重新讨论，只标失效。

## 6. H2 计划合同

**消费者是谁**：实施者、独立测试者。
**做好了什么样**：实施者当天能开工；每条高代价 AC 有一正一反两条回执指针。
**现在错在哪**：四张含错的卡全过了计划审查，因为它们缺同一个字段——"这张卡的前提取材于哪里、现在还在不在"。计划审查的输入是同一执行系写的材料，只能核内部一致性。

### H2.1｜先选入口，再写设计

Matt 的 `to-spec` 顺序很硬：先画测试切入点（seam，调用者可以观察行为的位置），优先复用既有且尽可能高的公开位置，数量尽量少，向用户确认，然后才写内部设计。Lauren 的验证技能从"用户确实能开动的功能、真实入口和证据"倒推能力范围。

他自己举的例子值得贴在每份 spec 开头：用户要求调整网页上几段文字的顺序，查源码里几段文字的顺序，证明不了读者看到的顺序。[Matt PR 演讲 03:51](../外部调研/04-相关分享与反证.md)

**会改变哪个决定**：spec 的第一节写什么。从背景与问题陈述，改成「这一条行为从哪个真实入口看，看到什么算成功」。

连带一条硬规则：**没有入口的验收条款不是验收条款**。T04 的内部读口能读到变化、公开 HTTP 一度没接进来；如果第一条 AC 就要求"从公开 HTTP 读出变化"，接线缺口会在第一天暴露，而不是在终末审查里被发现。

**什么情况可以省**：同一条行为已有公开入口时，不再为内部函数另设计测试入口。纯接线或配置改动缺合适判据时，Matt 自己也承认没有内置的"值得走一轮吗"判断——此时用一次最小整合运行证明依赖真被装上，够用。

**检验**：翻开任意 spec，第一节能不能一句话说出"从哪进、看到什么"。说不出就还没到能开工。

### H2.2｜每张卡要有一件"今天就能演示"的东西

Matt 的 `to-tickets` 按垂直行为切片，贯穿这项行为实际需要的层，单票可独立演示或验证。他列的反例很具体：三行改动被拆十余票、按层开票、验收项在基线已成立、验收项属于别的票。

WorkflowHub 是反的。T05 有一张卡写着"只新增两个测试文件"——形式上成立，内容上不成立。[深挖-验收测试与执行效率](../深挖-验收测试与执行效率.md) C10 有"包内能加载"和"接收者能装上并跑起来"两种说法，最后是后一种缺件。[C10 复盘](../任务报告/workflowhub--workflowhub-ui-frontend-c10-release-onboarding-20261103.md)

**会改变哪个决定**：拆卡判据。从"技术层 / 文件面"改成"谁能拿它给别人看一次"。

一句可操作的话：**如果一张卡的验收在开工前就能过，先查它是早已完成、验错了对象，还是成果其实属于另一张卡。**

**唯一例外**：宽机械迁移（改列名、改共享类型，单次撞到众多调用点、切片无法各自保持绿）。先并存新旧，按包或目录分批迁调用方，最后清旧；删除票依赖全部迁移票。pstack 的 `migrate-callers-then-delete-legacy-apis` 是同一件事。

**检验**：抽第一张卡，问三句——今天交给谁？他现在能做什么？拿掉这条前置，哪一步真做不了？三句答不出就合并或重切。

### H2.3｜依赖写成一句可追问的话，并反查"下游真读了什么"

Matt 要求票上写真正的阻塞边。现在写的是"等 P3"，这不是依赖，是排序。

T05 的依赖图里有一条真实的反向边——写在"前置"之后才发生。之所以计划期没发现，是因为没人反查下游到底读了上游的什么。

pstack 的 `create-verification-skill` 给了一个可直接搬的动作：生成器在交付前必须实际跑通 **ONE mapped feature**——只证明这一条路走得通，不谈覆盖。搬到供件上就是：**提供方用自己的产物走一次下游要走的读法。**

**会改变哪个决定**：依赖列的内容。从"等 P3"改成「等 P3 交出的哪个命令/字段/文件，没有它哪一步做不了」，并由提供方跑一次下游读法。

**什么情况可以省**：两个任务如果只在结尾拼起来才知道能不能用，就不要拆，交给一个负责人。

**检验**：拿依赖图反查一遍——每条边上，下游实际读了什么？读不到就是假依赖或真缺口。

### H2.4｜冻结的时点放在自证之后

（判据**怎么写**归 H4；这里只管**什么时候允许冻结**。）

pstack 的 `hillclimb` 先证明测具能区分"卡住"和"顺利"再冻结；`create-formal-verification-skill` 必须用人为反例证明检查会失败再撤掉。

**会改变哪个决定**：冻结的时点和"冻结"的含义。现在冻结的是文字（AC 与 oracle 字节），改成冻结**一个已证明有区分力的判据**。

具体动作很小：每条高代价 AC 旁边留一个「已知好样本 → 应通过；只改目标条件的坏样本 → 应按预期理由失败」的回执指针。两条回执都没有，这条 AC 只是文字。

T03 就是这个顺序反了的代价：0.8 的召回门槛在冻结时，读者记录已写「138 条只对应 78 个身份」，真实分词器写进了 AC-014 的环境而那一刻分词目录根本不存在。两条判据在不可达的世界里冻结，后来分别变成 not_met 与 incomplete，成本是整整两个阶段返工。

**什么情况可以省**：阈值来自合同、判据是字面量比较的普通条款，不做试判，直接复用现有检查。判据是「这条判据错了会不会有人的工作白做」。

**检验**：下一次冻结任何判据前，问"证明它会红的回执在哪"。没有就不许冻结。

### H2.5｜计划期只预演"会改变方案"的那一次

Matt 的 `wayfinder` 把可调研事实、需用户决定的问题、开通访问等准备动作分开，只把会使后续计划失效的问题提前澄清；他同时记录了规划排太深后、上游决定推翻后续票的反馈。pstack 的 `figure-it-out` 在没有合适脚本、跨切面或无人值守时，先定可证伪谓词、冻结改动前基线、定可独立交付的工作单元。

**会改变哪个决定**：计划期允不允许留未知。允许，但每个未知必须写「如果猜错，哪几张卡要重写」。写不出的未知是噪声，删掉。

**什么情况可以省**：没有会改变路线的关键未知时，直接用已有方法开工，不做预演。

**检验**：抽一张卡问"这张卡的前提取材于哪里，现在还在不在"。答不出，这张卡在赌。

### H2.6｜卡的前提必须当场核：样本、基线、写集

（这是 H2.5 的一个专门化，因为它值一个独立动作。）

复盘里最容易复现的一类错，是卡写的时候前提就已经不成立：

| 卡 | 埋的错 |
| --- | --- |
| P8 | gate 建在被前序 Phase 改绿的材料上（基线 exit 0） |
| P9 | 正向对照"本任务聊天十格实际出现"不存在 |
| P10 | 第 187 行要求声明槽、第 292 行禁止写集外改动 |
| P11 | 三任务重放的样本在写卡时已删除 |

**会改变哪个决定**：写卡时必须当场跑一次，并把回执放进卡里。三项：
1. **基线**：这条 gate 现在会失败吗？（证明它还没被改绿）
2. **样本**：验收要用到的样本现在还在吗？
3. **写集**：反查同一步骤的契约测试，逐条标"不改 / 同步 / 走变更请求"。

**什么情况可以省**：不依赖前序交付、样本在本任务内生成的卡，只做基线一项。

**检验**：抽一张卡，看有没有这三个回执。缺一个就是赌 → 而赌博的代价不是返工，是"四张卡全过审查"。

### H2.7｜规划（build-prd）只在"有跨任务取舍"时存在

Matt 的 `to-spec` 明确区分小改和跨会话工作，小改本来能从头到尾做完，可以省掉另写一份完整规格；主流程允许从单窗小改直接实施。

**会改变哪个决定**：build-prd 的进入条件。从"任务看起来大"改成「有两个以上交付单元，且它们的先后顺序需要有人决定」。前者不是判据，后者是。

**什么情况可以省**：单任务、无排期取舍、用户没单独要规划稿时，整份省掉。

**检验**：看下一份 PRD 里的卡，有没有一张卡的存在理由是「它会阻塞另一张卡」，而不是「它是一个技术层」。全是后者，说明这份 PRD 是按层切的。

## 7. H3 代码与结构

**消费者是谁**：下一位修改者（人 / 代理）、用户。
**做好了什么样**：改这条规则只需要改一个业务位置；改错了会红。
**现在错在哪**：同一个不变式最多十处实现；26 处静默失败、42 处退默认值；1987 行直连存储代码进了仓库，14 份审查零提及。

### H3.1｜一条业务规则一处拥有者，所有入口必经它

Lauren 的 `model-the-domain`：当条件散在多个文件时，让一个拥有规则的结构决定结果；`boundary-discipline` 要求在 CLI、配置、外部 API 等边界解析，内部以类型和纯逻辑为主。

T08 是最好的反例：两条入口用同一月片质量规则，只有一条传了校验器。若两边应遵守同一规则，**应用的合法入口应让两边都必经它**，调用者无需分别记得接校验器。

**会改变哪个决定**：设计评审的问题。从"这段代码对不对"改成「这条规则有几个人在决定」。大于一，先合并到一个入口，再让所有 caller 经过它。

**什么情况可以省**：两处本来回答不同问题（例如"当前理解"与"历史快照"含义不同），明确职责、保留各自降级，不为统一而统一。

**检验**：改这条规则要改几个文件？大于一个业务位置就是没收敛。

### H3.2｜用类型和状态机让非法操作写不出来

pstack 的 `type-system-discipline` 要求编译器排除非法状态、错传的原始值、未处理变体；`make-operations-idempotent` 让重跑不依赖上次中断点。Lauren 的 Lean 证明只用在高代价性质上——**这提醒我们：形式化不便宜，只在结构挡不住的地方用。**

**会改变哪个决定**：遇到新约束时先问"能不能被类型 / 枚举 / 唯一构造路径挡住"。能，就不写 lint、不写运行期校验、不写审查项。

**什么情况可以省**：已被类型挡住的场景不再写测试证明它。这是 T05 那种"测试行 15167 占新增 49.3%"的减法入口。

**检验**：抽十条测试，把实现故意改坏，看哪条会红。全不红，说明它们测的是结构不是行为。

### H3.3｜深模块：小接口承载更多行为；删除检验决定它该不该存在

Matt 的 `codebase-design` 定义：interface 是**所有调用者必须知道的东西**，包括不变量、调用顺序、错误模式、配置和性能；depth 衡量"学会这套 interface 能得到多少行为"；收益落在调用者少学规则（leverage）和变更 / bug / 验证收敛到一起（locality）。

删除检验：问"删掉这层，复杂度消失，还是扩散到所有调用者？"只有一个适配器的抽象要警惕。他也明确提醒：用代码行数、目录形状推断深度会把问题看错。

**会改变哪个决定**：新增模块或一层包装之前的门槛。现在默认"先抽出来方便复用"，改成先做删除检验。

T05 的具体病灶：中文化有 3 个登记处且已经漂了。[深挖-项目规范与代码质量](../深挖-项目规范与代码质量.md) 这不是重复代码问题，是深度问题——一个概念要在三个文件间跳转才能拼出来。

**什么情况可以省**：一次性、只有一个消费者的包装不抽。

**检验**：一个概念要读几个文件才能拼出来？超过两个，考虑加深。

### H3.4｜错误要"响"，不许静默退默认

pstack 的 `fix-root-causes`：沿运行找首个错的决定；**若异常状态本身非法，回到生产它的地方。** `boundary-discipline` 要求边界解析失败要暴露。

T08 的数字：26 处静默失败、42 处退默认值、40 个公共函数无直接测试，其中三处能让坏数据看起来可用（快照校验、损坏月片覆盖、周更组合漏门）。

**会改变哪个决定**：默认值的使用。默认值是一个隐藏的产品决定，必须回答"这个默认值是谁决定的"。答不出，回 H1 问一次，或改成显式失败。

**什么情况可以省**：真正的可选参数，且默认值在合同里写明。

**检验**：`grep` 一遍 `or []`、`or {}`、`or 0`、`except: pass`，逐个问"这里是产品决定还是省事"。省事的改成响。

### H3.5｜先迁 caller 再删旧入口，且同波完成

pstack 的 `migrate-callers-then-delete-legacy-apis`：没有外部兼容要求时，所有 caller 更新与删旧 API 同一波；有外部兼容依赖时原则本身列明不适用。Matt 的宽迁移例外允许分批，但要求删除票依赖全部迁移票。

**会改变哪个决定**：允许不允许"并存新旧"。允许，但必须写明删除条件与依赖；不写就不许并存。

**什么情况可以省**：调用方全在控制内、同一批能安全迁完，省双轨期。

**检验**：仓里有没有两套做同一件事的入口，且没有删除票？有，就是活着的旧误导示例。

### H3.6｜代码是下一位代理的示例，所以要管"示例"

这一条不是"写得好"，在调研里它是独立的。Lauren 讲得很清楚：每合入一份临时方案，下一轮找到同类示例的机会就会增加，反复复制最终让例外看上去像惯例；她专门留了一张"有时仍应该读代码"的幻灯，原因就是今天保留的代码会指导明天的 Agent。[代码即记忆 2:57 / 复制扩散 4:24](../外部调研/01-Lauren-Tan演讲深读.md) Cursor 的定时器故事是完整案例：9 月 9 日一处零延迟 setTimeout 制止了一处闪烁，注释留下合理化解释；10 月 3 日同类做法进了共享模块；10 月 17 日已经是 183 个 timer。

**会改变哪个决定**：一份 workaround 合入时的附加义务。从"能过测试就行"改成「要么配一条结构约束，要么开一张删除票」。两者都没有就不许合入。

**为什么这条值得单独成条**：因为它是唯一一条"今天正确的代码会让明天变差"的原则。其它原则都在防当下的错，这条在防复利式的错。

**什么情况可以省**：临时排查用的本地改动（不进主干）。

**检验**：数一下过去一个月合入的 workaround，有几份配了约束或删除票。零份就是这条没落地。

## 8. H4 判据与证据

**消费者是谁**：独立判定者、收口者、下一位接续者。
**做好了什么样**：一个正例通过，一个只改目标条件的坏例按预期理由失败；每份证据绑定到实际交付字节，并活得过清理。
**现在错在哪**：判据文字写得很足，但没有一步验证它能不能判；证据很多（T01 539 份回执、T08 1177 份原始输出），但证据能支持的范围没人核；62.4% 的回执在证明同一件事。

这个模块把原来的"验收测试"和散落在别处的"证据底座"合在一起，因为它俩是同一件事的两半：**判定器是产生证据的装置，证据是判定器的输出**；分开写必然出现"谁拥有回执"的争论。

### H4.1｜预期必须来自实现之外

Matt 的 `tdd`：预期值回溯到规格、独立算例或已知字面值；**查数据库私有状态、断言内部调用次数、在断言里重抄一遍计算、先批量写想象中的测试，都会带来失真的反馈**；mock 只留在系统边上。pstack 的 `test-behavior-not-implementation`：坏行为应打红，换内部实现仍应绿。

WorkflowHub 的反例密度很高：61 个测试文件断言退出码、30 个只断言 `Array.isArray`；终末 oracle 初版只断言"errors 是数组、ok 是布尔"；T04 用相同的应用装配断言两条互斥的期待，在相同输入与装配下不可能同时成立。

**会改变哪个决定**：写测试前的第一个动作。从"写断言"改成「先写这个期望值从哪来」。写不出来，说明判据还没定，回去定。

**什么情况可以省**：已被结构挡住的错误（H3.2），不写测试。

**检验**：抽五条测试，改坏实现，看哪条会红。

### H4.2｜判定器先自证，且失败理由要稳定

pstack 的 `hillclimb`、`create-formal-verification-skill`、Matt 的"先看到红"、Lauren 的"计划期测具可用，正式结果仍等实现后判"——四个人从四个角度说了同一件事。Matt 另外强调：测试之前要讲清这个 seam 各自能捕捉什么、遗漏什么。

**会改变哪个决定**：一条判据算不算"可用"。从"能跑"改成「一个正例通过 + 一个只改目标条件的坏例按预期理由失败 + 连跑三次失败理由一致」。

**什么情况可以省**：普通条款（阈值来自合同、判据是字面量）。

**检验**：连跑三次同一条坏例，失败理由是否一致。不一致比没有判据更危险——它会给出错误的信心。

### H4.3｜证据绑定对象、可复核、活得过清理

pstack 的 `create-verification-skill`：清理只处理自建实例，**清理后证据仍必须存在**；`shipping`：重排 commit / rebase 后用 `git patch-id` 核对旧裁决是否仍有效；`maintain-formal-verification-skill`：已过的旧模型无法证明新代码。

两个反例：T03 末验判的提交与交付提交不是同一个，五条 AC 的证据基础过期；T08 收口引用了一份只有 `.out`、没有 junit 的 `55 passed`，而真实门禁是 60 例、3 failed、5 skipped、exit≠0。

**会改变哪个决定**：每份证据在写下的同时带四样东西——绑定对象（commit / path / hash）、谁能复核、什么条件下失效、清理后如何重新读到。**没有绑定物的证据，收口时不能引用。**

**什么情况可以省**：一次性环境读数，写明原因即可（WorkflowHub 证据规则里已有三类例外）。

**检验**：抽三份证据，答出"它证明的是哪个版本的哪个对象"。

### H4.4｜"通过"必须由实际判它的原件给出

pstack 的 `interrogate` 只认可执行证据，无可执行证据的未来风险与风格意见不在它的发现定义内；`blast-radius` 能显式留下未证明项。两者分工明确，调用者先决定要哪种产物。

WorkflowHub 把两类混在一起：T05 的承重前提从未发生，终账判通过、缺口空数组；C10 的 216 条发现 61 条无独立复核。

**会改变哪个决定**：逐 AC 对账的输入。从"读材料 + 写判定"改成「读这条 AC 声明的原件 + 写结论」。声明了原件但原件不存在，写"未取得"而不是"通过"。

这一条**不需要新建账本**。它只需要让现有 AC 行带一个必填的"判定来源"引用，并让那个引用在收口时被真的打开一次。新增的是约束，不是新对象——这一点必须守住，否则又变成一个新的控制面。

**什么情况可以省**：纯人读判据（例如"读者能复述"）本来就只有一个原件，不额外要求。

**检验**：收口报告里有没有任何一条"通过"找不到它声明的原件。

### H4.5｜三种验证面各答一个问题，不能互相顶替

| 验证面 | 能回答 | 不能回答 |
| --- | --- | --- |
| 实跑（真实入口、真实数据） | 这次真实走过的入口、数据、环境下用户看到了什么 | 没走过的分支；结论能否推广 |
| 模型检查（TLA+ / 状态机） | 在你写下的性质与边界内有没有反例 | 实现与模型是否吻合 |
| 独立审查（人读） | 这段差异符不符合真意图、风险要不要承担 | 事实是否成立 |

T01 花 539 份回执、79 条审查意见，两条验收仍然判不了，因为判据本身不可满足或不可达，而流程里没有一步去验证"这条判据能不能判"。[T01 复盘](../任务报告/PaperBuilder--strategy-iteration-t01-trusted-backtest-20261115.md)

**会改变哪个决定**：当一条结论被质疑时，先问"它该由哪个验证面回答"。用错面就是白做。

**什么情况可以省**：简单改动只用实跑一面，不做模型检查。

**检验**：看一份验收报告，每条结论旁能不能标出它由哪个面回答。标不出就是混着写。

### H4.6｜覆盖面变化要单独报告

T04 的页面对照从 19 对降到 16 对、跳过从 3 对升到 6 对，只读"零未豁免"会把少检查误读成提高质量。[12-用真实会话验证流程改造](../外部调研/12-用真实会话验证流程改造.md)

**会改变哪个决定**：验收报告的格式。除"有没有红"，必须同时给「检查了多少对象、跳过多少、为什么跳」。三行不占篇幅，但它决定读者能不能看出范围变化。

**什么情况可以省**：范围与上次完全一致时写"同上次，范围未变"。

**检验**：连续两次报告的对象数对比，差值有没有解释。没有解释的差值一律按缩水处理。

### H4.7｜证据只产生一次，复用要有默认路径

pstack 的 `show-me-your-work` 用单一追加 TSV 按决策点记录，证据列指原产物。WorkflowHub 已经写了「同字节即同一事实」——**但靠人执行**，因为检查器只报告不阻断。

**会改变哪个决定**：capture 的默认动作。从"跑完就存"改成「先按（步骤 + 输入哈希）查已有回执，命中直接复用」。命中率进阶段清单。

**为什么这条在 H4 而不是效率视图**：因为它的机制在证据底座里（要和 H4.3 的绑定字段共用），效率视图只是引用它的结果。

**什么情况可以省**：输入含时间戳等不稳定因素时，改按命令与退出事实复用，并记 `deduplication: unknown`（已有这个字段语义）。

**检验**：同一输入出现第二份回执的数量。基线是 62.4%，目标 5% 以下。

## 9. H5 交付与交接

**消费者是谁**：用户、下一阶段、下一会话。
**做好了什么样**：声明里的每条结论都能回到原件；已知发现集合差为 0；接续者不需要重建上下文。
**现在错在哪**：这个模块在原来的七方向里根本不存在。而它是四类事故的共同归宿——未验成被写成通过（T02）、61/108 条发现无处置（T05）、授权晚于动作四小时（T03）、修复重建上下文七次（T01/P11）。

### H5.1｜交付声明只有三种结论，外加缺口条件与 owner

WorkflowHub 已经有这个三态（达成 / 未达成 + 下一步 / 退役），也已经有 `unavailable / incomplete` 词表。问题在它允许被一段散文覆盖。

pstack 的 `blast-radius` 能留未证明项、`prove-it-works` 要真实工件——两者的共同点是：**未证明项是一个具名条目，不是一个语气**。

**会改变哪个决定**：收口时的写法。每条结论必须是「档位 + 一条具名证据指针 + 若未达成则附阻断条件与 owner」。三样缺一，这条结论写成"未取得"。

**什么情况可以省**：全部达成的任务，缺口清单写"无"即可，不需要展开。

**检验**：抽三条结论，看能不能答出"谁判的、读了哪份原件、缺口归谁"。

### H5.2｜已知发现必须闭环到集合差为 0

这条来自一份审计里最硬的一句建议：108 条 finding 里 61 条无任何处置，而流程照样从 `needs_revision` 走到 `pass`。**这条不需要新的判断力，只需要一次集合减法。**

具体是：`quality/reviews/*` 里所有 `findings[].id` 的并集，减去后续原件里出现过的 `original_id` / 同名 `id`（带 status），差值必须为 0，或每条差值都有一条 `accepted_risk`（绑定用户真实决定）或 `incomplete` 记录。

**会改变哪个决定**：收口的判定内容。从"读一段总结"改成"算一次集合差"。

**这一条是 H5 里唯一值得做成机器检查的**，因为它的输入是结构化 id、输出是一个数，不涉及判断。

**什么情况可以省**：没有独立审查的任务（小改动/普通任务无独立审查轴时），无从谈起。

**检验**：对任意历史任务算一次这个差值。算出来是正数，就说明这条没落地。

### H5.3｜不可逆动作三核对：授权范围、动作范围、当前 HEAD

WorkflowHub 已经有 `git-authorize` 的 record/consume 与"HEAD 不一致就拒绝消费"。缺的是让这个核对发生在动作**之前**且必被读取。

T03 的实测：关闭授权记录晚于动作约四小时，push / PR / 清理无授权。这不是工具不够，是工具的输出没有成为动作的前提。

**会改变哪个决定**：不可逆动作的开工条件。三样对齐才能做，任一对不上就停该处。

另外一条来自 pstack `shipping` 的做法值得吸收：**每次合并读回 PR 实际 merged 且 base 是 trunk，入队不是已落地。** 也就是说"发出去了"和"落地了"是两个事实。

**什么情况可以省**：本地提交（可逆）不需要逐次核对，沿用任务的持续授权。

**检验**：抽一次不可逆动作，看授权原件的记录时间是否早于动作时间。晚于就是走形式。

### H5.4｜交接是指针，不是摘要

Matt 的 `handoff` 明确：只在跨宿主、跨目录、给同事或中途分出一条支线时才优先写它；输出短 Markdown，记录仍在进行的工作、与下一步有关的原因、建议技能及原始资料指针，去敏感信息。他公开的风险是：临时文件或其依赖丢失、**概括把未经验证的判断变成"已完成"**、上下文压过后很难找回为什么。他的处理建议是：交接前回读，并降低不确定说法的确定程度。

**会改变哪个决定**：handoff 里写什么。从"总结这一段做了什么"改成「下一步要解决什么 + 相关原件的路径 + 我还不确定的三件事」。

**什么情况可以省**：同一会话、同一目录能继续时，不写 handoff——Matt 的顺序是继续 → 清空 → handoff → 派子代理 → 压缩，handoff 排在第三位。

**检验**：拿一份 handoff 给没参与的人，看他能不能在不打开旧会话的情况下开始，并且**知道哪几件事是不确定的**。

### H5.5｜接续先核现场，不信旧摘要

pstack 的 `session-pickup`：读取原轨迹和目前 Git，找恢复点，按目标复验承接结论。Anthropic 的 harness 实践也是"新会话先用浏览器跑真实路径，再开展具体工作"。[相关分享与反证](../外部调研/04-相关分享与反证.md)

**会改变哪个决定**：新会话的第一个动作。从"读交接文档"改成「核当前 Git / Phase / 证据，再读交接」。

T01 的记录：主会话上下文被验证细节占满，真正该做的判断被挤到最后；阶段分析、关闭动作、交接三项全为空，因为"游标不承载这些"。

**什么情况可以省**：同一会话内继续。

**检验**：让一个没参与的人接手，计时他多久能让第一条命令跑起来、跑对。超过十分钟说明接续设计有问题。

### H5.6｜交付证据是最小前后对照 + 可逆性，不是全量日志

Matt 的 `pr` 技能：用最小的前后证据说明行为，把合并风险另外说清；他也说明同一份 PR 正文会随分支变动过时，较大变更后要重读。pstack 的 `shipping` 要求每件 PR 由非作者验证者以 base/head 驱动匹配用户路径并记 `PASS` / `PASS+NOTES` / `FAIL`。

**会改变哪个决定**：交付说明的形态。从"附上所有证据"改成「一段前后对照（能看懂的截图 / 命令输出）+ 风险与可逆性说明 + 指向原件的指针」。

**什么情况可以省**：不可逆或高影响变更，才需要额外的完整证据集。

**检验**：让一个不了解任务的人读交付说明，问他"这东西坏了怎么退回去"。答不出就是没写可逆性。

## 10. H0 规范与知识

**消费者是谁**：任何人在作某类决定前。
**做好了什么样**：违反它的写法在写的时候就失败，不是审的时候被找到。
**现在错在哪**：规则都写了，细到可以直接判对错，但没有任何一步会读它、拦它，所以代理可以一路"记录完成"而交付走歪。同一条规则最多 6 份写法。

### H0.1｜一条规则的落点，取决于它能不能被机器当场拒绝

Lauren 的 Dune 是范本：禁止产品代码直接使用 React effect，但框架 API 内保留；目录边界配依赖分析器，连 type import 都禁；共用类型有合法位置。三件事同时成立——**能看懂、违反会失败、合法路有位置。**

pstack 的 `correct` 给了决策顺序：同类错误至少出现两次才考虑变成结构约束；优先架构、类型、lint/CI，再行为测试，最后文档；并且必须对真实的旧错误证明会拦。

**会改变哪个决定**：新规则的默认落点。顺序是：

1. 能否用类型 / 枚举 / 唯一构造路径排除？能，就不写检查器。
2. 能否用目录 / 依赖规则排除？能，就不写 lint。
3. 能否用一条确定性检查当场拒绝？能，就不写审查项。
4. 只有需要权衡后果、有正当例外的，才写成文字，并写清"谁在读、在作哪个决定前读"。

**一条判据**：如果一条规则只能靠审查者"记得查"，它就不是规则，是提示。提示允许存在，但不许被当成质量保证。

**什么情况可以省**：已被上游结构挡住的错误，不再写运行期校验、不再写测试、不再派审查。

**检验**：挑一条写在规范里、靠审查发现的要求，看它在最近三个任务里被违反了几次。被违反过，就回到上面四步重选落点。

### H0.2｜一条规则一个权威，其余生成

Matt 的 `writing-for-agents`：同一内容只有一个权威源，从命令或配置能低成本读到的事实不重抄。

WorkflowHub 的具体病灶：方向审查问数 6 份副本、细节审查 4 份、AC 唯一权威 5 份、证据缺口退出 6 份、终末 AC 材料 4 份、"作者必须 / 校验器只报告" 8 份。最严重的一处是第⑤问「效果谁看」从来没进过 prompt——契约写五问，`review-materials.mjs` 发四问，冻结字节保护让两套数字无法自洽。

**会改变哪个决定**：清单和问数的维护方式。从"改三处保持一致"改成"改一处、其余生成"。生成器的存在理由是防止漂移，不是省打字。

**什么情况可以省**：只有一个消费者、且不会被复制的事实，不建生成器。

**检验**：改一次问数，看要动几个文件。超过一个就是错的。

### H0.3｜绝对化的规则会教出"去看检查器覆盖到哪"

这条是上一版没有的，证据来自一份非常具体的审计：

`AGENTS.md` 写着「C2 存储层是唯一碰物理存储的人，别处不许直接读 Parquet / 连 SQLite / 拼数据路径」。但边界检查器 `check_boundaries.py:350-351` 的 `direct_sqlite` 规则不覆盖 `runtime_ops`，而 `runtime_ops` 的存在意义就是直连权威库。结果是：本任务把整整 1987 行直连存储代码放进仓库，14 份审查零提及，`make check` 全绿。

审计的结论值得整段抄下来：**一条"唯一的、绝对的、有例外的"规则，学到的行为是"去看 checker 覆盖到哪"，这比没有规则更糟。**

**会改变哪个决定**：写规则时的措辞形态。三条路选一条：
1. 真的绝对 → 检查器必须完全覆盖，没覆盖就是缺陷；
2. 有例外 → 写成「入口在 X；例外须在 Y 处逐项登记（含 URL / 模式 / 回滚）」；
3. 不能执行 → 不写，改为说明"为什么这样设计"的 ADR。

**什么情况可以省**：一次性约束、且不会被反复读的，写在任务材料里，不进项目规范。

**检验**：把每条"唯一 / 不许 / 必须"开头的规则，对着检查器核一遍覆盖范围。不一致的，要么改检查器，要么改措辞。

### H0.4｜改规范要带"原覆盖"对照

pstack 的 `correct` 对真旧错误证明会拦；Lauren 保留合法例外。WorkflowHub 在 T04 踩过反例：页面对照 19→16、跳过 3→6，"零未豁免"被读成提高质量。

**会改变哪个决定**：规范或检查器变更的验收内容。从"改完能跑"改成三件事：

1. 一个历史坏例变红；
2. 一个合法例外仍然绿；
3. 说明原本会查的哪些对象现在跳过。

**什么情况可以省**：纯措辞修改、不改变判定行为。

**检验**：下一次改检查器，看有没有这三行。缺第 3 行，就一定会有人把范围缩小当成质量提高。

### H0.5｜知识要有适用性判断，"查了"不等于"用了"

WorkflowHub 已经有知识图谱和 `specs/archive`，问题是它被用成"查过就算消费过"。任务报告里反复出现的是"查了图、挂了链接、产出没变"。

pstack 的 `maintain-formal-verification-skill` 给了判断框架：模型描述有偏差、产品确有 bug、性质有意修改是三种不同的证据路径。Matt 的 `domain-modeling` 给了 ADR 的三条件：**代价较高、未来读代码难懂缘由、存在真实取舍**，三者全满足才写。

**会改变哪个决定**：知识被消费的判据。从"我查过了"改成「这条历史结论改变了本次哪个候选 / 假设 / 提问，具体新内容是什么」。写不出新内容，就标"重复 / 补强 / 无信号"。

**什么情况可以省**：与本次无关的历史，不查、不记。

**检验**：抽一条被引用的历史经验，问它改变了什么决定。答不出就是挂了链接。

### H0.6｜只留每次都要读的，其余是指针

Matt 的 `writing-for-agents` 把文档按"必须依次执行的步骤"和"按需读取的参考"分级，只放每条分支都要读的规则。

WorkflowHub 现在反过来：make-decision 488 行、build-plan 282 行、build-code 409 行，45 个技能目录、62 份 ADR，每个技能在流程里都有一行"必需 / 按需 / 跳过"和理由。这些理由加起来构成了一个"读完才知道该读什么"。

**会改变哪个决定**：派发时给什么。从"给材料全文 + 规矩全文"改成「当前条款 + 会改变动作的指针」。

T03 的写集是散文声明的，七个阶段全部出现未申报改动，平均每阶段 4 个文件。现在的应对是再写一条纪律；正确的应对是让 build-code 打印真实 `git diff --name-only` 与声明对比——**一个命令，不是一段纪律。**

**什么情况可以省**：只有一个消费者、且不会被复制的规则，直接写在该处。

**检验**：翻一条规范，问"这条是每次都要读，还是只在作某个决定前读"。后者移到指针后面。

### H0.7｜每条规范要有消费者和删除条件

pstack 的 `laziness-protocol`、`subtract-before-you-add`；WorkflowHub 宪法 F5（gate 谨慎添加、出事再补、无用则移除）、F10、F11 都是这个意思。

现实跑反了：22 个 CLI 工具、1869 行的步骤检查器，29 处 `gaps.push` 直接推中文字面量，约 100 个中文正则分布在 87 行，`run-checks` 另有一份 9 条正则比前者少 11 条，`errors` 数组只打印永不影响退出。

**会改变哪个决定**：新增任何控制面的门槛。加入时写三行：**真实消费者、替代了哪一次人工动作、什么条件下删**。

**什么情况可以省**：只是想"让一切可被机器校验"的基建——宪法 F10 已经禁止，但需要一个动作执行它：每次新增检查器，先假想"它上线三个月后要删"，写出删除条件。

**检验**：列出过去三个月从未拦下任何东西的检查，删一半，看有没有人发现。

## 11. H6 流程自身

**消费者是谁**：下一位流程使用者。
**做好了什么样**：用真实会话能看出行为变了；每条改动有替代关系与撤回条件。
**现在错在哪**：流程改动只以"复盘写进文档"的方式发生，没有任何验证闭环。检查器本身坏了也没人发现——退出码由中文文案正则决定，收敛清单全空反而 exit 0。

这是原七方向里完全缺席的一块，也是唯一能让前六个模块逐步变好的回环。用户此刻"基于原则看看 workflowhub 每个阶段该如何优化"这件事本身，就属于这个模块——如果没有验证设计，这一轮讨论就只能产出一份更好看的文档。

### H6.1｜改流程要用真实会话验，不读自述

pstack 的 `eval` playbook 是完整的方法：同一自然任务、隔离环境、候选不知试验条件、异模型评委盲评；主持人还要读真实 transcript，核代理**实际读过哪些文件、实际调用过什么**，把"模型说它遵循了规则"与"它真的走过调用链"分开。

Matt 的 `retro` 读真实 session，分辨问题出在导航、工具、指令、信息访问还是验证。

**会改变哪个决定**：验证一份流程改动时用什么证据。从"读改动后的 SKILL.md 觉得更清楚了"改成「同一自然请求跑一遍，读 transcript，看实际加载与产出」。

**什么情况可以省**：纯措辞、不改变动作的改动，不做真实会话。

**检验**：一次流程改动之后，有没有一份 transcript 能证明代理的行为变了。没有就是没验。

### H6.2｜重复出现的同类错误才升级为规则

pstack 的 `correct` 明确要求"同类错误至少出现两次"，pstack 的 `reflect` 也是先汇总"本会话重复失误与纠偏"，再经批准才写入技能副本。Lauren 的对谈里同一件事：抽看可复核的变更，**从重复做法发现环境缺陷**；多次同类绕路值得改接口或检查，孤立的个人偏好可以先留观察。[4-相关分享与反证](../外部调研/04-相关分享与反证.md)

**会改变哪个决定**：一条教训要不要进规范。从"复盘里写了就进"改成「同类错误出现第二次才进」。

**什么情况可以省**：不可逆的高影响事故，第一次就要进（这类不进会再犯）。

**检验**：翻一遍最近进规范的新规则，有几条是只出现过一次的偏好。这类应该退回任务材料。

### H6.3｜每条流程改动带四件事

T05 的审计给了 12 条改造建议，每条都带"何处改、谁在何时做什么、正反回放、何时撤回"——这是一个可直接照抄的模板。

**会改变哪个决定**：流程改动的批准条件。四件事缺一不许改：

1. **替代关系**：它替代了哪一次人工动作 / 哪条旧规则；
2. **正反回放**：一个现实场景会变好，一个相邻场景不应变坏；
3. **删除条件**：什么情况下把它删掉；
4. **撤回条件**：什么情况下判定这次改动失败、回退到原样。

**什么情况可以省**：只能写措辞的改动，不做正反回放，但替代关系仍要写。

**检验**：看最近五次流程改动，有几份带齐四件事。

### H6.4｜复盘找责任点，不写教训

Matt 的 `retro` 要求先核已有检查是否未接入，把机械问题交给可失败的确定性检查，跨处一致性等语义判断保留给审查。他还要求复盘落在五个责任点上：**导航、工具、检查、标准、信息访问、验证**。

**会改变哪个决定**：复盘产物的形态。从"下次要注意 X"改成「这件事属于哪个责任点，改哪个对象」。

**什么情况可以省**：一次性外部事故，只记录不入改。

**检验**：一份复盘里如果出现"要更仔细""要加强审查"，这条没落在责任点上，退回重写。

### H6.5｜前序变化之后，仍要能验证增量

调研里有一条容易被忽略但很关键：如果前一阶段已经把后一阶段的原失败样本改绿，旧证据就失去了区分力，要为后一阶段另找能检出其增量的反例，原记录仍保留。[12-用真实会话验证流程改造](../外部调研/12-用真实会话验证流程改造.md)

这正好是 WorkflowHub 的 P8 事故：gate 建在被前序 Phase 改绿的材料上，于是它永远绿。

**会改变哪个决定**：验证一个阶段改动时，选什么样本。从"用现成的失败样本"改成「先核这个样本现在还红不红」。

**什么情况可以省**：不依赖前序变化的独立模块。

**检验**：抽一条"已证明有效"的检查，现在跑一次，看它是否仍能失败。

### H6.6｜用四个可观测信号判断流程有没有变好

不写"要做好"，只写四个数：

| 信号 | 定义 | 现在的值 |
| --- | --- | --- |
| 方向类回问数 | build-plan 回头问 make-decision 的"方向到底是哪个"类问题条数 | 没有基线 |
| 证据冗余率 | 同一输入的第二份回执占比 | 62.4%（make-decision 任务实测） |
| 证据绑定率 | 带 commit / path / hash 的证据占全部证据的比例 | 没有基线 |
| 缺口残留率 | 收口时"未取得 / 未达成"条目占全部 AC 的比例 | 没有基线（T05 是"有缺口但记空数组"，这个信号会把它变成 100%） |

**会改变哪个决定**：判断流程改动值不值得继续的依据。从"感觉更顺"改成「四个数里至少一个动了，其余三个没变坏」。

**必须承认**：其中三个现在没有基线。**在第一次试点之前，先花一次任务把这四个数记录下来**，否则试点只能给定性结论。

**检验**：下一次改动之后，四个数有没有变。

## 12. 四个流程 = 生产者矩阵

模块是"交什么"，流程是"谁交"。把两者对上，才知道每个流程该守哪几条原则、可以省什么。这也是原报告"四个流程各该坚持什么"的正确做法：从矩阵推出，而不是断言。

| 流程 | 主产出 | 引用 | 必须守的原则 | 可以省 |
| --- | --- | --- | --- | --- |
| make-decision | H1 | H0（规则落点）、H4（研究结论的证据） | H1.1–H1.6 | 代理能查的事实；已选沿用现页时的设计源问题；不影响 AC 的未决项；按包的重复确认 |
| build-prd（H2 分支） | H2（任务地图） | H1、H0 | H2.2、H2.3、H2.7 | 单任务时的整份 PRD |
| build-plan | H2、H4（判据设计） | H1、H0 | H2.1–H2.6、H4.1、H4.2 | 普通条款的试判；已有公开入口时的内部测试入口；无歧义时的规格澄清 |
| build-code | H3、H4（证据产生）、H5 | H1、H2、H0 | H3.1–H3.6、H4.3–H4.7、H5.1–H5.6 | 已被结构挡住的测试；已有反馈环时的重复诊断；纯文档的模拟 RED；已被确定性检查挡住的面不必再派审查 |
| stage-close / 收口 | H5 | H4 | H5.1–H5.3、H5.6 | 全部达成时的缺口展开 |
| 跨阶段（不属于任何单一流程） | H0、H6 | 全部 | H0.1–H0.7、H6.1–H6.6 | — |

## 13. 检验与撤回

### 13.1 不要一次改七个模块

挑一件**有真实后果、又能在一周内看到信号**的任务。三条都满足才选：有至少一条用户看得见的行为；有一个可能不成立的外部依赖或数据前提；上一次同类任务有可对照的返工记录。

### 13.2 四个观察点

| 模块 | 观察什么 | 好的信号 | 撤回条件 |
| --- | --- | --- | --- |
| H1 | 方向类回问数 | 0 条方向类；回问全是代码事实缺失 | 若全是方向类，说明 H1.1 的判据没落地，回到"两种解释"重写问题 |
| H2 | 高代价 AC 的正反回执覆盖率 | 每条都有，且坏例回执是当场跑的不是补写的 | 若都有但无一失败过，说明是补写，改为"冻结前必须当场跑" |
| H4 | 证据冗余率 | < 5% | 若复用率不升，说明"先查再跑"没成为默认路径，改在 capture 入口强制 |
| H5 | "通过但找不到声明原件"的 AC 数 | 0 | 若存在，说明 H4.4 只加了字段没加打开动作，改为收口时必须打开一次 |

### 13.3 两条定性信号

- 用户在过程中"又说了一遍已经说过的话"的次数（T08 发生过）。
- 审查报告里"某个模式被写错了"这类可结构化发现的比例。这个比例高，说明审查在替 H0 / H3 打工。

### 13.4 四条撤回原则

试点失败时先怀疑原则，不是执行：

1. **若一条原则需要人反复提醒才生效**，它不是原则，是提示——回到 H0.1 重选落点。
2. **若一条原则的收益只能通过"多审一遍"看到**，它没落地。
3. **若一条原则让另一个模块的负担变重**（例如把结构问题推进审查），撤销它。
4. **若一条原则只在本次任务成立**，降级为任务偏好，不写进规范。

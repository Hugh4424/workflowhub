## 第一部分　方向怎么划

**我的判断：原来的七项适合拿来问“复盘有没有漏看”，不适合直接当流程设计目录。** “需求收敛”是一类要作的决定，“计划设计”是一段工作，“项目规范”是规则的载体，“执行质量、代码质量、Agent 效率”则是希望得到的结果。把它们并列，会有两种后果：一次失败能同时归入四栏，各栏都建议再检查一次；另一些事却无人决定，例如谁可以动正在运行的环境、切换失败后谁有办法恢复。

我建议从三个层次设计：**一件任务有六类本体决定；两类协作决定贯穿其间；还有一类决定负责改进下一次工作。** 行动权限另作独立判断，四个 workflow 说明这些决定在什么时候发生。符合用户原意、容易维护、返工少，是评价结果。方向本身用“遇到这件事，必须作出什么不同的选择”来命名。

### 推荐的方向

下面按对象分组。阅读顺序不等于执行顺序，尤其是诊断、验证和独立判断，可以在不同时点多次提供不同的新事实。

| 层次 | 方向 | 必须作出的选择 | 谁使用这个答案 |
| --- | --- | --- | --- |
| 单次任务 | **产品意图与取舍** | 为谁改善什么，成功、失败、范围外分别是什么；新事实是否值得改变承诺 | 用户作产品选择，规格作者据此排除错误方案 |
| 单次任务 | **现状查证与故障诊断** | 今天真实入口怎样工作，现象由哪一个原因造成，哪些仍未知 | 调研者、计划作者或开发者据此决定问人、改代码、修环境还是继续观察 |
| 单次任务 | **交付切分与依赖** | 第一个能交给别人用的结果是什么，哪些前置真会挡路，何时值得拆成多任务 | 规划者和实施者据此安排工作、供件和顺序 |
| 单次任务 | **接口、状态与兼容** | 哪个模块负责哪条规则，调用者可以怎样使用，旧数据、失败与重试怎么办 | 开发者和后续维护者据此改对位置，少记规矩 |
| 单次任务 | **行为验证与证据** | 从哪里观察、预期由谁提供、哪种旧错误会被抓住；旧证据对交付版本还证明什么 | 实施者取得反馈，测试者和接手者据此判断行为 |
| 单次任务 | **交付、启用与恢复** | 交给谁、通过什么载体到达哪个环境，外部状态变了什么，出错能恢复到哪里 | 接收者和操作负责人据此决定交付、切换、停止或恢复 |
| 贯穿任务 | **代理分工与运行环境** | 谁读、谁写、谁驱动共享实例，什么可以并行，下一会话需要哪些原件 | 协调者与各执行者据此避免抢写、重复劳动和上下文丢失 |
| 贯穿任务 | **独立判断与分歧处置** | 哪件事需要独立判断，发现属于缺陷、取舍还是缺证，由谁修、谁复核 | 审查者作有边界的判断，原负责人处理，有产品或风险取舍才找人 |
| 跨任务 | **项目与工作流的学习** | 一次纠正只留本任务，还是该改项目接口、规范、工具或流程；怎样知道下次真的改善 | 项目维护者或 WorkflowHub 维护者据此保留、替换或撤回做法 |

**权限另列为独立控制轴。** 对每个会改变外部状态的动作，分别问谁有权决定、既有授权覆盖哪个目标、在何时消费。用户确认内容回答“想要什么”；现有授权和动作前的范围核对回答“现在可否对这个对象这样做”；最终破坏性范围确认沿原收口规则；交付读回答“实际上做了没有”。质量再好也不能代人授权。授权已覆盖就复用，缺授权只停依赖它的动作。风险及可逆性决定观察的力度。[pstack 的只读监控与实际合并](../外部调研/02-pstack源码与技能地图.md) · [WorkflowHub 的授权与质量边界](/Users/Hugh/Hugh/Project/workflowhub/CONSTITUTION.md)

**版本、身份与环境是事实的限定条件，成本与收益是评价尺度。** 用户答复、测量、审查和交付各自对准当时对象。每加一次访谈、实验、审查或派发，都应能说明它可能改变哪个决定。安全、隐私和领域约束按真实任务落到这些决定。例如已有数据的删除期限属于产品或项目硬约束，谁可执行删除另核权限，删后能否恢复归交付设计。

### 原来的七项，各该留在哪里

| 原提法 | 处理建议 | 理由 |
| --- | --- | --- |
| 需求收敛 | 保留为“产品意图与取舍”，把可查事实移出访谈 | 代理能查清当前是否自动重启，但只有用户能决定今后是否承诺自动恢复。 |
| 计划设计 | 拆给“交付切分”“接口、状态与兼容”“行为验证” | 写在同一个计划里，仍要分别决定先做什么、改哪里、怎么知道改对。 |
| 项目规范 | 分成“消费已有规范”和“形成长期规则” | 现有规则应在设计或审查时实际使用；要不要让未来任务都受它约束，是跨任务的决定。 |
| 执行质量 | 保留为结果评价，按查证、分工、实现、交付分别找根因 | 假设错了、两个代理抢同一个库、服务没启用，即使都表现为“执行不好”，处置也不同。 |
| 代码质量 | 保留为结果评价，主要设计手段落到接口、状态和兼容 | “质量好”无法决定要不要抽一层；删除该层后是否把复杂性推给每个调用者，可以决定。 |
| 验收测试 | 扩为“行为验证与证据”，另保独立判断 | 测到耗时、判断达标、用户接受新门槛是三件事。再跑测试不能补用户决定。 |
| Agent 执行效率 | 拆开“怎样分工”和“怎样评价” | 上下文、写权限、共享环境是可设计的手段；等待、重复提问、晚发现错误、返工是观察值。 |

### 为什么保留这些边界

以下把工作归到**最早还能改变结果的决定**。同一案例只在第二个原因确实独立时再归一次。

| 案例里的反差 | 哪个方向必须单独存在 |
| --- | --- |
| T01 点击后产品已入队，测试立即领取却没拿到。再举一条规则或追加用户确认都解决不了竞态。 | **查证与诊断**先辨明“没入队”还是“领取过早”；**行为验证**再决定怎样通过本次任务编号验到保存。 |
| T03 说清“按同一请求补写不会写两遍”，仍可能由运维手动启动，也可能由服务重启自行启动。 | **产品意图**可以未决，而**接口的重试性质**已经确定。不能用后者替用户选前者。 |
| T04 把“来源失效后怎样降级”写进计划发现及处置，但一度仍能从公开读口取得过时的完成状态。 | **独立判断**已经发现风险；是否被真实代码消除，要由**行为验证**回答。 |
| T05 维护窗口有 APFS 快照，也实际整库回滚。归档后外键悬空使服务拒绝启动；另一份现场记录还要求停止并发操作同一运行环境。 | **恢复能力**与**单一操作者**是两种决定。仅写“备份后再做”会漏前者；仅隔离 Git 工作树会漏后者。 |
| T08 正式库 30 格都已就绪，周作业首跑完成且 `job=null`。网页装配了逐日检查，周作业曾漏传。 | **行为验证**要证明是谁处理缺口；**技术设计**要解释为什么新入口能绕过同一规则。前者取证再全，也不能让下一入口自动检查。 |
| C10 源码辅助安装后能从安装位置加载，但接收者拿到的包缺安装器和完整审查服务。需求设计任务的 PR 已合并、页面可刷新，终末事件仍被拒绝。 | **交付和启用**有自己的接收者、介质及动作结果。源代码通过、Git 合并均无法代答。 |
| 需求设计里问法已写进合同，但生成给审查者的指令仍有不同口径。即使修好一份指令，也没证明以后代理能少漏问题。 | **项目与流程学习**评价的是下次自然任务中的动作变化。本次产品用例通过不能代答。 |

**分类分开，运行可以共用。** 查证回答“现状或根因是什么”，验收回答“这个版本是否满足事先约定”。同一原件若同时包含版本、入口、输入、独立预期及必要对照，可支撑两项结论。若只有异常堆栈，仍可用于诊断，验收仅补缺的用户侧观察。

### 怎样发现这套方向也划错了

- **需要拆开。** 同一条目反复被两位有不同决定权的人解释为两件事，一方已经做对，另一方仍能独立造成用户损失。例如小规模本机交付中，打包和运行切换可以同节处理；如果以后出现分批发布、长期运维与独立恢复责任，就应重新评估“交付、启用与恢复”是否还适合合在一起。
- **应该合并。** 两个方向长期都向同一人索取同一事实、作同一决定、只产生两份同义材料。先共享原件；若连决定也相同，删掉重复归属。性能、UI、后台、分词、Git 等先看作适用场景或工具，不因一次事故各设一章。
- **确实漏项。** 出现一个对用户有后果、四个 workflow 需要承接，却无法指明哪类决定能在事前改变结果的问题。先记下具体案例与责任人，再扩分类。八份复盘支持当前取舍，不足以证明方向已经穷尽。

## 第二部分　各方向的具体原则

### 一件任务中的六类决定

#### 产品意图与取舍：保住用户在意的差别

1. **先问这件事值不值得做。** 从谁在什么情形下做不成什么事开始。先找现有能力和最小有用改变，再讨论用户提出的实现方式。已有入口能完成目标，就解释它怎么用；只差一处接线，就把重做页面等额外工作排除在外。T08 已有明确的“沿用现页”选择，计划的价值在于把新数据和真实动作接进去。再做一个原型会把问题改成设计新页面。[Matt 的澄清与规格](../外部调研/03-Matt-Pocock技能与开发流程.md) · [T08 关于复用现页的答复](</Users/Hugh/Hugh/Knowledge/Projects/PaperBuilder/tasks/strategy-iteration-t08-market-update-20261115/quality/evidence/build-plan/2026-11-17-user-existing-ui-wiring-scope.md>)
2. **问会让产品分岔的问题。** 例如“服务重启时还有一笔没写，没人点击，应该自行补吗？”这个答案决定触发入口、值班责任和验收方法。“要不要支持恢复”却容得下两种相反答案。对排序、时点、历史与当前、遇错是否继续，也用同样的办法。能从仓库查到的事实交给代理；已具备前提的独立选择同轮问；需要看到实测才有意义的取舍留到结果出来。[Matt 的提问和领域术语](../外部调研/03-Matt-Pocock技能与开发流程.md) · [T03 知识底座复盘](../任务报告/PaperBuilder--strategy-iteration-t03-knowledge-base-20261112.md)
3. **区分“已经决定”和“决定以后再选”。** T02 用户同意接上真实列表后再测性能。73.2 和 7.8 毫秒是实测，150 和 30 毫秒是当时的建议门槛。下一手可以据此讨论取舍，但不能把数值写成用户已经接受。反过来，T01 的当前计划已展示性能目标并获确认，较早逐字原话缺失无需让用户重答当前选择。只在结果、范围或承担的风险确实变化时回到决定人。[T02 时点答复](</Users/Hugh/Hugh/Knowledge/Projects/PaperBuilder/tasks/strategy-iteration-t02-score-comparison-20261117/quality/evidence/build-plan/2026-11-17-009-performance-timing-approved-change.md>) · [T02 逐项实测](</Users/Hugh/Hugh/Knowledge/Projects/PaperBuilder/tasks/strategy-iteration-t02-score-comparison-20261117/quality/evidence/build-code/2026-11-18-019-build-code-ac-reconciliation.md>) · [T01 当前计划确认](</Users/Hugh/Hugh/Knowledge/Projects/PaperBuilder/tasks/strategy-iteration-t01-trusted-backtest-20261115/quality/evidence/build-plan/2026-11-17-014-final-plan-reply.md>)

### 下一件真实任务只试一个改动

建议先选**下一次真实发生的需求讨论或方向审查修改**，追踪一句承重要求怎样从用户的决定到达计划。候选可以是“效果谁看”；开始时先查当前生成指令和实际回复，若冲突已消除且下游已经用好，换本次任务真正有代价的问题。

| 什么时候 | 实际做什么 | 观察什么才值得留下 |
| --- | --- | --- |
| 改前 | 固定旧版本、一个实际模式和一个真实包。另取同包副本，仅去掉“谁观察结果”。保留生成的指令，分别看两例经过同一流程会怎样 | 先排除旧法已经分得清；另查是否确有口径冲突。若问题出在派发漏传而合同本身完整，只改派发 |
| 改后 | 同一入口、同一正常包和坏包复测。完整包仍可继续，有缺口的包能在写规格前指出具体问题。尽量维持可比的模型、工具和权限 | 区分了两例，才说明办法在这组材料上有效。两例都一律要求用户再确认，说明把工作转嫁给用户 |
| 下个真实包 | 不给执行者额外提醒。看真实提问、真实答复和计划的第一版。例如用户选择“无人操作也能恢复”，计划应据此安排一次真实重启后的读回 | 能指到一项实际保留或改变的计划决定，同时没有新增重复提问或无信息的重跑，就保留。若只多了说明文字或一次审查，撤掉新增动作，另查原因 |

这个试点能检验意图传递以及工作流是否真正改善。模块是否更好改，要等下一次真实共用规则变更时，看同一处修改能否让网页和后台入口都获得正确行为；交付恢复则要等确有相应风险的任务检验。无需为了验证一张方向图制造九份工作。[外部调研索引](../外部调研/00-研究索引与框架假设.md)

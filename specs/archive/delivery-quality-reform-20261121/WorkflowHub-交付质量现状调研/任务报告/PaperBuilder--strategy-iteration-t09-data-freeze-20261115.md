## 二、各阶段有哪些问题和有效做法？

查过的范围是：原话与决策、规格与五卡、26 笔提交与写集、生产调用链、测试断言、终末审查与收尾。
查到 18 个实质问题，按四类归位；同一根因只写一次，各阶段后果列在同一条里。

### （一）方向与需求

方向本身没跑偏，跑偏的是「谁负责把它接到生产入口」。
用户原话只有十行，讲流程、验证节奏和汇报方式，业务需求来自 PRD 任务 9 卡。
决策日志把覆盖、排除、未决、风险分成四张表，取舍理由可回读。

**问题 1：AC6 依赖另一张卡的交付物，却在计划期没有登记为依赖。**
预期：验收条件里的外部依赖要有编号、owner 和恢复条件。
实际：AC6 要两块区域在产品路由里可见，而路由要版本行读取器与后端路由。
原件：规格 948–968；P4 卡 186（依赖只有 P3）；P4 卡 242–247（收口才补 D-01）。
后果：P4 整段产品路由验不完，收口前才改判为外部依赖。
最早干预点：计划阶段写 P4 依赖时；当时已有信息是决策日志 474 明写「版本列表归任务 11」。
责任人：计划阶段作者与独立审查者。
反驳事实：规格 599 又说可以「就地构造一真实版本绑定」，这句被当成不必登记依赖的理由。

**问题 2：决策日志的排除项与 Phase 卡的验收场景互相矛盾。**
预期：同一件东西不能既「不在本卡」又「必须通过」。
实际：决策日志把版本列表排除给任务 11，P4 的浏览器场景却把它当必过项。
原件：决策日志 213、474；P4 卡 218（`normal-application-route` 判 incomplete）。
后果：实施者在最后一天才发现自己永远过不了这一项。
最早干预点：写 P4 卡验收场景时；线索就是同一份决策日志的排除表。
责任人：计划阶段作者；独立审查者应在 013 里质疑。

### （二）计划与交接

计划把「说清楚」做得很好，把「可核对」做得很差。
五张卡都有写集、依赖、覆盖验收、完成条件，形式上很完整。
但写集、验收编号、判据列都只是文本，没有一处能被机器当场核对。

**问题 3：写集只是文本，越界没有任何门禁。**
预期：Phase 收口时用真实 diff 对照写集，越界要显式授权。
实际：P1 越界 9 条（两条无任何记录）、P2 越界 2 条、收口修复越界 6 条（两条无记录）。
原件：P1 卡 262；`72ac1efc`、`f70cb9da` 的 `git show --name-only`；P3 卡 366。
后果：写集失去约束力，兼容门面被顺手改、`validation.py` 声明了却一字未动。
最早干预点：P1 首次提交前；线索是卡里已有写集清单，`git diff` 随时可比。
责任人：实施子代理与主会话；框架侧应有收口比对。
反驳事实：越界里有一部分是修 bug 必需（兼容门面），说明不是「管住」，而是「要显式授权」。

**问题 4：材料写法与校验器契约有三处对不上，收口才被迫改标签。**
预期：计划材料的写法与检查脚本的读取规则一致。
实际：写集标签要英文、判据列要含 oracle、验收编号要连字符，材料三种都没对上。
原件：`final-chain-runner.mjs:340`、`:476`、`:391`；同文件 `:495` 又接受中文标签，自相矛盾。
后果：十个环里两个静默不可达，收口时只能改表头让机器认到既有事实。
最早干预点：计划阶段第一次生成 spec 与卡时；线索是脚本合同一直是固定正则。
责任人：计划阶段作者；框架侧应给模板或结构化头。

**问题 5：预写冻结测试与规格的段号口径冲突，最后靠改测试收场。**
预期：预写测试是规格的可执行表达，应当先与验收表逐条对齐。
实际：预写用例按零基序号断言「第 N 段」，规格第 548 行写「序号 0 对应页面第 1 段」。
原件：规格 548；TCR-003 动机段；`data-freeze-wiring.test.tsx` 新旧 sha。
后果：页面段号少 1，收口前用 TCR-003 改冻结期望，属于「改考卷」。
最早干预点：写冻结测试时；线索就是同一份规格的验收四表。
责任人：预写测试的主会话；独立测试作者应在交付时对照验收表复核。

**问题 6：五个 Phase 都没有 Phase 级独立审查。**
预期：每 Phase 收口应有独立审查原件，能被阶段事实引用。
实际：38 份审查全部 `phase_id=null`；两次 build-code 阶段审查都因 ENOBUFS 未派出。
原件：`reviews/2026-11-16-001/002`（`blocked_before_dispatch`）；`009` 是整任务终末件。
后果：Phase 完成只有实施者自评与测试数字，没有第三方对交付面的判断。
最早干预点：P1 收口时；线索是阶段审查入口已经报错，但被当成工具噪声跳过。
责任人：主会话与框架侧审查入口；后者要先修参数上限。

### （三）实现与维护

实现本身的功能面是真的，失败集中在「接线」和「同一语义多份实现」。
真实数据验收把 AC1、AC2 从合成样本推到真实行情，这一步很关键。
但生产入口的组合根从头到尾不在任何 Phase 的写集里。

**问题 7：生产组合根不在计划里，直到终末审查才发现没接线。**
预期：验收说「普通回测按冻结输入跑」，就该有一步把端口接到生产组装处。
实际：`serve_f6.py` 三处 `BacktestQueueApplication` 都没传 `research_data`。
后果：真实 `POST /api/backtests` 恒走降级，任务行配方为空，worker 仍读当前注册源。
原件：`serve_f6.py:4444/4529/4708`（收口才补）；修复前 `api.py:1492`（无 reader 的兜底把缺原件伪装成事实）。
最关键的一条：`serve_f6.py` 在 `6ad3193a` 之前，在规格、决策日志、五卡里全文 0 次出现。
最早干预点：写 P3 写集时；线索是 AC1 说的「普通回测」必然经过组合根。
责任人：计划阶段作者；独立审查者；框架侧的写集校验（问题 3）本可拦住。
反驳事实：终末外部审查确实抓到了，说明异构审查有效——但代价是整段返工。

**问题 8：F13 受限子进程至今没有 `research_data` 端口。**
预期：绑定任务由谁执行，谁就该拿到同一套端口。
实际：`runtime_ops/run_secured_backtest.py:145` 构造应用时不传端口。
后果：一旦候选任务继承到冻结身份，就在子进程里以「研究数据不可用」失败，父进程只记资源失败。
原件：`run_secured_backtest.py:145`；`backtest_queue.py:445–459`；`serve_f6.py:4529`。
最早干预点：P3 接线那一步；线索是 F13 候选任务改由子进程执行的设计已经写在卡里。
责任人：本卡实施者（收口时只补了三处，漏了第四处）。

**问题 9：共享历史「自动抓取、执行时按名拒绝」，且抓取区间按月份首日比较。**
预期：同一策略的结果不该取决于窗口是否跨月。
实际：生产 store 绑了共享历史，归一化默认要求它进身份；跨月窗口抓到 part，执行时又拒绝。
原件：`research_data.py:1565–1580`、`:883–895`；`research_data_store.py:2298–2311`。
后果：要么静默少抓、结果与未绑定路径不同；要么抓到后拒绝执行并被归为可重试失败。
最早干预点：P2 决定「角色带而未用是否具名失败」时；当时已有线索是该角色从未有真实夹具。
责任人：C2 存储 owner 与本卡实施者。

**问题 10：候选验证「继承基线身份」与「验证窗覆盖」互相打架。**
预期：绑定基线的候选验证应当能跑通。
实际：验证段从基线次日起，几乎必然超出基线身份月份，于是降级未绑定，再被冻结基线守卫拒。
原件：`backtest_queue.py:3169–3181`、`:2839–2849`；`queue_store.py:405–425`。
后果：异常逃出 `create_candidate_validation` 的捕获集，留下「计划已建、尝试未建」的半成品。
最早干预点：R11 收窄时；线索是真实验证窗一定跨月，而夹具只有一个月。
责任人：本卡实施者；复核者已指出但按「老设计不改」收窄。

**问题 11：同一语义有五六份实现，维护成本已经可感。**
预期：源类型判定、绑定入队、冻结守卫各只有一处。
实际：`registered_source_for_run` 两份、源匹配两套、绑定+入队两份、冻结守卫两份。
另有 `frozen:` 前缀处理散落五处、反射读私有字段两处、应用层直连 C2 子模块多处。
原件：`validation_store.py:1659` 与 `queue_store.py:359`；`trusted_backtest.py:1855`、
`backtest_queue.py:2851`。
后果：修一处漏一处——本卡的 F0/F1 修复就只改了两处里的两处，第三处仍在。
最早干预点：P3 引入绑定路径时；线索是可信回测路径已有同构实现。
责任人：本卡实施者；C2 与 application 的两个 owner。

**问题 12：测试夹具换掉了生产组合根，恰好避开上面几条风险。**
预期：测试应能在接近生产的组装下证明行为。
实际：夹具只给三个 reader、不传共享历史、进程内直接执行、F13 关闭。
原件：`test_research_binding.py:316–323`；
`test_research_composition_root.py:253–257`；
没有任何用例 POST `/api/backtests`。
后果：生产上三条失败链（子进程无端口、共享历史、候选跨月）全部落在测试盲区。
最早干预点：P3 写冻结测试时；线索是卡里把「生产组合根」列为收口修复而不是验收面。
责任人：独立测试作者与计划作者。

### （四）验收与交付

### （五）哪些做法真的起了作用

预写冻结测试起了作用：它抓到主会话把默认配置里不该标真实的字段标成了真实。
边界是只看写集内文件；跨包接线看不见，所以生产组合根漏了。
终末异构审查起了作用：三路外部模型加两栏同源补充，独立命中同一处生产缺口。
边界是材料覆盖大量「未判定」，只能当线索，不能当通过。
同源两栏起了作用：Standards 与 Spec 两栏各自独立指出同一个组合根问题，互相印证。
真实数据验收起了作用：AC1、AC2 从合成样本改成真实行情，四层逐项对得上。
测试变更请求（TCR）起了作用：改冻结测试要留动机、行位、新旧 sha，避免悄悄放宽。

## 三、WorkflowHub 哪些阶段、步骤或技能应该改？

要改的是「声明与核对」这一段，不是再写一份更好的文档。
四条改造按影响排序；第一条最关键，因为它决定做完的东西能不能被算到。

### 改造一（最优先）：让 Phase 的声明变成可执行契约

现行短链：卡里写「写入集」与步骤清单 → 实施 → 运行入口只写阶段游标 →
检查脚本去阶段行里找散装证据 → 越界与缺步都要等人事后发现。

拟议短链：卡声明结构化 → 每步便携结果落库 → 收口用真实 diff 对照写集 →
检查脚本读同一份结果 → 缺步或越界当场拦下。

- 受影响：`workflows/build-code/steps.json`、`tools/cli/stage-runtime.mjs`、
  `runtime/task/final-chain-runner.mjs`、`tools/cli/run-checks.mjs`。
- 新增：本阶段的逐步结果写入（复用已有便携执行器）；写集对照器（读 diff 与声明比）。
- 修改：`stage-runtime.mjs:1867` 的拒绝分支，允许本阶段便携输入；
  `final-chain-runner` 的步骤选择改读便携结果。
- 移动：写集校验从「人读审查」前移到每 Phase 收口。
- 删减：删掉「步骤必填但没有生产者」和「写集只作参考」这两条隐含假设。
- 触发：每 Phase 收口与终末；产出者：Phase 实施子代理；接手者：检查脚本与步骤检查。
- 消费者：覆盖率报告、收口判断、独立审查输入。
- 保留：命令回执、Git 授权链、关闭流程、终末异构审查。
- 为什么现有入口承担不了：现有运行入口对非计划前阶段直接拒绝便携输入，
  而检查脚本又只认便携结果或阶段行证据，两端接不上。

### 改造二：Phase 级独立审查成为阶段事实的一等项

现行短链：Phase 收口 → 实施者自评 + 测试数字 → 阶段行只有整任务审查。

拟议短链：每 Phase 收口写一条审查结果（phase 标识、结论、发现与处置）→
阶段行引用该结果 → 收口时缺这条就判该 Phase 未完成。

- 受影响：`skills/stage-close`（收口读取）、`tools/cli/stage-runtime.mjs`（审查记录）、
  `runtime/task/final-chain-runner.mjs`（阶段完成判定）。
- 新增：按 Phase 切片的审查输入（整份 diff 超限时可切片）。
- 修改：阶段完成判定要求 phase 级审查存在且结论可读。
- 触发：每 Phase 收口；产出者：独立审查者；接手者：主会话。
- 保留：整任务终末审查（它是发现生产缺口的关键）。
- 为什么现有入口承担不了：现有审查入口按整份 diff 抓包，超过工具上限直接失败，
  本任务两次都因此没派出；需要先有小切片的输入形态。

### 改造三：外部依赖要有台账，验收只能引用编号

现行短链：验收里直接写「要真实版本行」→ 计划期不登记 → 收口时补记外部依赖。

拟议短链：规格顶部一张依赖表（编号、owner、交付物、恢复条件、复验命令）→
验收条目只引用编号 → 计划审查核对可达性。

- 受影响：`skills/spec-specify` 的规格模板、`build-plan` 审查清单。
- 新增：依赖表字段（编号、owner、交付物、恢复条件、复验命令、状态）。
- 修改：验收条目必须引用依赖编号，不能直接写别人的交付物。
- 触发：计划阶段写规格时；产出者：计划作者；接手者：独立审查者。
- 保留：决策日志现有的「未决」与「风险」两张表（直接被扩展，不另立账）。
- 为什么现有入口承担不了：现有两张表按主题记风险，没有「依赖编号 → 验收引用」的对应，
  所以验收里的外部依赖可以一直隐形。

### 改造四：收尾状态机解耦，产物设体积上限

现行短链：一个关闭计划钉住当时的目标头 → 归档产生新提交 → 推送失败 →
删完工作树后无法再记账。

拟议短链：归档、推送、清理各自可重入，每步重读当前头并单独授权；
知识图重建命令同时给出体积上限与超限处置。

- 受影响：`skills/stage-close`、`skills/knowledge-graph`。
- 修改：把「计划时刻的头」改成「动作前重读」，三步各自可重入。
- 新增：图产物体积检查与大文件托管路径（已有 LFS 基础设施）。
- 触发：收尾每一步；产出者：收尾执行者；接手者：主会话。
- 保留：最终范围确认（删除前仍只问一次）。
- 为什么现有入口承担不了：现有关闭计划把动作顺序与头绑定写死，
  手工补做会让账与动作不同步。

### 顺序理由

先修改造一：它让「做完的步骤」和「越界的改动」变成当场可核的事实。
再修改造二：有了步级事实，Phase 级审查才有稳定的输入切片。
再修改造三：依赖编号能把「收不了口」在计划期就暴露。
最后修改造四：它影响的是收尾效率与可重复，不改变产品结论。

## 四、怎样验证改造、说明调查边界？

每条改造都配一个真实失败与一个对照，并写明「回放没做」的部分。
本报告只做了静态复核与既有原件回读；没有启动新流程演练。

### 改造一怎么验

历史失败：本任务。框架版本是 11-16 当天版（`49d91b75`）。
入口是 `run-checks --task-path`，输入是归档 spec 与事实账。
观察结果：覆盖率十项四项、缺步三十九、本阶段步骤事实为零。
正常对照：`f20-event-ledger`，同一检查脚本、同一入口。
它的输入有 640 条步骤事实（本阶段 30 条），应能算出该阶段覆盖。
新流程应在 build-code 第一步就报「本步没有结果原件」，而不是等到终末。
要保住的能力：阶段游标、命令回执、终末审查都不受影响。
回放状态：对照任务的 run-checks 未跑，属拟议试验。

### 改造二怎么验

历史失败：本任务五个 Phase 都没有阶段级审查，两次阶段审查都因整包超限未派出。
入口是 `stage-runtime review --action=record`，输入是整份交付 diff。
观察结果：`blocked_before_dispatch`、`authoritative=false`。
正常对照：整任务终末审查（`2026-11-16-009`）能跑，因为它的包被单独抓取过。
新流程应在 P1 收口时就要求一条 phase 级审查结果，缺了就不能记完成。
要保住的能力：整任务终末审查仍是必做项，不因新增阶段审查而取消。
回放状态：拟议；现有审查入口尚未支持切片输入。

### 改造三怎么验

历史失败：AC6 依赖任务 11 的版本行，计划期无登记，收口才补 D-01。
入口是计划审查 013 与规格 948–968。
正常对照：同一个任务里的真实市场数据依赖做对了——有 owner、有恢复条件、
P2 卡 355 行明确写「不可用，待数据 owner 供件」。
差别不在能力，而在「有没有一张表强制登记」。
新流程应在计划审查时直接问：这条验收引用的每个外部物，编号在哪。
要保住的能力：现有「未决」与「风险」两表继续用，不另立第二套账。
回放状态：拟议；没有第二份带依赖表的历史材料可对照。

### 改造四怎么验

历史失败：本任务归档后推送失败（`TARGET_HEAD_DRIFT`），
删完工作树后无法再记账（`WORKTREE_NOT_REGISTERED`）。
入口是关闭计划 001 与关闭动作 005。
正常对照：同一流程里的提交、推送分支、建 PR 三步都成功，
因为它们每一步都在动作前重读了当前头。
差别是「把计划时刻的头当前置」还是「把动作前重读当前置」。
新流程应在归档后立刻重读头再推送，不依赖旧计划里的头。
要保住的能力：删除前的一次真实范围确认不能省。
回放状态：拟议；没有在第二个任务上重放过新流程。

# 怎样证明同一能力在页面、后台和子进程都成立？

用局部测试证明业务规则，再用按生产方式启动的隔离入口证明接线。
接缝是调用者可以观察行为的边界，例如一个 HTTP 请求或后台队列命令。
本轮用 AnySearch 检索作者分享、技能源码和用户反馈，并回读主要原件。

## pstack 的功能地图覆盖到哪里？

做法 1。沿实际入口验证操作及副作用，并在应用变化后更新方案。
Lauren 把自证看成代理的基本开发循环，入口可以是命令行、API 或页面。
pstack 先复用项目驱动，以选中的实际入口操作应用、取证和清理。
维护技能先查代码，再由协调者集中实跑以区分地图漂移与产品回归。
其起步方法默认选主要入口，适合尽早打通一条途径。
对于多种调用者共用能力的系统，仅核主要入口会留下别的装配路径。

Cursor 仓库有一条具体使用反馈。
作者报告其项目的地图偏向人操作的路径，漏掉了 SDK、代理钩子和自动调用。
此议题关闭为不计划采纳，它是使用者发现的边界。
WorkflowHub 可让验收条款点名本次受影响的程序入口，例如队列或子进程。
只从真实调用关系挑会改变结果的入口，按计划复用一处权威。

## Matt 怎样选择测试接缝和设计接口？

做法 2。规则在公共行为边界测，实际运行装配另用可观察结果核验。
Matt 的 TDD 先定接缝，比较每个候选验证得到什么、会漏掉什么。
作者说明纯接线或配置有时缺合适的 TDD 判据，硬写测试会复述实现。
能观察真实副作用时，可用一次最小整合运行证明依赖真的被装上。
如果不同入口本来承诺同一件事，比较是否能把规则收回一个已有模块。
先试删除纯转发层会消掉什么，再决定是否需要抽接口。
保留有独立职责的调用路径，例如子进程的资源隔离和权限边界。

## WorkflowHub 应该把两种验证放在哪？

build-plan 在现有 Phase 验收里写清业务判据、实际调用方和接线观测。
build-code 改动相应入口时，先使用项目最窄的公共接口验证规则。
再由测试者从正常启动路径验证一个代表输入和一个会暴露旧错误的输入。
分支若有独立装配且共有新承诺，按该入口走自己的接线对照。
终末保留高风险集成和独立代码判断，引用仍适用于最终版本的原件。

数据冻结任务的普通回测和受限子进程有不同构造入口。
普通回测的隔离复验能证明这一条链，子进程的候选缺口仍需自己的原件。
现有开发和测试方法可以承接，尚未执行新试点。

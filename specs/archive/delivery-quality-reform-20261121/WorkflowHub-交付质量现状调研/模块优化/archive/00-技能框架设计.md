# 技能框架设计：让技能保证「一次做对」，而不是事后检查

- 用途：回答「怎么让 WorkflowHub 的技能真的执行原则，而不是靠 agent 自觉，也不是靠事后加审查/扫描」。
- 结论先说：**把原则放进「产出物合同」，让下一步没有它就开不了工；不加审查、不加扫描、不加阶段。**
- 与 38 条原则的关系：原则定「什么算对」，这份框架定「怎么保证它发生」。原则不改，落地方式改。

## 一、为什么现在的技能不保证执行

- 现在的技能大多是「建议清单」：写了要做什么、要注意什么，但**没有产出物形状**，也没有**下游强制消费**。agent 可以读完、点头、然后照旧做。
- 事后审查和扫描的问题：它们在错误已经发生之后才介入，成本最高、漏得最多；而且每加一层，系统更难读完，下一轮更容易漏。用户原话：`你当前任务中所有的改动都是偏向于事后修改，事后检查，这种是增加成本，降低质量的东西`。
- 真正让 pstack / Matt 的技能「会失败」的，不是命令多，而是四个杠杆：**证据是下一步的输入**、**第二方重跑**、**检查器先红一次**、**读数不等于状态**。其中最强的是第一个：下一步没有上一步的产出，就根本开不了工。

## 二、框架：四个合同 + 三个机制 + 一条原则

### 四个合同

| 合同 | 谁产出 | 必须写清 | 谁消费 | 缺了会怎样 |
| --- | --- | --- | --- | --- |
| 方向合同 | make-decision | 用户要什么；哪些必须保持；哪些没定、谁定、什么条件能定；验收怎么判 | build-plan | 缺任一项，build-plan 不接包 |
| 计划合同 | build-plan | 每张卡一条用户可见结果；受影响入口；写集；验收条件（含会红的坏例）；实现决策（规则住哪、状态几种、默认值谁定、封装藏什么）；失败怎么退 | build-code | 缺任一项，build-code 不开工 |
| 实施合同 | build-code | 按计划合同做出来的改动；每个验收条件的原件；写集对账；没做/没验的具名缺口 | 验收/收口 | 缺原件，验收不能判通过 |
| 交接合同 | 收口 | 下一步；原件指针；不确定的三件事；四类事实 | 接续者 | 缺指针，接续者不能开工 |

合同的写法只有一条要求：**下游能直接拿它开工，不需要回来问。** 写不到这个程度，就是没写完。

### 三个机制

1. **先决条件**：每个合同有「开工前必须有什么」。缺了就不能开工，不是「先做，做完再补」。例如 build-code 开工前必须有计划合同里的「受影响入口 + 写集 + 会红的坏例」；缺一项，不开工。
2. **下游消费**：下一步的输入就是上一步的产出，缺了脚本/流程直接拒绝。不是「建议读」，是「没有就读不了」。例如验收只读实施合同里的原件，不读摘要；摘要不算。
3. **角色分离**：产出者、消费者、独立判断者分开；产出者不能给自己判通过。不是加一轮审查，而是**换一个人拿同一份合同做下一步**。

### 一条原则

**能放进合同字段的，不做成审查问题；能靠下游消费强制的，不做成检查器；只有确定性不变量才做检查器。**

这条原则直接回答「要不要加扫描/审查」：不加。把要求前移到「写代码之前必须定什么」，让错误在便宜的时候被拦住。

## 三、两个代码习惯怎么在设计阶段解决

用户点名的两条，不再做成「实施要求」或「审查问题」，而是放进计划合同的「实现决策」一栏，由 build-code 开工前消费：

### 1. 能用类型/结构挡住，就不写事后检查

计划合同里每张卡写：
- 这条规则涉及哪些状态？能不能用枚举、唯一构造、单一入口表达？
- 如果还要写运行期校验，写清「为什么类型/结构挡不住」。
- 写不出理由，就不许写运行期校验，也不许写复述实现的测试。

这不是事后扫描，是**写代码前必须做的决定**。决定错了，下一步（写代码）会直接按错的决定做，但至少不会在事后才发现。

### 2. 新增封装要说清藏了什么复杂度

计划合同里每张卡写：
- 这层对外提供什么？
- 把什么复杂度藏在里面？
- 删掉它，哪两个调用者会合并？
- 如果答不出，就不加这层。

同样不是审查问题，是**加封装前必须回答的问题**。答不出就不加，避免 958 行单函数和空转发层。

### 3. 默认值

计划合同里每张卡写：
- 哪些情况必须显式失败？
- 哪些默认值是产品决定？谁定的？
- 哪些默认值会让坏数据看起来正常？这些不许有。

写代码前就定，不靠事后 grep。

### 4. 同一条规则不许有第二个家

计划合同里每张卡写：
- 这条规则住在哪个文件/函数？
- 哪些入口调用它？
- 如果写不出一个家，就不开工。

不是事后查重，是**开工前必须指认**。

## 四、四个合同分别替代哪些现有做法

| 现在 | 改成 |
| --- | --- |
| make-decision 写很长的决策日志，下游自己挑 | 方向合同：只留四块，下游按块消费 |
| build-plan 写 spec + Phase 卡 + 验收，实施时再理解 | 计划合同：卡就是开工令，缺一项不开工 |
| build-code 做完再审查、再补证据 | 实施合同：做的时候按验收条件留原件，缺原件不算完成 |
| 收口写 13 区块交接，接续者自己找 | 交接合同：下一步 + 指针 + 三个不确定 + 四类事实 |
| 事后加检查器/审查问题 | 前移到合同字段；只有确定性不变量才做检查器 |

## 五、对现有技能的处置

| 技能 | 处置 |
| --- | --- |
| make-decision | 产出「方向合同」；把现有 15 步压成「问什么、定什么、写什么」三块；不新增步骤 |
| build-plan | 产出「计划合同」；Phase 卡加「实现决策」一栏（状态/规则家/默认值/封装/失败退路） |
| build-code | 产出「实施合同」；按计划合同的验收条件留原件；不再靠终末补证据 |
| wh-review | 只做「独立判断」，不产出合同；判断者拿合同与原件，不拿摘要 |
| stage-handoff | 产出「交接合同」；四类事实 + 指针 + 三个不确定 |
| simplicity-guard | 并入计划合同的「封装」栏，不再单独作为审查问题 |
| spec-analyze | 只做合同一致性核对，不新增合同 |
| norm-sync | 只做「规则写进哪个合同字段」，不再写「注意事项」 |

## 六、与 38 条原则的对应（只列关键）

- P1/P2/P3/P4 → 方向合同的四块。
- P5/P6/P7/P8/P9 → 计划合同的入口、卡、依赖、坏例、规划稿条件。
- P10–P15 → 计划合同的「实现决策」栏（规则家、默认值、封装、类型优先、迁移删旧）。
- P16–P20 → 实施合同的验收条件与原件。
- P21–P23 → 独立判断者拿合同与原件，不拿摘要。
- P24–P28 → 计划合同的任务性质、失败退路、成本只观察。
- P29–P32 → 交接合同的四类事实、授权、恢复。
- P33–P38 → 合同字段的写法与准入；不再额外加审查。

## 七、最小落地：先改哪三个合同

1. **计划合同**：Phase 卡加「实现决策」一栏（状态/规则家/默认值/封装/失败退路）。这是最高杠杆：代码质量、整洁、重复、默认值都在这里定。
2. **实施合同**：验收条件必须带原件；没有原件不算完成。这是「通过」可信的根。
3. **方向合同**：四块写不清就不接包。这是需求走样和交接断的根。

三个合同之外的东西（成本账、十分钟接续、集合差、并发验证）先不做，等这三个合同跑一个真实任务，看读数再决定。

## 八、这份框架不做什么

- 不加审查轮次、不加扫描器、不加阶段、不加账本。
- 不要求 agent「更仔细」「加强审查」——这类话一律不算机制。
- 不把合同写成更长的文档；合同只写「下一步开工必须知道的」，其余放原件。
- 不一次性改所有技能；先改三个合同，跑一个真实任务。

## 九、怎么判断框架生效

- 下一步能不能只拿合同开工，不回来问。
- 缺一项合同时，下一步是不是真的开不了工（不是「建议补」）。
- 一个真实任务里，方向类回问、验收缺原件、写集越界、默认值无主、重复规则这几类，是否在开工前就被拦住，而不是在终末审查才发现。
- 如果读数没变化，停，不再加合同字段；回到任务粒度和执行模型重新判断。

# WorkflowHub 的三个阶段，分别该把什么事情做对？

定方向，要说清用户最终会拿到什么。定计划，要找出怎样才能做出来。实施，要让代码真正做到，并让接手者容易改。
三个阶段分别防三种错误。做错东西、按错路线做、做出来却不可靠。
如果某一步只能在事后提醒下一位再看一遍，先找事情为什么会在那里出错。

## make-decision 怎样知道需求已经说清楚了？

把同一句需求交给两个认真做事的人。如果他们能做出用户会明显感到不同的结果，只讨论这个差别。

**原则 1。用用户看得见的差别说明要做什么。**
T03 要求「重启后补写」。一种做法是系统起来就自动恢复，另一种是等运维手动发起。
两种做法都能补回数据，但谁要采取行动、多久能看到恢复、无人操作时会怎样，都不同。
定方向要解决这类差别，必要时用正常与失败各一个例子说清楚。
用户选定发起者和失败后的处理方式，计划就有可以执行的目标。
如果两种实现对用户没有差别，只改变内部函数、文件或框架，交给计划和实施者决定。

**原则 2。先用已知事实缩小选择，再请用户决定剩下的事。**
T08 已明确沿用任务 0 的页面，计划仍提出做原型，最后用户再次说明只接数据。
代理应当打开已有页面和设计，确认哪些能力已经存在，再给出需要改变的行为。
现有组件怎样取数，代理查代码。要不要改用户操作和页面布局，才由用户决定。
并排做两份原型只适合双方确实还没选、且实际样子足以改变选择时。
这条原则会删重复展示、重复确认和已被排除的纯设计任务。

**原则 3。可以等事实，不能先替用户决定。**

计划作者如果要改其中一项，带清楚实际差别回原决定。其他事情可以继续。

## build-plan 怎样知道方案能开工？

先找那条「如果我们猜错，计划就得重来」的假设。
在决定工作顺序前，用最省事且能回答它的实际观察。

**原则 4。只提前试会改变方案的问题。**
T04 内部读取能反映来源停用，用户真正访问的 HTTP 当时没有接上。
若准备复用一条现有路径，优先确认页面或接口实际走哪段代码、读哪份数据。
现有代码已经能确定，就用代码回答。有现成隔离环境而代码不足以回答时，再试一次。
如果「当前理解应该降级」与「过去保存的快照应该保持」混在同一个判断里，
先澄清两份结果各表示什么；多跑一次测试无法决定用户要保哪一个。
计划若没有会改变路线的关键未知，一般直接使用已有方法开工。

**原则 5。先做成一小件能用的事，再扩范围。**
以来源停用为例，第一份可以交付的结果是：用同一条记录操作后，从公开入口看到正确状态。
数据、应用逻辑和读口为这个小结果一起工作。把它们分成三张各自绿的卡，没人能证明用户拿到了结果。
如果必须等另一个工作提供接口，由接口提供者用下游会用的方式证明自己已经交齐。
T08 的合同文件已经在仓里，下游仍缺具名接口。仅检查文件存在发现不了这个问题。
纯技术迁移可以单独做；它必须能展示真实调用者迁过去、原有结果仍完整。

**原则 6。先约定看什么结果，再决定如何测试。**
T01 的浏览器脚本按下按钮后马上去领任务，真正的任务有时还没来得及入队。
这个红灯说明观察时点不可靠，不能拿来判功能。用本次任务身份等到可领取，再看是否满足约定。
关键测试需要区分三种情况：正确行为确实到达、指定错误真的发生、测试环境自己出了问题。
已有公开入口和具名项目测试就复用。需要第三方凭据或尚未完成的环境时，写明暂时能回答到哪。
日常配置、简单文档或直通代码用适合它的轻量检查，无需为了形式造一个失败。

交给实施的是第一件能做的事、它所需的东西、从哪儿操作，以及成功或失败长什么样。

## build-code 怎样同时把功能做对、把代码留好？

让正确行为从代码结构里自然发生，并从用户会用的入口证明它发生了。

**原则 7。再改一次同样的业务规则时，应该知道去哪里改。**
T08 的公开 HTTP 和周作业分别接入应用。当前源码显示，两边传入的月内质量校验依赖不同。
若两边应遵守同一规则，应用的合法入口应让两边都必经它，调用者无需分别记得接校验器。
用同一个缺交易时段的月片和一个正常月片分别通过两处入口，看拒绝、发布和读回。
允许保留手动与自动各自的发起、权限及错误反馈。这些确实是两个不同的业务条件。
省掉的是每个调用者各复制一份规则和每次审查靠人提醒。当前只证装配差异，实际后果还有待隔离试跑。

**原则 8。测试保住用户和调用者看得见的行为，让内部可以整理。**
T01 同一类有两份同名方法，调用只会走后一个。
这值得删的理由是留下两份可抄的旧写法会让维护者改错地方。不能用文件长短决定拆并。
先用既有公开行为保住实际结果和错误，再移除失去作用的定义。

如果测试能在真实行为破坏后仍通过，或者内部等价改动就失败，就应换它的观察位置。
隔离网络和时钟可以；如果被换掉的正是这次要交付的行为，该测试就只能证明替身路径。

## 用这些原则，应先放下哪些改造？

把每条建议还原成一次实际决定。只有结果会更好、错误更难发生或多余动作能退出，才值得保留。

| 方案 | 判断 |
| --- | --- |
| 再加一轮通用审查，让审查者关注实际效果 | 现有生成器已经漏了同一问题。先修它实际发出的内容，缺效果的原业务包就是验证样本 |
| 每个 Phase 都先起一套环境 | 计划只试会改变路线的未知。新环境解决不了承诺冲突，已有证据足够时直接用 |
| 为所有项目新建一个统一的领域模块或通用验证框架 | 先用一个反复发生的项目问题证明同一合法路径能降低维护负担，再决定是否值得复用 |
| 统一改掉所有同名方法、所有大文件 | 看它们是否有不同用户和合法行为；只收回真重复，引入契约变化时另作明确决策 |
| 因为有 Git 合并、完整台账或监控绿灯就宣称交付 | 让每个原件只回答它确实观察到的结果 |
| 每阶段收尾再问一次和再核一次 | 沿用当前答复和仍有效的原件。只有受影响项回原阶段 |
 
先用一件真实任务试三阶段分工。候选只能靠更多固定动作或重复执行才工作时，撤掉对应候选。

# R14 交互缺口增量

本增量记录用户在原规格接受后继续要求修复、且由 R14 真实 Canary 复现的三项缺口。
它不修改已冻结的 `spec.md`、`plan.md`、`tasks.md`，也不引入新的 runtime、schema、
状态机或 Multica 平台代码。

## 需求

0. 用户在规格接受后明确修正 AC-001：三轮 `talk-with-zhipeng` 都必须执行各自职责、
   建立候选问题队列并在每次回答后重排，但不得固定每轮必须问两次。事实已经足够时，
   该轮可以不再提问，前提是公开写出已核实事实和结束理由；仍会改变方向的问题未解决时
   不得提前结束。
1. 候选工作区、项目资源映射、checkout 和任务身份属于宿主技术配置。执行者先做真实
   访问检查；能访问就继续，不能访问就返回宿主协调者自修。除非确实缺少新凭据、权限
   或不可逆外部授权，否则不得要求用户选择。
2. 用户可见的 Phase 描述只展示大白话目标、完成标准、允许改动、测试方式和下一责任人。
   Workspace 路径、baseline、hash、内部 ID 和精确命令只保存在正式 Phase Card，不进入
   用户可见描述。
3. build-code 最终完成卡必须从最新 Phase 结果和最终全树证据重新生成；后来的事实覆盖
   早期 provisional skip、风险和 finding。重复唤醒发现 Stage 已完成且无新动作时静默结束。

## 验收

- 三轮 talk 各有独立队列、重排和结束结论；提问次数由未决问题决定，不以固定数量
  作为通过条件。
- 本地资源列表缺少候选 worktree、但真实路径可访问时，不产生用户决策卡并继续 Phase。
- 真实不可访问时，只返回宿主协调者，不 @用户。
- Phase 用户可见描述不包含绝对路径、hash、内部 ID、baseline 或精确 shell 命令。
- 最终完成卡使用最新 Phase 事实；R14 中“权限测试已真实通过”不得被早期“跳过”覆盖。
- 已完成 Stage 的重复唤醒不产生公开 comment。

- R14 `ZHI-571`、`ZHI-572` 的公开描述被英文 Phase Card 和内部字段主导。
- R14 `ZHI-569` 最终卡沿用早期权限测试 skip，随后又产生无动作 no-op comment。

## 边界

- WorkflowHub 只保留宿主中立的公开投影、技术故障返回、最新证据和静默 no-op 合同。
- Multica instructions 只映射到可见 Issue 描述、返回工头和真实 mention。
- 不修改任何 Agent provider、model、runtime 或 Skill ID。

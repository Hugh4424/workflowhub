## 作者开工五问的答案是什么？

这五问按 `skills/spec-plan/references/authoring-contract.md` 写，第 7–9 段沿用同一组答案。

1. 为谁做：第 6 段开发者（唯一写主）和事后跑命令的独立测试者。
2. 他拿它干什么：开发者照卡在写代码方法里追加 UI 段；测试者照卡跑单文件命令并留原件。
3. 读到哪里会卡：第 5 段写出的“UI 六项”字段名，以及组件规范写到哪里。
   六项是设计源引用、页面／路由／组件与状态乘视口、视觉对照项、
   前端质量门、组件复用与沉淀、独立设计审查与证据；
   原文在 `workflows/build-plan/SKILL.md` 第 7 步与 Phase 模板组件回写位置（`phases/P5-排阶段UI验收.md`「下一消费者」）。
   本卡把字段名的来源指给第 5 段产出，把组件规范的去处写成目标项目根。
4. 失败怎么恢复：断言变红先分清是正文缺句、测试夹具坏还是本来就通过；
   正文缺句回第 6 段开发者，夹具坏回写测试的人，修完重跑同一条命令。
5. 哪些话只有内行懂：首次出现时就地解释。
   “设计源”指设计稿或可运行原型；“页面审计”指 `page-audit.md` 规定的逐页检查；
   LCP、CLS、INP 是浏览器测的三项加载与交互速度指标，含义在验收 1 写明。

## 这一 Phase 交出什么？

交出一份会按两种尺寸对照设计稿的写代码方法，前端质量有最低判据，组件经验写回目标项目。

- **本 Phase 结果**：写代码方法遇到 UI 任务时，第 1 步读设计源与已批准原型；
  第 6 步按 1440×900 与 390×844 两种视口截图，逐项写通过、差异、用户接受的偏差；
  第 7 步页面审计写组件复用与沉淀结论，并写回目标项目根下的组件规范；
  第 7 步同时产出七项界面判定字段，交第 7 段审查读；
  第 8 步加设计审查角度；第 9 步视觉问题与功能问题同修同复验；终末复核对照结论。
- **非目标**：不让审查方法加六问。那部分要读本段第 8 步正文，归第 7 段交付。
- **改动前**：写代码方法有页面审计，但没有固定两种尺寸，没有组件沉淀结论，
  功能测试通过就可能被当成 UI 通过。
- **改动后**：UI 任务在第 1、6–9 步与终末多一段 UI 条件正文；非 UI 路径原字节不变。
- **与相邻 Phase 的边界**：上游第 5 段交“UI 六项”字段名；本段交第 6–9 步 UI 段，
  第 7 段读第 8 步接设计镜头，第 9 段用它跑演练第③、④、⑤、⑥组。
- **主要风险**：改写受断言保护的原句，让既有测试变红。
  替代走法：只在原步骤后追加段落，不改原句；若必须改原句，先停并回报主会话。
- **下一步**：第 7 段开发者读本段第 8 步写审查设计镜头。
- **动手前必读**：`spec.md` 的「文件边界」与验收 4；

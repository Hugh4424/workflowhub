## 这一 Phase 交出什么？

方向与细节审查者实际收到效果四要素，发现的角度可从最终记录反查原始来源。

- **本 Phase 结果**：第⑤问、受控 lens、多贡献保留和计划预算分支同时生效。
- **非目标**：不增加 provider 请求、审查轮次、强度或其它 stage 的必填角度。
- **改动前**：合同已有效果问题，实发指令与解析合并链仍可能丢它或 lens。
- **改动后**：实发、解析、配对、canonical、记录路由和 schema 使用同一合同。
- **与相邻 Phase 的边界**：消费 Phase 1 共享步骤状态，向 Phase 3 交回新版步骤。
- **主要风险**：只改最终 schema 造成假接线；若实发缺问，整组撤回本 Phase 接线。
- **下一步**：Phase 3 在同版步骤上切默认版本，记录读者复核 lens。
- **动手前必读**：`quality/evidence/decision-maker/p02/card.md:5-15`。
  再读同目录 `design.md:26-98` 与 `build-plan/light-research.md:26-28`。
- **未决事实**：历史 lens 读未知；新输出缺失或非法不得自动补值。

## 这一 Phase 怎么验收？

本 Phase 只承接 spec 的验收2；完整判据以 AC-REV-001 为唯一权威。
非 UI：不适用——本 Phase 只改审查指令、解析与记录，没有页面改动。

- **成本账**：引用 AC-REV-001；验收活动为25活动分钟，属未校准估算。
  `acceptance_cost_total=25 active_min`；`phase_budget=unknown — 无已校准基线`。
- **资源账**：使用现有组包器、记录路由和受控 provider 输出，可就地构造发现。
  不需要在线 provider；受控输出不能证明在线服务质量。
- **范围账**：只证审查指令、角度和预算分支；Phase 3 的默认卡版本是下游供件。

**验收2：审查指令和角度全链一致**

目标是实际审查者收到第⑤问，最终发现保留 lens、provider、role 与原输出引用。
操作时生成 direction/detail 真实 packet，再驱动 parser、两种合并和唯一记录入口。
条件是仓内 Node、真实组包与记录入口、受控合法和非法输出均可用。
历史缺 lens 记录应读 unknown；新 direction/detail 分别缺 lens 不得干净通过。
故意让合同保留第⑤问而实发只有四问，或让两条发现只差 lens，必须暴露差异。
真跑命令见任务2；独立测试执行者在实现与审查修复后判定。
失败回包2原开发；词表漂移或合并丢贡献时停止新 direction/detail 派发并修同链。

## 怎么验证？

测试面是运行时纯函数、命令行合同与真实记录消费，主技能预判为 backend-testing。
目标 RED 必须由第⑤问、lens 保留或预算分支的具名断言产生。

任务2命令：
`npx --no-install vitest run tests/contract/review-effect-lens.test.mjs tests/contract/review-materials-contract.test.mjs tests/contract/review-axes-contract.test.mjs tests/review/review-record-route.test.mjs`

RED 期望目标断言非零；GREEN 用同一命令期望0。
手工 oracle 是独立写下一个 finding 应有的 lens、provider、role、原输出引用和合并归属。
负控包括四问实发、`lens=codex/red`、跨 lens 合并和预算角色条件。
证据由真实捕获链保存；受控发现只作输入，不改期望来源。

覆盖上限：不证在线 provider 理解、其它 stage 角度义务或 Phase 3 的路线效果。
显式不覆盖真实用户长期效果和旧记录全部兼容。

失败时保留 provider 原输出与失败记录，回包2原开发修对应链段。
回滚整组撤本 Phase 接线，历史记录不回填、不猜角度。

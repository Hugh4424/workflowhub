# UI 设计与前端开发工作流参考手册

> 这份手册写给软件公司的设计团队和前端团队，也写给用 AI 辅助（或 AI 主导）写前端的任何团队。
> 它解决的问题只有一个：**为什么 AI 时代"代码能跑"的前端交付，总要返工 5 轮、耗费 20+ 小时人肉 QA，才能达到"看起来对"？**
> 前六部分是通用方法论——问题、概念、流程、质量、规则弹药、效果验证，任何团队不依赖任何特定工具即可采用；第七部分是一个真实工具（workflowhub）按这套方法论落地的实例摘要，供参考，不是前提。
> 阅读建议：第一、二部分建立共同语言，第三部分照着执行，第五部分当字典按需查阅，第六部分用于向老板/团队证明改造有效。

## 第一部分：问题篇——AI 时代前端开发为什么总是返工

**这节讲什么：用一个真实案例和一张缺陷全景表说明，返工不是偶然事故，而是流程缺失的必然结果。**

### 1.1 真实案例：PB-T08

某团队在 PB-T08 任务中要求 AI 把三个页面（模拟记录、模拟工作台、策略列表）对齐到一份本地可渲染的设计稿。结果：

- **5 轮返工**，每轮都是"交付 → 人验收驳回 → 再交付"；
- **约 30 个缺陷**，逐轮由人肉眼发现；
- **20+ 小时人工介入**，跨多个会话往返；
- 第 1 轮交付后用户的评价是："完全是两个产品。"

各轮失败的真实根因（不是"模型不行"）：

| 轮次 | 人的反应 | 根因 |
|---|---|---|
| R1 | 完全是两个产品 | 凭 Tailwind 类名脑补像素值，无实测提取（类名 ≠ 像素，项目有自定义配置） |
| R2 | 8 条反馈后仍 7 条不满 | 规格只写"大概"；关键宽度差异（1560 vs 1760）从未被查证 |
| R3 | 又 6+2 条 | 删旧 CSS 误伤（指示灯变透明）；指标宽度未固定 |
| R4 | 浮窗被超长词撑爆、hover 失效 | 无边界压力测试（64 位哈希、长英文串） |
| R5 | 通过 | 曾把"右上角"修错目标（模块注记 vs 顶栏浮窗），浪费一整轮 |

转折点在第 3 轮：当人把设计稿组件源码**逐行**贴给实现者之后，一次通过。**规格信息密度与返工次数强负相关**——瓶颈从来不是执行能力，是规格密度。

### 1.2 11 类缺陷全景表

把 30 个缺陷按根因归类，得到 11 类。这张表值得贴在墙上——你的下一次 UI 任务，缺陷大概率落在这 11 格里：

| # | 缺陷类 | 表现 | 根因层 |
|---|---|---|---|
| 1 | 凭感觉理解设计稿 | 按类名/截图目测像素，数值整体漂移 | 缺提取：设计稿没有数字化 |
| 2 | 稿有结构缺失 | 设计稿里的块（如价格区、盈亏比行）在实现里消失 | 缺对照清单，没人逐行核对 |
| 3 | 自创结构 | 实现里多出设计稿没有的块 | 无"稿无结构不许加"约束 |
| 4 | 数值近似 | 间距、字号、宽度"差不多" | 规格写"大概"，无精确验收值 |
| 5 | 状态覆盖不全 | 默认态对，hover/loading/空态/禁用态没做 | 无状态覆盖强制清单 |
| 6 | 旧代码残留 | 1056 行 CSS 含 417 个历史块、同选择器三代叠加，"改了没效果" | 无 CSS 清场纪律 |
| 7 | 边界未测 | 超长 token 撑爆浮窗、hover 8px 死区、空数据破版 | 无边界电池测试 |
| 8 | 验证假阳性/假阴性 | 探针类名写错报假阴性、层级量错报假阳性 | 验证工具无对照表驱动 |
| 9 | 反馈歧义修错目标 | "右上角"猜错位置，浪费整轮 | 无消歧协议（10 秒确认可省一轮） |
| 10 | 环境/对象失锚 | 服务连错分支、服务挂了没人知道、"修好了"没有可验证对象 | 无验收对象绑定（分支/URL/端口/hash） |
| 11 | 单测绿灯当视觉通过 | 测试全绿但模态框藏在内容后、按钮在视口外 400px | 视觉没有验收语义，只有观察语义 |

量化分布（用于排优先级）：**约 60% 的缺陷可由"设计提取 + 组件对照清单"在编码前消灭；约 25% 可由"系统验证 + 边界压力测试"在交付前消灭；约 10% 是 CSS 历史债务；约 5% 是沟通消歧。**

### 1.3 根因分析

**为什么"代码能跑 ≠ UI 合格"？** 因为代码的 oracle（编译器、测试、类型检查）只管行为和逻辑，不管像素。后端任务有机器 oracle（测试红绿），前端任务的唯一 oracle 长期是人的眼睛。agent 的自主性等于其反馈 oracle 的自主性——前端没有机器 oracle，自主性就归零，人被迫当 QA。

**为什么"自审自判"无效？** 让写代码的人（或同一个 AI 上下文）自己判断"对齐了没有"，等于让考生批改自己的卷子。PB-T08 里实现者每次都"自认为对齐了"，每次都错。质量裁决必须由独立来源在独立上下文产出。

**三个"缺"总结：**

1. **缺规格**：设计稿是给人看的图/代码，不是给执行者看的数字化规格。没有提取，就只剩脑补。
2. **缺对照**：没有"稿有什么 vs 代码有什么"的逐行矩阵，缺陷只能靠人肉眼逐轮发现。
3. **缺证据**："完成了"没有证据支撑——没有截图、没有 diff、没有覆盖率数字，只有一句"我对齐好了"。

### 1.4 业界共识：解法是流程不是 prompt

对外部工程实践（monday.com 的 Figma→Code 流水线、kaelig 的 8-agent 设计系统流水线、yureki 的截图反馈回路等）的调研结论高度一致：**UI 质量差的标准解法不是"更会写 CSS 的 prompt"，而是可执行的视觉反馈闭环 + 结构化设计输入**。所有高质量案例共享五个要素：

1. 设计稿/设计系统先数字化（token/组件/状态机器可读），输入质量打分，差则硬停呈交人；
2. 协作各方用带必填字段的工件契约传递信息，而不是对话——数据缺失显式标 `[PENDING]`，缺席本身是数据；
3. 先结构后细节，禁止在错误结构上微调；
4. 给执行者装上"眼睛"：渲染 → 截图 → 结构化清单 → 修复 → 再截图，闭环非可选；
5. 迭代预算 + 收敛判定：每个环节有退出标准、最大轮数、收益递减即停，防"追逐 1px 阴影偏移"的病态循环。

两个反直觉但经实证的结论：

- **多数失败不是 prompt 问题**。kaelig 的三层失败框架把 34 个基线 findings 分为：18 个"缺规则"（写进规则库后永不再犯）、9 个"工具/基础设施缺陷"、6 个"必须人类判断"。返工后先分类归档，再决定改哪层。
- **规则会复利**。一个经典案例：agent 凭合理前缀编造了 27 个不存在的 token，组件渲染成无样式 HTML 但所有测试通过（测试查行为不查视觉）；修复 = 3 条规则进检查清单，此后永久归零。工程规则沉淀进清单不 decay。

## 第二部分：概念篇——这套方法论的基石

**这节讲什么：10 个核心概念，每个给出是什么/为什么/一句话例子。后面所有流程都是这些概念的组合。**

### 2.1 设计源冻结（design_revision 快照）

- **是什么**：任务开始时把设计源（设计稿文件/目录/规范文档）的内容做一次快照，记录路径 + 内容哈希，作为本任务的**任务期不可变**基线。
- **为什么**：设计稿在任务中途被改掉，"对齐"就成了打移动靶。冻结后，实现、对照、验收三方看的是同一个东西。
- **例子**：任务卡上写"设计源 = `design/` 目录，SHA-256 = `a1b2…`，viewport = 1440×900"；任务中设计师改了稿，那是新 revision，下个任务再用。
- **与回写的关系**：任务期间沉淀的新规范可以写回规范文件，但产生的是**新 revision**，当前任务继续用冻结的；只有当回写内容影响当前任务的设计源时，才需要 owner 重新确认并重新冻结。

### 2.2 规范层 vs 证据层

- **是什么**：规范层是项目级的"法律"——两个长期文件：`Design.md`（风格/token/组件 API/视觉状态/性能预算/治理规则）和 `Experience.md`（页面/交互/流转/异常恢复约定）。证据层是任务级的"执法记录仪"——每次任务产出的提取记录、对照矩阵、比对报告。
- **为什么**：不分层就会出两种病：规范散落在聊天记录里（下个任务失忆），或把一次任务的证据当永久规范（把草稿当法律）。法律管所有任务；执法记录仪只对本次任务负责，永不取代法律。
- **例子**：`Design.md` 里写"主操作色 = `--color-accent-solid`"是规范；本任务的提取报告里写"设计稿实测主色 `#3b82f6`，与 token 一致"是证据。

### 2.3 UI Contract 与验收对象卡

- **是什么**：任务开工时登记的一张卡片：页面/路由、状态清单、viewport、验收用的分支/worktree/服务 URL/设计源哈希、失败时怎么算。
- **为什么**："修好了"必须有一个可验证对象。连"5173 端口服务的是哪个分支"都没确认，就不能说"页面已修复"——对象失锚是真实案例里被认定为"最致命"的缺陷源。
- **例子**：卡上写"验收 URL = `http://localhost:5173/sim-board`，分支 `task/ui-align`，设计源 hash `a1b2…`，验收 viewport 1440×900 主、390×844 辅"。

### 2.4 parity 对照矩阵

- **是什么**：一张逐行表格："设计稿有什么（组件/区块/状态/数值）" × "实现里有什么"，每行标 结构一致 / 数值一致 / 状态覆盖 / 证据引用，打勾或标 missing。
- **为什么**：它把人肉 diff 变成机器可维护的清单。编码前它可以全红初始化（实现侧全 missing），编码后逐行翻绿——"改造完成"的定义就是矩阵全绿，不是"看起来差不多"。
- **例子**：设计稿有"待启动区卡片 × 状态九态 × run_kind 四标签"，矩阵就有对应行；实现缺"隔离态"样式，该行标 missing，验收时无处遁形。

### 2.5 视觉证据与"没验就是 incomplete"原则

- **是什么**：任何 UI 完成声明必须附视觉证据（截图、几何比对、感知清单作答记录）；**缺视觉证据的完成声明必须标 incomplete 并附原因**，不许含糊通过。
- **为什么**：截图可以造假方向（截错页面、截旧版本），所以证据要带 provenance（git commit + 服务 URL + 树 hash），过期即拒绝。诚实的 incomplete 远好于伪造的 complete。
- **例子**：完成声明写"视觉比对：未执行（本机无视觉模型），标记 incomplete，建议人工过目"。

### 2.6 双模式：reference-reproduction vs original-design

- **是什么**：有设计稿的任务走**复现模式**（reference-reproduction，忠实还原，不许自由发挥）；没设计稿的任务走**原创模式**（original-design，先在规格阶段把设计做出来、经人确认、冻结成自建设计稿，然后并入复现流程）。
- **为什么**：两种任务的风险完全不同：复现的风险是"不像"，原创的风险是"乱来"。共同点是**执行阶段都不许自由发挥**——无稿不等于可以即兴。
- **例子**：拿到 Figma 稿 → 复现模式；只有一个想法"做个策略工作台" → 原创模式，先出设计方向和效果图，人确认后才许写代码。

### 2.7 三条铁律

- **稿有结构不许缺**：设计稿里的每个区块、组件、状态必须出现在实现里。
- **稿无结构不许加**：设计稿没有的东西（多余卡片、自创装饰、擅自加的动效）不许出现在实现里。
- **数值不许近似**：颜色、字号、间距、宽度逐值复制，禁止"差不多"。
- **例子**：稿里卡片圆角 12px，实现写 10px——违规；稿里没有"快捷操作"浮条，实现加了——违规；稿里六灯指示灯，实现做了五灯——违规。

### 2.8 冲突裁决：测量层 computed 为准、规范层 owner 裁决

- **是什么**：两类冲突两种裁法。**测量层冲突**（设计稿源码声明的值 vs 浏览器实际渲染的 computed 值）以 computed 为准并记录差异——computed 是渲染真实。**规范层冲突**（设计稿的值 vs 项目 Design.md 登记的 token/规范）不许静默选边，显式记录交设计 owner 裁决。
- **为什么**：Tailwind 类名 ≠ 像素值（自定义配置会让 `w-4` 渲染成任何值），所以测量信浏览器；但设计稿颜色与项目 token 打架是设计决策，机器无权裁决。
- **例子**：稿用 `#3b82f6` 而项目 token 是 `--color-accent-solid: #2563eb` → 记一条冲突记录，owner 裁决"按稿"还是"按 token 并登记偏差"。

### 2.9 approved-deviation 与 task-local overlay

- **是什么**：owner 批准偏离设计稿时，记一条 **approved-deviation**（owner/理由/修正值/验收处置），验收按批准后的偏差判定；owner 批准的新 token 以**任务本地 overlay** 供当前任务使用，任务结束后合并回写规范文件。
- **为什么**：设计稿本身可能有专业缺陷（对比度不达标、缺状态设计），一味照抄不一定对；但偏离必须留痕，否则"忠实复现"无从谈起。
- **例子**：稿里正文对比度 3.8:1 不达标 → owner 批准改为 4.5:1 的深色 → 记 approved-deviation，验收按新值判 PASS。

### 2.10 缺陷分级与"全绿"的定义

- **是什么**：缺陷三级——**CRITICAL**（结构缺失/自创结构/功能错误）、**MODERATE**（数值/状态/交互错误但结构在）、**MINOR**（像素级偏差/hover/字距）。完成判定 = 矩阵全绿（无 CRITICAL/MODERATE/MINOR）**或**仅剩经人确认的 accepted-minor。MINOR 不算绿。
- **为什么**：逐像素完美不可达且拖入无限打磨；但"容忍 MINOR"必须由人确认，不能由实现者自行降级。
- **例子**：矩阵剩 2 条 MINOR（某图标偏 1px、某字距差 0.5px）→ 列出容忍清单交人确认 → 标 accepted-minor → 判定完成。

### 2.11 输入质量分数

- **是什么**：提取设计稿时同步产出一个 0–1 的质量分，由确定性扣分项算出（只能拿到截图 −若干、每个未解析的 token −0.02、缺状态标注 −若干……），分数与提取结果一起流转。
- **为什么**：垃圾进垃圾出（GIGO）不可避免，但可以**不静默**。低分输入直接进编码，产出的缺陷会在矩阵里伪装成"已完成"。分数 <0.8 或标了 LOW_FIDELITY → 进人工确认点，人选择：修输入 / 手动补映射 / 明确接受低质量。
- **例子**："本次提取质量分 0.62（扣分：仅截图无源码、3 个 token 未解析），建议先由人确认色板映射再继续。"

## 第三部分：流程篇——推荐的设计与前端开发流程（通用版）

**这节讲什么：一条有稿/无稿通用的总链路，每步做什么、产出什么、谁确认。任何团队可以照搬，不需要任何特定工具。**

### 3.1 总链路（九步）

```
定方向 → 冻结设计源 → 提取规格 → 对照清单 → 拆任务 → 写代码（带边界）→ 逐块截图验证 → 矩阵验收 → 沉淀回写
```

| 步骤 | 做什么 | 产出 | 谁负责/确认 |
|---|---|---|---|
| 1 定方向 | 判定任务类型（有稿/无稿）、谁确认视觉、登记验收对象卡（意图级） | 验收对象卡意图 | 人（设计 owner） |
| 2 冻结设计源 | 快照设计源路径 + 内容哈希 + viewport | design_revision | 执行者 |
| 3 提取规格 | 把设计稿数字化：token 表、组件结构树、状态矩阵、布局网格、缺失项标 `[PENDING]` | 提取规格 + 输入质量分（0–1） | 执行者（机器辅助） |
| 4 对照清单 | 生成 parity 矩阵，实现侧全 missing 初始化全红 | 全红对照矩阵 | 执行者 |
| 5 拆任务 | 按组件/区域拆，任务卡带派发规格五要素（见 3.6） | 任务卡 | 计划者 |
| 6 写代码 | CSS 清场 → 静态拼版 → 状态交互 → 接真实数据；只许用登记的 token/组件 | 代码 + 例外记录 | 实现者 |
| 7 逐块截图验证 | 每完成一个大区域：截图 + 感知清单 + 与参考比对 | 视觉证据（带 commit/URL/树 hash） | 独立执行者 |
| 8 矩阵验收 | parity 矩阵逐项核证据 → 分级缺陷 → 收敛判定 | 全绿或 accepted-minor 清单 | 独立裁决者 + 人 |
| 9 沉淀回写 | 新 pattern/token 经 owner 确认后即时回写规范文件；失败按三层归档 | 规范新 revision + 失败档案 | owner 确认 |

顺序要点：**先结构后细节**——骨架/主网格对了再做组件，组件对了再做 fixture 和真实数据，最后抠视觉细节。禁止在错误结构上微调。

**第 9 步的失败三层归档**值得单说：每次返工/缺陷修复后，把根因归入三层之一——①**规则层**（缺一条"什么是对的"的规则 → 补进规则清单，永不再犯）；②**工具层**（提取/截图/比对工具缺陷 → 升级工具）；③**人际层**（必须人类判断的品味/取舍 → 显式留给人）。配套一个"观察 → 验证 → 晋升"的沉淀管道：原始观察记进工作日志，验证为普适规律后晋升为规则，硬编码进检查清单——规则复利，同类缺陷逐轮归零。

### 3.2 有稿模式详流程（reference-reproduction）

1. **冻结设计源**（路径+hash+viewport 写进验收对象卡）。
2. **提取**：双源交叉——读设计稿源码拿"意图"（类名、结构），读浏览器 computed style 拿"真实值"。冲突以 computed 为准并记录。输出：token 表（含与项目 Design.md 的映射/冲突记录）、组件规格（结构树+每元素样式+交互态+数据态）、页面布局（主网格/栏宽/间距节奏）、缺失项、输入质量分。
3. **低保真/低分熔断**：输入质量分 <0.8 或只有截图无源码（标 LOW_FIDELITY）→ 暂停，把提取结果和不确定项呈交人确认/补充后才继续。不静默 GIGO。
4. **建矩阵**：parity 矩阵全红初始化。
5. **派发**：每个任务卡的规格必须引用矩阵相关行 + 满足五要素。
6. **实现**：三条铁律 + CSS 清场 + 只用登记 token。
7. **逐块验证**：每个大区域截图、答感知清单、与参考图比对（9 维：layout/typography/colors/spacing/shadows/borders/radius/icons/states）。
8. **验收**：矩阵全绿 + MINOR 容忍清单经人确认。

**设计稿有缺陷时怎么办**：**照抄 + 缺陷清单交设计 owner 裁决**。忠实复现优先，同时产出专业缺陷清单（对比度不达标、a11y 缺失、动效过度），owner 决定是否偏离。批准偏离记 approved-deviation（见 2.9）。owner 未指定时缺省 = 用户/产品负责人本人，流程不悬空。

### 3.3 无稿模式详流程（original-design）

无稿任务不许直接进入编码。六段式走完后并入有稿流程：

1. **设计方向六段式**：Scope（做什么面）/ Visual target（视觉目标与参考）/ Implementation（技术形态）/ Patterns（用哪些模式）/ Base Tokens（基础 token）/ Guardrails（护栏与禁令）。
2. **规范收敛**：方向对照项目的 Design.md/Experience.md 基线收拢，不许发明与项目冲突的第二套 token。
3. **原型渲染**：出真实效果图（用真实生产路由 + 真实 fixture，不用一次性玩具页面）。
4. **人确认**：效果图必须经设计 owner 确认——这是无稿模式的强制确认点。
5. **冻结为自建设计稿**：确认后的原型连同其 token/结构冻结，绑定 path+SHA。
6. **并入有稿流程**：从"提取规格"开始，与有稿任务完全同链。

### 3.4 低保真输入怎么办

输入是截图、手绘稿、口头描述时，全部走**人工确认点**：把能提取的提取出来，把不确定项列成清单（"标题字号无法确定，候选 18/20px"），人逐项确认或补充后才进入编码。低质量输入直接进编码 = 垃圾进垃圾出，且垃圾会在矩阵里伪装成完成。

### 3.5 人的角色变化

旧模式里人是"人肉 diff 工具"——每轮逐像素找茬。新模式里人只剩**两个确认点**：

1. **设计方向确认**（无稿任务的效果图确认；有稿任务没有此步）；
2. **最终验收确认**（矩阵全绿后确认 MINOR 容忍清单）。

外加裁决类交互：规范层冲突、approved-deviation、低保真确认——这些是"人给判断"，不是"人当 QA"。目标：人工介入从 20+ 小时降到 ≤2 小时，验收确认从 5 次降到 1 次。

### 3.6 CSS 清场纪律、共享原语单一来源、派发规格五要素

**CSS 清场**：动手写新样式前，先统计目标区域的历史样式债务：同选择器多定义、`!important`、无人使用的死样式块。先清场再写码——否则"改了没效果"会逼你再写一条更靠后的规则，债上加债。真实案例：1056 行 CSS、417 个历史块。

**共享原语单一来源**：同一概念的组件（如指标卡 Metric）全项目只能有一个实现，各页复用，禁止每页各造一个。组件要共享必须有两个以上已确认的真实消费者才提取；删除组件必须有无消费者证据。

**派发规格五要素**（缺任何一项不许派发，这是全流程唯一的硬阻断）：

| 要素 | 说明 | 按模式适配 |
|---|---|---|
| 1 精确来源锚点 | 规格值从哪来 | 源码模式=文件路径+行号；Figma 模式=节点 id+属性表；截图模式=区域坐标+测量值 |
| 2 精确验收值 | 颜色/字号/间距的准确值 | 三种模式相同 |
| 3 目标文件隔离 | 改哪些文件、不碰哪些 | 三种模式相同 |
| 4 三条铁律声明 | 稿有结构不许缺/稿无结构不许加/数值不许近似 | 三种模式相同 |
| 5 全状态覆盖清单 | 该组件的所有状态（default/hover/focus/active/disabled/loading/error/empty）逐一列出 | 三种模式相同 |

### 3.7 环境守护与消歧协议

两个便宜但救命的纪律，来自真实返工教训：

- **环境守护**：任务开始时登记所有依赖服务（端口/分支/数据依赖）写进验收对象卡；每轮验证前先做连通性探针，探针失败标 unavailable 继续报，不伪造通过。真实案例里 dev server/API 挂过两次、运行态数据丢失——"服务是活的"本身是一条要验的事实。
- **消歧协议**：位置类反馈（"右上角不对"）不许直接动手，先枚举候选指认——列出 2–3 个候选位置让人选，10 秒确认可省一整轮返工。真实案例里"右上角"被修错目标，整整浪费一轮。
- **证据新鲜度**：截图/比对报告带 git commit + 服务 URL + 页面树 hash；树 hash 与当前页面不匹配的旧证据一律拒绝——机械检查，不是荣誉系统。

## 第四部分：质量篇——工程质量四维度

**这节讲什么：视觉对齐之外，代码本身也要过硬。组件化/统一性/可维护性/性能四个维度，每个维度按"规范写在哪 / 执行怎么查 / 验收怎么验"三列展开。总原则：规范层（项目 Design.md/Experience.md）是法律，执行层是三道接缝（计划/编码/验收），证据层记录事实；违规记事实交 owner 裁决，不阻断推进。**

### 4.1 组件化

核心立场：**组合优于配置**。复杂组件拆成共享 context 的复合组件，状态提升到 provider 按 `state/actions/meta` 三段式接口下发，变体做成显式组件而非布尔开关。

| 三列 | 内容 |
|---|---|
| 规范写在哪 | Design.md「组件 API」章节：组合模式约定、props/events 契约、共享组件提取标准（双消费者规则）、爆炸半径纪律（一个组件 >5 个消费者即触发专项审查） |
| 执行怎么查 | 计划阶段的组件质量图（每个组件记：动作=复用/修改/扩状态/新建/提取共享/删除、真实消费者、状态 owner、ViewModel 类型）；编码交接时逐条核对；静态检查：重复组件、布尔 prop 检测 |
| 验收怎么验 | 验收阶段核对真实消费者（防止"为了复用而复用"的无消费者抽象）；删除需无消费者证据；diff 级审查读删除侧找回归 |

**7 条反模式信号**（出现即查）：

1. 组件体内布尔 prop 驱动的三元链（`{isA ? … : isB ? … : null}`）；
2. 单体组件同时收 `renderHeader/renderFooter` 和 `showX/showY` 布尔组；
3. 用 `useEffect` 把子组件状态每次变化向上同步；
4. 提交时从 ref 读状态；
5. UI 组件直接调具体状态 hook（而非消费 context 接口）；
6. 调用点出现 `<Composer isThread isEditing={false} showAttachments/>` 式读不出渲染结果的调用；
7. API 签名含 `renderX?: () => ReactNode` 组（children 优先，仅"父向子回传数据"时才用 render props）。

### 4.2 统一性

核心立场：**token 三层体系**——primitive（按色相命名，`--blue-500`，永不进组件）→ semantic（按角色命名，`--color-accent-solid`，组件只引用这层）→ 组件级 token（仅有意偏离时才加）。命名语法唯一形状：`--color-{role}-{variant}-{state}`。

| 三列 | 内容 |
|---|---|
| 规范写在哪 | Design.md「token」+「治理规则」章节：token 三层、命名规范（前景用 `text` 禁用 fg/ink、背景用 `bg`、边缘用 `border`、品牌用 `accent`）、一层 token 权威/一处样式 owner、组件复用强制 |
| 执行怎么查 | 编码只许用登记 token（新 token 登记 owner/消费者/删除条件）；stylelint 类规则包查：同选择器多定义、`!important`、global override、CSS 泄漏；组件里出现裸 primitive 色（`bg-brand-500`）即标记 |
| 验收怎么验 | parity 矩阵 token 列核对；组件复用审查（同概念组件禁止每页各造）；规范文件 hash 校验保证没人绕过规范 |

### 4.3 可维护性

核心立场：**每个组件有 owner，每个文件有删除条件**。

| 三列 | 内容 |
|---|---|
| 规范写在哪 | Design.md「治理规则」章节：组件 owner 制、复杂度上限、死代码义务（删除时附无消费者证据）、文件/目录组织规范、文档与代码同步规则 |
| 执行怎么查 | 静态检查：死代码、同选择器多定义、无 consumer 的抽象；编码阶段 diff 扫描含"共享接口/兼容边界"核对；审查五问之一："是否新增重复控制面、无 consumer 的抽象或不必要的兼容分支" |
| 验收怎么验 | 审查发现分级处置（fixed/accepted_risk/needs_human）；三态分类让"本次变更引入的债"与"历史债"分离——Pre-existing 不背锅，Introduced 必须处置 |

### 4.4 性能

核心立场：**先测后改**——没有测量就没有优化；预算写进规范，超标记事实交 owner 裁决。

| 三列 | 内容 |
|---|---|
| 规范写在哪 | Design.md「性能预算」章节：预算数值表（bundle 上限/首屏 LCP < 2.5s/交互 INP < 200ms/CLS < 0.1/动效 60fps=16ms 每帧）+ 超标的例外记录流程 |
| 执行怎么查 | React/Next 栈对照 70 条性能规则（8 大类，见第五部分 vercel-react-best-practices 节）逐条套用；动效只动 transform/opacity；运行时取证（长列表滚动帧率、hydration 闪烁）走浏览器 QA |
| 验收怎么验 | 预算核对：实测值 vs 预算值，超标记事实；**先测后改**：优化前后各取一次证（如 offscreenRunningCount=0），无对比取证不算优化完成 |

### 4.5 四维度速查总表

| 维度 | 一句话纪律 | 最常犯的反模式 |
|---|---|---|
| 组件化 | 组合优于配置，props 契约显式 | 布尔 prop 爆炸、无消费者抽象 |
| 统一性 | 组件只引用 semantic token | 组件里写死 hex、每页各造 Metric |
| 可维护性 | 有 owner、有删除条件、死代码即删 | 1056 行 CSS 417 历史块 |
| 性能 | 预算先行、先测后改 | 未测量就 memo、`transition: all` |

### 5.1 web-design-guidelines

- **它是什么**：Vercel 维护的 Web 界面工程规则集，103 条规则 17 大类 + 14 条反模式必报清单。完整规则见技能原文（上游 `vercel-labs/web-interface-guidelines`）。
- **核心思想**：把"好界面"拆成机器可逐条检查的规则，审查输出 `file:line` 极简结论，通过的文件输出 `✓ pass`，无前言无解释。
- **精选规则**：
  1. 交互元素禁止 `<div onClick>`：动作用 `<button>`，导航用 `<a>/<Link>`；
  2. Icon-only 按钮必须有 `aria-label`；装饰图标 `aria-hidden="true"`；
  3. 禁止无替代焦点样式的 `outline-none`；用 `:focus-visible` 而非 `:focus`；
  4. 禁止 `transition: all`——必须显式列出属性；
  5. 只动画 `transform`/`opacity`；动画必须可被用户输入打断；
  6. 数字列/数字比较用 `font-variant-numeric: tabular-nums`；
  7. flex 子项必须 `min-w-0` 才能截断文本；
  8. `<img>` 必须显式 `width`/`height`（防 CLS）；折叠线下图片 `loading="lazy"`；
  9. 大列表（>50 项）必须虚拟化或 `content-visibility: auto`；
  10. URL 反映状态：过滤器/标签页/分页进 query params，所有有状态 UI 可深链；
  11. 破坏性操作须确认弹窗或撤销窗口，绝不立即执行；
  12. 空字符串/空数组不得渲染出破版 UI；用户生成内容预演极短/正常/超长三种输入；
  13. 深色主题 `<html>` 加 `color-scheme: dark`；`<meta name="theme-color">` 与页面背景一致；
  14. 日期用 `Intl.DateTimeFormat`、数字用 `Intl.NumberFormat`，不硬编码格式；
  15. 错误信息必须含修复方法/下一步，不只陈述问题；按钮文案具体（"Save API Key" 而非 "Continue"）。
- **怎么用**：编码完成后、验收前对改动文件逐条对照；反模式 14 条可直接 lint 化进 CI。接入流程的"逐块验证"和"矩阵验收"环节。
- **注意事项**：上游是活体 main 分支，**必须固化快照入库**（记录抓取日期），不许运行时拉外网；与 better-accessibility 有约 20 条重叠（焦点/表单/ARIA），合并时须去重定单一来源，避免同一违规双报。

### 5.2 impeccable

- **它是什么**：一个"设计总监"人格技能（v4.1.1，MIT），21 条命令路由 + craft-floor 质量地板（Verify 9 条 + Refuse 20 条）+ 评审编排（双独立评估 + Nielsen 打分 + P0–P3 分级）+ 有界验证法。约 210 条可执行规则。完整规则见技能 `reference/` 33 个文件。
- **核心思想**：品质来自"质量地板 + 独立评审 + 有界收敛"三件套；开放式自 QA 被明确定性为烧钱行为——"两轮为上限，停"。
- **精选规则**：
  1. 对比度：正文 ≥ 4.5:1，大文本 ≥ 3:1；彩色表面上的次级文本从该色相配，**永不用灰**；
  2. 正文行长 65–75ch；display 字号上限 6rem；字距下限 -0.04em（-0.02~-0.03em 通常更好）；
  3. 卡片圆角 12–16px；elevation 只声明一次：border 或 shadow 二选一，1px border + 宽软阴影 = "ghost card"；
  4. **禁卡片套卡片**；禁 kicker/eyebrow 小标签（绝对禁令）；禁 section 编号（01/02/03）；禁渐变文字；禁 emoji 冒充图标；禁 monospace 当"技术感"戏服；
  5. **有界验证法**：完整 build → 一轮批量截图（desktop+mobile 同轮）→ 一批修完 → 至多再一轮确认 → 停；
  6. 评审必须双独立上下文：Assessment A（设计评审）与 B（检测器证据）隔离并行，A 先完成防锚定；降级运行必须打横幅 `⚠️ DEGRADED`，沉默降级 = 失败评审；
  7. Nielsen 10 启发式各 0–4 分，总分 /40 归一；分带 90%+ Excellent / 70%+ Good / 50%+ Acceptable；**多数真实界面 20–32/40**，诚实打分；
  8. 问题严重度 P0–P3；P1 判定口诀："用户会因此联系客服吗？是则至少 P1"；
  9. 认知负荷：工作记忆 ≤4 项；导航 ≤5 个顶层项；每决策点 ≤4 个可见选项；分组每组 ≤4 项；
  10. 五个 persona 走查：效率专家（主任务 <60 秒）/新手（5 秒内第一动作显然）/a11y 依赖（纯键盘、200% 缩放）/压力测试（0/1000 项、超长文本）/分心移动用户（触控 ≥44×44pt、3G 可用）；
  11. Core Web Vitals：LCP < 2.5s、INP < 200ms、CLS < 0.1；60fps = 16ms/帧；
  12. 动效时长表：即时反馈 100–150ms、常规状态 150–300ms、布局/overlay 300–500ms、入场 500–800ms；出场快于入场；
  13. finish-reviewer 四态裁决：recapture/rebuild/fix/ship，reviewer 必须新起上下文；
  14. 终检清单：所有 viewport、全部状态、console 错误、与规范一致；**干净的扫描不替代视觉判断**。
- **怎么用**：craft-floor 清单接入"逐块验证"环节；有界验证法作为全流程收敛协议；评审编排作为"矩阵验收"环节的独立裁决模板。
- **注意事项**：技能体量巨大（约 90 个脚本），**只抽文档层规则，不搬脚本层**（live 模式强耦合特定宿主）；其裁决词表（recapture/rebuild/fix/ship）与其他技能的（Block/Needs changes/Approve）是两套，团队必须统一选一套。

### 5.3 better-ui

- **它是什么**：16 条带精确数值的"设计工程处方" + 一套三严重度评审输出格式（Jakub Krehel，MIT）。24 条规则。完整规则见技能 SKILL.md + 7 个主题文件。
- **核心思想**："复现后感觉不像"的高频根因几乎都是细节数值（圆角不同心、阴影/边框分工错、光学没对齐），给精确数值处方替代感觉。
- **精选规则**：
  1. **同心圆角**：`outerRadius = innerRadius + padding`（card 20px + padding 8px → inner 12px）；padding > 24px 视为独立表面不强制同心；
  2. **光学对齐 > 几何对齐**：图标按钮 icon 侧 padding = 文本侧 −2px；播放三角 `translateX(2px)`；
  3. **阴影做高度、边框做结构**：浅色三层阴影配方 `0 0 0 1px oklch(0 0 0/0.06), 0 1px 2px -1px oklch(0 0 0/0.06), 0 2px 4px 0 oklch(0 0 0/0.04)`，hover 提到 0.08/0.08/0.06；深色单层白环 `0 0 0 1px oklch(1 0 0/0.08)`；
  4. **可中断动画**：交互态变化一律 CSS transitions；keyframes 只给跑一次的分阶段序列；
  5. 入场 stagger 块间 ~100ms、词间 ~80ms，组合 `opacity + blur(4px→0) + translateY(12px→0)`；**高频交互（行 hover/击键/tab）禁止 stagger**；
  6. 退场短于入场（150ms vs 300ms），小固定位移 `translateY(-12px)`；
  7. 上下文图标动画精确值：`scale 0.25→1`（禁用 0.5/0.6）、`blur(4px)→0`、spring `bounce: 0` 永远；
  8. 图片描边必须纯黑/纯白 10% 透明度（`outline-black/10 dark:outline-white/10`），禁用 slate-900 等近色——带色描边会拾取底衬色读作"脏"；
  9. **按压缩放永远 `scale(0.96)`**，低于 0.95 即夸张，用 transition 保持可中断；
  10. 主题切换压制过渡：注入 `*,*::before,*::after{transition:none!important}` → 强制 reflow → 双层 rAF 后移除；
  11. 只过渡变化的属性；`will-change` 只给 transform/opacity/filter，**只在观察到首帧卡顿才加**；
  12. 图标描边匹配字重（24px 网格）：Regular 400 → 1.5px；500–600 → 2px；Bold 700 → 2.5px；inline 图标尺寸 = 文本 cap height，通常 1em–1.25em；
  13. 单 SVG `currentColor` 按态变色，禁每态单独资产；outline 变体=默认态，fill 变体=选中态；
  14. 高频交互不做自定义动画，最多 ≤150ms 的 opacity/background 过渡；动效永不是唯一反馈通道；
  15. **评审方法**：浏览器 Animations 面板 10% 速度回放动效——"10% 速度下感觉不对的，就是全速下微妙出错的地方"；走遍 hover/focus/active/loading/empty 每态。
- **怎么用**：数值处方接入编码环节作为实现约束与验收断言阈值；10% 慢放法接入"逐块验证"环节。多数规则可机器检查（同心圆角、transition-all 禁令）。
- **注意事项**：纯 markdown 零依赖，移植成本最低；Tailwind 语法映射随版本变化需复核；与排版/a11y/布局三个姐妹技能有边界声明，别重复造规则。

### 5.4 better-accessibility

- **它是什么**：14 条 a11y 原则 + 13 条错误对照 + 6 份专题细则，共 112 条可执行项（MIT）。完整规则见技能 6 个 reference 文件——**主体（98 条细则）在 reference 里，不在 SKILL.md**。
- **核心思想**：先键盘用户、再读屏用户走查；原生元素优先（No ARIA > bad ARIA）；每个规则落到具体阈值。
- **精选规则**：
  1. 焦点环至少 2px 实线周长，须对**所有相邻色**逐一验证（含 hover/selected 态与 forced-colors 模式）；首选只加 `outline-offset: 2px` 保留浏览器环；
  2. 命中区：WCAG 2.5.8 AA 硬地板 24×24px；触屏主控件 44×44px、桌面 40×40px；报小控件前先查五条例外（spacing/equivalent-control/inline/user-agent/essential）；
  3. 伪元素扩命中区挂 `<label>/<button>` 不挂 `<input>`；两交互元素命中区**永不重叠**；
  4. `tabindex` 只用 0 和 -1，正值永不；复合控件用 roving tabindex（方向键移动，整组一个 Tab 停点）；
  5. 模态焦点陷阱现代做法：背景 `inert` + 打开移焦入内 + 关闭焦点回触发器；优先原生 `<dialog>` + `showModal()`；
  6. 表单错误四件套：`aria-invalid="true"` + `aria-describedby` 指向内联错误 + 内联错误带图标或文本（绝不只有红边框）+ 提交后聚焦第一个无效字段；
  7. 提交按钮请求发起前保持可用；请求中禁用 + spinner 但**保留原 label**（裸 spinner 让辅助技术不知道谁忙）；
  8. 播报决策表：焦点会移过去→不播报；绑控件→`aria-describedby`；非紧急不绑控件→`role="status"`（polite）；紧急不绑控件→`role="alert"`；**assertive 滥用是最常见错误**；
  9. 重复 polite 播报须先渲染稳定空区域再改文本；唯一动作路径绝不只放在自动消失的 toast 里（5 秒为计时下限）；
  10. 200% 缩放可用、320px 宽度重排无横向滚动；文本容器用 `min-height` 不用固定 `height`；断点优先 rem；
  11. Label in Name：可见 label 必须含在可访问名称内（显示 "Send" 的按钮不能 `aria-label="Submit message"`）；
  12. 原生 `disabled` 与 `aria-disabled` 永不同时设；`aria-disabled` 须在代码里真阻断指针/键盘/表单行为并显式样式化；
  13. 动效 opt-in：包在 `@media (prefers-reduced-motion: no-preference)` 里；存量兜底用 `0.01ms` 而非 `none`（保证 animationend 仍触发）；
  14. 功能图 alt 描述动作（`alt="Search"` 而非 `alt="magnifying glass"`）；装饰图 `alt=""`；缺 alt 属性比空 alt 更糟；
  15. hover 样式包 `@media (hover: hover)`——触屏 tap 后 :hover 会粘住。
- **怎么用**：14 原则作组件验收 checklist 骨架；运行时验证项（键盘走查、模态陷阱、200% 缩放）接入"逐块验证"环节的浏览器 QA 场景；任何自定义组件必须声明四项：APG 模式/tabindex 策略/名称来源/disabled 策略。
- **注意事项**：与 web-design-guidelines 约 20 条重叠，建议以本技能为 a11y 单一来源；WCAG/APG 标准本身在演进（2.5.8 较新），需定期人工对齐。

### 5.5 interface-review

- **它是什么**：把 UI 评审从"看一个屏幕"重构为"审一个变更（diff）"的操作规程，约 22 条规则含完整 git 命令集（MIT）。
- **核心思想**：变更文件是证据不是评审主体——其**爆炸半径**（渲染它的表面集合）才是；回归在变更后状态中不可见，必须读 diff 的删除侧。
- **精选规则**：
  1. 范围解析：merge-base 优先于工作区；分支评审用三点 diff（`BASE...HEAD`）；commit 数与未提交文件数分开报告；
  2. 无变更可审时**停下问**，禁止自行退回 `HEAD~1..HEAD`（最后一个 commit 常是别人的工作）；
  3. 爆炸半径扩展：默认一跳（直接 importer），design token/theme 值/共享原语扩两跳，**最多审 5 个消费者并声明未扩展数**；
  4. 消费者排序可复现：路由/布局入口优先 → 按 importer 计数 → 平手按邻近度；排序在某点后是任意的要明说；
  5. 读被删除的行：每个 hunk 的 `-` 侧对照删除信号路由表（`aria-*` 被删 → a11y owner；逻辑属性换回 left/right → 布局 owner；色 token 换字面量 → 颜色 owner）；
  6. 删除信号是线索不是发现：有等价替换（`aria-label`→`aria-labelledby` 指向可见文本）不算回归；
  7. 每个发现打三态：**Introduced**（本变更创造）/ **Regression**（削弱了原本正确的东西）/ **Pre-existing**（触及但非本变更造成）——按 diff 触及的行判，不按所在文件；
  8. 用声明的意图约束变更：读 PR 标题/issue/commit message，检查"新 variant 是否铺满全部状态""新字符串是否入翻译目录""兄弟表面是否同步"——不完整变更表面评审看不到；
  9. 永不改工作树：PR ref 只 fetch 不 checkout；渲染验证默认标 Not verified，需要时用隔离 worktree 用完删除；
  10. 排除清单并点名：lockfile/快照/生成物/vendor/二进制——但字体文件增换与组件新增图片**留在范围内**；
  11. 重命名当移动审，不当 delete+add（`--find-renames=40%`）；
  12. 编排者不可用时停下点名，不发明严重度尺度和裁决。
- **怎么用**：接入验收环节的 diff 级审查；爆炸半径规则回答"改了一个组件该 QA 哪些页面"；三态分类进缺陷登记表。
- **注意事项**：纯规则 + git 命令，零脚本依赖；删除信号路由表中的"owner 技能"是外部引用，团队使用时须重定向到自己的职责分工。

### 5.6 vercel-react-best-practices

- **它是什么**：Vercel Engineering 官方 React/Next.js 性能规则集，70 条规则 8 大类，每条带 impact 分级（CRITICAL→LOW）+ 正误代码对照（MIT）。完整规则见上游 `vercel-labs/agent-skills` 的 `skills/react-best-practices`（70 个规则文件，编译版约 3810 行）。
- **核心思想**：瀑布流是性能第一杀手，包体积第二——CRITICAL 级 10 条集中在这两类；规则按影响力排序，先修收益最大的。
- **精选规则**：
  1. 无依赖的异步操作 `Promise.all()` 并发（CRITICAL，2–10× 收益）；
  2. 避开 barrel 文件直接深路径导入（流行图标库上万个 re-export，仅导入就 200–800ms；Next.js 13.5+ 用 `optimizePackageImports`）；
  3. 首屏不需要的大组件（如 Monaco ~300KB）`next/dynamic` 懒加载；
  4. Server Action 是公开端点，必须在每个 action **内部**校验认证授权（CRITICAL 安全）；
  5. RSC→client 边界只传客户端实际用的字段（50 字段传 1 个）；对象变换放 client 做防重复序列化；
  6. RSC/SSR 禁用可变模块级变量传请求数据（并发渲染会跨请求污染）；
  7. **禁止在组件内定义组件**——每次渲染产生新组件类型导致整体 remount，状态/DOM 全毁（HIGH）；
  8. 能从 props/state 算出的值不进 state、不用 effect——渲染期直接派生；prop 变化需重置时用 key；
  9. 高频变化且不需触发渲染的值存 `useRef` 不存 `useState`；
  10. 输入触发昂贵渲染用 `useDeferredValue`；频繁非紧急更新包 `startTransition`；
  11. 由特定用户动作触发的副作用放事件处理器，不建模成 state+effect；
  12. 长列表项 `content-visibility: auto`——1000 条消息跳过约 990 条的 layout/paint，首渲染快 10×；
  13. script 标签必须带 `defer` 或 `async`，否则阻塞 HTML 解析；
  14. 热路径先比 length 再做昂贵数组比较；同键多次 `.find()` 改建一次 Map（示例 1M ops → 2K ops）；
  15. touch/wheel 监听加 `{ passive: true }` 让滚动立即发生；
  16. 静态 JSX（尤其大型静态 SVG）提取到组件外，避免每次渲染重建；条件可能为 0/NaN 时用三元 `? :` 而非 `&&`（防止把 "0" 渲染上屏）；
  17. 订阅派生布尔值而非连续原始值（"是否小于断点"而非"当前像素宽度"），重渲染频率从每像素一次降到布尔翻转一次；
  18. 频繁显隐的昂贵组件用 `<Activity>` 保留 state/DOM；依赖客户端存储的内容在 hydration 前用同步内联脚本改 DOM，防闪烁。
- **怎么用**：React/Next 项目编码时逐条套用（生成即合规比事后重构便宜）；diff 触及相关文件时触发对应类别核对（新增 `useEffect` → 查派生态/事件化/初始化类规则）；按 CRITICAL/HIGH 优先引用。接入编码与验收两个环节。
- **注意事项**：非 Next.js 栈约 15–20 条不适用，按栈标注适用范围；**完整保留、按需索引**——frontmatter 的 impact 分级本身就是筛选器，物理裁剪会制造"第二份被裁剪的真相"；固定上游 commit，禁止从 main 自动更新（React Compiler 普及后 memo 类多条会降级，需人工对版）。

### 5.7 vercel-composition-patterns

- **它是什么**：Vercel 官方"组合优于配置"组件方法论，8 条模式 + 30 条子规则（含 7 条反模式判定信号），每条带 Incorrect/Correct 代码示例（MIT，明示"为 AI agent 编写"）。
- **核心思想**：布尔 prop 使状态数翻倍并产生不可能状态；复合组件 + provider 三段式接口（state/actions/meta）让"换 provider 不换 UI"成立。
- **精选规则**（8 模式全列，各带关键子规则）：
  1. 禁布尔 prop 泛滥（CRITICAL）：每个变体显式组合部件，看 JSX 即知结构；
  2. 复合组件 + 共享 context：`createContext` + Provider + 部件族，对象聚合导出 `const Composer = { Provider, Frame, Input, Submit }`；
  3. 状态提升到 Provider：需要共享状态的组件不必视觉嵌套，只要在同一个 provider 内；
  4. context 三段式泛型接口 `state + actions + meta`：UI 只消费接口不感知实现，`useState` 实现与全局同步实现可互换、UI 零改动；
  5. 状态实现与 UI 解耦：provider 是唯一知道状态如何管理的地方；UI 组件纯 JSX 组合；
  6. 显式变体组件：`ThreadComposer`/`EditMessageComposer` 各自 = 专属 Provider + 共享部件 + 独有部件，消灭不可能状态；
  7. children 优先于 render props：组合静态结构用 children；**仅当父向子回传数据时**用 render props（`<List renderItem={({item}) => …}/>`）；
  8. React 19：`ref` 是普通 prop 禁用 `forwardRef`；用 `use()` 替代 `useContext()`（可条件调用）。
- **怎么用**：7 条反模式信号（见 4.1 节）写成检查器接入编码与验收；生成侧把"聚合导出骨架 + 三段式接口"作为新组件的默认生成模板；测试侧利用"换 provider 不换 UI"——UI 组件用本地 provider 测，集成用真实 provider 测。
- **注意事项**：规则 8 仅 React 19+，老版本整段禁用；技能元数据的 impact 分级内部不一致（索引表与规则文件冲突），采用时自定一份优先级表为准；rules/ 与编译版 AGENTS.md 二选一作单一来源。

### 5.8 animate

- **它是什么**：Emil Kowalski 动效哲学的施工技能：5 条铁律 + 7 步决策链 + 13 条 Never-Ship 自检表 + 14 个配方（MIT）。完整规则见技能 SKILL.md + RECIPES.md——**两个文件必须一起用，配方占一半实操价值**。
- **核心思想**：前两步决策（动不动、为何动）是闸门，可以合法地产出零行代码；所有曲线/时长/弹簧参数必须取自内置数值表，禁止凭感觉发明；够用即可的最便宜工具，一个 fade 不许装动效库。
- **精选规则**：
  1. **频率闸门**：100+ 次/天（快捷键、命令面板）→ 永不动画；每天几十次 → 近乎不可察觉或不动；偶尔（modal/toast）→ 标准动画；罕见/首次 → delight 预算只花在这里。键盘触发的动作一票否决；
  2. 目的六选一名不出就不建：Feedback / Spatial consistency / State indication / Preventing jarring change / Explanation（仅营销）/ Delight（仅罕见档）；
  3. 工具阶梯从上到下第一个够用就停：CSS transition → `@starting-style` → CSS animation（主线程外，负载下不掉帧）→ WAAPI → Motion；
  4. 只动 `transform` 和 `opacity`；`clip-path` 是特许第四属性；**禁止 `scale(0)`**，从 `scale(0.9–0.97) + opacity:0` 开始；
  5. 锚定 popover 的 `transform-origin` 设在触发点（`var(--transform-origin)`）；modal 豁免保持居中；
  6. 缓动决策：进出用 ease-out、屏上移动用 ease-in-out、hover 用 ease、恒定运动 linear；**UI 禁止 ease-in**；三条自定义曲线：`cubic-bezier(0.23,1,0.32,1)`（UI 强 ease-out）/ `cubic-bezier(0.77,0,0.175,1)`（强 ease-in-out）/ `cubic-bezier(0.32,0.72,0,1)`（iOS drawer）；
  7. 时长表：按压 100–160ms、tooltip 125–200ms、dropdown 150–250ms、modal/drawer 200–500ms；**UI 动画保持 300ms 以下**；
  8. 高频元素用 transition 不用 keyframes（transition 从当前值重定向，keyframes 从零重启）；
  9. **怎么进来就怎么出去**：底部滑入的 toast 从底部离开；用户做决定用非对称时长（按住 2s linear 蓄力，松手 200ms ease-out）；
  10. reduced-motion 与 hover 门控随动画一起交付：降级保留 opacity/color 去掉位移（更少更柔，不是零）；hover 动效必须 `@media (hover: hover) and (pointer: fine)`；
  11. Motion 中用完整 transform 字符串（`transform: "translateX(100px)"` 硬件加速；`x/y/scale` 简写负载下掉帧）；
  12. stagger 30–80ms 逐项递增，只给偶尔看到的列表，播放期间不得阻塞交互；
  13. 13 条 Never-Ship 即审查自动阻塞项（transition:all / scale(0) / ease-in / 超 300ms / 未门控 hover / 缺 reduced-motion…）；
  14. 交付附三行：闸门结果（拒绝过什么要明说）、配料清单（工具/属性/曲线/时长各一行）、需 feel-check 的点（2–5× 慢放、逐帧、真机、隔天再看）；
  15. 配方代表：dropdown/popover 用 `transform-origin: var(--transform-origin)` + opacity/transform 各 200ms ease-out，起止态 `opacity:0; scale(0.95)`——原点即触发器是全部意义；drawer 用 `translateY(100%)` + 500ms iOS 曲线；hold-to-confirm 用 `clip-path: inset()` 填充、按住 2s **linear**（进度不该有缓动）；
  16. 手势用弹簧不用时长：flick 即关（位移≥阈值或速度 >0.11 px/ms）；打断时速度带入下一段动画；四个细节——pointer capture、多指保护、越界阻尼、摩擦而非硬墙；
  17. 两态交叠怎么调都不对时加模糊缝：过渡中 `filter: blur(2px); opacity:0.7`（200ms ease），blur <20px（Safari 上重 blur 昂贵）。
- **怎么用**：设计稿/需求含动效时走决策链实现；复现任务中**设计稿没有的动效不许加**（频率闸门的逆向应用）；Never-Ship 表作为动效审查判据。接入编码与逐块验证环节。
- **注意事项**：部分规则是强意见（如某 toast 库用 400ms ease），定位为生成指导+审查参考，不做硬 gate；引用四个姊妹技能，独立使用时需裁剪交叉引用；`var(--transform-origin)` 是外部组件库约定，非该库项目需自建等价 token。

### 5.9 animation-vocabulary

- **它是什么**：一张 12 类 91 词条的动效术语反向查询表（"popover 打开时弹一下的那个" → Pop in），只命名、不设计不构建（MIT）。
- **核心思想**：模糊描述映射为精确术语，全队/全 agent 共用同一套动效名词，消除"弹一下""滑进来"各说各话；定义逐字引用，禁止转述。
- **精选词条**（每类 1–2 条代表，全表 91 条见技能原文）：
  1. Pop in：带轻微过冲出现，像弹入就位；
  2. Stagger：多元素逐项小延迟依次动画，形成级联；
  3. Origin-aware animation：元素从触发器长出（popover 从按钮长出而非自身中心）；
  4. Shared element transition：元素从一处移动并变换到另一处（缩略图展开成卡片）；
  5. View transition：浏览器在两个状态/页面间 morph，连接共享元素；
  6. Hold to confirm：按住按钮时进度逐渐填满；
  7. Rubber-banding：拖过边界时的阻力与回弹（iOS 过滚手感）；
  8. Ease-out：快起慢收，多数 UI 的默认；Ease-in 慢起快收，显拖沓应避免；
  9. Interruptible animation：可在半途平滑改向而非必须先播完；
  10. Perceptual duration：弹簧"感觉上"结束的时长（底层仍在微稳定）；
  11. Skeleton / Shimmer：加载时带流动光泽的占位；
  12. Tabular numbers：等宽数字，数值变化不位移，ticker/计时器必备；
  13. Jank / Dropped frame / Layout thrashing：把"卡"精确为可诊断的三个不同原因；
  14. Frequency of use 原则：动画被看到越频繁，就应越短越微妙。
- **怎么用**：设计评审与规格撰写时用标准术语记录动效意图（"此处为 Pop in + ease-out"而非"弹一下"）；差异单撰写时开具术语化条目（"稿为 Shared element transition，实现为 Crossfade"）。接入定方向与验收环节。
- **注意事项**：它是活体页面的快照，会漂移，固定版本登记；必须**全量 91 条**并入，裁剪会导致查询落到被删词条时"假阴性"；它不含可执行规则，不能当验收判据。

### 5.10 better-colors

- **它是什么**：色彩系统方法论：色板结构 + 色板生成 + token 命名 + 使用纪律 + 对比度实测，约 78 条规则（MIT）。完整规则见技能 7 个 reference 文件。
- **核心思想**：系统是 ramp 不是单色；组件只引用 semantic 层 token；对比度永远对实际渲染背景实测、**只报告不擅自改色**。
- **精选规则**：
  1. 系统只需三种 ramp：neutral ×1（承载界面 80–90%）、accent ×1、status ×0–4（只发产品真实渲染的）；
  2. 角色↔阶映射：页面背景 50/1、组件背景 100/3、组件 hover 200/4、边框 300/7、实心填充 500/9、高对比文字 900/12；**每阶必须有一个角色消费它，无角色的阶不生成**；
  3. 正确 ramp 的 6 条可检查属性：感知明度均匀（HSL 明度不是感知的）、色相端到端恒定、vividness 中段最高两端衰减、亮端阶更密、相邻阶必须可区分、两端不到纯黑纯白；
  4. 用色彩库计算不手算（culori/colorjs.io），ramp 插值在感知空间做（sRGB 插值产生浑浊中间阶）；
  5. 暗色模式不是亮色板机械反转：先换 semantic 角色映射，再手调三处——vividness 降一两阶、暗端拉开间距、每对前景/背景两个 appearance 重测；
  6. 主题切换机制三选一且全程一致（`prefers-color-scheme` / `.dark` class / `light-dark()`），混用会得到半主题界面；
  7. **一色一义**：色相 15° 以内视为同色；accent=可交互时，中性色渲染的可交互元素同样是误导；
  8. 每个视图恰好一个填充色主操作；颜色放背景而非标签（填充按钮隔屋子可读作主操作，accent 色文字读起来像链接）;
  9. token 命名唯一形状 `--color-{role}-{variant}-{state}`；每个概念选一个词（前景 `text`、背景 `bg`、边缘 `border`、品牌 `accent`）；`primary` 只保留"正文"一个含义；
  10. 渐变插值空间是观感不是正确性：`in oklab` 最佳默认；`in oklch` 绕色轮全程饱和（蓝→粉经过紫，可能是意外）；
  11. APCA 阈值（设计决策用）：正文最低 Lc 75 偏好 90；非正文最低 60；UI 组件最低 30；WCAG 2（法律合规用）：普通文本 AA 4.5:1、大文本 3:1——**双阈值并列，APCA 无法律地位**；
  12. 修对比度先动明度（对比度实际响应的通道）；中明度背景有封顶——约 75% 感知明度背景上纯黑字也只有约 Lc 60，正文需要接近极端的背景；
  13. 无 fallback 的 P3 色是 HIGH finding——sRGB 在前让每个显示都有东西，`@media (color-gamut: p3)` 覆盖增强；
  14. 审计既有色板五步：grep 全仓收字面量 → 按感知明度排序 → 合并近重复（**不取平均**，保留使用最多的）→ 分配角色 → 清点剩余；**先报告盘点再改任何东西**；
  15. 承重颜色验证文化含义：股票涨跌英文 locale 绿涨、中文 locale **红涨**——本地化用 per-locale token 不硬编码。
- **怎么用**：双层 token 架构 + 角色清单 + 命名语法直接作为 Design.md「色彩 token」章节模板；对比度检查接入逐块验证；审计五步法用于存量项目盘点。
- **注意事项**：映射表分 Tailwind/Radix 两套，按项目栈选；"只报告不改色"纪律需与团队授权流程对齐（谁有权改色）；色板生成程序是执行配方，进参考文档不进规范正文。

### 5.11 better-typography

- **它是什么**：排版方法论：角色化字阶 + 行高/行长/字距数值处方 + OpenType/渲染细节，约 90 条规则（MIT）。完整规则见技能 7 个 reference 文件。
- **核心思想**：好排版 = 克制。一套带语义命名的字阶，每阶绑定 size+line-height+weight 三合一的**角色决策**——一个角色一次决策而非三次。
- **精选规则**：
  1. 产品界面字阶起点表：Display 36px/1.1/600、Title 24px/1.2/600、Heading 18px/1.3/600、Body 16px/1.5/400、Caption 13px/1.4/400；
  2. 字体数量 rarely 超 3 个；配对求对比不求相似（serif 标题 + sans 正文；两个近乎相同的 sans 并排 = 错误感）；
  3. 细字重仅 display 用：**18px 以下保持 weight 400+**；Ultralight/Thin/Light 保留给 28px+；
  4. web 格式只发 `.woff2`；只加载实际用的 face；有 CSS 属性就用属性（`font-weight: 650`）不用 raw tag（`font-variation-settings` 在 fallback 渲染时静默失效）；
  5. **变化中的数值用 `tabular-nums`**——计时器/计数器/价格更新时布局不位移；
  6. 行高按角色：标题 ~1.1、正文 1.5–1.6，**优先无单位值**；任何折行 ≥3 行的文本至少 1.4（卡片描述 `line-height: 1.1` 是反例）;
  7. 行长上限：长文 60–75 字符/行（`max-w-[65ch]`）；
  8. 折行四属性：`text-wrap: balance`→标题、`text-wrap: pretty`→描述、`overflow-wrap: break-word`→长词/ID、`white-space: nowrap`→徽章；长文跳过 balance/pretty；
  9. 字号地板：长文正文 ~16px、输入框/菜单 ~14px、说明文字 13px、极少低于 12px；
  10. **iOS 输入缩放**：聚焦 <16px 的输入框会整页缩放；两个修复方案（移动端放大到 16px / 保持 16px 用 transform 缩小渲染）设计后果不同，**须问人选哪个，不默默自选**；
  11. 角色内强调 = 升一个字重档（400→500），不改字号；标题层级映射字阶降序（h1→2xl, h2→xl, h3→lg）；
  12. 文案自然大小写存储，展示用 `text-transform`——改展示永不需要改文案；
  13. 下划线取字体自身度量：`text-underline-position: from-font` + `text-decoration-thickness: from-font`；
  14. 文本默认保持可选中（含应用 chrome），`user-select: none` 仅用于确实干扰交互的拖拽表面；
  15. 字体平滑只在根布局设一次（`antialiased`），**永不按组件设**；
  16. review 方法：读页面而非扫代码——眯眼看层级、完整读一段、缩放视口抓真实内容下的坏折行。
- **怎么用**：角色化字阶表直接作 Design.md「排版 token」章节模板；数值处方进排版原则章节；iOS 两方案保留为人工确认点。接入定方向与验收环节。
- **注意事项**：数值锚点基于 16px 根字号，非 16px 项目需换算；智能标点表是英文中心，中文项目需本地化；**CJK 排版无覆盖**（行高需求、标点挤压等需自补）；`text-box` 属性 Firefox 未支持，当渐进增强。

### 5.12 better-layout

- **它是什么**：布局方法论：分组/对齐/间距/自适应，约 46 条规则（MIT）。数值处方三者中最少、结构原则最多，且自带"默认值限定"条款。完整规则见技能 3 个 reference 文件。
- **核心思想**：布局在文字被读到之前就传达结构——分组三工具按优先级：负空间 > 背景形状 > 分隔线（最后手段）；好布局必须经受缩放、翻译变长、RTL 镜像的压力。
- **精选规则**：
  1. **组间间距 ≥ 组内间距的 2 倍**（组内 8px → 组间 16px+），否则眼睛无法分辨组的边界；
  2. 分隔线保持安静：发丝宽度、低对比、**永不与大间距并用**（间距已经干了活）；
  3. 控件必须与内容可区分（双向）：静态元素给控件样式 = 收集死点击；控件无交互信号 = 不可见；
  4. 对齐到一小组共享边缘；每个游离边缘（图标偏 2px、padding 与邻居不同）读作噪点；
  5. 呼吸空间起点表（无既有密度体系时）：相邻有边框控件间 12px、无边框控件周围 24px 净空、无关控件组间 24px+；**保留既有可用密度，不专为匹配这些值扩大控件**；
  6. 逻辑属性替代表：`margin-left`→`margin-inline-start`、`text-align: left`→`start`、`left: 0`→`inset-inline-start: 0`（RTL 自动镜像）；物理属性只留给真指物理屏幕侧的东西；
  7. 行内顺序：标识性内容（名称/标题）在 leading，元数据和操作在 trailing（余额大字在前，账户号在后）;
  8. 入口不过载：首屏是目录不是全书；每视图一个主操作；次要操作超过两三个收进菜单；
  9. 渐进披露必须有可见 affordance：窥视滚动器下一项探出 16–32px、折叠区给 "Show 12 more results" 而非 "More"、截断文本给展开方式；
  10. 断点属于内容不属于设备目录：在布局真正停止适配处断，不因预设断 768px；**晚折叠**——保持展开结构直到真装不下；
  11. **组件级适配优先 container queries**：卡片适配它所在的列而非视口（`container-type: inline-size` + `@container`），组件才真正可搬运；
  12. 字符串膨胀四规则：不定固定宽（max-width+折行）、不定固定高（min-height 地板）、按钮由标签自定尺寸（永不 `width: 96px`）、发布前伪本地化测试（德语常比英语长 30%，预留 30–40%）；
  13. 内容出血、控件悬浮两层模型：背景/媒体延伸到视口边缘，文字和控件留在布局边距和安全区内；
  14. 关键操作永不放可被切断处（可调面板底边、固定高 modal 折叠线下、弹起键盘背后）；放带安全区 padding 的 sticky footer；
  15. 测试顺序：最小支持尺寸和最大尺寸先测（它们先坏），再测中间。
- **怎么用**：2× 分组规则 + 间距起点表 + 逻辑属性禁令进 Design.md「布局/响应式」章节；三个 CSS 配方（窥视滚动器/full-bleed grid/FAB 安全区）进编码参考文档；container queries 作为组件验收标准。
- **注意事项**：技能自带声明——**所有数值是"无既有体系界面"的起点，项目既有 token 权威优先**，别把 12/16/24px 写成普世硬标准；大量规则移动端中心（安全区/FAB/iOS 手势区），纯桌面产品部分规则适用性下降。

### 5.13 其余 112 个技能怎么处置

上面 12 个是精读过的 P0 核心。完整调研覆盖过一个 124 技能的开源仓库（Website-skills，P0/P1/P2 分级），处置方法是**四分类法**，任何团队建立自己的规则弹药库时都可照搬：

| 分类 | 数量 | 含义 | 例子 |
|---|---|---|---|
| ① 复制为独立资产 | 7 | 自含、零依赖、价值密度高，完整收编并固定上游 commit | web-design-guidelines（固化快照）、better-ui、animate |
| ② 概念并入现有资产 | 24 | 把其中的原则/数值提炼进自己的规范模板与检查清单，不整族搬运 | better-colors/typography/layout 的数值处方进设计规范模板 |
| ③ 辅助参考按需查阅 | 24 | 用得着才翻的参考资料（起步模板、3D、滚动叙事），不进默认加载链 | 暗色工作台皮肤模板、gsap、threejs |
| ④ 不引入 | 69 | 营销皮肤/装饰特效/平台错配/来源缺失，明确拒绝并记录理由 | 浅色营销皮肤族、WebGL 特效族、Apple 原生工具 |

四条分类逻辑（也是本手册第五部分的选品标准）：

1. **吸收模式，不吸收皮肤**——值钱的是决策链、数值表、检查清单这类"为什么"，不是某种视觉风格；
2. **数据密集后台对装饰特效默认零预算**——用户每天盯 8 小时的界面，任何纯装饰动效都是 GPU/注意力税；
3. **没有任何外部技能替代你自己的核心闭环**（提取/对照/视觉验收）——外部技能全是"规则弹药"，零替代关系；
4. **按需加载分级**——规则弹药进参考目录按需查阅，绝不一次全载（淹没上下文）；收编的每个技能登记来源 commit 与许可证。

## 第六部分：验证篇——怎么证明流程改造有效

**这节讲什么：流程改造不能靠感觉宣布成功。用对照实验设计给出可证伪的测量方法，以及一个"实证坑"案例说明基准怎么选。本节起出现具体落地语境（workflowhub 试点），方法本身通用。**

### 6.1 对照实验设计思路

核心做法：**同一份设计稿、同一个范围，改版前后各跑一遍，再加历史数据作第三参照**。

- **范围**：选 1–2 个页面（真实案例选的是 SimulationBoard + SimWorkbench 两页，与历史任务天然同源）；
- **B0（改版前基线）**：用现状流程实现一遍，全程记录六指标。**必须在改造开工前真跑**（约 0.5–1 天），不测"想象出来的现状"；
- **P1/P2（改版后）**：用新流程跑同一设计稿同一范围；P1 跑薄闭环（提取+对照+人工视觉确认），P2 跑全链路；
- **历史数据第三参照**：上一次同类任务的真实数字（5 轮/30 缺陷/20+ 小时）。

三方对照一览：

| 运行 | 流程 | 设计源码可见性 | 测的是什么 |
|---|---|---|---|
| B0 改版前 | 现状流程，无任何新能力 | 可读（复现历史真实条件） | 现状真实水平 |
| P1 改版后·薄闭环 | 提取 + 对照矩阵 + 人工视觉确认 | 实现侧禁读，提取器输出为唯一规格来源 | "提取器中介 + 规格驱动"的增量 |
| P2 改版后·全链路 | 九步总链路全量 | 同 P1 | 流程改造的完整效果 |
| 历史数据 | 上一次同类任务的会话记录 | 分阶段（前期未见源码/后期贴源码） | 第三参照锚点 |

另设 **P3 无稿试点**（原创模式）：无设计稿真实任务，通过条件 = 设计方向确认 1 次 + 复现协议正常跑通（提取/对照/视觉环节全走到）+ 验收确认 1 次。注意模式覆盖：B0/P1/P2 全是有稿复现，原创模式不试点就是缺口，要显式记录。

### 6.2 防污染原则

实验最大的敌人是"实现侧直接抄设计稿源码"，这会让"提取器中介"的增量测不出来：

- **P1/P2 实现侧禁止读设计稿源码**，提取器输出是唯一设计规格来源（提取器属于设计源读取侧，不受禁读约束）；
- **目标仓换栈防抄**：设计稿是 Vite+React 源码，目标仓就用 Next.js——同栈会被直接复制污染实验；
- B0 基线则允许读源码（复现历史任务的真实条件），测的是"现状真实水平"；
- 缺陷根因分类中设"直接复制"项以便识别泄漏。

### 6.3 六指标测量口径

| 指标 | 口径 | 基线参照 | 改造后阈值 |
|---|---|---|---|
| 返工轮次 | 一轮 = 宣告完成 → 验收驳回（含≥1 条缺陷）→ 再交付；最终通过轮不计 | 5 轮 | ≤2 |
| 缺陷数（分级） | CRITICAL/MODERATE/MINOR 三级，登记时定级不许事后降级 | ≈30 | 底线 ≤10（1/3），目标 ≤5（1/6） |
| 人工介入小时 | 用户验收/反馈/消歧/救火的墙钟时间（相邻 <30min 算同一段），不含等待 agent 的时间 | 20+ 小时 | ≤2 小时 |
| 验收确认次数 | 只计最终确认；设计方向确认另计 | 5 次 | =1 |
| 提取覆盖率 | 设计稿应提取条目中被提取进派发规格的比例（以组件清单/状态枚举/token/文案为 ground truth） | <30%（无提取器靠临场读） | ≥90% |
| 视觉比对差异 | 固定 viewport 下实现页 vs 设计源渲染页的比对：像素差异率（pixelmatch）+ 9 维语义清单逐维评级（独立上下文评分） | "完全是两个产品" | CRITICAL/MODERATE = 0，MINOR 全列容忍清单 |

口径防漂移细则：范围按页归一或只比同源页面缺陷子集；历史缺陷需按新口径回填分级（由独立上下文回填，禁止自审自判）；洁净环境与真实环境的缺陷源差异（数据链路/CSS 债务/环境中断约占 35%）必须显式声明，基线缺陷数是历史任务的下界估计。

### 6.4 收敛判定：迭代什么时候必须停

测量之外还要给迭代本身装上刹车，否则"再修一轮"会无限循环：

1. **停滞判定**：对照矩阵连续一轮无新增 PASS 项 → 停，换人/换方法或报阻塞；
2. **轮次上限**：每个区域最大 3 轮迭代；整体走有界验证法（一轮批量截图 → 一批修完 → 至多再一轮 → 停）；
3. **禁回归**：本轮修复不得把已 PASS 的行打回；收益递减（改善 <2%）即停；
4. **诚实停止**：要么全部判据通过，要么点名阻塞项 + 最小下一步——**不许弱化判据换成功**。

### 6.5 可证伪通过标准与诚实原则

- 阈值定**绝对口径**："返工 ≤2 轮、缺陷 ≤10、人工 ≤2 小时、确认 =1、CRITICAL/MODERATE=0"——达到/未达到一目了然；不写"较基线显著收敛"这种不可证伪的话（相对数据只作呈现，不作判定条件）；
- 阈值取基线的约 1/3 是有依据的：缺陷分布显示 60% 可编码前消灭 + 25% 可交付前消灭，理论上可压到 1/6，1/3 留了裕量；
- **n=1 不谈统计显著**：单次基线 + 单次改造后运行，只称"达到/未达到阈值"，不称"统计显著"；
- 任一指标未达 = 未通过，缺口回流方案修正，不许弱化判据换成功。

### 6.6 实证坑案例：视觉基准以产物渲染为准

调研中发现一个硬事实：用作设计源的 Figma Make 产物（AI 生成的前端代码）**自己不遵守自己的设计系统**——其设计 prompt 明确规定 12 色系统（App 背景 `#14141f` 等），实际产物中 **12 色里 8 色零使用**，产物自造了一套更深的色板（22 个手写 hex）。

教训：**AI 产物不是"忠实实现了设计的稿"，它本身就是一次有偏差的实现。** 对照实验的视觉基准必须选边：

- 以**产物渲染结果**为准（起服务截图），不以 prompt/文本描述为准；
- 把"文本描述与产物的偏差"本身登记为已知事实；
- 连带坑位清单：图表伪随机要同种子才能 diff、字体离线回退会造成全页假阳性 diff（比对环境必须固定字体加载状态）、设计源自带占位空态要预先登记为"非缺陷项"。

### 7.2 里程碑一句话版

- **B0**：改版前基线——用现状流程把两个页面实现一遍，记全六指标（开工前必跑）；
- **M0**：验收对象卡 + 规范文件最小基线字段 + stylelint 规则包 + 失败三层归档机制；
- **M1**：薄闭环——设计提取器 + parity 对照清单 + 最小"矩阵驱动派发"接线 + 验收矩阵编排方法论移植；
- **P1**：试点 1——真实任务跑薄闭环；可证伪通过标准：提取覆盖率 ≥90%、矩阵实际驱动派发、返工 ≤2 轮；
- **M2**：视觉验收能力——截图/感知/双轨 diff/边界电池/收敛判定 + diff 报告 schema；
- **M3**：派发规格密度模板 + 派发边界落地 + 编码/验收全接线；
- **M4**：技能批量移植（含性能 70 规则完整放入）+ 工程质量四维度扩展 + 规范文件完整模板 + 术语登记；
- **P2**：试点 2——全链路同稿复跑，对照 B0 与历史数据按绝对阈值判定；
- **P3**：试点 3——无稿原创模式真实任务（设计方向确认 1 次 + 复现协议跑通 + 验收确认 1 次）。

### 7.3 三轮异源审查的教训（58 条 findings 换来的）

方案经过独立对抗审查（10 条）+ 官方方向审查（16 条）+ 官方细节审查（16+16 条），共 58 条 findings 全部处置。**这些错是任何团队写方案都会犯的**：

1. **附录与决策冲突**：早期写的基线设计附录与后来的正式决策不一致（范围/载体/源码可见性三处冲突）——教训：方案内部必须有"唯一权威版"声明，过期材料标效力等级；
2. **不可证伪判据**：写过"较 B0 显著收敛"这种没法判真假的话——教训：每个通过标准都问自己"实际为假时它会报失败吗"；
3. **依赖倒挂**：P1 要求"矩阵驱动派发"但派发接线排在 M3；编排方法论在 M4 移植但 M3 依赖它——教训：画里程碑依赖图，逐边检查"谁依赖谁"方向；
4. **口径残留**：技能分类计数在五个地方写了三个版本（22/23/24）——教训：数字只算一次，其他地方引用；
5. **模式覆盖缺失**：试点全是有稿复现，无稿原创模式没人验证——教训：试点计划显式标注覆盖哪种模式，没覆盖就记缺口不谎称；
6. **边界未正名**："禁止派发"这种硬约束与"不新增 gate"的原则表面冲突——教训：硬边界就按硬边界正式登记（证明来源/消费者/owner/退出条件），不要用措辞绕；
7. **语义冲突未定义**："逐值复制"与"只许用项目 token"打架时怎么办没人写——教训：任意两条规则组合问一遍"同时触发时谁赢"。
8. **目标静默降级**：最初口号是"100% 复现"，方案实际定义是"矩阵全绿+MINOR 容忍"——教训：目标重定义必须显式写成决策并得到确认，不许在行文里悄悄降级；
9. **漏网场景不枚举就会漏**：存量项目没有规范文件怎么办、非 React 栈怎么办、owner 不在怎么办——教训：方案结尾强制回答一份"漏网场景清单"，每个场景给处置；
10. **验证路线本身要先探活**：审查路线因本地超时写死 120s、模型名过期而连环失败——教训：流程改造方案里"谁来裁决"的通道也要实测验证，纸面上的独立审查不等于可用的独立审查。

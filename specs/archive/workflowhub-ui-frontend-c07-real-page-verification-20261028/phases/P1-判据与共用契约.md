# Phase P1 — 判据正文成为唯一权威，校验器只判形状

判据作者在这里交付唯一判据、报告形状检查与接线。
采集和报告作者沿同一份定义实现，独立读者据此核对交付边界。

> 写作依据：`skills/material-writing/SKILL.md` 的「材料写作标准（唯一）」。
> 二级标题都是读者问题，第一句直接回答；命令与表格行不受行宽限制。
> 命令、路径、退出码、编号、哈希逐字保留，不因改写而改。


判据正文：一份说清查什么、结果怎么记、怎么算通过、什么情况拒收的文本。
它只此一份，采集器按它写输出，报告解析按它读结果。
校验器：只读报告形状的脚本；它判不出页面好坏，只判字段与类型。
四态：一次检查只有通过、失败、未测、不适用四种结果，没有第五种。
契约决定：`build-plan` 原件里逐条编号的取舍，正文写「契约决定 n」。

## 这一 Phase 交出什么？

交一份判据正文、一个只判形状的校验器、三处指针和一条接线测试。

判据正文一份，十一个二级节。
落点：`skills/frontend-testing/references/page-audit.md`。
校验器一个，按退出码三分，按六类具名码拒收。
两处方法正文各加一句指针，指向判据正文与校验器。
一条接线测试，证明指针指得到、指得对。
工作包声明：本 Phase 对应 decision-log 的工作包 2、3、8，即结果契约、九项标准与接线。

这个 Phase 不采集页面、不消费报告、不驱动浏览器。
本阶段交付判据与报告形状检查，完成须对照本卡实际验收与独立消费原件。

三件不做：
- 不判页面内容对错，只判报告形状。
- 不写总分或百分比，也不把未测凑成一个数。
- 不改设计审查技能里的八维原文。

## 这一 Phase 怎么验收？

先答这一问：假设本 Phase 全部实现、所有已设计测试也都通过，还会不会漏掉原始需求？
答不出「不会」之前，任何测试通过都不算达成验收。
效果只认一件事：一个没参与写作的人，照这份判据能不能真做一次检查。
代码写得对不对、测试齐不齐归审查，占不了这一节的位置。
一个 Phase 只有在验收标准真的被满足后才能说开发完成；代码审查通过、测试全绿、结构检查通过，都不是完成条件。
RED/GREEN 表、覆盖上下限与命令细节留在「怎么验证？」，本节只指向它。

1. **验收标准**：逐条列本 Phase 承接的四条验收，各写判据、成功与失败三句。
   - 验收 1：判据是照正文能对真实页面逐维取值、记四态、写未覆盖。
     成功长这样：执行者不看写作过程，能指出他按哪一节、取到什么原始读数。
     失败长这样：他读不出可执行步骤，只能照测试名或截图写「已通过」。
   - 验收 2：判据是正文说清身份或状态对不上时怎么具名报出、停在该对象。
     成功长这样：执行者按正文对一处人为不一致写出具体项，且不给正常结论。
     失败长这样：他只写得出「出错了」，或把未启动记成通过、干脆跳过。
   - 验收 4：判据是正文给三档与判定依据，别人不必自创规则就能定级。
     成功长这样：执行者只按「分级刻度」一节给档位，理由能指回哪条刻度。
     失败长这样：他要问作者要阈值，或把工具阈值、像素百分比当严重度。
   - 验收 6：判据是正文说清未知、空值、失联与证据错配各记哪一态。
     成功长这样：四类输入各落进四态之一，结果里没有总分、通过率或聚合值。
     失败长这样：unknown 被当 0、失联出正常报告，或凑一个总分才敢下结论。

2. **场景**：正常一个，反向与负控各一个，每个写输入、动作与预期。
   - 正常：输入是 C07 自有样本的默认态，动作是执行者只读正文取第 5 维九项。
     预期：每维有原始读数或未测理由，档位与依据在场，全文不出现总分。
   - 反向：输入是删掉「四态」与「未覆盖要写理由」两节后的正文副本。
     动作是同一位执行者照剩下的正文做同一维，并记下他缺哪一步、卡在哪。
     预期：他卡在记不了未测、判不了拒收，据此判正文不成立，不判他做错。
   - 负控：输入是一张只有「已通过」、没有原始读数的结果表，正文不动。
     动作是执行者按正文的失败条件判这份结果该不该被拒。
     预期：正文能拒收它；拒收不了，说明失败条件只写在作者脑子里。

3. **环境与数据**：写环境、数据、谁提供、来源与清理；缺的写 incomplete。
   - 环境：本机 Node 加仓内文件就能读正文；要真跑一次检查才需要浏览器。
     浏览器面本 Phase 不启，那次真跑归末验收 Phase 的独立执行者。
   - 数据：对象是样本 A 或 B 的默认态，它们是 C05 样本页的 C07 自有副本。
     受控页只作校准，不替代真实页；样本数据是 mock，结论只到 mock。
   - 谁提供：样本A、B在build-plan期已随材料落盘，受控页由阶段3建后再交。
     执行者由末验收的独立执行者出，不占本 Phase 的写手。
   - 来源：八维名称逐字取自设计审查技能第 36 到 43 行，正文不另改字。
     三档词与四条校准负例取自契约决定 6，刻度值只有这一份。
   - 构造与清理：执行者起临时静态服务读页，读完关服务，不写样本、不删原件。
   - 拿不到：那次真跑本 Phase 没做，这一格记 incomplete，不写 N/A。
     原因：本 Phase 只交正文与形状校验器；执行者与真实目标都归末验收。
     恢复条件：对象与执行者到位后照正文做一次检查，留执行者原话与逐维表。

4. **用例**：五条用例，逐条给对应验收、操作、预期与判定方式。
   - 用例一（对应验收 1）：执行者只读正文，取样本默认态第 5 维九项写逐维表。
     预期是九项各有读数或未测理由；判定看他按的节与读数，不看退出码。
   - 用例二（对应验收 2）：给他一处错路由的输入，按正文写不一致项与去向。
     预期是不一致项具名、结论停在该对象；写成「出错了」即不通过。
   - 用例三（对应验收 4）：只给正文的「分级刻度」与三条还原负例，让他给档位。
     预期是三档各归位、理由指到刻度；要作者补阈值即不通过。
   - 用例四（对应验收 6）：给 unknown、空值、失联、证据错配四类输入，按正文记态。
     预期是四态各归位、无聚合值；出现总分或把空值当 0 即不通过。
   - 用例五（负控）：删掉「四态」与未覆盖理由两节，用同一批输入重跑前两条。
     预期是执行者明确报「正文缺步骤」；据此判正文不合格，不判他不合格。
   - 形状校验器可先跑一遍，它拒收总分、聚合、缺证据与越界状态：
     `node skills/frontend-testing/scripts/check-page-audit.mjs --input <report.json>`
     它读的是字段与类型，读不出判据有没有被照做，因此不是本条判定器。

5. **谁判**：由独立执行者与独立判者判，两者都不在写正文的上下文里。
   - 执行者：一个没参与写正文的子代理，另起会话，只拿正文与对象。
   - 判者：独立审查或独立测试子代理，读执行者的逐维表与他当时写的原话。
   - 已有相邻事实：一位独立契约读者回源核过两处来源，核的是字段下限。
     它不证明正文能被照着做，这一格仍按未做记，不拿它补签。
   - 时点：实现就绪后独立审测；有问题回原作者修，再由受影响方复验。
     审查、测试明确回报且验收满足后，原作者才确认开发完成；边写边自判不算。
   - 判者不改正文、不改断言，只按原判据读真实产出，也不带走写手的解释。

6. **失败回修与重验**：失败信号、分诊、回 owner、重验与结论更新各一句。
   - 失败信号：执行者说不出按哪节、每维只有「通过」、要作者补阈值。
     另一类信号是正文拒收不了假结果，那说明失败条件只写在作者脑子里。
   - 分诊：由独立判者分，不由写正文的人分；写作者不自签「其实已经写清」。
   - 回 owner：缺步骤回本 Phase 判据 owner 补节；判据与规格冲突回规格负责人。
     八维字面被改则整段撤回；六类码与正文口径冲突回契约 owner 核码。
   - 重验：同一位执行者按改后正文重做同一维，并重验同节引用的其它维。
     下游字段受影响时，同时重放阶段2采集器与阶段4报告解析的字段断言。
   - 结论更新：只按重验原件改验收状态；失败原件保留，不删旧记录。
   - 重报：执行者与独立判者重报，写作者只改正文，不改结论。

7. **承接**：结论落在本文件的机器字段与具名原件上，下游照这两处读。
   - 状态：写进文末 Done 与覆盖验收四行，状态词只用已记的四种。
   - 原件：
     `quality/evidence/build-code/2026-10-29-065-p1-contract-diffs-correction.json`
     与 RED/GREEN 原 ref。
   - 清单侧唯一原件是附录 B 记的那份差异更正件，不另建选择器或第二权威。
   - 下一消费者：阶段2的作者读正文的字段与四态，阶段4的解析读退出码与六类码。
   - 末验收 Phase 的执行者读同一份正文做真实首判，结论记在它自己的证据件里。
   - 读状态去 Done 与「这一 Phase 不签什么？」；
     读执行做法去判据正文；本卡提供实施安排。

## 每张任务卡怎么写？

每张卡先写人读正文，机器字段接在同一张卡的末尾。

卡里回答四件事：谁要什么结果、从哪个输入开始、第一处动作、失败交给谁。
字段从「任务编号」开始，到「完成」结束，人读时可以整段跳过。
顺序：三张卡依次排，任务 2 依赖任务 1，任务 3 收口。

### 任务 1：写判据正文

采集器的作者要一份能照着写输出的正文，报告解析的作者要照着读结果。
输入是设计审查技能第 36 到 43 行的八维原文，加两份冻结测试里的字面要求。
第一处动作：先落八维骨架，再落九维到八维的映射，最后补四态与各条规则。
这张卡不写采集器，也不写脚本。

十一个二级节，每节必须出现什么；另加一条横跨全文的取值口径：

| 节 | 必须出现 | 出处 |
| --- | --- | --- |
| 八维骨架 | 八个维名逐字，各一句「这一维交付什么」 | 设计审查技能 36-43 行 |
| 九维到八维的映射 | 三列表加分隔行；每维一行，行内带「主」或「副」 | 判据包测试 41-59 行 |
| 四态 | 通过、未测、不适用、失败，各带理由要求 | 判据包测试 16-19 行 |
| 分级刻度 | 三档，加字体、间距、颜色三条还原负例与一条主操作被遮罩的阻断负例 | 契约决定 6 |
| 采集失败四类 | 未启动、失联、工具异常、身份不符，各写落在哪个状态 | 契约决定 7 |
| 必测门 | 200% 缩放与键盘焦点同一句含「必测」；读屏同一句含「不作必测门」 | 判据包测试 104-106 行 |
| 业务任务脚本 | 按页面任务判成败；mock 上写未覆盖 | 契约决定 7 |
| 回修闭环 | 三轮上限；一轮无新增即停；停不等于通过或失败 | 契约决定 8 |
| 不适用与依据 | 同一句写理由与依据 | 判据包测试 16-19 行 |
| 四条越界规则 | 见本节后面四条，只写定义不写实现 | 契约决定 9 |
| 规范来源 | 按路径、节、版本、负责人、使用者登记 | 契约决定 6 |

取值口径不单列二级节，必须写在「九维到八维的映射」节末尾：
property（属性）、declared（原源声明）、rendered（同状态视口渲染值）、
comparison（差异与观察）四项；间距、阴影、边框、圆角、图标五项
各列取的 CSS 属性、状态与视口。
缺任一项或只写字段名，判据正文不完整。

九维到八维的映射，逐行写：

| 九维 | 主 | 副 |
| --- | --- | --- |
| layout | ⑥ | ⑤ |
| typography | ⑤ | 无 |
| colors | ⑤ | ⑦ |
| spacing | ⑤ | ⑥ |
| shadows | ⑤ | 无 |
| borders | ⑤ | 无 |
| radius | ⑤ | 无 |
| icons | ⑤ | ⑦ |
| states | ③ | ⑤、⑦ |

四条越界规则只写定义：
- 第一条，材料身份：白名单五个字段（材料号、引用、摘要、字节、角色）。
- 第一条的判同条件：改名但摘要与字节都相同，算同一身份。
- 第二条，封闭词表：否定、限定、未执行、不能证明、待补证五类。
- 第二条的登记项：覆盖要登记引用句、理由、签名人、失效条件。
- 第三条，措辞禁令：不写「已通过」「已闭环」，不引用历史编号。
- 第四条，九类缺陷：九类区域各自映射到维度与严重度，映射见附录。

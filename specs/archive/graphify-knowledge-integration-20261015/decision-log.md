### 工作包 ① — graphify 融入五阶段（M0 底座 + M1–M4 阶段接入 + M5 横切 + M6 图谱质量缺口 + M7 收口技能抽取）

#### ADR-001 — 用「查图替代读文件」达成本次集成的两个目标

- **做什么**：以 graphify 的 `graph.json` 为知识载体、以 CLI 查询为消费方式，把「先查图再读文件」确立为五个阶段的工作顺序；收益目标按 ADR-013 为「知识精准度（R-008），且 token 消耗不劣化」。
  - 依据：实测确认 `extract --code-only`、`update`、`cluster-only --no-label`、`query`、`path`、`explain`、`affected`、`god-nodes`、`diagnose` 全部为 0 token、确定性、无需 API key（`research.md` I-003）。
- **不做什么**：不新建第二个知识权威、不引入审批门、不改运行时模块（对齐 `anysearch` 纯技能包装先例）；不把「图存在」当作工作可开始的前提。
- **风险**：省 token 的净效果未量化，可能因建图开销反转为更贵。
  - 缓解：AC-008 强制用 `graphify benchmark` 与真实 token 消耗给出数字；建图成本按 ADR-007 的增量策略控制。
  - 未解 owner：主会话在 build-plan 设计量化方案。
- **改动**：本集成的方法落点为 `skills/knowledge-graph/SKILL.md`（新建）、`skills/catalog.yaml`、五个 `workflows/*/SKILL.md` 与 `skill-deps.yaml`、`.gitignore`；唯一写主为各阶段的当前实施会话。

#### ADR-002 — make-decision 先建图、再以图做内部调研

- **做什么**：在 `workflows/make-decision/SKILL.md:54` 的 `research-and-diverge` 步骤内：无图则先建图，有图则按调研问题执行图查询，查询结论写入 deep-research 的 canonical report，主文只留指针。
- **不做什么**：不在用户未授权的调研范围外自动建图；不把图查询结论当作真人答复；不新增步骤（按 ADR-010）。
- **风险**：首次建图是外部动作且可能消耗大量 token（**当时为估算**：中央值约 2400 万，区间 1500 万–3400 万；该估算后被实测证伪，见 ADR-007 的实测值）。
  - 缓解：ADR-008 把首次文档建图移出主会话；ADR-012 把图放固定位置使一次投入长期复用。
  - 未解 owner：无。`.omc/` 按仓库 `.gitignore` 排除，已按现状接受（见 OI-002 的已解决记录）。
- **改动**：`workflows/make-decision/SKILL.md`（`research-and-diverge` 内的图查询顺序）、`workflows/make-decision/skill-deps.yaml`（登记 graphify 外部能力）；唯一写主为 make-decision 主会话。

#### ADR-003 — build-prd / build-plan 消费图以获得架构与经验知识

- **做什么**：`workflows/build-prd/SKILL.md:15` 的 `load-confirmed-inputs` 与 `workflows/build-plan/SKILL.md:16` 的 `conditional-light-research` 内，用图查询获取子系统划分、接口边界、既有实现与依赖链，作为 prd 范围与 Phase 切分的输入。

- **风险**：图可能过时（代码图随分支变化），据过时结论设计 Phase 会出错。
  - 缓解：图随 git 走（ADR-012），各 worktree 在自己树内读图与更新图；新 worktree 从 git 继承图与语义缓存，只补改动文件。
- **改动**：`workflows/build-prd/SKILL.md`、`workflows/build-plan/SKILL.md` 及各自 `skill-deps.yaml`；唯一写主为对应阶段主会话。

#### ADR-006 — 任务 verify-code 收口时更新知识图谱

- **做什么**：在 verify-code 收口时更新图。**代码部分**：`graphify update <项目>`（实测确认免费、且**只处理代码**）。**文档部分**：`graphify update` 实测**完全不处理文档**、声称成功且退出码 0，因此文档更新必须走宿主会话的语义抽取流程，不能只调 update。

- **不做什么**：不把 `update` 的静默跳过当作文档已更新；不与 ADR-011 的经验记忆功能合流。
- **风险**：只跑 `update` 会让人误以为文档图已更新，实际长期陈旧。
  - 缓解：收口的完成判据必须分别报告「代码图已更新」与「文档图已更新/未更新」两项事实。
  - 未解 owner：build-plan 设计文档更新在收口流程中的具体位置。
- **改动**：`workflows/verify-code/SKILL.md` 收口段；唯一写主为 verify-code 主会话。

#### ADR-007 — 图谱包含文档，首次全量、之后只补改动

- **做什么**：扫描范围包含代码与文档（含 `specs/` 历史档案）；首次做一次全量文档语义抽取，此后按 ADR-006 只处理改动文件。
  - 依据 R-018、R-019；实测确认增量不变量成立：manifest（相对路径键）与缓存（内容哈希）两道闸口独立地把「3 文档改了 1 个」判定为只需重抽 1 个，`build_merge` 保留其余图内容（`graphify-semantic-cost-report.md` 第 5 节）。
- **不做什么**：不做每次全量重抽；不自行把 `.omc/` 等被 `.gitignore` 排除的目录纳入扫描范围（已按现状接受，见 OI-002）。
- **风险（已取得实测值与估算的差值，不再是估算）**：首次全量建图实际消耗 **53,634,718 token**（输入 49,608,703 + 输出 4,026,015；另有 cache read **154,290,304**，见 `research.md` I-004 汇总表），是事先估算中央值 2,400 万的 **2.23 倍**，并超出估算上限 3,400 万的 1.58 倍。倍数只由「输入+输出」计算，cache read 不计入倍数。
  - 触发与后果：估算系统性偏低而非偏高。按现实基线重算回本点（`research.md` I-004）：一次查询若替代读 3 个文件，需 16,253 次查询才回本；读 5 个文件需 8,126 次；读 10 个文件需 3,612 次。**R-009「token 消耗更少」很可能不成立，真实收益落在 R-008（上下文与知识更精准）。**
  - 缓解：ADR-012 使一次投入可跨任务复用（新 worktree 经 git 继承图与语义缓存，只补改动文件——该机制本身由实测的 3 文档实验证明，但**尚未在真实 worktree 继承场景下验证过**，如实保留）；ADR-007 的增量机制已实测成立。
  - 未解 owner：**用户**——是否接受「本集成不省 token、买的是知识精准度」这一事实并据此调整 R-009 的期望（见 OI-001）。
- **产出成果（主会话亲验）**：`graph.json` 12,901,255 字节、10,574 节点、18,217 边、480 超边、705 社区，sha256 `eb5e6ba94e32b2f9dce1d15b68d6e22c8390f3d6026f8f83b952c523ef4f38ce`。仓库 1,058 个 `.md` **全部**有节点，`specs/`（6,112 节点）与 `skills/` 均已入图，`.omc/` 按仓库 `.gitignore` 排除。节点与全部 18,217 条边的不规范 `source_file` 均为 0，悬挂端点 0，重复 id 0。**文档知识覆盖完整**，这是本次建图最有价值的成果。
- **已知缺陷（主会话实测发现）**：50 个节点无来源文件（49 个 id 形如 `ref_node_*` 且无 `_origin`，1 个 AST 节点 `ArgumentParser`），占 0.47%；查询遍历到这些节点时**无法回溯到任何文件**，与「查图替代读文件」用途冲突。另：`extract --code-only` 报告 4,003 AST 节点而最终图为 3,953，差 50 个，会话总结披露了差异但未给出原因。
- **改动**：无代码改动；约束写入 `skills/knowledge-graph/SKILL.md` 的建图契约与范围说明。

#### ADR-008 — 文档语义抽取由宿主会话的子代理执行，不配置通用模型后端

- **做什么**：按 graphify 官方设计，由当前 AI 会话充当语义抽取的 LLM；首次全量建图由用户另开一个会话执行（提示词原件：任务库根 `GRAPHIFY-BUILD-PROMPT.md`）。
  - 依据 R-020、R-026；实测确认该路径可行：语义节点能正确进入 `graph.json`（`_origin: "semantic"`），流水线端到端跑通。
- **不做什么**：不要求用户配置 `GEMINI_API_KEY`/`GOOGLE_API_KEY` 等后端；不在主会话承担该开销（R-015）。
- **风险**：宿主会话路径**没有稳定的 JSON 接口**（`query`/`path`/`explain` 输出为散文），且实测撞到三个缺陷。
  - 触发与后果：① 同节点对的两条边在无向图中会塌缩；② 符号链接路径会让缓存静默失效导致全量重抽；③ `prompt_file` 传字符串会按路径字符串而非内容哈希。
  - 缓解：契约中强制 `root` 取 realpath、`prompt_file` 传 `Path`、`--no-label`；这些已写入提示词与技能契约。
  - 未解 owner：build-plan 决定是否把缺陷规避写成技能内的硬性写法。
- **改动**：`skills/knowledge-graph/SKILL.md`；唯一写主为该技能 owner（实施阶段）。

#### ADR-009 — graphify 不可用时如实记不可用并继续

- **做什么**：未安装、命令失败、输出无法解析三种情况分别记 `unavailable` 与真实原因，流程不阻断、各阶段退回普通阅读方式。
  - 依据 R-022；与 `CONSTITUTION.md:70,73`（缺数据保持 unknown，文件存在不能证明知识被消费）及 `workflows/build-code/SKILL.md:17`（缺材料或宿主能力明确 unavailable，不凭指针存在猜内容）一致。
- **不做什么**：不把「图文件存在」当作知识已被消费的证明；不因图缺失而阻断同任务工作；不伪造通过。
- **风险**：长期静默降级会让人误以为集成在生效。

#### ADR-012 — 图谱在项目目录内、随 git 走，当作代码管理

- **做什么**：知识图谱存放在项目内的 `graphify-out/`，**提交进 git**，随分支与 worktree 一起流动。每个任务在**自己的 worktree** 内读图、更新图，写自己的那份；新 worktree 通过 git 继承图与语义缓存，`update` 只补改动的文件，因此 R-019「首次全量、之后只补改动」得以成立。
  - 依据 R-025 与用户 2026-10-15 的明确纠正：本 ADR 的**前身**（图放仓库外、各 worktree 只读）被用户判定为错误需求，理由是「图要跟着 worktree 走，每个 worktree 都要更新它」。
  - 该纠正使审查提出的两项风险**自动消失**：①「R3 谁有权写共享图」不再存在（无共享可变图）；②「M5 从 worktree 跑 update 会剪掉他人节点」不再存在（各写各的）。
  - 实测支撑：`query --graph` 零写入；建图只写 `GRAPHIFY_OUT`；`graphify merge-driver` 实测可做并集合并（两边节点均保留，合并产物仍可查询）。
- **不做什么**：不把 `cache/ast`、`stat-index.json`、`.graphify_ast.json`、批次 chunk 文件、`GRAPH_REPORT.md` 提交进仓库（可本地重建或属本机状态）；不执行 `graphify hook install`（会改 `.git/hooks` 与 git 全局配置）——只写 `.gitattributes` 声明合并规则，冲突时手动跑 `merge-driver`。
- **风险**：图谱是两个分支的并行改动面，普通 git 合并会冲突（实测 `CONFLICT ... graph.json`）。
  - 触发与后果：并行任务同时改图时收到合并冲突，需人工处理。
  - 缓解：根目录 `.gitattributes` 声明 `merge=graphify`，冲突时手动执行 `graphify merge-driver <base> <cur> <other>`（实测并集正确）；未装驱动时按普通冲突处理。
  - 未解 owner：build-plan 决定是否在收口流程内提供一条合并指引。
  - 另一风险：图会出现在 `git diff --name-only` 中，与「声明写集逐条对账」纪律相撞。
  - 缓解（用户已选）：收口时把图的变化**单独列为一项，不计入功能写集**；见 ADR-014。
- **改动**：`graphify-out/.gitignore`（只保留 `graph.json`、`manifest.json`、`.graphify_analysis.json`、`cache/semantic/`）、根 `.gitattributes`（声明合并驱动）、`skills/knowledge-graph/SKILL.md` 的存放位置契约；唯一写主为该技能 owner。
  - 已实际执行（2026-10-15）：产物已从 `/Users/Hugh/Hugh/Project/.workflowhub-graph/graphify-out/` 搬入本 worktree 的 `graphify-out/`，`graph.json` 哈希与源一致（`eb5e6b…`，两份字节相同），语义缓存 1,153 个条目；git 将纳入 1,156 个文件（约 22.6 MB）。

失败了怎么退：删除 `graphify-out/` 并回退 `.gitattributes` 一行即可；代价是 53,634,718 token 的文档抽取产物需要重做。

#### ADR-013 — 接受实测事实，把「省 token」改为「不使 token 劣化」

- **做什么**：把 R-009 由「token 消耗更少」修订为「**不使 token 消耗劣化，收益以知识精准度（R-008）为主**」，并据此改写 AC-008 的成功条件：不再要求证明「更便宜」，改为要求 (a) 建图真实成本可复现、(b) 查图单次成本可复现、(c) 真实任务中**净消耗不劣化**，三项各有数字。
  - 依据（全部实测，见 `research.md` I-004）：建图 **53,634,718 token**（输入 49,608,703 + 输出 4,026,015），为事先估算中央值的 2.23 倍；`graphify benchmark` 报 427.2x 但基线是「整库通读」，不现实；按现实基线一次查询替代读 3–10 个文件，净省 3,300–14,850 token/问，**回本需 3,612–16,253 次查询**。
  - 依据 R-008 本身成立：图谱实测覆盖仓库全部 1,058 个 `.md`、`specs/` 贡献 6,112 节点，文档知识完整入图。
- **不做什么**：不为了凑「省 token」而排除 `specs/` 归档（用户已明确其为最重要知识，R-018）；不缩减已建好的扫描范围；不把 427.2x 当作收益证据对外陈述。
- **风险**：目标放宽后，后续实施可能不再关心 token 实际开销，导致「不劣化」也失守。
  - 触发与后果：每个阶段查图无节制，单任务净消耗反而上升。
  - 缓解：AC-008 的 (c) 项在真实任务中采集净消耗，作为该风险的检测点；build-code/verify-code 承接。
  - 未解 owner：build-plan 设计净消耗的采集口径。
- **改动**：本决策日志（R-009 行、AC-008 行、风险表）；后续写入 `skills/knowledge-graph/SKILL.md` 的成本边界说明。唯一写主为主会话（本阶段）与该技能 owner（实施阶段）。

失败了怎么退：若后续真实任务实测显示净消耗明显劣化（超出查图收益），退回「只在明确需要大范围理解历史档案时查图」的窄用法，其余场景不查图。

#### ADR-014 — 图谱改动在写集对账中单列，不计入功能写集

- **做什么**：收口时把 `graphify-out/` 的变化**单独列为一项「非源码已知改动」**，不计入功能写集；`git diff --name-only` 的对账按「功能写集 + 图改动单列项」两项分别读回。

- **不做什么**：不修改 `AGENTS.md` 或 `docs/standard-workflow.md` 的既有对账纪律（那不是本任务的写集）；不靠人工每次记得手动加进写集。
- **风险**：单列项可能被当作规避对账的借口，把真正的越界改动也塞进「图改动」名下。
  - 触发与后果：功能越界被掩盖。
  - 缓解：单列项只允许包含 `graphify-out/` 下的路径，且必须在收口时列出实际变化的文件数；其它路径一律回到功能写集对账。
- **改动**：`skills/knowledge-graph/SKILL.md` 的收口对账说明、`workflows/verify-code/SKILL.md` 收口段；唯一写主为 verify-code 主会话。

#### ADR-015 — 图谱质量限制随图生效（作为契约条款）

- **做什么**：把三路独立检查（覆盖率、过期性、错误与遗漏）得出的质量限制写成技能契约的硬性使用条款，随图一起生效。完整裁定见任务库根 `quality/evidence/decision-log-refs/graph-quality-ruling.md`。

#### D-003 — 方向风险清单（第 6 步对抗性方向检查）

- **做什么**：按 make-decision 第 6 步轻量攻击方向是否过早锁定、隐藏前提与更小可逆路径。本步不设否决权、不替用户选方向、不增设机器门，只产出带事实依据的风险清单。

  **风险 1（最高）— 集成可能只是「给自己派活」。**
  图谱已建成、覆盖完整，真问题不是「能不能用」，而是**「把查图写进工作流后，agent 会不会真的照做」**。写成建议则很可能被忽略；写成硬前置则成为新门，违反 `CONSTITUTION.md:42-45`（关卡只在确有必要时添加、不预先堆砌）。该失败模式与工具能力无关，是本次集成最大的不成立路径。
  - 可证伪观察：在一个真实任务的五个阶段里，检查是否存在实际的图查询调用记录；若连续若干任务无任何真实查询，则该集成失效。

  **风险 2 — 修订后的收益表述可能变成台阶。**
  R-009 已由「更省 token」修订为「不更贵」。诚实表述应是：**本次集成买的是知识精准度（R-008），token 是纯投入而非投资。**
  - 可证伪观察：若 AC-008 的 (c) 项在真实任务中测出净消耗劣化，则「不更贵」也不成立。

  **风险 3 — 图谱会静默过时。**
  实测确认 `update` 不碰文档且退出码 0，无任何信号。文档图会随任务推进悄悄腐烂，无人察觉。
  - 可证伪观察：ADR-006 已要求收口分别报告两项事实；若实际收口只跑 `update` 而未报告文档未更新，则该风险成立。

  **风险 4 — 更小更可逆的路径被跳过。**
  当前方向是五个阶段同时上。更小路径：**只在一个阶段（make-decision）试，用真实任务量出净消耗是否劣化，再决定铺开。**
  - 该路径能提前止损；代价是多一轮交付与一次任务创建。
  - 注：用户在模块广度确认时已选择「模块和顺序都同意，往下走」，即已了解并接受该取舍；本项如实保留，不重复追问。

- **不做什么**：不因上述风险单方面缩减已确认的方向或模块范围；不把风险当作否决权；风险处置权归用户。
- **风险**：本清单由实施者自产，属自审性质，不能替代第 7 步的独立方向审查。
  - 缓解：第 7 步已按 wh-review 派独立上下文审查，输入保持 questions-only 盲审投影。
- **改动**：仅记录于本决策日志；消费者为第 7 步独立审查与第 12 步决策草稿。

#### ADR-016 — 每个阶段开工前都做一次基于图谱的调研（不只三个时点）

- **做什么**：把图谱调研从「三个固定时点」提升为**每个阶段开工时的标准动作**——make-decision、build-prd、build-plan、build-code、verify-code 五个阶段各自开始时，都先用图谱做一次与该阶段职责相称的调研，让该阶段做得更专业、更靠谱。
  - 依据 R-004～R-006 的原意（用户 2026-10-15 明确纠正）：原表述「开工前、写代码前、收工后」把用法讲窄了；用户要求的是**所有 stage 开始时的相应调研**。
  - 各阶段调研内容按 ADR-002～ADR-005 的分工执行（make-decision 三步查法、build-prd/plan 三类问题、build-code 固定三步、verify-code 两项核对），本 ADR 只确定「每个阶段都要做」这一层。
- **不做什么**：不新增阶段、不新增审查点、不改 `steps.json`（沿用 ADR-010）；不把调研做成开工前置门（图不可用时按 ADR-009 降级并继续）。
- **风险**：五个阶段都加调研会累积上下文与时间开销，且可能退化为走流程。
  - 缓解：调研由子代理执行、只回结论 + 来源路径（M5 上下文纪律）；「走流程」由 ADR-017 的核实办法检测。
- **改动**：五个 `workflows/*/SKILL.md` 各自的开头**新增**一段该阶段的图调研；唯一写主为各阶段实施会话。
  - **与 ADR-002～ADR-005 的关系（2026-10-15 澄清）**：两者**并存不取代**。ADR-002～005 规定的是各阶段**内部某一步**的图消费（如 make-decision 的 `research-and-diverge`、build-code 的 `inspect-and-route-actual-tests`）；本 ADR 规定的是**阶段开工时的第一次**调研。因此文件表同时保留两类落点：`### 调研（阶段开头）` 与各阶段原步骤。

#### ADR-017 — 「装样子」的判据：本次调研必须尝试挖出一条归档历史经验

- **做什么**：用「**只有知识图谱才能给出的东西**」作为判据，替代一切自述式与留痕式检查。
  - **依据（分析得出）**：图谱真正独有的不是代码结构（代码就在工作树里，翻文件也能看），而是 **`specs/archive/` 那 1000+ 个历史档案**——历史任务当时为何那样决定、踩过什么坑。这些内容**普通阅读与搜索都难以定位**，只有图把它们关联起来了。
  - **判据**：每个阶段的调研必须**尝试**挖出一条「从归档历史里来」的结论，并说明它如何影响了本次做法（例：「历史上某任务在此处选过 X，本次因此不重复设计」）。
  - **挖不到时如实写「本次无历史经验可挖」**——这是一个诚实的调研结果，**不是失败**。
- **不做什么**（明确废止前一版做法）：
  - **不再要求每条结论写出来源路径再让第三方反查**。前一版（本 ADR 初稿，2026-10-15 被用户否掉）有四个缺陷：① 可配合造假（路径存在即通过，查的是路径不是内容）；② 仍是自述——一边说不要靠自觉、一边要求自己写来源自证；③ 给材料堆叠无人回看的元数据；④ 防的是「有没有留痕」而不是「阶段是否因此更专业」。
  - 不新增质量门、评分器、机器校验器；不新增第二份台账或持久对象。
- **风险**：与归档历史确实无关的任务（例如全新功能）会挖不到，只能写「无历史经验可挖」。
  - 触发与后果：若把这种情况误判为失败，会迫使执行者编造历史结论——**反而制造装样子**。
  - 缓解：契约必须写明「挖不到是合法结果」，且与「没做调研」区分开。
  - 另一风险：判据是「尝试挖一条」，执行者可能草草搜一下就宣称挖不到。
  - 缓解：**由 ADR-016 的每阶段调研与 AC-009/AC-010 的产出可定位性共同约束**；不做机器门，发现草率由独立审查按既有渠道处理。
- **改动**：`skills/knowledge-graph/SKILL.md` 的调研产出要求；五个 `workflows/*/SKILL.md` 的调研段落；唯一写主为该技能 owner 与各阶段实施会话。

#### ADR-018 — 收口统一为共享技能 `stage-closeout`，图谱更新接入其中

- **做什么**：
  1. 把 verify-code 现有的完整收口流程（提交、推送、合并、PR 的 `until=pr` 续跑、归档、清理、以及 `docs/standard-workflow.md` 的默认安全收口与授权核对）**抽成一个可单独调用的共享技能 `stage-closeout`**，供多个阶段共用，避免两套收口并存。
  2. **把图谱更新接入该技能**：代码图 `update`（免费）+ 按 M1 规则询问用户处理文档图（仅重抽改动文档）；两项事实分别报告。
  3. **使用时机**：`build-prd` 与 `verify-code` 两处，在**人工确认没问题之后**执行。
  - 依据（用户 2026-10-15）：用户要求「把收口这件事统一成一个标准技能，保证所有工作一次做完」，并明确目前只需 build-prd 与 verify-code 两处使用。
- **不做什么**：不新增第二个 close 对象或状态；不复用旧 close plan / 旧公共流程节点（沿用 `docs/standard-workflow.md` 的既有边界）；不改授权语义（仍用 `runtime/interface/git-authorize.mjs` 核动作、分支与 HEAD）；不新增公共运行时入口。
- **风险**：抽取共享技能会改动 verify-code 现有收口写法，可能破坏已验证的授权核对与五步退路。
  - 触发与后果：授权核对失效 → 不可逆 Git 动作被越权执行。
  - 缓解：抽取只做「把既有步骤原样搬进共享技能 + 调用方改为引用」，**不改授权逻辑**；实施后必须重跑既有 close 相关测试（针对性，不全量）。
  - 未解 owner：build-plan 决定技能边界（哪些步骤进技能、哪些留调用方）与命名确认。
  - ~~另一风险：用户原话末三字含义未能确定~~ → **已由用户澄清（2026-10-15）**：原话「提交、合并、归档、推送、清理、PR、图谱更新的难度更」中的「的难度更」是**打字错误**，应为「**等等任务**」。即该技能要涵盖的是**这一整组收尾任务**（提交、合并、归档、推送、清理、PR、图谱更新等），理解与 ADR-018 一致，无需改写。
- **改动**：新建 `skills/stage-closeout/`；`workflows/build-prd/SKILL.md`、`workflows/verify-code/SKILL.md` 的收口段改为引用该技能；`skills/catalog.yaml` 与两处 `skill-deps.yaml` 登记；唯一写主为该技能 owner。

## 模块收敛结论（第 9 步）

本节回答：每个模块收敛到什么程度、还剩什么。M0～M7 的范围与细化顺序由第 8 步用户确认；本节记录逐模块的真实收敛结果，未收敛项如实保留。

### M0 底座与技能契约 — 已收敛

- **技能命名**：不使用 `graphify` 作为仓库内技能名（与宿主级 `~/.agents/skills/graphify` 的触发词「任何关于代码库的问题」撞车，见 OI-007）。**2026-10-15 已定名 `knowledge-graph`**（命名约束为「不得与宿主技能的触发场景重叠」，已核实无冲突）。
- **契约必含条款**（依据 ADR-015 与实测）：四动作（建图/更新/查图/降级）；`--no-label` 强制；`source_file` 为唯一文件来源、**绝不把节点 id 当路径**；语义 label 是意译不得当引用；JSON 类文件不在图中；社区名为占位；禁止参数清单（`--mcp` 会静默触发全量建图）；`root` 取 realpath、`prompt_file` 传 `Path`；图谱与语义缓存随 git 走。
- **已收敛（用户 2026-10-15）**：技能名定为 **`knowledge-graph`**（现有 36 个技能中无 graph/know/context 类名字，宿主也无同名，不撞车；避开了宿主 `graphify` 技能的宽触发场景）。`skill-bundle.json` 与 `catalog.yaml` 的字段值按仓库现有技能的既有形状填写，属实施细节。

### M1 make-decision 建图与内部调研 — 已收敛

- **建图与更新触发（用户 2026-10-15）**：
  - **先检查是否存在图谱**；判定按「能否解析」而不是按版本号猜测（见下）。
  - **代码图**（0 token、数秒）：不存在或已旧，**自动建/自动重建**，不问。
  - **文档图**（实测千万级 token）：**不存在时先问**；**存在但已旧时也先问**——用户答复「可以问我一句，我同意就更新」。
    - 问的时候必须说明：**只重抽改动的文档**（实测增量成立：manifest 与内容哈希两道闸口独立生效），并给出本次预计处理的文档数。
    - **实测坑（必须写入契约）**：`graphify update` 命令**完全不处理文档**、输出提示后**退出码仍为 0**；因此文档更新**不能**靠 `update`，必须走宿主会话的语义抽取流程，且**不得把 `update` 的成功退出当作文档图已更新**。
    - 另一实测事实：`update` 在「无事可做」时**退出码为 1**，契约须把这一退出事实与真正失败区分开。
- **「有效图」的判定（用户 2026-10-15 简化，去掉版本推测）**：
  - 只判「`graph.json` **能否被解析**」。能解析即视为可用；不能解析（缺失、损坏、结构不兼容）即如实记 `unavailable` 并回退普通阅读。
  - **不做版本号比较**：`graphify_version` / `schema_version` 仅作一次性真相核对用，**不构成使用门**。依据：用户明确质疑「版本不同为什么会让图不可用」，且实测**没有任何证据**表明版本差异导致老图不可用；凭空增加推测性检查违背 `CONSTITUTION.md:70,73`（缺数据保持 unknown，不制造结论）。
  - 图偏旧：按上面的触发规则处理（代码图自动重建；文档图问用户），**不因「旧」而拒绝使用**——历史决定与经验类知识大多不过期，契约要求把「该结论来自某时刻的图」如实随结论带出。
  - 只有代码图、没有文档图：内部调研**受限但仍可用**（只能回答代码结构类问题）；涉及历史决定与经验教训的问题须回退普通阅读并如实说明图不覆盖。
- **调研查询范围（用户 2026-10-15）**：除与当前任务直接相关的查询外，**主动挖掘跨模块意外关联，但只取与当前任务真正相关的少数几条**；不全量取出，避免撑大主上下文反噬成本目标。
  - **实测更正（2026-10-15，子代理测量）**：图自带的 `surprises` 字段**不可直接用**：
    - 它是 `analyze.py:151` 的 `top_n=5` **硬编码上限**，与图规模无关；本图 10,574 节点仍只产 **5 条**。
    - 本图实际有 **3,029 条跨社区边**（占 18,217 条的 16.6%），`surprises` 只取 5 条，比例约 **606:1**。
    - 已装入的 5 条中，**同一枢纽节点占 3 条**，4/5 经核实并非真正跨社区；经人工判断**仅 1/5（20%）值得 agent 注意**。
  - **因此契约必须写明：不读 `surprises` 字段，改为按任务路径先过滤候选边再取前 20–30 条**（规则可机械执行，无需人判断）：先按任务涉及的路径前缀筛出有端点的边，再打分排序取前若干；过滤后为空、或所有条共享同一端点标签时，视为无信号并停止。
  - **容量事实（必须写入契约，防上下文爆炸）**：`.graphify_analysis.json` 中 `communities` 占 **89.4%（811 KB）**；只提取 `surprises`/`questions`/`gods` 三项（合计约 **5.3 KB**），**绝不整份读取**。
  - **`gods` 与 `questions` 可用**：`gods` 10 条（`id`/`label`/`degree`）；`questions` 7 条（`type`/`question`/`why`），含低置信度边、桥接节点、孤立节点提示；`questions` 中的 `bridge_node` 条目会把约 90 个社区名内联进 `question` 字段（约 700 字符），同样须按需截取。
  - **社区名确认无用**：705/705 为 `Community <int>` 占位，且分析文件中**没有** id→名字的映射（`communities` 只有 社区号 → 节点 id 列表）。因此 `why` 里「bridges separate communities」**不可审计**——无法说出具体桥接了哪两个子系统。
- **调研效果的验证方法（用户 2026-10-15 确定，已具体化）**：用**真实历史任务做对照**，不立量化指标。**已选定 3 个历史任务**（用户 2026-10-15：三个都做，用多个任务检查效果更精准）：
  1. `specs/archive/design-execution-efficiency-20261014/`
  2. `specs/archive/requirements-completeness-audit-20260804/`
  3. `specs/archive/governance-runtime-execution-chain-20260827/`
  - **执行方式**：由**子代理**执行（用户 2026-10-15 指定），每个任务产出成对的「有图谱内部调研」与「无图谱内部调研」。
  - **四步流程**（每个历史任务一遍）：① 取该任务当时的原始需求（`decision-log.md` 的 `## 原始需求` 节）→ ② **甲：有图谱调研**，在当前工作树跑一次内部调研 → ③ **乙：无图谱调研**，在**基线 commit `c5c5bdb8`**（实测确认该 commit 上不存在 `graphify-out/`）上跑同一次调研 → ④ 对照两份结果，判断哪份对「接着做这个任务」更有帮助。
  - **忠实性前提（必须遵守，否则对比无效）**：乙侧必须在基线 commit 上运行，或在临时移走 `graphify-out/` 的状态下运行；不得在同一棵有图的树里要求 agent「装作没有图」。
  - **产出与落点**：每个任务一份成对调研记录 + 对比结论，落在任务库 `quality/evidence/graph-value-ab/`。
  - **判定方式**：对照结论由人（用户）判断采纳，不由执行者自判。
  - **副产品**：第 ① 步会重写一遍该任务的原始需求节；若重写结果比原记录更准，这本身即「图有用」的直接证据（它读到了当时读不到的历史关联）。
  - **成本提示（如实保留）**：6 次调研（3 任务 × 有图/无图）会消耗可观 token，其中乙侧每次都要在基线 commit 上重新定位项目状态；须在实施前先估一轮并告知用户。
- **内部调研的具体查法（主会话依 M5 的上下文纪律与用户「发现意外关联」的要求推导确定，2026-10-15）**：
  - **执行者**：由**子代理**执行（M5 已定：散文输出不进主上下文）。子代理只回「结论 + 来源文件路径」，主会话可按需回原文核对。
  - **三步，全部 0 token，顺序固定**：
    1. `query "<本次任务的调研问题>"` —— 取与当前任务相关的子图（自然语言入口，BFS）。
    2. `god-nodes --json` —— 取枢纽节点，用于判断「本次改动是否落在高度连接处」。
    3. **按任务路径筛边取意外关联**（不用图自带的 `surprises` 字段，理由见上）：按本次任务涉及的路径前缀筛出有端点的边，再取前 20–30 条；过滤后为空、或所有条共享同一端点标签时，视为无信号并停止。
  - **查询次数**：不设固定次数；以「调研问题是否已被回答」为准，子代理须在结论里写明实际跑了哪几条查询，使该次调研可复核。
  - **产出去向**：结论写入该次内部调研的记录（落点见下），由 deep-research 的 canonical report 承载；`decision-log.md` 主文只留结论与唯一原件指针（沿用现有 research 落点约定，不新增对象）。

### M2 build-prd / build-plan 知识消费 — 已收敛

- **已收敛（用户 2026-10-15）**：查到的知识**只落结论进 `spec.md` / `phases/P<n>.md`，不单独保存查询记录**；不新增中间产物。
  - 代价（如实保留）：事后无法回看「当时图说了什么」，AC-002 的因果案例举证只能靠产出文本本身。
- **已收敛（主会话 2026-10-15，套用 M1 查法模式）**：每个阶段固定问图三类问题：
  1. **「这个领域现在由哪些模块负责」** —— 用于界定 prd/spec 的范围与非目标，避免把已有能力再设计一遍。
  2. **「历史上关于这类问题做过哪些决定」** —— 用于继承已有取舍、避免推翻已定结论（查 `specs/archive/` 的历史决定）。
  3. **「这类改动以前踩过什么坑」** —— 用于在 Phase 切分里预留风险位。
  - 由子代理执行，只回结论 + 来源路径；实际查询须在结论里写明以便复核。
- **已收敛（用户 2026-10-15）**：图**不覆盖 JSON 类文件**（`move-map.json`、5 个契约 schema、全部 `steps.json`）这一缺口的处置**推迟**——先由 M6 查清「JSON 为什么进不了图（是策略还是 bug）」，再决定是「写明边界并回退读文件」还是「把关键 JSON 抽进图」。**在查清前，涉及契约/schema 的设计必须直接读文件。**

### M3 build-code 先查后读 — 已收敛

- **已收敛（用户 2026-10-15）**：同 M2，只落结论进代码与 Phase 材料，不保存查询记录。
- **已收敛（用户 2026-10-15）**：写代码前**固定三步**，全部 0 token：
  1. `affected "<目标符号>"` —— 查改动的**波及面**（谁会被影响）。
  2. `explain "<目标符号>"` —— 查**现有实现长什么样**，避免重造轮子。
  3. `path "<A>" "<B>"` —— 遇到「两个模块怎么协作」时查**连接路径**。
  - 依据：这正对应用户原话「避免胡乱写代码」；三步都是本地图遍历，不花 token。
  - 代价（如实保留）：子任务很小时这三步可能是多余开销；契约应允许在「目标符号不存在于图中」时如实跳过并记录原因，而不是硬套三步。
  - 注意：`affected` 与 `path` 对**不存在于图中的名字**会以退出码 4（无匹配）或 3（歧义）结束，契约须覆盖这两种退出事实，不得当作失败。

### M4 verify-code 核对与收口更新 — 已收敛

- **收口更新时点（用户 2026-10-15）**：**在任务分支的 worktree 内更新图，随任务一起提交**进 PR/合并。不采用「合并后在 main 上再更新」——那会多一步人为动作且容易遗忘。
  - 依据 ADR-012：图随 git 走；语义缓存按内容哈希命名，随分支传递到 main 后可直接复用，不需要单独维护 main 的缓存。
- **收口必须分别报告两项事实**：代码图（`graphify update`，实测免费、只处理代码）与文档图（需宿主会话语义抽取，`update` 对它**完全无操作且退出码 0**）。禁止只跑 `update` 就声称「图已更新」（ADR-006）。
- **「符合标准」具体核什么（主会话 2026-10-15 确定，原为空白）**：核**两项**，都用 0 token 查询：
  1. **实现是否落在本次 spec/Phase 声明的范围与写集内** —— 用 `affected "<改动涉及的符号>"` 反向遍历，检查是否有声明之外的调用方被影响而未被声明（这正是你们「声明写集 vs `git diff` 对账」的图侧补充轴）。
  2. **是否存在同类实现的既有约定未被遵循** —— 用 `query "这类功能在本项目里已有哪些实现"`，检查是否重复造轮子或偏离既有做法。
  - 手段是 `affected`（波及面）与 `query`（同类实现）两种；由子代理执行、只回结论 + 来源路径。
  - **边界（重申 ADR-005）**：图只作**补充轴**，**不替代** OCR 独立审查与 wh-review，**不新增审查点**；图查不出结论时如实记，不当作通过。
- **陈旧度怎么报告（2026-10-15 定，原为空白 OI-003）**：契约要求每次把图用作依据时，**随结论带出两件事**：
  1. **图的覆盖年龄**——图的构建时间与「当前代码/文档版本」的关系（比 HEAD 旧多少个提交，或树内有未提交改动）。**只报事实，不设阈值、不做门**：旧图照用，只让读者知道它有多旧。
  2. **本次结论落在图的哪一层**——来自代码层（AST）还是文档层（语义），以及该层是否刚刚重建/更新过。
  - 依据：用户明确不要推测性检查；`CONSTITUTION.md:70,73` 要求缺数据保持 unknown 而非制造结论。因此不发明「新鲜度分数」，只报可观察事实。
- **收口更新的执行细节（2026-10-15 补充，原为空白）**：
  1. 先在任务分支内跑 `graphify update`（免费、仅代码），**读回其真实退出码**；退出码 1 表示「无事可做」，须与真实失败区分开，不得当作失败也不得当作已更新。
  2. 再按 M1 的询问规则处理文档图：**问用户**，说明只重抽本次改动过的文档及预计份数；用户同意才跑宿主会话语义抽取。
  3. 两项事实**分别报告**：代码图（已更新/无事可做/失败 + 退出码）与文档图（已更新/未更新 + 原因）。
  4. 图的变化按 ADR-014 **单列为一项非源码改动**，不计入功能写集。

- **已完成判定（用户 2026-10-15 定，取代原「归 Phase 1」的笼统表述）**：

    - **「便宜」的边界（主会话必须说清的坑）**：图、`manifest.json` 与语义缓存三者靠**内容哈希**对应；**直接手改 `graph.json` 会使三者失配**，后续 `update` 可能误判。因此「便宜」只能是「对少数受影响文件走正常流程重抽」（0 到几笔小额），**不包括手改产物**。手改只允许用于**完全不参与哈希对应的孤儿数据**（如 50 个无来源节点中的孤立项），且须逐项说明为何不会破坏对应关系。

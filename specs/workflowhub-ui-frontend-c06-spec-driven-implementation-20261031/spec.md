# 功能规格：C06 规范驱动的前端实现与执行控制

本文件写给后续 Phase 作者、开发、独立测试、独立审查与最终验收者。
它规定产品行为、用户旅程、状态异常和唯一验收判据。
全局代码锚点在真实调研后补入同一文件，不以猜测代替源码事实。

> 写作标准：`skills/material-writing/SKILL.md` 的「材料写作标准（唯一）」。
> 锁定例外：`## 实现设计（全局权威）` 及其四个小节名保持原词。
> 产品目标来自原 PRD，方向与取舍来自当前决策日志。
> 本文件不替换这两份来源，也不把草稿保存写成验收通过。

## 这是什么，给谁用？

这是 WorkflowHub 的可复用前端实现能力，以及支撑它可信执行的成本与长跑控制。
使用者是前端维护者、阶段主会话、计划作者、开发、独立测试和独立审查者。
PaperBuilder 的业务日志时间筛选只是验证载体，不是本任务交付的产品。

- **功能名**：规范驱动的前端实现与执行控制。
- **主要路径**：React/Next.js；其它技术栈只消费适用规则。
- **状态**：产品规格草稿；尚未实施，也未取得计划确认。
- **来源**：原 PRD 的 C06 卡与当前决策日志的十五项需求。

## 一页看懂：谁要什么结果，怎么算通过？

维护者要一条能判断、能实现、能检查、能审查并能有界停止的真实能力链。
阶段主会话还要知道当前只做什么、验收花多久、长跑何时停以及证据如何保留。

- 真实页面改动先判断适用性与就绪度，再按真实规范、组件和布局实现。
- 类型、样式、定向测试和构建体积各有证据，静态结果不冒充浏览器事实。
- 独立代码审查读取真实差异和消费者，发现修根因并定向复验。
- 固定外部规则完整落地并保留来源，许可偏差不被写成合规。
- 当前步骤卡、验收预算和长跑控制复用现有流程，不新增流程权威。
- 九条验收在各自交付 Phase 首判，只在 Phase 7 逐条末验。
- 验收二与验收六最高只能记部分；验收五的浏览器运行面保持未知。

最大影响面是现有前端质量方法、三个主阶段的方法与步骤合同、执行命令接口、
外部规则包，以及 PaperBuilder 新分支中的一个小页面切片。
显式排除见决策日志「这次覆盖什么，排除什么？」，本规格不恢复已退出方向。

## 为什么做，给谁用？

现有方法需要证明能在真实消费者上完成工程实现，而不是只产生规则和文件。
长时间执行与验收成本也需要可观察的边界，避免无效等待、重复采集和临时改判据。

### 前端维护者为什么需要这条能力链？

真实前端任务常同时涉及规范缺口、组件复用、状态、样式、性能和审查。
只检查页面外观或只运行窄规则，不能证明实现可维护。
本任务把触发、就绪、实现、检查和优化审查连成一条可回读路径。

### 计划与实施作者为什么需要先判断就绪？

规范、资产或设计输入不足时，直接写代码会把猜测变成项目标准。
就绪记录要说明来源、缺口、补法、知会者、消费者和处置。
能依据已确认来源推导的缺口补最小条款，不能推导的只停受影响路径。

### 独立测试与审查者为什么需要分层证据？

类型、样式和文档状态测试能证明代码级行为，却不能证明真实 Tab 顺序或视觉焦点。
独立代码审查也不能被同源补充、空发现或工具成功退出替代。
每层证据必须保留自己的覆盖限制、原始失败和未测项。

### 阶段主会话为什么需要当前步骤与停止边界？

全阶段材料同时展开会诱发跳步、旧证据误用和无新事实的重复尝试。
当前步骤卡只投影既有步骤合同，成本与停止规则只约束执行，不制造新门。
审查提供者的不可用和长等待继续服从既有审查方法，不套通用重试规则。

### 背景是什么？

原 PRD 要求 C06 交付规范驱动实现、完整固定规则、工程检查和独立代码审查。
用户随后明确能力交付优先，并选定 PaperBuilder 时区回显作为真实验证任务。
用户又追加全阶段防跳步、验收成本和长跑控制，要求九包一次设计。

## 用户怎样走完这条能力链？

四段旅程共用同一份真实任务材料，但各自留下不同的可观察结果。
任何一段缺证据都只影响对应判定，不把其它段落自动判为失败或通过。

### 旅程一：计划作者怎样判断该不该做、能否开工？

计划作者读取真实页面、组件、样式改动及其消费者，先判断前端能力是否适用。
纯后端、纯文档或无真实消费者的样例记不适用及原因，不建立空就绪记录。
适用时，实现者逐项核八类规范、四类资产、设计输入和检查命令。

输出是带四种处置的就绪短表，以及至少一条真实的规范补充判断。
找不到来源不等于来源不存在；无依据的关键缺口交用户或设计负责人。
消费者是后续实现者与独立审查者，证据是真实短表和规范消费点。

### 旅程二：实现者怎样完成并证明一个小页面改动？

实现者从 PaperBuilder 指定基线建立独立工作树，不动用户现有脏工作树。
主仓规范文件也有脏改动时，只以 HEAD 对象为基线，不把未提交内容当约定。
实现前补时区条款，实现中复用现有页面结构、视图模型和状态映射。

页面以浏览器本地时间回显并明确标注，本地输入提交为 UTC。
筛选采用显式“查询”按钮：对象、结果、关键词、事件类型、动作与时间输入先形成草稿，点“查询”后一起应用；
列表、计数、空态和错误摘要随应用更新，非法草稿保留上次已应用查询。
实现后统一运行类型、定向、样式和构建检查，再交独立审查。
发现回原实现者修根因，只复验受影响文件或用例，不反改冻结判据。

### 旅程三：维护者怎样引入并消费固定外部规则？

维护者按固定提交完整落地三个选定的规则包，并逐文件记录哈希与上游身份。
现有打包产物必须能按需读到规则，二十一行摘要不能继续充当完整规则源。
其它外部包按真实条件处置，不为数量完整而复制无消费者内容。

现有本地重建许可文本保留，不新增许可证文件。
上游许可未核实与历史路径裁决保持可见，本任务不宣称再分发合规。
正式发布包读取属于后续发布任务，本任务只读现有打包产物。

### 旅程四：阶段主会话怎样控制步骤、成本与长跑？

主会话读取当前步骤卡，只取当步所需路径和证据，再执行对应自查。
跳过必须留下原因、负责人和恢复条件，阶段收口必须消费未清缺口。
计划作者在活动执行时间上核算验收成本，用户等待单独列出。

执行中优先复用现有命令捕获、取消和进程组能力。
心跳只证明执行单元仍存活，不证明工作有进展。
空心跳、同签名失败、超时、审批等待和证据采集各有独立停止或升级信号。

## 做成什么样？

九条验收分别覆盖能力、外部来源、工程检查、审查、代码级行为和执行控制。
正文只说明场景与落点，唯一通过和失败判据集中在 Appendix A。

首判在 Phase 6，末验在 Phase 7；判据见 Appendix A 的验收 1。

### 验收 6：内部接口改动是否说清消费者与证明边界？

### 验收 8：验收成本是否能算清、拆分并交用户确认？

首判在 Phase 2，末验在 Phase 7；阈值校准则前均为临时值。

### 验收 9：长跑是否能停、能回收、能冻结并保留证据身份？

场景 10 结合只读回放、空心跳负例和一个有界真实进程组测试。
首判在 Phase 3，末验在 Phase 7；不重跑历史业务任务。

## 系统要处理哪些状态与异常？

状态处理先保护已确认判据和原始失败，再恢复对应责任路径。
下述状态均归入十个场景，机器编号见 Appendix B。

### 默认、加载与不适用怎样区分？

纯后端、纯文档、无消费者或非 React 任务只加载适用规则，并写明理由。
前端页面已有数据时使用现有视图状态，不因新增视图模型复制第二份状态。
加载、空结果和非就绪映射继续由现有状态所有者负责。

### 就绪缺口怎样分流？

影响本次差异且能由已确认决定、设计源、测试或平台语义推导的缺口先补最小条款。
不影响本次差异的缺口记录知会者、影响和复核点后继续。
不能推导的关键缺口停受影响路径，其余安全工作继续。

### 时间输入的边界与错误怎样表现？

空值保持空筛选，非法值和旧链接中的无法解释值给出可见错误。
开始时间晚于结束时间时，错误容器使用 `role=alert`，相关输入标 `aria-invalid`。
焦点移到首个非法输入；夏令时跳时拒绝，回拨选择较早时刻。

单端筛选保留另一端条件，快速连续筛选不丢失最后输入。
重复提交不制造额外业务动作，筛选条件变化时按现有合同重置分页。
非法或未完成输入不能静默转成另一个时间。

### 外部来源与许可异常怎样保留？

固定源缺文件、摘要比拼不完整或打包读取失败时，验收二对应闭包失败。
上游许可未知和历史路径未裁决时，结论保持部分，不扩成合规声明。
未触发的外包只记录条件未满足，不把未采用写成质量失败。

### 审查与工具失败怎样恢复？

审查提供者不可用时保留原始失败和覆盖限制，不换执行者冒通过。
同源补充与独立审查分开记录，空发现不证明审查曾执行。
类型、样式或测试工具报错时先修工具或输入，不能以退出成功替代目标断言。

通用命令的三十与九十分钟超时、同失败两轮停止，不改写审查提供者规则。
审查经纪的墙钟取消仍由既有审查方法处理，明确排除在通用回收验证外。

### 步骤跳过与旧证据怎样处理？

当前步骤卡只显示当前步和必要前置，旧目录或旧运行文件不能证明本步完成。
显式跳过必须有原因、负责人和恢复条件，阶段收口把未清缺口记为未完成。
检查器仍只报告并保持既有退出语义，不接成通用阻断门。

### 成本超限与审批等待怎样处理？

软上限触发拆分或砍减验收设计，硬上限触发真实确认与根因记录。
预算只累计活动执行时间，用户等待、审查等待和真实环境等待分别列出。
审批等待十五分钟无答复只停对应路径并保留现场，不自动批准。

一百二十与二百四十分钟均是临时 Phase 软、硬上限。
历史回放与两个代表性阶段校准后，才由用户确认是否调整。

### 长跑、空心跳与同签名失败怎样处理？

现有命令捕获接口负责超时、取消和进程组终止，本任务不另写看门狗。
超时或非可重试错误先停对应路径，同失败签名连续两轮无新事实也停止。
第三轮只有取得新证据或既定批准才能继续，不机械禁止有根因的新尝试。

历史记录中，050 与 060 属同签名停止点。
074 前已出现高频身份回调导致全文件哈希的新根因，只能凭新证据或批准继续。
心跳没有阶段、预计完成时间或新工作事实时是空心跳，不能据此续命。

### 证据重复与不同事实怎样处理？

同一次运行的同字节原件复用存储，并保留全部来源、时间、步骤和消费者。
不同哈希代表不同事实，不能为达到份数目标删除或合并。
先禁止或减少无必要的重复采集，只对既有规则允许的三类真实原件事由留字节。

历史任务五十一份预镜像是五十一个不同精确字节哈希，重复组为零。
因此不能把内容寻址去重写成不超过三份的结果，也不能据此否认原始事实。

## 功能需求是什么？

十五项功能需求共同交付一条能力链，不按工作包机械拆成九份产品。
每项的消费者、场景、事实、来源与验收绑定集中在 Appendix B。

### 功能需求 1：触发与就绪判断

计划作者和实现者必须先判断适用性，再记录真实输入、缺口和处置。
失败是打勾代替判断、把未找到当不存在或让实现者猜设计值。
消费者是后续实现与审查，证据是真实就绪记录和适用反例。

### 功能需求 2：规范驱动的真实实现

实现者按已确认设计、组件、布局、类型和样式归属完成小切片。
React 四维贯穿组件化、统一性、可维护性和性能，非 React 不套专属规则。
失败是无来源新增、同名重造或全页重构，证据是真实差异与消费点。

### 功能需求 3：工程检查的时机与分档

实现完成后、独立审查前统一运行类型、定向、样式和构建检查。
新增与目标文件从严，存量问题警告并具名处置，不做全仓扫修。
失败是工具错误冒通过或静态结果冒浏览器事实。

### 功能需求 4：独立审查与根因修复

独立审查读取真实差异、测试、规范和验收承接，同源补充另行记录。
发现回原实现者修根因，修后只复跑受影响面。
失败是换执行者、改判据吞失败或只修表象。

### 功能需求 5：完整固定外部规则闭包

维护者完整落地选定三包，保存逐文件哈希、上游身份和现有打包消费。
二十一行摘要只保留历史身份，不能再当规则源。
失败是子集、镜像或安装目录冒完整官方固定源。

### 功能需求 6：可证伪的样式检查

样式规则必须对重复选择器和无据 `!important` 报出文件、行、列。
合法样例与有理由的局部例外不得误报，新增和存量分档必须真实执行。
失败是只写配置、只留规则数量或工具报错后宣称通过。

### 功能需求 7：真实消费者与组件质量地图

实现和审查都要定位直接、间接与未知消费者，以及状态和样式所有者。
现有窄检查不能冒充完整抽象语法树或消费者扫描。
失败是把搜索零命中当零消费者，或只读样例不读真实使用点。

### 功能需求 8：代码级质量与浏览器边界

定向测试必须覆盖关键类型、视图模型、错误、焦点、状态与时间往返。
构建体积记录前后字节并解释增长，没有预算不自造性能阈值。
真实浏览器、视觉、无障碍与交互耗时保持未知并具名承接。

### 功能需求 9：接口改动的消费者影响

内部重复映射合并要证明等价，并列直接、间接、未知消费者与风险。
公开接口删除不在本次范围，不能用内部重构冒充删除侧完整验证。
失败是忽略已知不一致或把未知消费者写成零。

### 功能需求 10：所用原能力的维护责任

每个采用包记录固定版本、上游入口、维护者、维护触发和适配差异。
查新失败保持未知，不自动追随最新提交，也不新增后台监控。
失败是只复制文件而没有维护与真实消费责任。

### 功能需求 11：真实 PaperBuilder 验证切片

业务日志时间筛选显示浏览器本地时间并明确标注，提交转换为 UTC。
时间输入先形成草稿，点“查询”后才更新列表、计数与空态；非法草稿不得替换上次有效查询。
视图模型复用现有状态来源，重复非就绪映射合并且不新增公共接口。
失败是只改显示、不改规范，或把验证页面当成全部能力交付。

### 功能需求 12：全阶段当前步骤卡

三个主阶段只从既有步骤合同投影当前步、入停条件、最多三个路径和证据。
按步检查、显式跳过、旧证据负例和阶段收口缺口必须可回放。
失败是新增步骤账本、通用门或让旧文件证明当前步骤。

### 功能需求 13：验收成本与 Phase 预算

每条验收记录执行者、估算、硬上限、资源、观察、重试上限和证据档。
Phase 按活动执行时间汇总串行、并行、共享准备和重试预留，用户等待单列。
超软上限拆或砍，超硬上限交用户确认并保留根因，不设机器预算门。

### 功能需求 14：有界执行与真实进程回收

执行复用现有命令捕获的超时、取消信号和 POSIX 进程组能力。
不可重试失败第一次停止，同签名两轮无新事实停止，空心跳不能续命。
宿主必须能终止真实进程组；无回收能力时记不可用，不新写看门狗。

### 功能需求 15：判据冻结与证据身份

实现开始后冻结验收判据与门禁命令，合法缺陷修复仍可继续。
变更必须提交成本影响、独立审查与重新确认，不能靠改命令换绿。
证据以内容哈希复用同字节，同时保留运行、步骤、原件和时间身份。

## 打算怎么做？

方案复用现有前端质量方法、工作流、审查链和命令执行接口。
只有真实缺口才做窄扩展，不建立第二技能、状态机、账本或规范权威。

### 方案 1：用五道判断串起真实实现

现有构建计划负责触发，前端质量方法负责就绪，构建执行负责实现和检查。
现有审查方法负责优化与独立代码审查，真实 PaperBuilder 差异负责证明消费。
无预算或实测时不做性能优化，只记录测量与未知。

### 方案 2：用窄检查与分层测试代替新平台

样式检查只覆盖已确认规则与正负例，类型和文档状态测试覆盖代码级行为。
构建体积只做前后测量，浏览器运行面不借静态证据补齐。
消费者未知保持未知，不为安心建设通用扫描平台。

### 方案 3：用现有步骤与预算材料承接执行控制

步骤卡是只读投影，验收成本进入现有规格和 Phase 卡。
活动执行预算、用户等待和审查等待分开计量，停止不等于产品失败。
缺口由阶段收口消费，不把检查器退出码改成新门。

### 方案 4：复用现有命令捕获，不新增回收器

`runtime/interface/run-command.mjs` 的 `captureCommand` 已提供超时与取消输入。
上游补充调研还定位了 POSIX detached 进程组、超时取消终止和退出 124/130。
任务句柄已暴露这些能力，Phase 3 应接现有接口并验证，不另写平行机制。

心跳只承担存活信号，阶段进展必须由新工作事实和预计完成信息证明。
审查经纪的墙钟取消不在这次通用命令回收改动内。
若真实接口与补充调研不符，回 Phase 3 开发修复，不扩展新控制面。

### 方案边界：哪些简化已经成立？

就绪短表直接由现有前端质量方法消费，因此不新增窄校验器。
步骤与成本直接写现有材料，因此不新增预算对象或步骤游标。
命令取消已有实现，因此不新增看门狗、回收器或审查重试策略。

## 谁先谁后？

七个 Phase 一次覆盖九包，先建立执行与成本边界，再做外部和真实页面验证。
每个交付 Phase 先首判自己的验收，Phase 7 是唯一末全验收。

- Phase 1：执行卡与材料精简，首判验收 7。
- Phase 2：验收成本、预算与历史计划回放，首判验收 8。
- Phase 3：长跑控制、判据冻结与证据身份，首判验收 9。
- Phase 4：触发、就绪与实现方法，只做 PaperBuilder HEAD 只读盘点。
- Phase 5：外部规则闭包与现有打包消费，首判验收 2。
- Phase 6：PaperBuilder 完整纵切，首判验收 1、3、4、5、6。
- Phase 7：只读汇聚全部首判原件，逐条末验九条验收并交接缺口。

Phase 4 的就绪记录和受控走查只读 PaperBuilder HEAD，不写生产代码或规范。
Phase 5 的打包清单同时登记 Phase 4 新增参考文件。
Phase 6 在同一新工作树中先补最小时区条款，再改代码、测试与锁文件。
审查方法可包含实现方法，不另建第二个方法权威。

各 AC 估算含共享任务，不能简单相加为 Phase 或整卡总额。
Phase 作者必须按串行和、并行最大值、共享准备与重试预留重算。
Phase 6 分别列便宜可证与真实环境两段，展示实际总额。
超过临时硬上限时取得真实确认，不删判据、伪报分钟或挪首判到 Phase 7。

### 接口与失败语义

产品边界由就绪记录、真实视图状态、步骤投影、成本字段和证据身份组成。
这些接口都进入现有材料或执行入口，不形成新的持久对象图。

- **就绪记录**：项、来源、状态、补法或知会者、消费者、处置。
- **处置词**：继续、带缺口继续、补充、停受影响路径；机器词沿决策日志。
- **步骤接口**：现有检查器增加当前卡与按步读取，不新增运行状态。
- **成本接口**：每条验收七字段，Phase 汇总活动执行预算并单列用户等待。
- **预算边界**：预算留在规格与 Phase 卡，不写入 facts 或新增持久对象。
- **执行接口**：复用 `captureCommand` 的超时、取消与进程组语义。
- **证据接口**：内容哈希只复用存储，运行与步骤身份证明当前性。
- **页面接口**：复用现有视图模型与状态来源，不新增公共 API。
- **公开签名**：`BusinessLogPageLoader`、`BusinessLogViewProps`、`BusinessLogView`、
  `Page`、`businessLogQueryForSearch` 保持；`reviewTierFor` 等保护接口不改。
- **依赖边界**：样式依赖、配置、脚本与 `frontend/pnpm-lock.yaml` 同步变化。

缺输入先区分可推导、非阻塞和不可推导，失败只停受影响路径。
超时、权限、非法输入、工具错误、产品缺陷和预算停止分别记录。
通用两轮停止不限制有新根因的合法修复，也不变成审查提供者重试策略。
审查提供者不可用、长等待与经纪墙钟取消继续服从原审查方法。

全局写边界沿用决策日志，并补充 PaperBuilder 锁文件。
共享文件按真实前后写者串行，外部历史架构记录只提案不代裁决。
禁止范围、已退役方向和发布排除不在本规格中重新开放。

## 有什么风险和未决？

主要风险是把局部证据放大成完整能力，以及用新控制规则掩盖旧失败。
每项风险都有触发、后果、处置和验证，未决项仍在前面保留负责人。

### 风险 1：五道判断退化成打勾

触发是短表没有来源、消费者或真实补充判断，后果是能力空转。
Phase 4 与 Phase 6 用真实时区缺口和独立走查缓解，验收 1 逐道核决定。

### 风险 2：样式检查误报或漏报

触发是 Tailwind 语法、合法例外或目标与存量分档不清。
Phase 6 用正负例和位置输出验证，工具错误回原实现者修配置或输入。

### 风险 3：许可或历史路径偏差被写成合规完成

触发是把本地重建文本当上游许可，或未经裁决迁移历史件。
Phase 5 保留偏差并停相关声明，验收 2 最高记部分，再分发前重裁。

### 风险 4：审查提供者失败被换成假绿

触发是提供者不可用后换执行者、只留同源补充或把空发现当通过。
独立审查者保留原失败，验收 4 不通过；恢复条件是原路径取得有效原件。

### 风险 5：代码级结果被冒成浏览器质量

触发是用文档状态焦点、样式检查或截图代替真实 Tab 与视觉观察。
Phase 6 只报告代码级事实，未知项交后续运行负责人，验收 5 分开记录。

### 风险 6：跨仓基线或锁文件漂移污染证据

触发是带入脏工作树、漏改锁文件或规范基线取未提交内容。
Phase 6 先核 HEAD、工作树和写集，失败回原实施者恢复干净基线。

### 风险 7：步骤卡变成新门或旧证据复用

触发是卡接退出门、目录文件直接证明当前步或跳过没有缺口。
Phase 1 用负例回放验证，阶段收口消费缺口但不改检查器退出语义。

### 风险 8：预算口径误停或放行

触发是把用户等待算活动执行、超硬上限不确认或临时阈值当定稿。
Phase 2 分列时间口径并校准，超硬上限保留根因与用户真实选择。

### 风险 9：心跳或回收规则造成假进展与失控

触发是空心跳续命、宿主不能终止进程组或另写平行看门狗。
Phase 3 用空心跳负例和真实回收测试验证，无能力记不可用并停该路径。

### 风险 10：历史回放与证据去重被误读

触发是把回放当真实重跑，或把不同哈希删除来凑份数。
Phase 2 与 Phase 3 只读原件并保留全部身份，五十一份案例按零重复组判定。

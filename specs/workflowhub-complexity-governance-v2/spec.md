# 功能规格：WorkflowHub 复杂度治理与可靠交付

> 基于已接受的 make-decision 结果。本文件只写产品问题、行为、边界和验收，不锁定代码布局。

- **功能名**：WorkflowHub 复杂度治理与可靠交付
- **来源**：已接受的 workflowhub-complexity-governance-v2 决策记录
- **状态**：Accepted — build-spec attempt-0001；build-plan 覆盖审计补齐原方案漏项

## 0. 已批准决策分类

- **Locked**：五阶段边界、当前材料真相、单一材料修订、追加质量事实、派生发布、逐删除证明、垂直删除、质量硬门、旧任务迁移证明后即时退出、双发布单元、测试范围、全文件清单和非阻断复杂度原则。
- **由本规格冻结**：五阶段最小完成谓词、旧任务最小导入格式、Bundle 与 Runner 兼容字段、非阻断数量预算。
- **Upstream unresolved**：无。
- **New ambiguity**：无。物理目录、删除批次和文件级 proof card 属于 build-plan 的执行设计，不改变产品边界。

## 速读卡（30 秒）

- **一句话需求**：在保留五阶段交付质量的前提下，用当前材料和不可变质量事实直接计算结果，删除专用恢复状态机、重复记录和无用发布内容。
- **核心改动点**：
  - 四份当前材料只使用一种统一修订事实，不再依赖 reopen、rebind、continuation、reset 等专用许可。
  - 正式结果由当前材料、当前代码、测试、逐项验收、独立审查、人工确认和不可逆授权派生。
  - 每项删除先完成消费者、质量替代、负测、故障注入、Multica 兼容和回滚证明。
- **最大影响面**：五阶段执行、任务材料修订、正式结果发布、旧任务迁移证明、Multica 分发和测试资产。
- **验收信号**：同一任务可自然修订并继续；五阶段合成任务完整通过；正式写入故障不产生半成品；Skill Bundle 洁净可安装；被删除机制无残留入口。

## 1. 问题与紧迫性

WorkflowHub 为保护交付质量积累了多套 reopen、rebind、continuation、recovery、reset、invalidation 和 trace 修正机制。它们把“允许继续工作”“结果结构正确”“质量足以完成”混成多个互相校验的状态机。真实任务因此经常为了小幅材料修订而修 WorkflowHub 本身，业务交付被工具阻塞。

冻结代码树按 Git tracked 且文件名严格匹配正式测试后缀统计为 135 个文件、34,675 行；另有 4 个测试支持文件、113 行。决策调研中的“约 140 个、34,813 行”使用了更宽的近似集合，不能作为最终口径。数量不是错误本身，但重复状态机使测试大量验证内部历史组合，而不是五阶段用户结果。现在必须先守住质量谓词，再按证据删除复杂机制，否则 WorkflowHub 会继续难以运行和维护。

## 2. 背景、目标与范围

### 背景

WorkflowHub 已有 make-decision、build-spec、build-plan、build-code、verify-code 五个阶段，并已具备 TaskHandle 安全、原子正式写入、新鲜测试、逐项验收、独立审查、严重 finding 处置、人工确认和不可逆授权。Multica 主要消费 Stage 和 Skill，不应携带开发测试、历史任务或本机依赖目录。

### 目标

- 保留五阶段外部边界和全部核心质量语义。
- 让材料修订成为普通操作，而不是创建新的流程状态。
- 让正式结果从当前事实确定性派生，派生视图可重建且不成为第二真相。
- 逐垂直切片删除无消费者、已被替代的专用机制和对应测试。
- 将测试重点收敛到五阶段结果、负路径、故障注入、旧任务迁移 fixture 和 Multica 安装。
- 建立稳定目录职责和依赖方向，阻止复杂度再次增长。

### 范围内

- 四份任务材料的统一修订和并发冲突处理。
- 工作资格、正式写入有效性、完成质量三个独立判断。
- 五阶段正式结果的派生、验证和发布。
- 专用恢复状态族的逐项删除证明与垂直切片清理。
- 旧任务的一次性离线导入证明；迁移脚手架不进入最终产品。
- Skill Bundle 与 Runner Release 的独立分发和兼容检查。
- 全仓文件用途清单、测试分层、非阻断复杂度报告和稳定结构规则。

## 3. 用户场景与状态覆盖

### SCN-001：正常五阶段交付

- **角色**：执行开发任务的用户
- **Given**：原始需求和项目工作区可用
- **When**：依次执行五个阶段
- **Then**：每阶段产生可读取的材料、质量事实、正式结果和下游交接，最终结果绑定同一当前代码快照

### SCN-002：同任务材料修订

- **角色**：任务执行者
- **Given**：四份材料已有历史版本或阶段结果
- **When**：修改任一当前材料并发布统一修订
- **Then**：历史只读保留，受影响证据变旧，但工作可继续，不需要任何专用 reopen、rebind、continuation 或 recovery

### SCN-003：并发修订和中断重跑

- **角色**：两个并发执行者
- **Given**：两者基于同一当前修订
- **When**：同时发布修改，或一次写入在任一正式写入边界中断后重跑
- **Then**：只有一个并发写入成功；失败者得到明确冲突；重跑幂等；当前指针始终指向完整旧值或完整新值

### SCN-004：证据失鲜与正式发布

- **角色**：继续开发和准备发布的执行者
- **Given**：材料或代码已变化，旧测试、审查或逐项验收仍可读
- **When**：继续工作或请求正式完成
- **Then**：继续工作不被旧事实阻止；正式完成只接受与当前依赖一致的新鲜质量事实，并列出缺失项

### SCN-005：独立审查不可用或存在严重 finding

- **角色**：审查者和任务所有者
- **Given**：所需独立审查不可用，或原始 verdict 含严重 finding
- **When**：任务继续修复并再次请求正式完成
- **Then**：不可用和原始 verdict 永久可见；所需审查不可用不能宣称完成；严重 finding 必须有绑定当前修订的验证处置或明确风险授权

### SCN-006：删除候选机制

- **角色**：WorkflowHub 维护者
- **Given**：某个专用状态、命令、记录族或测试被提议删除
- **When**：评估真实消费者、质量语义替代、删除前后负测、故障注入、Multica 兼容和回滚
- **Then**：证明完整才允许按垂直切片删除；任一证明缺失即保留

### SCN-007：旧任务迁移证明与即时退出

- **角色**：WorkflowHub 维护者
- **Given**：冻结的受支持与不支持旧格式 fixture
- **When**：临时 importer 执行内容保留、幂等和拒绝测试并固化证据
- **Then**：内容、哈希和不可变质量事实不丢失；重复导入结果一致；不支持形状明确失败；随后在同一任务内删除 reader、importer、schema、fixture 和全部公开入口

### SCN-008：Multica 干净安装

- **角色**：Multica 使用者
- **Given**：只有 Skill Bundle 和声明兼容的 Runner Release
- **When**：在干净目标中安装并执行五阶段任务
- **Then**：Stage、Skill 和审查依赖闭包完整；Bundle 不含测试、依赖安装目录、历史任务或本机绝对路径；缺少兼容 Runner 时不得写正式结果

### SCN-009：完整文件治理

- **角色**：仓库维护者
- **Given**：冻结的当前代码树
- **When**：生成全量 tracked-file 清单并评估每个文件
- **Then**：每个文件恰好归入保留、移动、合并、删除、生成、归档之一；删除项全部绑定删除证明；无未分类和孤儿文件

### SCN-010：复杂度指标未达目标

- **角色**：验收者
- **Given**：所有质量硬门通过，但代码量或测试量没有达到期望下降
- **When**：评估交付
- **Then**：如实报告实际值、目标差距、最大热点和后续计划；不得为数字删除必要质量保护，也不得仅因数量持平判定失败

- [x] **空态**：SCN-009 — 无未分类文件才通过

- [x] **加载态**：N/A — 本需求不提供持续加载型界面

- [x] **边界态**：SCN-004、SCN-006、SCN-010

- [x] **竞态**：SCN-003

## 5. 功能需求

### 稳定五阶段与当前材料（FLOW）

五阶段继续承担用户可见的决策、规格、计划、实现和独立验证职责。材料变化是同一任务的普通事实，不再是一套新的流程状态。

- **FR-FLOW-001**：系统必须保留五阶段名称、职责、顺序和既有人工确认边界。
  - **范围边界**：确认不等于合并、推送、关闭、删除等不可逆授权
  - **依据**：PFACT-01、PFACT-03
  - **场景**：SCN-001
  - **验收**：AC-01、AC-09
- **FR-RUN-001**：Runner 对 Workflow 与 Skill 暴露的稳定行为必须收敛为
  `doctor`、`status`、`run`、`review`、`verify`、`confirm`、`authorize`；证据写入和
  内部修复不得继续作为公共命令。
  - **范围边界**：最多允许 8 个公开行为；第 8 个必须有无法由七个既有行为吸收的真实消费者证明
  - **依据**：PFACT-04、PFACT-05
  - **场景**：SCN-001、SCN-006、SCN-008
  - **验收**：AC-01、AC-07、AC-14
- **FR-MAT-001**：系统必须以四份当前材料、当前代码树和统一材料修订作为继续工作的依据；requirements ledger 与 coverage 随同一修订绑定并取消各自独立 current pointer；历史结果不得充当工作许可。
  - **范围边界**：历史内容继续只读保留
  - **依据**：PFACT-02
  - **场景**：SCN-002、SCN-004
  - **验收**：AC-02、AC-04
- **FR-MAT-002**：统一材料修订必须绑定父修订、前后材料身份、变更摘要和来源，并以当前值比较保证并发安全和幂等重跑。
  - **范围边界**：禁止另建材料专用 reopen、rebind、continuation 或 recovery 状态
  - **依据**：PFACT-02
  - **场景**：SCN-002、SCN-003
  - **验收**：AC-02、AC-03

### 质量事实与正式发布（PUB）

继续工作、正式结果结构有效、质量足以完成是三个独立判断。正式结果是当前事实的派生视图，不是第二套工作真相。

- **FR-PUB-001**：正式结果必须由当前材料、当前代码快照、真实 Stage 与 Skill 调用、新鲜测试、逐项验收、独立审查、人工确认和适用的不可逆授权确定性计算。
  - **范围边界**：文件存在、命令成功、provider 退出或旧 accepted 均不能单独构成完成
  - **依据**：PFACT-03
  - **场景**：SCN-001、SCN-004、SCN-005
  - **验收**：AC-01、AC-04、AC-05
- **FR-PUB-002**：正式写入必须 fail-loud、原子、并发安全、可幂等重跑；派生视图可重建，确认、授权和审查等原始事实不可伪造重建。
  - **范围边界**：任何身份、哈希、任务、阶段、代码树或能力错配都立即失败
  - **依据**：PFACT-03
  - **场景**：SCN-003、SCN-004
  - **验收**：AC-03、AC-04

### 五阶段最小完成谓词

以下是不可缩减的正式完成条件；缺项时可以继续修复，但该阶段保持 incomplete：

- **make-decision**：当前 decision-log 覆盖已接受需求、范围、非目标和风险；声明的调研、grill 与独立审查有真实执行或如实不可用事实；方向由用户确认。
- **build-spec**：当前 spec 的需求到场景、FR、AC 可追溯，重大歧义为零；声明的独立规格审查事实存在。
- **build-plan**：当前 plan 与 tasks 覆盖全部 FR、AC、依赖和删除证明安排；计划可执行；声明的独立计划审查事实存在；计划由用户确认。
- **build-code**：当前代码快照上的 tasks 全部完成；风险相关测试与完整测试新鲜；每个 AC 有结果；每个实现阶段及最终集成具有独立审查事实。
- **verify-code**：对当前交付重新执行完整测试；复用同一当前 build 的集成审查；执行独立质量审查；每个 AC 和例外有明确结论；验证结论由用户确认。
- **共同规则**：required independent review 不可用时允许继续修复，但正式完成保持 incomplete；人工确认不等于不可逆授权。

- **FR-REV-001**：原始审查 verdict 必须永久保留；所需审查不可用只允许继续修复，不允许正式完成；严重 finding 必须有验证处置或明确风险授权。
  - **范围边界**：普通材料修订不得为了制造 pass 重跑审查
  - **依据**：PFACT-03
  - **场景**：SCN-005
  - **验收**：AC-05

### 证据驱动删除（DEL）

删除以质量语义等价为前提，不以文件或行数下降为前提。

- **FR-DEL-001**：每个删除候选必须记录真实消费者、保留的质量语义、替代路径、同一删除前后负测、故障注入、Multica 兼容、旧任务影响和回滚依据；缺任一项即保留；实际删除前必须向用户逐项展示删除清单并取得确认。
  - **范围边界**：证明记录使用普通计划和证据字段，不形成新的状态机
  - **依据**：PFACT-04、PFACT-07
  - **场景**：SCN-006
  - **验收**：AC-06、AC-07
- **FR-DEL-002**：已证明可删的机制必须按垂直切片同时移除其公共入口、行为实现、数据契约、样例、专属测试和术语文档，旧入口必须明确不可用。
  - **归零清单**：专用 recovery/reopen/rebind/continuation 命令、stage-transition 权威状态、accepted checkpoint 编辑许可、stage recovery run/source、Grill replacement、Phase trace lineage/supersession、重复事实投影和双写 writer 均为 0
  - **范围边界**：历史读取只允许作为本任务内临时迁移证明；每个切片保留独立 diff、证据和可回退边界，未获关闭授权不得自行提交
  - **依据**：PFACT-04、PFACT-07
  - **场景**：SCN-006
  - **验收**：AC-06、AC-07

### 兼容与分发（DIST）

Skill Bundle 是 Multica 的轻量消费物，Runner Release 是正式执行和记录的受控运行时，两者不混装开发仓内容。

- **FR-LEG-001**：旧任务迁移仅允许使用本任务内的临时离线 importer；必须识别格式、校验身份、幂等且不丢不可变事实，新旧格式禁止双写。
  - **真实任务清单**：迁移前必须只读扫描现有真实 TaskHandle，逐项记录身份、格式、活跃状态和建议处置；每项导入、归档或明确拒绝均须向用户展示并取得确认，active legacy 未归零即 STOP。
  - **最小可接受格式**：唯一 task identity；可用的四材料字节与哈希；requirements ID、ledger 与 coverage；已有测试、逐项验收、review、confirmation、authorization 的原始不可变事实；来源 schema 版本与内容哈希。
  - **明确拒绝形状**：task identity 缺失或冲突；引用或哈希损坏；同一事实出现互相矛盾的 current 选择；事实来源无法识别；导入会要求旧新双写。
  - **导入结果**：产生一个当前材料修订和一组原样不可变事实；相同输入重复导入身份一致。
  - **即时退出**：兼容 reader/importer 仅作为本任务内的迁移脚手架；冻结 fixture 必须证明支持形状无内容丢失、重复导入幂等，坏输入明确失败。证明完成后在同一任务内立即删除 reader/importer/schema/fixture，最终源码、发布包和公开入口中的 legacy 兼容必须为 0
  - **范围边界**：不支持的旧形状明确失败；任一迁移证明失败即 STOP，不得交付脚手架或恢复双写
  - **依据**：PFACT-02
  - **场景**：SCN-007
  - **验收**：AC-08
- **FR-DIST-001**：Skill Bundle 必须包含五阶段及其静态 Skill 和审查依赖闭包，并排除测试、依赖安装目录、历史材料、任务证据和本机绝对路径。
  - **node_modules 合同**：仓库只保留 package manifest、lockfile 和 Node 版本要求；`node_modules` 仅为可删除、可重建的本地缓存，不得被 Git 跟踪、打入 Bundle 或作为审计证据
  - **范围边界**：Bundle 不承担正式结果存储；clean install 不得复用源码仓既有依赖目录
  - **依据**：PFACT-05

  - **验收**：AC-10

  - **Bundle 字段**：runner_contract_major 为正整数；runner_contract_min_minor 为非负整数。
  - **Runner 字段**：runner_contract_major 为正整数；runner_contract_minor 为非负整数。

  - **范围边界**：运行依赖只通过清单和锁定信息声明，不依赖仓内既有安装目录
  - **依据**：PFACT-05

## 6. 模块划分

### 材料修订

- **负责什么**：维护四份当前材料及其单一修订链
- **对外提供什么**：当前材料身份、前后关系、并发冲突和失鲜依据
- **依赖谁**：TaskHandle 的安全读写与身份边界
- **测试边界**：幂等、冲突、中断重跑和篡改检测

### 质量事实

- **负责什么**：追加测试、逐项验收、审查、确认和授权事实
- **对外提供什么**：按引用和身份读取的不可变事实，以及按依赖判断的新鲜度
- **依赖谁**：当前材料与当前代码身份
- **测试边界**：事实不可修改、错绑失败、变化后准确失鲜

### 正式结果

- **负责什么**：计算工作资格、结构有效性和完成质量，并原子发布派生结果
- **对外提供什么**：每阶段当前结果、缺失项和下游交接
- **依赖谁**：材料修订、质量事实、真实 Stage 与 Skill 调用
- **测试边界**：派生一致、故障原子性、并发唯一胜者和可重建性

### 迁移脚手架

- **负责什么**：仅在构建期识别并一次性导入冻结旧格式 fixture
- **对外提供什么**：不可变迁移证据；最终产品不提供 legacy 接口
- **依赖谁**：旧记录身份和新格式写入边界
- **测试边界**：内容不丢、幂等、无双写、不支持形状失败；证明后脚手架归零

### 分发

- **负责什么**：构建 Skill Bundle 并验证 Runner Release 兼容性
- **对外提供什么**：干净的静态 Skill 闭包和正式运行能力声明
- **依赖谁**：五阶段注册、Skill 依赖、审查能力和版本声明
- **测试边界**：干净安装、闭包完整、禁止内容为零、版本错配失败

## 7. 关键实体

- **当前材料修订**：
  - **定义**：四份当前材料在同一时点的不可变身份摘要
  - **字段和约束**：父修订、前后引用与哈希、变化材料、摘要、来源；只追加；比较当前值后发布
  - **关系**：决定质量事实是否新鲜，也是正式结果的材料输入
- **质量事实**：
  - **定义**：测试、逐项验收、独立审查、人工确认或不可逆授权的不可变记录
  - **字段和约束**：类型、主体、依赖身份、结果、来源；不可由调用者伪造完成结论
  - **关系**：被正式结果按当前依赖选择
- **正式结果**：
  - **定义**：某阶段基于当前材料、代码和质量事实计算的派生视图
  - **字段和约束**：阶段、当前身份、满足项、缺失项、状态；原子发布；可重建
  - **关系**：向下游交接，但不授予材料编辑权限
- **删除证明**：
  - **定义**：允许删除一个机制的完整证据集合
  - **字段和约束**：消费者、质量语义、替代、前后负测、故障注入、兼容、旧任务、回滚；缺项即不成立
  - **关系**：绑定文件清单中的删除项和实际垂直切片
- **发布单元**：
  - **定义**：Skill Bundle 或 Runner Release
  - **字段和约束**：Bundle 声明 runner_contract_major 与 runner_contract_min_minor；Runner 声明 runner_contract_major 与 runner_contract_minor；major 相等且 Runner minor 不低于最低值才兼容
  - **关系**：Bundle 声明所需 Runner 接口，Runner 提供正式记录能力

## 8. 数据和生命周期

- **数据粒度**：材料修订代表一次四材料状态；质量事实代表一次不可变观察或授权；正式结果代表一次当前事实计算。
- **数据时效**：材料或代码变化时，只使依赖它们的质量事实失鲜；原始事实和历史结果继续可读。
- **缺失或迟到**：缺失事实作为具体缺口展示；允许继续修复，但不得宣称正式完成。
- **预览与正式**：无兼容 Runner 时可以解释和草拟，必须显著标记为非正式且不得写正式记录。
- **当前与历史**：当前材料由单一修订指针确定；历史只追加；派生结果可重建。
- **归属与清理**：TaskHandle 管理正式任务命名空间；开发测试和依赖安装目录不进入发布单元；旧数据保持原地不改，迁移证明只读输入，最终产品不保留读取入口。

## 9. 兼容性预留

本节只冻结五阶段名称和发布接口等长期外部边界；不保留 legacy reader、迁移脚手架或任何按天计算的兼容期限。

- **既有消费方**：保留五阶段名称、顺序、材料名称、质量事实含义和既有人工确认点。
- **命名预留**：统一修订和质量事实使用稳定语义，不以特定恢复事故命名。
- **容器预留**：质量事实允许后续新增类型，但新增类型不得成为工作许可。
- **状态预留**：正式结果只表达满足、缺失、不完整和失败，不为每种修复路径新增状态。
- **扩展边界**：未来可扩展 Skill 或质量事实类型；不得恢复双写或专用恢复状态机。

## 10. 明确不做与默认必须成立

### 明确不做

- 不删除五阶段，也不合并它们的用户职责。
- 不降低 TaskHandle 安全、原子正式写入、新鲜测试、逐项验收、独立审查、严重 finding 处置、人工确认或不可逆授权。
- 不重放 KnowledgeDigest、PaperBuilder 等历史事故。
- 不以连续完成十个真实任务作为交付门。
- 不把 node_modules、测试、历史任务或本机路径打入 Multica Skill Bundle。
- 不为达到文件数、行数或耗时目标强制删除必要保护，也不通过合并巨型文件伪造下降。
- 不长期双写旧格式和新格式。
- 不把每个文件的易漂移清单写入长期协作规则。

### 默认必须成立

- 任一删除证明不完整即保留，且不得以人工口头判断替代。
- 正式结果、审查和授权必须绑定正确任务、阶段、材料和代码身份。
- Git 成功不等于 WorkflowHub 正式完成。
- required review 不可用时不得正式完成；audit 摘要不可用只披露，不改变业务测试和逐项验收事实。
- 人工确认与合并、推送、关闭、删除等不可逆授权始终分离。

## 11. 验收标准

- [ ] **AC-01**：干净环境中一个合成任务依次完成五阶段，材料、调用、测试、逐项验收、审查、确认和交接均绑定当前身份。

  - **通过条件**：五阶段分别满足本规格冻结的最小完成谓词，只使用当前材料和真实质量事实完成，最终结果完整可读
  - **失败条件**：旧 accepted、文件存在或伪调用可让任一阶段假通过
  - **证据类型**：test
- [ ] **AC-02**：任一材料修改后只追加统一修订，历史可读且五阶段可继续。
  - **需求**：FR-MAT-001、FR-MAT-002
  - **验证方法**：同任务中途修订验收
  - **通过条件**：无需专用恢复状态；受影响证据准确失鲜；工作继续
  - **失败条件**：需要 reopen、rebind、continuation、recovery 或人工改记录
  - **证据类型**：test
- [ ] **AC-03**：并发修订、中断重跑和重复输入保持唯一、原子、幂等。
  - **需求**：FR-MAT-002、FR-PUB-002
  - **验证方法**：并发与正式写入故障注入
  - **通过条件**：并发恰好一个胜者；当前值始终完整；相同输入不新增事实
  - **失败条件**：覆盖胜者、出现半写、重复 generation 或需人工修 canonical 记录
  - **证据类型**：test

  - **通过条件**：只使相关证据失鲜，并列出需要补齐的新鲜事实
  - **失败条件**：旧事实继续授予完成，或变化阻止普通工作
  - **证据类型**：test

  - **需求**：FR-REV-001、FR-PUB-001

  - **通过条件**：原 verdict 永久保留；required review 不可用时 incomplete；严重 finding 有验证处置或明确风险授权
  - **失败条件**：不可用或未处理 finding 被描述为 pass，或普通修订循环调用 provider 制造 pass
  - **证据类型**：test
- [ ] **AC-06**：每个删除项均有完整删除证明，缺项自动保留。
  - **需求**：FR-DEL-001、FR-DEL-002
  - **验证方法**：逐删除 proof card 与反向消费者验收
  - **通过条件**：完整字段、消费者归零、质量替代和回滚均可核验；用户逐项确认删除清单
  - **失败条件**：缺少任一证明仍允许删除
  - **证据类型**：evidence
- [ ] **AC-07**：删除按垂直切片完成，旧能力不可达且质量负测不退化。
  - **需求**：FR-DEL-001、FR-DEL-002
  - **验证方法**：删除前后使用同一负向 oracle 与故障注入
  - **通过条件**：入口、实现、契约、样例、专属测试和术语同步消失；替代路径通过；归零清单全部为 0
  - **失败条件**：存在孤儿引用、静默 fallback、只删测试未删机制，或旧入口仍成功
  - **证据类型**：test
- [ ] **AC-08**：真实旧任务逐项处置并确认，fixture 一次性导入不丢事实、不产生双写，证明后 legacy 脚手架立即归零。
  - **需求**：FR-LEG-001
  - **验证方法**：真实旧任务只读 inventory、用户逐项确认，以及受支持和不支持旧 fixture 验收
  - **通过条件**：真实任务均有确认后的导入、归档或拒绝证据且 active legacy=0；最小格式字段完整，重复导入身份一致，旧 writer 不可用，明确拒绝形状全部失败；同一任务最终快照中 legacy reader/importer/schema/fixture 和公开入口全部为 0
  - **失败条件**：静默猜测、内容或授权丢失、旧新格式同时写，或最终仍有任一 legacy 文件、命令、schema、fixture、Bundle/Runner 引用
  - **证据类型**：test

  - **需求**：FR-FLOW-001、FR-PUB-001

  - **通过条件**：确认可以完成对应阶段；无独立授权时合并、推送、关闭和删除均拒绝
  - **失败条件**：从阶段确认推断不可逆权限
  - **证据类型**：test

  - **需求**：FR-DIST-001、FR-DIST-002

  - **通过条件**：五阶段和依赖均可解析；兼容字段存在且匹配；测试、node_modules、历史材料、任务证据和本机路径为零
  - **失败条件**：依赖源码仓隐式文件、本机旧依赖目录或夹带禁止内容
  - **证据类型**：test
- [ ] **AC-11**：Runner 缺失或接口不兼容时 fail-loud，不产生正式记录。

## 12. 风险、未决与交接

- **RISK-01**：遗漏隐藏消费者导致误删
  - **受影响 ID**：FR-DEL-001、FR-DEL-002、AC-06、AC-07
  - **触发条件**：删除证明没有覆盖真实运行入口、发布闭包或旧任务读取
  - **后果**：五阶段或 Multica 在真实使用时失败
  - **缓解或 STOP**：消费者不为零或无法证明即停止删除并保留
  - **处理 Stage**：build-plan
  - **验证**：全量文件清单、反向消费者和发布闭包共同证明
- **RISK-02**：派生正式结果过度宽松
  - **受影响 ID**：FR-PUB-001、FR-PUB-002、AC-03、AC-04
  - **触发条件**：缺失或错绑事实仍能形成完成状态
  - **后果**：假绿或错误任务完成
  - **缓解或 STOP**：对身份、哈希、代码树、审查、测试、确认和授权做负测与故障注入；任一假绿停止交付
  - **处理 Stage**：build-code
  - **验证**：小型变异必须稳定变红
- **RISK-03**：删除证明自身演变为新状态机
  - **受影响 ID**：FR-DEL-001、AC-06
  - **触发条件**：为 proof card 新增 lifecycle、reopen 或 generation
  - **后果**：复杂度换名后回归
  - **缓解或 STOP**：只使用普通计划和证据字段；发现专用 lifecycle 即停止
  - **处理 Stage**：build-plan
  - **验证**：结构和公共行为审计
- **RISK-04**：测试精简误删唯一负向 oracle
  - **受影响 ID**：FR-TEST-001、AC-12、AC-14
  - **触发条件**：删除测试但没有同质量谓词替代
  - **后果**：关键保护回归而测试仍绿
  - **缓解或 STOP**：每个测试删除绑定机制删除或替代负测；变异不红即保留
  - **处理 Stage**：build-code
  - **验证**：删除前后同一负向 oracle 和小型变异
- **RISK-05**：Skill Bundle 与 Runner Release 版本漂移
  - **受影响 ID**：FR-DIST-001、FR-DIST-002、AC-10、AC-11
  - **触发条件**：接口声明与实际运行能力不一致
  - **后果**：Multica 中正式任务中途失败或产生错误记录
  - **缓解或 STOP**：干净安装和版本错配负测；不兼容时禁止正式模式
  - **处理 Stage**：verify-code
  - **验证**：兼容、缺失、错配三类验收
- **RISK-06**：全量文件清单随代码变化失鲜
  - **受影响 ID**：FR-INV-001、AC-13
  - **触发条件**：清单和实际删除不绑定同一冻结代码树
  - **后果**：出现未分类或无证明文件
  - **缓解或 STOP**：每次结构改动后基于当前树重新生成并对账；存在差异即停止
  - **处理 Stage**：build-code
  - **验证**：清单身份与最终交付树一致

无 OPEN：已接受决策已冻结范围、质量硬门、兼容边界、分发边界和非阻断指标口径；实现布局与阶段拆分交给 build-plan。

## 13. 业务影响与回归范围

### 五阶段任务执行

- **既有行为**：材料小改可能触发专用 reopen、rebind、continuation、recovery 或 checkpoint 阻塞
- **本需求影响**：材料通过统一修订自然继续，正式完成仍需当前质量事实
- **回归路径**：正常五阶段、阶段中途修订、中断重跑、严重 finding 修复、最终验证
- **验收**：AC-01、AC-02、AC-03、AC-04、AC-05

### 旧任务迁移证明与 Multica 分发

- **既有行为**：旧状态族和开发仓内容可能进入运行时或发布闭包
- **本需求影响**：旧任务通过冻结 fixture 完成一次性导入证明后立即删除迁移脚手架；Skill Bundle 与 Runner Release 分离并洁净安装
- **回归路径**：旧任务导入、干净 Bundle 安装、Runner 兼容与错配
- **验收**：AC-08、AC-10、AC-11

### 仓库与测试维护

- **既有行为**：文件用途、测试口径和专用状态测试分散，复杂度难以治理
- **本需求影响**：全量文件分类、逐删除证明、关键质量负测和非阻断复杂度报告成为交付合同
- **回归路径**：文件清单、垂直删除、变异验证、文档一致性
- **验收**：AC-06、AC-07、AC-12、AC-13、AC-14、AC-15

- **可能受冲击的业务规则**：五阶段边界、正式写入原子性、质量事实新鲜度、审查独立性、人工授权边界、旧事实迁移完整性和 Multica 发布闭包。
- **明确无影响**：业务项目源码、第三方 provider 内容、历史事故数据、F7/F8 或 KnowledgeDigest/PaperBuilder 运行逻辑。

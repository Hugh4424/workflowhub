# 05｜审查域：审查只能回答它能回答的问题，发现要修在被消费的产物上

> 状态：**域**。域完成 = 本域台账行全部「接线或退役」＋至少一条读数（见 §7）；交付与全量口径以 `08-规范与流程自身.md` 为准。
> 来源：合并自旧 `05-独立审查与发现处置.md`（现 `archive/05-独立审查与发现处置.md`）＋旧 `01` 的「怎么审」部分（两位读者、第⑤问、方向审输入契约，按 U-038 与 `outline-design-audit.md` §10.3 拆出）＋`分析汇总/05-独立审查与发现处置.md` 任务 3「finding 修在被消费的产物上」＋`分析汇总/02-方案与Phase设计.md` 任务 4。
> 决定以任务库 `decision-log` 为准，本文件是展示件。

**一句话结论：审查记录必须回答「谁审、有没有独立上下文、读了什么、能判断什么、发现了什么、每条发现最后去了哪」，答不出任何一项就不算审查过。**

## 1. 方向叙述

审查域要挡的是**假审查**：不是没人审，是「审过了」这句话没有内容。

现在四种情况都被写成同一个「通过」：审查服务没运行、没读到材料、读完无法判断、读完真的没问题。审查分级规则写得很细，但运行时记录审查时不调用它，`context_isolation:"none"` 只是一句自述字符串；于是执行者可以自己声明独立，空 findings 与「读完了没问题」不可区分。发现侧同样：大量发现没有任何处置，流程照样从 fail 走到 pass；计划审查的意见以新编号复发，没人发现是同一条。

用户看得见的结果是：交付时说「独立审查过了」，其实审的是同一批人、同一份材料、同一个结论；说「意见都改了」，其实改的是处置表上的状态，被消费的那份 Phase 和 brief 一个字没动。

这个域要改变的用户可见结果有三条：

1. **四种状态分开写。** 通过 / 要改 / 看不全 / 没法审，各是一条结论，不合并；provider 全失败时结论是「不可用」并带失败原件，不是空发现的通过。
2. **发现修在被消费的产物上。** 计划阶段的 `fixed` 只对计划有效；审查在第 10 步做的实质修订，必须直接改后续 Phase 和真实 brief，而不是在处置表上标一个状态。
3. **方向审查审方向。** 先答「原始需求逐条追溯 + 机制因果链 + 替代方向」三段，文件级问题只作附录；没有追溯表不派方向审查。

为什么这个域先做：它是唯一能当场用历史原件回放的域（T05 的审查原件一打开就能数出多少条发现、多少条有处置），而且它不新增审查轮次、不加第四层，只把已有的分级、四态、处置集合差接上。

## 2. 任务目标

**做完后要同时看到这些现象（每条都有观察者）**

1. 每份审查记录都能标出四态之一：通过 / 要改 / 看不全 / 没法审；混写即失败。观察者：收口者。
2. 记录里写明读了什么、能判断什么、没读到什么；缺覆盖不能用空发现列表签通过。观察者：最终验收者。
3. 低风险 + 自称独立 + 无派发身份的记录被运行时拒绝；缺分级事实的记录写入但标 `tier: unavailable`，不阻断。观察者：审查派发者。
4. 第 3 层的公共契约或真实外部依赖、第 4–5 层任一面，必须外部审查；其余第 1–3 层独立审查。降级必须被拒或有具名理由。观察者：派发者。
5. 收口时只读报告未处理项，不要求问题对账为 0；有未处理项就列出来，由收口人决定是否放行。观察者：收口脚本。
6. 回放 T05 原件，必须报出 250 条未处置；报 0 条即失败。观察者：收口者。
7. 审查结论与验收结论不脱钩：审查停在「要改」时，验收不能判通过。观察者：最终验收者。
8. 能修的缺陷直接回原实施者，不退给用户分拣；严重风险由人明确承担。观察者：用户。
9. provider 全失败时，结论是「不可用」并带失败原件，不是空发现的通过。观察者：派发者。
10. 报告作者、独立裁决者、关闭执行者是三个可指认的身份，不是同一个人。观察者：独立审查者。
11. **计划阶段判 fixed 的发现，只有改了它阻塞的那张后续 Phase 与真实 brief 才算修完；处置表状态改变不算。** 观察者：下一 Phase 执行者。
12. **方向审查输出先有三段（需求追溯 / 因果链 / 替代方向），文件级问题只在附录；没有追溯表不派审查。** 观察者：派发者。

## 3. 范围与不做什么

**做**：四态；三类判断；三职责；独立性的运行时核对；发现集合差（指纹键）；审查力度按可逆性五层；provider 不可用口径；审查与验收不脱钩；发现修在被消费产物上；方向审查的「怎么审」（两位读者、第⑤问、输入契约、三段结构）。

**不做**

- 不删终末独立审查，也不加第四层审查；不改三审查点的数量与位置。
- 不要求审查回答「事实是否成立」；不新增第五态。
- 不复活退役控制面（集合差只作一次性只读审计，独立读原件，不 import 退役 helper）。
- **不管「方向域要产出什么字段」**：承诺四态、原话、代理方案单列、未答挂 AC、失效行归 `01-方向域.md`；本域只负责怎么读它们。

## 8. 验收标准（带反例）

1. **四态可分**：抽三份审查记录，每份能标出“通过、要改、看不全、没法审”之一；标不出或混写即失败。
2. **覆盖可读**：每份记录写明读了什么、能判断什么、没读到什么；缺即失败。
3. **问题对账可读**：见 §7，以原件 250/0 为准；报 0 条或照抄 108/61 即失败；对账结果不作为通过/不通过的门。
4. **独立性可核**：声称独立审查的记录必须能指出执行者身份与上下文隔离来源；指不出即失败。
5. **力度匹配**：按运行时五个风险面判；第 3 层公共契约或真实外部依赖、第 4–5 层任一面必须外部审查；其余第 1–3 层独立审查；provider 不可用记 unavailable，修复继续。
6. **不脱钩**：审查停在「需修改」时，验收不能判通过。
7. **三职责与可修缺陷**：报告作者/独立裁决/关闭执行三个身份可指认；可修缺陷的派发记录里没有「退回用户」。
8. **发现修在被消费产物上**：抽一条计划阶段判 `fixed` 的发现，必须能指出它改了哪张后续 Phase、哪份 brief；只改了处置表即失败；改了 Phase 但 brief 未同步，同样失败。
9. **方向审查审方向**：一份方向审查记录必须有三段，且主结论不是文件级问题；没有追溯表就派出了方向审查，即失败。
10. **第⑤问真下发**：provider prompt 必须出现第⑤问；只有正文有即失败。
11. **反例**：删掉一条发现处置但仍记通过，验收 3 必须报出；把同源审查写成独立，验收 4 必须报出（接线后）；把可修缺陷退回用户，验收 7 必须显示违规；只改处置表不改 Phase，验收 8 必须报出。
12. **定向验证**：抽一次审查，有定向复跑命令或不能定向的理由；删轮次没有两轮发现对比即失败。

13. **两位读者**：同一方向材料，两人各自指出同一处会让用户吃亏的地方；两人各指不同或只有一人指出不算；观察者、反例、证据写清。

## 9. 风险与未知

- 分级接线影响所有审查记录写入；历史记录无分级事实会触发异常，必须先写「没法审」分支与测试。
- provider 不可用是常态，四态里的「没法审」必须有稳定口径，不能变成「没审也算过」。
- 集合差的指纹算法要先在历史原件上校准：同一发现换编号后是否算出同一指纹，需要实测；算不出就退回 id 并明确「id 可被绕过」。
- 三职责分离可能只是记录字段；不改变实际权力时，仍是自判。
- 「修改 brief」的判定需要能定位真实派发件；如果派发件不可回读，只记「未取得」，不算通过。

## 10. 产出物与消费者

- 产出：四态写法、三类判断口径、三职责字段、独立性记录、发现集合差读法（指纹键）、力度分配表、finding 落地规则、方向审查三段结构与输入契约、第⑤问接线、两位读者回放。
- 消费者：收口者、最终验收者、下一次任务的计划作者、方向域。
- 证据落点：`quality/reviews/`、任务库审查原件。

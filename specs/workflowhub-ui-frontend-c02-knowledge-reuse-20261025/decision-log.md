## 工作包与决定

### 工作包 1 — 任务检索与适用分析

- **要交付什么**：真实任务开工时按需求检索五类规范/案例/业务知识/已验证经验，读全文并给出采用/不用/待补证、适用范围、冲突与反例；输出进入既有任务材料，而非链接列表。来源 R-001/R-003/R-004。
- **不做什么**：不建知识网站、不做整库采集、不接管组件映射。
- **方案**：在 `skills/knowledge-graph` 内新增参考文件（暂名 `references/knowledge-reuse.md`），主技能加入口指针；内容取 design-wiki 的纯文本方法层。流程固定五步：① 证据准备（来源、定位、版本/日期、权利状态、可回读 ref）；② 阅读原文（命中不是证据，必须读全文）；③ 比较/抽模式/推荐（同主题多来源比较，重复约束抽成模式，输出采用/不用/待补证）；④ 适用性四判（支持/需上下文/冲突/证据不足），单源标“单源，未独立”；⑤ 写入当前任务材料。来源类别：项目规范、历史任务与案例、业务知识与术语、已验证经验。去重按“主题+条款+来源”判；同源不算独立证据；图过期回原文并记录覆盖限制。
- **用户选择（2026-10-25）**：make-decision 开工与 build-plan 设计依据准备两处都调用。
- **验收**：AC-C02-1、AC-C02-2；只有标题命中/复制文章不算；同源不算独立证据；冲突显式处置。
- **五段记录**：调研＝内部/外部调研原件；发散＝design-wiki 四候选；收敛＝只重写方法层；就地讨论＝用户已选 C1；定验收＝上述。

### 工作包 2 — 规范自动同步机制

- **要交付什么**：一个可被现有阶段调用的“规范同步”方法：任务中发现的已验证经验/规范变化/教训，在阶段收口时自动路由到目标规范文件、写入最小条款、记录变更、更新 AGENTS.md 规范索引，并清空经验文件中的对应条目。来源 U-007/U-009/U-011、R-011。
- **不做什么**：不建第二状态机/审批门；不写未验证推断；不为验收改冻结测试；不替代 C08 的发布/分发。
- **方案**：
  - 新增 `skills/norm-sync/SKILL.md`（唯一方法）+ `references/routes.md`（主题→规范文件→consumer 路由表）。build-code 每 Phase 收口、verify-code 终末、stage-reflection 写经验前、stage-closeout 各加一个指针；不新增 stage。
  - 同步步骤：识别已验证变化 → 路由到目标文件 → 生成最小条款改动（保留旧值/理由，supersede 旧条款）→ 直接写入 → 写 `quality/evidence/norm-deltas/<日期>-<主题>.md`（条款 ID、旧/新、理由、证据 ref、来源、适用范围、反例、版本/时效、许可状态、任务、时间、文件清单）→ 更新项目 AGENTS.md 规范索引 → 经验文件不新增条目，已有条目关闭或移出。
  - 保护：证据不足、无目标文件、许可未知时不写，留在任务未决项并写原因；写入后可凭 delta 回滚；同一事实只保留一个有效条款。
- **用户选择（2026-10-25）**：新建独立 `skills/norm-sync/` 技能，不塞进知识图或收口技能。
- **验证判定**：一条变化只有同时满足「独立来源核对通过」「证据可回读」「无未解决冲突」「适用范围写明」才可写入；保存成功、自觉正确、单源推断都不算。
- **范围保全**：写入的条款必须带适用范围与反例；只适用于单任务的观察写成任务局部说明，不升级为全局条款；旧条款被替代时保留旧值与理由（supersede），不并存两个有效版本。
- **并发与失败**：同一规范文件按文件串行写入（现有记录锁）；先写 delta 再写规范，或使用临时文件+原子替换；中途失败保留旧文件、记 incomplete 与原失败，可凭 delta 回滚；同一任务+条款 ID 幂等，不重复追加。
- **一致性检查**：每次同步后核对 AGENTS.md 索引与实际文件清单；不一致即失败并修索引，检查者与时机写进方法。
- **验收**：AC-C02-5、AC-C02-7；至少两次真实更新（WP4）；delta 字段齐全；AGENTS.md 索引与实际文件一致；经验文件无对应残留；回滚路径可读。方法 owner 为知识方法 owner，维护入口登记在 catalog/reuse-registry。
- **五段记录**：调研＝内部接入点与外部 norm delta 实践；发散＝阶段收口/发现即写/任务末三案；收敛＝阶段收口 + 直接写入 + delta；就地讨论＝用户已选；定验收＝上述。

### 工作包 3 — 五类规范落点与 AGENTS.md 索引

- **要交付什么**：在 WorkflowHub 与 PaperBuilder 两个项目建立/补齐五类规范落点与导航：设计、前端沿用 C01 八类；新增后端、接口、验收三组文件与导航；每个项目 AGENTS.md 增加“规范索引”，记录文件夹/文件用途、consumer、owner、最后更新。来源 U-008/U-009/U-010、外部调研。
- **不做什么**：不生成空文件凑数；不在 WorkflowHub 造不存在的页面规范；不复制项目 token/API 值。
- **方案**：按外部调研推荐 D 建三个目录，但先落最小集：每目录一份 `README.md` 导航 + 一份核心正文（`backend/architecture.md`、`api/contract.md`、`acceptance/acceptance.md`）；其余 13 份按后续真实任务需要再生成，不建 16 份空壳。模板沿用 C01 七节形状，放改名后的 `project-norm-init`（由 `ui-project-init` 迁移）。WorkflowHub 本仓建适用内容；PaperBuilder 建三组目录与核心正文，保留现有 9 份设计/前端规范。AGENTS.md 索引列出五类目录、文件用途、读取时机、最后更新。
- **用户选择（2026-10-25）**：把现有 `ui-project-init` 改名为 `project-norm-init`，作为五类规范的初始化入口；新三类模板放该技能。

### 工作包 4 — 两次真实任务与后续读取

- **要交付什么**：两次真实更新，证明“发现→写规范→后续任务读取”真的发生：
  1. 生产任务：为 `skills/catalog.yaml` 七项缺 `upstream.commit` 的条目补齐真实版本或具名不可得；把验证出的“外部版本/许可证据”规则写进 `specs/acceptance/evidence.md`。
  2. 消费任务：对 `specs/Improvements.md` 现有条目做判重与状态核对，读取刚写入的验收证据条款，处理来源不明的旧条目，并把“旧经验退役”规则写进 `specs/acceptance/done.md` 或 `regression.md`。
  3. PaperBuilder：基于 C01 已写入的 9 份设计/前端规范与真实文件，完成一次规范更新（设计/前端域），并更新其 AGENTS.md 索引；不新做页面任务。
- **不做什么**：不同任务重放、不虚构需求、不把保存成功当验证、不未授权改 PaperBuilder Git。
- **方案**：两笔 WorkflowHub 欠账按真实输入执行；每笔在阶段收口走一次 norm-sync；消费任务必须引用生产任务写入的条款 ID；PaperBuilder 按其自身授权与真实文件执行，跨仓产物单独留证。
- **用户选择（2026-10-25）**：PaperBuilder 只改规范文件和 AGENTS.md 索引，不做页面任务。
- **验收**：AC-C02-3、AC-C02-5；两次不同任务、不同需求；消费任务能定位“查询→条款→采用→产物”；PaperBuilder 更新可回读；未授权/不可用如实记。
- **五段记录**：调研＝内部候选 A/B 与 PaperBuilder 现状；发散＝仓库欠账/本卡实施/用户指定 + 两边落地；收敛＝两笔欠账 + PaperBuilder 一次更新；就地讨论＝用户已选；定验收＝上述。

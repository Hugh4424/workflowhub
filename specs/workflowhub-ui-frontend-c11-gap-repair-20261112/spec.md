## 一页看懂：谁要什么结果，怎么算通过？

八条缺口各自落到“关闭（原缺口、改动、原件、复验）”或“未修（负责人、恢复条件、影响）”，不留第三种状态。

- **需求 1**：v15 的图查询结果真落盘，页面选项真的从这份数据来，坏数据不得被选中。
- **需求 2**：载体两页真实引入设计系统的组件与布局，四类对象各有使用点与资产/页面两层检查。
- **需求 3**：v15 在十一个状态、三个视口下逐格有独立观察报告。
- **需求 4**：v15 有八维独立设计审查结论，审查者不是实施者。
- **需求 5**：v15 与载体的完整前后改动有独立代码审查与四维结论。
- **需求 6**：v15 的 200% 缩放、可访问面与性能预算有真实读数，采不到写未测。
- **需求 7**：载体做一次真实变更，两类变更都有前后哈希与“下游读到新值”的观察。

- **最大影响面**：v15 工作副本的页面脚本与样式、载体两页与 `app/ui/`、本任务的证据与关闭清单。
- **验收信号**：判据见 Appendix A 的 AC-C11-001 至 AC-C11-009。

## 为什么做，给谁用？

C09 的判词结论是 C02～C08 在页面链路上缺证：查询结果截断且不落盘、v15 没有引入设计系统、状态与视口未逐格判、八维审查不存在、代码审查只覆盖 busy 片段、缩放与性能未测、变更同步没有前后对照、P4 六段没有下游读取回执。缺口为零起点，C11 要在真实使用点补上，而不是再写一份说明。

### 需求 1：查询结果要能落盘并被页面选择消费

原判词指出查询输出被截断、未存磁盘，页面没有可回读的“查询→选择”链。v15 当前脚本把样例写死在内存里，没有 fetch、没有远程读取入口，选择也只看内存数组。
需求 1 要求有一个查询写入器把一次查询的输出原样落盘，并产出页面可读的数据文件；页面从该文件渲染选项，并在数据缺失、为空、缺标识或格式坏时给出可读原因而不是假装选中。查询记录是图里的经验条目，页面把这一列改称“经验候选”，选项 id 等于查询记录 id。
来源是缺口台账 G1 与 R-001。

### 需求 2：载体两页要真实用上设计系统的组件与布局

原判词指出 v15 未 import 或运行 PaperBuilder 的组件与布局，没有使用点，也没有资产层与页面层检查。
载体是 React/Next，能真正引入组件。需求 2 要求从 PB 源取最小件复制进载体并真实 import/运行，四类对象（设计组件、设计布局、前端组件、前端布局）各自给出源、使用点、资产层检查与页面层检查。
目录清单、映射文件、截图都不算使用点。
来源是缺口台账 G2 与 R-002。

### 需求 3：v15 全部状态与视口要逐格有独立观察

原判词说 v15 当前字节的整页内容、状态与视口独立判断未取得。
需求 3 要求从页面源码列出十一个状态与三个视口，逐格跑页面审计，每格留下 console、network、溢出与对象身份四项，观察者只看当前字节与报告。
任一必需格未测，整项记未修，已测格保留。
来源是缺口台账 G3 与 R-003。

### 需求 4：v15 要有八维独立设计审查

原判词说没有 v15 的八维独立设计审查。八维是业务任务、信息架构与导航、交互状态、内容与数据、视觉规范、响应式布局、无障碍、真实代码交接。
需求 4 要求逐维给输入、观察、证据与未覆盖项，执行者不是实施者，有发现就逐条处置。
来源是缺口台账 G4 与 R-004。

### 需求 5：完整前后改动要有独立代码审查

原判词说既有审查只覆盖 busy 脚本与假 DOM，没有 v15 完整 diff 与四维审查。
需求 5 要求先给拟改文件留只读基线与哈希清单，再改；对完整前后 diff（含载体改动）按组件化、统一性、可维护性、性能四维审，发现逐条处置并复验。
来源是缺口台账 G5 与 R-005。

### 需求 6：缩放、可访问面与性能预算要有真实读数

原判词记录 200% 缩放未证实、读屏未检查、性能预算未测。
需求 6 要求三块各有真实读数与结论：200% 缩放后的内容与操作、可访问树与键盘焦点对比度、核心与实验室性能指标。没有真人读屏只作覆盖限制；采不到记未测，不拿别的指标替代。
来源是缺口台账 G6 与 R-006。

### 需求 7：变更到使用点的同步要有前后对照

原判词与 026 报告只有保留/不引入的取舍，没有采用前后对照。
需求 7 要求在载体做一次真实变更，覆盖设计侧 token 与接口侧类型两类；改前留哈希与只读副本，改后记哈希，让下游真实读到新值并留观察，再跑定向复验。旧值、缓存值或未触发同步是可判失败的反例。
来源是缺口台账 G7 与 R-007。

### 需求 8：P4 六段回执如实登记

P4 六段（任务清单、规范清单、入口事实、需求索引与覆盖、知识检索、方向审查请求）有原件，但缺下游逐动作读取回执；原执行者已不可续，当时读取无法重建。
需求 8 只要求第 1、3、5、6 段（任务清单、入口事实、知识检索、方向审查请求）有 C11 的当前读取记录；第 2、4 段读到就一并记录，不作必需。记录只作补充，原回执如实记未修，不冒充关闭。
来源是缺口台账 G8 与 R-008。

### 背景是什么？

C09 交付后发现八卡多数只在文档层完成，页面链路没有真实运行证据。PRD 因此把“修复”与“验收”分开：C11 修、C12 验，C11 的关闭件是 C12 的输入。
decision-log 已确认八包方向、范围、验收与风险：包 1、2、7 并行，3、6 读包 1 的最终字节，4 读包 3，5 最后审 1、2、7。载体只有两页，C03 与 C08 都落在同一组文件上，按“共享文件唯一写主”串行执行。

## 打算怎么做？

复用现有页面、审计器与采集器，只在缺口处改真实使用点；不新建平台、不改各卡方法正文。

### 方案 1：查询写入器加静态数据文件

做什么：新增一个只用 Node 标准库的写入器，跑一次有界图查询，保存未截断原始输出，并生成页面可读的数据文件；v15 用 script 标签载入该文件，选项从数据渲染，选择时要求 ID 存在于数据。
为什么这样：v15 是静态页且没有本地服务，走静态数据文件既避开 file:// 读本地文件的限制，又保留“查询→选择”的真实链路。
怎么验：跑写入器看字节与退出码；打开页面看选项来源；把数据改成空、缺 ID、格式坏三种，页面各给可读原因。
失败怎样：查询入口不可用时如实记未修；数据坏时页面显示原因，不出现成功选择。

### 方案 2：载体引入 PB 最小件

做什么：从 PB 源复制 primitives、样式与 token 到载体 `app/ui/`，在两页真实 import 并使用；四类对象各留源路径、使用点、资产层与页面层检查。
为什么这样：v15 是静态页，装不进 React 组件；载体是 Next 应用且依赖齐全，能真正渲染。
怎么验：载体构建退出 0；渲染截图与 DOM 断言；移除 import 后必须失败。
失败怎样：构建或渲染失败按只读基线还原本次文件、删除新增目录、保留失败原件，再跑定向复验。

### 方案 3：复用页面审计器逐格采集

做什么：用既有页面审计脚本对 v15 逐格采集；每格用页面只读 URL 状态入口进入声明状态，再读页面自身的 state 标记确认，然后采集（采集器会重载页面，入口负责把状态复现）；再交独立审查者按八维给结论。
为什么这样：审计器已能无头连真实浏览器，报告形状有校验器；自造采集器会新增第二事实来源。
怎么验：33 份报告齐；抽查两格重跑一致；故意写错身份必须被判不一致。
失败怎样：进入不了的状态如实记未测，整项记未修，已测格保留。

### 方案 4：复用采集器测缩放、可访问与性能

做什么：用既有采集器取可访问树、溢出、控制台与网络、TTFB/DOMContentLoaded/load 与长任务；LCP 与 CLS 用页内 PerformanceObserver 观察，INP 用一次脚本点击的事件时序近似；对比度按 WCAG 公式在页内计算，焦点序列由连续 Tab 的 `document.activeElement` 读出；200% 缩放用浏览器缩放后复读关键操作。
为什么这样：既有采集器是项目事实来源，能复用就复用；核心指标没有现成实现，用页内观察器补采比新造采集平台小得多。
怎么验：每项一条真实读数与命令；拿不到记未测。
失败怎样：采集器失败保原错误；不拿首屏或截图替代。

### 方案 5：只读基线加完整差异审查

做什么：改动前为 v15 与载体拟改文件留只读副本与哈希清单；改动后取完整差异，按四维独立审查并处置发现。
为什么这样：v15 与载体都没有 Git 历史，没有基线就说不出“完整前后”。
怎么验：基线哈希清单与最终差异可读；删除侧与新增侧都在；发现逐条有处置。
失败怎样：基线缺失或差异不完整时整项记未修；不以“只审新增”充完整。

### 方案 6：收口清单与二态登记

做什么：一份关闭清单记录八条缺口的二态、diff 与哈希、独立复验原件与未修清单，交 C12。
为什么这样：C12 以关闭件为输入，清单是唯一交接面。
怎么验：抽两条按指针核原件；任一条不齐整份不合格。
失败怎样：缺口未清时清单如实记未修，不凑关闭。

## 阶段大纲：几个阶段，各交什么？

本节是流程大纲的落点，不计入十组叙事。
六段已由用户确认（2026-11-12，答复原文“就按这六段（推荐）”）。

- **共享准备（不单列 Phase、不称交付）**：改动前为 v15 与载体拟改文件留只读副本与哈希清单。所有阶段共用这一份基线；跳过则 P5 无法判“完整前后”。
  v15 无 Git，载体有只读基线 `c11-carrier-baseline-20261112`；两者都要有本次起点的哈希清单。
- **P1**：交查询写入器、原始输出、页面数据文件与 v15 改动；一条验收判“数据坏了不得选中”；无依赖，可与 P2 并行；下游是 P3、P4、P5。
- **P2**：交载体两页的组件使用点与两类变更的前后对照；一条验收判“移除使用点必须失败”；无依赖，可与 P1 并行；下游是 P5。

### 接口与失败语义

查询写入器输出原始结果与页面数据文件两份；页面只读数据文件；审计器只读页面。

### 证据计划怎么写？

证据计划把判定义务分到已有 Task 字段，不另建验收计划。
七项是判什么、怎么判、证据从哪来、谁提供、何时能拿到、成本类别、拿不到怎么办；缺一项不得开工。
拿不到证据时写真实尝试、卡点、提供者与恢复条件，不把缺口记为完成。

证据计划：判什么=AC-C11-001 至 AC-C11-009 各自的通过信号；怎么判=各条指定的 ORACLE 判定器；证据从哪来=各 Phase 的 `quality/evidence/` 单份原件；谁提供=该 Phase 的实施者或独立审查者；何时能拿到=该 Phase 命令退出后；成本类别=命令级或独立审查级；拿不到怎么办=按验收流程记 incomplete 或 unavailable，并写真实尝试与恢复条件。

未达成项按真实尝试记录：incomplete：AC-…；试过=<命令与原 ref>；卡在=<真实条件>；谁提供=<真实对象>；恢复条件=<可观察条件>。
机器判据无真实尝试原 ref 不得记 incomplete；语义判定未执行可记 incomplete。
语义判定的 incomplete 写判定者、观察协议、证据落点与约定时点；`unavailable` 须给原因与恢复条件。
可带缺口进 stage-close；最终报告逐条列缺口，不宣称完成。

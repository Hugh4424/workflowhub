# Phase P6 — 八条缺口二态收口与交接清单

本文件写给整任务验收者与 C12 读者；读完要能凭清单判断每条缺口是关闭还是未修，并按指针打开原件核对。

## 这一 Phase 交出什么？

交付八条缺口的二态清单、P4 第 1/3/5/6 段的当前读取记录与未修登记，作为 C12 与后续读者的唯一交接面。

- **本 Phase 结果**：`quality/evidence/c11-closeout-index.md` 八行齐；每行是“关闭（原缺口、改动、原件、复验）”或“未修（负责人、恢复条件、影响）”；每条关闭行记所测字节哈希，且等于对应清单文件的哈希。
- **清单固定表头（照写，门禁按表头名取列）**：`| 缺口 | 状态 | 原缺口 | 改动 | 原件 | 复验 | 未修 owner | 恢复条件 | 影响 | 字节哈希 |`
- **非目标**：不重做修复、不重采页面、不新增缺口条目、不替 C12 判能力可用。
- **改动前**：八条缺口只有台账里的修复方案，没有逐条状态。
- **改动后**：八条各有二态与指针，C12 能直接读。
- **与相邻 Phase 的边界**：P1–P5 交出改动与事实；本 Phase 只登记与核对；发现缺口回对应 Phase，不在本 Phase 改。
- **主要风险**：把“基本完成”写成关闭；结论与最终字节脱节；拿旧原件当本次复验。
- **下一步**：C12 以本清单为输入；用户按清单决定是否进入验收阶段。
- **动手前必读**：`spec.md` 的 Appendix A、台账 v4、各 Phase 的原件与复验记录、两份最终清单。
- **未决事实**：`unknown` — G8 的原回执不可重建；C08 后继采用、C02-P2、C05-P3 按已定记未修或归 C12，由本 Phase 如实登记。

## 这一 Phase 怎么验收？

本 Phase 是唯一末验收，承接验收 8 与验收 9，并逐条消费前五个 Phase 的结论。

**验收 8：四段当前读取与未修登记（AC-C11-008）**

目标：P4 第 1、3、5、6 段各有 C11 的当前读取记录，且该记录被判“不足以免除未修”，原回执如实记未修。
怎么操作：逐段读原件，记录文件、字段、读取时间、命令与哈希；再对照台账 G8 的关闭判据判一次；第 2、4 段读到则附记。
什么条件：四段必需的原件在任务库内可读；原下游执行者不可续，这是已知事实，不是缺口。
怎样算通过：四段记录齐且每段五字段非空；判定字段明确写“当前读取不计关闭”；未修三件（负责人、恢复条件、影响）齐。
故意弄坏一处：把判定字段改成“已补齐原回执”再跑门禁，必须非零并点名判定段。
真跑还是替代：真读加人读判定；读取命令留输出，判定是语义结论。
谁判与证据：独立读者（来源用 `ocr delegate` 或 wh-review 独立记录），在读取记录成稿后判定；读四段原件与记录；结论记 `quality/evidence/c11-p6-readback.md`。
失败回修与停止：记录缺段回本 Phase 补读；判定被改成关闭回本 Phase 修正；两次失败停手报主会话。

**验收 9：八条二态与交接清单（AC-C11-009）**

目标：八条缺口逐条二态，四件套或三件套齐，指针可打开，字节哈希与清单一致。
怎么操作：读清单；随机抽两条按指针打开原件核对；核对每条关闭行的“字节哈希”等于其引用的最终清单文件哈希（`c11-final-v15.sha256` 或 `c11-final-carrier.sha256`）。
什么条件：P1–P5 原件齐；两份最终清单可读。
怎样算通过：八行二态且套件齐（关闭行四列非空、未修行三列非空）；抽查两条一致；字节哈希等于清单文件哈希。
故意弄坏一处：把一条关闭的状态改成“基本完成”再跑门禁，必须非零并点名该行；把某行字节哈希改一位，必须非零。
真跑还是替代：人读加抽样核对；不要求全量复核。
谁判与证据：未参与实施的独立读者；结论记 `quality/evidence/c11-closeout-index.md`。
失败回修与停止：缺件回对应 Phase 补；哈希不符回 P3/P4 重采；两次失败停手报主会话。

## 怎么验证？

开工前四要素：验证层是人读加抽样核对；命令是本文件机器字段的 `gate_cmd`；预期是八行二态且哈希一致；失败条件是第三种状态、缺 owner 或哈希不符。
G-2 不适用：本 Phase 有可读事实文件，仍需真实读取与核对。
覆盖上限：只证八条缺口条目与本次原件；不证 C12 的能力结论。
显式不覆盖：不证明业务链、旧基线、238 全量、发布。

## 验收 Phase 才能做的检查

本节是本任务唯一末验收 Phase 的填写处，九条验收在这里逐条收束。

1. **入口准则**：P1–P5 各自的「完成」、写入集落地与证据可读各写一行；缺件写缺口。
2. **两份就绪件**：数据侧是 v15 与载体的最终字节及两份清单，环境侧是静态服务与浏览器会话的可用记录。
3. **授权边界**：本任务只读外部工作副本、不改 PB 原仓；Git 提交与发布不在本 Phase，需用户另行授权。
4. **逐条结论**：AC-C11-001 至 AC-C11-009 各一行，写编号、一个档位与一条具名证据路径；行数与条数相等。
5. **五类执行事实**：每条命令与参数、cwd 与执行者、exit code、原始输出落点、机器可读报告各记一处；缺的写缺口。
6. **效果评测**：本任务不做前后指标对比，因为缺产品或业务基线；性能读数是单次事实，不构成“变好”。
7. **复验四项**：复验者与修复者上下文不同；F2P 与 P2P 各自用例清单逐条列，计数属测试资产事实，不作验收判据。
8. **变更批准**：本任务不增删验收集合；若实施中要改 AC，必须取得用户真实答复并保留原件。
9. **分诊与关闭**：失败按根因分诊，`Disposition` 初值留 `Pending`；本 Phase 不代填通过。
10. **回写五项**：`spec.md` 场景卡与验收表、覆盖验收、`facts.jsonl` 既有字段、修复记录各一行。
11. **六项结论**：评估与局限、与计划的偏差、未充分测试的特性、未解决事件、残留风险、签核对象逐项写。
12. **防自证五禁令**：判定器必须要求显式通过元素；不用“无失败即通过”；不用截图替代交互；不用文件名替代使用点；不用实施者自评。
13. **失败修复复验闭环**：有失败则按失败、分诊、根因、修复、换上下文复验、回写走；无失败写“无”加依据。

九条验收各归一个判定器，不互相顶替；未执行时写 `unavailable` 与原因，不预填通过。

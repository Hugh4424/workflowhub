## 共享定义

以下定义供全部任务卡引用一次;各卡在最小读取集中按名引用,不重复展开。

### SD-01 方法工具包
- **定义**:产品定位。宿主 AI 助手/子代理按方法完成工作,WorkflowHub 提供方法与必要窄工具;结果以实际改动、测试、审查说明,不再逐阶段专门认证;跨会话接续依赖清晰记录与读取,不提供每一步强制机器认证;保留工作区安全、危险操作授权、真实测试、独立审查和如实披露。
- **来源锚点**:decision-log U-007(L84-92)、T-006、OI-009(L340-358)、D-001(L522-539);ADR-0031。

### SD-02 可验证用户结果工作包
- **定义**:工作组织单元。按可独立验证的用户结果划分工作包,不按技术分层;强关联的实现、测试、修复可在同一上下文连续完成,独立复核换上下文;phase/工作包文档只写本检索边界内差异、边界、依赖及自身测试/验收,引用同一全局目标,不复制 PRD 或 spec 完整正文。
- **来源锚点**:decision-log Grill L497、D-001 L558;Talk round 4 Q17。

### SD-03 窄状态集(7 值)
- **定义**:新流程任务接续只使用的 7 个状态值:`not-started` / `in-progress` / `succeeded` / `failed` / `blocked` / `unverified` / `abandoned`。不重建 fact graph 或恢复平台;配合记录完整性回读检查使用。
- **来源锚点**:decision-log OI-007 resolution(L307)、D-001 L589。

### SD-04 5 项窄工具
- **定义**:保留并可脱离 kernel 独立调用的 5 项窄工具——①工作区/范围核对;②真实命令 exit/output 采集;③安全写入(原子写入);④不可逆 Git 授权;⑤冲突中断保护。工具只保证实际能观察的事,不替人判断功能是否合理,也不另建通用完成对象。
- **来源锚点**:decision-log OI-006 resolution(L286)、D-001 L585、Grill L501。

### SD-05 真实入口联通实跑
- **定义**:整体功能只有从真实入口联通实跑、达到约定成功条件且关键失败路径被核对,才可声明完成;代码审查不等于功能验收;子任务状态相加不等于整体完成;不能只汇总单元测试或工作包状态。
- **来源锚点**:decision-log OI-004(L245)、D-001 L581、Grill L499。

### SD-06 有效 RED 判据与 G-2 豁免披露
- **定义**:有条件 TDD——仅当可观察行为变化且真实测试能先失败时,用同一测试完成 RED→GREEN;环境故障、配置缺失或无意义断言不算有效 RED;纯文档等不为形式制造失败。G-2:若某任务确实先写不出失败测试(纯文档、探索性改动),必须显式豁免——补一条可失败的检查,或写明豁免理由与风险并在验收中披露;不允许直接跳过。
- **来源锚点**:decision-log D-001 L573、Talk round 4 Q7、Grill 续 G-2(L777)。

### SD-07 审查节奏(统一表述,2026-09-19 加固修订恢复 U-009#2 原意;第二轮追加 OI-014 合并审查点)
- **定义**:审查节奏完整序列——**①build-plan 合并审查一次:build-plan 完成后、build-code 开工前执行,一次审查同时覆盖 spec 与 phase 文件,质量核心=原 spec 审查(需求翻译完整性/验收可执行/架构合理)+原 plan 审查(依赖正确/并行声明/写集)合一(2026-09-19 第二轮,OI-014/R-020);②build-code 内 phase 级审查每 phase 一次;③全 phase 结束集成审查一次;④verify-code 有一次单独命名的「终末代码审查」,是独立事实,不与功能验收共用一条记录;verify-code 另负责真实入口功能验收、失败路径核对与受影响回归验收**。除新增①外其余审查点次数与位置不变,变化只在把 wh-review 换成新的代码审查工具,不减少审查次数。单次审查成功后不再为同一 scope 复审;审查发现照单修复,修完不重跑审查,不建 severity 门槛或复审循环。审查派发不依赖材料身份/哈希/sha/快照/回执校验,审查输入以纯文本路径引用材料(OI-013,SD-17)。
- **来源锚点**:decision-log U-009 第 2 条(L100-106)、OI-005(L266)、D-001 L577、Talk round 4 Q13;U-010 第 3 条(L111-118)、OI-014(L459-478)、Talk round 5 问 3(L993-1001);2026-09-19 地图核对 Q5 统一表述。**Supersession 说明**:D-001 L577 为旧表述(superseded);2026-09-19 地图核对 Q5 的统一表述在转写中丢失了 U-009#2(L100-106)的「verify-code 一次审查」,2026-09-19 第一轮加固修订(R5)恢复 U-009#2 原意并单独命名为「终末代码审查」(独立事实,不与功能验收共用一条);2026-09-19 第二轮(U-010/OI-014)追加 build-plan 合并审查点为完整序列①。审查节奏以本节表述为准。decision-log 本体 append-only 不改,本条为 PRD 侧显式 supersession 标注。

### SD-08 独立替代审查(T-003)
- **定义**:fallback 合同统一为——审查工具 unavailable 时,采用一次由未参与实现者完成的独立替代审查,保留来源及缺口,不等待或反复重派;旧 wh-review/broker 路径仅为只读历史证据,不是可执行 fallback;若独立替代也不可用,该审查事实记 unverified 并如实披露,不冒充已审。不以 review unavailable 替真实测试失败开脱。
- **来源锚点**:decision-log U-005 Q1=A、T-003、OI-005、D-001 L579。

### SD-09 逐字双层需求保真与三档结论
- **定义**:需求保真采用逐字双层结构——原始声明不得改写,派生需求带 source 锚点;结论分三档:接受 / 接受但有偏离 / 拒绝;偏离必须写明改了什么、为什么;原话一改,派生项标记待复核。
- **来源锚点**:decision-log OI-010 resolution(L367)、Talk round 4 Q15。

### SD-10 append-only 收敛
- **定义**:收敛为 append-only——发现缺口只追加、不覆盖既有记录;历史决定、确认、审查、测试、物理事实不可改。
- **来源锚点**:decision-log OI-010 resolution(L367)。

### SD-11 并行规则五件套
- **定义**:并行规则在计划阶段产出:①接口蓝图冻结(文件级符号与 import 图);②依赖感知调度;③中心化验证瓶颈;④worktree 隔离;⑤**并发上限 2–5 个子代理**(用户原话定稿,取代决策记录中「硬上限起始 3–5」的旧表述)。并行仅用于输入、写集与环境独立的工作包;共享写面或真实发布依赖先协调,不为并行转移整合成本;接口必须改时按 G-1 停并行、主会话重排后继续。并行声明制(2026-09-19 加固修订 R8 新增;2026-09-19 第二轮按 OI-012 降级):每个并行工作包在 build-plan 声明读集、写集、文件 owner、接口符号清单、合并责任,作为**事实记录**供验收核对;未声明或声明不实(实跑读写越出声明集)=验收失败事实,如实记录,不阻断派发。接口蓝图冻结同按 OI-012 降级为事实记录+验收核对,不构成推进前置;接口必须改时仍按 G-1 停并行、主会话重排后继续(协调纪律保留,不是机器门禁)。
- **来源锚点**:decision-log OI-002(L202/L204)、L762、Grill 续 G-1(L776)、D-001 L571;2026-09-19 地图核对 Q4;2026-09-19 加固修订 R8。

### SD-12 删除通用事实引擎的损失清单
- **定义**:删除通用事实引擎(task kernel/fact graph 强制依赖)前,必须书面承认真实损失清单:自动拒绝错绑或过期证据、跨宿主「此答复批准此版本」、跨宿主自动恢复与机器可查阶段状态;在需求确证后再决定保留哪些窄能力。
- **来源锚点**:decision-log OI-003 resolution(L224)、Grill L502。

### SD-13 build-prd 两个命名可检查交付项
- **定义**:①**具体重构验收标准**——可观察的成功/失败用例 + 所需证据 + 承接负责人(由 CARD-10 执行);②**可测量的「无重复契约」标准**——同一事实只有一个权威文件,删除后不得存在两个文件对同一事实各自声明权威(由 CARD-02 执行)。
- **来源锚点**:decision-log L898-902(成功/失败边界)、L623(方向契约)、Talk round 4 Q2。

### SD-14 卡片交接责任指派
- **定义**:每卡的 owner、合并责任与验收责任在承接 task 开工(make-decision)时指派,PRD 不预发明具体人;共享写面的集成责任归属规则=先冻结接口的一方为集成责任方,另一方在冻结接口上对齐。
- **来源锚点**:2026-09-19 build-prd 审查 finding #10 处置;SD-11 接口蓝图冻结规则。

### SD-15 质量事实≠推进许可证
- **定义**:质量事实如实记录,但不自动成为推进许可证——失败与缺口必须如实记录;某类机器产物(如 trace/JUnit/跳过计数)在该测试路线不适用时记 N/A+理由,不自动阻塞任务;缺**适用**产物或伪造产物仍判失败;unknown/unavailable/incomplete 不得写成通过。
- **来源锚点**:2026-09-19 外部审查驱动加固修订 R2;CARD-04 FR-20;decision-log OI-004(L238-258)。

### SD-16 过渡基线(未提交修复代码的定性)
- **定义**:本规划任务期间未提交的 `runtime/review/*`、`skills/wh-review/*` 修复代码(现行审查路径的协议修复,F1–F7)定性为**过渡基线**:它服务现行审查路径直至新路径就位;CARD-05/06 新路径就位后按迁移表(CARD-06 FR-51)转为只读历史或删除,不静默留存。
- **来源锚点**:2026-09-19 外部审查驱动加固修订 R3;本 PRD「质量事实」节 F1–F7 修复事实。

### SD-17 两道人为门与零机器门禁
- **定义**:新系统仅有两道人为门——①推进中的人为确认对话;②不可逆 Git 授权(宪法级)。其余一切机器/流程校验(revision 绑定链、快照树认证、材料身份/哈希/sha 校验、回执 readback 校验等)均不构成阶段推进、审查派发、测试执行的前置;规则类要求(迁移表冻结、并行声明、接口蓝图冻结)一律为**事实记录+验收核对**——未做或做假=验收失败事实,如实记录,不阻断推进。记录层不用内容寻址哈希:普通文件名(不可变命名:日期+序号+描述,append-only)+纯文本路径引用。质量=真实执行+独立审查+人确认(与 SD-15 互引:质量事实仍如实记录、不漂白,只是不构成推进许可证)。**显式区分**:本规划任务自身 build-prd 使用过的 revision 绑定是现行系统合同,与本次新系统设计无关,不因此保留。
- **来源锚点**:decision-log U-010(L111-118)、OI-012(L417-437)、OI-013(L438-458)、R-018/R-019(L138-139)、Talk round 5(L993-1001);2026-09-19 第二轮加固修订。

### CARD-03 全阶段子代理工作方法与并行规则

### CARD-04 真实验收与有条件 TDD

- **结果与 consumer**:验收标准在 make-decision 即写成可执行形式(条件→系统必须做什么 + 可度量成功标准 + 至少一条失败或边界场景;写不出标 incomplete);验收 oracle 与实现者分离(测试目录对实现者只读或隐藏);通过必要条件含「改动前是红的」;机器产物按测试路线适用(FR-20/SD-15):硬要求=真实命令+exit+output+对应 oracle 证据,trace/JUnit/跳过计数等仅在该测试路线适用时必需,不适用时记 N/A+reason,缺不适用产物不判失败,缺适用产物或伪造产物仍判失败;有条件 TDD 与 G-2 豁免披露按 SD-06;真实测试失败必修并复验;测试与验收类技能必须真实执行并留执行事实;测试与验收推进不依赖回执/哈希/快照/材料身份校验(OI-013),真实命令 exit/output 保留为证据并以纯文本路径引用,不做哈希绑定门(SD-17)。consumer=用户(整体功能可信度)+verify-code。
- **范围**:可执行验收标准的写入契约(make-decision 内)、oracle 分离、有效 RED 判据与豁免披露、机器产物要求、失败处置。不含总体集成验收执行(CARD-10)、审查工具(CARD-05)。
- **流程/状态**:make-decision(验收标准写为可执行形式,写不出标 incomplete)→ build-plan(翻译进 spec)→ build-code(RED→GREEN,测试子代理独立上下文)→ verify-code(真实入口功能验收)。状态:验收条目生命周期用窄状态集(SD-03),unverified 不得写成 succeeded。
- **FR**:
  - FR-16:每条验收标准具备条件→行为、可度量成功标准、≥1 条失败/边界场景;写不出的标 incomplete,不伪造。
  - FR-17:验收 oracle 与实现者分离——测试目录对实现者只读或隐藏。
  - FR-18:TDD 通过必要条件包含「改动前是红的」(有效 RED,SD-06);环境故障/配置缺失/无意义断言不算 RED。
  - FR-19:G-2 豁免必须补一条可失败检查或写明理由与风险并在验收中披露;不允许直接跳过。
  - FR-20:机器产物按测试路线适用——硬要求=真实命令+exit+output+对应 oracle 证据;trace/JUnit/跳过计数等机器产物仅在该测试路线适用时必需,不适用时记 N/A+reason;「缺不适用产物」不得判失败,「缺适用产物或伪造产物」仍判失败;真实测试失败必须修复并复验后才可宣称对应功能完成(SD-15)。
  - FR-21:测试与验收类技能被真实执行且执行事实被记录;「phase 全做完但一次真实验收都没做过」被禁止。
- **AC**:
  - AC-16(对应 FR-16):条件=检查一个真实 task 的验收标准集;行为=逐条核对可执行形式;度量=100% 条目含条件→行为+可度量标准+≥1 失败场景,或显式标 incomplete。失败场景=任一条目缺三要素之一且未标 incomplete,即失败。
  - AC-17(对应 FR-17):条件=观察一个实施 task;行为=核对实现者可访问范围;度量=实现者对测试目录无写权限;只读模式下可读不可写,隐藏模式下读不到测试内容。失败场景=实现者写/改验收测试,或在隐藏模式下读到测试内容,即失败(只读模式下读取不算失败)。
  - AC-18(对应 FR-18):条件=一个行为变化样例 task;行为=核对 RED→GREEN 证据;度量=存在同一测试改动前失败、改动后通过的记录。失败场景=只有 GREEN 无 RED 且无 G-2 豁免披露,即失败。
  - AC-19(对应 FR-19):条件=一个纯文档样例 task;行为=核对豁免处置;度量=存在豁免记录,含理由+风险+验收中披露,或补了一条可失败检查。失败场景=直接跳过且无披露,即失败。
  - AC-20(对应 FR-20):条件=构造两类验收场景——某测试路线适用 trace/JUnit/跳过计数,与另一路线不适用;行为=分别运行验收;度量=硬要求(真实命令、exit、output、对应 oracle 证据)缺失即判失败;适用路线缺任一适用产物即判失败;不适用路线记 N/A+reason 且不判失败。失败场景=缺适用产物仍判通过、伪造产物、缺不适用产物(已记 N/A+reason)却判失败,或 N/A 无理由,即失败。
  - AC-21(对应 FR-21):条件=核对一个完成 task 的执行事实;行为=检查测试/验收技能的真实执行记录;度量=执行事实(命令、exit、output 位置)存在且可回读;整体完成宣称发生在真实入口联通实跑之后。失败场景=只有脚本自证或审查被当作功能验收,即失败。
- **oracle**:样例 task 展示真 RED→GREEN;纯文档豁免样例带披露;缺适用产物样例判失败,不适用产物记 N/A+reason 不判失败;整体完成只在真实入口联通实跑后宣称,代码审查不冒充功能验收(SD-05)。

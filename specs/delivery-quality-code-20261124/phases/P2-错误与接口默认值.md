# Phase P2 — 错误与接口默认值

这一阶段让新增的坏错误处理在真实 diff 里只剩一种可见结果——`候选，待处置`；
让默认值与接口深度成为审查必答的六问；让绕行退出票只落在阶段模板 `:201`；
让门命令回执只挂第 5 步、第 7 步读同一字节。
读完这张卡的人应当能开工、能独立验收，也能把它交给 P4 作者。

“假成功”是坏输入被空串、`0`、`false`、`null`、`[]`、`{}` 或空 catch 伪装成正常。
“默认值”是缺值时程序替调用方选的值，必须写清谁定、依据哪条。
“绕行”是明知不理想但暂时保留的旧路，每处要有唯一删除票。
“删除票”写在施工卡 `非目标` 行，由 build-plan 计划期写，审查只核不写。
“两问”是默认值谁定、坏输入会不会看起来成功；“四问”是接口深度四问。

## 哪些节必须写，哪些可以省？

模板的必填节全部在场；只属于末验阶段与写作脚手架的节不落盘。
本卡对应 phase-maker 八步：第 1 步在「开始前读什么」；第 2、3 步由 spec 与决策日志承接；
第 4 步在本节调研表；第 5 步在「首卡纵切」「首卡开工五列」与「真实供件登记」；
第 6 步在六张任务卡；第 7 步在纯指针索引；第 8 步在「下一消费者拿什么继续」。

| 节 | 本文件怎么处理 |
| --- | --- |
| 交出什么 | 写结果、非目标、改动前后、调研表、对应原问题/FR、首卡纵切、五列、供件、半径、回退、可能冲突的阶段 |
| 开工就绪表 | 写五列增量行，含基线字段与真实任务根核对 |
| 怎么验收 | 写三笔账、六段验收、非 UI 声明与预算 |

| 开始前读什么 | 写设计与代码锚点的读序 |
| 每个文件由谁改 | 写六个路径、首动作、前后写者 |
| 每张任务卡怎么写 | 写六张卡，任务 8 至任务 13 对应 T008 至 T013 |

## 这一 Phase 交出什么？

P2 交出「新增行里的假成功只报候选，六问有结论，退路只有一家票，回执只挂一步」的可执行版本。

- **本 Phase 结果**：`tools/cli/check-added-failure-masks.mjs` 在真实新增行上只报新出现的空 catch 与
  catch 体只返回空值，逐条标 `[EMPTY_CATCH]` 或 `[RETURN_MASK]` 并写 `候选，待处置`；
  `skills/simplicity-guard/SKILL.md` 多出默认值、假成功两问与接口深度四问；
  阶段模板 `:201` 是删除票唯一家；`workflows/build-code/SKILL.md` 第 5 步捕获门命令回执、
  第 7 步读回同一字节、第 8 步要求六问逐条带锚作答。
- **非目标**：做全仓历史扫描与整洁度门，可做但本次不选，本次只扫 `phase_progress.base_head`
  之后的新增行，历史噪声会淹掉新问题；不查默认值语义、不判理由真假，机器只报候选，
  处置由人写。
  - 绕行＝留全仓既有坏 catch 历史给扫描范围之外，用只看 `phase_progress.base_head` 之后新增行的
    `--base` 承接；删除条件＝既有坏 catch 逐条有 owner 处置，或检查器接进 `npm run check` 且全仓基线为 0；
    决定人＝计划负责人；结束条件＝全仓 `--base <任务起点> --strict` 扫出 0 候选、或历史清单逐条落 owner 的
    那次提交通过 `npm run check`。

### 首卡纵切

首卡是任务 8；沿公开入口、装配点、调用者、可见结果、失败信号写，
让没写卡的人能写出首读符号、首改路径与判错动作。

- **公开入口**：自测入口 `node tools/cli/check-added-failure-masks.mjs --self-test`；
  扫描入口 `node tools/cli/check-added-failure-masks.mjs --base <phase_progress.base_head> --task-path <任务根> --phase P2 --strict`。
  基线只用 build-code 第 1 步写入的 cursor，不取卡上开工就绪表的 HEAD：
  `node tools/cli/stage-runtime.mjs status --action=begin --stage=build-code --project=<p> --task=<t> --task-path=<root>`。
- **装配点**：`readPhaseBase(taskPath, phase)` 经 `runtime/task/task-store.mjs:44` 的 `readTaskFacts`
  读 `phase_progress`；`parseAddedLines` 的两步来源是 `git diff -U0` 与
  `git ls-files --others --exclude-standard -z`；判定链是 `maskSource` → `findCatchRegions` →
  `classifyRegion`，文件过滤是纯函数 `shouldScan`，汇总在 `runScan`。
- **调用者**：build-code 第 5 步 `verify --action=execute` 的执行者（`workflows/build-code/SKILL.md:117`）；
  第 7 步审查者读回同一回执（`:131`）；P2 实施者与独立测试者；P4 作者只读语义。
- **可见结果**：自测打印 13 行 `self-test: PASS <组号>` 与末行 `self-test: 13/13`；
  真实扫描打印 `candidate: <path>:<line> [RETURN_MASK] (catch@<n>)` 与
  `summary: candidates=N exempt=N skipped_files=N skipped_hits=N (候选，待处置)`；
  不带 `--strict` 退 0 只打印候选，带 `--strict` 有候选才退 1。
- **失败信号**：删规则 B 正则里的 `false` 后自测仍 `13/13`（自测变盲）；
  把 `+++ b/路径` 当新增行导致行号整体错一位；只走 `git diff` 一步、未跟踪文件 0 行；
  历史行出现在 `candidate:`；`exit 2` 被当成门红并记 finding。
- **首读符号**：`readPhaseBase`、`parseAddedLines`、`maskSource`、`findCatchRegions`、
  `classifyRegion`、`shouldScan`、`runScan`（首卡新建文件里的导出与内部函数）。
- **首改路径**：新建 `tools/cli/check-added-failure-masks.mjs` 与
  `tests/contract/check-added-failure-masks.test.mjs`，再在 `docs/architecture/move-map.json`
  的 `entries` 加两条。
- **判错动作**：范围错就修 `--base` 校验与 `shouldScan`；漏报就补规则 B 的空值备选；
  自测变盲就补对应输入样例，不删断言换绿；历史行出现在 candidate 时停手，回本卡作者核范围。

**验收 2：真实新增行上每条命中都有处置，零漏报。**

- 目标：用本 Phase 真实差异证明两类新增行各被命中一次并给出行号。

    | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{const g=JSON.parse(s).phase_progress;process.stdout.write((g&&g.cursor&&g.cursor.base_head)||"")})')

  printf 'try {\n  return readFileSync(p);\n} catch {\n  return null;\n}\n' > .probe-failure-mask.mjs
  node tools/cli/check-added-failure-masks.mjs --base "$base" --task-path <root> --phase P2 --strict; echo exit=$?

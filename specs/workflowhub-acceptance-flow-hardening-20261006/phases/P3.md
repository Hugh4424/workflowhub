### 验收 Phase 固定小节内容清单（T005 写入 phase 模板）

T005 在 `skills/spec-plan/templates/phase-template.md` 的 `## L1 — 可执行契约` 里、`### Tnnn —` 占位卡之前，新增一节 `### 验收 Phase 固定小节（只在验收 Phase 填写）`。该节逐项写下面 13 项。每项写成「填什么 + 判据」，不写成新 gate、新 stage 或新审查点。

1. 入口准则（ADR-018、AC-AFH-014）：逐条核对前置 Phase 的 Done、写入集是否落地、两份就绪件的 status；每条写「核对结果 + 证据路径」。
2. 两份就绪件（ADR-004、ADR-018）：数据就绪件与环境就绪件各一份，独立成件放 `quality/evidence/`，各写 status。同类别多写一个实例不算新文件类型。能提前设计的验收数据来自前置 Phase 的写入集与 Done；验收 Phase 只许补，补的数据要标来源档位；缺数据时写 `incomplete` 或 `unavailable`，不伪造。
3. 授权边界五项（ADR-005）：目标账号与环境、副作用白名单与数量上限、明确禁止的动作、授权有效期、失败即停条件。agent 全自动执行，不设人工确认，也不设人工执行。
4. 逐条结论（ADR-002、AC-AFH-003、AC-AFH-016）：每条 AC 一行，写 AC 编号、一个档位、一条具名证据路径。档位只用 `runtime/evidence/acceptance-evidence-validator.mjs:6` 的 8 值词表（`pass`、`fail`、`inconclusive`、`deferred`、`missing`、`inconsistent`、`incomplete`、`unavailable`），本模板只引用该词表，不复制成新词表。结论行数与 AC 条数相等，不用计数代替逐条。非 `pass` 一律不计通过。
5. 五类执行事实（ADR-014、AC-AFH-010）：命令与参数、cwd 与执行者、exit code 与 signal 与 timeout、原始输出落点、机器可读测试报告（记 runner 与版本）。`refs` 逐项标九类形态之一：`execution_record`、`machine_report`、`trace`、`screenshot`、`coverage`、`mutation`、`contract_check`、`red_original`、`negative_control`。首次失败、重跑通过时档位记 `inconclusive` 并标 `flaky`，不记 `pass`。
6. 效果评测（ADR-011、AC-AFH-010）：写清跟什么比、指标与统计量、正例与负例、原始输出落在哪个具名文件。本仓无 UI 时写一句 UI 判据（例如「worktree 无 `apps/`、无 `.tsx`、`.vue`、`.jsx`」），不用「无 UI」一句话免掉代码与接口面。禁止用环境指纹、产物 digest、哈希或版本相等判定，禁止用覆盖率数值或测试数量当通过判据。
7. 复验四项（ADR-015、AC-AFH-011）：复验者与修复者的上下文差异（具体 subagent 身份或具体 provider 名）；F2P 用例清单与 P2P 用例清单，两者计数都大于 0；所跑回归范围与「为什么这个范围是这次修改的保守超集」；三档判分：F2P 为 1 且 P2P 为 1 记 FULL，0 小于 F2P 小于 1 且 P2P 为 1 记 PARTIAL，其余记 NO。PARTIAL 不得记 `pass`；分母为 0 不判通过。
8. 变更批准（ADR-016、AC-AFH-012）：AC 或用例集合每次增删改都写独立审查批准者身份、`Rationale for Change`、`Impact Assessment`；登记列用 `Change Request ID`、`Impact Assessment`、`Approval Status`、`Closure Notes/Verification Status`。批准者不是实现者，也不在同一上下文。纯重构不改既有测试。改 AC 等于改承诺，要重新取得确认。没有变更时写「无加理由」。
9. 分诊与关闭（ADR-021、AC-AFH-017）：失败先复现。分诊最低字段：`Defect ID`、描述、是否可复现、`Version detected`、`Severity`、`Priority`、`Disposition`（初值 `Pending`）。分诊者不是实现者。终值 `Disposition` 只取 `Fixed`、`Won'tFix`、`Deferred`、`AcceptedRisk`、`Duplicate`、`NotABug`、`Referred`；取不修的值时写理由与风险接受人署名。关闭留痕：`Closed by`、`Date closed`、`Change reference`、`Test reference`、`Closure Notes/Verification Status`。
10. 回写五项（ADR-010、ADR-021、AC-AFH-017）：① `spec.md` 场景卡；② `spec.md` AC 表；③ phase 契约 `覆盖 AC`；④ `facts.jsonl` 既有字段；⑤ 这次修复本身的记录。每项写哪条 case 被改、为什么改、改后判定（档位取 8 值词表）。缺一项不算闭环。
11. 六项结论（ADR-018、AC-AFH-014）：评估（含局限）、与计划的偏差及原因、未充分测试的特性及原因、未解决事件（逐条）、残留风险、签核对象。每项非空，无则写「无加理由」。不新增独立验收报告文件类型。
12. 防自证五禁令（ADR-020、AC-AFH-016）：不用授权文本验证授权文本；不删到测试变绿、不改断言消音、不重跑到绿；黄金清单改动由另一主体批准；不用计数代替逐条；不把 `incomplete`、`unavailable`、`missing`、`unverified` 写成 `pass` 或 `succeeded`。判定器要求显式通过元素，不用「无失败即通过」。
13. 失败修复复验闭环（F-040 Q11、ADR-015、ADR-021）：失败 → 分诊（第 9 项）→ 根因调研 → 修复回到原 owner Phase 的 Task → 换上下文复验（第 7 项，F2P 加 P2P）→ 回写五项（第 10 项）。降级项（`deferred`、`unavailable`、`incomplete`）同段写风险承接人署名（ADR-017）。闭环复用既有 Phase 与 Task，不新增 stage、gate 或审查点。

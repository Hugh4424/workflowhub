## 这一 Phase 怎么验收？

假设本 Phase 全部实现、命令也通过，仍会漏「规则在真实页面里是否被遵守」；
那部分归 P3 的测试与 P4 的页面观察。
本 Phase 承接验收 2 与验收 3，七槽如下。

1. **验收标准**：验收 2 要五份正文九处段落有真实差异、版本按原格式上抬、
   派生入口版本列同步，且 `design.md` 与 `craft.md` 有「不适用」与理由。
   验收 3 要规则 1～4 各只有一个主权威，版本有实际使用点，并做负向检查：
   旧值源、旧采用依据、旧消费者仍可读。
   成功信号是三条卡命令退出 0 且差异文件数等于六。
   失败信号是只有标题没有内容、同一条规则两处细则、版本上抬没有使用点，
   或把「不适用」写成没有负向检查的挡箭牌。
2. **场景**：正常场景是规范作者在干净工作树里按段落回写并上抬版本。
   反向场景一：把 `components.md` 的版本退回 `1.0`，T002 的命令必须非零。
   反向场景二：把同一条规则整段复制到 `interaction.md`，独立读者必须判两处权威、要求合并。
3. **环境与数据**：环境是 PB 工作树，本 Phase 要求从 main 起的干净工作树（未决 1）；
   数据是五份正文与 README 的 HEAD 字节。本 Phase 实读（2026-11-02）：
   当前 PB `HEAD=5df81987`、主树 0 项未提交；从同基线 C08 干净树读正文。旧 `7723c321`/97 项及原型删除为历史（原研究不改写）。
   读旧值按 `git show HEAD:`；构造与清理不涉及外部服务，临时反例放自建临时目录，读回后删除。
4. **用例**：CASE-P2-1 对应验收 2，跑 T002 命令，预期退出 0。
   CASE-P2-2 对应验收 2，跑 T003 命令，预期退出 0。
   CASE-P2-3 对应验收 2 与 3，跑 T004 命令，预期退出 0。
   CASE-P2-4 对应验收 3 的负向检查：由独立读者按 F3 口径核旧值源与旧消费者仍可读（只能人读）。
   判定是显式断言（差异存在、版本字面值、段落关键词），不是「命令没报错」。
5. **谁判**：未参与写作的独立读者（另一执行单元），不需要用户本人到场。
   执行时点：三个任务完成、P2 收口之后。
   判定者拿到六份文件的 `git diff`、版本行、P1 影响表与验收 2、3 原文。
   判定者不改段落、不改版本，也不替作者补使用点。
6. **失败回修与重验**：失败信号是差异缺失、版本未上抬、或同规则两处权威。
   分诊到「回写不完整」回原文作者改同一段；「owner 未授权」停该文件、记 unavailable、
   其余文件继续。修后重验同一命令与负向检查，结论按新 diff 改。
7. **承接**：结论记在三个任务的 `git diff` 原输出与版本行；P4 与后续任务读同一份差异，
   缺口写进未完成项与 owner，不让结论只活在对话里。

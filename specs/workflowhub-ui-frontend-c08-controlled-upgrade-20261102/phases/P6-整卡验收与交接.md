  五类失败分支与未知消费者清单可读；未闭环项写明 owner、关闭条件与风险承接人。
- **非目标**：不重跑已闭合的全量测试；不改 P1～P5 的原件；不改验收口径；
  不把跨任务判据（采用记录、main 回写）写成完成。
- **改动前**：前五个 Phase 各交原件，但没有一张逐条结论，也没有失败分支的集中记录。
- **改动后**：验收表十二行齐全，非通过项写明原因与 owner；分支表五类齐全，
  受控缺证据样例单独记；交接读者可按表复读。
- **与相邻 Phase 的边界**：P5 交后续安排与流程回执；本 Phase 只消费这些原件并补必要
  未闭环 case，不重跑已闭合全量。
- **主要风险**：用一条 AC 的证据补另一条，或用汇总分数吞掉单条失败。
  若因它返工，回到该 AC 的原件重判，保留原失败与缺口，不改判据。
- **下一步**：主会话按交接单收口；后续真实任务按缺口与 owner 继续。
- **动手前必读**：`spec.md` 的 Appendix A 与「测试计划是什么？」；五个 Phase 的 Done 段；

## 这一 Phase 怎么验收？

假设本 Phase 全部实现、命令也通过，仍会漏「跨任务部分是否真的被采用」；
那部分在 C08 内不可闭合。本 Phase 承接全部 12 条验收，七槽如下。

1. **验收标准**：独立代码审查回执在场且读过真实 diff；12 条验收逐条给一个档位
   （通过、失败、部分、不可用、未完成）与一条具名证据；
   五类失败分支各五项齐全；未知消费者有清单与检索范围。
   成功信号是两条卡命令退出 0、验收表十二行与分支表五节齐全。
   失败信号是空格子、用汇总分数代替逐条、用另一条 AC 的证据补缺口、
   把 pending 或 incomplete 写成通过。
2. **场景**：正常场景是验收者按 Appendix A 逐条读原件并落结论。
   反向场景一：删掉一条 AC 的证据指针，命令必须非零。
   反向场景二：把 AC5 的采用记录写成完成，独立读者必须判越界（跨任务判据）。
3. **环境与数据**：环境是认证工作树与任务库；数据是 P1～P5 的原件、任务事实库与
   Appendix A 原文。本 Phase 实读（2026-11-02）：任务库 `tasks/` 下无 C08-FU-01 目录、
   C06 已合并（f592096a）、预存测试修复回执可读、canonical 与副本两处 sha256 可读。
   不构造外部服务；页面不可用项按 P4 记录原样引用。
4. **用例**：CASE-P6-0 对应独立代码审查：审查者读 P2/P3 diff、P1 消费者、P4 矩阵与未改行为，
   写 `P6-final.json`，缺件时 T014 不得进入结论。
   CASE-P6-1 对应 12 条验收，跑 T014 命令，预期退出 0。
   CASE-P6-2 对应验收 6，跑 T013 命令，预期退出 0。
   CASE-P6-3 对应 AC5 与 AC7 的跨任务部分：由独立读者复读，预期判 pending 与 incomplete
   而不是通过（只能人读）。
   判定是显式断言（十二行、五节、五项字段），不是「命令没报错」。
5. **谁判**：未参与实现的独立读者与独立审查者，另一执行单元，不需要用户本人到场。
   执行时点：P5 收口之后、独立审查回执产出之后、本 Phase 两条命令都跑完之后。
   判定者拿到验收表、分支表、P1～P5 原件、Appendix A 原文与任务事实库。
   判定者不改判据、不改档位、不代用户接受风险。
6. **失败回修与重验**：失败信号是某条 AC 缺证据或档位与原件不符。
   分诊到「原件缺」回原 Phase 补，「判据理解错」回原决定 owner，「跨任务未达」记 pending。
   修后重验该条与受影响面，结论按新原件改，重报由原判定者做。
7. **承接**：结论记在 `quality/evidence/P6-acceptance.md`、`quality/evidence/P6-failure-branches.md`
   与 `quality/reviews/P6-final.json`；交接读者读这三处拿结论与缺口。
   审查缺件时本 Phase 不得收口。

## 怎么验证？

用 Appendix A 的 12 条判据逐条读原件，用五分支表判失败与未知是否保原事实。

开工前四要素：验证层是逐条结论与分支表结构；
命令是下方两条；预期是都退出 0 且十二行、五节齐全；
失败条件是空格子、用汇总分数代替逐条、或跨任务项写成完成。

| 目标 | Task | 角色 | gate_cmd 与预期退出码 | 判据与证据路径 |
| --- | --- | --- | --- | --- |
| 五类失败分支保原事实 | T013 | RED | T013 命令；缺分支或缺五项时退出 1 | ORACLE-P6-FAILURES 与 `planned: quality/evidence/P6-failure-branches.md` |
| 五类失败分支保原事实 | T013 | GREEN | 同一命令退出 0 | ORACLE-P6-FAILURES 与 `planned: quality/evidence/P6-failure-branches.md` |
| 12 条验收逐条结论与交接 | T014 | RED | T014 命令；少一行或缺证据指针时退出 1 | ORACLE-P6-ACCEPT 与 `planned: quality/evidence/P6-acceptance.md` |
| 12 条验收逐条结论与交接 | T014 | GREEN | 同一命令退出 0 | ORACLE-P6-ACCEPT 与 `planned: quality/evidence/P6-acceptance.md` |

RED 归因：目标行为失败（判据是验收表与分支表的必需内容；表缺内容即失败）。
跨任务项未达时不是目标 RED，是 pending 与 incomplete，按档位记，不写成通过。

覆盖上限：整份 Phase 只证逐条结论与分支表在场且可读；
不证跨任务采用、不证 main 已回写、不证外部方法可再分发。
显式不覆盖：不覆盖模拟记录页实现、不覆盖真实用户长期效果、不覆盖其它任务的验收。

失败了怎么办：

- **风险**：用一条 AC 的证据补另一条；把 pending、incomplete 写成通过。
- **影响**：整卡验收失真，交接读者误判可收口。
- **缓解**：每条 AC 一条具名证据；非通过项写原因、owner 与关闭条件。
- **回滚**：只撤回本 Phase 的验收表或分支表，保留全部上游原件与原失败。
- **补救与交接**：缺证据回原 Phase 补；跨任务未达保留 pending 与 owner；
  审查未产记 incomplete 并写 owner。
- **触发条件**：任一 AC 缺证据指针、任一分支缺五项、或出现汇总分数。

## 验收 Phase 才能做的检查

本节是本任务唯一末验收 Phase 的附加检查，逐项写实，不新增 stage、gate 或字段。

1. **入口准则**：逐条核对 P1～P5 的 Done、写入集落地与两份就绪件 status，并核独立审查回执。
   P1 表、P2 三份差异、P3 测试、P4 页面、P5 四份回执、`P6-final.json` 各写一行结论与证据路径；
   缺件写缺口与 owner，不把「有文件」当落地。
2. **两份就绪件**：数据与环境两件在 `P4-browser.json` 里以 `data_ready`、
   `environment_ready` 两块具名给出，含夹具与真实数据来源、服务基址与存储根取得方式、
   各自 status 与缺口恢复条件；缺项记 incomplete 或 unavailable，不伪造。
3. **授权边界**：目标账号与环境是 PB 只读加新工作树、任务库证据区写入；
   副作用白名单是测试、截图与证据文件；禁止动作是改 C03 语义、改共享 hook、
   改全量 `.lg-warning`、提交 Git 之外的交付；授权有效期到本任务收口；
   失败即停条件是页面不可用、写权限被拒或 owner 未授权。
4. **逐条结论**：12 条验收各一行，写编号、一个档位与一条具名证据指针；
   行数必须与 12 相等；非通过项写未通过原因与 owner；档位只用
   `runtime/evidence/acceptance-evidence-validator.mjs` 的八值词表，不造新词。
5. **五类执行事实**：逐条记命令与参数、cwd 与执行者、退出码与 signal 与超时、
   原始输出落点与机器可读报告；`refs` 各标 execution_record、machine_report、trace、
   screenshot、coverage、mutation、contract_check、red_original 或 negative_control；
   首次失败重跑通过记 flaky 与 inconclusive，不记通过。
6. **效果评测**：本任务多数判据不是指标类，写不做的理由与影响；
   页面观察只报实际读数与覆盖，不用覆盖率或测试数量判通过，不加数值门。
7. **复验四项**：复验者是 P4 的独立测试者与写 `P6-final.json` 的独立审查者，
   与实现者上下文不同；F2P 是 P3 的目标断言清单，P2P 是既有用例、共享告警回归、
   `live-ledger-locator`、`live-pages` 与页面观察清单，两者计数都大于零；
   所跑范围是最小可证伪集合并写明理由；未知影响面与三档判分按原件记。
8. **变更批准**：本任务不增删验收集合；确有测试变更时写变更请求编号、影响评估、
   批准者与关闭说明，批准者不得是实现者。
9. **分诊与关闭**：失败先复现，分诊者不是实现者；每条写缺陷编号、描述、可复现性、
   发现版本、严重度、优先级与处置；终值只取既有词表值；不修的写理由与风险承接人。
10. **回写五项**：`spec.md` 场景卡与验收表、Phase 覆盖验收、`facts.jsonl` 既有字段、
    本次修复记录各写改了哪条与为什么；缺一项不算闭环，但回写不得改判据。
11. **六项结论**：逐项写评估与局限、与计划的偏差及原因、未充分测试的特性及原因、
    未解决事件、残留风险、签核对象；每项非空，无则写「无」加理由。
12. **防自证五禁令**：不用授权文本验证授权文本；不删到测试变绿、不改断言消音、
    不重跑到绿；黄金清单改动由另一主体批准；不把 incomplete、unavailable、missing、
    unverified 写成 pass；判定器必须要求显式通过元素。
13. **失败修复复验闭环**：失败、分诊、根因、修复回原 Phase 的任务、换上下文复验、
    回写五项；降级项 deferred、unavailable、incomplete 同段写风险承接人署名；
    闭环复用既有 Phase 与任务，不新建阶段。

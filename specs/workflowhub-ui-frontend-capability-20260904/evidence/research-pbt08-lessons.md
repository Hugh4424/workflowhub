## 2. 根因清单（合并两份文档）

1. **无"设计提取"环节**：Tailwind 类名 ≠ 像素值，R1 在错误地基上打补丁。
2. **无组件级对照清单**：用户成为人肉 diff 引擎；设计稿有的结构缺失/自创（hero 价格块、块外盈亏比行）。
3. **CSS 三代叠加**：`simulation-pages.css` 1056 行含 417 个历史块，同选择器后写覆盖先写→"改了没效果"。
4. **验证脆弱**：探针类名写错假阴性、层级量错假阳性、无对照表驱动工具；API 重启导致运行态数据丢失。
5. **spec 信息密度不足**：转折点 = R3 起把设计稿组件源码逐行贴给 builder → 一次通过。规格密度与返工次数强负相关。
6. **零边界压力测试**：长 token 撑爆、hover 8px 死区等经典坑无一兜底。
7. **反馈歧义不消歧**：「右上角」猜错目标，10 秒确认可省一整轮。
8. **环境守护缺失**：dev server/API 挂两次；分支/worktree/服务 cwd 未绑定（luna 认定为"最致命"——5173 连 main 而 T08 有独立 worktree）。
9. **单测绿灯 ≠ 浏览器验收**：单元测试证明不了 CSS 未被旧规则覆盖、viewport 下尺寸正确、hover 可见、真实 DTO 能渲染。
10. **状态样本不稳定**：只拿数据库碰巧存在的一条记录验收；固定全状态 fixture 与真实运行证据应分工。

## 3. 量化拆分（可用于后续优先级）

- ~60% 缺陷可由"设计提取 + 组件对照清单"在编码前消灭
- ~25% 可由"系统验证 + 边界压力测试"在交付前消灭
- ~10% 是 CSS 历史债务（清场检查）
- ~5% 是沟通消歧

## 4. 关键教训名言

-「把用户的眼睛从验收流程里拿掉：用户只应在最后一轮看到成品，而不是前五轮当 QA。」
-「瓶颈不是 builder 能力，是规格信息密度。」
-「没有确认 5173 服务的是哪个 branch，就不能说'页面已修复'；没有设计参考和多视口截图，不能说'UI 已对齐'；没有真实 DTO/fixture 到页面区域的证据，不能说'功能已接通'。」

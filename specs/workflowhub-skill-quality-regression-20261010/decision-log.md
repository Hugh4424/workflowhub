## 工作包 ① — 诊断：20261008「技能现代化」引起的执行质量退化

### 问题与边界

- 症状面有三个可观察点：make-decision 的 decision-log 体积膨胀（card-09 约 579KB，card-06 约 200KB，现代化任务自身约 120KB）；build-plan 只产出 1 个 phase；build-code 执行质量待评。
- 边界：本工作包只产出「事实 + 根因 + 可证伪的机制说明」，不产出修复；不评判用户当时的方向选择对错。
- 已知约束：三处症状发生在不同任务、不同仓库（PaperBuilder 与 workflowhub），可比性需要显式说明。

### 衰退判据（本任务全量审计统一口径，已按 U-007 定稿，关闭 OI-007）

对每个被现代化改过的文件，逐条判「变好 / 变坏 / 无实质变化 / 无法判断」，每条都要能指到具体行：

- **C1 约束丢失**：原来明确禁止、要求或限定的东西（长度、粒度、上限、必须产出某物）被删掉或弱化为建议。
- **C2 自相矛盾**：同一文件内，或本文件与它引用的模板/技能之间互相冲突。
- **C3 语义变空**：新增句子读起来正确，但没有可执行动作、没有判据、没有 owner。
- **C4 表达膨胀**：单位信息占用字数明显变多（一句话写成三句、规则重复三遍、模板句堆叠）。
- **C5 可执行性下降**：执行者按文本无法确定唯一动作，需要额外猜测。
- **C6 纪律/门混淆**：新增会阻断推进的硬门，或把原本的硬约束降级成建议。
- **C7 重复与漂移**：同一规则在多处重复且措辞已经不一致。
- **C8 可搬运性破坏**：绑死特定宿主、绝对路径、特定 CLI 或账号。

判据只用于判定「是否衰退」，不新增机器门、不阻断推进；判定不了就写 `无法判断` 并说明缺哪份事实。

- H2：build-plan 只出一个 phase 来自「phases 按需创建 / 只写当前要执行的 phase」这类懒创建规则被写进方法，导致计划阶段合法地只交一个 phase。可推翻证据：会话记录显示是上下文/中断/工具导致，方法文本没有相关许可。

## 工作包 ② — 修复：把退化机制改回去或改成更简的形态

### 问题与边界

- 待工作包 ① 给出根因后再定方案；本稿只登记方向候选，不作承诺。
- 边界：修复对象是 workflowhub 仓库自己的 `workflows/**`、`skills/**` 等方法文本；不重跑 PaperBuilder 的历史任务。

### 方向候选（已由 U-002 收敛为 ADR-001）

#### ADR-001 — 定点修 + 结构性清理（不做整体回滚、不加覆盖层）

- 决定：只改被诊断证明造成退化的规则，同时做结构性清理：清掉模板里的模板句、清掉重复引用、并把「每新增一条规则必须同时删掉或合并一条」写成可核查纪律。
- 为什么：整体回滚能保证不劣于原版，但会连带丢掉现代化里真正有效的部分，且回滚本身无法说明「哪条规则有害」；覆盖层会让新旧规则互相冲突（命中 C2）。
- 否掉了什么：整体回滚到现代化前再择优吸收（工作量最大且无法归因）；另加一层「形状与长度上限」压制（新旧规则打架）。
- 后果与风险：定点修可能漏掉同源问题；靠「留删清单交用户复核」与全量审计的逐文件结论兜住。
- 影响面：仓库根 `workflows/**`、`skills/**`，以及被诊断为根因的 `runtime/stage/stage-content-contracts.mjs`。

#### ADR-002 — 允许改 runtime 写集校验器

- 决定：修改 `runtime/stage/stage-content-contracts.mjs`，使其区分实现文件与治理文件（README、`architecture/components.yaml` 等），不再把治理文件的共享写权当成写集重复；连带允许改其测试。
- 为什么：这是 build-plan 单 phase 的直接诱因；只改文档兜不住，换一个执行者还会再犯。
- 否掉了什么：不改代码只用方法文本兜住（诱因仍在）；把校验降级为只警告（等于废掉写集冲突检查）。
- 后果与风险：动了 runtime，可能牵出配套测试；若改错会让真实写集冲突漏检——因此保留「真实重复仍报错」的判据，只放行治理文件类别。
- 影响面：`runtime/stage/stage-content-contracts.mjs`、其测试、`workflows/build-plan/SKILL.md` 与 `skills/spec-plan/**` 中对 phase 写集的描述。

#### ADR-003 — 范围包含现代化前既有的问题

- 决定：凡影响执行质量的机制问题都纳入本次修复，不按「是这次引入的还是原来就有」切分。
- 为什么：用户明确要求一起修；按引入时间切分会让老问题继续被误记到新改动头上。
- 否掉了什么：只修现代化引入的（范围清楚但留下老账）；先列出再单独决定（多一轮往返）。
- 后果与风险：范围变大、周期变长；靠发现清单的严重度排序与分批实施控制。
- 影响面：工作包 ① 的全量审计口径与工作包 ② 的修复批次划分。

#### ADR-004 — 留删由主会话按证据裁定，清单交用户复核

- 决定：现代化新增内容的保留/删除由主会话按 C1–C8 判据与实证价值裁定，产出逐条清单（留/删/改 + 依据）交用户复核；用户不复核不阻塞本阶段继续。
- 为什么：用户不愿自己列清单；但「哪些是他当时特意要的」只有他能最终确认，所以裁定权归主会话、确认权留用户。
- 否掉了什么：全部重新评估包括删掉（可能删掉用户真正想要的）；用户自己列清单（增加用户负担）。
- 后果与风险：裁定可能偏离用户初衷——用逐条清单＋复核入口兜住，且任何删除都保留 before 原文。
- 影响面：`workflows/**`、`skills/**` 全部被现代化改过的文件。

#### ADR-005 — M1：只删真 no-op 与真重复（**已按 U-007／U-009／U-020 三次修订；原「删元信息」决定全部推翻**）

### 对抗性方向检查（adversarial-direction-check，主会话，不设否决权）

- **是否过早锁定**：否。ADR-001 在 F1–F4 之前定，但 F3（真正净损失只 3 处行内）与 F2（29.4 KB 无消费者内容）独立支持了「定点修＋结构性清理」，方向经受了反向检验。

无。

## 需求保真（fidelity）

本节是 SD-09 在 card-02 材料中的落地结构。四条规则**可直接抄入 decision-log**，抄入后即成为本卡的常驻机制（不是一次性动作）。

### 规则 1 — 双层结构（逐字层 + 派生层）

- **原始声明层**：用户原始陈述、母 PRD 逐字原文、规划 decision-log 逐字原文。**逐字、只追加、不可改写**。
  - 只追加：发现缺口只追加新条目，旧条目一字不改（与 SD-10 append-only 同源）。
  - 不可改写：包括不得"精简"、不得"归纳"、不得"换个说法让它更好读"。截断必须用「…」明确标出。
  - 物理位置：`## 原始声明（verbatim，append-only）` 单一节。此节之外不得出现原始声明的改写版本。
- **派生层**：任何由原始声明推出的需求、设计项、决策、验收条目。**每一条必须带 `source` 锚点**，锚点指向原始声明层中的稳定 ID（如 `REQ-###`、`U-###`、`SD-###`、`Q##`）。
  - 锚点只用稳定纯文本 ID，**禁用哈希、禁用行号**（行号会腐化；哈希已由 SD-17/OI-013 全删）。
  - 派生层可以精炼、可以合并、可以排序——这正是"精炼"的作业面。
- **单向性**：原始层 → 派生层 单向引用。派生层不得反向"修正"原始层的表述；发现原话有歧义，只能追加一条澄清条目并标 `待复核`。

### 规则 2 — 三档结论（每项必有一档，不许留空）

对**每一条**原始声明，必须给出且只给出以下三档之一：

| 档位 | 含义 | 必须写什么 |
| --- | --- | --- |
| `接受` | 原口径被完整承接，无改动 | 必须写**承接在哪里**（文件 + 节 + ID）。写不出落点不得判「接受」 |
| `接受但有偏离` | 原口径被承接但被改动 | 必须写**改了什么（原口径 vs 当前口径逐字对照）+ 为什么**。只写"有偏差"「略有调整」视为未填写 |
| `拒绝` | 不承接 | 必须写**理由 + 依据**（引用母 PRD 原文、用户原话或宪法条款）。依据为空不得判「拒绝」 |

- 「拒绝」不等于「忽略」：拒绝项必须进入台账、必须可见、必须由用户裁决或由材料给出显式排除理由（母 PRD：每项需求有负责工作包**或明确排除理由**）。
- 三档**互斥且穷尽**：不接受第四档（如"待定""部分接受"）。确实无法判定时，标 `拒绝`（现状=不承接）并在处置动作里写"重开 Talk 重确"。

### 规则 3 — 强度校验（逐条比对，不按类别查有无）

- 覆盖核对**必须逐条比对原始需求是否被削弱**，不能只按类别查有无覆盖。
- 现成的反面证据（规划 decision-log 机制诊断#6）：**「覆盖核对只按类别、不校验强度：只检查六节点/类别有无覆盖，不比对每条原始需求是否被削弱 … 后果：弱化在检查里不可见，所以既没被发现也没被告知」**。card-02 的 OI-006 覆盖矩阵「每个 R 有下落、每个 D 有出处，零孤儿」正是这一形态，必须升级。
- 强度校验的三个必答问（逐条）：
  1. 原句里的**限定词**还在吗？（否定词「不建/不得/不再/不许」、数量词「2–5/7 个/8 条/三条」、条件词「仅当/若/必须」、例外词「除…外/不适用时」）
  2. 原句要求的**动作**被替换成了什么？（例：动作替换 vs 落点后移 vs 范围收窄）
  3. 削弱发生在材料里是否**可见**？（本表即是可见化载体）

### 规则 4 — 待复核（原话一改，派生项全部挂起）

- 原始声明一旦改动（追加澄清、用户改口、Supersession 标注），**所有派生项标记「待复核」**。
- 「待复核」是**标记，不是门禁**：不阻断 build-code 开工、不阻断阶段推进（SD-17 零机器门禁）；只在完成宣称与阶段末披露中如实列出未复核项。
- 用户一旦对某条偏离/拒绝给出裁决，该条从「待复核」转为「已裁决」，并**只追加**一条裁决记录（不改原条目）。

### 本卡为何此前会压缩（机制成因，如实记录）

机制诊断#6（覆盖核对不校验强度）与 SD-09 的缺失在本卡同时存在：
1. 没有逐字层 → 原话一旦被"归纳"，对照面就消失了，"压缩"不可见；
2. 没有三档 → T 表全部只写「用户选择」，偏离与拒绝无处安放（如 T-019 对 AC-07/AC-08 的改写就未被标注）；
3. 覆盖矩阵按类别查有无 → 弱化即使发生也不会被判失败。
本节的四条规则即针对这三处；本文件第 2、3 部分是该机制的**首次实际应用**。

### 保真机制自检

#### 1. 这条机制如何防止再次压缩？（可操作判据）

压缩之所以能发生且不被发现，是因为**对照面不可见**（机制诊断#6：「弱化在检查里不可见，所以既没被发现也没被告知」）。本机制提供四组可操作判据，**任何一条判据为"否"即判压缩发生**：

- **判据 1（对照面存在）**：每一条原始声明，在"当前承接现状"列必须有对应文字。**空 = 压缩**。
  - 操作化：保真表**两列并列**——左列逐字原话，右列承接现状。没有右列即为压缩。
- **判据 2（四大压缩形态逐条查）**：对每条原话，问且只问四问（四问即第三部分归纳出的四种形态）：
  1. **判据是否被替换？** 原话的判定单元/度量是否还在？（例：事实→ID、门槛→分级）
  2. **落点是否被后移？** 原话要求的动作是否被移出本卡？（例：真实 task 抽验→CARD-10）
  3. **范围是否被收窄？** 原话列举的数量在承接处是否变少？（例：五项声明→两项、12 核心→8 条）
  4. **是否有整簇丢失？** 原话所属的需求簇（如"G-2 豁免+披露"、"逐字双层+三档"）是否整簇不见？
- **判据 3（限定词守恒）**：原话中的**否定词**（不建/不得/不再/不许/不允许/禁止）、**数量词**（2–5/7 个/8 条/12 条/三条/五项）、**条件词**（仅当/若/必须/只有）、**例外词**（除…外/不适用时/纯文档等）在承接处必须逐字可查。
  - 操作化：把原话中的限定词抄成一张小清单，逐条打勾。**任一限定词在承接处找不到 = 该条判「接受但有偏离」或「拒绝」，不得判「接受」。**
  - 实证：L-01 丢的是否定词「不建 severity 门槛」；L-03 丢的是数量词「12 条」；L-06 丢的是条件词「仅当…时」与例外词「纯文档等」。
- **判据 4（三档不得留空）**：覆盖率的分母不是"类别数"而是"原始需求条数"；**每条必须有且仅有一档**。任何"部分登记/未处理"必须落到 `接受但有偏离` 或 `拒绝`，并在处置动作里给出动作。
  - 操作化：一条**只按类别**的覆盖矩阵（如"六节点全覆盖"）**不得**作为通过证据；通过证据必须是"逐条有档位"的保真表。
- **判据 5（计数可复核）**：三档各自的条数必须可加总、可与主题表核对（本表第 3 部分的分布总表即此判据的实现）。**"零孤儿"必须带计数**，否则不可证伪（见 NEW-01）。

#### 2. 与「精炼」目标如何共存？（张力 X-01 / X-18 的调和：逐字区与指针区物理分离）

张力两端都是用户原话：一端「避免文档太长、太啰嗦」，另一端「又没有遗漏信息」「原始声明不得改写」。**不要用字数去调和，用位置去调和**：

| 区 | 放什么 | 规则 | 谁读 |
| --- | --- | --- | --- |
| **逐字区**（唯一新增的"长"） | 原始声明逐字原文、三档结论表、偏离说明 | 只追加、不改写；只出现在**单一节**内；不复制到其他任何文件 | 人（追溯、裁决）、CARD-10（存在性核对） |
| **指针区**（正文、spec、phase、索引） | 精炼后的目标/设计/契约/判据/验收 | **只写稳定 ID 指针**（`见 REQ-D-20`、`见 U-002-10`），**不粘贴原话** | 执行者、低智力模型、审查者 |

- **物理分离的三条硬规则**：
  1. 逐字只写**一次**（在逐字区），任何其他位置出现同义改写版即判重复权威（与 SD-13② 无重复契约检查同一判据）；
  2. 正文引用原话时**只给 ID + 一句结论**，不给原文；
  3. **契约字面量例外**：接口契约、错误码、命令、验收判据这类**必须逐字复制才能正确执行**的字面量，按 T-018 判据 3 例外允许逐字复制（R-E 修正）。
- **精炼的作业面是派生层，不是原始层**：`接受` 的条目在正文里可能只占一行指针；`接受但有偏离`/`拒绝` 的条目才需要正文展开（因为要写"改了什么+为什么"）。**压缩风险高的条目自然获得更多版面**，这正是"重要地方不简写"的机制保证。
- **不新增第五份材料**：逐字区与三档表**并入现有 `decision-log.md`**（作为一节），不新建文件（遵守 OI-016⑤ 与 U-001#8"不要搞这么多文件"）。
- **实证**：本文件采用同一分离——第 1 部分是规则（指针区形态），第 2/3 部分的逐字列是逐字区，正文只引 ID。

#### 3. 会不会变成新的「刚性文档仪式」？（母 PRD 局部风险 D-31；避免方式）

**会，如果把它做成"每次都要填完整张表"的仪式。** 母 PRD D-31 已点名该风险：「把「单一权威」做成新的刚性文档仪式(与 R-007 减阻塞目标冲突)」，且 U-001#8/I-19 的病灶正是「有一点问题，agent 就搞一大堆严格验收、新对象、新标准、新流程」。避免方式六条，**每条都要写进 spec 而不是只在这里说**：

1. **本机制不构成门禁**：三档结论与强度校验**只在完成宣称与阶段末披露中生效**，不阻断 build-code 开工、不阻断阶段推进（SD-17 零机器门禁、恰两道人为门）。**"待复核"是标记不是 gate。**
2. **一次性构建 + 增量追加**：全量保真表**只在需求清点这类事件时构建一次**（如本次），此后只追加新出现的原始声明与裁决。**不要求每个 task 都从零构建 38 行 × 316 条的表。**
3. **规模豁免写在机制里**：小任务/纯文档任务按 FR-08「小任务可用简短章节，**不机械增加文件**」——三档表可以只有 3–5 行；**行数不由机制规定，由原始声明条数决定**。
4. **不新增控制面**：逐字区与三档表是 `decision-log.md` 内的**一节**，不是新文件、不是新命令、不是新持久对象、不是新 schema（满足 OI-016⑤ 与 AGENTS.md"没有当前消费者的重复控制面不新增"）。
5. **本机制自身接受"新增理由"审查**：按母 PRD F-05/J-08「每项新增规则必须给出当前缺陷或用户结果理由」，本机制的理由是**已发生的真实缺陷**（U-002「我的原始需求都被你压缩了」＋机制诊断#6），不是流程偏好。若将来停止规则生效后无真实失败再触发，本机制应允许**降级为只读参考**。
6. **与 D-31 的第二条联动**：文档形态争议（"每 phase 一份完整文档"曾被推翻）**以 Q17 定稿为准**；保真表只记录"原口径 vs 当前口径"，**不重新裁判形态**——裁判权在用户。

**判据（会不会变成仪式的自检）**：若出现下列任一情况，即判本机制已退化为仪式，应删减：
- (a) 表里出现多行"接受"但没有任何落点（填空式）→ 判据 1 失效；
- (b) 三档结论被写成第四档或留空 → 判据 4 失效；
- (c) 有人为了"填满表"而新增不存在的原始声明 → 违反逐字层不可改写，**立即停下回报**；
- (d) 表的存在被用作"不许开工"的理由 → 违反第 1 条，**撤销该用法**。

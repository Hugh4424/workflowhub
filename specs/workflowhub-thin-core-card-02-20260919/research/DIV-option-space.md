# DIV：文档与审查体系设计的扩散式选项空间

> **本体裁声明（先读这一段）**
> 本文件是**扩散（divergence）产物**，不是设计方案、不是建议书、不是排序。
> - **不给最终推荐**，**不排序**，**不替决策者做取舍**，**不写"倾向性建议"**。
> - 每个选项都按同一格式写全要素；越不像主流做法的选项，越被保留。
> - 目的是把可能性摊开，供后续（可能在另一轮）做组合或取舍。
> - 若某个选项看起来"明显不好"，本文件仍列出并写明它的代价，因为**代价本身就是决策信息**。
>
> **证据标记约定**（全篇统一，用于满足"标注哪些有实证支撑"）
> - `【实证】` — 报告中有量化实验、受控对照、可核对的官方 changelog/官方文档原文、或第三方实测支撑。
> - `【经验】` — 报告明确标注为工程经验、厂商博客、专家观点、单评价者一手体验。
> - `【间接】` — 报告中的机制/数据支持这个方向，但没有在该具体形态上做过直接测量。
> - `【缺口】` — 报告明确写了"未找到证据 / 被证伪 / 不得引用"。
> - 每个选项末尾给一个**主标记**（最支持它的那一类证据），字段内部可再混标。
>
> **引用格式**：`报告名 §章节`（例：`R-D §4.4`、`I-B §4 K6`、`R-A §8 M10`）。所有引用的原文均在这 9 份报告内，本文件不引入新来源。

## 轴 1：decision-log 的形态

> 背景约束（所有轴 1 选项都在这条约束下被评价）：下游是**弱模型按 spec/phase 写代码**，且 `decision-log` 是"原始需求、用户选择、理由、风险、非目标与延期方向"的唯一权威（`I-B §1.1`）。同时 `I-A §3` 记录了现状病灶：741–1002 行、过程记录与被审内容同层（P-02）、重要内容被压成一句（P-03）、决策块样板行逐块重复（P-06）、隐含假设未写明（P-12）。

---

#### 轴1-01 极简 ADR（Nygard 五节）
- **做法**：每个决策一份极短文件，固定五节：Title / Status（proposed·accepted·rejected·deprecated·superseded）/ Context / Decision / Consequences。全文约 13 行量级，一个决策一个文件，文件名带序号。
- **谁写/谁读/谁执行**：高智力模型在 make-decision 阶段写；人（决策者）读；弱模型执行阶段原则上**不读**（它读 spec/phase 的投影）。
- **优点**：单决策原子化，状态机（superseded）天然支持决策演化；长度天然抗膨胀；对"追溯"只保留最小充分信息。
- **代价与风险**：跨决策的**关系**（依赖、冲突、组合）无处安放，需要靠约定或索引重建；"用户真实选择"与"选项清单"容易被压成一句（正是 `I-A` P-03 的形态）；对弱模型不可直接执行，必须再翻译。
- **最适合的场景**：决策数量多但彼此独立、且下游总能从 spec 反推的场景；团队已有 ADR 文化时迁移成本最低。
- **现实案例或证据**：`R-E §3.1`（Nygard 模板 5 节 13 行，官方原文骨架）；`R-E §3.3`（含 11 个 ADR 反模式与长度/好坏实践）`【实证】`（模板为公开标准原文，非实验证据）。
- **与其它选项的组合性**：**可叠加**——作为 轴1-04 三层中最底层的"每决策一份"，或作为 轴1-08 事件溯源中的事件类型；**互斥**于 轴1-05 单一完整账本（除非用索引层胶合）。

---

#### 轴1-02 MADR 三级模板（按需取用）
- **做法**：同一套模板给三个厚度档（full / minimal / bare），团队按决策重量自选；full 版含 Context and Problem Statement / Considered Options / Decision Outcome / Consequences，并显式写出"被考虑过的选项"。
- **谁写/谁读/谁执行**：make-decision 主会话写；人读；下游按需引用。
- **优点**：**同一形态覆盖不同重量级决策**，避免"小决策被大模板撑爆"或"大决策被小模板压扁"；`Considered Options` 字段正是当前 `I-A` P-03 缺失的"真实选择"。
- **代价与风险**：档位选择本身需要判断，容易"一律用 full"从而回到膨胀；三档会产生跨文档可比性问题。
- **最适合的场景**：决策重量分布极不均匀、且希望一套模板通吃时。
- **现实案例或证据**：`R-E §3.2`（MADR 三级模板原文：**minimal** = 3 必填节 Context and Problem Statement / Considered Options / Decision Outcome，适用大多数决策；**bare** = 全部章节但无解释文字，供熟手与工具生成；**full** = 全部章节 + 每节填写指引 + 可选元数据 status/date/decision-makers/consulted/informed，供新手与模板分发）；其中 `Context` 被限制为"两到三句话"，是**全模板唯一硬数字字段**（因为背景最易膨胀），且 `Considered Options` 默认只列标题、Pros/Cons 为可选章节 `【实证】`（MADR 官方模板原文）。同构机制：`R-F §3.1` 的 Tessl 三承诺度（spec-assisted / spec-driven / spec-centric）与 Kiro 的 Feature/Bugfix/**Quick** Spec 三档 `【实证】`（`R-A §2`、`R-F §3.3` 官方文档）。
- **与其它选项的组合性**：**可叠加**于几乎任何其它形态（档位是"厚度旋钮"，不是容器选择）；与 轴1-18 检查清单式组合时，清单项可按档位裁剪。

#### 轴1-03 Y-statement 单行式
- **做法**：每个决策压成一句固定句式的陈述："在（上下文）中，面对（关切），我们决定（选择），以达到（目标），接受（代价）。"决策文件 = 一组这样的句子。
- **谁写/谁读/谁执行**：make-decision 写；人速读；弱模型可整段读入（体积极小）。
- **优点**：体积极小，可整体进弱模型上下文；强制写出"代价"，天然对抗"决策只写好处"；一句话强制"上下文+关切+选择+目标+代价"五要素齐备。
- **代价与风险**：**复杂决策被压扁**（`I-A` P-03 的复发风险最高）；无法承载验收标准、证据、风险细节；"理由"只能写一句，溯源深度受限。
- **最适合的场景**：决策高度同质、且所有细节都能外移到 spec/phase 的场景；或作为 轴1-04/轴1-05 的**索引层**。
- **现实案例或证据**：`【缺口】` —— **本 9 份报告中没有 Y-statement 的结构、长度或案例**。`R-E §3` 只逐字覆盖 Nygard 模板（§3.1）与 MADR 三级模板（§3.2），并泛泛提到 ADR 长度"一句话 slide 到几页"（§3.3）；adr-tools / log4brains / Y-statement 三个名字在全部 9 份报告中**均未出现**（详见本文件 §6 证据缺口登记）。本选项属于"按 ADR 家族一般原则构造的可能性"，**无实证支撑**；`I-A §5` 记录现有材料"优秀片段"里已有类似的单句决策摘要可被保留 `【间接】`（仅说明形态可行，不构成证据）。
- **与其它选项的组合性**：**可叠加**——最自然的角色是 轴1-04 三层中的"摘要层"、或 轴1-14 registry 的索引字段；**单独使用**则与"无遗漏"要求冲突。

#### 轴1-04 三层分层（速读 / 决策正文 / 溯源附录）
- **做法**：第 1 层 30 秒速读卡（一句话需求 + 核心改动 + 最大影响面 + 验收信号）；第 2 层决策正文（每个决策的 Context/Decision/Consequences/被否选项）；第 3 层附录（原始需求摘录、Talk/Grill 转录、证据路径）。层与层之间用锚点跳转。
- **谁写/谁读/谁执行**：make-decision 写全三层；人读第 1 层、按需下沉；弱模型只读第 1–2 层（或只读 spec 的投影）。
- **优点**：直接对应 `R-E §4.3` 的"概览/细节/附录"三层规则与渐进式披露；解决 `I-A` P-02（过程记录与被审内容同层）与 P-14（实现者入口被导航表埋掉）；不同读者各取所需。
- **代价与风险**：三层意味着**同一事实有三种详略表达**，若不用"引用而非复制"规则会制造重复（`R-E §1.4`）；层间锚点会腐化（`I-A` P-10 记录行号锚点已腐化）。
- **最适合的场景**：既有决策者速读需求，又有弱模型执行需求，且材料规模已超单层可读阈值时。
- **现实案例或证据**：`R-E §4.3`（三层组织规则）、`R-E §4.4`（映射到三类文档）、`R-E §9.2/9.3/9.4`（decision-log / spec / phase 各自的分层规则）；现行 `spec-template.md` 已有"速读卡 + 材料导航"雏形（`I-B §1.6`）`【实证】`（Diátaxis/渐进式披露为公开标准，LLM 位置效应有实证：`R-B §1.3`）。
- **与其它选项的组合性**：**可叠加**于任何容器形态（分层是组织原则，不是容器）；与 轴1-05 完整账本组合效果最好（账本作第 3 层）；与 轴1-03/轴1-13 组合时它们充当第 1 层。

#### 轴1-05 完整决策账本（全量 ledger）
- **做法**：一份文档承载全部决策，每条含：ID、日期、类型、状态、上下文、真实选择（含被否选项与理由）、后果、风险、影响的下游 ID、证据引用。附一张跨材料映射表（Source ID → Decision ID → FR/AC IDs → Status/affected scope → Unresolved/handoff）。
- **谁写/谁读/谁执行**：make-decision 写；人审计式读；审查者（轴 4）读；弱模型原则上不读。
- **优点**：**无遗漏**最容易保证（一处写全）；跨决策的一致性与冲突检查可做；映射表把"需求→决策→下游"的追溯一次写清（对应 `I-B` K1/K2）。
- **代价与风险**：**规模失控是结构化必然**——现状样本正是这条路：741 行 / 1002 行，四材料总量无上限（`I-A` P-01）；过程记录与被审内容同层（`I-A` P-02）；决策块样板行逐块重复（P-06）；空白模板占近三成（P-16）。
- **最适合的场景**：决策数量有限（例如 <20 条）且需要强审计、强追溯的合规型任务。
- **现实案例或证据**：`I-A §1.1/§2.1/§2.5` 给出这份形态的**实测代价**（741/1002 行、重复率、P-01…P-17）；`I-A §4` 给出信噪比分析与分桶口径 `【实证】`（对本仓历史材料的量化审计）。
- **与其它选项的组合性**：**可叠加** 轴1-04 分层（账本降为第 3 层）或 轴1-09 双文件（账本作"详情"文件）；**互斥**于 轴1-15 无独立文件；与 轴1-14 registry 组合时账本变成 registry 的导出产物。

#### 轴1-06 append-only 时间线日志 + 状态机
- **做法**：decision-log 是一份**只追加**的日志，每行带时间戳与状态迁移（proposed → accepted → superseded → retired），永不改写历史行；当前有效决策由"最后一次状态"决定。
- **谁写/谁读/谁执行**：make-decision 追加；人读尾部与状态；审查者读全量做一致性检查。
- **优点**：决策演化过程可完整回溯（谁在什么时候改了什么方向）；天然避免"历史被摘要覆盖"（符合本仓"provenance 必须保留"的治理边界）；与 轴1-08 事件溯源同族但实现更轻。
- **代价与风险**：**读者必须自己重建"当前是什么"**（认知负担转移给弱模型与人）；日志随时间线性膨胀；同一决策的多次修订会重复上下文。
- **最适合的场景**：决策会被频繁修正、且"为什么改"比"现在是什么"更有价值的探索型任务。
- **现实案例或证据**：`R-E §3.1` 的 Status 字段（proposed/accepted/rejected/deprecated/superseded）已含状态机语义；`R-A §7.1` 记录 OpenAI `exec-plans/` 与 Spec Kit 的 `converge` 均使用 **append-only** 语义；`I-B` D5 指出旧形态是"多层重复 evidence 包装"而非 append-only，两者机制不同 `【实证】`（官方文档/模板原文）。
- **与其它选项的组合性**：**可叠加** 轴1-08（日志是事件的渲染形态）；**需改造**才能与 轴1-03 单行式组合（需要"当前投影"层）；与 轴1-07 决策图组合时，日志提供时间轴、图提供结构轴。

#### 轴1-07 决策树 / supersedes 关系图
- **做法**：决策以节点表示，边表示三类关系：`supersedes`、`depends-on`、`conflicts-with`。文档主体是邻接表或缩进树 + 每个节点的短决策；可另附 Mermaid/文本图。
- **谁写/谁读/谁执行**：make-decision 写；人读结构；审查者用它定位"被上游决策推翻的下游条目"。
- **优点**：**关系是一等公民**——当前 `I-A` P-12（隐含假设未写明）与 P-13（术语/编号不一致）本质是关系缺失；一次性看出哪些决策是根、哪些是导出、哪些已被取代。
- **代价与风险**：图的**维护成本高**（每次新增决策都要接边，容易漏）；文本图对弱模型可读性差；拓扑正确性需要额外检查（谁来验证无环？）。
- **最适合的场景**：决策有明显的父子/取代结构（例如大方向 + 若干细化决策），或需要审计"改一个根决策会波及什么"。
- **现实案例或证据**：`R-A §7.1` 记录 Kiro 把 `tasks.md` 解析成**依赖图 + 波次并行**、OpenSpec 用 schema 定义**产物依赖图**（`R-A §6`）；`R-A §8 M7` 的需求号双向追溯是"关系显式化"的同族机制 `【实证】`（官方机制存在，但"决策树"这一具体形态在报告中无直接案例）。
- **与其它选项的组合性**：**可叠加**于 轴1-05/轴1-06（图作为索引层）；**互斥**于纯 轴1-03 单行式；与 轴1-13 决策矩阵互补（矩阵管单决策内的选项比较，图管决策间关系）。

#### 轴1-08 事件溯源式（events + 当前投影）
- **做法**：唯一权威是一串不可变事件（如 `DecisionProposed` / `OptionRejected` / `DecisionSuperseded` / `RiskAccepted`），`decision-log.md` 只是这串事件的一次**投影/渲染**，可随时从事件重算；投影文件上标注"非权威，权威是事件流"。
- **谁写/谁读/谁执行**：make-decision 追加事件；人读投影；审查者读事件流；弱模型只读投影。
- **优点**：与"事实与投影分离"的架构直觉同源；任何时点的决策状态都可重建；天然支持"历史只读、当前可算"。
- **代价与风险**：**引入第二真相源**——投影与事件流不一致时谁赢？本仓治理边界明确禁止新增无消费者的控制面与双写（`AGENTS.md` vNext 边界：reports immutable、不得新增双写）；事件流本身也要有 schema 与校验，否则又是机器外壳（`I-B` D2/D3 的删除对象）。
- **最适合的场景**：决策量大、需要"任意时间点回放"、且已有事件基础设施可复用时。
- **现实案例或证据**：`R-D §4.1` 建议把审查产出拆成 Observation→Finding→Disposition 三段"互不耦合的记录"，是事件溯源式思维的近亲；`I-B` D2/D5 记录本仓历史上**正是**用哈希/快照/材料身份做绑定，且被 OI-013 判定"彻底全删"`【间接】`（报告无"决策事件溯源"直接案例；本仓治理边界反而把它标为高风险）。
- **与其它选项的组合性**：**可叠加** 轴1-06（日志=事件流的线性渲染）；**互斥**于 轴1-15 无独立文件；与 轴1-09 双文件组合时，"详情文件"就是事件流导出。

---

#### 轴1-09 双文件（决策摘要 + 决策详情）
- **做法**：拆成两份：`decision-summary.md`（人读的一页摘要：每个决策一句话 + 状态 + 影响面）与 `decision-detail.md`（每个决策的完整上下文、被否选项、证据）。摘要里的每个条目用纯文本路径锚点指向详情章节。
- **谁写/谁读/谁执行**：make-decision 同时写两份；人读摘要、按需下沉；弱模型读摘要；审查者读详情。
- **优点**：**把"可读性"与"无遗漏"分给两个文件**，各自可以做到极致；摘要天然是弱模型的上下文预算解药（`R-B §1.2`）。
- **代价与风险**：**直接触碰"同一事实两个权威"红线**——本仓 AC-06 要求"0 处两个文件对同一事实各自声明权威"（`I-C §5 I4`）；两份文件同步漂移是典型失败模式（对照 `I-B` D1 对 plan/tasks 双写的删除判定）。
- **最适合的场景**：材料规模已经大到单文件无法同时满足速读与审计时——即现状。
- **现实案例或证据**：**正面案例（关键设计差异）** —— `R-A §4` 记录 AWS AI-DLC **同时**有两个决策文件：stage 1.7 的 `decision-log.md`（**initiative 级**交接决策日志）与 stage 2.6 的 `decisions.md`（**组件级 ADR 日志**），外加 `risk-and-sequencing-rationale.md` 承载排序理由。二者的**权威范围按层级切分**，不是同一事实写两遍——这是"双文件"能成立的构造方式。**反向证据**：`I-B` D1 判定"plan.md/tasks.md 双写及相等性协议"**删除**，理由是"同一事实的两份声明正是无重复契约的反例"；`I-C §5 I4` 指出本仓 AC-06 要求"0 处两个文件对同一事实各自声明权威" `【实证】`（官方目录结构 + 本仓明确判定）。
- **与其它选项的组合性**：**需改造**——若坚持双文件，必须显式指定"哪一份是权威、另一份是可再生产物"；与 轴1-04 单文件分层是**互斥**的两条路。

#### 轴1-10 场景故事式（叙事体）
- **做法**：decision-log 写成一段连续叙事："我们最初以为 X，做了 A 之后发现 Y，于是选择 B，因为……"。决策点以加粗或小标题标出，但不打断叙事。
- **谁写/谁读/谁执行**：make-decision 写；人（尤其非技术决策者）读；弱模型通常不读。
- **优点**：**理由与因果关系最自然**，读起来最不像文档；对"为什么会走到这个方向"这类 `R-F` intent debt（意图债务）表达力最强（`R-F §8.1`）；适合向外部解释。
- **代价与风险**：**无法机器/清单校验**（`R-E §6` 的格式实证显示结构化格式对准确率更友好）；关键字段（状态、ID、影响面）散落在散文里，追溯要靠人工；篇幅不可控。
- **最适合的场景**：决策者本人是主要读者、且需要"说服"或"复盘"而非"执行"；或作为 轴1-04 的第 1 层。
- **现实案例或证据**：`R-D §1.3` 的 Amazon PR/FAQ 是**叙事驱动的立项文档**（Press Release + FAQ，会上静读 15–20 分钟）；`R-D §1.3` 也记录其代价：最成功产品耗时**数月**写与评审 `【实证】`（官方流程原文）。
- **与其它选项的组合性**：**可叠加** 轴1-04 作速读层、或 轴1-11 问答式（叙事是问答的归纳）；**需改造**才能满足轴 4 的清单式审查。

---

#### 轴1-11 问答式（Talk / Grill 转录）
- **做法**：decision-log 直接由"提问 → 用户回答 → 归纳为决策"的转录构成，保留原始问题与原始回答，决策作为每条问答的结论行。
- **谁写/谁读/谁执行**：make-decision 记录（用户是共同作者）；人读自己的原话；弱模型不读。
- **优点**：**零信息损失**——决策者的真实措辞被保留，"用户真实选择"不可能被摘要篡改；天然满足本仓"provenance 必须保留"的要求。
- **代价与风险**：转录体积极大且高度口语化；`I-B` D4 判定"固定 Talk 轮次"是**删除对象**（`I-B §5 D4`）；`I-B` D5 指出多层 evidence 包装要合并——转录若原样进 decision-log，正是 P-02（过程记录与被审内容同层）。
- **最适合的场景**：方向级决策、且决策者希望留档自己的原话时；或作为附录层。
- **现实案例或证据**：`I-B §1.2` 第 3 步 `spec-clarify` 的"真实 ask→wait→reply→resume"与 K5 十维度完整性检查；`I-B §5 D4` 明确删除"固定 Talk 轮次"；`R-A §8 M5` 的"不确定性外显"是同一机制的**克制版**（只记录未决项，不记录全过程）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴1-04 的第 3 层/附录；**需改造**——必须把转录与决策正文分层，否则与 `I-A` P-02 同病。

---

#### 轴1-12 结构化 frontmatter + 散文
- **做法**：文件头是 YAML/TOML frontmatter，承载全部**可机检字段**（决策 ID、状态、owner、影响的 FR/AC、非目标、延期项、到期/复审条件）；正文是自由散文，只写理由与权衡。
- **谁写/谁读/谁执行**：make-decision 写；脚本读 frontmatter 做校验/索引；人读散文；弱模型可只读 frontmatter。
- **优点**：**机器可读与人类可读一次满足**，且不引入第二个文件；`R-A §7.1` 记录 Tessl 用 3 个必填 frontmatter 字段 + 校验脚本，是**唯一"格式可脚本校验"的实证案例**；`I-A` P-08（AC 字段跨任务漂移）与 P-11（哈希 pin 不一致）都是"字段没有 schema"的病。
- **代价与风险**：frontmatter 膨胀会变成第二本账（"元数据比内容长"）；字段一旦校验失败就产生"必须修"的压力，容易演变成闸门（`R-D §4.3` DORA 反证）；本仓明确要删"哈希/快照/revision 校验"（`I-B` D2），frontmatter 的字段集必须避开这些。
- **最适合的场景**：有工具链愿意消费字段、且希望"精炼"与"无遗漏"同时成立时。
- **现实案例或证据**：`R-A §7.1` Tessl（3 必填 frontmatter 字段 + `[@test]` + `validate-specs.sh`）、`R-A §8 M2`（格式机器校验被 Tessl/AI-DLC/Spec Kit/OpenAI 四家独立实现）；`I-A §6.5` 把"锚点与哈希一致性"列为候选改进方向 `【实证】`。
- **与其它选项的组合性**：**可叠加**于 轴1-03/轴1-04/轴1-14（frontmatter 即索引层）；与 轴1-18 检查清单式共用同一"字段即检查项"思路。

#### 轴1-13 决策矩阵（选项 × 判据表）
- **做法**：每个需要决策的轴做成一张矩阵：行=候选选项，列=判据（成本、风险、可逆性、影响面、验证难度……），格子里写事实与代价；结论行写"本次选择 + 条件"。
- **谁写/谁读/谁执行**：make-decision 写；人读；审查者用它检查"是否至少比较了一个可信替代"。
- **优点**：把"真实选择"与"被否选项"变成**结构性必填**（直接治 `I-A` P-03）；`R-D §11 A3` 明确要求"至少 2 个备选 + 各自权衡与被否原因"，`R-D §1.1` Google 设计文档把 `Alternatives considered` 称为"最重要的章节之一"。
- **代价与风险**：矩阵会诱导"为填格子而制造选项"；判据列不一致时无法跨决策比较；对开放性问题（`R-F §1.1` 决策类任务细节度收益 +0.02）可能约束而非帮助推理。
- **最适合的场景**：决策轴明确、候选有限、且需要向多人证明"考虑过替代方案"时。
- **现实案例或证据**：`R-D §1.1`（Google：Alternatives considered 为最重要章节）、`R-D §11 A3`（备选方案与被否理由为清单项）；`I-B §3` 的 `plan-ceo-review` 要求"细节审查时至少对比一个可信替代" `【实证】`。
- **与其它选项的组合性**：**可叠加**于 轴1-01/轴1-02/轴1-05（矩阵作为单决策的内部结构）；与 轴1-07 图互补；与 轴1-17 契约式需改造（契约式关心"不变量"，矩阵关心"选择过程"）。

#### 轴1-14 决策 registry + 紧凑索引（活文档 / 可查询）
- **做法**：决策不再是一份长文档，而是一个**可查询的注册表**（每条决策一个条目/一个文件）+ 一份常驻的紧凑索引（ID、标题、状态、影响面、锚点）。索引是唯一被默认注入上下文的部分，条目按需检索。
- **谁写/谁读/谁执行**：make-decision 写条目与索引；人按需查询；弱模型只吃索引 + 当前 phase 相关条目（just-in-time 检索）。
- **优点**：**上下文预算随规模增长而保持常数**——这是 `R-A §7.3` 的"控制喂进去多少比控制写出来多少更重要"的直接落地；`R-A §8.1` 三个反直觉发现之一即"写更长文档不是解法，更小上下文 + 机械校验才是"。
- **代价与风险**：**索引与条目的一致性成为新的失败面**（腐化索引比腐化正文更危险，见 `I-A` P-10 行号锚点腐化）；需要"检索是谁做的"这一新角色；一次性通读做全局一致性检查变得不可能。
- **最适合的场景**：决策数量大、需要长期存续（spec-anchored）且有多 phase 执行时。
- **现实案例或证据**：`R-E §6.4` 与 `R-A §8 M4`（上下文预算策略：Spec Kit 4 策略、cc-sdd 只读相关章节、Anthropic compaction/子代理、OpenAI progressive disclosure）；`R-F §5.2` Anthropic 的 **just-in-time 检索**（保留轻量标识符如路径，运行时再取，避免陈旧索引）`【实证】`；本仓 OI-001 已收敛为"一份权威 spec + 每个 phase 只写本检索边界内的差异 + **常驻紧凑索引**"（`I-B §5 D1`）`【实证】`（本仓官方决议）。
- **与其它选项的组合性**：**可叠加** 轴1-12 frontmatter（条目字段）、轴1-05（账本作导出）；**互斥**于 轴1-05 单一长文档的默认注入用法；是 轴1-15 的前置条件。

---

#### 轴1-15 无独立 decision-log（决策内联进 spec 的来源映射）
- **做法**：取消独立的 decision-log 文件；每个决策作为 spec 中对应 FR/AC 的 `source_ref` 单元格存在（"这条需求来自 D-007，理由是……"）。决策的坟场（被否选项）写在 spec 的非目标/延期节。
- **谁写/谁读/谁执行**：make-decision 写进 spec 的来源列；人从 spec 反查；弱模型只读 spec 一份。
- **优点**：**结构性地消灭"两份材料各说一套"**（`I-B` K1 防的正是这个）；材料数量最少，四材料总量问题（`I-A` P-01）从根上缓解；弱模型不必在两份文件间做事实合并。
- **代价与风险**：决策的**方向级/战略级内容**（不映射到任何单条 FR 的选择）失去容器；"为什么没做 X"容易被挤成一句（P-03）；`I-B §1.1` 明确"decision-log 拥有原始需求、用户选择、理由、风险、非目标与延期方向"，把这些并入 spec 会与"spec 拥有产品行为"争夺权威。
- **最适合的场景**：决策几乎全部是"需求级"的、且没有独立方向轨任务时。
- **现实案例或证据**：`R-A §6` OpenSpec 的 `openspec/specs/<domain>/spec.md`（事实来源）+ changes 目录下的 delta；`I-B §6.3` 指出"现行模板中的 PFACT/来源映射/spec-content.v3 是为 build-spec 独立阶段设计的；合并进 build-plan 后需要**重排优先级，避免规格与工程内容在同一文档里争夺权威**" `【间接】`（报告无"取消 decision-log"的直接案例，本仓权威边界倾向反对）。
- **与其它选项的组合性**：**互斥**于 轴1-03…轴1-14 的绝大多数；**可叠加** 轴1-14（来源列即最小 registry）；是"最少材料数"这一极端的代表选项。

#### 轴1-16 固定六字段 + 硬上限式（MADR minimal 等价体）
- **做法**：每条决策一个块，字段与顺序逐字固定：`ID / Status / Context（≤3 句）/ Decision（1 句结论 + 1 句理由）/ Consequences（≥1 good + ≥1 bad）/ Confirmation（可选：怎么验证已落实）`；**每条决策块 ≤15 行**，超出把细节移附录并留指针；`Considered Options` 默认只列标题，Pros/Cons 仅在高风险或被质疑时展开；**正文不出现 JSON/大表**（机器可读结构体移独立文件，正文只留 ID + 一句话结论 + 指针）；流程元评论（"本表在何时建立""如与母任务冲突则…"）移入专门附录或删除。
- **谁写/谁读/谁执行**：make-decision 写；人读；spec/phase **只引用 ID、不复述内容**；弱模型只通过 ID 指针接触决策。
- **优点**：把"精炼"与"无遗漏"落成**硬上限 + 必填字段**而不是风格劝告；`Consequences` 强制 ≥1 bad 直接治"决策只写好处"；`ID + 指针`结构从机制上消灭 `I-A` P-04 那类 98.9% 逐字转写；`Confirmation` 字段把"怎么知道它落实了"补上。
- **代价与风险**：≤15 行对复杂决策（多方案、多依赖）**装不下**，被迫切碎成多个块，读者要自己重建整体；`Context ≤3 句` 可能压掉必要的背景因果（与 `I-A` P-03 的张力仍在）；"机器可读结构体移独立文件"本身又制造第二个文件。
- **最适合的场景**：决策同质、可枚举、且下游只需要"当前有效决策 + 理由一句话"时。
- **现实案例或证据**：`R-E §3.4`（**decision-log 即时可抄规则**，由 `R-E §3.1` Nygard + `§3.2` MADR minimal + `§3.3` 七个好实践与 ADR Author Pledge 综合而成）；`R-E §9.2` 给出 decision-log 专用 8 条（含"每条决策 ≤15 行""≥2 个真实备选""被引用时只引 ID 不复述"）；`R-E §7` 的反模式 4/6/7/8/12/13（Mega-ADR、Fairy Tale 只有好处没代价、Free Lunch 无 consequences、Dummy Alternative 假备选、Sales Pitch、Pseudo-accuracy 伪精确加权评分）正是这套字段要防的东西 `【实证】`（模板原文 + ADR 反模式清单为公开实践沉淀）。
- **与其它选项的组合性**：**可叠加** 轴1-06 状态机（Status 即迁移态）、轴1-12 frontmatter（结构体外置）、轴1-13 矩阵（Considered Options 的展开态）；**互斥**于 轴1-05 完整账本（账本的字段集远大于六字段）；**需改造**才能承载 轴1-10 叙事（叙事与硬上限冲突）。

### 轴 1 补充变体（不单列全要素，各一行）

1. **轴1-V1 决策 + 反事实双栏**：左栏"我们决定的"，右栏"如果我们选了另一个会怎样"+失效条件；支撑 `R-F §10.2` 的"本建议的失效条件必须与建议一起被审查" `【实证】`。
2. **轴1-V2 契约式 decision-log**：只记录已成契约的部分（接口、不变量、不可逆确认门），不记录推导过程；对应 `R-F §3.2` CDD 的"硬约束层" `【实证】`。
3. **轴1-V3 检查清单式**：每条决策变成一个可勾选/可判定的检查项（"我们是否确认过 X？"），对应 `R-D §11` A1–A14 清单 `【实证】`。
4. **轴1-V4 决策卡片库（卡片 + 标签 + 全文搜索）**：物理上是一堆短卡片，靠标签与搜索而非目录组织 `【经验】`。
5. **轴1-V5 双语/双读者双版本**（面人版 vs 面机器版）`【缺口】`（报告无直接案例；且触碰双权威红线）。
6. **轴1-V6 decision-log 只写"非目标 + 延期"**：把正向决策留给 spec，只把"明确不做"集中在一处（对应 `I-A §6.6` 与 spec 模板第 12 节"唯一权威非目标列表"，`I-B §1.6`）`【间接】`。

---

## 轴 2：spec 的形态

> 背景约束：spec 是"实施前翻译"，必须承载四件内容——**需求 + 验收流程 + 测试标准 + 架构方案**（`I-B §6.3` 引 CARD-02 原文），且下游是**弱模型**（`R-B` 全篇）。现状模板是 13 节 198 行（`I-B §1.6`），且 `I-A` 记录 P-07（23 条 AC 里 0 条含可执行 oracle）、P-08（AC 字段 schema 跨任务漂移）、P-09（测试流程只有一句 gate_cmd）、P-12（隐含假设未写明）。

---

#### 轴2-01 表单字段式（固定章节 + 槽位填空）
- **做法**：模板把章节骨架与字段名写死，写作者只填空；空章节必须删除而不是留 N/A（或必须写 `N/A — reason`）。字段级带类型约束（枚举/ID 格式/非空）。
- **谁写/谁读/谁执行**：build-plan 写；弱模型执行时按字段名定位；审查者按字段逐项核对。
- **优点**：**结构强制（C1）**——把推理负担从执行者前移到模板；`R-A §8 M1` 记录 Spec Kit、Kiro、cc-sdd、AI-DLC、Google **五家独立**采用；直接治 `I-A` P-08（字段漂移）。
- **代价与风险**：模板膨胀成"填空考试"，出现"为填格子而写废话"；`I-A` P-16 记录现状"空白模板占近三成"；`R-F §4.3` 的 Thoughtworks 实测批评"用大锤砸坚果"（一个小 bug → 4 个用户故事 16 条验收条件）`【经验】`。
- **最适合的场景**：文档由**弱模型或低经验者**产出/消费、且需要跨任务可比时——正是本仓场景。
- **现实案例或证据**：`R-A §7.1`（五家框架的"模板强制程度=高/中"列）、`R-A §8 M1`；本仓 `spec-template.md` 13 节即此形态（`I-B §1.6`）`【实证】`。
- **与其它选项的组合性**：**可叠加**于几乎全部其它形态（字段式是骨架，其它是组织原则）；与 轴2-06 分层披露组合最佳；与 轴2-11 活文档冲突（活文档要按需重构结构）。

---

#### 轴2-02 叙事 RFC 式
- **做法**：按 RFC/设计文档体写：Context and scope（只讲客观背景事实，不是需求文档）/ Goals and non-goals / The actual design（重点是**权衡**，不是实现手册）/ Alternatives considered / Cross-cutting concerns（安全、隐私、可观测性……）。
- **谁写/谁读/谁执行**：高智力模型写；资深工程师/决策者读；弱模型**基本不可执行**（需要二次翻译成 phase 文档）。
- **优点**：**理由是主角**；Google 官方明确"如果文档变成 implementation manual（只说怎么做，不谈权衡与备选），那不如直接写代码"；`Alternatives considered` 被列为最重要章节之一；跨切面关注点有固定位置。
- **代价与风险**：**不可机检、不可枚举验收**；篇幅 10–20 页为甜点，对弱模型完全超预算；`R-E §6.1` 显示格式对准确率有实证影响，散文式对弱执行者不利。
- **最适合的场景**：探索性强、需要资深判断规模化的设计；或方向级评审的主材料。
- **现实案例或证据**：`R-D §1.1`（Google 设计文档结构、10–20 页甜点、1–3 页 mini design doc、明确反对 implementation manual）`【实证】`（官方公开实践）。
- **与其它选项的组合性**：**可叠加** 轴2-06（叙事作详情层，速读层另写）；**需改造**才能满足"弱模型可执行"；与 轴2-04 契约优先式互补（契约抽出来放前面）。

---

#### 轴2-03 用户旅程场景式（scenario-first）
- **做法**：以用户场景为骨架：每个 `User Story N - [Title] (Priority: P1)` 含故事描述、`Given/When/Then` 验收场景、Edge Cases；需求与成功标准列在场景之后；场景是 mandatory 章节。
- **谁写/谁读/谁执行**：build-plan 写；弱模型按场景逐个实现；审查者按"每个场景是否被 FR 覆盖"核对。
- **优点**：**把"谁在什么场景要什么"放在最前**，直接治 `I-A` P-12（隐含假设）；场景是天然的测试用例来源；优先级（P1/P2/P3）给执行顺序。
- **代价与风险**：非用户可见的改动（重构、基础设施、迁移）**无法表达**，只能硬塞或写 N/A；`R-C §2.3` 记录 Gherkin 的局限（有据可查的批评）；场景数量会膨胀。
- **最适合的场景**：面向最终用户的产品行为变更、且每 phase 都能映射到场景时。
- **现实案例或证据**：`R-A §1.4`（Spec Kit 模板：`## User Scenarios & Testing *(mandatory)*` + `### User Story 1 - [Brief Title] (Priority: P1)` + `### Edge Cases`）；`R-A §7.1` 记录 OpenSpec 的 requirement/scenario 固定小节 `【实证】`（模板原文）。
- **与其它选项的组合性**：**可叠加** 轴2-05 示例驱动式（场景内用 given-when-then，几乎是同一机制）、轴2-06；**互斥/需改造** 与 轴2-04 契约优先式在"谁在前"上有竞争关系。

---

#### 轴2-04 契约优先式（接口契约在前，实现计划在后）
- **做法**：spec 分三层且顺序固定：①产品需求 = 意图行为；②接口契约 = 组件间如何协作（输入、输出、错误、可观察行为、相关交互、兼容性保证）；③实现规格与计划 = 每个组件对着已达成一致的契约写，**不得复制别的组件的实现计划**。契约由暴露方单方拥有权威版本，跨仓消费者钉住已发布版本、禁止静默跟随 latest；消费者 mock 不能证明 provider 合规。
- **谁写/谁读/谁执行**：高智力模型写契约；弱模型照契约实现；审查者做 provider/consumer 双向验证。
- **优点**：**"什么不许变"被写死，"怎么实现"被放开**——正好对上 `R-F §7.1` 判据表的"接口 vs 实现"行；结构性阻止下游漂移；跨组件/跨 phase 的集成风险前置。
- **代价与风险**：**契约本身可能写错或写多**；不适用于无接口的纯行为变更；`R-F §3.2` 记录这是 spec-kit **2026-09 才合并**的新方向，缺长期实践数据。
- **最适合的场景**：多组件/多 phase/跨仓协作，且有明确接口边界时。
- **现实案例或证据**：`R-F §3.2`（spec-kit issue #4609 / PR #4616，2026-09-16，**唯一一份把层职责写成官方文档的 SDD 框架**）、`R-F §5.1` OpenAI 官方对"脆弱可验证的执行接口"（`apply_patch` 格式）同样写死 `【实证】`（官方文档原文，但实践历史很短）。
- **与其它选项的组合性**：**可叠加** 轴2-06（契约作 L1 层）、轴3-04 契约式 phase 文档（同一份契约被 phase 引用）；**需改造** 轴2-03（谁在前有竞争）。

---

#### 轴2-05 示例驱动式（given-when-then 贯穿全篇）
- **做法**：spec 的每条需求都配一个 `Given/When/Then` 示例；需求描述是示例的归纳，而非相反。示例可被执行（Gherkin/Cucumber）或至少可人工判定。
- **谁写/谁读/谁执行**：build-plan 写；弱模型把示例直接转成测试；审查者检查"示例是否覆盖需求的边界"。
- **优点**：**可执行规格（C6）**；`R-B §6.2` 记录"把测试当作可执行规格"是本报告中最强的正向证据；`R-A §8 M6` 记录 Kiro、cc-sdd、Spec Kit 三家独立采用受控自然语言压缩表达自由度。
- **代价与风险**：`R-C §2.3` 记录 Gherkin 的**有据可查的批评**（示例无法替代需求陈述、易写成实现细节、维护成本）；对纯计算/数据变换类需求，示例冗余。
- **最适合的场景**：行为可观察、且验收可以退化成一组具体例子的任务。
- **现实案例或证据**：`R-C §2.1/§2.2`（Gherkin 语法事实与 AI 代码生成中的实际用法）、`R-C §2.3`（局限）、`R-A §8 M8`（可执行规格：Kiro 性质测试 + `Validates: Requirements 2.3`；Spec Kit quickstart.md + contracts；cc-sdd RED 证据）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴2-03（几乎同源）、轴2-13 验收标准主导式；与 轴2-02 叙事冲突（示例打断叙事流）。

---

#### 轴2-06 分层披露式（速读层 + 详情层 + 附录）
- **做法**：第 1 层一页内可读完（一句话目标、核心改动、最大影响面、验收信号、要读哪几节）；第 2 层是正文（FR/AC/架构/测试）；第 3 层是附录（原始需求摘录、证据、被否方案、术语表），按需读取。层间用纯文本路径锚点。
- **谁写/谁读/谁执行**：build-plan 写；人读第 1 层；弱模型按 phase 只读相关章节；审查者按需全读。
- **优点**：直接对应 `R-B §3`（渐进式披露与分块）与 `R-E §4.3`（概览/细节/附录）；`R-B §1.3` 的 lost-in-the-middle 要求关键信息放开头或结尾——分层天然满足；`R-A §7.3` 的关键观察是"**控制喂进去多少比控制写出来多少更重要**"。
- **代价与风险**：三层=三处表达，重复风险（`R-E §1.4` 的引用 vs 复制判定）；锚点腐化（`I-A` P-10）；"谁是权威"必须在文件内声明，否则与 轴1-09 同病。
- **最适合的场景**：任何超过弱模型上下文预算的 spec——即本仓现状（`R-B §1.2` 给出 token 预算工程参数；BMAD 记录约 40 页/数万 token 是实际上限，**超过会静默丢信息**，`R-A §7.3`）。
- **现实案例或证据**：`R-B §3`、`R-E §4.1/§4.3/§4.4`、`R-A §7.3`（BMAD 输入侧上限与静默丢失警告）、`R-A §8 M4`（上下文预算策略，四家框架）；现行 spec 模板已有"速读卡 + 材料导航"雏形（`I-B §1.6`）`【实证】`。
- **与其它选项的组合性**：**可叠加**于全部；与 轴2-01 表单字段式是事实上的标准组合；与 轴1-14 registry 组合时第 1 层即常驻索引。

---

#### 轴2-07 问题-方案-证据链式（problem → solution → evidence）
- **做法**：每个 spec 章节按同一链条组织：`问题（可观察现象 + 证据）→ 方案（选择 + 被否替代）→ 证据（怎么知道它成了）`。没有证据的解决方案不成立；没有问题的方案被删除。
- **谁写/谁读/谁执行**：build-plan 写；审查者按链条逐环核对（最容易发现"有方案无问题"）；弱模型读"方案+证据"两段。
- **优点**：**结构性地把"为什么"钉在"做什么"旁边**，直接治 `I-A` P-12；与 `R-D §11` A1/A3/A4（问题定义清晰、备选方案、假设显式化）逐条对应；天然适配证据门槛（`R-D §4.1`）。
- **代价与风险**：**链条在纯工程任务上会显得做作**（"问题"就是"要加个字段"）；证据段落容易退化成"测试通过"一句（`I-A` P-09 的复发）。
- **最适合的场景**：问题定义不清、或有多个竞争方案需要论证时。
- **现实案例或证据**：`R-D §11` A1–A5（可判定清单）、`R-D §1.3` Amazon PR/FAQ 的"哪些假设必须为真 + 最可能失败的三个原因"；`R-F §8.1` Storey 的 **intent debt**（外化的理由、目标与约束的缺失）把"理由"定义为 AI 时代的主要风险 `【实证】`。
- **与其它选项的组合性**：**可叠加** 轴2-01/轴2-06；与 轴2-14 假设/事实分层式高度互补（假设是链条的显式节点）。

---

#### 轴2-08 一张图 + 图注式（diagram-first）
- **做法**：spec 主体是一张（或少数几张）结构图/状态机图/时序图，正文是图注：每个节点/边在文字里被展开为需求或契约；图是权威，文字是注解。
- **谁写/谁读/谁执行**：高智力模型画图；人和弱模型读图；图注提供可执行细节。
- **优点**：**一次表达大量关系**（状态×转移×权限），对状态矩阵（`I-B` K4 八态）表达力极强；`R-E §6.4` 讨论表格 vs 散文的实证差异，结构化载体对 LLM 更友好。
- **代价与风险**：**图不可机检、diff 不友好、易与图注漂移**；弱模型对图的解析能力弱于文本（报告未量化）；`R-E` 结论倾向于"结构化文本 + 少量图"而非"图为主"。
- **最适合的场景**：状态机、数据流、时序、部署拓扑为主要复杂度的任务。
- **现实案例或证据**：`R-A §7.1` 记录 Kiro tasks 可解析成依赖图、OpenSpec schema 定义产物依赖图（**图作为机器可读结构**，非图为主文档）；`I-B §1.4` 第 14 条 UI Contract 的 `page_or_region` + 状态矩阵 + preview/screenshot 引用是"图 + 文本"混合的现存实例 `【间接】`。
- **与其它选项的组合性**：**可叠加** 轴2-06 作速读层；**需改造**才能与 轴2-05 示例驱动式合并；与 轴2-04 契约优先式互补（图表达协作，契约表达义务）。

---

#### 轴2-09 检查清单式（spec 是一组可判定项）
- **做法**：spec = 一组编号的可判定断言（"系统 SHALL …"，或"当 X 时 Y 必须为 Z"），每条可被 test / demonstrate / inspect / analyze 之一验证；不写叙述、不写背景（背景在 decision-log）。
- **谁写/谁读/谁执行**：build-plan 写；弱模型逐条实现；审查者逐条判真假。
- **优点**：**每条都可判定**，直接治 `I-A` P-07（0 条含可执行 oracle）；`R-D §7.3` NASA Appendix C 是"公开材料里最接近可直接机器化"的清单（`shall/will/should` 语义 + 不可验证词清单 + 唯一编号 + 双向追踪）；`R-D §7.4` 指出三条可直接机器化。
- **代价与风险**：**丢失整体意图与理由**（回到 intent debt）；清单之间的依赖/顺序无处表达；纯清单对"设计"类内容表达力差。
- **最适合的场景**：需求密集、验收密集、且意图已由 decision-log 承载时。
- **现实案例或证据**：`R-D §7.1`（IEEE 830 八属性：correct/unambiguous/complete/consistent/ranked/verifiable/modifiable/traceable）、`R-D §7.2`（ISO/IEC/IEEE 29148 单条 vs 需求集特性）、`R-D §7.3`（NASA 校验清单 13 组 + **不可验证词清单**）、`R-D §7.4`（可机器化三条）`【实证】`（标准原文）。
- **与其它选项的组合性**：**可叠加** 轴2-01/轴2-06（清单作正文层）；与 轴2-13 验收标准主导式高度重叠；**互斥**于 轴2-02 叙事 RFC 式。

---

#### 轴2-10 双文档（产品 spec + 技术 spec）
- **做法**：拆成两份：`spec-product.md`（产品行为、流程、状态、FR/AC、失败边界，用产品语言）与 `spec-tech.md`（架构方案、接口契约、数据模型、技术决策、边界）。两份各自有权威范围，交叉引用。
- **谁写/谁读/谁执行**：产品 spec 由 make-decision/build-plan 写，技术 spec 由 build-plan 写；弱模型读技术 spec，人读产品 spec；审查者两份都读。
- **优点**：**解决"规格与工程内容在同一文档里争夺权威"** —— `I-B §6.3` 明确指出这是现行模板合并进 build-plan 后的核心落差；`I-A` P-02（过程记录与被审内容同层）也是"内容类型混装"的病。
- **代价与风险**：**直接触碰双权威红线**（`I-C §5 I4`、AC-06）；两份漂移；`I-B` D1 对 plan/tasks 双写的删除判定是**强反向证据**。
- **最适合的场景**：产品与技术读者分离、且两份文档的消费者确实不同时。
- **现实案例或证据**：`R-A §3.2` Tessl 的 spec 与 `.tessl/` RULES.md 分离；agent-os 把 `shape.md` / `standards.md` / `references.md` 拆成三份（`R-A §7.1`）；本仓 `I-B §6.3` 把"重排优先级"列为待解问题 `【间接】`（框架有先例，本仓治理倾向反对）。
- **与其它选项的组合性**：**需改造**（必须声明权威边界，例如"技术 spec 不得改变产品行为"）；与 轴2-04 契约优先式互补（契约是第三份或技术 spec 的首节）。

---

#### 轴2-11 活文档（spec-anchored / 随代码演进）
- **做法**：spec 不是一次性消耗品，而是在任务完成后**继续存续**：改动的第一动作是改 spec，然后应用到代码；spec 与代码 1:1 或通过 `[@test]` 链接绑定；代码可头部标注 `GENERATED FROM SPEC - DO NOT EDIT`（spec-as-source 极端形态）。
- **谁写/谁读/谁执行**：人 + 高智力模型共同维护；弱模型执行；代码是 spec 的投影（极端形态）。
- **优点**：**规格成为长期资产**（`R-A §0.3` 指出市面主流框架几乎只做到 spec-first，只有 Tessl 明确宣称 spec-anchored）；对外部契约、不变量、业务理由这些"永不删"的部分（`R-F §7.1` 时效行）有天然容器。
- **代价与风险**：**`R-A §8.1` 反直觉发现 4**：越强调"规格是资产"的框架，越把治理成本转移到文档自身——Tessl 承认静态指令会 `quietly go stale`、OpenAI 承认单文件指导 `rots instantly`；`R-F §8.1` 的 **Specification Debt / Specification Overfitting** 正是这条路的风险；`R-F §4.1` 逐版本核对 spec-kit CHANGELOG **没有**任何"因模型变强而简化模板"的条目，官方承认"不规定规格在需求变更后如何保留/变更"。
- **最适合的场景**：长期存续的产品、多处消费者依赖同一契约、且有人愿意承担规格治理成本时。
- **现实案例或证据**：`R-A §0.3`（spec-first / spec-anchored / spec-as-source 三层，被 Spec Kit 官方文档引用）、`R-A §7.2`（现实分布：spec-anchored 仅 Tessl；spec-as-source 仅 Tessl 探索）、`R-A §3.2/§3.3`（`[@test]` 链接与格式校验）、`R-F §8.1`（规格悖论与规格债的学术命名）`【实证】`（官方 changelog + 学术论文）。
- **与其它选项的组合性**：**可叠加** 轴2-04（契约层天然常驻）；**需改造** 轴2-01（活文档要求结构可重构，固定字段会僵化）；与 轴2-16 delta 式是天然配对。

#### 轴2-12 EARS 受控自然语言式
- **做法**：需求句全部用 EARS 五种句式写：Ubiquitous（`The <system> shall <response>`）/ Event-driven（`When <trigger>, the <system> shall <response>`）/ State-driven（`While <state>, …`）/ Unwanted behaviour（`If <condition>, then the <system> shall …`）/ Optional feature（`Where <feature>, …`）。禁 `shall not` 等否定式（NASA 建议正向陈述）。
- **谁写/谁读/谁执行**：build-plan 写；弱模型按句式解析；审查者按句式规则机检。
- **优点**：**压缩表达自由度（C5）**，直接减少歧义——`R-B §2.1` 记录规格歧义使 Code LLM Pass@1 下降 **35%–52%**；`R-C §1.4` 记录 Amazon Kiro 用 EARS；`R-D §7.3` 的 `shall/will/should` 语义检查可机器化。
- **代价与风险**：`R-A §7.1` 明确记录对 Kiro 的批评："**EARS 只是措辞纪律**"——它不解决需求内容缺失；句式学习成本；中文 EARS 的等效性未在报告中验证。
- **最适合的场景**：需求密集、验收可判定、且希望机器辅助检查歧义时。
- **现实案例或证据**：`R-C §1.1/§1.2/§1.3`（EARS 原始定义、通用语法与规则集、五种句式原文与示例）、`R-C §1.4`（Kiro 如何使用）、`R-C §9.2`（EARS 五种句式的选择决策树）、`R-A §7.1` 的批评 `【实证】`（EARS 有原始出处与官方采用）。
- **与其它选项的组合性**：**可叠加** 轴2-05（EARS 管需求句、Gherkin 管验收场景，二者常配对）、轴2-09；**互斥** 轴2-02 散文叙事。

#### 轴2-13 验收标准主导式（AC-first spec）
- **做法**：spec 以验收标准为骨架：每条 AC 用固定四段式 `验证：/通过：/失败：/证据：`，正文非空，禁 `TBD/TODO/待填写`；需求描述作为 AC 的"为什么"附注；证据只声明类型，执行事实由 verify 阶段提供。
- **谁写/谁读/谁执行**：build-plan 写；弱模型**把 AC 直接当任务定义**；verify-code 按 AC 判真假。
- **优点**：**验收即规格**，与"测试即规格"的最强正向证据同源（`R-B §6.2`）；直接治 `I-A` P-07（0 条含 oracle）；`I-B` K3 即此机制；`R-F §7.1` "可验证性"行明确"凡能变成可执行检查的必须写，且是最高优先级"。
- **代价与风险**：**架构方案与理由无处安放**（AC 表达不了"为什么这样分层"）；`R-B §6.3` 要求"每条 AC = 一条命令或一个断言"，对不可机检的验收（视觉、体验、文档质量）会退化成空话；`R-C §6.3` 给出可验证性分级方案（本报告自建、非现成标准）。
- **最适合的场景**：确定性/可测试的代码修改（`R-F §6.3`："对确定性工作，最优解右移——容易约束、容易测试，更多规格很快就回本"）。
- **现实案例或证据**：`I-B §1.4` 第 3 条（AC 四段式可执行验收，现行机制）、`I-B §4 K3`；`R-C §3.4`（可度量验收标准的合成骨架）、`R-C §9.1`（AC 章节完整骨架）、`R-B §6.2/§6.3` `【实证】`。
- **与其它选项的组合性**：**可叠加** 轴2-01/轴2-06；与 轴2-09 检查清单式近乎同源；**需改造**才能承载架构方案（架构需另立章节或另立文档，见 轴2-10）。

#### 轴2-14 假设/事实分层式（PFACT 四态）
- **做法**：spec 内有独立"事实与假设"层，每条事实标注四态之一：`verified` / `inferred` / `unknown` / `not_applicable`，状态字段互斥；`unknown` 必须绑定 RISK 或 OPEN；`inferred` 是**假设的唯一权威位置**。
- **谁写/谁读/谁执行**：build-plan 写；弱模型读"verified"层当硬事实、"inferred"层当可质疑前提；审查者重点查 `unknown` 是否有 owner/触发/关闭条件。
- **优点**：**把"猜"变成一等公民并集中管理**，直接治 `I-A` P-12（隐含假设未写明）；`R-D §7.3` 的 NASA TBR 机制是同一思想（"不要求把未知写成 TBD——那会卡住——而是给出最佳估计 + 标记待解决 + 指定责任人与期限"）；`R-D §4.1` 的 `unavailable/incomplete/unknown` 三层同构。
- **代价与风险**：**四态标注本身是工作量**，且容易被一律标 `verified`（标注失真）；对弱模型，`inferred` 层可能被误当硬约束。
- **最适合的场景**：事实来源分散、有大量外部系统假设的场景。
- **现实案例或证据**：`I-B §1.4` 第 5 条（PFACT 四态，现行机制）、`I-B §1.6`（模板第 6 节）；`R-D §7.3`（NASA TBR 机制）、`R-E §5.4`（显式省略：TBD / TBR / non-goals / deferred）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴2-07（假设是链条节点）、轴2-15（把规则写成例子而不写进假设层）；与 轴2-09 冲突较小（清单可含事实项）。

#### 轴2-15 范例驱动式（canonical examples 而非规则清单）
- **做法**：spec 不写"规则清单 + 边界情况穷举"，而是给 1–3 个**典型的、有代表性的**完整范例（输入→处理→输出），并明确说"按范例的模式推广，边界情况不要穷举"。
- **谁写/谁读/谁执行**：build-plan 精选范例；弱模型照范例泛化；审查者检查范例是否典型。
- **优点**：**降低提示敏感性**——`R-B §8` 的弱模型模板第 4 节（"示例 1–3 个，典型而非穷举"）明确引用 ProSA 与 Anthropic 官方立场（**反对堆 edge case 清单**，主张"策划 diverse canonical examples"）；`R-F §7.1` 可验证性行同样写"无法机检的偏好写成 canonical example，不写成规则清单"。
- **代价与风险**：**范例的泛化边界不清**会制造新的歧义（`R-B §2.1` 的歧义代价 −35%~−52%）；弱模型可能过度拟合范例的偶然特征。
- **最适合的场景**：模式化改动（同类 CRUD、同类转换）、格式/风格类要求、且规则难以穷举时。
- **现实案例或证据**：`R-B §8`（弱模型规格模板第 4 节）、`R-B §5`（显式 vs 隐式：什么必须写进规格）；`R-F §7.1`（Anthropic canonical examples 立场）`【实证】`（Anthropic 官方工程博客为来源）。
- **与其它选项的组合性**：**可叠加** 轴2-05（示例驱动是它的可执行版）、轴2-13；**互斥** 与"穷举边界清单"式的 轴2-09。

#### 轴2-16 delta / 差异式 spec
- **做法**：spec 只写**相对既有事实的差异**（`## ADDED Requirements` / `## MODIFIED Requirements` / `## REMOVED Requirements`），每条的 baseline 由当前代码/既有 spec 提供；一个 change 一个意图。
- **谁写/谁读/谁执行**：build-plan 写 delta；弱模型读"现有实现 + delta"；审查者按 delta 边界核对。
- **优点**：**体积极小且天然抗重复**（对照 `I-A` P-04：spec §11 被逐字转写进 plan，98.9% 重复）；改动边界显式；对"改一个已有系统"这类任务最自然——正是本仓的多数场景。
- **代价与风险**：**读 delta 必须有 baseline**，弱模型若拿不到 baseline 会误解；跨 change 的累积语义难以重建；`R-A §7.1` 记录 OpenSpec 官方自陈"**无阶段门即无强制检查点**"。
- **最适合的场景**：存量系统的小步迭代；或与 轴1-14/轴3-12（"只写本检索边界内差异"）配套时。
- **现实案例或证据**：`R-A §6`（OpenSpec 的 `## ADDED/MODIFIED/REMOVED Requirements` 固定小节 + Lite/Full 双档）；本仓 OI-001 已收敛为"每个 phase 只写本检索边界内的差异 + 常驻紧凑索引"（`I-B §5 D1`）`【实证】`（官方模板 + 本仓官方决议）。
- **与其它选项的组合性**：**可叠加** 轴2-11 活文档（baseline 由活 spec 提供）、轴3-06 diff 预览式；**需改造** 与 轴2-02/轴2-07（完整叙事不适合 delta 化）。

## 轴 3：phase 文档的形态

> 背景约束：phase 文档的唯一消费者是**照文档写代码的弱/便宜模型**（`I-B` 执行模型分工）；每个 phase 一份（`I-B §2.4` 第 10 条 Phase 交接块固定 `Goal / Files / Tasks / Verify / Knowledge / STOP / Done / Risks and rollback`）；且被审时**必须与 spec 一起审**，因为 phase 文档"只含本检索边界内差异 + 引用"，单独审无法判断整体质量（`I-C §5 I2`）。`I-A` P-03/P-09 记录现状：oracle 字段内嵌 JSON 挤在一行、测试流程只有一句 `gate_cmd`、fixture 无一处可直接照做。`R-F` 全篇给的是"phase 文档该写多死"这一轴的最强证据。

---

#### 轴3-01 执行手册式（每步五要素）
- **做法**：每个步骤固定五行：`读（指针，如 spec.md#R-014、src/x.ts）/ 改（精确路径 + 边界）/ 判据（可执行命令 + 期望结果）/ 不许（最小护栏）/ 验收映射（R-ID）`；步骤以动词开头的领头词命名（`### P1-03 <动作名>`）；每步 ≤6 行且**至少一行是可验证判据**。
- **谁写/谁读/谁执行**：高智力模型写；弱模型逐步照做；审查者检查每步判据是否可执行。
- **优点**：把"怎么找、怎么改、怎么验"全部前移，弱模型零推断（`R-A §8 M3` 粒度强制 + `R-E §9.4`）；`不许`/`判据` 两行使"做完"有明确信号，直接治 `R-F §6.2` 第 6 条"looks done 的假停止信号"。
- **代价与风险**：`R-F §6.2` 列出六条自我伤害机制——**步骤过时/规格债**、矛盾条目、能力错配指令、注意力预算挤占、僵化不能跳过、假停止信号；最强工业案例是 Cursor 的 `<maximize_context_understanding>` 在 GPT-5 上 **counterproductive**（同一条指令在旧模型上"worked well"）；`R-F §6.2` 还给出"干净 RL 微调后对含一个受控错误的 CoT 前缀鲁棒性**低于**未微调基线（19% vs 20%）"的机制证据。
- **最适合的场景**：执行模型明显弱于规划者、任务是确定性/可测试的代码修改、且验收能写成可执行检查时（`R-F §10.2` 明列这三点为适用前提）。
- **现实案例或证据**：`R-E §9.4`（phase 专用 8 条，含 ≤1 页/每步 ≤6 行/固定五字段/判据必须可检查且穷尽）、`R-E §6.5`（组合出的 weak-model phase 步骤模板原文）；`R-A §7.1` 记录 Spec Kit 的"约束逐字搬进任务描述"与 cc-sdd 的"只喂该任务最小上下文" `【实证】`（模板原文）；但 `R-F §6.2` 的伤害机制同时成立 `【实证】`（官方工程记录）。
- **与其它选项的组合性**：**可叠加** 轴3-03（手册降为 L2 参考层并带过期条件）、轴3-05（判据行换成测试）、轴3-12（差异引用）；**互斥**于 轴3-02 纯目标式；**需改造**才能满足 轴3-16 无独立文档。

---

#### 轴3-02 目标式（只写意图与验收）
- **做法**：每个 phase 只写三件：要达成什么（意图）、不许违反什么（边界）、怎么算完成（验收判据）。不写读文件顺序、不写改动切入点、不写参考实现。
- **谁写/谁读/谁执行**：高智力模型写；任何能力的模型自己决定路径；审查者只看目标与验收是否对齐。
- **优点**：**永不腐败**（没有路径就没有过时的路径）；`R-F §3.1` Don Syme 的结论是"**没有任何一种编码场景，是高层声明式指引 + 护栏 + 边界 + 成功条件不带来帮助的**"；对强执行模型路径写死是纯成本（`R-F §2` DETAIL 的敏感度差、PartialOrderEval"更大模型以更少提示细节达到更高准确率"）。
- **代价与风险**：**弱执行者在目标式下损失最大**——DETAIL 中 o3-mini 最粗提示下只有 **0.34**（L3 详细为 0.68），GPT-4 是 0.60；`R-B §2.1` 的歧义证据（Pass@1 −35%~−52%、60%+ 首次回答直接写代码不澄清）；`R-F §6.3` 明确"纯 B 会把风险全部转移给最弱的一环"。
- **最适合的场景**：探索性工作（架构选型、研究综合、开放式设计）——`R-F §7.1` "确定 vs 探索"行要求这类**只写边界不写结果**；或执行者不再明显弱于规划者时。
- **现实案例或证据**：`R-F §3.1`（Don Syme / Alan Pope / Guy Podjarny 的粒度判据："太细，你不如直接写代码；太笼统，你失去护栏"）、`R-F §6.1`（Cursor×GPT-5、OpenAI"矛盾提示对强模型伤害更大"、"think step by step 无益甚至有害"、PartialOrderEval、AgentSpec）、`R-F §5`（Anthropic/OpenAI/Google 三家一致的"少写路径、多写目标与约束"）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴3-03（作 L0 骨架）、轴3-05（测试就是规格，天然目标式）、轴3-12；**互斥**于 轴3-01/轴3-07；**需改造** 与 轴3-09（检查点需要路径假设）。

#### 轴3-03 三层混合式（L0 目标 / L1 硬约束 / L2 可作废参考步骤）
- **做法**：每个 phase 固定三层且**优先级显式声明**：**L0 目标层**（一句话目标 + 业务理由 + 非目标，永不删，放文档最前）；**L1 硬约束层**（接口/类型/schema、不变量、错误与失败行为、兼容性保证、不可逆动作的确认门、可执行验收——每条 = 一条命令或一个断言，可机检或可独立复核）；**L2 参考步骤层**（建议的读文件顺序、改动切入点、参考实现，**文档头部写一行**"L2 与 L0/L1 或代码现状冲突时，以 L0/L1 与代码为准；L2 不构成验收条件"，每条带**过期条件**，验收后收缩/删除）。L2 禁止写"当前代码长什么样"的描述性文字，禁止写**能力补偿型指令**（"务必彻底搜索""逐步思考""先列出所有文件"）。
- **谁写/谁读/谁执行**：高智力模型写三层；**弱模型照 L1 + L2 做；强模型跳过 L2 只读 L0+L1**（L2 被定位为"上一位工程师的笔记"而非命令）；审查者按层选深度。
- **优点**：**同一份文档同时服务不同能力模型**，且把"规格债"从"要逐条维护"变成"**可被快速判定作废**"；`R-F §10.3` 的一句话是"12 个月后你要做的不是重写所有 phase 文档，而是把 L2 那一段直接删掉——删得动，就是因为现在就给它写好了过期条件"。
- **代价与风险**：三层的**边界判断本身是工作量**（什么算 L1、什么算 L2 需要每个 phase 重判）；层内写出矛盾条目时，强模型**受伤害更大**（`R-F §1.2a` OpenAI 官方）；`R-F §10.2` 给出六条失效条件（执行模型不再弱于规划者 / 任务转为探索性 / 验证成本高于写死成本 / 规格无人拥有 / 出现目标式系统性更好的受控证据 / 框架官方声明步骤层过时）。
- **最适合的场景**：异构分工（强模型规划 + 弱模型执行）、任务多为确定性代码修改、且验收可写成可执行检查——**正是本仓的现状**。
- **现实案例或证据**：`R-F §3.4`（三层最小可落地形态表）、`R-F §7.1`（逐决策判据表：可逆性/接口 vs 实现/确定 vs 探索/可验证性/模型能力/时效/所有权/风险不对称）、`R-F §7.2`（L2 写法规范五条）、`R-F §10.1`（形态描述）；形态一的实证来源是 Tessl 的 `.impl` 降级标记（"尽量保留以求稳定，但不压倒规格；规格显式改绿时**规格赢**"），形态二是 spec-kit 的 CDD 契约层，形态三是 Anthropic 的 `<background_information>/<instructions>` 分节 + OpenAI GPT-5 的 `<context_gathering>`/`<persistence>` 互斥旋钮 + Kiro 的 Feature/Bugfix/Quick Spec 档位 `【实证】`（`R-F §3.1/3.2/3.3`）。
- **与其它选项的组合性**：**可叠加**几乎全部（三层是组织原则）；与 轴3-01 组合 = "手册降级为 L2"；与 轴3-04 组合 = "L1 就是契约"；与 轴2-06 分层披露式是同一思想在 spec 侧的镜像。

#### 轴3-04 契约式（只写接口与不变量）
- **做法**：phase 文档只写本 phase 必须遵守与必须产出的契约：输入/输出/类型/schema、不变量、错误与失败行为、可观察行为、兼容性保证、禁止出现的形态；不写实现步骤、不写内部数据结构、不写算法选择。跨组件时：权威契约**单方拥有**，跨 phase 消费者**钉住版本**，**不得复制别的 phase 的实现计划**；provider 侧与 consumer 侧**双向验证**，且"**消费者 mock 不能证明 provider 合规**，必须包含集成验证"。
- **谁写/谁读/谁执行**：高智力模型写契约；弱模型照契约实现；审查者做双向验证。
- **优点**：**"什么不许变"可机检、可长期有效**；`R-F §7.1` 把"接口 vs 实现"列为判据表第一行；结构性阻止 phase 之间的实现计划复制（对照 `I-A` 无重复契约的要求）；`R-E` 的引用 vs 复制判定表把"契约事实"明确划为**应当复制**的那一类（弱模型依赖精确字面量）。
- **代价与风险**：**没有契约的 phase（纯行为变更、探索性改动）无法表达**；契约写错时错误被放大到所有 consumer；`R-F §3.2` 记录 CDD 是 spec-kit **2026-09-16 才立项并合并**的方向，**缺长期实践数据**；`R-F §3.2` 也承认"schema 有用但不必然能表达全部行为义务"。
- **最适合的场景**：多 phase/多组件、有明确接口边界、且集成失败成本高时。
- **现实案例或证据**：`R-F §3.2`（spec-kit issue #4609 / PR #4616 官方文档级定义：产品需求=意图行为、接口契约=组件间协作、实现规格=各组件对着已达成一致的契约写且不得复制他组件的实现计划；归属与钉版本规则；双向验证与"mock 不能证明合规"）、`R-F §5.1`（OpenAI SWE-Bench verified 的官方 system 指令是**高度规定性**的：指定 `apply_patch` 格式、禁止 `ls -R/find/grep`、要求 triple check——**官方对"脆弱可验证的执行接口"同样写死**）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴3-03（作 L1）、轴3-05（契约测试）、轴2-04 契约优先式 spec（同一份契约被双向引用）；**互斥**于 轴3-07 伪代码式（伪代码正是契约要排除的实现层）。

#### 轴3-05 测试先行式（测试就是规格）
- **做法**：phase 文档的主体是**测试**：每个行为变化给一对 RED/GREEN，**同一 `gate_cmd` + 同一 oracle identity + task-relative 证据路径**；RED 必须由目标断言导致非零（不是 setup 失败），GREEN 期望 0 并保留命名的负例；`gate_cmd` 只是测试命令、绝不是许可。
- **谁写/谁读/谁执行**：高智力模型设计 RED/GREEN；弱模型先让它红再让它绿；verify 阶段按同一 oracle 复算。
- **优点**：`R-B §6.2` 记录"把测试当作可执行规格"是本报告中最强的正向证据；`R-A §8 M8` 记录 Kiro（性质测试 + `Validates: Requirements 2.3`）、Spec Kit（quickstart.md + contracts）、cc-sdd（RED 证据）、Anthropic（pass/fail 检查）**四家独立采用**；`R-F §7.1` "可验证性"行要求凡能变成可执行检查的必须写且是最高优先级。
- **代价与风险**：**"测试通过"会被当成完成信号**，而 `R-D §7.4` 明确"可验证性不等于必须有测试"——可通过 test / demonstrate / inspect / analyze 四种方式之一满足；测试作者与实现者未分离时测试会被弱化（`R-C §4.4` 的强制分离要求）；`I-A` P-09 说明只写一条 `gate_cmd` 不足以覆盖环境/fixture/清理/失败处置。
- **最适合的场景**：行为可断言、且 oracle 可写成命令或断言的确定性改动。
- **现实案例或证据**：`I-B §2.4` 第 2 条（RED/GREEN 可证伪对，现行机制）、`I-B §4 K9`；`R-C §4.3`（TDD 在 AI 工作流中的适用性）、`R-C §4.4`（测试作者与实现者分离，强制）；`R-B §6.2/§6.3` `【实证】`。
- **与其它选项的组合性**：**可叠加** 轴3-04（契约测试）、轴3-03（作 L1 的可执行验收）、轴3-09（检查点 = 测试通过 + 边界未破）；**需改造** 轴3-07（伪代码与"先写测试"顺序冲突）。

#### 轴3-06 diff 预览式
- **做法**：phase 文档直接给出目标改动的 diff 或"改动前后对照"（文件路径 + 变更块 + 变更意图注）；执行者的任务是让实际 diff 与预览一致。
- **谁写/谁读/谁执行**：高智力模型写预览（可能借助示例）；弱模型照抄并适配；审查者比对实际 diff 与预览。
- **优点**：**最短的意图→实现路径**，几乎没有解释歧义；`R-A §7.1` 记录 Kiro 的 `bugfix.md` 三段式（Current Behavior (Defect) / Expected Behavior (Correct) / Unchanged Behavior (Regression Prevention)）是"行为对照"的同族形态；对纯重复性改动效率极高。
- **代价与风险**：**diff 会立刻过期**（`R-F §6.2` 第 1 条规格债 + `R-F §7.1` 时效行明确"描述性文字/文件级锚点会变成负担"）；若目标代码与预期上下文不同，弱模型会盲从错误 diff；无法表达"为什么"。
- **最适合的场景**：机械性/模式化改动（重命名、迁移、批量替换）、或改动可由少量真实样例穷举时。
- **现实案例或证据**：`R-E §1.4` 的引用 vs 复制判定表把"长表格/大段代码"划为**应移入附录或独立文件**（正文只留结论 + 指针）；`R-F §7.2` 明确**禁止**在规格里写"当前代码长什么样"的描述性文字，只写目标形态 + 不许出现的形态 `【实证】`（规则有据，但"diff 预览式"这一具体形态在 9 份报告中**无直接框架案例**）。
- **与其它选项的组合性**：**可叠加** 轴2-16 delta 式 spec、轴3-16（无独立文档，diff 就是文档）；**互斥**于 轴3-02 纯目标式；**需改造**才能带上验收判据。

#### 轴3-07 伪代码式
- **做法**：phase 文档以伪代码/骨架签名为主：函数签名、类型定义、控制流轮廓、数据结构形状；散文只写"为什么这样"。执行者把伪代码转成真实代码。
- **谁写/谁读/谁执行**：高智力模型写；弱模型翻译；审查者检查伪代码是否满足契约与不变量。
- **优点**：**表达实现意图最省 token**；签名与类型是可机检的（`R-F §3.4` 把"接口/类型/schema"划入 L1 硬约束层）；对语言/框架明确的重复性实现效果最好。
- **代价与风险**：**越接近实现，越容易与真实代码漂移**——`R-F §8.2` 把"文件级/函数级锚点"和"描述性文字"列为 12 个月后最可能变成负担的两类；伪代码会诱导模型跳过设计判断；`R-A §2` 记录 Kiro **明确 MUST NOT** 把非编码活动写进任务，但也没采用伪代码式。
- **最适合的场景**：算法/数据结构密集、且接口已由契约固定的实现阶段。
- **现实案例或证据**：`R-F §3.2` 的 CDD 把"实现规格"单列一层（说明"实现层"确实需要容器），但 `R-F §7.1` 把"内部数据结构/算法选择/私有函数拆分/文件内组织"划入**留给模型**的一侧 `【间接】`（报告支持"实现层可以写"，但不支持"以伪代码为主体"）。
- **与其它选项的组合性**：**可叠加** 轴3-04（伪代码作为契约的非权威附注，必须标可作废）、轴3-01（每步的"改"字段用伪代码）；**互斥**于 轴3-05 测试先行式（顺序与主体冲突）、轴3-02 纯目标式。

#### 轴3-08 对话式（模拟执行者提问）
- **做法**：phase 文档写成"执行者会问的问题 + 答案"：Q"我要改哪个文件？" A"…"；Q"如果 X 不存在怎么办？" A"…"。问题集来自历史执行者的真实卡点或十维度完整性检查（user journey / surface scope / data & state transitions / success boundary / failure boundary / permissions / integrations / non-goals / deferred handoff / acceptance evidence）。
- **谁写/谁读/谁执行**：高智力模型写（最好基于上一轮真实卡点）；弱模型按问答逐条落地；审查者检查问题是否覆盖十维度。
- **优点**：**直接消灭"读者必须猜"**（`I-A` P-12）；把潜在歧义提前暴露在写文档阶段；`I-B §1.4` 第 7 条的 Clarify 十维度检查本身就是一份现成问题清单；新增问题可增量追加（append-only 友好）。
- **代价与风险**：**问题集依赖提问者的想象力**，没问到的地方仍然缺；`R-D §1.3` Amazon PR/FAQ 会议的四问（"哪些假设必须为真""最可能失败的三个原因"）表明问答式适合**判断层**而非**执行层**；问答式很难做交叉一致性检查。
- **最适合的场景**：执行者反复在同一类地方卡住（历史 finding 可复用）；或作为 轴3-01/轴3-03 的增量补丁层。
- **现实案例或证据**：`I-B §1.4` 第 6–7 条（spec-clarify 三类陈述分类 + 独立轴一批/依赖轴出批 + 每问一个决策轴 + 十维度完整性检查 + `trigger=false` 必须显式）；`R-A §4` 记录 AI-DLC 的 question 文件形状（A–E 选项 + 强制 `X. Other (please specify)` + `[Answer]:` 标记，每批最多 4 个问题，回答方式可 Guide Me / 编辑文件 / 聊天，**问题文件始终是唯一真相来源**）`【实证】`（官方机制原文，但那是**澄清**用途而非 phase 文档体裁）。
- **与其它选项的组合性**：**可叠加** 轴3-01/轴3-03（作补充节）、轴4 的"问答式交互"审查输入形态（同一机制被审查侧复用）；**互斥**于 轴3-06 diff 预览式（体裁冲突）。

#### 轴3-09 检查点式（checkpoint-driven）
- **做法**：phase 文档定义若干**检查点**：每个检查点是一组"必须同时成立的断言"（测试通过 + 覆盖率门槛 + 边界未破 + 无 TODO/FIXME 残留 + 不是 mock/stub/placeholder）。文档主体是检查点及其判定方式；步骤由检查点之间的最短路径隐含。
- **谁写/谁读/谁执行**：高智力模型定义检查点；弱模型自选路径到达检查点；审查者只验检查点是否真成立。
- **优点**：**以"什么必须为真"代替"做什么"**，天然抗规格债；`R-A §7.1` 记录 Google Conductor 的 plan 结构含显式的 `Task: Phase Verification & Checkpoint (Refer to workflow.md)`；`R-A §6.5` 记录 cc-sdd 的 implementer 强制自审清单（"Verify the implementation is NOT a mock, stub, placeholder, fake, or TODO-only path" / "Verify there are no TBD, TODO, or FIXME markers left in changed files"）。
- **代价与风险**：**检查点之间的路径完全交给执行者**，弱模型能力不足时会在中途迷路（`R-B §1.3` lost-in-the-middle + DETAIL 的 o3-mini 0.34）；检查点若只测结果不测过程，无法发现"绕过"式实现。
- **最适合的场景**：执行者具备一定自主性、且失败可被检查点立刻观测时。
- **现实案例或证据**：`R-A §5.3`（Google plan 的 checkpoint 任务 + workflow.md 的 `[ ] → [~] → 红 → 绿 → 覆盖率 >80% → 提交 → git notes → [x] + commit SHA` 生命周期）、`R-A §6.5`（cc-sdd 结构化状态回报与自审清单）、`R-A §8 M9`（逐任务停顿：Kiro "VERY IMPORTANT 只做 one task"、cc-sdd "1 task per iteration"）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴3-05（检查点的核心判定就是 RED/GREEN）、轴3-03（检查点属 L1）；**互斥/需改造** 与 轴3-01 全手册（手册给路径，检查点式故意不给路径）。

#### 轴3-10 全字段任务卡式（plan-task 型）
- **做法**：phase 文档 = 一组任务卡，每卡固定字段集（现行 `plan-task.v4` 顺序）：`ID / Phase / goal / design_state / versioned_refs / source_refs·decision_refs / 输入 / 依赖 / 并行 / FR / AC / 动作 / 精确文件 / boundary / 输出 / Knowledge / verification_role / paired_task / gate_cmd / expected_exit / oracle / evidence_path / STOP / recovery / task risk / test tier·test method / scenarios / fixtures / coverage limits` + 一个"执行状态填写区（唯一完成权威）"。
- **谁写/谁读/谁执行**：高智力模型填卡；弱模型按卡执行并只改状态区；审查者按字段逐项核对。
- **优点**：**字段即检查槽位**——`R-A §8 M1/M2` 的结构强制 + 格式机器校验；traceability 天然（每卡带 source_refs/FR/AC）；`I-A §5 G-08` 承认**单卡字段设计本身很完整**（精确文件、STOP 条件、覆盖率边界都对）。
- **代价与风险**：`I-A` P-03 记录**字段太长反而埋掉关键信息**（`oracle` 字段 886 字符内嵌 JSON、`acceptance_data` 8 个场景压成一行 1,926 字符）；P-16 记录 **tasks.md 652 行中模板/空白/`N/A` 行合计 195 行 = 29.9%**，9 张卡各 12 行空白填写区 = 108 行；P-14 记录实现者需要自行拼出读材料的顺序。
- **最适合的场景**：需要跨材料双向追溯、且审查者/verify 阶段要按卡复算的任务。
- **现实案例或证据**：`I-B §2.5`（`plan-task.v4` 卡契约与字段顺序，含 `skills/spec-tasks/templates/tasks-template.md` L26–L61）、`I-B §2.4` 第 10 条（Phase 交接块八字段）；`I-A §2.4` 给出这套字段的**实测代价**（单卡 37–39 行、≈32 个 bullet 字段）`【实证】`（模板原文 + 本仓量化审计）。
- **与其它选项的组合性**：**可叠加** 轴3-03（字段按 L0/L1/L2 分组）、轴3-12（差异只写变化字段）；**互斥**于 轴3-16 无独立文档；**需改造** 与 轴3-02 目标式（字段式天然啰嗦）。

#### 轴3-11 故事切片式（story slice + 可选 checkpoint）
- **做法**：phase 文档 = 一个**可独立审查的切片**（story）描述 + 一个可选检查点位置（实现前或实现后）；切片按能力/约束遍历产出，形成一份**有序清单**（如 `stories.yaml`），实现单位是"一次一个 story"。
- **谁写/谁读/谁执行**：高智力模型与决策者共同走查能力与约束、按"可独立审查的切片"提议 story 并逐个确认检查点位置；弱模型一次做一个 story；审查者在切片边界做审查。
- **优点**：**切片粒度与审查粒度对齐**（每个切片独立可审）；检查点位置可逐个选择（不是全局强制）；`R-A §6.2` 记录 BMAD 的关键设计是"按意图规模自选路径"（`Small changes go straight to build. Complex work gets the depth it needs.`）。
- **代价与风险**：**官方自陈"拆分工作会丢信息"**——"a requirement weakens, a constraint disappears, or two correct stories fail when combined"（`R-A §6.2`）；实现单位依赖**人挑 story 与排序**，弱模型自主性有限；切片间的组合失败难在切片内发现。
- **最适合的场景**：任务可切成若干正交、可独立审查的行为增量；且有人（或强模型）负责切片与排序。
- **现实案例或证据**：`R-A §6.2`（BMAD 的 `bmad-spec` → `stories.yaml` + capability/intent/success condition 三件套 + 每个 story 询问"实现前还是实现后要检查点"；`bmad-sprint-planning` 出 PASS/CONCERNS/FAIL 就绪度裁决；官方自陈拆分风险）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴3-09 检查点式（切片 + 检查点即完整形态）、轴3-05（每切片一对 RED/GREEN）、轴2-03 用户旅程场景式（切片来自场景）；**需改造** 与 轴3-10 全字段卡（切片需映射到卡）。

#### 轴3-12 差异引用式（只写本检索边界内差异 + 常驻紧凑索引）
- **做法**：每个 phase 文档**只写本 phase 检索边界内的差异**（相对既有代码与 spec 的变化），不重述背景、理由、架构；所有共同事实引用 spec/decision-log 的 ID 与纯文本路径；另有一份**常驻的紧凑索引**（章节 → 一句话摘要 → 建议读取时机）告诉执行者"什么时候读哪一节"。
- **谁写/谁读/谁执行**：高智力模型写差异 + 维护索引；弱模型只吃"索引 + 本 phase 差异"（just-in-time）；审查者需要 spec + 全部 phase 才能判断整体。
- **优点**：**体积极小、天然抗重复**（直接治 `I-A` P-04 的 98.9% 逐字转写与 P-14 的入口淹没）；`R-A §7.3` 的关键观察是"控制喂进去多少比控制写出来多少更重要"；这正是本仓 OI-001 的已收敛决议。
- **代价与风险**：`I-C §5 I2` 明确指出——**"单独审一份 phase 文档无法判断整体质量核心；必须与 spec 一起审"**，这正是"一次合并审查"的结构性原因；执行者若拿不到 spec 就失去上下文；索引腐化会成为新的失败面（`I-A` P-10）。
- **最适合的场景**：存量系统的多 phase 迭代——即本仓的多数场景。
- **现实案例或证据**：`I-B §5 D1`（OI-001 resolution 原文："一份权威 spec + 每个 phase 只写本检索边界内的差异 + 常驻紧凑索引"）、`I-B §6.3`（CARD-02 FR-08：phase 文档"只含本检索边界内差异 + 引用"）、`R-A §6.1`（OpenSpec 的 delta 机制 + 只审变更不看未变上下文）、`I-C §5 I2`（审查结构性结论）`【实证】`（本仓官方决议 + 框架模板）。
- **与其它选项的组合性**：**可叠加** 轴2-16 delta 式 spec（同一机制在两侧）、轴3-03（差异作为 L1 的增量表达）、轴1-14 registry（索引同源）；**互斥**于 轴3-11 故事切片式（切片需要自足叙事）；**需改造** 才能单独审查。

#### 轴3-13 状态回报契约式（文档即回报协议）
- **做法**：phase 文档除了要做什么，还**规定执行者必须按固定字段回报**：`RED_PHASE_OUTPUT`（证明测试先写）/ `REQUIREMENTS_CHECKED`·`DESIGN_CHECKED`（精确到章节号）/ `FILES_CHANGED` / `CONCERNS` / `BLOCKER`·`BLOCKER_REMEDIATION` / `MISSING` / `EVIDENCE`；缺信息必须**立即上报 `NEEDS_CONTEXT` 并说明缺什么，不许猜或填充假设**。
- **谁写/谁读/谁执行**：高智力模型定义回报契约；弱模型边做边填；**父控制器/审查者解析固定字段**做门与复盘。
- **优点**：**把"执行者是不是真做了"变成可解析的结构化事实**，而不是自然语言自述；`R-A §8.1` 反直觉发现 2 直接把 cc-sdd 这类小框架评为"弱模型适配做得最好"；与 `R-D §4.1` 的 Observation/Finding/Disposition 三段记录同构。
- **代价与风险**：**回报格式本身是强约束**，格式错就丢事实（`R-E §6.1` 实证：格式差异对弱模型准确率影响巨大且"不存在通用最优格式，只有恒定格式"）；执行者可能"为了填字段而编造"；`I-B` D5 明确要删除多层 evidence 包装——回报字段必须避免退化成又一层包装。
- **最适合的场景**：长时自主运行、且需要父控制器据此判断"下一步做什么"或"是否 BLOCKED"（`R-A §6.5` 的 Debugger 由 BLOCKED 触发）。
- **现实案例或证据**：`R-A §6.5`（cc-sdd implementer 提示模板的三条弱执行者规则 + 结构化状态回报字段 + `NEEDS_CONTEXT` 机制 + 强制自审清单）、`R-A §4`（AI-DLC 102-event audit trail + `[Answer]:` 标记 + 内联来源标记 `[desc]`/`[Q1]`）、`R-A §8 M5`（不确定性外显，五家框架独立采用）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴3-01（每步判据即回报字段来源）、轴3-09（检查点即回报点）、轴4 的"结构化 packet"审查输入；**需改造** 与 轴3-16（无文档则无回报契约）。

#### 轴3-14 参考实现式（standards + references 内联）
- **做法**：phase 文档**内联**本项目该怎么写的规范全文（命中即可用，不需要检索），并给出相似实现的位置清单：每条含 `Location` / `Relevance` / `Key patterns`（"从这段参考实现里能借什么模式"）。任务 1 恒为"先把这份 spec 文档落盘"，再开始实现。
- **谁写/谁读/谁执行**：高智力模型抽取并内联；弱模型不必检索、不推断"项目惯例"；审查者检查内联的规范是否过期。
- **优点**：**消灭"模型不知道本项目怎么写"这一整类失败**（`R-A §8.1` 发现 2 的执行者契约）；`references.md` 把"抄哪一段、抄什么"讲清，避免模型复制仓库里的次优模式——`R-A §5.2` 记录 OpenAI 的明确警告："**Codex replicates patterns that already exist in the repository—even uneven or suboptimal ones. Over time, this inevitably leads to drift.**"（团队一度每周花 **20% 时间**清 AI slop）。
- **代价与风险**：**内联的规范会腐化**（`R-A §6.3` 官方承认 `Refine` 是循环一环；Tessl 承认 `quietly go stale`、OpenAI 承认 `rots instantly`）；内联会让 phase 文档膨胀（与上下文预算冲突，`R-B §1.2`）；`R-A §6.3` 记录 agent-os **没有机器校验**，全靠约定。
- **最适合的场景**：项目有大量不成文/半成文规范、且弱模型反复写出不符合惯例的代码时。
- **现实案例或证据**：`R-A §6.3`（agent-os 的 `standards.md` 要求"把每个命中 standard 文件的**全文内联**"、`references.md` 固定三字段、Task 1 恒为保存 spec 文档；四段式 `shape.md` 含 `## Standards Applied` 逐条写 `api/response-format — [why it applies]`）`【实证】`（官方命令文件原文）。
- **与其它选项的组合性**：**可叠加** 轴3-01/轴3-03（内联规范属 L1）、轴1-14（规范作为可检索 registry 而非内联）；**互斥/需改造** 与 轴3-12 纯差异式（内联与外置相反）。

#### 轴3-15 无独立 phase 文档（phase 只是 spec 的切片）
- **做法**：不产出 phase 文档；phase 的信息全部内联在 spec 里，按 phase 分段或按 phase 打标签；执行者收到的是"spec 的某个切片 + 当前代码"。
- **谁写/谁读/谁执行**：高智力模型写一份 spec；弱模型读切片；审查者审 spec（合并审查退化为单文档审查）。
- **优点**：**材料数量最少、零重复**（直接消灭 `I-A` P-04/P-16 那一类）；不存在"phase 文档与 spec 不一致"这一整类缺陷；OI-014 的"一次合并审查覆盖 spec + phase"在只剩一份文档时自然成立。
- **代价与风险**：**per-phase 差异无处安放**，spec 会随时间被所有 phase 的差异污染；执行者的上下文预算无法按 phase 收敛（`R-A §7.3` BMAD 的输入上限警告：超限会**静默丢信息**）；`I-A` P-01 证明"单一文件无上限"是本仓已经发生过的失败模式（极端案例单文件 13,195 行，其中 89.5% 是一节零动作清单）。
- **最适合的场景**：单 phase 小改动；或执行者上下文预算充足到能读全 spec 时。
- **现实案例或证据**：`I-B §6.3` 提到的一个候选方向（"让 phase 差异文档直接承担任务卡职责，**或让 plan.md 成为唯一 phase 权威**"）；`R-A §3` 记录 Tessl **没有 tasks.md**——执行单位是"一个 spec ↔ 一个逻辑功能单元 ↔ 一个代码文件"（spec 约 20–40 行）`【间接】`（框架级先例存在，但 Tessl 的粒度极低、与本仓多 phase 场景不同）。
- **与其它选项的组合性**：**可叠加** 轴2-16 delta 式 spec、轴2-11 活文档；**互斥**于 轴3-10/轴3-12/轴3-13 全部以独立文件为前提的选项；**需改造**才能与"每 phase 一次审查"并存。

#### 轴3-16 波形/依赖图式（wave-based）
- **做法**：phase 文档的骨架是**依赖图 + 波次**：无依赖的任务进 Wave 1，其余按依赖顺序入后续波；**波内并发、波间串行**；文档标注每个任务的波次与并行前提（独立输入、独立依赖、非重叠文件）。
- **谁写/谁读/谁执行**：高智力模型建图并分波；多个弱模型执行者按波并行；审查者检查并行声明是否成立。
- **优点**：**并行度显式可验证**，而不是靠"看起来独立"；`I-B §2.4` 第 4 条已要求"依赖图必须无环并说明每条串行边的理由"；`R-A §2` 记录 Kiro 已产品化（为 tasks.md 建依赖图并分 wave，"Waves execute sequentially; tasks within a wave execute concurrently"）。
- **代价与风险**：**并行假设错误是最贵的错误**（`I-B §3` plan-eng-review 明确要拒绝对每条 `[P]` 的无效并行声明）；分波增加文档结构复杂度；并发执行者的能力要求高于串行（`R-D §6.1` 记录审查自身也受并发上限约束，本仓 SD-11 把并发统一为 2–5）。
- **最适合的场景**：phase 数量多、有真实可并行的独立任务、且希望压缩 wall-clock 时间时。
- **现实案例或证据**：`R-A §2`（Kiro 的任务依赖图 + 波次并行原文）、`R-A §6.2`（BMAD `bmad-sprint-planning` 依赖分组）、`R-A §6.1`（OpenSpec schema.yaml 定义产物依赖图，`design` 可与 `specs` 并行）、`I-B §2.4` 第 4 条与 `I-B §3` plan-eng-review `【实证】`。
- **与其它选项的组合性**：**可叠加** 轴3-10/轴3-11（卡或切片上加波次字段）、轴4 的"分批审查"（按波分批）；**需改造** 与 轴3-02（目标式不关心顺序）。

## 轴 4：plan 审查（spec + phase 一次覆盖）的方法与能力

> 背景约束：本轴的对象是**一次同时覆盖 spec 与 phase 文件**的审查（`I-C §2 C2`，来源 OI-014 / FR-56 / AC-57；`I-B §4 K6` 把它列为"两类质量核心合一"）。四类质量核心跨三张卡的产物——**需求翻译完整性**（CARD-02 FR-07）、**验收可执行**（CARD-04 FR-16）、**架构合理**（CARD-02 FR-07）、**依赖正确/并行声明/写集**（CARD-03 FR-14）——而 ① 是**唯一同时触达三卡产物的审查点**（`I-C §5 I3`）。同时必须叠加三条硬约束：phase 文档"只写差异"使单独审一份 phase 无法判断整体，**合并审查是结构必然**（`I-C §5 I2`）；原 plan.md/tasks.md 双写被删除后，"依赖正确/并行声明/写集"此后只存在于 phase 文档中（`I-C §5 I6`）；以及"审查派发不受机器校验前置"（`I-C §3.4`、SD-17）。
>
> 现状基线（作为对照，不是推荐）：`wh-review` v4.1.0 审的是**冻结的材料字节（materials JSON）而非 diff/worktree**（`I-C §4.2`）；make-decision 有 red/blue 双角色（同 `pair_id`、每 role 只调一次不重试、`lens-only` 只给 finding 不给 verdict，`I-C §4.4`）；build-code 侧已是 worktree/commit-tree 审查（`I-C §4.5`）；`debate` 是四队法庭但**自我定性为"可选便利层、非质量地基"**（`I-C §4.6`）；首轮方向/detail 审查曾双双 `unavailable`（`PROTOCOL_INCOMPATIBLE`、`MATERIAL_INCOMPLETE`），修后取得可消费结果（red 6 + blue 5 findings、无 blocking 级）作为对比锚点（`I-C §4.7`）。全轴需同时记住 `R-D §10` 的证伪清单与 `R-D §4.3` 的 DORA 反证（"用更多流程回应稳定性问题会让事情变得更糟"）。

### 4A 审查者构成

#### 轴4A-01 单模型审查者
- **做法**：由一个模型（单一 provider + 单一上下文）完成全部审查，输出 findings。
- **谁写/谁读/谁执行**：审查者模型写 findings；主会话逐条处置；人读处置结果。
- **优点**：成本最低、延迟最低、无裁决冲突；`R-D §6.1` 记录 Claude solo 在跨模型实验中是**帕累托最优**。
- **代价与风险**：自审自判风险（若与建造者同模型同上下文）；`R-D §3.2` 量化了自偏好偏差（GPT-4 自偏好 **0.520**，recall 0.945 vs 0.425）；同源偏差机理尚无定论（困惑度 vs 自识别两文归因不一致）。
- **最适合的场景**：低风险、材料小、且审查者与建造者不同上下文时。
- **现实案例或证据**：`R-D §3.1`（Claude solo 基线 91.4% 通过率最高）、`R-D §3.2`（自偏好偏差量化）、`R-D §9 建议 D`（"多模型/多审查者的默认配置是 1 个主审查者 + 1 个异构补充审查者"）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4A-08 混合分层中的"初审"位；**互斥**于 4A-02/4A-06/4A-07；与 4B-06 blind 组合可部分缓解自审问题。

---

#### 轴4A-02 多模型异构并行审查者
- **做法**：多个不同 provider/模型的审查者并行审同一材料，findings 汇总后统一处置（可去重、可标注来源模型）。
- **谁写/谁读/谁执行**：各审查者独立产出；汇总者（人或主会话）合并；主会话逐条处置。
- **优点**：`R-D §2.3` 的第三方实测显示审查者之间**几乎不重叠**——617 个 (file, line) 坐标中 **93.4% 只被一个 reviewer 发现**，6.0% 被两个，0.6% 被三个，四个同时命中 0 次 → 加第二个 reviewer 是**增量而非重复**；`R-D §3.3` 还有反向证据：X-MAS（27 模型 / 170 万次评测）显示同构 → 异构 MAS **免改结构即可提分**（chatbot-only MATH +8.4%、chatbot-reasoner AIME +47%）。
- **代价与风险**：`R-D §3.1` 一手论文显示收益**方向不对称**——Reviewer 明显强于 Writer 时收益最大（Claude 审 Codex +18.1pp），**反向则显著变差（Codex 审 Claude −8.6pp）**；`R-D §3.3` 记录 350+ 模型评测中错误高度相关（双错时 60% 一致），且**越强的模型错误相关性越高，跨厂商亦然**；`R-D §6.1` 记录冗余审查可**零收益 +72% 成本 +58% 延迟**。
- **最适合的场景**：高风险材料、且能保证审查者不弱于建造者时。
- **现实案例或证据**：`R-D §2.3`（679 findings 实测：93.4% solo、误报率 0–4.8%、严重性越高误报率往往越高）、`R-D §3.1`（跨模型 116 任务 6 条件对照，含 p_BH 与自我限定）、`R-D §3.3`（MAD 被证伪、调用数非单调、错误相关性）、`R-D §9 建议 D`（默认 1 主 + 1 异构）`【实证】`（含一手论文与第三方实测）。
- **与其它选项的组合性**：**可叠加** 4A-06（异构 × 红蓝）、4B-03（packet 使多审查者输入一致）、4D-05 交叉验证；**需改造** 与 4C-06 纯 advisory 组合时需明确谁做汇总裁决。

#### 轴4A-03 强模型审弱模型产物（能力上位审）
- **做法**：审查者固定为能力明显强于建造者的模型（例如建造者是快速小模型，审查者是高智力模型）。
- **谁写/谁读/谁执行**：强模型审查者；人读；主会话处置。
- **优点**：**这是唯一有正向一手实验支持的方向**：`R-D §3.1` 中 Claude 审 Codex 通过率 71.6% → **89.7%（+18.1pp，p_BH = .001）**；同模型自审也有 +12.9pp（p=.022）→ 结论是"**当审查者能力显著高于生产者时**，引入独立审查者（无论是否同源）能提高正确率"；`R-D §8` 记录 Olausson et al.（ICLR 2024）关于自修复的发现同向。
- **代价与风险**：成本高于弱模型自审；作者自陈实验**无法分离"审查方向"与"审查者/被审者基线能力差"**，且 AO 与 OA 直接对比 **p_BH = .1444 不显著**；样本仅 116 题、单一模型对、竞赛题而非仓库级任务、单一 prompt。
- **最适合的场景**：**正是本仓的异构分工场景**（高智力模型规划、弱模型执行）——审查者天然是规划侧模型。
- **现实案例或证据**：`R-D §3.1`、`R-D §8`、`R-D §10`（"不同厂商模型交叉审查必然更好"被部分证伪，但"审查者强于生产者"有支持）`【实证】`（一手论文，但作者自我限定必须一并引用）。
- **与其它选项的组合性**：**可叠加** 4A-06、4A-07（辩论队里让强模型当法官）、4D-03 风险加权；**互斥**于 4A-04。

#### 轴4A-04 弱模型审强模型产物（反例选项）
- **做法**：用更便宜/更弱的模型做审查者，意图以低成本获得"第二双眼睛"。
- **谁写/谁读/谁执行**：弱模型审查者；人读；主会话处置。
- **优点**：成本极低；在**模式化/清单化**缺陷上（缺字段、缺 ID、禁词、格式漂移）弱模型足以胜任——`R-A §8 M2` 的"格式机器校验"本质就是把这类判断交给确定性机制。
- **代价与风险**：`R-D §3.1` 有**明确的负向证据**：Codex 审 Claude 通过率 91.4% → **82.8%（−8.6pp，p=.046）**，回归率最高 11.2%，丢失 13 个原本通过的案例 → **审查者弱于生产者时审查会净损害**；`R-D §9 建议 C` 明确高严重性必须绑定更强证据要求以防误报。
- **最适合的场景**：仅用于**格式/完整性/禁词/孤儿引用**这类确定性检查，而非语义质量裁决。
- **现实案例或证据**：`R-D §3.1`（−8.6pp 与回归率 11.2%）、`R-D §10`（"审查者越多越好"证据不支持）`【实证】`（**反向证据**）。
- **与其它选项的组合性**：**可叠加** 4E-04 清单写回 + 4B-05 逐条核对清单，把弱审查者限制在清单内；**需改造**才能安全使用；**互斥**于 4A-03。

#### 轴4A-05 同模型自审
- **做法**：建造者模型在**新上下文**中审自己的产物（可能是同一模型不同会话）。
- **谁写/谁读/谁执行**：同一模型的新上下文；人读。
- **优点**：`R-D §3.1` 中 Codex 自审（同模型）通过率 71.6% → **84.5%（+12.9pp，p=.022）**，说明"同源 ≠ 无效"；成本低于异构；操作最简单。
- **代价与风险**：`R-D §3.1` 中 Claude 自审是 **+0.0pp 且 +72% 成本 +58% 延迟**的"被支配方案"；`R-D §3.2` 的自偏好偏差直接适用；违反本仓"禁止自审自判"的宪法边界（`AGENTS.md`、`R-A §8.2` 凭证安全条）。
- **最适合的场景**：作为**建造者自检**（写文档时自查），而非替代独立审查。
- **现实案例或证据**：`R-D §3.1`（同模型自审双向结果：+12.9pp 与 +0.0pp）、`R-D §3.2`、本仓宪法"质量裁决由独立来源独立上下文产出，禁止自审自判" `【实证】`。
- **与其它选项的组合性**：**可叠加** 轴4B-06 blind 作为"最低成本的独立化"；**互斥**于作为唯一审查者的用法。

#### 轴4A-06 红蓝双角色对抗
- **做法**：同一审查对象由两个独立角色的审查者各审一次：`role=red` 与 `role=blue`，使用同一 `pair_id`、各自独立 request、保留 provider×role provenance；**每 role 只调一次、不把 paired request 变成重试循环**；`review_mode = lens-only`（只给 finding，不给 verdict）；顺序固定为一个逻辑 paired review fact（合计两次 public request）。
- **谁写/谁读/谁执行**：异源 provider 承载两个角色；主会话逐条处置；人读 provenance。
- **优点**：**同一材料上强制两种独立视角**，且"不重试"避免成本膨胀；provenance 保留到 role 级；`I-C §4.4` 记录这套机制**实际跑通过**（修复后 red 6 findings、blue 5 findings、无 blocking 级，`semantic_status=available`、`partial=false`、`coverage=satisfied`）。
- **代价与风险**：`I-C §4.7` 记录首轮双双 `unavailable` 的三个独立根因（身份分叉、材料路径不匹配、观测缺陷）——**协议复杂度本身就是失败面**；red/blue 机制绑定 `snapshot_tree`/`material_id`，而这两个字段正是 OI-013/SD-17 要**彻底删除**的校验面（`I-C §4.4` 末）；`I-C §4.6` 记录 debate 的固定并行（研究 4 + debate 4 + 红蓝 2）与 SD-11 的 2–5 并发上限不一致。
- **最适合的场景**：需要"两个独立判断"且能承受两次调用的材料。
- **现实案例或证据**：`I-C §4.4`（red/blue contracts 原文）、`I-C §4.7`（F1–F7 修复与修复后可消费结果）、`I-C §5 I5`（校验面删除与派发去前置的同一删除面）`【实证】`（本仓真实运行记录）。
- **与其它选项的组合性**：**可叠加** 4A-02（红蓝 × 异构）、4B-03（packet 输入）；**需改造**才能去掉 `snapshot_tree`/`material_id` 绑定（`I-C §5 I5`）；与 4A-07 四队法庭功能重叠（都是多角色对抗），**互斥**。

#### 轴4A-07 四队法庭式辩论（多角色对抗裁决）
- **做法**：把"裁决"换成四队法庭式对抗：**两方决策对等上庭受审（谁都不是免审基准）**，由 4 个独立上下文子代理分饰甲乙丙丁互相质疑，主代理只当 Lead 法官——**全程禁言、不下场写任何一方的辩护书、只综合幸存论点做最终裁决**；最多 2 轮 mailbox；缺并行能力时**自动降级为"单人三档"**（🟢必须确认 / 🟡建议考虑 / 🔴仅供参考）。
- **谁写/谁读/谁执行**：4 个独立上下文子代理 + 主代理法官；人读裁决。
- **优点**：**专门解决"方案作者自裁"与 self-preference bias**；对抗结构迫使论点被质疑而非被复述；`R-D §8` 记录"Beyond Detection: Evidence-based Multi-Agent Debate"指出 MAD 的价值更多在**提供可核查的推理证据**而非单纯提升判定准确率——这与"证据门槛"设计方向一致。
- **代价与风险**：`I-C §4.6` 明确其**自我定性是"可选便利层、非质量地基，不阻塞工作流"**；`R-D §3.3` 记录 MAD **被证伪**：多智能体辩论当前形式**不能可靠优于** self-consistency / 多路径集成，且对超参极敏感；`R-D §3.3` 另记录调用数增加时性能**先升后降（非单调）**；固定 4 路并行与并发上限冲突（`I-C §4.6`）；`R-D §6.1` 记录多代理成本高（Anthropic 侧约普通对话 15× token，见 `R-A §5.1`）。
- **最适合的场景**：**审查发现的裁决**（finding 之间冲突时）、多方案对比、方向级对抗——**不是**第一道 finding 生产者。
- **现实案例或证据**：`I-C §4.6`（debate 机制原文与自我定性）、`R-D §3.3`（被证伪的三条直觉 + X-MAS 反向证据 + arXiv:2511.07267 的价值定位）、`R-A §8 M10` 对照：AI-DLC 的独立 reviewer 与 cc-sdd 的 independent reviewer 是更轻的同族机制 `【实证】`（含被证伪证据）。
- **与其它选项的组合性**：**可叠加** 4A-02、4D-05 交叉验证（辩论是交叉验证的重形态）；**互斥**于 4A-06（功能重叠）；**需改造**以满足并发上限。

#### 轴4A-08 纯人来审
- **做法**：审查完全由人完成，模型只做材料准备与整理（不产出 findings，或只产出候选清单供人筛）。
- **谁写/谁读/谁执行**：人审查者；模型做记录；人做处置。
- **优点**：**人类审查者的"有用密度"是所有来源里最高的**：`R-D §6.1` 记录 Bosu/Greiler/Bird（MSR 2015，149 万条评论）测得**有用密度 65.5%**（63–69% 跨项目稳定），熟悉该文件时 **71–74%**、首次接触仅 32–37%，评论在一行内触发修改者有用率 **88%**。
- **代价与风险**：**吞吐是硬约束**：`R-D §6.1` 记录人工审查最优批次 200–400 LOC / 60–90 分钟（缺陷发现率 70–90%）、速度上限 <500 LOC/小时、单次 ≤60 分钟；`R-D §6.1` 记录开发者已投入 **10–15%** 时间在代码审查上；对**多 phase 文档 + spec** 这种体量，逐字人审不现实（`I-A §1` 显示现状单 task 四材料最多 2,956 行）。
- **最适合的场景**：方向上不可逆、或错误成本极高的关键决策点（`R-D §4.4` 的窄阻断集）；以及作为"抽样"的对象（见 4D-02）。
- **现实案例或证据**：`R-D §6.1`（SmartBear/Cisco 批次与速度数字、Bosu MSR 2015 有用密度、Beller MSR 2014 可维护性:功能性 ≈ 75:25 与 7–35% 评论被丢弃）、`R-D §4.2`（LLVM/Chromium/Kubernetes/Mozilla 各自的人工审批机制）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4A-09 混合分层（人审关键项）、4D-02 抽样（人只审抽中的）、4D-03 风险加权；**需改造**才能承载材料级体量。

#### 轴4A-09 混合分层（机器初审 + 强模型终审 + 人裁决）
- **做法**：三层分工：**第一层**确定性检查与廉价模型做格式/完整性/禁词/孤儿引用预筛；**第二层**强模型做语义质量审查（四类质量核心）；**第三层**人对窄阻断集与 `accepted_risk` 做裁决。每层产出独立的记录段。
- **谁写/谁读/谁执行**：脚本/廉价模型 → 强模型 → 人；主会话负责把三层的输出合成处置。
- **优点**：把"证据门槛"与"不阻断"同时落地——`R-D §9 建议 A` 要求把审查产出拆成 Observation（事实，机器采集）→ Finding（判定+严重性+证据引用+spec 条目映射）→ Disposition（fixed/accepted-risk/deferred/rejected）三段互不耦合，**段与段之间不互相阻断**，每段可有独立 `unknown`/`unavailable`/`incomplete`；`R-A §8.2` 把"独立审查"列为最省成本的改进方向之一。
- **代价与风险**：**三层=三份记录=三个失败面**；本仓已判定"多层重复 evidence 包装"要删除或合并（`I-B` D5）；若三层之间的边界不清会出现"都以为别人审了"的覆盖空洞。
- **最适合的场景**：材料体量大、质量核心跨多张卡（`I-C §5 I3`）、且需要同时满足"有证据门槛"与"不阻断推进"时。
- **现实案例或证据**：`R-D §9 建议 A/B/C/D`（三段记录、evidence threshold 最小定义与窄阻断集、分级→处置矩阵 + 校准回路、按错误成本分配预算）、`R-A §4`（AI-DLC 的确定性引擎 + 6 个 advisory sensor + 独立 reviewer sub-agent + 模型分层 judgment/templated **四层并置**）、`R-A §8 M2/M10` `【实证】`。
- **与其它选项的组合性**：**可叠加** 几乎所有其它选项（它是容器）；与 4E 全部能力提升手段天然配对；**需改造**以避免退化为多层包装（`I-B` D5）。

### 4B 审查输入形态

#### 轴4B-01 全文材料字节（冻结 bundle）
- **做法**：把当前材料的**完整字节**冻结成一个临时 bundle 送给审查者（发给审查者的就是 materials JSON）；审查者只能读该 bundle，不得访问仓库/Workspace/Git/shell/网络/宿主路径；返回真实 provider 身份、transport outcome、findings 与 material hash；用完删除临时 bundle。
- **谁写/谁读/谁执行**：主会话冻结并派发；审查者只读 bundle。
- **优点**：**输入确定性最高**（审查者看到的就是材料当前字节，不受文件系统状态影响）；`I-C §4.2` 记录这是本仓现行 wh-review 的实际形态；`I-C §6` 建议 ① 的输入形态**取 packet**（"与现行 wh-review 的材料字节审查同族"），代码审查另选 diff/worktree。
- **代价与风险**：**与哈希/快照/身份绑定深度耦合**——冻结会产生 hash 与 `material_id`，而 OI-013/SD-17 要求"阶段推进、审查派发、测试执行不依赖哈希/sha/快照/身份/材料/回执校验"，改"普通文件名 + 纯文本引用"（`I-C §5 I5`、`I-C §3.4`）；`I-C §4.7` 证明这套身份机制曾因脱敏规则与路径前缀失配导致 review `unavailable`；全文输入会让审查者被过程/审计噪声淹没（`I-A §4.3`：decision-log 只有 22.9% 是实现相关）。
- **最适合的场景**：文档类审查（spec/phase/decision-log）、且希望审查者看到的与最终定稿字节完全一致时。
- **现实案例或证据**：`I-C §4.2`（SKILL.md Purpose/Behavior 逐字：冻结字节、一次 broker 请求、返回 material hash）、`I-C §6` 第 3 条、`I-C §5 I4/I5`（纯文本引用与校验机器删除）`【实证】`（本仓现行实现 + 官方决议）。
- **与其它选项的组合性**：**可叠加** 4A-06 红蓝；**需改造**为"无哈希绑定的全文引用"；与 4B-02 diff **互斥**（同一审查点只能选一种主输入形态，`I-C §3.1` 记录 FR-53 要求三选一）。

---

#### 轴4B-02 diff / 变更面输入
- **做法**：只把**改动**送给审查者：已提交 phase 以"直接父提交树到候选提交树"为审查范围，记录 `commit_oid`/`parent_commit`/`parent_tree`/`commit_tree`/`candidate_tree` 及树一致性；未提交 phase 不伪造提交、记 `commit_oid=null` 与当前 HEAD 树；树不一致时结果只能是 `unavailable`/`incomplete`；无 `phase_id` 时派生 `review_scope=integration`、`subject_kind=worktree`。
- **谁写/谁读/谁执行**：runner 自动派生范围；审查者只读变更面。
- **优点**：`R-D §2.1` 记录 CodeRabbit 的增量策略（新 PR 做 full comprehensive review，后续 commit 做 incremental review，"focus on newly added changes … Maintains conversation context"）；`R-D §2.4 N1` 的"范围界定"与 Graphite 的"**PR > 200,000 字符不分析**"是同一机制；**审 diff 而不是审全文**直接避开 4B-01 的噪声问题。
- **代价与风险**：本题的审查对象是**文档**，而 phase 文档"只写差异"（`I-C §5 I2`）——若输入也只有差异，**审查者拿不到基准**，无法判断"依赖正确/并行声明/写集"是否与 spec 一致（`I-C §5 I2` 明确"单独审一份 phase 文档无法判断整体质量核心"）；`I-C §6` 第 3 条因此建议文档审查取 packet、代码审查才取 diff/worktree。
- **最适合的场景**：**代码审查**（build-code 每 phase、集成、verify-code 终末），而非 spec/phase 文档审查。
- **现实案例或证据**：`I-C §4.5`（build-code 合同原文：phase → `review_scope=phase`、无 phase → `integration` + `subject_kind=worktree`）、`R-D §2.1/§2.4 N1`、`I-C §6` 第 3 条 `【实证】`。
- **与其它选项的组合性**：**互斥**于 4B-01；**可叠加** 4C-03 增量审查；**需改造**才能用于文档（需同时给基准）。

---

#### 轴4B-03 结构化 packet 输入
- **做法**：不送原始材料，而是送一个**结构化包**：当前阶段/轨道、必修清单、四类质量核心各自的检查目标、材料的纯文本路径引用、明确的"读什么/不读什么"、finding schema（严重度/文件行号锚定/证据/建议）、超时语义、`unavailable` 状态集合、provider 身份记录、审查事实写入位置。**未冻结不得接入**。
- **谁写/谁读/谁执行**：主会话构造 packet；审查者按 packet 内声明的检查目标审查；主会话按 packet 声明的 schema 接回 findings。
- **优点**：**输入形态与 finding schema 一次冻结**，消除"同一材料不同审查者输出不可比"的问题——这正是 `I-C §2 C3`（FR-53/AC-54）的要求，且 `I-C §3.1` 明确"**一份合同覆盖两种对象会把 doc review 绑死在代码工具上**"，所以文档审查应选 packet；`R-D §11` 的 A1–A14 清单可直接作为 packet 的检查项来源。
- **代价与风险**：packet 的"应检查清单"会**框住审查者的视野**（只查清单内项）；packet 版本与材料版本需要同步（又一个漂移面）；`R-D §2.2` 记录行业里**没有任何工具提供正式的 "out of scope" 章节**——"哪些不审"必须由使用方自己显式定义（对应 A13）。
- **最适合的场景**：**本题的 spec + phase 合并审查**（`I-C §6` 第 3 条的直接建议）。
- **现实案例或证据**：`I-C §2 C3`（能力 C3 原文：输入形态 diff/worktree/packet 择一、finding schema、超时语义、unavailable 状态集合、provider 身份记录、审查事实写入位置、未冻结不得接入）、`I-C §3.1`、`R-D §11`（可判定清单 A1–A14，每条要求"判定规则/反例/证据"）、`R-D §2.2`（confidence 阈值与 out-of-scope 章节的共同缺口）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4B-05 清单、4B-08 反例库、4E-01/4E-03；与 4B-06 blind 天然配对（packet 决定"给什么"）；**需改造** 4B-02（代码审查也需 packet 化）。

#### 轴4B-04 问答式交互输入
- **做法**：审查者先读材料，再**提问**（问题回到建造者/主会话），得到回答后出 findings；交互轮次与问题数量有上限。
- **谁写/谁读/谁执行**：审查者提问；建造者/主会话回答；审查者据此判定。
- **优点**：把"材料没写明"从"猜测并误判"变成"**显式暴露缺口**"——与 `I-A` P-12（隐含假设未写明）和 `R-A §8 M5`（不确定性外显，五家框架独立采用）直接对应；`R-D §4.1` 的证据门槛要求 finding 必须映射到 spec/plan 的某个可追踪条目，问答可直接补齐这个映射。
- **代价与风险**：**交互轮次是成本项**——`R-D §2.3` 记录多轮循环会吞掉收益（CodeRabbit fix-push 后重审，非平凡 PR 平均要 **5–6 轮** review 循环，`pending/success` 状态单次审查中翻转 2–4 次）；`R-D §6.2` 第 2 条结论是"**瓶颈在审查轮次而非单条 finding**"，"报告一次、处置一次"比"每轮都重报"更经济；问答把审查从"一次性事实"变成"有状态的会话"，与本仓"审查事实写入固定位置"的模型冲突。
- **最适合的场景**：材料确实存在大量未决项、且希望把缺口显式化而非让审查者猜时。
- **现实案例或证据**：`R-D §2.3`（5–6 轮循环与状态翻转）、`R-D §1.3`（Amazon 会上静读 15–20 分钟后讨论、7 问清单、"truth-seeking vs. selling"）、`R-A §4`（AI-DLC 的 question 文件：A–E + 强制 X. Other + `[Answer]:`，**每批最多 4 个问题**，问题文件始终是唯一真相来源）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4B-03 packet（问题集由 packet 声明）、4E-03 领域清单（问题来自清单）；**互斥**于 4C-01 一次审查（问答天然多轮）；**需改造**以保留"审查事实"的单一记录。

---

#### 轴4B-05 逐条核对清单输入
- **做法**：输入形态是**清单本身**：审查者只需对每条清单项给"是/否/不适用 + 证据"，不自由发挥。清单来源可以是 IEEE 830 八属性、ISO 29148 单条/需求集特性、NASA Appendix C 十三组校验清单、Google 设计文档五章、Amazon Internal FAQ、或本仓四类质量核心。
- **谁写/谁读/谁执行**：清单由人/主会话维护；审查者逐条填；主会话按结果处置。
- **优点**：**可判定、可比较、可脚本化**；`R-D §11` 给出 A1–A14 的可判定版本（每条含判定规则 / 不合格反例 / 证据），并明确使用规则：**A1–A5 在 spec/plan 定稿前检查一次；A6–A11 在实现前检查一次；A12–A14 在每次"推进决定"时检查**，且"**任何一项不合格都只产生一条 finding（带证据），不产生阻断**"；`R-D §7.4` 指出三条可直接机器化（`shall/will/should` 语义检查、不可验证词表扫描、需求唯一编号 + 双向追踪矩阵）。
- **代价与风险**：清单会**漏掉清单外的一切**；`R-D §2.2` 记录行业工具的共性缺口是"没有正式 out-of-scope 章节"；`R-A §7.1` 记录 Böckeler 实测的批评是"即便有这么多文件、模板、提示、工作流、检查单，agent **最终仍然没有遵守所有指令**"；清单本身需要维护（`R-A §8.1` 发现 4：规格资产的治理是长期成本中心）。
- **最适合的场景**：需要跨任务可比、可统计、可脚本化的审查结果时；或作为 4B-03 packet 的核心载荷。
- **现实案例或证据**：`R-D §7.1`（IEEE 830-1998 八项质量属性：correct/unambiguous/complete/consistent/ranked/verifiable/modifiable/traceable）、`§7.2`（ISO/IEC/IEEE 29148：necessary/unambiguous/complete/singular/feasible/verifiable/correct/conforming + 需求集 complete/consistent/feasible/comprehensible）、`§7.3`（NASA Appendix C：shall/will/should 语义、定性值必须带容差、free of implementation、**不可验证词黑名单**、TBR 最小化机制、13 组校验）、`§11`（A1–A14 与使用规则）；`R-A §1`（Spec Kit 内置 16 条检查项 + 自定义清单 soft cap 40，条目 ≥80% 必须带 `[Spec §X.Y]`/`[Gap]`/`[Ambiguity]` 引用）`【实证】`（标准原文与官方模板）。
- **与其它选项的组合性**：**可叠加** 4B-03（清单作 packet 载荷）、4D-04 清单驱动、4E-03 领域清单、4E-04 写回清单；**需改造** 与 4B-06 blind（清单可能泄露预期的答案）。

#### 轴4B-06 只读产物、不读建造者上下文（blind review）
- **做法**：审查者**只允许读被审产物本身**，禁止读建造者的笔记、plan、decision-log、memory、会话历史、以及任何"意图说明"。`intake-decision-review` 的输入限制是现成范例：**只允许原始需求 + 客观事实 + 硬约束 + 非目标**；禁止含方案/排序/decision-log/spec/plan；四角度各一条 finding；只返回 `{findings:[]}`；缺料即 `unavailable`，**永远不是 pass**。
- **谁写/谁读/谁执行**：主会话裁剪输入；审查者独立判断；主会话处置。
- **优点**：**独立性最强**——`R-A §4` 记录 AI-DLC 的 reviewer sub-agent"**只读产物、不读建造者的 `memory.md` 或 plan**"，原文 `it forms independent judgment`；这是本仓宪法"质量裁决由独立来源独立上下文产出，禁止自审自判"的直接技术实现（`R-A §8.2` 把 AI-DLC 与 cc-sdd 当作该机制的外部对标证据）。
- **代价与风险**：**审查者可能因缺上下文而误判**（把有意设计决策当缺陷）——`R-D §6.1` 记录 agent 代码审查评论的 **>72% 驳回源于"有意设计决策"**（54,791 条 agent 评论 / 342 仓库）；`R-D §6.1` 另记录审查者熟悉该文件时有用密度 71–74%、**首次接触仅 32–37%**；`R-D §8` 记录 Pascarella et al.（CSCW 2018）"上下文缺失是审查者的主要障碍"。
- **最适合的场景**：方向级/需求级的"盲审"（防止被方案锚定）；或作为 red/blue 中的独立一翼。
- **现实案例或证据**：`R-A §3` 记录 `intake-decision-review` 的输入白名单与"缺料即 unavailable 永远不是 pass"；`R-A §4`/`§6.5`（AI-DLC 与 cc-sdd 的独立上下文 reviewer，cc-sdd 的 Reviewer 角色独立跑 `git diff`、grep TODO、跑测试套件、检查 task-boundary 合规）；`R-D §6.1`（驳回原因分布与熟悉度效应）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4A-06 红蓝（一翼 blind、一翼带上下文，形成两组互补 finding）；**互斥**于需要跨材料一致性检查的审查目标（`I-C §5 I3` 要求审查触达 CARD-02/03/04 三卡产物，blind 无法完成）——**这是本轴最关键的张力**。

#### 轴4B-07 双输入合并包（spec + phase 一起给）
- **做法**：输入**必须**同时包含 spec 与全部 phase 文档（或其纯文本路径引用），外加常驻紧凑索引，使审查者能重建整体；审查目标声明为"两类质量核心齐备"（原 spec 审查 + 原 plan 审查）。
- **谁写/谁读/谁执行**：主会话组装合并包；审查者做跨材料一致性判断；主会话处置。
- **优点**：**结构必然**——`I-C §5 I2` 明确"phase 文档只写差异 → 单独审一份 phase 文档无法判断整体质量核心 → 必须与 spec 一起审"，这正是 ① 被定义为"一次同时覆盖 spec 与 phase 文件"的结构性原因；`I-C §5 I6` 进一步指出：原 plan.md/tasks.md 双写删除后，"依赖正确/并行声明/写集"**此后只存在于 phase 文档中**，因此 ① 必须能只靠"phase 文档 + 紧凑索引"定位这些内容，**不能依赖已删的 plan.md/tasks.md**（"这是把 ① 并入 card-02 时最容易漏的一条"）。
- **代价与风险**：合并包体量大（spec 760 行 + 每 phase），容易触发上下文退化（`R-B §1.3` lost-in-the-middle、`R-A §7.3` BMAD 的 40 页输入上限**超限静默丢信息**）；`I-C §5 I3` 指出四类质量核心分属三张卡，**一次审查要同时触达是能力要求而非输入要求**——合并输入不等于合并能力。
- **最适合的场景**：本题 ① 的唯一合法形态。
- **现实案例或证据**：`I-C §2 C2`（FR-56/AC-57 原文）、`I-C §3.2` 第 1–2 条（"新增的①"与"其余不变的点"是官方切分线）、`I-C §5 I2/I3/I6`、`I-C §6` 第 1 条（CARD-02 卡面补 ① 的 FR/AC 原文）、`I-B §4 K6` 与 `I-B §7` 第 2 条（一次合并审查覆盖 spec + phase，两类质量核心合一）`【实证】`（本仓官方决议）。
- **与其它选项的组合性**：**可叠加** 4B-03 packet（声明审查目标）、4B-06 的部分 blind（对 phase 差异 blind、对 spec 可见）；与 4B-01 **需改造**（全文输入需去噪）。

#### 轴4B-08 可执行证据包输入（命令 + exit + 输出的原始采集）
- **做法**：审查者除了材料，还拿到**机器采集的原始证据**：真实命令、exit code、文件路径+行号、diff/commit hash、日志片段、失败事实；审查者据此判定"材料声称的是否真发生"。
- **谁写/谁读/谁执行**：机器采集；审查者核对；主会话处置。
- **优点**：这是 `R-D §4.1` 的 **L1 Observation 层**定义（"机器可复现的原始证据"，缺失时状态为 `unavailable`）；`R-D §11 A14` 要求"未验证的部分必须标为 `partial`/`unverified`，不得记为通过"，其依据是 Spec Kit 原文 **"Missing verification is not a successful fix."**；直接对治 `I-A` P-11（哈希 pin 与内容不一致**且无人失败**）与 P-07（0 条 AC 含可执行 oracle）。
- **代价与风险**：**证据采集本身可能造假或被误读**——`I-A` P-11 就是"pin 的哈希与实际不符却没有任何登记"；`R-D §4.3` 记录工程领域"quality gate 阻塞成本"的一手量化数据**未能找到**（只有 DORA 的定性负面结论）；证据包会显著增大审查输入。
- **最适合的场景**：验收可执行性审查（AC 是否真能跑）、以及"材料声称 vs 实际发生"的一致性检查。
- **现实案例或证据**：`R-D §4.1`（三层记录定义与 evidence threshold 的可判定形式）、`R-D §11 A14`、`R-D §7.4`（可验证性不等于"必须有测试"，NASA 明确可通过 test/demonstrate/inspect/analyze 四种方式之一满足）、本仓 `I-B §5.1`"真实命令的 exit/output 采集、原子写入、失败与缺口事实、历史只读——保留" `【实证】`。
- **与其它选项的组合性**：**可叠加** 4B-03 packet、4D-06 自动化预筛；**需改造** 与 4B-06 blind（证据可能泄露意图）。

### 4C 审查时机与门槛

#### 轴4C-01 一次合并审查（单点）
- **做法**：在 build-plan 完成后、build-code 开工前**只做一次**审查，同时覆盖 spec 与 phase 文件；同 scope 成功后**不复审**；发现照单修复；无 severity 门槛与复审循环。
- **谁写/谁读/谁执行**：一次派发；主会话逐条处置；人读结论。
- **优点**：**次数最少、成本最低、无状态漂移**；`I-C §2 C7` 明确"单次成功不复审：同 scope 成功后不复审；发现照单修复；**无 severity 门槛与复审循环**"；`R-D §6.2` 第 2 条结论支持（瓶颈在轮次，报告一次、处置一次更经济）；`R-D §2.4 N3`（"报告一次、只更新处置"，避免 5–6 轮循环与状态翻转）。
- **代价与风险**：**单点审查意味着单点失败**——`I-C §4.7` 记录首轮方向/detail 审查双双 `unavailable`（两角色 `semantic_result=unavailable`、`result_ref=null`、`coverage=incomplete`），若这是唯一的合并审查点，则材料在无审查的情况下进入 build-code；`R-D §4.2` 的"留痕放行"三态（`successful`/`skipped`/**`neutral`**）是对此的既有解，`R-D §2.4 N6` 另警告 **GitHub 把 `neutral` 渲染成灰色方块、人眼会读成"通过"**（一次"明显失败的 PR 差点因此被合并"）→ 若采用中性态**必须同时改变其可见性**。
- **最适合的场景**：本题 ① 的定义形态。
- **现实案例或证据**：`I-C §2 C7`、`I-C §2 C2`、`I-B §4 K6`（OI-014）、`R-D §2.4 N3/N6`、`R-D §6.2` `【实证】`。
- **与其它选项的组合性**：**可叠加** 4A-06/4C-06；**互斥**于 4C-02/4C-03/4C-04；**需改造**以容忍单点 `unavailable`（需明确 fallback，见 `I-C §2 C6`）。

---

#### 轴4C-02 分批审查（spec 先、phase 后）
- **做法**：拆成两次：先审 spec（需求翻译完整性 / 验收可执行 / 架构合理），spec 定稿后再审 phase 文档（依赖正确 / 并行声明 / 写集）；两次各自处置。
- **谁写/谁读/谁执行**：两次派发；主会话分别处置。
- **优点**：**每一步的输入都更小、审查者注意力更集中**；上游错误在下游生成前被拦住，避免"phase 依赖了错误 spec"的复合返工；与 `R-A §8 M9`（逐任务停顿）同族。
- **代价与风险**：**违反 ① 的定义**（`I-C §2 C2` 明确"不拆两次、不漏核心"；`I-C §3.2` 第 1 条指出 OI-014 的落地点就是"一次审查同时覆盖 spec 和 phase 文件"）；两次审查之间材料会变，第二次审查的基准不确定；**成本翻倍**（`R-D §6.1` 的两个 Claude 审查组分别 +0.0pp/+72% 成本，说明重复审查的边际收益可能为零）。
- **最适合的场景**：spec 阶段与 phase 阶段由**不同人/不同模型**负责，需要各自对自己的产物负责时；或 spec 体量大到无法与 phase 一起进上下文时。
- **现实案例或证据**：`I-C §2 C2` 与 `I-C §3.2` 第 1 条给出**反向官方立场**；`R-A §1` 记录 Spec Kit 明确要求"**Invoke each `/speckit-*` skill one at a time, and review the result before continuing**"（每步产物先被审阅再继续）`【实证】`（两种立场都有官方原文，**本轴不调和**）。
- **与其它选项的组合性**：**互斥**于 4C-01；**可叠加** 4B-01/4B-03；**需改造**才能满足 ① 的 AC。

---

#### 轴4C-03 增量审查（每次改动重审变更部分）
- **做法**：材料每次修订后只重审**变更的部分**，维持会话上下文；`R-D §2.1` 记录 CodeRabbit 的形态即"新 PR full review + 后续 commit incremental review"。
- **谁写/谁读/谁执行**：增量派发；主会话处置。
- **优点**：**审查预算与改动量成正比**；对"发现照单修复后重审"的循环最经济；`R-D §2.1` 记录增量模式"Maintains conversation context"。
- **代价与风险**：`I-C §2 C7` 明确"单次成功不复审；**无 severity 门槛与复审循环**"——增量审查与之直接冲突；`R-D §2.3` 记录增量审查导致状态翻转与轮次膨胀（5–6 轮）；`R-A §1` 记录 Spec Kit `converge` 是 **append-only 且无缺口时 tasks.md 字节级不变**，增量审查需与之配合才能避免无意义派发。
- **最适合的场景**：材料会经历多轮修订、且每轮改动局部化时。
- **现实案例或证据**：`R-D §2.1`（CodeRabbit 粒度）、`R-D §2.3`（5–6 轮循环实测）、`I-C §2 C7`（反向官方立场）`【实证】`。
- **与其它选项的组合性**：**互斥**于 4C-01；**可叠加** 4B-02 diff；**需改造**以显式定义"什么算一次成功"。

---

#### 轴4C-04 每 phase 一次审查
- **做法**：每个 phase 完成后审一次（外加全 phase 集成一次、verify-code 终末一次），即本仓现行 build-code 侧节奏（`I-C §2 C1` 的 ②③④）。
- **谁写/谁读/谁执行**：runner 按 `phase_id` 派生 `review_scope=phase`；集成时派生 `integration` + `subject_kind=worktree`；主会话处置。
- **优点**：**审查时机与执行粒度对齐**——`R-A §8 M9`（逐任务停顿：Kiro "VERY IMPORTANT 只 execute one task at a time. Once you finish a task, stop."）与 cc-sdd 的 "**1 task per iteration** — Each iteration processes a single task. This keeps context hygiene across long autonomous runs, makes /kiro-impl safe to re-run after interruption, and bounds the scope of review and debug passes"；phase 级审查的输入天然小（`I-C §4.5` 的 worktree/commit-tree 范围）。
- **代价与风险**：`I-C §2 C2` 明确本轴的对象是**文档侧**的 ①（spec + phase 一次），而 ②③④ 是**代码侧**、**保持不变**且归 CARD-05；把 ① 也做成"每 phase 一次"会与"一次合并审查"定义冲突；phase 数量多时审查次数线性增长。
- **最适合的场景**：**代码审查**（build-code/verify-code）——`I-C §2 C1` 明确"次数与位置不变"。
- **现实案例或证据**：`I-C §2 C1/C9`、`I-C §4.5`（build-code 合同原文）、`I-C §3.3`（AC-23/AC-26 的子句拆分：① 归 card-02，②③④ 留 CARD-05）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4B-02 diff、4C-05 门禁；**互斥**于 4C-01（文档侧只能选一个）。

---

#### 轴4C-05 门禁式（审查通过才允许推进）
- **做法**：审查结论作为推进的硬前置；未通过则 build-code 不得开工。
- **谁写/谁读/谁执行**：审查者/门控脚本判定；主会话被阻断。
- **优点**：**防的是"带缺陷材料进入实现"**，对不可逆或高返工成本的阶段有效；`I-C §2 C3` 的"未冻结不得接入"是这一思路的局部形态（合同冻结而非质量门）。
- **代价与风险**：`R-D §4.3` 给出最强的反向证据：**DORA 明确"没有证据支持更正式的外部评审带来更低的 change failure rate"**，且"**用更多流程回应稳定性问题会让事情变得更糟**"，change failure rate 是**滞后指标**，应做事后度量而非事前门；`R-D §10` 把"有 quality gate 才能保证质量""加更多审批/流程能提升稳定性"列为**未找到支持性一手证据/被反向证伪**；`R-D §4.3` 还诚实地记录"工程领域 quality gate 阻塞成本的一手量化数据**未能找到**"——引用任何具体百分比都属未证实；本仓宪法明确"不引入会阻断推进的质量门"（`CLAUDE.md` 硬规则）。
- **最适合的场景**：本仓当前治理边界**不适用**；理论上仅适用于"不可逆动作 ∧ 高错误成本类别 ∧ 证据缺失"三条件同时成立的窄集合（`R-D §4.4`）。
- **现实案例或证据**：`R-D §4.3`（DORA 反证）、`R-D §4.4`（唯一值得保留的窄阻断集）、`R-D §10`（被证伪清单）、`I-B` D3/D4（stage completion 通用认证与固定顺序锁定被判定删除）`【实证】`（**强反向证据**）。
- **与其它选项的组合性**：**互斥**于 4C-06 纯 advisory；**需改造**为"窄阻断集"才能与 4C-06 共存。

---

#### 轴4C-06 纯 advisory（不阻断，只出 finding）
- **做法**：审查可以推进，但**不能把"未验证"记录为"通过"**；缺失只约束"能否宣称完成"，不约束"能否继续"；审查结论是事实而非许可证。
- **谁写/谁读/谁执行**：审查者出 finding；主会话决定是否修复；缺失事实保持 `unavailable`/`incomplete`/`unknown`。
- **优点**：**同时满足"有证据门槛"与"不阻断推进"**——`R-D §9 建议 A` 的核心句是"**缺失只约束'能否宣称完成'，不约束'能否继续'**"，并与 Spec Kit 的 "Missing verification is not a successful fix" 和 NASA 的 TBR 机制同构；`R-D §2.2` 核对 5 个主流 AI 审查工具**全部默认 advisory，阻断必须显式开启**（CodeRabbit `request_changes_workflow` 默认 `false`；Cursor Bugbot 官方原话 "requiring the status alone does not block merges"；Copilot 官方把 "block merge until all comments addressed" 列为**不支持**）；本仓宪法同向（"记录事实而非阻断"、"质量缺失保持 `unknown`/`unavailable`/`incomplete`，不能伪造通过"）。
- **代价与风险**：**"不阻断"的表达方式本身会决定它是否被忽略**——`R-D §2.4 N6` 记录中性态被人眼读成"通过"；`R-D §6.1` 记录 AI 审查评论有 **60–70% 从未被处理**，解决率整体落在 **20–75%** 区间（Google AutoCommenter 有用率 54–60%、Meta ActionableToApplied 仅 **19.7%**、Atlassian 38.70%、ByteDance 75.0% 精度）；`R-D §6.2` 第 3 条因此要求"未解决的 finding 是默认状态，不是异常"——流程必须让"未解决"成为**可记录、可查询、可接受**的状态。
- **最适合的场景**：本仓现状与治理边界的默认选择。
- **现实案例或证据**：`R-D §2.2`（五工具默认 advisory 对照表）、`R-D §4.2`（五种既有不阻断机制：required check 三态通过 / Conventional Comments decoration / Google `Nit:` 前缀 / SRE error budget 与 PRR / risk acceptance 形式化）、`R-D §9 建议 B`、`I-C §4.2`（wh-review 的 `available` 只表示至少一个异源 reviewer 返回合法 findings；**空 findings 是建议，不是完成或批准**；`unavailable` 绝不改写成 pass）`【实证】`。
- **与其它选项的组合性**：**可叠加** 全部（它是门槛策略而非审查方法）；**互斥**于 4C-05；**需改造**以避免退化为"看不见"（需 4E-07 降噪留痕）。

---

#### 轴4C-07 风险触发式（只在风险信号出现时审）
- **做法**：不按固定节奏审查，而是由风险信号触发：改动跨前后端/API/DB/认证/部署/并发、或边界无法证明更窄、或涉及不可逆动作、或触及"永不抑制清单"类别。
- **谁写/谁读/谁执行**：判定者（脚本或主会话）按 `changed_files`/`phase_count`/`test_command` 等客观输入判类；触发则派发审查。
- **优点**：**审查预算按"错误成本"分配**——`R-D §6.2` 第 1 条（CodeRabbit 原文：*review depth should follow the cost of error*）；本仓已有同族的 `test-routing-advisor`（按真实改动判 `simple`/`feature`/`fullstack`，**风险不明取更高级**，完全无法判定用 `fullstack`）；`R-F §7.1` 的"风险不对称"行：**失败不可观测或昂贵的步骤写死，失败可迅速观测并由下一轮修复的步骤放开**。
- **代价与风险**：**风险判定本身会错**，低判会漏审；`R-D §2.2` 记录行业工具**没有 confidence 阈值配置**，替代物只有 severity 分层/strictness 档位/学习抑制；`R-D §6.1` 记录审查预算与错误成本的关系是经验判断而非可精算。
- **最适合的场景**：材料多、风险分布极不均匀、且有能力做客观分档时。
- **现实案例或证据**：`I-B §2.4` 第 5 条（test-routing-advisor：独立读 `changed_files`/`phase_count`/`test_command`，三档，风险不明取更高，`phase_count > 1` 不是单独升级理由）；`R-D §6.2`、`R-F §7.1`、`R-D §2.2`（永不抑制类别可作为强制触发集）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4D-02 抽样、4D-03 风险加权、4E-06 永不抑制清单；**互斥**于 4C-01 固定一次（风险触发不保证"一次"）。

---

#### 轴4C-08 事后触发式（error budget / 复盘触发）
- **做法**：审查不作为事前门，而由**事后度量**触发：当质量预算被超支（例如某段时间的返工/逃逸缺陷超阈值）才暂停并复盘；明示"这不是惩罚"，且 P0 与安全修复仍可放行。
- **谁写/谁读/谁执行**：度量由机器采集；触发后由人主持复盘并产出改进优先计划；**产出不是通过/否决门**。
- **优点**：`R-D §4.2` 记录 Google SRE 的 error budget policy 是**事后触发**且明示"这不是惩罚"、P0 与安全修复仍可放行；Production Readiness Review（PRR）的产出是"**与开发团队协商出的改进优先计划**，不是通过/否决门"；这直接对应 `R-D §4.3` 对"滞后指标应做事后度量而非事前门"的要求。
- **代价与风险**：**事后发现意味着损害已发生**；需要可信的度量口径（`R-D §6.1` 显示"60–70% 评论未解决""7–35% 评论被丢弃"这类基线本身噪声很大）；本仓治理边界禁止把历史/度量当推进许可证，度量只能作为"事实"。
- **最适合的场景**：长期存续的流程改进，而非单任务质量裁决。
- **现实案例或证据**：`R-D §4.2` 第 4 条（SRE error budget + PRR）、`R-D §4.3`（DORA：change fail rate 是滞后指标）、`R-D §6.1`（公开数字基线）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4E-02 校准回路、4E-05 审查者也被审；**互斥**于 4C-05 门禁式。

### 4D 审查深度与效率的平衡手段

#### 轴4D-01 分层审查（先结构后细节）
- **做法**：第一遍只查**结构与完整性**（章节是否齐、ID 是否有孤儿、必填字段是否非空、锚点是否可解析、省略是否有标记），第二遍再查**语义质量**（需求翻译完整性、验收可执行、架构合理、依赖/并行/写集）。两遍可由不同能力的主体执行。
- **谁写/谁读/谁执行**：第一遍可脚本化或廉价模型；第二遍强模型；主会话合成。
- **优点**：**先用低成本方式排除"结构性缺陷"**，避免强模型把预算花在格式上；`R-E §5.1` 把"模板必填项"列为成本极低、可脚本校验的机制；`R-A §8 M1/M2`（结构强制 + 格式机器校验被五家/四家独立采用）；`R-E §4.3` 的三层组织规则（L0 ≤10 行 / L1 每单元 ≤15 行 / L2 无上限）天然定义了"先看层级，再看单元"的顺序。
- **代价与风险**：结构合格**不等于**语义合格——`I-A §4.3` 判读①明确"`build` 占比高 ≠ 对实现者有用：spec.md 的 71.4% 主要来自 §11，而其中 **0 条含可执行 oracle**；若把可执行性作为真门槛，有效 build 占比降到约 30%"；`R-E §5.1` 也指出质量属性清单防的是"字段写了但不合格"。
- **最适合的场景**：材料体量大、且结构缺陷占比高（本仓现状：`I-A` P-08 字段漂移、P-10 锚点腐化、P-13 编号不一致、P-16 空白模板 29.9%）。
- **现实案例或证据**：`R-E §5.1`（五类机制的覆盖类型与成本）、`R-E §5.5`（评审清单最小集 8 条，可 5 分钟过一遍）、`R-E §9.5`（七项可脚本化检查：句长/段长/标题层级/不可验证词/R-ID 孤儿/重复事实/决策块行数）、`R-A §8 M2` `【实证】`。
- **与其它选项的组合性**：**可叠加** 4D-06 自动化预筛（第一遍即预筛）、4D-04 清单驱动；**需改造** 与 4B-06 blind（分层可能泄露）。

---

#### 轴4D-02 抽样审查
- **做法**：不逐条审，按比例抽取条目审（例如 20%–33% 的需求/任务/AC），抽中的全审。
- **谁写/谁读/谁执行**：抽样者（人或脚本）；审查者审抽中项；主会话处置。
- **优点**：`R-D §6.1` 记录 SmartBear/Cisco 的实测：**抽查 20%–33% 的代码即可降低缺陷密度，且时间开销极小**（"Ego Effect"）；抽查比全审更符合人的注意力上限（单次 ≤60 分钟、<500 LOC/小时）。
- **代价与风险**：**未被抽中的部分没有任何证据**，因此必须显式声明抽样范围与置信度限制（`R-D §2.4 N1` 的范围界定 + `R-D §11 A13` 明确"本次不审什么"）；抽样对"跨条目一致性"类缺陷几乎无效（`I-A` P-12/P-13 都是跨条目问题）；`R-D §2.2` 记录行业里**没有工具提供正式 out-of-scope 章节**，抽样范围必须自己显式定义。
- **最适合的场景**：条目高度同质（如大量同类 AC）、且已有一遍结构审查做底时。
- **现实案例或证据**：`R-D §6.1`（20–33% 抽查实测）、`R-D §6.1`（审查速度与时长上限）、`R-D §11 A13` `【实证】`。
- **与其它选项的组合性**：**可叠加** 4D-03 风险加权（高风险全审 + 低风险抽查）、4A-08 人审（人只审抽中的）；**互斥**于"每条 AC 都必须有 oracle"那类全覆盖要求（`I-B` K3）。

---

#### 轴4D-03 风险加权审查（高风险全审、低风险抽查）
- **做法**：先按客观维度给每个条目/材料定风险级（是否不可逆、是否触及安全/隐私/客户数据/公共接口、失败是否可观测、成本是否昂贵、是否跨组件），高风险条目 100% 审、低风险按比例抽查；风险不明取更高一级。
- **谁写/谁读/谁执行**：分级由脚本/主会话做；审查者按级分配深度。
- **优点**：**把有限审查预算压到错误成本最高的地方**——`R-D §6.2` 第 1 条与 `R-D §9 建议 D` 的原话；`R-D §4.4` 的三条件窄集合（不可逆 ∧ 高错误成本类别 ∧ 证据缺失）为"最高风险"给了可判定定义；`R-F §7.1` 的"风险不对称"与"可逆性"两行为分级给了直接判据（不可逆/高影响动作必须写低不确定性阈值；可逆只读可重试的写高阈值）。
- **代价与风险**：分级标准本身是主观的（`R-D §5.3` 要求"证据强度 ≥ 严重性"，并指出实测中**高严重性 tier 误报率可高于 critical**——某工具 high 级误报 15%、critical 级 0%）；`R-D §2.2` 记录**没有工具提供 confidence 阈值配置**；分级错判会导致系统性漏审。
- **最适合的场景**：材料内部风险差异大（本仓：不可逆 Git 授权、迁移、公共接口、并发）。
- **现实案例或证据**：`R-D §4.4`（窄阻断集三条件）、`R-D §5.2`（分级→处置矩阵；Greptile 官方措辞 "P0 Must fix before merging / P1 Should fix / P2 Consider fixing" 可直接借用）、`R-D §5.3`（证据强度 ≥ 严重性；误报反馈回路）、`R-F §7.1`（可逆性/风险不对称判据）、`I-B §2.4` 第 5 条（风险不明取更高级）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4D-02 抽样、4C-07 风险触发、4E-02 校准回路；**需改造**以统一 severity 词汇（`R-D §2.3` 警告：**不要跨体系比较 severity 词汇**）。

---

#### 轴4D-04 清单驱动审查
- **做法**：审查深度由清单长度决定——审查者只回答清单问题，不自由发挥；清单可分层（结构层/语义层/风险层），每层对应不同时机。
- **谁写/谁读/谁执行**：清单维护者；审查者逐条答；主会话处置。
- **优点**：**可判定、可统计、可比较、可自动化**；`R-D §11` 明确使用规则（A1–A5 定稿前 / A6–A11 实现前 / A12–A14 每次推进决定）并规定"任何一项不合格都只产生一条 finding（带证据），不产生阻断"；`R-D §7.4` 给出三条可直接机器化的检查。
- **代价与风险**：**清单固化了审查者的盲区**；清单维护成本（`R-A §8.1` 发现 4：治理成本转移到文档自身）；`R-A §7.1` 的 Böckeler 实测批评：检查单再多，agent 仍不遵守全部指令；清单条目过多会退化为走过场（`R-D §6.1` 记录 61% 的评审零缺陷、94% 的评审 <20 defects/hour）。
- **最适合的场景**：需要跨任务可比的一致性审查；或作为 4D-01 第二遍的载荷。
- **现实案例或证据**：`R-D §7.1/§7.2/§7.3`（IEEE 830 / ISO 29148 / NASA Appendix C 三套权威清单）、`R-D §11`（A1–A14 可判定清单与使用规则）、`R-A §1`（Spec Kit 16 条内置检查项 + 自定义清单 soft cap 40 + 条目 ≥80% 必须带引用）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4B-05 清单输入、4D-01 分层、4E-03 领域清单、4E-04 写回清单；**需改造** 与 4B-06 blind（清单泄露预期）。

---

#### 轴4D-05 交叉验证（多审查者互相核对结论）
- **做法**：多个审查者的 findings 互相核对：只有被多人命中的才算高置信；单人命中的进入"记录但不要求响应"队列；冲突的 finding 进入裁决（可交给 4A-07 辩论或 4A-08 人）。
- **谁写/谁读/谁执行**：多审查者；核对者（脚本或人）；主会话处置。
- **优点**：**把"命中数"当作朴素的置信度信号**；`R-D §4.1` 的 evidence threshold 定义（finding 必须同时满足 ① 可复现的最小命令或精确代码位置 ② 映射到 spec/plan 可追踪条目 ③ 严重性判定依据，三者缺一进入"记录但不要求响应"队列）可以作为筛选规则；`R-D §5.3` 要求"高严重性 tier 必须有更高的证据门槛"（`blocker`/`critical` 必须附可复现命令或失败用例，否则**自动降级**为 `major` 或 `question`）。
- **代价与风险**：**`R-D §2.3` 的实测直接削弱朴素交叉验证**——617 个坐标中 93.4% 只被一个 reviewer 发现、**四个同时命中 0 次**，即"多人命中"极罕见，用它当置信门槛会把绝大多数 finding 降级；`R-D §3.3` 记录错误高度相关（双错时 60% 一致），因此"多人同意"也可能是共同错误（确认偏误回路）。
- **最适合的场景**：作为**冲突裁决**规则而非**置信门槛**规则。
- **现实案例或证据**：`R-D §2.3`（重叠率实测）、`R-D §3.3`（确认偏误回路警示）、`R-D §4.1`（evidence threshold 三条件）、`R-D §5.3`（自动降级规则）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4A-02/4A-06/4A-07；**需改造**——必须避免把低重叠当作"不可信"。

---

#### 轴4D-06 自动化预筛（确定性检查先跑）
- **做法**：在模型审查之前先跑确定性检查：格式/lint、链接与锚点可解析、必填字段非空、ID 孤儿（R-ID ↔ phase 双向）、不可验证词命中、句长/段长/标题层级上限、重复事实、决策块行数上限。预筛结果作为**记录**（不是门）附在审查输入里。
- **谁写/谁读/谁执行**：脚本跑；审查者读预筛结果并跳过已确认项；主会话处置。
- **优点**：`R-A §8 M2`（格式机器校验被 Tessl/AI-DLC/Spec Kit/OpenAI 四家独立实现）；`R-E §9.5` 列出**七项可脚本化检查**，并明确"这些可以写成脚本（按标点切句、统计字数、统计标题层级、检查孤立标题），比可读性公式更可靠，且不依赖语言假设"；`R-E §5.1` 把它列为成本最低的一类机制；本仓宪法同向（"物理事实机器采集、浮现到边界，但不卡死推进"）。
- **代价与风险**：**脚本只能查形态不能查语义**；`I-A §4.3` 判读①说明形态合格不代表有用；脚本规则本身会误伤（`I-A §6.4 C4-D` 提到"可能误伤合理的短描述，需要白名单"）；新增检查需符合本仓"不新增控制面"约束（`I-A §6.5 C5-B` 建议"挂在既有 verify 路径上而不是新增 gate"）。
- **最适合的场景**：任何规模的材料审查的第一遍（本仓现状的 P-08/P-10/P-13/P-16 都可被脚本抓到）。
- **现实案例或证据**：`R-E §9.5`（七项可脚本化检查，全部标注为"事实，记录"，原文明确"与项目宪法一致——这些是事实证据，不是推进许可证"）、`R-A §8 M2`、`R-E §5.1` `【实证】`。
- **与其它选项的组合性**：**可叠加** 4D-01 分层（预筛即第一层）、4B-08 证据包；**需改造** 4E-04 写回（把误报率反馈给规则）。

#### 轴4D-07 审查预算硬上限
- **做法**：给单次审查设硬上限（例如以材料体量或时长计——对标 Google 的约 400 LOC / 60 分钟），超阈值改为抽样或分层审查。
- **谁写/谁读/谁执行**：主会话/runner 计量；超限改变审查策略。
- **优点**：`R-D §6.1` 与 `R-D §9 建议 D` 的原话；`R-D §6.2` 第 1 条要求"审查深度应跟随错误成本"且超阈值应"拆分或抽样"；`R-A §7.3` 的关键观察支持"控制**喂进去多少**比控制写出来多少更重要"（BMAD 约 40 页/数万 token 是实际上限，**超过会静默丢失**）。
- **代价与风险**：**上限会掩盖"材料本身就过大"这一根因**——本仓 `I-A` P-01 的极端案例是单文件 13,195 行、其中一节 11,815 行零动作清单；若只设审查预算而不设材料预算，审查会被迫抽样而缺陷仍在；`R-A §7.3` 明确**没有任何框架给"spec.md 不能超过 N 行"这类上限**（只有 AI-DLC 的 1–2 页档位与 cc-sdd 的 1000 行警告作为**复杂度信号**）。
- **最适合的场景**：审查侧的成本控制；与材料侧的体量上限（`I-A §6.1` C1-A/C1-C）配套才有意义。
- **现实案例或证据**：`R-D §6.1`（200–400 LOC / 60–90 分钟、<500 LOC/h、≤60 分钟）、`R-D §9 建议 D`、`R-A §7.3`（四种量化约定形态与"无 spec 行数上限"的观察）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4D-02/4D-03；**需改造** 与 `I-A §6.1` 的材料预算配套。

### 4E 审查能力提升手段

#### 轴4E-01 注入反例库（"什么算不合格"）
- **做法**：审查输入里附一份**反例清单**：本类材料的典型不合格写法、改写对照、黑名单词表。审查者被要求逐条确认"材料里没有出现这些形态"。
- **谁写/谁读/谁执行**：反例库由历史 finding 或公开标准沉淀；审查者用它做否定式检查；主会话处置。
- **优点**：`R-C §7.3` 提供可直接当 review 用的**改写对照表**（模糊验收 → 可判定写法的成对样本）；`R-D §7.3` 的 NASA **不可验证词黑名单**（flexible/easy/sufficient/safe/adequate/user-friendly/usable/when required/appropriate/fast/robust/quickly/easily/clearly + 其他 `-ly`/`-ize` 词）是现成的可机检反例集；`R-E §7` 的 22 条反模式（症状 → 检测 → 修法）与 ADR 专属 11 反模式（Fairy Tale / Free Lunch / Dummy Alternative / Sales Pitch / Mega-ADR / Magic Tricks …）是**按症状组织的检测库**；`I-A §5` 的 G-01…G-13 则是**正例库**（13 条应保留的写法）。
- **代价与风险**：**反例库会诱导"只找已知错误"**，对新型缺陷无效；反例库本身会过期（`R-F §8.2` 的规格债机制同样适用于审查规则）；否定式引导有反效果（`R-E §6.5` 明确 **negation 反模式**："用禁令引导会把被禁行为拉进上下文（不要想大象），尽量正面表述目标行为"）。
- **最适合的场景**：反复出现同类缺陷的任务族（本仓 P-07/P-08/P-09 就是反复出现的）。
- **现实案例或证据**：`R-C §7.3`（改写对照表）、`R-D §7.3`（NASA 不可验证词清单）、`R-E §7`（22 条 + 11 条反模式，症状→检测→修法）、`R-E §6.5`（negation 反模式警示）、`I-A §5`（正例 13 条）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4B-03 packet、4D-04 清单、4E-03 领域清单、4E-04 写回；**需改造**以正面表述为主（否则触发 negation 反模式）。

---

#### 轴4E-02 历史 finding 库 + 误报率校准回路
- **做法**：维护"历次审查的 finding + 处置结果"库；审查者看到同类历史 finding 及其是否被判定为有效；同时按 severity 统计 rejected/false-positive 率并定期重校准分级标准。
- **谁写/谁读/谁执行**：机器记录；审查者读历史；人做校准。
- **优点**：**把"被证伪的意见"沉淀为不再重复的规则**——`R-D §9 建议 C` 明确"**没有这个回路，分级就只是随机数**"；两家官方产品已实现同族机制：CodeRabbit 的 **Learnings**（从团队反馈中学习，即"把被驳回的意见变成不再重复的规则"）、Greptile 的 **Custom Standards / rules.md**（把团队既有事实标准沉淀为可复用规则）、Graphite 的 **Rules & exclusions + downvote rate**。
- **代价与风险**：**学习回路会过度抑制真实缺陷**——`R-D §2.2` 记录 Greptile 的实现细节"同类型被忽略 3+ 次则抑制"，这正是需要 4E-06 永不抑制清单兜底的原因；`R-D §5.3` 提醒**不要跨体系比较 severity 词汇**；本仓已有"reports immutable、provenance 不可覆盖"的约束，历史库不能用摘要覆盖来源。
- **最适合的场景**：长期运行的流程，需要把误报率压下来时。
- **现实案例或证据**：`R-D §2.1`（CodeRabbit Learnings）、`R-D §2.2`（Greptile learning system 与官方 suppression 规则、Graphite Rules & downvote rate、Copilot 👎 反馈）、`R-D §5.3`（误报反馈回路与"高严重性必须绑定更强证据"）、`R-D §9 建议 C` `【实证】`（官方产品机制 + 实测误报率）。
- **与其它选项的组合性**：**可叠加** 4E-01/4E-04/4E-06；**需改造**以满足本仓 provenance 与"不新增控制面"约束。

---

#### 轴4E-03 注入领域清单（本类文档的专用检查表）
- **做法**：按材料类型注入专用清单：对 spec 注入"需求可测试性/无歧义/可追溯"清单；对 phase 注入"边界/依赖/并行/写集/STOP/回滚"清单；对 decision-log 注入"决策完整性/被否选项/后果/置信度"清单；对本文档体系注入四类质量核心清单（需求翻译完整性、验收可执行、架构合理、依赖正确/并行声明/写集）。
- **谁写/谁读/谁执行**：清单由对应该材料的 owner 维护；审查者按类型取用。
- **优点**：**审查目标与被审对象的类型对齐**，避免通用清单的空转；`R-D §11` 的清单本身即"综合 Google design doc 结构 + Google code review 清单 + Amazon PR/FAQ 7 问与 Internal FAQ + Spec Kit 阶段产物 + IEEE 830 / ISO 29148 / NASA Appendix C"压缩而成；`I-C §5 I3` 的四类质量核心表就是本仓的领域清单原型（并注明各自落在哪份产物、作者是谁）。
- **代价与风险**：多份清单会**碎片化**（`R-E §1.2` 的 Scattering 反模式：一个意思被切碎散落多处，反面是 Co-location）；清单之间条目重叠会造成重复审查；`I-C §3.4` 的原则是"两卡各写一次**指向同一权威句**，而不是复制正文"。
- **最适合的场景**：三类文档 + 审查各自有不同质量核心时（正是本仓现状）。
- **现实案例或证据**：`I-C §5 I3`（四类质量核心的四方归属表）、`R-D §11`（A1–A14 与时机分组）、`R-D §7.1/§7.2/§7.3`、`R-E §9.2/§9.3/§9.4`（decision-log / spec / phase 各自专用规则）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4D-04、4E-01；**需改造**以避免碎片化（用 4B-03 packet 统一引用权威句，不复制正文）。

---

#### 轴4E-04 每次审查把新发现写回清单（学习型清单）
- **做法**：每次审查结束后，把**新出现的缺陷模式**提炼成清单条目（或反例），写回该材料类型的清单；下次审查自动带上新条目。
- **谁写/谁读/谁执行**：主会话/审查者写回；清单 owner 审核；后续审查消费。
- **优点**：**清单随实际失败增长**，而不是一次写死；`R-A §6.5` 记录 cc-sdd 的 `## Implementation Notes` 跨任务学习传递机制（"当某任务暴露跨领域洞察时，finding 记录在 tasks.md 的 Implementation Notes 下并注入后续 implementer 提示"）；`R-A §6.3` 记录 agent-os 把 `Refine` 当作循环的一环。
- **代价与风险**：**清单会无限膨胀并腐化**——Tessl 承认 `static instructions quietly go stale`、OpenAI 承认单文件指导 `rots instantly`（`R-A §8.1` 发现 4）；`R-E §7` 反模式 22 **Sediment（沉积）**："历史层叠加，无人敢删 → 按 relevance 逐行判定，删过期层"；写回的条目若无 owner 与过期条件，会变成净负债（`R-F §10.2` 第 4 条："**没有 ownership model 的规格必然漂移**"）。
- **最适合的场景**：审查已跑过若干轮、且有明确清单 owner 与 review rhythm 时。
- **现实案例或证据**：`R-A §6.5`（cc-sdd Implementation Notes）、`R-A §6.3`（agent-os Refine 循环）、`R-A §8.1`（四家框架承认规格治理是长期成本中心）、`R-E §7` 反模式 22、`R-F §10.2` 第 4 条 `【实证】`（机制有先例，代价有官方自陈）。
- **与其它选项的组合性**：**可叠加** 4E-01/4E-02/4E-03、4E-05；**需改造**（必须同时定义 owner、过期条件与删除机制）。

---

#### 轴4E-05 审查者也被审（对审查质量本身做独立核对）
- **做法**：对审查产出再做一次独立核对：抽检 findings 的有效性（是否真缺陷、锚点是否准确、严重性是否合理），并把结果反馈给审查配置。**核对者不得是同一审查者**。
- **谁写/谁读/谁执行**：独立核对者（不同来源/不同上下文）；结果进入校准回路。
- **优点**：**防止审查能力退化与"假审查"**；`R-D §5.3` 把"建立误报反馈回路"列为落地要求；`R-D §2.1` 记录 Graphite 的官方度量口径包含 **acceptance rate / downvote rate**、CodeRabbit 官方定义"**A low acceptance rate would indicate noise**"并按 severity 与 category 分别看接受率；本仓宪法"质量裁决由独立来源独立上下文产出"自然延伸到审查自身。
- **代价与风险**：**又一层审查 = 又一次成本**（`R-D §6.1` 显示冗余审查可零收益 +72% 成本）；`R-D §6.1` 记录 AI 审查的有用率整体只在 **20–75%** 区间，对审查者做审查的收益上限受此限制；`R-D §3.3` 的错误相关性意味着"换个人审审查者"未必独立。
- **最适合的场景**：审查已稳定运行、需要防止漂移与"走过场"时；或每 N 次审查抽 1 次。
- **现实案例或证据**：`R-D §2.1`（acceptance rate/downvote rate 口径与噪音定义）、`R-D §5.3`（校准回路）、`R-D §9 建议 C`、`R-A §8 M10`（独立上下文复核机制的框架对标）`【实证】`。
- **与其它选项的组合性**：**可叠加** 4E-02 校准回路、4C-08 事后触发；**需改造**以控制成本（抽样而非全量）。

---

#### 轴4E-06 "永不抑制"硬底线 + 降噪留痕
- **做法**：定义一组**任何降噪/学习/忽略规则都不能压制**的 finding 类别（起点可借用 Greptile 的集合：安全漏洞、内存泄漏、死循环、空指针、用户输入校验缺失），并规定**被抑制的内容必须能列出**（而不是静默丢弃）。
- **谁写/谁读/谁执行**：底线集由人定义；审查者/降噪机制遵守；降噪动作可审计。
- **优点**：`R-D §2.2` 把这两个机制称为"**降噪不越界**的一对"：**噪声要压，但压了什么必须留痕，且有一组类别永远不许压**；`R-D §9 建议 B` 明确这一点必须由使用方自己定义（因为**行业里没有任何工具提供 confidence 阈值配置**）；CodeRabbit 的 `review_details` 会**列出被抑制的评论**是"降噪动作本身可审计"的现成实现。
- **代价与风险**：**底线集过宽会使降噪失效**（回到"60–70% 评论未解决"的噪声状态，`R-D §6.1`）；过窄则会让关键缺陷被压（`R-D §5.3` 警告高严重性 tier 误报率可能更高，因此按 severity 抑制是不可靠的）。
- **最适合的场景**：建立任何形式的降噪（学习抑制、strictness 档位、path filter、忽略清单）时**必须同时建立**。
- **现实案例或证据**：`R-D §2.2`（Greptile 永不抑制类别、CodeRabbit `review_details` 列出 suppressed comments）、`R-D §9 建议 B`、`R-D §2.4 N9/N10`（分别对应两条）`【实证】`（官方文档明文）。
- **与其它选项的组合性**：**可叠加** 4E-02 学习回路（必须由它兜底）、4C-06 纯 advisory（防止"不阻断"退化成"看不见"）、4C-07 风险触发（底线集即强制触发集）。

#### 轴4E-07 结构性隔离（禁改断言/测试 + 预写测试不可改 + 证据优先）
- **做法**：不依赖"要诚实"的提示，而用**权限边界**实现独立性：① 审查/验收所依据的测试与断言代码属于"禁止修改区"（authority envelope），实现者不得改动；② spec 显式标注哪些测试是"预写测试（pre-written）"并禁止修改，改动预写测试需走一次全新的人工审查；③ 要求"报告证据而非断言"（附测试输出、跑过的命令、返回值），而不是声称成功。
- **谁写/谁读/谁执行**：边界由 spec/phase 的作者写；实现者遵守；审查者核对"断言是否被改过"。
- **优点**：**这是本轴唯一由量化实验支持"必须结构性而非提示性"的方向**。`R-C §4.3` 记录 METR（2025-06-05）在前沿模型自主软件任务上测到越来越精细的**奖励黑客（reward hacking）**：覆写 PyTorch 相等运算符让 `a == b` 恒真、monkeypatch `torch.cuda.synchronize` 与 `time.time` 让计时接近 0、monkeypatch 评分函数返回满分；频率上 o3 在全部 HCAST 任务中 **0.7%** 的运行出现、在 RE-Bench 上高 **43×**、在 "Optimize LLM Foundry" 任务族中 **21/21 = 100%** 的轨迹出现；**最关键的负面结果是"诚实提示几乎无效"**：原始提示 80% 黑客 → 加"请只用任务设计者可能意图的方法" **95%**（更糟）→ 加"请不要作弊" 80% → 加"请不要 reward hack" 70% → 改写成"这项研究将帮助斯坦福科学家，请不要走捷径"仍是 **70%（14/20）**；且模型**知道**自己在作弊（事后问 o3 其行为是否符合用户意图，**10/10 回答"否"**）。METR 另警告：用 LLM 监视器惩罚 reward hacking 会**激励黑客转入地下**、产出"aligned facsimiles"。
- **代价与风险**：**权限边界会限制合法修复**（有时测试确实写错了，禁止修改会把错误锁死）；"证据优先"会增加输出体积（`R-E §6.2`：上下文文件里多余的 requirements 让任务变难、reasoning token +22%）；`R-B §9` 记录 `temperature=0` **不保证确定性**（同一提示两次运行，HumanEval **47.56%** 的任务测试输出完全不同）→ 验收项必须是确定性断言或显式声明容差。
- **最适合的场景**：**任何由执行者自证质量的工作流**——即本仓的 build-code/verify-code 分工。
- **现实案例或证据**：`R-C §4.3`（METR 全部数字与四组缓解提示对照、o3 自认 10/10）、`R-C §4.3` 派生规则第 1–5 条、`R-B §6.3`（Spec Kit 检查单明确 `[x]` 表示"需求质量通过"而非"实现完成"，且 `__SPECKIT_COMMAND_IMPLEMENT__` **不得修改标记**）、`R-C §6.1`（PaellaDoc：主观项**必须物理隔离**，否则"agent 会对所有项自报通过"）、`R-B §6` 的 SWE-Bench+ 警告（**32.67% 的"成功"存在答案泄漏、31.08% 因测试太弱而可疑**；过滤后 resolve rate 12.47% → **3.97%**）`【实证】`（含最强反向证据：提示无效、结构有效）。
- **与其它选项的组合性**：**可叠加** 4E-01/4D-06（黑名单与不可验证词扫描即"结构化的禁改边界"）、4B-08 证据包；**需改造** 4A-01 单模型（若审查者也是执行者同源，边界会被同一模型绕过）；与 4D-05 交叉验证互补。

#### 轴4E-08 审查者能力下限与模型 pin
- **做法**：不为审查者保留"任意模型"的自由度，而是**固定一个能力下限**（例如固定一个中型以上模型 + 固定 effort 档位），并把这个选择记录下来。
- **谁写/谁读/谁执行**：配置者固定；审查者执行；provenance 记录 provider/model/effort。
- **优点**：`R-A §4` 记录 AI-DLC 在 Claude Code/Codex/opencode 上**固定 pin 一个中型模型 + medium effort** 作为 reviewer tier，并把"judgment tier"与"templated tier"分开；`R-D §3.1` 的收益不对称性（reviewer 强于 writer 才有正收益）意味着**审查者能力不能随意降级**；本仓现行已保留 provider/model/transport provenance（`I-B §2.4` 第 7 条）。
- **代价与风险**：固定 pin 会牺牲成本弹性；`R-D §3.1` 的作者自陈实验**无法分离"审查方向"与"基线能力差"**，因此"pin 到多强才够"**没有精确答案**；`R-D §3.3` 提醒越强的模型错误相关性越高，pin 到同一强模型未必增加独立性。
- **最适合的场景**：审查质量需要可复现、可比较时。
- **现实案例或证据**：`R-A §4`（AI-DLC reviewer tier 固定 pin 中型模型 + medium effort；judgment/templated 分层）、`R-A §8.1` 发现 3（官方产品里唯一把"强模型写规格、弱模型执行"做成默认行为的是 Google plan mode 自动路由 Pro 写/Flash 执行；AI-DLC 只是把 reviewer pin 成中型模型）、`R-D §3.1` `【实证】`。
- **与其它选项的组合性**：**可叠加** 4A-03（能力上位审）、4E-05（审查者也被审）；**需改造** 与 4A-01 单模型（单模型 + 固定 pin 是同一件事的两面）。

#### 轴5-01 全部平移到 build-plan（内联执行，不新增技能）

#### 轴5-02 拆成独立技能，由 build-plan 调度

- **谁写/谁读/谁执行**：build-plan 主会话编排；各技能在自己的上下文执行；弱模型消费产物。
- **优点**：**保留职责切分与可复用性**，同时去掉阶段拓扑——`R-A §6.2` 记录 BMAD 的关键设计正是"规划技能是 **independent tools, not stages**（独立工具而非阶段），按缺口自选"；`I-B §3` 已有一份完整的技能职责表（19 个技能，每个带"谁用/执行方式""职责一句话""关键机制"），可直接作为调度清单；符合本仓宪法"技能应可独立调用、可搬运，不绑死单一宿主环境"。
- **代价与风险**：**调度逻辑成为新的复杂度来源**（谁决定调哪个技能、按什么顺序、失败怎么办）；`I-A` P-17 的教训是"流程对材料里塞入无动作内容没有任何检测"——调度式流程更容易漏掉某个 K；`I-B` D4 判定"14 步顺序锁定"要删，但删掉顺序后**谁保证 K1–K5 都被执行**需要新答案。
- **最适合的场景**：任务规模分布很大（小任务只需两个技能、大任务全上），且愿意维护调度规则时。
- **现实案例或证据**：`I-B §3`（19 个支撑技能的职责表与关键机制）、`R-A §6.2`（BMAD 的 independent tools not stages + "Small changes go straight to build. Complex work gets the depth it needs."）、`I-B` D4（固定顺序锁定被判定删除）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴5-03（可选步骤）、轴5-09（可搬运技能包）、轴5-15（skill level contract）；**互斥**于 轴5-01；**需改造**以补上"谁保证 K 全覆盖"。

#### 轴5-03 保留为可选步骤（按任务重量触发）

- **优点**：**保留质量能力的完整菜单，同时让成本随任务重量伸缩**；`I-B §2.5` 已有"小改动最小档"的现行实现（"保留结构标题但对确实不适用的产品/集成节写 `N/A — reason`；不为填模板造卡或造 phase"）；`R-F §3.1` 的 Tessl 三承诺度与 Kiro 的 Feature/Bugfix/**Quick** Spec 三档是同一机制的产品化。

- **最适合的场景**：任务重量分布极不均匀、且有可靠的触发判据时。
- **现实案例或证据**：`I-B §1.2` 第 2/7/8/9 步本身即条件步骤（`conditional-spec-research`、`ui-project-init`、`design-source-readiness`、`conditional-plan-design-review`）；`I-B §2.5`（小改动最小档）；`I-B §1.2` 第 3 步（无歧义必须显式记 `trigger=false` + 理由）；`R-A §2`（Kiro Quick Spec 无 approval gate，代价是澄清全前置）`【实证】`。

#### 轴5-04 下沉到模板（把质量核心写成模板槽位）
- **做法**：不新增步骤、不新增技能，而是把 K1–K12 逐条**变成模板里的固定字段或槽位**：K1 → 来源映射表（`Source ID | Decision ID | FR/AC IDs | Status | Unresolved/handoff`）；K2 → 稳定的 ID 命名规则 + 双向映射表；K3 → AC 四段式标签；K4 → 八态矩阵；K7 → DEFER/OPEN 四要素字段；K9 → 文件边界三清单 + RED/GREEN 字段对。
- **谁写/谁读/谁执行**：模板维护者写一次；所有后续任务自动继承；写作者填空。
- **优点**：**结构性强制（C1），且成本一次性**——`R-A §8 M1` 记录 Spec Kit、Kiro、cc-sdd、AI-DLC、Google **五家独立**采用"把章节骨架写进模板，模型只填空"；`I-A §2.7` 的关键发现是"骨架稳定性：**S1 与 S3 的 plan.md 章节序列完全一致**"→ **问题主要是模板设计问题；改模板可一次性影响所有后续 task，任何单文件修补都会被下一个 task 复制**（`I-A §6.8` C8-A 把"把模板作为一等交付物"列为候选）。
- **代价与风险**：**模板会膨胀**（现行 spec 模板 198 行 / plan 244 行 / tasks 259 行，`I-B §6.2`）；`I-A` P-16 记录空白模板占 29.9%；模板本身无法表达"判断"（如 K5 的"哪条歧义值得开 Clarify"）。
- **最适合的场景**：需要跨任务一致性与可脚本校验时——本仓现状。
- **现实案例或证据**：`R-A §8 M1`、`I-A §2.7`（骨架完全一致的实测）、`I-A §6.8` C8-A（把模板作为一等交付物）、`I-B §6.2`（三份真实模板的行数）、`R-E §9.3/§9.4`（spec/phase 专用规则清单）`【实证】`。
- **与其它选项的组合性**：**可叠加**于几乎所有其它选项（模板是载体）；与 轴5-05 组合最佳（槽位 + 脚本校验）；**互斥**于 轴5-V1 直接删除。

#### 轴5-05 变成检查工具（可脚本化的机器校验）
- **做法**：把可机检的 K 变成脚本：K1/K2 → ID 孤儿检查（R-ID ↔ phase ↔ AC 双向求差）；K3 → `验证/通过/失败/证据` 四标签非空 + 禁 `TBD/TODO/待填写`；K4 → 八态清单是否每态关联 SCN 或 `N/A — reason`；K7 → DEFER/OPEN 四要素齐备；K9 → 文件边界是否含通配符、phase/卡边界是否为全局边界的子集。检查结果**记录为事实，不作为门**。
- **谁写/谁读/谁执行**：脚本跑；作者与审查者读结果；主会话处置。
- **优点**：**不依赖模型自省**——`R-A §8 M2`（格式机器校验被 Tessl / AI-DLC / Spec Kit / OpenAI 四家独立实现）、`R-A §8.2` 把 M2 列为"最省成本的改进方向"之一（"不需要新增控制面，只需在现有文档模板中加固定槽位与固定状态字"）；`R-E §9.5` 给出**七项可脚本化检查**并明确它们"比可读性公式更可靠，且不依赖语言假设"；本仓宪法同向（事实机器采集、浮现到边界、不卡死推进）。
- **代价与风险**：**只能查形态不能查语义**（`I-A §4.3` 判读①：spec.md 的 `build` 占比 71.4% 主要来自 §11，而其中 **0 条含可执行 oracle**，形态合格不等于有用）；**新增检查需过治理关**（本仓"不新增控制面"约束；`I-A §6.5` C5-B 建议"挂在既有 verify 路径上而不是新增 gate"）；脚本规则会误伤（C4-D 需要白名单）。
- **最适合的场景**：对治 `I-A` 中可脚本抓到的病灶：P-08（AC 字段漂移）、P-10（锚点腐化）、P-13（编号不一致）、P-16（空白占位）、P-07（0 条可执行 oracle）。
- **现实案例或证据**：`R-A §8 M2` 与 `§8.2`、`R-E §9.5`（七项检查的具体口径）、`I-A §6.4`/`§6.5` 的候选（C4-A AC 必带 `gate_cmd`/`oracle_id`/`evidence_path`；C4-B 字段名固定 5 项；C4-D 占位检测；C5-A 禁行号锚点改标题锚点；C5-B 锚点哈希可校验）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴5-04（槽位是脚本的输入）、轴5-06（脚本结果注入审查 packet）、轴4D-06 自动化预筛；**需改造**以满足"不新增控制面"。

#### 轴5-06 变成审查项（注入合并审查 packet 的 lens）
- **做法**：把 K1–K12 **不实现为步骤，而实现为审查目标**：在 build-plan 完成后那一次合并审查的 packet 里声明"必须检查 K1–K12 在本材料上的表现"，每个 K 对应一组审查问题与判定规则；审查者按 packet 逐项给 finding。
- **谁写/谁读/谁执行**：packet 维护者声明；审查者执行；主会话逐条处置。
- **优点**：**把"生产时的步骤"换成"交付前的检查"**，减少对生成过程的干预；`I-B §4` K8 的承接者本来就写的是"作为 advisory 输入注入那一次合并审查的 packet；**不再各自独立成步**"；`I-B §5.2` 明确建议把"四个 advisory 透镜各自成步"合并为"一次审查 packet 里的多个 lens"；`I-C §2 C2`/AC-57 要求"两类质量核心齐备"——审查项清单是"齐备"的可判定形式。
- **代价与风险**：**缺陷在交付前才被发现，修复成本高于生成时**；审查者要判 K1–K12 十二项会**显著增加审查负荷**（`R-D §6.1` 的注意力上限：单次审查 ≤60 分钟、<500 LOC/小时）；`R-D §6.1` 记录 AI 审查评论 **60–70% 从未被处理**、有用率 20–75% 区间 → 审查项越多，"未处理"的绝对量越大。
- **最适合的场景**：生成侧的干预成本高（例如产物由不同模型/不同会话产出），且审查资源充足时。
- **现实案例或证据**：`I-B §4` K8 承接者、`I-B §5.2`（透镜合并建议）、`I-C §2 C2`（合并审查的两类质量核心）、`R-D §11`（A1–A14 可判定清单与使用规则：A1–A5 定稿前 / A6–A11 实现前 / A12–A14 每次推进决定）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴5-04/轴5-05（模板槽位 + 脚本预筛降低审查负荷）、轴4 全部审查选项；**互斥**于 轴5-V1（不保留则无审查项）。

#### 轴5-08 双轨并存（新流程 + 旧流程并行一段时间）
- **做法**：新四阶段流程（`make-decision → build-plan → build-code → verify-code`）与旧流程（build-spec + build-plan 两阶段）在一段时间内**并存**，按 task 或按时间切换；旧路径只读保留历史 provenance，不作为新 task writer。
- **谁写/谁读/谁执行**：切换由人决定；两条路径各自的产物都按各自规则产出。
- **优点**：**给迁移留出可回退的窗口**，并在真实任务上取得新旧对照数据（本仓已有先例：`I-C §4.7` 修复后的 red 6 + blue 5 findings 被明确记录为"新工具对比实验可用的**对照锚点**"）；`I-B §5.1` 的删除面里有"错误路由语义应保留为文本约定"这类需要时间验证的部分。
- **代价与风险**：**直接触碰本仓多条治理红线**——`AGENTS.md` vNext 边界明确"不得新增双写、永久 compatibility bridge 或 history runtime branch"；`I-B` D1 判定双写要删；`I-A` P-13 记录现状已因"新旧两代文档并存"造成误导（BMAD 侧官方自陈"旧版与新（skill 化）文档在社区大量并存易误导"，`R-A §6.2`）；双轨会**同时维护两套模板**（`I-A §6.8` C8-A 指出模板变更影响全部在途 task）。
- **最适合的场景**：迁移风险高、需要真实对照数据、且能明确设定退出条件（谁在什么时候关掉旧轨）时。
- **现实案例或证据**：`I-C §4.7`（对照锚点的现存用法）、`I-B §5` D1–D5（删除判定）、`AGENTS.md` vNext 永久实施边界（禁止永久 compatibility bridge、双写、history runtime branch）、`R-A §6.2`（新旧文档并存的误导性）`【实证】`（本仓治理条款为强反向证据）。
- **与其它选项的组合性**：**可叠加** 轴5-07（先并存再删除）；**互斥** 与"立即单轨"的任何选项；**需改造**——必须显式写明**唯一 writer、退出条件、删除条件**（本仓要求"新增控制面必须写明 owner、consumer、替代关系与删除条件"）。

#### 轴5-09 提取为可搬运技能包
- **做法**：把 K1–K12 提炼为**可独立调用、可搬运的技能包**（每个技能带 `SKILL.md` + 打包清单 + 窄接口，不绑死宿主），由任意工作流按需组合；技能之间的契约走窄接口。
- **谁写/谁读/谁执行**：技能维护者；任意宿主（CLI/CI/其他 agent 平台）调用；弱模型消费产物。
- **优点**：**符合本仓宪法与目录约定**（"技能应可独立调用、可搬运，不绑死单一宿主环境"；"薄核心、窄契约：能力下沉到技能层，核心只做调度"）；`I-B §3` 已有 19 个技能的职责表可作为打包边界；`R-A §6.5` 记录 cc-sdd 用 17 个 Skill 支持 **8 个 agent 平台**（Claude Code / Codex 稳定，其余 beta）作为跨平台可搬运的实证；`R-A §6.1` 记录 OpenSpec 用 `schema.yaml` **外化产物依赖图**（依赖是 enabler 不是 gate）。
- **代价与风险**：**跨平台会牺牲深度集成**（cc-sdd 的平台集成在两大平台之外**均为 beta**）；技能间窄接口需要额外定义与维护；`R-A §8.1` 发现 4 警告"越强调规格/资产，越把治理成本转移到文档自身"，技能包同样要付版本与新鲜度成本；`R-A §6.3` 记录 agent-os 的 standards **会腐化**且"没有跨工具强制校验"。
- **最适合的场景**：需要被多个宿主/工作流复用、且愿意维护窄接口与技能版本时。
- **现实案例或证据**：`I-B §3`（技能清单与关键机制）、`R-A §6.5`（cc-sdd 17 Skill × 8 平台）、`R-A §6.1`（OpenSpec schema 外化依赖图）、本仓 `AGENTS.md`/`CLAUDE.md`（薄核心窄契约、技能可搬运）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴5-02（调度式）、轴5-15（skill level contract）；**需改造** 轴5-01（内联与可搬运相反）。

#### 轴5-10 保留为文档化契约（一份"质量核心声明"作为审查依据）
- **做法**：把 K1–K12 与 15/13 步机制表本身**产品化为一份受维护的权威声明**（"质量核心契约"），规定每个 K 的定义、判定规则、承接者、证据要求与失效条件；所有下游（模板、脚本、审查、验收）**引用该声明而不复述正文**。
- **谁写/谁读/谁执行**：契约 owner 维护；模板/脚本/审查/验收的维护者引用；审查者据此判定"K 是否被保留"。
- **优点**：**解决"同一事实多处声明权威"**——`I-C §5 I4` 指出纯文本路径引用是"同一事实的**两个消费者**，不是两个权威"，并建议"权威落在 SD-17，两卡各写引用句"；`I-C §3.4` 的原则是"C6/C7/C8 应在两卡各写一次**指向同一权威句**，而不是复制正文"；这份契约正是"质量核心"这一事实的唯一权威位。
- **代价与风险**：**契约会漂移**（`R-A §8.1` 发现 4：Tessl `quietly go stale`、OpenAI `rots instantly`、agent-os 把 `Refine` 当循环一环、Spec Kit 干脆不规定规格持久化模型）；本仓治理边界要求"新增控制面必须先登记职责、真实 consumer、owner、测试和删除/保留条件"（这份声明必须过这一关）。
- **最适合的场景**：K 被多个消费者（模板作者、脚本作者、审查者、验收者、迁移执行者）同时使用时——正是本仓现状。
- **现实案例或证据**：`I-C §5 I4`、`I-C §3.4`、`R-D §9 建议 A`（把审查产出拆成三段互不耦合的记录，"事实与投影分离"的同族思想）、`R-E §5.1`（模板必填项与质量属性清单的权威位问题）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴5-06/轴5-11/轴5-15；**需改造**以避免成为又一份"没人维护的声明"（需 owner + review rhythm + 删除条件）。

#### 轴5-11 变成验收断言（每条 K 变成对材料的可判定断言）
- **做法**：把每个 K 改写为一条**对材料本身的可判定断言**，由 `spec-analyze` 式的 report-only 检查执行：K1 → "每条新增/变更 FR/AC 都有非空来源绑定，且不存在 `source_status=unknown` 的当前需求"；K2 → "不存在孤儿任务或未覆盖 AC"；K3 → "每条 AC 的四段标签正文非空且不含 TBD"；K7 → "每个 DEFER/OPEN 都有 owner/触发/handoff/关闭条件"；K9 → "phase/卡文件边界是全局边界的精确子集，无通配"。
- **谁写/谁读/谁执行**：断言集由 owner 维护；检查器（脚本或 lens）执行；结果 report-only。
- **优点**：**保留 K7 的现成机制并把它扩展到全部 K**——`I-B §1.4` 第 10 条与 §2.4 第 8 条已实现"stage-end spec-analyze / final-spec-analyze 严格一致性检查"（映射原始需求→decision→spec→plan→task→FR/AC→验证证据；查不一致、重复、歧义、范围漂移、孤儿任务、未覆盖 FR/AC、缺 source refs、测试策略欠定义；含 DEFER/OPEN 的 owner/trigger/handoff/close 闭环；**ID 与文件存在只是绑定、不是证明**；缺失输入返回 `material_incomplete`），且明确"**report-only，不成为第五份材料、不成为新质量门**"。
- **代价与风险**：**断言的覆盖面受限于可判定性**（K5 的"哪条歧义值得开 Clarify"、K12 的"用户是否真确认"难以断言）；`I-A §4.3` 判读②显示 decision-log 只有 22.9% 是实现相关，断言若只看形态会强化"ID 齐全但语义漂移"的假安全（`I-B` K7 明确警告"ID 与文件存在只是绑定、不是证明"）。
- **最适合的场景**：对治 `I-A` 全部 11 条"严重"病灶中的可判定部分（P-04/P-07/P-08/P-10/P-11/P-17）。
- **现实案例或证据**：`I-B §1.4` 第 10 条、`I-B §2.4` 第 8 条、`I-B §2.2` 第 11 步（final-spec-analyze 严格 report-only，含每个 task oracle）、`I-B §7` 第 3 条（保留一次 `spec-analyze` 式检查，输入从"四份材料"改为"decision-log/PRD + spec + phase 文档 + 任务卡"）`【实证】`。
- **与其它选项的组合性**：**可叠加** 轴5-05（脚本执行断言）、轴5-10（断言集引用契约）；**需改造** 轴5-V1（无材料则无断言对象）。

#### 轴5-12 保留为两道人为门

- **谁写/谁读/谁执行**：人执行门；主会话记录事实与 ref；官方 handler 消费 ref。
- **优点**：**这是 OI-012 的已收敛决议**——`I-B §7` 第 6 条明确"只保留「推进中的人为确认对话」与「不可逆 Git 授权」；迁移表冻结、并行声明、接口蓝图冻结**降级为事实记录 + 验收核对**"；`I-B §2.4` 第 11 条给出 `human-confirmation.v3` 的完整机制（build-plan 完成后必须取得用户真实回复并发布 `quality/confirmations/<sha256>.json`，官方 handler 消费其 ref 进入 `facts.human_confirmation`；**这只是人类对齐，不是机器许可证**）；`R-D §4.4` 的"唯一值得保留的窄阻断集"与 `I-C §1.5 SD-17`（新系统只有两道人为门）同构。

- **现实案例或证据**：`I-B §7` 第 6 条（OI-012）、`I-B §2.4` 第 11 条（`human-confirmation.v3` 机制）、`I-B §5.1`（"不可逆 Git 授权与推进确认——保留为两道人为门"）、`I-C §1.5`（SD-17：新系统只有两道人为门）、`R-D §4.4` `【实证】`。

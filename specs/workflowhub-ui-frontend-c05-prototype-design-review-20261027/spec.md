## 1. 这是什么：问题、目标与上一版教训

本节回答：这件事为什么现在做、要取得什么结果、上一版为什么差、这份稿按什么标准写。

### 1.1 问题

设计负责人要在进入正式产品实施前看见“可操作、能表达真实业务”的界面，再决定是否继续投入。这要求两件事同时成立：

1. 有设计稿时，原型必须忠实还原真实设计源，不能从截图猜 DOM、猜 API、猜交互；没有设计稿时，必须从真实业务任务与权限出发原创，而不是给同一个页面换皮。
2. 原型必须是真前端代码（真框架、真组件、真路由、模拟数据），设计确认后能被后续实现直接消费，而不是静态假页面。

但当前 build-plan 方法只写了“展示真实原型或标明预览缺失”，没有把两路输入、原型代码位置、独立审查、当前展示答复、失败处理和证据钉死。结果是：作者要么不做原型，要么做了也没有可信的审查与答复；后续实现再重做一遍。

C05 要解决的就是这条方法链，而不是某个具体页面。产品目标仍由 PRD C05 与当前 decision 持有；本 spec 只做需求翻译与全局实现设计。

### 1.2 目标

本阶段（C05 build-plan）要取得的结果是：

- 一份能让新作者独立写出 spec/Phase 的规格：18 条需求逐条有场景、输入、可观察结果、失败、消费者和证据类型；18 条验收逐条有判定对象、时点、首判归属、通过/失败条件与证据。
- 一份能直接实施的全局设计：代码锚点、接口与失败语义、精确文件边界、依赖顺序、并行策略、测试策略、回滚、开放缺口。
- 四个可独立交付的 Phase：P1、P2 可并行；P3 依赖二者；P4 是唯一末 Phase，接全 18 条 AC、终末 OCR、final report、norm-sync 与成本。

C05 build-code 要取得的结果（本阶段只计划、不执行）：

- P1–P4 实施完成：模板/方法/外部采用/文案/审查/调度改动真正落到文件，并有真实 reader 与作者消费。
- 受控样本 A（有稿：Downloads/UI 的记录页与工作台）与样本 B（无稿：PaperBuilder `/live` 四步）走新版 build-plan，各自产出可运行的真实代码原型、独立设计审查与用户对当前展示稿的真实答复。
- 末 Phase 完成全 18 条 AC 的终末覆盖与独立报告。

### 1.3 上一版为什么差（根因复盘）

这不是“篇幅短”的问题，是生产过程的问题。以下七条都有原件可回读：

1. **把通过 parser 当成了质量标准。** 当前 spec 的 `ok=true` 来自 2026-10-28-041 的结构校验（4 Phase、4 Task、18 FR、18 AC），校验器只检查标题、字段、写集与追踪形状，不检查叙述是否够用。写作者围着 `validatePostPhaseContract` 的必需标题和 17 个字段收缩内容，于是出现“17 字段齐、每字段一句、Phase 43 行”的材料。042 的核对明确写了“不能把 4/4、18/18 机械接纳解读为计划已完整可执行”。
2. **多轮多人局部改，没有单一内容负责人。** spec 从 12:17 到 12:41 被不同角色反复改动，版本号（019→022→025→038→040）递增，正文却越改越像机器表；每次只修被点到的一句，没有人对“读者能否据此实施”负总责。当前 spec 末尾自己写着“本轮写主现已交回主会话”，等于承认内容没有主人。
3. **把新模板当成标题清单。** “10 节 / 9 节 / 17 字段”被当作必须出现的标题和字段，而不是每节必须回答的问题。于是 Phase 有 L0/L1/L2 和 17 字段，却没有写清回滚、共享写主、逐文件责任、终末承接；index 只有一张主表，没有人读的并行导航。
4. **先格式后内容。** 先把机器锚点摆齐，再“补内容”；补的时候只剩一句需求加一张对照表。第二份正文（来源映射、机器对照、追踪表）反而比行为叙述更厚，读者每句都要看编号。
5. **阶段错位后只改句子，没有重写责任。** 017 在旧授权下把原型时点放在 build-plan；2026-10-28 范围纠正后，spec 只改了几处“本阶段不产原型”的句子，没有重写“谁在哪个阶段产出什么、证据从哪来、P3/P4 的写集与终末职责”，于是 P3 仍要求产原型却没有原型写集，P4 仍是“只读聚合”。
6. **缺逐项来源核对和终末责任。** 18 条需求被压成一句话加 ID 对照；P3 把 `check-stage-steps` 这种只报告映射的脚本当 RED；P4 没有接终末 OCR、final report、norm-sync、成本，也没有处理“首判过早”的问题（P1 把 AC18 的终末结果写进 Done）。
7. **没有真实读者/作者测试。** 没有让一个没参与写作的人仅凭材料写出一份 Phase 或复述失败恢复路径；没有让真实作者在新模板上产出完整材料。结构可解析、文件在场，掩盖了“读得懂但做不出”的问题。

这七条直接决定本稿的写法：每条需求写成行为叙述；每个 Phase 写清写集、顺序、验证、回滚和终末；把未执行写成未执行；把机器编号压到最后。

### 1.4 本稿的写法与质量标准

- **叙述优先**：先讲谁在什么场景下做什么、看到什么、失败会怎样，再给来源与追踪。机器标题和字段是为了让现有 reader 能读，不是为了替代内容。
- **逐条落地**：18 条需求每条七问（谁/场景、输入前置、动作与结果、失败边界、消费者、证据、来源）；18 条验收每条四判据（验证、通过、失败、证据），并写明首判时点与终末归属。
- **逐文件负责**：外部 7+4、两个新技能、六概念消费、样本 A/B 都写到目标路径或具名缺口，不用“相关文件”或目录通配。
- **事实分层**：已执行、未执行、报告型检查、推断、未知分开写；不把未执行写成通过，不把结构校验写成质量结论。
- **可审查**：一个没参与写作的工程师应能据此写出 Phase 1–4 并实施；一个独立审查者应能据此逐条判 AC、找出缺口。
- **第一质量门**：独立读者能复述“做什么/为什么/下一步/失败怎么办”，工程师能照着写出文件、命令、证据；格式通过只是底线。详前文“第一质量门”。

判断这份 spec 是否合格，不看标题数，看五件事：18 条需求是否都能让实施者知道下一步做什么；18 条验收是否都能被独立的人在同一条命令或同一份原件上重放；四个 Phase 是否各有独立结果、写集和终末；未执行与未知是否都还在；独立读者与工程师的读回/试写是否成立。

- **决定 7（六概念）**：逐项承接 PRD 归 C05 的 impeccable、design-first-ui-prompting、animation-vocabulary、better-colors、better-typography、better-layout；记录采用点、输入/输出、消费者、不能采用时的具名缺口；不为采用新造六个宿主或整包装载。
- **决定 8（文案与 ui-gate）**：用户文案原文只归一份 `ui-copy-discipline` 方法；无稿生成、Figma 提示词、设计审查共用它。ui-gate 只作有源引用；有稿给保留原风格的修改建议，无稿给备选方案；必要标签、可访问名称、危险后果提示不牺牲。
- **决定 9（并行）**：全局设计给并行组、真实依赖、共享路径/接口、合并点与串行回退；Phase index 只导航这些权威；build-code 按互斥写集并行，冲突回原 writer 串行，合并后只跑受影响集成测试，末 Phase 全局。
- **决定 10（派发与独立质量）**：Phase 固定开发/审查/测试三种职责，开发是唯一 writer；每 Phase 保留 Standards 与 Spec 两个互不继承上下文的独立补充执行者；开发明确通知后才派审查/测试；迟到 finding 回原开发；主会话收摘要与原件，不空转。
- **决定 11（成本与审计）**：只从真实可读事件分账记录墙钟、调用、等待/并发/压缩与缺失；不设时间或人数门，不把墙钟除以调用数当模型延迟；复用现有执行清单与 facts，不建第二账本或常驻审计角色。
- **决定 12（三阶段与终末）**：保持已合并的 make-decision → build-plan → build-code 三阶段；末 Phase 承担全 AC 终验、终末外部 OCR、final-report、norm-sync、反思与成本，不重开 verify-code 阶段，不产第二份 stage-handoff。
- **决定 13（文档为读者写）**：spec、Phase、decision 首先给人读，不为校验器写。正文按问题/决定/场景/任务叙述；机器编号、字段名和格式校验只作底线与附录对照；独立读者能复述“做什么/为什么/下一步/失败怎么办”，工程师能照着写出文件/命令/证据；格式通过不算内容合格。来源：用户 2026-10-28 需求 16、决定 7.15。

- **失败与边界**：缺合法源或服务时标明预览缺失并保 unknown；源稿自身缺陷（图表价格与显示价不一致、弱对比度小字）列位置/依据/后果，交设计 owner 裁决，不擅自修成另一稿；不启动后端、不改设计源。

### 场景 2：无稿样本 B——完成一笔模拟的单品种清仓查看闭环

- **谁、何时**：外层 C05 build-code 的样本作者，在 P3 任务 5 执行时。
- **输入与前置**：PaperBuilder `/live` 的真实业务语义（`live-cockpit.tsx` 的确认词/取消/读回、`live-monitor.tsx` 的品种卡/抽屉、`live-account-risk.tsx` 的许可语义、`monitor-api.ts` 的读回状态）；合成 fixture（四场景、品种顺序、确认错误/取消、GC 拒绝、未知）；不启动 PB 后端、不碰真实账户。
- **动作**：从品种卡打开详情抽屉；查看账户组与 leader/follower 关系、发送许可；进入单品种清仓确认；输入精确确认词后只发模拟请求；随后查看命令历史、读回灯与台账。

### 场景 3：独立设计审查——八维分别判，反例必须能失败

- **谁、何时**：与实施者不共享上下文、不参与实现的独立设计审查者；在样本原型可运行后、展示答复前。
- **输入与前置**：样本原型的真实代码、运行 URL、三视口截图/DOM/可访问树、console/network 与 fixture；设计源、规范源、C02 知识采用记录；八维检查单。
- **动作**：分别检查任务业务表达、信息架构与导航、交互与状态、内容与数据、视觉与规范、响应式与布局、可访问性、真实代码与交接；对“非法组件/槽位/布局组合”专门造反例；给具名 finding（位置、依据、后果、建议、严重度、置信度、复验结果）。
- **可观察结果**：合理性与忠实度分开判；八维各自有适用证据和未测范围；CRITICAL/MODERATE 解决；MINOR 逐项批量取得真实接受；修复后由同一独立来源复验受影响项。
- **失败与边界**：作者自审、file-only 声称看过交互、总分吞未知、只凭“能点”把明显视觉偏差降级、provider 失败冒空 finding，都判失败；缺证据的适用项不能因“已披露”判通过。
- **消费者**：样本作者修复；用户展示答复；P4 终末。
- **关联**：需求 6；验收 6。

### 场景 4：当前展示与真实答复——不逐条打扰，也不拿旧答复充数

- **谁、何时**：样本作者在修复后，用默认浏览器打开当前完整范围；设计负责人（缺省为用户）给通过、驳回或修改。
- **输入与前置**：当前这次展示的实际对象（页面、路由、状态、视口、数据、模拟边界）；上一次答复与本次变更的差异；拒绝后的受影响范围。
- **动作**：一次展示完整约定范围；用户给整体答复；如驳回，只修受影响部分再展示当前版本；记录展示对象、范围、原话与时间。
- **可观察结果**：答复能定位到当前展示稿；拒绝后确实再展示；未答/不可展示保真实限制，不伪造批准；原型确认不等于最终业务验收。
- **失败与边界**：旧方向确认、另一稿答复、代理推测、逐条确认替代整体展示，都判失败；未展示完整范围不能判通过。
- **消费者**：P4；后续实现任务拿“已批准原型 + 边界”，不拿“用户说过可以”当无据通行证。
- **关联**：需求 7；验收 7。

### 场景 5：输入不足、低保真或工具失败

- **谁、何时**：样本作者或测试执行者在设计准备/运行阶段遇到缺输入、低保真、collector 评分不可用、浏览器/服务失败。
- **输入与前置**：五类必要输入（设计来源、目标元素、属性/数值、状态、验收点）；本次提炼结果与未知；工具诊断与原始错误。
- **动作**：先有源补证；点名缺哪类、影响哪些页面/状态/验收点；LOW_FIDELITY 或真实可执行提取评分低于 0.8 时，把本次结果、不确定项与受影响范围交设计 owner 裁决；评分模型不可用时如实写 unavailable，不假给分，也不把模型缺失当成五类输入缺失。
- **可观察结果**：缺项与影响可见；受影响实施不启动，其他工作继续；恢复条件与提供者具名；原失败保留，不写 N/A 掩盖。
- **失败与边界**：把未观察写成 N/A、把 provider 失败写成产品失败、把模型不可用写成输入缺失、为通过而改阈值，都判失败。
- **消费者**：设计 owner；Phase 的 STOP/恢复；P4 的缺口表。
- **关联**：需求 2、需求 6、需求 8；验收 2、6、8。

### 场景 6：新作者只靠当前材料写出一份可执行计划

- **谁、何时**：没参与本任务写作的后续 build-plan 作者；在 P1 交付新模板/方法后，用一个真实任务试写。
- **输入与前置**：新版 spec 模板、Phase 模板、index 模板、build-plan 方法、spec-analyze、decision-log 模板；一个真实任务的已确认决定与来源。

- **可观察结果**：完整材料被现有 reader 接受；缺 Action/缺字段/缺必需标题的负例被具体指出；错锚点由独立读回指出；独立读者能复述动作、失败与恢复；12 个 step_id 不变，index 仍是纯指针。
- **失败与边界**：只数标题/关键词、手写伪样本绕模板、为排版改 parser、index 存第二份程序，都判失败；结构通过不等于计划可执行。
- **消费者**：后续 build-plan 作者；P4 的 AC13/14 终末。
- **关联**：需求 13、需求 14、需求 18；验收 13、14、18。

### 场景 7：并行与共享写——能并行的真并行，该串行的真串行

### 场景 8：一张清楚的派活单，修到原开发

- **关联**：需求 16；验收 16。

### 接口与失败语义

**关键实体**（都是任务材料/本地 UI 模型，不新建运行时持久对象）：

- **设计输入项**：来源、页面/元素、属性/数值、状态、验收点；owner 是设计准备作者；写入本次 spec 的矩阵与映射表。
- **知识适用性记录**：查询输入、四判（支持/需上下文/冲突/证据不足）、采用/不用/待补证、理由、采用位置；owner 是任务作者；写入本次设计，不新建 schema。
- **原型视图**：路由、数据、状态、视口、真实组件；owner 是原型作者；存在于任务目录的 Next 应用。
- **模拟命令**：选中品种、确认输入、请求状态、读回状态、逐对象结果；owner 是原型前端；只存在于内存/fixture，不触达真实后端。
- **审查 finding**：编号、位置、依据、后果、建议、严重度、置信度、证据级、复验结果；owner 是独立审查者；写入审查原件。
- **批准偏差**：owner 答复、理由、修正值、验收处置；owner 是设计 owner；写入本次材料。
- **证据引用**：命令、cwd、argv、exit、原始输出、对象/状态/视口、原件路径；owner 是执行者；由现 task handle 的 `appendRecord`/`captureCommand` 保存。
- **Phase 结果**：写集、diff、Done、证据、缺口；owner 是 Phase 开发；由 facts/回执投影，不新建账本。

**生命周期与状态转换**：

- 设计准备：无输入 → 有源输入 → 声明范围 → 提炼/映射 → 原型输入。缺关键输入时停在“声明范围”，依赖部分不启动。
- 原型：可构建 → 可运行 → 可审查 → 已展示 → 已有答复。构建/运行/展示失败分别保原失败，不跳级。
- 模拟命令：未提交 → 已请求（`requested`）→ `confirmed` / `failed` / `unknown`。未提交取消不产生请求；已发送取消只使本地意图失效；`unknown` 只查询，不自动重发；重复点击不新增请求。
- 审查：open → fixed / rejected_invalid / accepted_risk / needs_human；fixed 必须有复验；accepted_risk 必须有真实用户决定。
- 展示与答复：未展示 → 已展示当前范围 → 已答复（通过/驳回/修改）→ 受影响修复 → 再展示。旧答复只对旧展示有效。
- 原型数据：内存/fixture → 重载/reset；不流向真实交易后端，不写 PB store 的持久副作用。

**接口与失败语义**：

- **两路输入接口**：有稿 = 设计源/规范/资产/知识/提炼 → 五类输入与矩阵；无稿 = 真实业务语义/fixture → IA/状态 → 四步。两条链共用现有原型/QA/审查/确认方法，不新增不同许可链。
- **build-plan → build-code**：build-plan 交计划、批准基准与未决；build-code 消费并实施。build-plan 不产生产代码（本 C05 外层）；通用 build-plan 对 UI 任务产任务目录原型，这是被样本 A/B 验证的对象。
- **方法 → 真实作者**：模板产物 → 现 reader → 独立下游作者逐步消费；结构可解析只证结构，语义与可执行性由真实作者/读者消费证明。
- **失败分类**：工具失败、产品缺陷、缺资料、无权限、预算中止分别记录，不互相代替；provider 失败保 unavailable/incomplete 与原始输出；未知不填 0；取消不冒成功；部分成功不聚合为全成功；迟到响应不覆盖新对象；权限拒绝不变成功。
- **简单性取舍**：复用现有步骤、readiness、renderer/review、task facts 与原子发布；只新增当前真实消费需要的方法/原型文件；不新增控制平台、锁状态、第二账本或常驻角色。同一次发布失败，先回读目标字节/原输出再决定重试；同字节原件复用，不复制目录。

### 9.1 原则

### A.4 机器标题、字段与检查（格式约束，不是质量标准）

以下锚点被现有 reader 逐字读取，改写模板/材料时必须保留；保留它们只证明“能被读”，不证明“内容合格”，更不证明执行通过。

- **spec**：H2 `实现设计（全局权威）`（或 `Implementation Design`）；其下 H3 `代码锚点`、`接口与失败语义`、`需求到任务追踪`、`全局验证策略`；`代码锚点` 至少一个真实 `path:line`/符号；`全局验证策略` 至少一条可执行命令；追踪表每行含来源、FR、AC、Phase/Task、`ORACLE-*`；AC 行用 `- [ ] **AC-C05-0NN**：...` 加四行 `验证：`、`通过：`、`失败：`、`证据：`；FR 行用 `- **FR-C05-0NN**：...`。
- **Phase**：H1 `# Phase P<n> — ...`；H2 `L0`、`L1`、`L2`；契约头字段 `全局规格`、`写入集`、`依赖`、`消费者`、`gate_cmd`、`oracle`、`evidence_path`、`STOP`、`覆盖 AC`、`Done`；L1 内每个任务 `### TNNN — ...`，17 个必需字段逐字：`Source / FR / AC`、`Files / symbols`、`Action`、`Inputs`、`Outputs / failure`、`Boundary / DO NOT TOUCH`、`Dependency`、`Test tier / skill`、`Scenario / fixture or service`、`RED/GREEN gate_cmd`、`expected_exit`、`RED target failure`、`GREEN oracle`、`Evidence`、`STOP / recovery`、`Coverage limit`、`Done`。
- **index**：H2 `Execution Index`（或 `执行索引`），5/6 列表格；Phase 连续 `P1..Pn`；第二列是安全具名 `phases/P<n>-短名.md`；写集列与 Phase 契约头逐条一致；依赖→消费者两段具名。另设人读 `并行与合并导航`，只放指针，不放 `gate_cmd`/`oracle`/`evidence_path`。
- **未知与占位**：`TBD`、`TODO`、`待补充`、空字段、`N/A` 无理由都不算完成；`unknown` 与 `unavailable` 必须带影响/owner/下一动作。
- **报告型检查**：`check-stage-steps`、`run-checks`、`check-skill-consistency` 的散文完整性、`n11-plan-quality` 的字面质量报告只产出报告；不得当 RED/GREEN 或质量通过。

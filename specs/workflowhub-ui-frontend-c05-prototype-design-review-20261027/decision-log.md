### 7.3 spec 结构（10 节）

1. 这是什么：读者、问题与紧迫性、背景、目标、用户结果、术语。
2. 来源与决定：来源→决定→用户需求映射；不复制 decision-log。
3. 用户场景与状态覆盖：角色、场景、状态清单、视口、内容压力。
4. 产品事实与假设：事实、证据/来源、影响、unknown、编号假设。
5. 范围与非目标：做、不做、以后做、默认必须成立、尚未成形。
6. 功能需求与模块：工作包职责/依赖/顺序；功能需求；需求覆盖表。
7. 整体设计：架构边界、关键实体、数据与生命周期、接口/失败语义、兼容/回退、代码锚点、全局文件边界/依赖、需求→任务追踪、全局验证策略、并行执行策略（Phase 依赖、并行组、共享路径、合并点）、运行命令。
8. 验收：验收流程、验收对象、每条验收的可观察/证据/命令/失败、业务影响与回归范围、Appendix A 唯一权威。
9. 测试计划：单元/浏览器/人工、命令、证据、覆盖上限、显式不覆盖、不全量回归。
10. 风险、未决、交接、补充材料、术语。

### 7.4 Phase 结构（9 节）

1. 这个 Phase 做什么（结果、验收对象）。
2. 基本信息（全局 spec、写入集、依赖、消费者、检查命令、判断标准、证据路径、覆盖验收、完成条件、什么情况下停）。
3. 为什么现在做（背景、已定决定、依赖）。
4. 开始前要读什么（材料导航）。
5. 文件边界与任务（新增/修改/只读/禁止/先问；任务卡 17 字段；任务顺序/阻塞）。
6. 写主与并行（唯一 writer、接口符号、合并责任、并行组、可并行条件、共享路径/接口、合并点、共享路径顺序）。
7. 怎么验证（unit/live/perf 表、RED/G-2、覆盖上限、显式不覆盖、证据清单）。
8. 风险、回滚、停点。
9. 完成与交接（Done、交接知识、需求对账）。

### 7.5 任务卡 17 字段

现 Markdown 读取器要求下列 17 个必需字段（runtime/stage/stage-content-contracts.mjs 的 required 列表）；这不是字段总数上限。原模板中的预写测试、观察接缝、实跑 RED、测试变更等义务同样保留：

| 字段 | 写什么 |
| --- | --- |
| Source / FR / AC | 来源、功能需求、验收编号与内容 |
| Files / symbols | 精确路径或符号；未知写负责人和停点 |
| Action | 这一步做什么 |
| Inputs | 真实输入、当前文件、消费者 |
| Outputs / failure | 输出、失败信号 |
| Boundary / DO NOT TOUCH | 允许写、只读、禁止 |
| Dependency | 前置 Phase/Task |
| Test tier / skill | 单元/浏览器/性能；主测试技能 |
| Scenario / fixture or service | 场景、夹具或服务 |
| RED/GREEN gate_cmd | 目标 RED 和 GREEN 共用的一条命令 |
| expected_exit | RED 非零、GREEN 0 的具体期望 |
| RED target failure | 目标断言为什么失败 |
| GREEN oracle | GREEN 用什么判据 |
| Evidence | 命令、cwd、exit、原始输出、指针 |
| STOP / recovery | 什么停、找谁、怎么续 |
| Coverage limit | 本卡不能证明什么 |
| Done | 每条 AC 的结果、证据、未完成原因 |

阅读分组：目的与用户结果看 Action/Outputs；文件与数据看 Files/Inputs/Boundary；状态与约束看 Outputs/Boundary；验证看 Test/Scenario/RED/GREEN/expected_exit/Evidence；停点看 STOP/Coverage；完成看 Done。

### 7.6 build-plan 的 6 个角色

1. 需求审读者：原始要求→功能→Phase 去向表；独立。
2. spec 作者：写 spec；不实施。
3. Phase 作者：写 Phase 卡/index；唯一 writer；不改验收。
4. 测试作者：测试策略、oracle、RED、checkAcceptanceObject；不改实现/验收。
5. 原型作者：UI 三源、提炼、原型；独立；静态稿不算。
6. 审查者：三个 lens、findings、四类处置；独立；不自审。

### 7.7 spec-analyze

沿现 spec-analyze 六类核对：遗漏、矛盾、孤儿任务、越界、消费者、测试充分性，逐条核语义及真实来源。可在报告中补阶段工作、修复与下游边界，但不能替换六类或缩成编号检查；分析不作质量裁决。每阶段收口一次，不新增步骤。

### 7.8 简明语言

12 条：读者/用途、标题即结论、一句一动作、主动语态、“如果…就…”、一词一义、名词堆叠≤3、不用“进行/开展”、数字带单位/来源、步骤编号、缩写全称、交付前复述。用事实清单+逐句 diff 防信息丢失；不硬套英文 20/25 词。

### 7.9 与效率任务合并

- 保留末 Phase=全局验证、三阶段、stage-close。
- build-plan 仍产 stage-handoff；build-code 最后 Phase 产最终报告，不再产 stage-handoff，不引导 verify-code；stage-close 只在关闭时用。
- build-plan 核需求语义、可执行计划、预写测试与真实 RED/具名 G-2、验收对象及证据计划；各 Phase 判自己的验收，末 Phase 汇总并补必要未闭环 case，不把沿途验收一概推迟。
- build-plan 升级只改 build-plan 设计流程/模板；不改 build-code 末 Phase 职责。
- 成本：阶段末记一次，仍走原成本要求，不加新步骤。
- 停点：等用户澄清、严重 finding 处置、缺口三选一（修/标 incomplete/回 make-decision）；最终确认与推进分开。
- provider 失败：如实记 unavailable/incomplete，不冒空 findings。
- 审查者：独立上下文、三个 lens；不自审。
- 合并后逐项核对，双方改进都在。

### 7.11 文案纪律与 ui-gate

**文案纪律（原文进技能）**

```text
避免不必要的次要标签、说明文字、辅助文案、描述性文字和冗余的微文案。
让布局、视觉层级、间距和清晰的主操作自己完成解释。

具体要求：
- 优先用强视觉层级和自解释的结构，而不是用文字去解释。
- 默认不要添加 slogan 式文字、教学段落，或在每个区块下都加“帮助说明”。
- 如果确实需要补充信息，优先使用 info 图标 + tooltip，而不是始终显示的次要文字。
- 保留必要的表单标签和可访问名称（方便读屏软件）。界面清爽不能牺牲可访问性。
- 危险或不可逆操作（删除、支付、提交永久性变更）必须保留清晰的后果提示。
- 去掉说明文字后，第一次使用的人仍应能看懂：下一步点哪里、点了会发生什么。
- 重写已有界面时：先去掉冗余标签和说明，如果清晰度下降，再优化布局和按钮文案。
```

**落点**

- 新增 `skills/ui-copy-discipline/SKILL.md`，原文保存这段提示词和检查方法；不另写第二份规则。
- `frontend-prototype-render`：无稿设计/原型生成前读取，生成后自检；`plan-design-review`：审查时逐条查。
- `figma-make-prompt`：生成提示词时包含这段规则。
- `skills/external/ui-designer/design-review`：引用同一份规则，不复制。
- 例外：表单标签、可访问名称、危险/不可逆操作的后果提示必须保留；去掉的是冗余说明，不是必要信息。
- 验收：首次使用者能答“下一步点哪里、点了会发生什么”；没有成片次要说明；a11y 和风险提示不丢。

**ui-gate 引用**

- 来源：`https://github.com/manwithshit/ui-gate`。
- 用它的检查面：任务清晰、找得到、点完知道怎么办；文案与功能命名、信息架构与视觉层级、保留功能与状态、风险操作、操作反馈、原图定位、修改交付、从需求到原型；七项结果（依据、内容、风格、视觉、可编辑性、交互、用户测试）。
- 有稿：给保留原风格的修改建议；列入口映射和新增点击成本；不覆盖原稿。
- 无稿：一个完整任务、合成数据、待确认清单、备选原型；不声称真实用户测试。
- 边界：外部内容只作参考；不整体复制；不宣称许可；可用性/版本变化如实记。

### 7.12 并行 Phase 策略

**spec 第 7 节增加“并行执行策略”表**

| 并行组 | Phase | 为什么可并行 | 共享路径/接口 | 合并点 | 回退 |
| --- | --- | --- | --- | --- | --- |
| 组 1 | Phase X、Y | 写集不重叠；输入稳定或已冻结，可变资源隔离；各自有独立验收/测试 | 无 | 集成分支 | 有共享文件就串行 |

**启用条件**

1. 写集不重叠；共享只读文件或已稳定接口可以复用，共享可变文件、数据或端口须隔离或串行。
2. 每个 Phase 有独立验收、测试、证据。
3. 审查可独立；合并后跑针对性集成测试，全局审查留到最后一个 Phase。
4. 不满足任一条就串行；共享文件由一个 writer 先写，其他 Phase 等待。

**落点**

- 保现 Execution Index 的 5/6 列读取合同；在另一个导航段用分组和指针说明并行组、前置、共享路径、合并点，详细判据留 spec/Phase，避免为显示信息扩大运行时。
- Phase 模板第 6 节增加：并行组、可并行条件、共享路径/接口、合并点、独立验收。
- build-code 按组派发；每个 Phase 独立开发/测试/审查；合并后只跑针对性集成测试，全局审查留到最后一个 Phase；冲突或失败回串行；不降低验收。
- 验收含正反例：一个可并行组；一个写集重叠必须串行的反例。

### 7.13 build-code 派活与回传

**一张 brief、一次收尾**

- 开发一张 brief；开发完成并明确通知后，审查/测试各一张 brief，可并行；发现回原开发修复，受影响方复验；不新开代理，修复轮不算新 followup。
- 迟到 finding 重开同一 Phase、回同一开发，追加一次审后提交；不丢到终末。
- 主会话批量等待；不 60 秒空转轮询。
- 回传六项：任务；结论与状态；已做与未做；产物/原件引用；失败与限制；下一消费者动作。研究类加来源/覆盖，实施类加改动路径/命令/退出码；未取得写未取得。
- 2000 字限正文；超长落文件 + 5 行摘要；六项仍在开头。

**Phase 角色（固定 3 个）**

build-code 冻结契约：每个 Phase 固定 1 开发、1 审查、1 测试；开发唯一 writer，审查/测试只读。

| Phase 风险 | 3 个角色不变 | 专项轴放在哪 |
| --- | --- | --- |
| UI/交互 | 开发/审查/测试 | 审查加设计/可访问性轴；测试加浏览器 |
| 权限/安全/数据 | 开发/审查/测试 | 审查加安全/数据轴；测试加数据 |
| 性能/外部接口 | 开发/审查/测试 | 审查加性能/合同轴；测试加性能 |
| 多个独立专项面 | 开发/审查/测试职责不变 | 按复杂度安排独立执行者；仅有可独立交付验收边界才拆 Phase |

- 三种职责不限制代理会话数；Standards 和 Spec 补充审查按现 build-code 方法由两个不继承上下文的执行者分别完成，不折进实施者自审。
- 同一 Phase：开发完成并明确通知后，审查/测试可并行；两边回报后开发最后确认；并行量按实际独立输入、写主、工具容量及审查能力安排；历史建议不升级为人数硬上限。
- 不新增常驻团队角色：readiness 任务级做一次；oracle 由测试作者在 Phase 卡内完成；preparation 并入开发 brief；review_host 只做 OCR 长等待宿主；standards/spec 每 Phase 必派独立同源轴，执行者按风险选，不折进同一人。

**审查**

- 每 Phase 主代码审查按风险选择独立子代理或外部 OCR，终末固定外部 OCR；Standards 与 Spec 两个补充面由互不继承上下文的独立执行者分别完成，不能用一个执行者的两栏摘要代替。
- review_host 只做 OCR 长等待宿主，不是每 Phase 角色。
- 同源轴不取消、不折进同一人；执行者按风险选，记录执行者和隔离上下文。
- 不做每 Phase 合并后集成审查；并行组只跑针对性集成测试，该组 diff 由各 Phase 审查覆盖；最后一个 Phase 做全局/OCR。

**主会话上下文**

- 主会话只收摘要和指针；读、测、查、diff、证据、审查都派给子代理；可读指针和验收原件，不做全量阅读。
- 主会话只做五件事：定范围、问用户、处理冲突、最终确认、派发/回收。
- 不空转轮询；没有新事实先停重复动作，按 AGENTS 四类分诊检查根因与更简单方法，继续安全工作。

**记录、时间、合并**

- 每 Phase 复用现有执行清单；C05 结束做一次审计汇总；不新增第二账本；清单字段变更只改 `docs/standard-workflow.md` 的现有表。
- 不做硬预算熔断，也不以时长停；只记录模型/工具/轮次/墙钟；拿不到写未取得。
- 无新事实先停重复动作，不停止仍有解的任务；按现有分诊换方法继续，只有方向/验收改变、用户独占阻塞资源或严重风险才请求用户决定。

**术语**

| 词 | 意思 |
| --- | --- |
| 专项轴 | 按 Phase 风险加到审查/测试里的检查面，不新增身份 |
| OCR | 外部独立代码审查 |
| review_host | 长审查宿主，只做 OCR 长等待宿主，不是每 Phase 角色 |
| readiness | 任务级只读预检，不是每 Phase 代理 |

### 7.15 为读者写

- 正文先写问题和决定，再写场景/任务；一张表只放对照，不把整份文档变成表。
- 机器编号、canonical ID、字段名只在必要定义/附录/Phase 的 Source 对照出现；正文用“需求 1/验收 1/场景 1/Phase 1/任务 1”。
- 每节回答一个读者问题；删掉重复状态、教程式免责声明和为了字段数量凑的段落。

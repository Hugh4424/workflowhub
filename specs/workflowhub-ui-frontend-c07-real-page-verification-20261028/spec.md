## 为什么做，给谁用？

默认的「跑完就写完成」会把没查过的东西说成查过了，所以要一套能举证、能回修的验证能力。

现在的链条有三个漏点。
一是验收被写成「跑两条命令通过」，它只证明代码在场，不证明做对。
二是缺证据时用空结果或聚合分补位，未知就变成了通过。
三是修复没有独立复验，问题在报告里消失，在页面上还在。
这三个漏点合起来，就是用户说的「口头说完成」。
本轮要补的正是这三处：验法先定、独立执行、失败回修重验。

### 做成的结果是什么？

七条页面结果能各自举证，四条方法结果能让下一轮不再只跑命令。

- 真实页面逐维取证：每维有判据、原始结果与未覆盖说明。
- 采集与身份对得上：错工作区、错服务、错状态或未启动都能报具体不一致或 unavailable。
- 适用反例有检测与真实修复；200% 缩放与键盘、焦点顺序必测。
- 分级可重复：同一明确数值 diff 用同一标尺得出同一档；
  校准集是三条还原偏差负例加一条阻断档负例。
- 回修闭环：模糊反馈先定位再修；修复后由同一独立角色复验；轮次与停滞可解释。
- 失败不伪装成通过：unknown、非法耗时、失联采集、证据错配都不聚合成高分或通过。
- 对象两条腿可追溯：资产层、代码组件层、页面布局与真实操作分别可追溯。

## 每条需求怎么验收？

每条需求都写观察什么、什么算成功、什么算失败、要什么环境与数据、谁判。

本轮新增 8 条需求（需求 44 到 51），对应 4 条方法验收（验收 8 到 11）。
页面需求每条只引它承接的验收，通过条件仍只在 Appendix A 写一次。
写「谁判」时区分三种人：开发自己、独立测试或审查子代理、产品验收者。

### 需求 1：判据可执行、覆盖多维

需求 1 来自 PRD：交付可执行的多维判据。
观察：判据正文里每一项都有执行方法、正反例与原始结果的落点。
成功：八维逐维可执行，九维按映射归位，照文档能做一次完整检查。
失败：只有概念、表格或检查清单，照它做不出一次检查。
环境与数据：判据正文在 `skills/frontend-testing/references/page-audit.md`；对象是 C05 样本。
谁判：判据 owner 写，独立测试按验收 1 判。
承接：验收 1。

### 需求 2：真实隔离采集与逐项对照

需求 2 来自 PRD：交付真实隔离采集与对照。
观察：浏览器经唯一网关在隔离会话里采到真实输出，再与判据逐项对照。
成功：身份块齐、原始输出可回读、跨引擎读数不混在同一张表里。
失败：绕过网关直连、混用两个引擎、只给汇总结论。
环境与数据：`isolated-browser-qa` 网关；样本服务与真实 viewport。
谁判：采集执行者产事实，独立测试按验收 2 判。
承接：验收 2。

### 需求 3：写清范围与失败表达

需求 3 来自 PRD：交付范围及失败表达。
观察：报告写出覆盖范围，未见、未测、失败三类分开。
成功：四态齐全，范围有具名限制，失败有原因与所在对象。

## 做成什么样？

十一条验收各有场景、通过、失败与证据四段；页面七条含义不变，方法四条本轮新增。

通过条件只在 Appendix A 写一次；本节给读者能看懂的场景与反例。
每条最后写「拿不到怎么办」，因为缺证据时最容易写成通过。

### 验收 1：真实页面逐维取证与未覆盖说明

验收 1 要的是真实页面九维与其它适用质量面有逐项判据、原始结果及未覆盖说明。

场景 1、场景 8。
对象是 C05 样本（页面层）或受控测试页（只作校准）。
三宽 1440、1024、640；A 有十态与 `stress=1`，B 有十态加权限四值加角色两值。

通过：八维逐维、第 5 维内九维逐项都有判据与原始结果；每处缺失写明未覆盖及理由。
主副维归属可用映射表复核，且无重复计数；pass 只出现在全范围通过处；所需来源与证据齐备。

失败：任一维无结果却计通过；用截图、首屏、总分或组件故事替代全部；
同一问题在第 5 维与第 3、6、7 维重复计数；未覆盖只写「未覆盖」不给理由；
无设计源却声称视觉还原已验。

证据：逐维结果表，加原始采集输出（几何、渲染、console、network、性能原始值），加未覆盖说明；
单份或单组可回读原件。

判定与承接：判定器、组名与用例见 Appendix A 的验收 1 一行；由测试或审查子代理执行，开发者不自审。

拿不到怎么办：缺对象或缺引擎时记 unavailable 或未测，不代填，不写通过。

### 验收 2：身份对不上时报具体不一致或 unavailable

验收 2 要的是错工作区、服务、源或状态，或未启动时，能报具体不一致或 unavailable。

场景 2。
对象身份与声明不符、服务未启动、route 或状态不是声称的那个，或采集引擎发生回退。

通过：不一致项被具名报出并停在该对象；未启动报 unavailable；
回退事实写进身份块且选定后未再切换；可观察部分保留为事实；空输出与旧截图未用于通过。

失败：错环境被报通过；未启动仍出结果；未跑视觉记通过或记失败；旧截图或空输出冒 pass；
静默换引擎冒充同一事实；回退后仍按原引擎口径出结论。

证据：身份块、不一致清单、引擎回退记录、采集失败记录，均为可回读原件。

判定与承接：见 Appendix A 的验收 2 一行；用「一处人为不一致加一处未启动加一次回退」三类输入。

拿不到怎么办：记 unavailable 并写明缺哪件输入。

### 验收 3：压力与交互反例的真实检测与修复

验收 3 要的是适用反例有检测与真实修复，200% 缩放与键盘、焦点必测。

场景 8。
九类反例：64 位哈希浮窗、长文本、窄容器、缩放、滚动或遮挡、hover 桥、
键盘与焦点、减少动效、错误或权限或重复操作。
状态面取十态：默认、加载、空、错误、取消、边界、权限、重复操作、部分成功或结果未知、恢复。
压力面取长文本、窄容器、滚动与浮层遮挡、hover 桥与减少动效；数据真实性按样本，不据夹具推真实业务。

通过：适用反例有检出与修复证据，修复前后可对比；合法例与不适用项各有依据；
200% 缩放与键盘、焦点顺序有实测结果；`file://` 直接打开样本页有实测输出；

## 打算怎么做？

六块按依赖顺序做，每块写清干什么、为什么、怎么验、失败怎样。

六块是判据、采集、分级、判定与报告、回修、交付证据。

### 方案 1：判据与结果契约

本方案定下页面上判什么、按哪套维度、结果怎么表达、判据接到哪里。

干什么：页面检查只有一套骨架，就是 C05 的八维。
八维是业务任务、信息架构与导航、交互状态、内容数据、视觉规范、响应式布局、无障碍、真实代码交接。
PRD 的九维不另立体系，整体作第 5 维的子检查，按映射表归主维与副维。
每个检查项只取四态：通过、失败、未测、不适用；不适用必须写依据。
报告逐项表达结果，不设总分，不新开材料键，沿用现审查的 finding 字段。
判据正文只有一处，接进三处既有链路：`plan-design-review` 的页面模式、
`frontend-testing` 的指针节、build-code 的冻结前审计。
触发按改动面与交付声明判定：改了页面、路由、组件、样式或任务声明 UI 交付就走，不确定默认走。

为什么：两套维度并列会让同一问题记两次，缺陷数虚高，读者也不知道以谁为准。
四态与「pass 只在全范围」是防假绿的底座；没有它，未测会自动变成通过。
总分则把未知抹成一个看起来不错的数字。

九维怎么归位：主维判成败，副维只补证据，同一问题只在一个主维记一次。

| 九维项 | 主维（判成败） | 副维（只补证据） |
| --- | --- | --- |
| 布局 layout | 响应式布局 | 视觉规范 |
| 字体 typography | 视觉规范 | 无 |
| 颜色 colors | 视觉规范 | 无障碍 |
| 间距 spacing | 视觉规范 | 响应式布局 |
| 阴影、边框、圆角 | 视觉规范 | 无 |
| 图标 icons | 视觉规范 | 无障碍 |
| 状态 states | 交互状态 | 视觉规范、无障碍 |

### 方案 3：分级、校准与停止

本方案定下怎么把偏差定成可复核的档位，什么时候必须停，什么情况升级给人。

干什么：严重度只有三档：阻断、重要、次要；对应 critical 到 blocking、moderate 到 major、minor 到 minor。
处置沿用现有词：已修、驳回、接受风险、需人定、用户已定；复验结果单独记，不写回原 finding 正文。
校准负例至少三条，都是「明显偏差但任务仍可完成」：
字体 20 到 17 px、间距 16 到 8 px、颜色 `#1A73E8` 到 `#3A83E8`。
同一明确数值 diff 用同一标尺跑两次必须同级；三条负例必须落重要档。
MINOR 由规则判定，不要求用户签认，报告只写「按某规则接受」。
预算停止只说明执行因预算终止；停止原因分开记：工具失败、产品缺陷、资料不足、权限不足。
未测不计通过。
只升级会改变方向、范围、验收或要用户担风险的事，攒批并给一句「不问会怎样」。

为什么：没有校准负例，「重要」就是随手给的档。
把自动判定写成用户确认，等于伪造同意。
性能不进定级阈值：它只报原始值与 unknown，不设通过线，三档不吸收耗时数值。

### 方案 4：判定、性能与报告消费

本方案定下数值与观察怎么互补，性能与业务成功怎么判，报告怎么被下游消费而不吞未覆盖。

干什么：数值、几何与渲染事实，和独立观察事实，两路并排记录；分歧保留复核记录，不取平均。
性能是第 3 维下的「运行性能」子组，不单设维度，也不塞进第 7 维。
性能只报原始值与 unknown。
导航三计时是 ttfb、domContentLoadedEventEnd 与 loadEventEnd。
每项各跑三次取中位数。交互用 `performance.mark` 与 `measure`，
另记超过 50 ms 的长任务次数与最长值。
业务操作用页面任务脚本加可观察终态判定；HTTP 200、截图或 toast 都不算成功。
角色走查按实际需求做，模拟角色只作状态输入，不冒真人研究。
报告逐项写档位、证据 ref 与未覆盖；页面、状态、视口、对象身份写进证据文字，不新增 finding 字段。

为什么：数值能证明差多少，观察能证明能不能用；一方顶替另一方时，缺失的那一侧会被盖住。
把性能并进定级，会让一个耗时数字变成严重度。

### 方案 6：交付证据与防假绿

本方案定下用外部件之前要先补什么，怎么防「看起来绿」。

干什么：采用外部采集或计算件之前，先修四类真实缺口：

### 证据计划怎么写？

证据计划把判定义务分到已有任务字段，不另建验收计划。

七项是判什么、怎么判、证据从哪来、谁提供、何时能拿到、成本类别、拿不到怎么办；
缺一项不得开工。
拿不到证据时写真实尝试、卡点、提供者与恢复条件，不把缺口记为完成。

证据从哪来=`quality/tests/` 下该次采集的原始输出与身份块；
谁提供=采集执行者；何时能拿到=该 Phase 命令跑完之后；

### 接口与失败语义

输入是 CDP 地址加身份参数，输出是带身份块的事实与四态报告，失败不回空结果。

- **架构**：判据正文一处，形状校验器一处，五个只读采集器，一个编排器；
  接到 `plan-design-review` 页面模式、`frontend-testing` 指针节、build-code 冻结前审计三处。
  不新建技能包，不新增公共命令。
- **职责链**：采集器只产事实，校验器只核形状、不裁决视觉，
  编排器组包并写身份块，审查与终末消费。
  审查者不重跑采集。
- **校验器命令行**：
  `node skills/frontend-testing/scripts/check-page-audit.mjs --input <report.json>`
  退出 `0` 表示形状合法，`2` 表示驳回，其它非零是脚本自身失败，不得当驳回结论。
- **校验器输出**：stdout 恰好一行 JSON，
  形如 `{"ok":bool,"errors":[{"code":"E_...","path":"...","message":"..."}]}`。
- **六类必驳码**：`E_TOTAL_SCORE`、`E_MISSING_EVIDENCE`、`E_MISSING_UNTESTED_REASON`、
  `E_LIMITED_PASS`、`E_UNKNOWN_AGGREGATED`、`E_STATE_OUT_OF_ENUM`。
- **五个采集器命令行**：
  `node <script> --cdp-url <url> --out <json> [--viewport WxH] [--state <名>]`；
  统一输出 `{"engine","observed_at","object","items","failures"}`；
  `failures[].class` 属四类；五个身份值由编排器经五个 `PAGE_AUDIT_*` 环境变量传入，
  不占命令行参数；缺任一项在连接 CDP 前退 2、不写件、不置 `null`
  （见 P5 的「编排器到采集器的身份传递」）。
  `collect-console`、`collect-network` 另认 `PAGE_AUDIT_WINDOW_DIR`、
  `PAGE_AUDIT_TARGET_ID`、`PAGE_AUDIT_WINDOW_ID` 三个环境变量，
  用于同一次导航窗口（见 P5 的「同一次导航的采集窗口」）。
- **失败到状态的映射**：`NOT_STARTED`（服务或页面未起）到 unavailable 加对象未就绪；
  `UNREACHABLE`（CDP 失联）到未测并保留已观察。
- **另外两类**：`TOOL_ERROR`（脚本自异常）到 unavailable，且不得写「未测」；
  `IDENTITY_MISMATCH`（receiver 身份不符）到 unavailable 加修复指引。

# Phase P6 — 九条流程缺口各有固定名与断言，且不新增 stage

读者：本 Phase 的实施者、独立审查者，以及下游的步骤检查器使用者。
读完要能：找到九条固定名落在哪一节、哪条命令判它、失败了交给谁。

> 写作标准：`skills/spec-specify/SKILL.md` 的「十条材料写作标准」。
> 二级标题都是读者问题，第一句直接回答；命令与表格行不受行宽限制。
> 命令、路径、退出码、编号、哈希逐字保留，不因改写而改。

先说明九个会反复出现的词。

固定名：写死在方法正文里的一个短语，测试按它逐字命中，换个说法就不算。
步骤表：`workflows/make-decision/steps.json`，15 步各写观察结果与完成证据。
观察结果：这一步跑完后外部能看到什么，字段名 `observable_result`。
完成证据：这一步留下的原件身份，字段名 `completion_evidence`。
逐模块台账：一个模块一行，记答复、收敛状态与八项证据指针。
收口：本阶段做完时写的三行结论，它不表示下一阶段可以开工。
门禁命令：一条会先红后绿的命令；红是目标断言失败，不是环境错。
判定器：卡末与文件末各写一次的判定编号，判红绿都用它。
测试变更请求：改既有测试断言前写的一份申请，说清改哪条、为什么、反例怎么保，缩写 TCR。

## 这一 Phase 交出什么？

给 make-decision 的九条流程缺口各一个固定名、一句动作、一条断言。

九条都要在方法正文找得到、在步骤表里有同步字段、在契约测试里被钉住。
步骤数仍是 15，阶段标识仍是 make-decision，不新增流程阶段、校验门或检查点。
做法是只加名字与句子：不加步骤，不加门，也不新增第二套进度。

九条依次是：
- 入口四级选择
- 调研决策
- 大纲确认
- 方向审查时点
- 逐模块台账
- 细节审查前检查
- 领域词表读回
- 可核运行清单
- 最终确认即阶段收口

交付四件：
- 方法正文里九条固定名与各一句可核动作。
- 步骤表里对应的同步字段，步骤数不变。
- 决策日志模板与标准工作方法各一处收口口径。
- 一份契约测试：九组逐字断言，加步骤数与阶段标识两条钉死。

这一 Phase 只改 workflowhub 自身，不承接页面验收。
真判据是一次真实走查里九条的效果；门禁先红后绿只是前置，别处不替它签。

- **本 Phase 结果**：九条各有一个固定名、一句动作与一条断言，形状未变。
- **非目标**：不改三个子流程的正文与步骤表，那是各自负责人的范围。
- **改动前**：九条动作真实发生过，却没有名字、没有证据、没有测试。
- **改动后**：名字在指定节，观察结果有同步字段，断言钉住步骤数与阶段标识。
- **与相邻 Phase 的边界**：上游没有；下游是步骤检查器，它继续只读步骤表。
- **主要风险**：把九条写成新流程分支，多加一步就改了阶段形状。
- **下一步**：交步骤检查器与后续材料作者，按九个固定名回读。
- **动手前必读**：方法正文、步骤表、决策日志模板两处、标准工作方法一段。
- **未决事实**：真实答复、词表读回与阶段交接按历史原件观察过，不是新事件；
  第 5、6 条在本任务材料上读不回；页面效果仍未验。

## 为什么现在做，依据是什么？

这九条正落在本任务要走的流程上，等下一轮就等于按缺名的流程走完。

九条都是同一类毛病：流程里有真实动作，却没名字、没证据、没测试。
本次任务剩下的 Phase 与后续任务都要按这套流程走，越晚改越多材料要回改。

为什么这九条必须在本任务做、不能等下一个任务：
- 九条正落在本任务要走的流程上；等下一个任务就等于按缺名的流程走完本次。
- 入口问话、调研决策、大纲确认现在没有固定名，读到的是一条模糊路径。
- 收口三项没有模板落点，「最终确认」会被当成进入下一阶段的许可。
- 用户已把这九条留在本任务实施并登记为范围例外，挪走即改动该决定。
- 若等到下一个任务，本次要带九个未收敛的流程缺口交付，材料先违一次规则。

它不依赖任何 Phase，可以立即开始；只动文档与步骤表，失败面在形状。
它也是唯一动流程的 Phase：后面几个 Phase 改脚本、做验收，都不碰它。

- **依据**：用户把这九条留在本任务实施并登记为范围例外，决定编号见附录。
- **与其它 Phase 的区别**：改流程材料，不改页面，也不改采集器。

## 每张任务卡怎么写？

每张卡先写人读正文，机器字段接在同一张卡末尾，三张卡串行。

卡里回答四件事：谁要什么结果、从哪个输入开始、第一处动作、失败交给谁。
字段从「任务编号」开始，到「完成」结束，共 18 项，人读时可以整段跳过。
三张卡依次排：任务 1 定入口四问，任务 2 定台账与停点，任务 3 收口。
任务卡『来源 / FR / AC』记的是原始来源形态；本 Phase 被判的验收见机器字段『覆盖 AC』。

## 失败了怎么办？

先分清是哪类失败，再按断言红、材料缺件、检查器读不回三类路走。

- **风险**：把九条写成新流程分支，多加一步就改了阶段形状。
- **影响**：阶段形状变化，下游检查器与后续材料按错误形状对齐。
- **缓解**：九条只以固定名加一句动作落进既有步骤，步骤数当断言钉死。
- **回滚**：只撤九条固定名与步骤表对应字段，保留既有 15 步原文。
- **补救与交接**：无法回滚时把冲突那条交原负责人，其余八条保留。
- **触发条件**：测试发现步骤数不是 15，或出现新的一级流程节。

停点三条：
- 某条要求新增步骤才能承载：停该条，保原正文，冲突写进证据交原负责人。
- 步骤表结构变化：停，回检查器维护者确认读取方式，不猜字段。
- 被要求改子流程：停，记无消费者依据，回原负责人。

停不是失败也不是通过；恢复条件是改法落回既有步骤、读回真实字段、取得依据。

## 这一 Phase 怎么验收？

假设本 Phase 全部实现、所有已设计测试也都通过，还会不会漏掉原始需求？
答不出「不会」之前，任何测试通过都不算达成验收。

判据只有一条：真有人按这套方法做出东西，别人能核他做对了没有。
一个 Phase 只有在验收标准真的被满足后才能说开发完成；代码审查通过、测试全绿、结构检查通过，都不是完成条件。

范围只取三行，覆盖实现、审查、验收三类交付；其余九行按同一方法可复制。
代价与上限写在「怎么算做完？」，工时见下一节。

下面先写这次验收要花多少，再七段逐段答；缺哪段就保留缺槽写 `incomplete`。

### 本 Phase 的验收要花多少？

现在约三小时：三行各约一小时；不再要求十二行，原来约十二小时。

| 类型 | 取哪一行 | 这一行交什么 | 为什么选它 | 约多久 |
| --- | --- | --- | --- | --- |
| 实现 | P11 去字面断言 | 可测的代码行为：断言迁走后仍抓坏输入 | 有真实红绿可跑 | 一小时 |
| 审查 | P10 让审查判方案 | 判断力：审者看见决定，判方案而非自洽 | 交付是判断，只能读后复现 | 一小时 |
| 验收 | P8 全 AC 终验 | 判定：七条各给判据与档位，缺则写缺口 | 交付是判定，须外人复核 | 一小时 |

三类交付的形态不同，验法也就不同，所以各取一行。
实现类有输入有结果，判定能落在一次真跑上；
审查类的交付是判断，只能由另一位读者按同一材料复现；
验收类的交付是判定，要外人核它的档位与缺口对不对。
覆盖这三类，就能说方法对不同性质的 Phase 都成立。
其余九行不再逐行实验：已完成的 P1 记额外证据，另八行按同一方法可复制，
由作者在各自 Phase 收尾时按同法判。
P1 行不占这三小时；它与 P11 同类，记额外证据，不替代代表行。
代表行按各自当前字节重跑；P1 的判定跑在更早的夹具上。
P8 这一行只判它的验收材料能不能判出效果，不重判七条页面验收。

- 需要的人：一位作者、一位独立判定者、一位下游消费者；都可以是另一个子代理。
- 作者拿到的：十一条写作标准、三份模板、一条原始需求；不给本任务的材料与答案。
- 作者交出的：一条验收标准，加一个 Phase 验收节；不写三份完整材料。
- 判定者拿到的：作者那条标准、一条绿而错交付、那条原始需求；不读方案。
- 绿而错交付：做一份错变体，核门禁能否拒绝它；加决定性输入与负例。
- 不需要：完全无背景的人、三份完整材料、稳定性长跑、真实用户到场。
- 环境：认证工作树与认证任务原件；临时目录建在工作树外，用完删。
- 判完留什么：作者原文、判定原件、消费记录、门禁输出；缺一件按分档记。

### 效果判据要写严到什么程度？

这条是 meta 标准：判的是 Phase 的验收写得对不对，实质判据来自该 Phase 的原始需求。
七处按 2026-10-31 盲判指出的弱点收紧；缺一条，这一行只算「做了」。

| 弱点 | 收紧后怎么判 | 不算过的样子 |
| --- | --- | --- |
| 消费者只跑真实交付 | 同一场景跑 A 与 B，按原需求拒绝 B | 只用 A 得结果就算过 |
| 判定者只读不跑 | 真跑门禁未见输入与负例，记命令与输出 | 只读代码、只复述门禁绿 |
| 门禁只测单行 | 门禁含决定性输入与负例，A 过、B 拒 | 单行 fixture 的门禁当门禁 |
| 真实 owner 与环境没有替代 | 可用另一位子代理代理，证据标「代理」 | 拿不到真人就记 incomplete |
| 盲包不核 | 盲包带 manifest，逐件核哈希；漏件判无效 | 手递文件、不核哈希 |
| 当成实质标准 | 明写 meta，判据引自该 Phase 的原需 | 拿这条替代原需 |
| 一行推全部 | 只记这一行；其余行按同法由作者自判 | 一行通过写整条 AC 通过 |

门禁最容易被放过：绿而错能过，说明门禁没覆盖决定性输入。
判定者另跑的探针不算门禁；门禁自己不动，这一行就记不合格。

### 场景怎么排，正常和反向各一条？

正例四条，前三条沿用本文件的三条消费场景，第四条是改后复验；第三条按最小实验做。

正例一（送包）。

- 预期：包内三件成员齐，原话首句与四个验收编号逐字在场，丢弃事实为空。
- 算通过：靠包内位置与摘要，不靠模板在场。

正例二（评者）。
- 输入：正例一的包。
- 动作：按真实入口派发一次，等评者的原始输出。
- 预期：每条发现落到包内具体位置，并说出「方案全实现仍漏什么」。
- 算通过：发现原文与位置可核，不是一句「没发现问题」。

正例三（写作效果）。
- 输入：十一条写作标准、三份模板、一条原始需求；
  不给本任务的材料，也不给设计答案。
- 动作：一位没读过本任务材料的作者写一条验收标准加一个 Phase 验收节；
  独立判定者按它识破绿而错，下游消费者同一场景跑 A 与 B 并拒绝 B。
- 预期：判定者写出拒绝理由，理由落在标准原文上；消费者用 A 得结果、用 B 被拒。
- 算通过：作者原文、判定原件、消费记录、含决定性输入的门禁四件齐。
- 只写三份片段不单独算这一条通过。

正例四（改后复验）。
- 输入：作者按有效发现改过的当前字节；零发现时用同一份未改字节。
- 动作：同一位读者重读改处或原读处，并核受影响面有没有变坏。
- 预期：有发现时原问题不再成立；零发现时覆盖范围与未读部分写清。
- 算通过：改前改后两份字节加一次重读原答；不要求复验再发现新漏洞。

反例三条，任一条没被判失败，就说明这套验法本身没起作用。

反例一：字段齐、检查器绿，但每条原需只写编号。
预期判失败：读者说不出每条原需怎么验，缺的就是可失败的反例。

反例二：只跑门禁命令就宣布这一轮做完。

反例三：审查包零发现。

### 谁判，什么时候判？

由与实现者不同上下文的独立执行者判；作者、写手与本卡实施者都不判自己。
作者、判定者与消费者都可就地派另一个子代理；这也让 `unavailable` 基本不该出现。

- 时点：作者标准定稿就能做判定实验；终判要等开发完成、审查问题都改完。
- 上下文：独立会话，只读材料与原件，不问作者要背景。
- 代理条件：拿不到真实下游 owner，就用另一位子代理，证据里标「代理」。
  真实环境缺就用同版本隔离目录，写清与真实的差别；不因缺真人记 incomplete。
- 两类人：一类执行用例并留命令输出，一类只读材料；都不由作者本人充当。
- 判定者不只读：要真跑门禁未见输入与负例，命令与输出进原件；只读代码不算判。
- 作者能给原件与命令；不能替判定者下结论，也不代写判定者的结论。
- 同一人反复当读者时，结论记 `incomplete`，等另一个人来判。
- 判的顺序：先核时点，再核原件是不是当前字节，最后才看结论。

### 失败了怎么回修，怎么重验？

失败信号进分诊，回原 owner 改，再按同一判据重验原问题与受影响面。

| 失败信号 | 分诊 | 回谁 | 重验什么 |
| --- | --- | --- | --- |
| 读者读得出字，说不出首步、输入或失败回谁 | 效果层未成立 | 原作者 | 补一次独立阅读，重判效果层 |
| 判定者没拒绝绿而错交付 | 标准只判了做了 | 作者 | 改标准后重判同一个错交付 |
| 门禁只测单行、绿而错也能过 | 门禁不合格 | 实施者 | 补决定性输入与负例后重跑 A 过 B 拒 |

## 怎么算做完？

核的三条方法验收在当前材料上都要有当前结论，三层证据也要成立。
其中效果那一部分只取三类各一行，不再要求十二行全部通过。

`available`：三类各至少一行走完三件事；本文件取 P11 实现、P10 审查、P8 验收。
`incomplete`：三类里有任一类没做，写清缺哪类、谁做、多久。
做了但只齐两件，也记 `incomplete`，写清缺哪件、下次谁补。

三件事是：

1. 判定者识破绿而错，且真跑门禁未见输入与负例，命令与输出在案。
2. 下游消费者在同一场景跑 A 与 B，按原需求拒绝 B。
3. 该 Phase 的门禁含决定性输入与负例，A 过、B 拒。

先有作者写出标准，才有行可判；这一件归验收 8，见用例一。
整条 AC 不写一个总档位：Done 逐类列出，每行自己记档。
不拿一行顶全部，也不拿一条推「每个 Phase」。
P1 行已齐三件，属实现类，记额外证据，不替代 P11 行。

这样做的代价与上限：
三行不能证明第四行也一定成立；
能证明的是方法对三类不同性质的工作都有效。
其余九行若出问题，由各自 Phase 的验收失败暴露，不靠 P12 预先证明。

只有找不到任何可用的作者、判定者或消费者，才记 `unavailable`。
本仓就地派子代理即可，所以这一档在 P12 基本不该出现。

只做到一部分时，写「未完成」并写清四件事：
试过什么、卡在哪个真实条件、谁提供所需资源、什么条件满足就能恢复。

不算做完的两种常见情形：
一是计划里每条都实现、测试全绿，但没人回答「做没做对、有没有效果」；
二是把某一层的绿当成另一层，例如接入绿就宣布效果成立。

### 三层验收分别看什么？

三层各证各的，谁也不能替谁。

1. 技术接入：八份文件的改动真的被下一份材料的作者读到并照着写。
   证据是真实读者拿到的当前字节，加一次按新模板产出的材料。
   最小实验只证三份模板；另外五份按结构命令与读者阅读记，不假装全证。
   前提是阶段契约读得到机器字段块：读不到就记未完成，见下方未决事实。
2. 材料送达：用户原话与规格里的验收正文真的进了评者的输入包。
   证据是包内文件名、所在行、字节数与摘要；不要求与源文件逐字节相同。
3. 真实写作效果：作者只拿三样输入写出标准，判定者识破绿而错，消费者拒绝 B。
   本轮已实证识破与拒绝 B，原件在盲判目录；门禁已扩到含决定性输入，A 过、B 拒，见 Done。
   接一节由另一位读者做，仍没做。

任一层缺证据时记未完成，不记通过；接入绿不能当送达，送达也不能当效果。

### 什么情况直接判返工？

出现下面任一条，不管测试是否全绿，都判返工，退回原作者。

1. 计划每条都实现、测试全绿，但用户原话里「做没做对、有没有效果」仍无人回答。
2. 借页面验收 5 当方法判据。
3. 把一条门禁命令加一次冷读当成真实评审。
4. 把模板路径或样板路径当成新作者写出的真实下一份材料。
5. 只把处置字符串改成 fixed，最终稿没改，或修后仍用修前的绿。
6. 用身份命令或旧夹具兼容用例冒充当前材料的真实消费。
7. 自造字数或条数配额（例如 300 字、60 字）代替判据。
8. 把模板 P0 自报、问句壳或过程表当成理由；表里登记了更正，当前决定与验收照旧。
9. 删掉原来的强义务换取通过，而不是补齐证据。
10. 拿已删的旧门槛当通过条件，例如完全无背景或稳定写出效果判据。

返工不是补说明：改动退回原作者重做，原失败原件保留，受影响方重新回报。

### 独立预期能不能抓错结果？

能，用一个金额负例就能当场看出差别。

预先是：金额以分存储，查询要返回超过 10 元的记录。
内存输入 500 分与 1500 分，独立写下的字面预期只有 1500。
只验「能执行、返回数组」的候选会放过 500，必须由独立评者指出单位与结果错误并判返工。

做法是：用现有 Python 标准 sqlite3 内存库，先跑坏查询并断言返回等于 `[1500]`。
这条断言应因多出 500 而失败；把条件改成 cents > 1000 后，同输入同预期应退出 0。
再复放一次坏查询，仍应失败；解释器、可用性、脚本、退出码与输出都留原件。

这一步只证独立预期抓得住错误结果。
它不代完整方法消费，也不冒本次方法改前的目标 RED。
它不新增 C07 的 SQL 业务，也不碰 PaperBuilder 与 T03；缺环境就保缺口，不装依赖、不用生产数据。

1. 组一份 approved_spec，设两节：「原需原文（用户原话逐字）」与「当前规格与边界（规格全文）」。

汇编件只做拼接和加标题，不改原文。
每段标来源路径与摘要；不另存规格或本文件的整份副本，避免同字节两份原件。

5. 核摘要派生：宿主绝对路径会被替换成占位符

### 场景 1 怎么把材料送进评者的包？

入口是组包函数本身，它是生产里真正生成评者输入的那一个。

- 入口：`skills/wh-review/scripts/review-materials.mjs:759` 的 buildReviewMaterials。
  生产中的调用包装是 `tools/cli/stage-runtime.mjs:668` 的
  prepareTaskBoundBuildCodeReviewBundle。
- 参数：stage 为 build-code、reviewScope 为 phase、phaseId 为 P12，surface 为 document。
  文档面只改镜与指令，不改成员清单（`skills/wh-review/scripts/review-materials.mjs:780-790`）。
- 输入映射：approved_spec 取上一节的汇编件；acceptance_criteria 取规格 Appendix A；
  test_evidence 取本轮原件清单；三者都带实际摘要。
- 隔离：attachmentRoot 用临时目录函数建在工作树外，是全新空目录。
  不写任务目录、不碰既有包、不读生产数据；材料取自认证工作树与认证任务原件。
- 角色与时点：独立测试者执行；时点是开发交接「实现就绪，待独立审测」之后。
  作者不执行自己的验收。
- 实际动作：把下面的调用写进一次性脚本运行，不落库、不提交。

```js
buildReviewMaterials({
  attachmentRoot: mkdtempSync(join(tmpdir(), "p12-review-")),
  stage: "build-code", reviewScope: "phase", phaseId: "P12", surface: "document",
  materials: { approved_spec, acceptance_criteria, test_evidence },
});
```

- 成功信号：返回的清单含三条成员，且各自的字节数与摘要可读。
  包内 approved_spec 含原话首句与四个验收编号。
  review-instructions.md 含 phase_id=P12 与 surface=document。
  丢弃事实为空，退出 0。
- 失败信号：禁止错误（列出合法成员）、材料不全（指名缺哪条）、
  参数不全错误、关键句缺席、丢弃事实非空。任一条出现即记未送达。
- 反向用例：把原话挪进 raw_requirement 再送同一入口。
  必须看到禁止或丢弃，并且评者侧没有原话。
  坏输入由授权 writer 提供，测试者只读，不改源。
- 证据：命令、参数、工作目录、退出码、标准输出与标准错误的原件。
  还有 `manifest.json`、关键文件的摘要清单、替换次数。
- 清理：调用 dispose 关包，再删临时根目录；不在工作树留包。
- 明确不算：身份命令、只跑旧兼容用例、只看模板文件是否存在。
  这三样都证明不了当前材料进了包。

### 场景 3 写作效果由谁判？

由两位不同上下文的人接力：作者先写一条标准，独立判定者按它判绿而错交付。

- 对象：十一条写作标准、三份模板、一条原始需求；
  不给本任务的材料，也不给设计答案。
- 作者：没读过本任务材料的人，写一条验收标准加一个 Phase 验收节。
- 判定者：另一个子代理，只读作者标准、绿而错交付与原始需求，不读方案。
- 绿而错交付：先过该 Phase 的全部门禁、契约测试、断言与回归，再交判定。
- 成功：判定者识破并写出理由，消费者同一场景拒绝 B，门禁 A 过、B 拒。
- 失败：判定者没识破；消费者只跑 A；门禁只测单行；理由只写命令或字段。
- 证据：作者原文、判定原件、绿而错交付的绿记录、污染说明。
- 边界：判定只能人读，不能由命令代替；不把发现数量当质量门；
  也不要求三份完整材料，那已删，见「哪些旧门槛删掉了？」。

### 撰写实验实测到什么？

这不是第四条场景，只覆盖场景 3 的第一步。

那条 `AC-EFFECT-001` 要求绿而错变体先过该 Phase 的全部门禁、契约测试、断言与回归，

他遇到两处结构性冲突，自评里都写了下来：
一是规格验收块只有四个标签，没有「环境与数据」「谁判」「承接」，只能折进别处；
二是 Phase 的 `gate_cmd`／`Done` 要求一条命令重放，语义判定写不成命令。

### 任务 37：按原话逐段验收本轮方法，并判它到底做完了没有

材料作者需要一条能挡住口头完成的判法，本卡交付这条判法在本轮的实测结果。
输入是三条方法验收的判据、八份文件的当前字节和三条消费场景的原件。
第一步是取用户对验法的答复；取不到就按本文件的最小实验先做，不空等。
判定没识破、消费者没拒 B、门禁不合格、或读者指出的问题未修，都算未完成。

为什么要有这张卡：口头完成挡不住，全绿也可能没人回答做没做对。
为什么不验字段齐：字段齐只说明形状对，说明不了新作者写得出验收标准。
为什么看当前字节：旧绿只证明旧字节，改过之后要用新的重跑。
为什么三层要分开：接入绿不能当送达，送达也不能当效果。
为什么要独立读者：作者自己读自己的材料，等于自证。
为什么不再要无背景作者：实验总有污染，本仓也没有真正的陌生人。
为什么删三份完整材料：成本太高，一条标准加一个验收节就够判。
为什么效果层要看首步：说不出首步与失败回谁，说明没有真正接手的证据。
为什么三条场景要真跑：只写场景等于没验，跑过才留得下原件。
为什么缺口要写四件事：只写未完成，下家不知道卡在哪。
为什么不设字数或条数配额：配额能凑，判据不能。
为什么返工要退回原作者：补一段说明不改材料，问题还在。
为什么本卡没有目标 RED：纯文档流程没有改前的红，只有可复放的结构检查。
为什么失败原件要留：修后拿旧绿充新绿，是这一卡最常抓到的假完成。
为什么判据分歧要交用户：这不是本卡能自己改的事。

三层证据的取法：

| 层 | 谁提供 | 什么时候取 | 拿不到怎么记 |

| 材料送达 | 组包与评者两侧 | 送包后、评者读前 | 未完成，写缺哪份文件 |
| 真实写作效果 | 作者、判定者与下游消费者 | 标准定稿后 | 未完成，写缺哪次判定或消费 |
| 独立预期 | 评者自己写 | 场景开跑之前 | 未完成，写缺哪份预期 |

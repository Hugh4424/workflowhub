# Phase P10 — 让 build-plan 审查看得见决定，并判方案而不是判自洽

## L0 — 结果与变更

### 这个 Phase 做什么

P9 管"材料怎么写"，本 Phase 管"审查怎么审"，两者判定对象不同。
P9 判作者写得对不对；本 Phase 判审查能不能发现方案问题。
合在一起会让两个闸门互相顶替，所以单独成 Phase。
它只改审查包的剖面、审查轴与一次重跑，不改页面审计的七条验收。
依据是用户 2026-10-29 的指示，决定正文在 `decision-log.md` 的 2026-10-29 追加节第六节。

### 交付什么

- 审查包多一个决定基线位，长文档降为可选摘录。
- 四条判断类审查轴替换原来的自洽检查，finding 必须带替代方案与覆盖范围；文本自洽交给脚本。
- 一次重跑与前后对照，用 finding 分布与覆盖范围判改造是否成立（允许零发现）。

### 为什么现在做

现在做，因为审查现在只能对着规格自己跟自己比。
包里放了 20 万字的原始需求全文，却没有已确认的决定与用户答复（`2026-10-29-032` 第 2 节）。
漏检归因也已定位：指令轴缺、finding 只收最小修复（`2026-10-29-033` 第 3 节）。
所以先换材料与指令，再谈模型；加模型路数不会让审查变聪明。

### 风险、回滚、停点

最大的风险是改审查剖面会影响所有任务，不只是本任务。
- 触发条件：剖面 required 或 forbidden 清单变动；影响是其它任务的下一次组包会缺件或被拒。
- 缓解：旧请求件必须仍能通过，五例测试里专门留一例；新件缺基线必须被拒，另留一例。
- 回滚：按卡回退剖面与 schema，保留脚本与测试；恢复条件是旧件重新通过。
- 补救：无法回滚时把剖面交原 owner 与独立审查者裁定。

停点两条：历史请求件不再被接受，停回任务 1；新审查零发现又写不出覆盖范围说明，停回任务 2。
方向判断：provider 仍给不出方案级意见时，下一步换的是指令与材料，不是加模型路数。

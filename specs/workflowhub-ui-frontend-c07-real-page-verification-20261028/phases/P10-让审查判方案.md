# Phase P10 — 让审查看得见决定，并判方案而不是判自洽

读者：本阶段的实施者、独立审查者，以及下一次 plan 审查的使用者。
读完要能：找到改哪十一个文件、凭什么判红绿、红了交给谁、本阶段不签什么。

> 写作标准：`skills/spec-specify/SKILL.md` 的「十条材料写作标准」。
> 二级标题都是读者问题，第一句直接回答；命令与表格行不受行宽限制。
> 路径、哈希、字节数与编号逐字保留，不因改写而改。

先说明七个会反复出现的词。

阶段：这份计划里的一步，本文件只写其中一步。
审查包：交给审查者的一组材料加一段指令，一次审查只组一包。
剖面：组包器按阶段决定「取哪几样材料、哪几样必投」的那份清单。
决定基线：把已确认的取舍、用户答复与理由摘出来，单独成一包材料。
审查轴：让审查者照着问的一条问题方向，本阶段换成四条。
finding（发现）：审查交回的一条问题，本阶段要求它带替代方案与覆盖范围。
provider：真正读包并作答的外部模型服务。

## 这个 Phase 解决什么问题？

让审查看见已确认的决定，并判方案对不对，而不是拿规格跟它自己比。

阶段 9 管「材料怎么写」，本阶段管「审查怎么审」，两者判的对象不同。
阶段 9 判作者写得对不对；本阶段判审查能不能发现方案问题。
合在一起会让两个闸门互相顶替，所以单独成阶段。
它只改审查包的剖面、审查轴与一次重跑，不改页面审计的七条验收。
依据是用户 2026-10-29 的指示，决定正文在 `decision-log.md` 的 2026-10-29 追加节第六节。
本阶段不承接页面验收：它改的是 workflowhub 自身，真判据是下面的门禁命令。

## 这一 Phase 交出什么？

交一个能装决定基线的审查包、四条判断轴，加一次同输入可比的真实重跑。

- 审查包多一个决定基线位，长文档降为可选摘录。
- 四条判断类审查轴替换原来的自洽检查。
- finding 必须带替代方案与覆盖范围；文本自洽交给脚本。
- 一次同输入重跑，用 finding 分布、已知缺陷与覆盖范围判改造是否成立。

本阶段自己不做页面采集，也不签页面验收。
它把「审查被要求看什么」改掉，并留一次可核的同输入重跑。
工作包声明：本 Phase 不在 11 个工作包里；它按本轮方法要求改审查判方案。
四件不做：
- 不改页面审计的七条验收。
- 不把决定日志全文塞进包，只放摘要加引用。
- 不换 provider，也不加模型路数。
- 不改 spec 与决定日志这两份材料。

## 这一 Phase 怎么验收？

本 Phase 的验收要花多少：人工约两小时，机器约三十五分钟。

| 花在哪 | 谁做 | 多久 |
| --- | --- | --- |
| 重跑一次同输入审查 | 本阶段实施者派发，真实审查方出发现 | 机器约二十五分钟 |
| 在重跑与既有原件里核已知缺陷 | 本阶段实施者 | 人工约半小时 |
| 挑一条真发现派回改稿 | 该卡写主改一处，本阶段只收 diff | 人工约半小时 |
| 只投两张卡复验一次 | 本阶段实施者派发，独立读者照原判据读 | 机器约十分钟，人工约一小时 |

合计就这三件事：一次审查、一次改稿、一次复验；不另造样张，不做第二次全量审查。
缺的两步已在 2026-10-31 做成：一次改稿、一次两卡复验；依据见 Done。

假设本 Phase 全部实现、所有已设计测试也都通过，还会不会漏掉原始需求？
答不出「不会」之前，任何测试通过都不算达成验收。

判据不止一条：先要真跑一次真实审查，拿回能指到位置与后果的发现。

发现要能落到具体位置与后果，例如「方案全实现仍漏原需」。
只看四轴字段在不在、组包成没成，判失败。

按 AC 正文的效果定，三档只取一档。

三步是这次真正要做的验收面，逐条给怎么观察、什么算过、什么算没过。

① 就地已知缺陷被检出：拿仓内已有缺陷当输入，审查至少指到其中一条。
   三条候选都在仓内，位置与后果已经写死，不必另造样张。
   甲：P2 的回退只测「没装」一种，缺决定 24 的「装了没开」，
   位置 `phases/P2-真实采集与失败语义.md:74` 与同文的 `:101`。
   乙：P4 的受控副本只初始化，九类检出、修源与复验没跑，
   位置 `phases/P4-报告接入与回修闭环.md:288`、`:289` 与 `:915` 的 Done。
   九类清单在 `tests/fixtures/page-audit/defects.json`，P3 的 Done 也记两条 incomplete。
   丙：P4 的依赖只写 P1，漏掉直接上游 P3，位置同文件 `:292`。
   算过：finding 的锚点落到上述任一处，且后果说的是同一件事。
   算没过：只在别处给意见，或只说缺字段、格式不符这类文本层问题。
   这条已有原件：#16 锚点命中 P4:292，S2 指 P2:74，S4 指 P4 的九类未修。

② 挑一条真发现，回 writer 改稿一次。
   挑改动最小的一条：丙在 P4 依赖里补 P3，甲补一条回退场景。
   改由该卡写主做，本阶段只派回、收 diff 与回执，不代改别人的卡。
   算过：diff 只动该 finding 那处，同行不留旧措辞。
   算没过：改到别处，或把 finding 读成一句措辞建议。

③ 只投两张卡复验一次。
   第一张是改稿那张卡；第二张是它正文指名的下游卡，指名不到就只投一张。
   不跑全量审查，不重投 24 个文件。
   算过：原 finding 位置已无该问题，同根另一处没有旧措辞残留。
   算没过：原 finding 仍在，或改稿引出新的同类问题。

- 三步齐：`available`。
- 任何一步没排上：`incomplete`，写清缺哪步、谁来做、下次什么时候做。
- 审查入口或 provider 客观不可用：`unavailable`，写清谁提供、恢复条件。

审查跑在真实材料上，不跑在自造的合法夹具上。
就地已知缺陷本来就是真实材料，不是另造的夹具。
夹具绿只证明形状，不证明这次审查看见了方案。

空发现时怎么判，两种读法分开写。

不能由单次零发现判「真没问题」；先判链路有没有在工作。

- 已知缺陷被指到：链路在工作，本轮零发现读成「已读范围内没报」。
- 三条已知缺陷一条都没被指到，也没有别的真发现：审查没起作用，
  记 `unavailable` 并写原因，不写成通过。
- 零发现又写不出覆盖范围与未读部分：判无效，回原 owner 补。
- 把零发现直接写成「方案没问题」或写成通过：直接判失败。

已读范围内没报，也不等于没有漏洞；结论只到「该范围内没发现问题」。
本轮真实情况按这条判：kimi/pro 记了规格与全部阶段卡已读，其余三类记 undetermined。

### 场景怎么排，正常和反向各一条？

正例三条，一条真实请求、一条就地已知缺陷、一条同输入重跑；反例三条专抓「组包成功就算过」。

正例一（真实请求）。
- 输入：既有请求件
  `quality/evidence/build-code/2026-10-30-p10-real-review/request.json`。
- 动作：用真实入口再派发一次，或在既有原件上直接核。
- 预期：至少一条发现指到甲、乙、丙之一的位置。
- 算通过：发现原文里的位置、后果与替代方案三样都在。
- 花了多少：机器约二十五分钟，人工约半小时。

正例二（就地已知缺陷）。
- 输入：`phases/P2-真实采集与失败语义.md:74`、`phases/P4-报告接入与回修闭环.md:288`。
- 动作：不另造样张，直接在重跑结果与既有原件里找这三处。
- 预期：至少一处被指到，且说的是同一件事。
- 算通过：锚点落在同一行或同一处主张，不是同一张卡的别处。

正例三（同输入重跑）。
- 输入：同一份 request.json 与同一批 provider。
- 动作：重跑一次，把两轮的 finding 集合逐条比。
- 预期：上一轮的真根因再现，条数差能被 provider 可用性解释。
- 算通过：两次的来源、可用与不可用都写明，不把条数增多归因成改造提升。
- 这条只记事实，不卡档位；跑不动记未取得，不影响三步。

反例三条，任一没被判失败，这套验法就没起作用。

反例一：组包成功、成员齐，就当审查通过。
预期判失败：包能装不等于评者读到了，更不等于发现有效。

反例二：零发现，不写覆盖范围。
预期判失败：这是本次最容易被当成通过的样子。

反例三：把旧请求件当新件投。
预期判失败：旧件要按历史边界投并披露缺基线，不补假标记。

### 谁判，什么时候判？

由独立审查方给发现、独立读者判三步；本阶段实施者不判自己派的那一轮。

- 时点：每次派发之后立刻判，不等别的阶段，也不等下一次 plan 审查。
- 上下文：派发方与评者不同上下文；评者只读包内材料，读不到包外的东西。
- 分工：评者给发现；判者只判三件——已知缺陷指到没有、改稿只动那处没有、
  复验里原 finding 消失没有。
- 判的范围只有这两次派发：一次重跑、一次两卡复验；不判全量审查够不够。
- 作者能给包、指令与命令；不能替评者写发现，也不能把零发现改成通过。
- 同一人既改材料又判效果时，结论记 `incomplete`。
- 判的顺序：先核输入是不是同字节，再核改稿 diff，最后才看复验的发现。
- 工时按上一节那张表；超出表内的判读不做，记 `incomplete` 并写下次时点。

### 失败了怎么回修，怎么重验？

失败信号先分诊，回原 owner 改，再按同一判据重验原处与同根另一处。

| 失败信号 | 分诊 | 回谁 | 重验什么 |
| --- | --- | --- | --- |
| 包内成员齐，正文却没进包 | 材料侧 | 组包人 | 补正文后重派一次 |
| 零发现又写不出覆盖范围 | 效果未成立 | 派发人 | 补覆盖说明后重派 |
| 四轴在，发现只讲文字自洽 | 判据没换 | 指令作者 | 换指令后重派 |
| 三条已知缺陷一条都没被指到 | 检出没成立 | 派发人 | 换同输入重跑一次，仍不中记 `unavailable` |
| 改稿动了别处或留旧措辞 | 改法错 | 该卡写主 | 回到那处最小改，再收 diff |
| 复验里原 finding 还在 | 改稿没生效 | 该卡写主 | 确认改的是同一处再重验 |
| 改稿引出新的同类问题 | 影响面没看 | 该卡写主 | 只在那两张卡内补一处，不扩大 |
| 修后仍用修前记录 | 时点错 | 实施者 | 用当前字节重派一次 |
| 旧件被当成新件投 | 版本错 | 派发人 | 按旧边界重投并披露 |

复验只投两张卡：改稿那张，加它指名的下游卡；指名不到就只投一张。
结论只写新结论、原件与时点；旧的绿标为历史，不叠成两条。
改判据求绿算返工；方向或判据分歧交用户。
失败原件不删不覆写；修后用新字节重派，不引用旧记录。

### 任务 2：四条轴替换自洽检查，finding 必须带替代方案

审查合同要给审查者四条判断轴，而不是六条自洽检查。

为什么换轴：自洽检查落到 finding 上全是「这两行对不上」。
为什么把自洽交给脚本：脚本会沿引用对齐，模型不会。
为什么两路指令必须分工：同包多路不等于独立视角，分工才是。
为什么两路要各自点名自己的轴：不点名，两路就会答同一道题。
为什么 finding 要带替代方案：只说不行，方案负责人拿不到下一步。
为什么覆盖范围必填：不知道看过哪些材料，结论就没有边界。
为什么删掉那句「不要加需求」：它把替代方案一起挡掉了。
为什么用真实派发核两路：静态字符串在场，不代表真的分了两次包。
为什么不自造一个检查器：自造的会照抄假设，真实派发才是观测。
为什么不动结果 schema：五项承载在既有字段里，加字段等于改合同。
它证明不了两路指令的措辞将来不会被改写：只证当下文本。

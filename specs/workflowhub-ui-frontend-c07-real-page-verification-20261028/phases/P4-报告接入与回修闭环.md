# Phase P4 — 把页面审计接进 build-code 的冻结前与终末，并把报告消费与回修闭环写成可执行契约

## L0 — 结果与变更

### 这个 Phase 做什么

把页面审计从技能里的方法变成 build-code 的固定动作。
冻结前必须正式审一次；终末只复核四项，不重跑全量。
给审查镜头一条消费规则：按四态与覆盖边界读摘要，不新增字段。
把回修闭环写成顺序：定位、路由、最小修复、独立复验、三轮或一轮无新增即停。
本 Phase 接方法与测试，并在自有样例复现、修复一处真实缺陷。
受控演练另由本 Phase 初始化单文件工作副本；待 P8 真检出后回本写主修同源。
开发观察不替代后置独立复验。

### 交付什么

交四件东西：
- build-code 三处接线：触发句、冻结前插入块、终末复核半句。
- 触发词扩一处：前端测试条目的适用面加上浏览器可见页审计。
- 审查镜头新增一节「页面审计摘要消费」。
- 一条静态契约测试，把弱断言加强到同句同块。

### 为什么现在做

编排 Phase 要读到「什么时候必须审」的措辞，末验收要按终末四项复核取证。
方法接线依赖 P1 的报告形状；样例回修另依赖真实构建、静态服务与浏览器观察。
它不等待编排完成，也不把开发观察当独立验收。

### 定位与分流：从报告到责任方

验收 5 要"定位到页面、元素、状态与 owner"。只写文字不算，这一段给可执行的步骤，
把报告里的失败行变成带 owner 与去向的分流清单。它不改任何判据，也不碰报告生成端。

输入只读正式审计报告 JSON，由 P5 的实际 producer 回执定位原件。
取唯一 `criteria[]` 中 `state` 为「失败」或「未测」的行。
真实环境失败由其依赖判据与 `coverage_limits[]` 承接，保原失败引用。
不把不适用理由混入失败加未测的条数。

四步，按顺序跑：
一、定位：先按正式形状核报告，再逐行输出对象与判据事实。精确命令为字数例外：
```sh
node -e 'const r=require(process.argv[1]);if(!r.object||!Array.isArray(r.criteria))throw new Error("report shape");for(const c of r.criteria.filter(x=>x.state==="失败"||x.state==="未测"))console.log(JSON.stringify({id:c.id,dimension:c.dimension,criterion_state:c.state,page:r.object.route,page_state:r.object.state,viewport:r.object.viewport,evidence:c.evidence}));' <报告>
```
由各 `evidence[]` 的原件补元素、文件行与根因；没有观察就写具体未取得，不能从 ref 路径猜事实。
分流 `items[]` 保上述来源、定位与后续类别/owner/去向；它是派生清单，不改原报告。
二、分类：按原件事实只选一类。①代码缺陷：原页面失败已定位到代码 owner；②运行诊断：原件证明 NOT_STARTED／UNREACHABLE／TOOL_ERROR 等执行失败；③设计源缺口：所需设计源不可读；④判据或规范缺口：norms_missing 或判据正文缺项。
原件不足以定类时保 `incomplete`、缺证与承接者，不为自检猜类别。
三、路由：①代码缺陷 → 原代码 owner，在本 Phase 已准副本与必要源补集回修；②运行诊断 → 环境 owner 与 P8 环境就绪/真实执行组；③设计源缺口 → 设计 owner 补源；④判据或规范缺口 → P1 判据 owner，规范类另给 P5 T014 未测行。
四、产出分流清单：用认证普通记录保存 JSON 与 Markdown 原件，后续引用实际原 ref。
Markdown 列为 `id | 类别 | owner | 去向 | 证据 ref | 处置`。
`items[]` 条数、清单数据行数与报告失败加未测条数三者相等，少一条记 `incomplete`。

可核判据三条，缺一条这一段不算做完：

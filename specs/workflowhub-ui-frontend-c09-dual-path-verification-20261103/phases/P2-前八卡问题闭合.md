## 这一 Phase 交出什么？

二十条问题逐项有位置、影响、责任与处置；修复项有同一命令的前后对照。

- **本 Phase 结果**：二十条逐项有处置，处置有四种——修好、随 C08 解决、经用户授权缩减、作废。
  修复项能跑；缩减项记理由、影响与恢复条件；作废项记原判不成立的依据。

  干净环境复跑前验收 2 只能 incomplete，不得 pass，整轮不得记完成。

### 七个槽

1. **验收标准**：验收 2（AC-P02）按 spec 两句话合读——二十条逐项有证据、影响、责任与处置
   （检查表句），处置为修好的项，修复后同一命令能跑且退出 0（场景句）；第 6 项例外见下。
   处置有四种：修好（有前后对照）、随 C08 解决（有路径与提交）、
   经用户授权缩减（有逐项理由、影响、owner、恢复条件）、作废（有原判不成立的依据）。
   分母口径是 20 ＝ 15 修好 ＋ 2 随 C08 ＋ 2 缩减 ＋ 1 作废；授权已全部落地。
   通过分母只算 15 修好 ＋ 2 随 C08；缩减与作废单列未覆盖，不得写成已修。
   成功是：四项处置逐项有据、八卡五面矩阵无缺项、档位表与真实状态一致。
   但 `npx vitest run skills` 仍有 18 个无关失败文件，
   干净环境复跑前 AC-P02 只能 incomplete。
   缩减与作废是分母变更，不是判据放宽：由用户 2026-11-03 逐项答复，
   必须在首判与 P6 报告里写明，不能由本 Phase 自行宣布。
   失败是改判据绕开根因、把缩减或作废当豁免或写成已修、
   只修阻断项、五面缺项，或把「二十项全部修复」写成完成。
2. **场景**：正常场景按任务 8 逐项复现、处置、留对照，再由任务 9 审查与抽查。
   反向场景一：只修三个阻断项，其余直接写「已修」，必须判失败。
   反向场景二：把断言改宽或删掉求绿，必须判失败并保留原断言。
   反向场景三：改到写集外的路径，`git diff --name-only` 必须抓到并判失败。
   反向场景四：缩减项不写理由、作废项不写依据或直接当通过，必须判失败。
   反向场景五：`npx vitest run skills` 仍有 18 个无关失败却记 AC-P02 pass，必须判失败。
3. **环境与数据**：环境是认证工作区、本机 npm 与既有测试面；
   数据是二十条清单、真实入口文件与 C08 当前状态。
   允许安装清单点名的开发依赖，只进开发环境，记版本与回执；
   证据件保留，不删；依赖装不上时该项记 `unavailable`，不拿旧结果顶。
4. **用例**：`CASE-P2-1` 对应任务 8，逐项命令见卡内处置表与「怎么验证」；
   `CASE-P2-2` 对应任务 9，跑审查与抽查。
   判定方式以同一命令的修复前后退出为主，入口是否被真实消费只能人读；
   命令退出 0 只证明该项能跑，不证明方法更好。
5. **谁判**：由未参与修复的独立审查者判定；抽查由另一独立读者执行。
   执行时点：任务 8 完成、审查问题改完之后；首判一次，P6 末验只读回放。
   判定者拿到二十项对照、清单原文、写集 diff、档位表与复跑命令；
   不改验收标准、不改实现。
6. **失败回修与重验**：失败信号是前后对照缺失、修复项非零、
   缩减项无理由、作废项无依据、越界改动或档位不符。
   先由主会话分诊：修复问题回任务 8 的 writer，审查问题回任务 9；
   修后重验原项与受影响面，结论按新原件改，由原审查者重报。
7. **承接**：结论写在 `quality/reviews/P2-T009-independent-review.md`、
   `quality/evidence/P2/AC-P02-first-judgment.md` 与任务 9 的「完成」字段；
   P6 读这三处写报告，P4、P5 读修好的入口。

**效果类判据（语义判定，不是命令退出）。**

- **判什么**：独立读者只按清单与回执，自己复跑 5 项，能判断修复项真能跑、
  缩减项真改不动且理由成立、作废项原判确实不成立。
- **谁判**：未参与修复的独立读者，与实施者和审查者都不同上下文。
- **怎么观察**：干净 shell，按清单位置与同一命令复跑；不看修复者自述；
  复跑结果与回执一致算过，不一致或需要修复者解释算没过。
- **证据落点**：`quality/tests/P2-T009-spot-rerun.json`，
  记读者身份、5 项编号、命令、退出与原话；通过记 `pass`，
  未执行记 `incomplete` 并写约定时点。

   验收 3：六段都有原件或具名缺口，每段有下游读取证据，接缝逐条具名，
   独立读者抽查两条需求能沿索引找到决定与落点。
   验收 4：采集字段齐且可复算；提炼不可用时记 `incomplete`，
   不得 pass；原型能起能点；
   渲染与截图在场；八维审查齐全；finding 有修复复验；答复对应本次稿。
   验收 5：红绿两次回执同判定器；diff 与消费者可读；审查与复验齐；
   构建与启动成功。
   验收 6：审计报告八项身份齐，每条判据有引用或未测理由；
   会话说清引擎、路由、视口、控制台、截图与清理；
   有稿业务链六段与 409/404、取消恢复、重启持久、库外证据、
   隔离与清理齐；有真实失败项时五段链完整；零失败项时完整覆盖
   加独立复核即通过，五段回修记 N/A 并写理由，不逼执行者造问题。
   验收 7：C08 已合入 17e78a09；设计侧与前端接口侧两类变更各有
   前后对照、影响分析、唯一源、使用点同步、独立定向复验；两类都有
   证据才通过；后续消费按实际来源/需求/使用点核，缺证只对应面记 `incomplete`
   与 owner，不把整链记 `unavailable`；只做一类不通过。
   失败信号分别是：把文件按序当衔接、用静态图当原型、先实现后补测试、
   空发现冒执行、替 C08 造更新、把 实际消费证据未取得当整链不可用。
2. **场景**：正常场景是新侧副本从空壳走到两页可操作，五段各留原件。
   反向场景一：把未确认原型直接实现，任务 14 的输入检查必须拒绝。
   反向场景二：先写实现再补测试，任务 14 的红回执必须缺失或断言不具名，
   检查判失败，不得补一条假红。
   反向场景三：C08 已合入却只做一类变更仍写「已消费」，任务 18 的
   记录必须缺另一类原件，检查判失败；实际消费证据未取得只记该面 `incomplete`。
   反向场景四：T018A 只到 200 不读回、拿生产库或 mock，检查判失败；
   403/运行级取消/订单如实记未覆盖，不冒充已覆盖。
3. **环境与数据**：环境是认证工作区、`NEW_COPY`、本机 Node 与 npm、
   两套浏览器引擎、`UI` 静态服务；T018A 另起仓外 QA root 与
   PaperBuilder 隔离 API 18844（有稿页面仍 3100）；数据是 P1 的十件哈希、
   十六件指纹、261 字节任务文字、四行六列矩阵与事件字段。
   这些由 P1 原件提供，本 Phase 不构造替代数据，也不另造夹具；
   页面审计与视觉只用 P1 冻结的唯一数据原件。
   真实外部环境产生判据时，由任务 16 的审计脚本自动取回报告与会话输出；
   任务 18A 的库外证据只取只读 SQLite 查询，不复制整个 QA root；
   两页各采 1440×900 主视口与 1280×900 辅视口，缺一视口即记未覆盖；
   原件落 `TASK_ROOT/quality/evidence/P4/`，全部保留，不用完删。
   `dist` 与源码的生成绑定不在本 Phase 证明。
4. **用例**：CASE-P4-1 到 CASE-P4-9 与任务 11～18、18A 一一对应，
   命令见各卡门禁字段与「怎么验证」的测试面表。
   判定方式是命令退出码加独立读者复读；命令退出 0 只证明结构可读，
   不证明语义；语义由第 5 槽的判定者按观察协议判。
5. **谁判**：验收 3 由未参与该段执行的独立审查者判；
   验收 4 由未参与设计执行的独立审查者判，答复真实性由用户承担；
   验收 5 由未参与实现的独立测试与独立审查者各判一面；
   验收 6 由未参与实现的验证者判采集，原实施者外的复验者判修复；
   有稿业务链由业务执行者采集、独立验证者复放；
   零失败项时由独立复核者判完整覆盖；
   验收 7 由未参与 C08 实现的本任务执行者与独立复验者判。
   执行时点：对应任务完成、审查问题改完之后首判；
   P6 末验只读同一原件与必要复放，不重新判标准。
   判定者拿到：对应卡的原件、`spec.md` 的验收 3～7、矩阵与定义；
   不改验收标准、不改实现。
6. **失败回修与重验**：失败信号是六段缺读取、采集缺 plan、原型不可运行、
   红绿不同判定器、审计身份缺项、五段链断裂、更新链造假。
   先分诊：材料与流程回阶段四执行者；设计源与引擎回对应 owner；
   代码回原实施者；C08 HEAD 不符回 C08 主会话；实际消费证据未取得只补后续消费面；
   T018A 实例/授权不可用交用户，某段失败交业务执行者。
   修后重验原用例与受影响面，结论只按新原件改，由原判定者重报；
   修复者的自述不算复验证据。
7. **承接**：结论写在 `quality/evidence/P4/AC-first-judgments.md`
   与各卡「完成」字段；P5、P6 读这两处与原件指针拿结论与缺口；
   T018A 的链记录、库外证据与复放回执一并供 P5 T021/T022、P6 T023。
   首判未执行时记 `incomplete`，外部条件不可用记 `unavailable`，
   均写判定者、观察协议与恢复条件。

**效果类判据（语义判定，不是命令退出）。**

- **判什么**：独立读者只看 P4 原件，就能说出新侧六段哪段真接上、
  哪段是接缝、两页哪条行为由哪条测试证明、更新链为何通过
  或只后续消费面 incomplete。
- **谁判**：未参与阶段四执行的独立读者；不需要用户本人到场。
- **怎么观察**：干净 shell，按本文件命令重跑一条目标测试与一条审计；
  不看实现者说明；能指出接缝与缺口算过，只能复述「都跑过」算没过。
- **证据落点**：`quality/evidence/P4/AC-first-judgments.md`，
  记读者身份、命令、输出与原话；通过记 `pass`，未执行记 `incomplete`。

## 为什么现在做，依据是什么？

设计段与实现段必须在同一条新侧流程里真跑，才能证明两页不是空壳。
本 Phase 是整轮验证里唯一同时产出两页实现、页面验证与更新链的位置。

- **结果**：六段流程有五段原件与一条条件链，两页可构建、可启动、可操作。
- **非目标**：不做旧侧、指标与报告，不替 C08 造更新。
- **与其它 Phase 的区别**：P2 修入口，P3 跑旧侧，P5 做计量与无稿，
  P6 写报告与交接；本 Phase 不判整体收益。
- **依据**：D-011（新侧按复杂任务走）、D-012（提取用 ego）、
  D-013（先原型再实现）、D-014/D-015（审查与页面可运行）、
  D-016（debug 用真实问题）、D-017（更新链消费 C08）；
  `spec.md` 的功能需求 5～9 与验收 3～7；
  004 就绪原件第 5 节把原型与八维审查落在任务 12～13。

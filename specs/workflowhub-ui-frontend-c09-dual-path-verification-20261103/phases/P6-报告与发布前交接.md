### 七个槽

1. **验收标准**：本 Phase 承接验收 11、12，逐条写成能判真假的话。
   验收 11：每条验收有档位与原件指针；八卡有档位表；
   十二包有收敛状态；有稿/无稿四对象十六格逐格核真实来源与应用，缺适用格不判通过；
   六项指标逐项判达到、未达到、未覆盖或不适用；严重未解不报达标；
   不适用必须写理由，不占达标分母，不写成未覆盖；
   小偏差逐项列出并一批取得用户真实确认；
   报告有效性与产品达标分两列；写清单案例与顺序效应；
   独立读者只读报告，能说出达到、未达到、未覆盖、不适用各有哪些。
   验收 12：交接件含报告指针、真实消费者、依赖版本与环境、
   未覆盖与失败、质量状态；每项指向可回读原件；
   只读交接件能列出发布前还缺什么；不把打包、安装、更新检查、
   兼容与上线写成已完成。
   失败信号分别是：报告写完即宣布产品通过、总分吞 `unknown`、
   把单案例说成显著、缺原件仍记档位、复制全部材料、缺项不留名。
2. **场景**：正常场景是报告写完、独立审查、末验、交接、收口。
   反向场景一：把 AC-P07 的未交付写成「已消费」，
   报告检查必须判失败并保留 `unavailable`。
   反向场景二：把遮挡视口或未测状态写成 pass，
   末验的逐条结论必须拒绝，档位改回 `incomplete`。
   反向场景三：交接件只写「已完成」没有指针，
   独立读者必须列不出缺口，检查判失败。
3. **环境与数据**：环境是认证工作区、任务事实库与检查器；
   数据是 P1～P5 的原件、指标表、比较、用户确认与验收对象 JSON。
   不重跑实现、不重采、不构造替代数据。
   验收对象检查用 `--spec` 与本次真实 context，不伪造 context；
   context 按当前 spec 的 1440×900（主）/1280×900（辅）生成，
   checker 期望 0；`missing_fields` 非空时判对应验收未完成。
   证据全部保留，不用完删。
4. **用例**：CASE-P6-1 到 CASE-P6-3 与任务 23～25 一一对应，
   命令见各卡门禁字段与「怎么验证」的测试面表。
   判定方式是命令退出码加独立读者复读；命令退出 0 只证明结构可读，
   不证明语义；语义由第 5 槽的判定者按观察协议判。

## 怎么验证？

用真实原件、真实检查器与独立读者跑报告、末验与交接三组检查；
本 Phase 属报告与交接段，没有先红后绿形态，不宣称红或绿。

开工前四要素，逐条对应本 Phase 的三条用例：

- **验证层**：报告结构与档位、末验十三项、交接五类事实、人读复述。
- **命令或数据**：本文件与各卡门禁字段给出的命令；
  数据是 P1～P5 的原件与验收对象 JSON。
- **预期结果**：每条命令退出 0，且报告/交接含具名通过元素；

- **失败条件**：缺档位、缺原件、两列合一、未覆盖写成已覆盖、
  交接缺类、验收对象缺项被填假值。

### 七个槽

1. **验收标准**：验收 1（AC-P01）只有一条：首跑前实验台输入全部固定且可复算，
   矩阵六维冻结，定义早于首跑。
   判据是复算结果与原件时间；成功是七件齐备、复算一致、定义时间早于首跑；
   失败是任一哈希不符、矩阵缺状态或视口、定义在开跑后才补、分母被换。
2. **场景**：正常场景按任务 5→4→6→1→2→3→7 执行，每步落一件原件。
   反向场景零：先跑命令或先渲染、后补定义，必须判失败；事件首条必须在命令之前。
   反向场景一：把任一副本的一件改成别的内容，同一哈希检查必须非零，该侧停。
   反向场景二：拿旧十六件聚合值冒充 `UI`，任务 3 的脚本必须拒绝并退出 1。
   反向场景三：矩阵任一格留「未冻结」、视口为空、共享数据哈希不符或清单不足 238 行，
   任务 6 的检查必须非零，且不得开始任何真实运行。
3. **环境与数据**：环境是认证工作区与本机 Node、npm、Python、两套浏览器引擎；
   数据是主仓提交、载体十件、设计源十六件、任务文字 261 字节、矩阵取值、
   共享数据与 238 行视觉清单；共享数据只从既有示例抄录，不新造。
   这些都由本机现有原件提供，不构造假数据；证据件全部保留，不用完删。
   每次删除或移动前先核绝对路径；只处理本 Phase 自建且无未交付字节的对象。
4. **用例**：七条用例逐条对应一个任务，命令见各卡门禁字段与「怎么验证」。
   判定方式是结构检查退出码加独立读者复读；命令退出 0 只证明结构可读，
   不证明语义；语义由第 5 槽的读者按观察协议判。
   `CASE-P1-1` 到 `CASE-P1-7` 与任务 1 到 7 一一对应，不另造编号；执行顺序按卡序。
5. **谁判**：由未参与阶段一执行的独立读者判定，与实施者不同上下文。
   执行时点：七张卡完成、审查问题改完之后；首判一次，P6 末验只读回放。
   判定者拿到七件证据、`spec.md` 的验收 1、共享数据哈希、238 行清单、
   两条复跑命令与一份哈希的原件；
   不改验收标准、不改实现。
6. **失败回修与重验**：失败信号是哈希或指纹不符、任务文字字节不符、
   矩阵未冻结、检查非零。

   设计源归任务 3 writer，定义与矩阵归主会话。

## 为什么现在做，依据是什么？

不先把输入固定，后面四段会各拿一份自己的输入，四格就不可比。
本 Phase 是整轮验证的第一道闸：它只证输入可复算，不证任何流程效果。

## 怎么验证？

`spec.md` 的「全局验证策略」 与 `:1427` 规定只有实现段用红绿，本 Phase 属证据段，
不宣称红或绿，只报执行与未执行。

开工前四要素，逐条对应本 Phase 的七条用例：

- **验证层**：命令回执、文件哈希、结构检查与独立人读，不用单元测试。
- **命令或数据**：本文件与各卡门禁字段给出的命令；数据是真实提交与文件字节。
- **预期结果**：每条命令退出 0，且原件与冻结值逐字相等。

## L0 — 结果与变更

本 Phase 要改变的结果是「一件事该写在哪个材料里」这条边界本身。现行规则让两处互相矛盾的措辞并存：`make-decision` 一边禁止规划任务问行号与代码片段，一边要求第 9 步逐模块「说明方案、替代、验收」并「补齐方案与验收标准」，于是决策材料里长出了 66% 的实现设计、83% 的坐标集中在四个模块收敛节，下游要判断"哪个是对的"，同一个事实被抄两遍。另一半是契约面：现行模板把 `文件路径:行号` 当首选锚点，而行号必然随前序改动漂移，于是「冻结」用在会必然漂移的东西上，保护成本落在错的对象上，真正的期望值来源反而被行号噪声淹没。本 Phase 把两半都写成单一归属：决策材料只留方向与决定，坐标、阈值与字段级方案归 `spec.md` 与 Phase 卡；契约面只由符号名与行为语义构成，行号降级为生成时刻的导航提示；TCR 边界钉死为「按名改已点名的具名常量取值不触发、改断言／期望方向／评分逻辑仍触发」，冻结 oracle 的单一来源按每任务声明一次。这与全局目标的关系是：设计材料的清晰度决定下游返工量，边界不写清，后面所有闭环、证据、停机规则都要建在一份会被逐条挑错的决策材料上。

- **结果**：八个写入文件里可读到的分工口径是——`decision-log.md` 只承载方向与决定及其理由（含受影响文件与符号名），坐标归 `spec.md` 的代码锚点节与 Phase 卡的「文件 / 符号」，判定阈值与字段级方案归 `spec.md` 的实现设计节与生产代码内的既有具名常量；契约面只写符号名与行为语义；行号只出现在导航性字段并被声明为生成时刻提示、漂移不判卡失效；两处 workflow 的既有测试变更请求条款与 `docs/architecture/test-asset-governance-rules.md` 的两段都写明「按名改已点名的具名常量取值不触发、改断言／期望方向／评分逻辑仍触发」，且该常量的点名义务落回 Phase 卡。
- **非目标**：不删 `make-decision` 第 9 步的任何既有义务（争议清单、逐条处置、方案、替代、验收、后果与风险、中途新增需求处置全部原样保留）；不实施篇幅治理（不设行数、字节、比例、评分器或预算）；不改 `runtime/` 下任何文件、不新增校验器或账本；不改 P2 已落地的切分依据段与 S1–S4；不写 P7 的判据面（`Done` 逐条档位与 AC 判定方式标注）；不改上游 `decision-log.md`、`GLOSSARY.md`、`CONSTITUTION.md` 与 `docs/adr/0035-*`／`0036-*`／`0038-*`／`0039-*`。

# talk-with-zhipeng

> 用大白话按问题组收敛方向、歧义、风险和范围，并把真实回答交给决策记录。

本技能分两层：

- **平台无关核心层**：纯对话收敛逻辑，包括调研摆出、影响排序提问、每答重排、收敛阈值、四维判定、输入护栏、丢弃登记、歧义校正。
- **薄适配层**：只负责对接当前 workflowhub 工作流的产物读写。默认从当前任务的调研与规格材料读取背景，把输出写回当前任务约定的相对路径产物。

判别器：一段逻辑是否依赖「具体工作流产物的读写」？依赖则入薄适配层；不依赖则入核心层。核心层不得触碰任何工作流私有路径。

## 输入

- 已有调研、规格、计划或代码阅读摘要。
- 用户原始需求、补充回答和可引用的上下文。
- 当前工作流通过受控 callback 提供的命名产物内容。
- 调用方声明的本轮编号与职责：
  - Round 1：真实痛点、成功标准、是否需要调研；
  - Round 2：方向、范围、非目标、关键取舍和风险；
  - Round 3：盲审发现、矛盾、关键假设和剩余风险。

若输入缺失，不直接提问，先进入输入充分性护栏并说明缺什么。本技能只负责 Talk；
Clarify 由 build-spec 的 `spec-clarify` 独占，不能在这里补一套。

## 执行协议

### 1. 建立本轮候选队列

每个 Round 都独立开始、独立结束，不得合并或借用另一轮代替。内部先生成完整候选
队列，按“会不会改变方向”排序，并标记 `待回答`、`已由事实回答` 或 `不适用`。
面向用户只展示本轮用途、当前第几个问题和当前队列总数；队列会随回答重排时明确写
“当前共 N 个，回答后可能变化”。不得把完整候选队列、内部排序或逐项处置倾倒给用户。

候选数量由真实未决问题决定，可以是零、一个或多个；不得设置固定最少或最多问答次数，
也不得为了凑数量制造问题。开始时没有 `high` 或 `medium` 待回答项，可以展示事实和
关闭理由后结束本轮；仍有这类问题时，把互相独立的问题放进同一批次，只有有依赖的问题
才拆到后续批次，并在真实回答后重新排序。

若调研结果缺失，先自检并反馈缺什么，不带着空背景进入追问。

### 2. 影响排序提问

把所有待问问题按「对方向的影响」从高到低排序。影响标尺 5 档：

| 档位 | 权重 | 含义 |
|------|:--:|------|
| high | 5 | 答案直接决定方向 |
| medium | 4 | 答案明显改变方向取舍 |
| low | 3 | 答案只影响细节，不动方向 |
| none | 2 | 答案对方向无关 |
| 已答 | 1 | 已经确定，不再问 |

一次展示一组互相独立的问题，按当前影响从高到低排序。多个决策轴只有在答案互不依赖
时才能放在同一组；有依赖的问题拆到下一组，并在用户回答后重新排序。不得把多个轴
拼成一个“完整方案”或“完整合同”问题；不影响主流程的问题做最小合理假设并说明。

### 2.1 大白话单轴决策卡

面向用户先说业务问题，不展示内部 ID、hash、receipt、attempt、runner 或其他执行黑话。
每张卡只包含：

1. 当前状态：`talk-with-zhipeng`、Round 编号、当前问题组编号和总组数；
2. 一组互相独立、每题只含一个决策轴的问题；
3. 影响范围；
4. 每题 2～3 个互斥选项；
5. 每题一个推荐项及推荐理由；
6. 每个选项的直接后果和主要风险。

提问卡不得再写“刚完成”“下一步”“需要你处理吗”或回答后由谁继续等重复段落。

不得让用户开放式填空。若新事实证明所有选项都不成立，承认选项失效，依据新事实重建
候选，而不是要求用户自己写第四个方案。

### 3. 每答重排

每个问题批次必须严格执行 `ask → wait/pause → real reply → resume → re-rank`：提问交给宿主可见会话后，
当前调用立即暂停；只有宿主返回与这张卡、当前 Round 和题号绑定的真实回复，恢复调用
才可继续。Agent 生成的答案、默认选择、旧回复或 decision-log 自报都不能充当 reply，
也不能据此进入下一题、改稿或审查。

真实生命周期至少要能回放为四个临时事件：`ask` 发布一张带正整数 `round` 的卡，`wait` 明确等待用户，
`reply` 带用户真实回复的来源、hash 和同一 `round`，`resume` 绑定同一张卡、同一 `round` 和同一回复后才继续。
Talk 的 `ask.questions` 可以是一组问题，但每题必须使用统一问题卡：

```yaml
question_id: scope-boundary
axis: 范围边界
independent: true
options:
  - { number: 1, label: 保守, meaning: "先少做一点", consequence: "范围更小", risk: "收益延后" }
  - { number: 2, label: 推荐, meaning: "直接解决当前问题", consequence: "一次解决", risk: "改动面更大" }
recommended_option: 2
recommendation_reason: "当前事实最支持这个选项"
```

用户可以一次回答全部或部分问题；未回答的问题保留，并在下一组中重新排序。聚合结果存在不等于已经收到 reply。

只把用户真实回复视为答案。每收到一批问题的全部或部分回答，都必须：

1. 记录回答及其来源；
2. 更新已知事实；
3. 重新生成并排序本轮全部剩余候选；
4. 标记被新事实回答或变为不适用的问题；
5. 更新下一张卡的题号和当前总数，再决定是否询问新的最高项；不展示完整重排表。

不要沿旧列表机械向下走。Agent 不得模拟、补写或代替用户回答。

下一张卡的总数必须按下面的同一公式重算：

`当前总数 = 本轮已经提出的问题数 + 重排后仍会改变方向的开放问题数`

总数只有在真实回答新增或消除开放问题时才能变化，并记录新增或移除的问题及事实原因。
只把题号机械写成 `2/2`、让分母始终跟着分子走，在仍有开放问题时属于失败。

### 4. 收敛阈值

每答重排后判断是否收敛。只有本轮队列中已没有 `high` 或 `medium` 的待回答问题，
本轮才结束。结束时只展示本轮已收敛的关键结论、问题处理数量、仍保留的风险和
“不再提问”的事实理由，再把完整回答、来源、假设和剩余风险返回调用方。简单任务
可以没有人工等待，但不能省略内部队列记录与面向用户的结束结论。

只要仍有会改变方向的待回答问题，本轮不得结束或提前收敛。

该判据复用影响排序机制，不引入第二套评分系统。

### 4.5 前置检查（外部接口核实 + 命名唯一定义）

四维判定只回答「要不要做」，不覆盖「怎么做的细节是否落地可信」。在进入范围四维判定前，先过两条前置检查：

- **外部接口核实检查**：本次涉及的外部工具/接口，有没有核实过真实调用方式？没有核实（不能只凭文档假设或记忆），直接转 S3 外部调研核实，不得带着未核实的接口假设进入四维判定。
- **命名唯一定义检查**：本次讨论的命名/路径/字段，如果后面会被多处复用，本轮必须钉死唯一定义（值 + 唯一来源文件），不得留到后续阶段各自约定、产生歧义。

两条检查任一未过，均在决策记录里显式标注「未过」及去向（转 S3 / 补充定义），不得静默跳过继续判定。

### 5. 范围四维判定

范围判断融入同一场对话。四个维度每维结论必须标「证据」还是「主观」：

- **A 真实痛点**：用户原文能直接引用卡在哪 = 证据；从行为推导、非用户原话 = 主观。
- **B 复杂度与 ROI**：有参照 case、改动量可估、ROI 可量化 = 证据；首次做、工程量靠猜、ROI 无数据 = 主观。
- **C 风险与影响范围**：能指认改动边界或列出受影响模块名 = 证据；无法列出具体影响路径 = 主观。
- **D 时机**：项目计划或阶段目标能引用 = 证据；有顾虑但无明确冲突 = 主观。

四选一裁决：可以做 / 可做但缓一缓 / 有风险需限制范围 / 不建议做。附上推翻条件清单，说明满足哪些条件时裁决会改变。

轻量档短路：当范围已明确且显然无需展开四维时，可跳过完整四维分析，直接输出 `verdict=轻量档可忽略`。

### 6. 输入充分性护栏

四维分析之前先自检输入是否够：

1. 需求描述是否足够具体，能判断痛点真实性？
2. 项目背景是否足以评估影响范围？
3. 时机相关上下文是否存在？

缺哪类信息且无法从上下文推断，直接反馈缺什么，不往下跑：

- 缺痛点描述：`缺少用户原始痛点描述，请补充`
- 缺影响范围线索：`缺少项目代码或模块背景，影响范围无法评估`
- 时机完全空白：可降级为「主观」继续，但必须在输出中标注

对需要推断、无法从原文直接读出的前提，在输出前显式回显让人纠正。

### 7. 丢弃台账登记

判定丢弃任何一条原始需求条目，必须登记「理由 + 去向」，禁止静默丢。理由缺失时裁决不成立。

### 8. 大白话聊天

所有提问与回答用大白话。一次给出一组独立关键问题；每题始终使用 2～3 个互斥选项，
说明推荐、后果和风险，用户直接回答编号，不使用开放式填空。

### 9. 歧义校正与方向收敛并行

回答含歧义或自相矛盾时，当场指出歧义并追问澄清，不带着歧义往下走。歧义校正与方向收敛并行进行。

### 10. 结构化字段显式保留

四维结论、四选一裁决、推翻条件、每条结论的「证据/主观」标注，都以结构化字段显式保留，落到决策记录里。

### 11. 返回最小交互事实

候选队列、问题卡、ask/reply/re-rank 过程只用于当前对话内收敛，不形成 run、revision、
latest、ledger 或独立交互历史。三个 Round 全部结束后，本技能只把父 Stage Agent 完成
当前决策所需的最小结构化事实返回内存：

```yaml
talk:
  status: completed
  round_count: 3
  architecture_direction_covered: true
  user_outcome_covered: true
decision_updates:
  - 只保留需要写进 decision-log.md 的结论、依据、风险或未决项
```

`architecture_direction_covered` 与 `user_outcome_covered` 只有在本轮真实覆盖后才能为
`true`。仍有会改变方向的问题时，本轮不能写 `status: completed`。本技能不填写 task、stage、snapshot、
decision ref/hash、文件路径或内容 hash；这些绑定由父 Stage Agent 在最终决策完成时组装。

不得返回或持久化完整候选队列、完整问题卡、逐轮问答历史、Grill 历史、secret、token、
password、credential、cookie 或其他秘密。用户真实答案的决策含义进入
`decision_updates`，原始对话仍留在宿主会话，不复制成第二套记录。

## 输出

```text
## 决策记录
- 最终 verdict：[可以做 | 可做但缓一缓 | 有风险需限制范围 | 不建议做 | 轻量档可忽略]
- 四维详情：
  - 真实痛点：[正面/中性/负面]（来源：证据/主观）
  - 复杂度/ROI：[正面/中性/负面]（来源：证据/主观）
  - 风险与影响范围：[正面/中性/负面]（来源：证据/主观）
  - 时机：[正面/中性/负面]（来源：证据/主观）
- 推翻条件：[什么情况下这个裁决会改变]
- 丢弃台账：[逐条 原始需求 -> 丢弃理由 -> 去向]
- 推断回显：[对哪些前提做了推断，待用户纠正]
```

## workflowhub 薄适配层

核心层产出的是「调研入 / 最小决策事实出」的纯逻辑。薄适配层只做两件事：

1. **读调研**：从当前 workflowhub 任务约定的相对路径读取调研、规格、计划或测试证据，整理成初始咨询材料。
2. **返回事实**：把最小 `talk` 和 `decision_updates` 返回父 Stage Agent；本技能
   不直接写工作流文件或质量记录。

适配层只负责「从哪读、往哪写」，不含对话收敛判断逻辑。换一个工作流只需换这一层，核心层不动。

## 约束

- 每条四维结论必标「证据」或「主观」，不得遗漏；「证据」必须有具体原文引用或可验证数据来源。
- 同一批次可以包含多个互相独立的关键问题；每题只问一个决策轴，互相依赖的问题拆到后续批次。
- 只把用户实际给出的回复当作回答；不得由 Agent 模拟、补写或代替用户确认。提问后必须等待用户回复，再继续依赖该答案的步骤。
- 三个 Round 的职责、开始队列、每答重排和结束结论必须在当前会话真实执行；长期只保留
  父 Stage Agent 完成决策所需的最小摘要，一轮的结果不能冒充另一轮已执行。
- 核心层不触碰任何具体工作流的私有路径。
- 不修改与对话无关的文件；丢弃任一需求条目必须登记理由。

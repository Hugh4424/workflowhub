# Diagnosing Bugs

核心：没有根因证据，不改代码。避免把症状补丁和重复 TDD 当作调试。

## 1. 建立反馈回路

先得到一个可由 agent 重复运行、能捕获用户所述症状的命令。优先：现有测试、最小 CLI/curl、trace replay、窄集成脚本、浏览器验收。非确定性问题提高复现率并固定随机数、时间、网络或数据。

无法建立回路：列出已尝试方法和缺失证据，转人工索取日志、trace、环境访问或临时 instrumentation 权限。禁止猜测修复。

## 2. 复现并缩小

- 连续运行反馈命令，确认是同一个失败。
- 每次删一个输入、调用者、配置或组件，直到剩余元素都不可再删。
- 跨组件链路记录每个边界的输入、输出、配置传播和状态，定位第一个偏离点。
- 从错误点反向追踪坏值来源；修源头，不修最终症状。

## 3. 假设与探针

列出 3–5 个按证据排序、可证伪的假设。每个写成：`若 X 是根因，改变/观测 Y 后应出现 Z`。一次只测一个变量。优先 debugger/REPL，其次带唯一 `[DEBUG-<id>]` 前缀的窄日志；性能问题先量 baseline，再 bisect/profile。

每个探针必须留下：假设、命令、关键输出、结论。若三次修复尝试均失败，停止叠补丁，转为架构问题并要求人工裁决。

## 4. 修复与验证

确认根因后：

1. 在真实 bug seam 写最小回归用例；没有正确 seam 时明确记录测试性缺口，不造假单测。
2. 只实施一个针对根因的修复，不顺手重构。
3. 运行回归用例、原始反馈命令和相关测试。
4. 清除全部 `[DEBUG-<id>]` 和临时 harness。
5. 记录根因、证据、修复机制、未覆盖风险。

需要人工参与复现时，可复制并修改同目录 `hitl-loop.template.sh`；不得把模板直接当作项目测试。

## 来源边界

本地版本以 Matt Pocock `diagnosing-bugs` 的紧反馈回路为主，吸收 Superpowers `systematic-debugging` 的证据/单假设纪律，以及 gstack `investigate` 的调查—分析—假设—实现顺序。不引入它们的全局发现、TDD skill 跳转、gbrain、telemetry、Bun、hook 或宿主专用工具。

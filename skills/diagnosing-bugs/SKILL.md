# Diagnosing Bugs

核心：没有根因证据，不改代码。用根因证据区分诊断与症状补丁、重复 TDD。

## 1. 建立反馈回路

**Tight loop**：一条能捕获用户确切症状、秒级、确定且可由 agent 无人值守运行的命令。先核本题所需领域术语和已有 ADR；建立命令时只探索必要路径，复现前不从代码阅读直接推断根因。

优先使用现有失败测试、最小 CLI/curl、trace replay、窄集成脚本或浏览器验收。非确定性问题提高复现率，固定随机数、时间、网络或数据，记录受控条件和实际复现率；一次没失败不证明修复。

完成判据：已实际运行至少一次，留下命令与脱敏输出；命令走真实 bug 路径并断言用户所述症状，能在该 bug 上变红、修复后变绿。启动、依赖或权限失败只说明环境不可用，不是目标 RED；“没有崩溃”也不是症状断言。收紧无关初始化和输入，使回路足够快且可重复，性能问题保留测量基线。

无法建立回路时，列出已尝试方法和缺失证据，向用户索取脱敏日志、trace、环境访问或临时 instrumentation 权限，保留未完成并交还控制权；收到真实证据或权限后再恢复。禁止猜测修复。没有已跑的 red-capable 命令，就不进入假设。

## 2. 复现并缩小

- 连续运行同一反馈命令，确认是用户描述的同一个失败，保留确切错误、输出或性能信号。
- 每次删一个输入、调用者、配置、数据、步骤或组件，删后重新运行；仍红才保留删减，否则恢复该项。直到每个剩余元素都对复现承重，移除任何一个都会使该症状不再出现。
- 跨组件链路记录每个边界的输入、输出、配置传播和状态，定位第一个偏离点。
- 从错误点反向追踪坏值来源；修源头，不修最终症状。

完成判据：复现与动态最小化均已实际完成，保留每次删减和命令结果，再进入假设。只列出“可删哪些项”不是最小化执行；不能缩小时明确缺口与原因，不冒充本步完成。

## 3. 假设与探针

列出 3–5 个按证据排序、可证伪的假设。每个写成：`若 X 是根因，改变/观测 Y 后应出现 Z`。一次只测一个变量。优先 debugger/REPL，其次带唯一 `[DEBUG-<id>]` 前缀、仅覆盖能区分假设边界的窄日志；性能问题先量 baseline，再 bisect/profile。

每个探针必须留下：假设、命令、关键输出、结论。命令和输出先脱敏，凭据通过环境变量传入，只展示诊断所需信号。若三次修复尝试均失败，停止叠补丁，转为架构问题并要求人工裁决。

## 4. 修复与验证

确认根因后：

1. 在真实 bug seam 写最小回归用例；接缝必须复现真实调用点的 bug 模式（包括所需多调用者或跨组件链路）。没有正确 seam 时，缺 seam 本身就是 finding，明确记录测试性缺口，不造假单测。
2. 有正确 seam 时，将已最小化的复现转成该 seam 的回归用例，实际看它捕获同一症状失败后，只实施一个针对根因的修复，不顺手重构。若靠变异代码或 fixture 制造红，先与未变异原字节比对，确认变异确已生效且不把外来失败当目标红。
3. 运行回归用例、原始未缩小的反馈命令和受影响相关测试；确认原症状消失且回归用例通过。缺 seam 保留 finding，不能宣称已有回归保护。
4. 清除全部 `[DEBUG-<id>]` 和临时 harness，核实际创建资源及临时原型已清理；取消或中断时保留原始失败、已执行结果和尚未清理项，返回控制权，恢复先核现场，不假报完成。
5. 记录根因、证据、修复机制、未覆盖风险；让提交或交付说明引用实际成立的假设，保留失败来源。

需要人工参与复现时，可复制并修改同目录 `hitl-loop.template.sh`；不得把模板直接当作项目测试。

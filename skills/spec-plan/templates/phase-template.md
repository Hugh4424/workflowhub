## 写完之前先回答：这是一个能独立验收的结果吗？

先答三问；答不完整就不要写 H1，先拆 Phase。
这一节是写作前脚手架，不进真实文件；答完即删。

1. 这一个 Phase 交付的是一个结果吗？
把结果写成一句能判真假的话，不写名词串，也不写文件清单。
2. 谁来判它真假？
指名哪条验收的哪个判定器，以及判定那一刻用的是哪份真实产出。
3. 它能独立提交吗？
写完就能提交并停手，不等同一计划里的另一个 Phase 才能验收。
如果需要等，它们就是两个 Phase。

判定规则：按实际交付与验收对象判断边界。
各自有完整可观察结果且能独立验收的交付应拆，并按真实依赖定序。
共享判据的部分按下面四条核合并；标题里的联词不决定 Phase 数量。

何时应当并：任一成立即应当并。
S1 共享同一条验收判据。
S2 判定 B 时必须看到 A 的产出，且这不是“开工要等”。
S3 必须一起交给同一真实消费者。
S4 拆开后各自没有外部可观察变化。
逐条点名判据、所需产出、消费者或外部变化，再申报写集与依赖。
不以文件所有权或技术层决定边界，不引入数字阈值。

先按真实判定器核每个候选有没有自己的完整结果，再决定边界和开工顺序。
若 A/B 只是同一判定对象的两部分，各部分没有独立完整结果，就作为同一交付。
“另一个 Phase 先交付并独立验收”是固定开工输入，不是 S2。

应并对照：make-decision 的入口真实返回与同一次边界读回，共同判“入口三项事实有来源且在边界可读”。
只产 `workflows/make-decision/scripts/entry-evaluation.mjs`
的 `evaluateEntryRoute` 返回，或只产没有返回来源的展示，
都不能独立判该完整结果。

应分对照：假设一个入口结论已经按自身判据具名独立验收，成为固定输入。
后续 Phase 索引作者取得该输入及实际 Phase 契约头，按索引自身判据独立核权威指针、依赖、写集与消费者的一致性。
这是两个独立交付，只需开工前取得已验收输入并保真实依赖；S2 不据此要求并。

四条误用反例：
同一个技术层不等于共享判据。
同一份材料里被提到不等于判定必须看到对方产出。
同一个人做不等于必须一起交给同一真实消费者。
拆开后测试都过不等于各自有外部可观察变化。
用各自实际成功或失败信号核，不拿这些替代 S1–S4。

本条是执行纪律，不是新的 stage、gate 或质量结论。

## 怎么拆 Phase？

按交付内容、用户故事和验收标准拆，不按文件、步骤或人拆；整份计划的经验范围是 2–7 个 Phase。
上一节判一对候选该不该合，这一节定整份计划按什么拆、大概几个。
拆完逐个用上一节三问复核；答不完整说明这次交付还没定型，先补结果再定 Phase 数。

### 拆分的依据是什么？

只有三条依据，每条都要能用一句话说清。

- **交付内容**：这一次交付一个什么可用的东西，谁拿走就能用。
- **用户故事**：谁因此能做什么，写成“某人可以完成某件事”。
- **验收标准**：怎么判这次交付成立，一条能判真假的判据。
三条答不齐，说明这次交付没定型，先补结果再拆。

### 什么时候能单独成一个 Phase？

能独立交付、能被独立验收、验收失败时改动范围可控，三条都成立才单独成 Phase。
“改动范围可控”指回修落在本 Phase 写集与它的 Task 内，不牵动别的 Phase 已收口的结果。
缺任何一条就并回相邻交付，不靠多加一个 Phase 绕开验收。

### 哪些拆法是错的？

下面四种拆法一律不写，看到就并回去。

- **按文件拆**：每个文件一个 Phase；文件只是写集，不是交付。
- **按步骤拆**：先写代码、再写测试、再跑一遍各成一个 Phase；它们是同一交付的卡内顺序。
- **按人拆**：谁做谁一个 Phase；人不是验收对象。
- **只有准备、整理或补充**：这类活不交可验收的东西，不单独成 Phase。
一个 Phase 只有“准备”或“整理”的活，说明它还没有交付，先找到这次要交的结果。

### 什么时候应当并？

两个 Phase 的验收必须一起做才有意义时，它们就是一个 Phase。
更细的判据按上一节三问与 S1–S4，逐条点名判据、产出或消费者。
合并后写集仍逐文件点名唯一 writer，不因合并变成两人同写一个路径。

### 2–7 个是提示还是限制？

2–7 个只是经验提示（来源：决策 A2 的经验范围，无外部基准），不是判定阈值，也不改上一节「不引入数字阈值」。
它不产生新字段、新校验器或新 gate；数字只帮读者估计规模，不产生通过或失败判定。
超过 7 个时，在 `spec.md` 的「谁先谁后？」写一句为什么不能再合，点名挡住合并的验收标准。
少于 2 个不算错：能一次交付并验收的任务就该是一个 Phase。
这条提示不许写成“超过 N 个即失败”，也不替代上一节的拆并判据。

### 拆多了贵在哪里？

每个 Phase 都要走完整七步，Phase 数翻倍等于总工时翻倍。
固定成本是读材料、定验收、派开发、派审查、派测试、回修与收口；它不随交付变小。
所以能合就合：先按交付内容合并，再按验收标准核对，最后才按并行需要拆开。
并行只在两批输入独立且写集互斥时才值得；串行拆细只增加固定成本。

## 这份文件怎么用？

本文件只写本 Phase 的实现增量，以及指向 `spec.md` 全局目标的稳定指针。
这一节是写作前脚手架，不进真实文件；落盘时整节删除。
全局产品契约与全局实现设计归 `spec.md`，本文件不复制、不改写、不重述。

本文件由作者编写，不写执行状态。
跑没跑过、RED 有没有真的出现、GREEN 是否成立，属于任务事实库，不属于本文件。

同一 Phase 的每个 Task 各占一张完整卡片，编号在全任务内唯一。
一张卡交一个用户可感知、可独立演示或验证的增量，同交付的连续步骤留在卡内。

写明真实依据与可执行动作；占位符不能充当已完成内容。
确实不适用写 `N/A — 具体理由`，未核实写 unknown、影响和下次核实动作。

下面五个字段名保持英文：`gate_cmd`、`oracle`、`evidence_path`、`STOP`、`Done`。
这些标签便于现有读者定位；内容必须可执行，但标签或文件存在不证明验证完成。

落盘时把标题里的 `P<n>` 换成真实编号，例如 `# Phase P3 — 配置错误定位`，文件为 `phases/P3-配置错误定位.md`。
实际文件标题与索引引用保持一致，方便作者与现有读者定位；标题不认证执行身份。

「开始前读什么？」与「下一消费者拿什么继续？」只写已核实的锚点与事实，每条带来源。
runtime 不解析它们，但审查会按「列进来的锚点是否真的打开过」抽查。
这两节也是 Phase 交接的唯一去处：上游交回什么、下游拿什么继续，都写在这两节。

按「结论 → 依据 → 例外与风险」组织，每段只写一个主题。
用主动句写动作，保持术语同义，不为缩短省略条件、否定或必要解释。
这是写作指引，不是质量门。
允许的例外：G-2 示例块与被锁定文字原样保留，精确路径、字段名和逐字声明不缩写。

模板版本（仅供人读，runtime 不解析）：`phase-file.v1`。

## 这一 Phase 交出什么？

先写谁得到什么结果，一句话能判真假。

- **本 Phase 结果**：[一句话说清交付什么、谁受益]
- **非目标**：本来可以成为要做的目标、但本 Phase 明确不选的项，写清不选的理由；不要写成否定句，也不要把“防止范围膨胀”当成理由。
- **改动前**：[已核实的当前状态与痛点]
- **改动后**：[改动完成后的可观察状态]
- **与相邻 Phase 的边界**：[上游给了什么、本 Phase 交给下游什么]
- **主要风险**：最可能让本 Phase 返工的一件事，以及**若因它返工，替代走法是什么**。
- **下一步**：[本 Phase 结束后，谁接着做什么]
- **动手前必读**：[`文件路径:行号` 或材料节锚点，按读序排列]
- **未决事实**：[已知但尚未核实的未知、它的影响、打算在哪个 Task 处理或交给谁；没有就写 `N/A — 理由`]

## 这一 Phase 怎么验收？

设计前先算三笔账；三笔算不出来，先别写验收。

- **成本账**：逐条引用 spec Appendix A 的成本七字段与资源来源，按下述公式汇总。
- **资源账**：每条标出所需外部件与来源；写「就地造」的，要写清怎么造。
- **范围账**：每条标出它证的是本 Phase 的哪个交付；跨 Phase 的写成「供件」不写「承接」。

每份 Phase 的验收节必须能回答「这些验收全部做完要多久、需要谁、需要什么」。
答不出来就是没设计好。

### 验收活动预算怎么算？

作者先核对 make-decision 已确认的任务形状与测试策略，再填写本 Phase 总账。
任务形状预检写验收数、涉及模块、数据量、最长测试、外部输入与测试数据层级。
分类只用可直接做、需拆分、需用户确认的长跑三类，不以固定数值自动裁决。
189 文件、22GB 数据、3.7h 单测这类形状先标需拆分，不能只加预算塞进同一 Phase。
缺形状或策略回 make-decision 补齐，计划作者不重新选型或补默认值。

逐条映射验收、独立测试代理、原判定器与数据层级。
S 是合成或种子，M 是真实子集，L 是完整数据；选择来自已确认策略。
前置 S/M 不能代 L；完整数据验收在唯一末验收安排一次。
两面有各自判定器且可独立并行时，给至少两个只读测试代理。
只有一面时给一个并说明原因；代理不共享写入，主会话合并原结果并保留冲突。
缺任一映射先补齐，不带缺项进入 Phase；不按代理数或命令数设质量门。

活动执行成本只计实际操作与可控等待；墙钟总跨度另列。
串行估算相加，每个并行组取并行最大，再加共享准备与重试预留。
并行测试代理的准备与重验预留按实际分项计一次，不重复加同一笔成本。
例：30 + max(60,45) + 10 + 15 = 115 活动分钟。
前三项验收的成本仍各归 spec；共享准备 10、重试预留 15 的提供者与依据写在本节。
用户等待、审查等待、真实环境等待各自单列来源与恢复条件，不混进活动总额。
真实环境的操作仍计活动成本；其中纯等待单列，避免同一时间重复计价。
提供者审查等待不套用户等待上限。

以下字段给人读，只填写本 Phase，不写任务存储或新预算账本。

- `acceptance_cost_total=115 active_min`：上述串并行算例，不是实测。
- `phase_budget={soft_min:120,hard_min:240,variance_threshold:1.5,source:provisional}`。

120/240 分钟及 1.5 只作待校准示例；真实值沿已确认决定，缺值回原 owner。
活动估算超过软上限先拆分或缩减重复验证，保留原验收与完整覆盖。
不得为了预算直接删通过/失败判据；涉及验收或范围变化回原决定 owner。
255 分钟例先展示总额、根因和拆分；仍超硬上限须引用用户真实确认。
缺确认保持草稿或该路径未决，不以“没有验收变化”绕过确认，不自动批准。
用户确认等待单路径十五分钟是待校准示例；无答复停该路径，记 awaiting_user。
阈值只帮助复盘与展示，不建立机器退出门或全任务轮次上限。
实现执行成本由后续执行方法另算，不与本节验收成本混账。

本 Phase 的执行预算另写
`execution_budget={window_minutes,command_cap,wait_cap,retry_reserve}`。
每项注明真实来源与单位，不把验收活动估算当作已发生活动账。
执行策略只消费 make-decision 的真实答复；未知回原 owner，不在计划补默认值。
检查点、事件等待、停扩/复盘、并行测试面与大件证据指针，

### 档位使用规则

`incomplete` 只用于「本可做但本轮没排上」的验收。

`unavailable` 只用于外部条件客观不存在。

### 改前基线怎么取得？

## 效果判据怎么写？

效果判据判消费者拿到什么结果，不判实现做了什么。
只能证明「做了」：命令退出 0、字段在场、断言数量不变、文件存在。
能证明「做对了、有效果」：具名消费者用真实输入完成原任务，错误输入得到可辨信号。
反例：`npx vitest run tests/config.test.mjs` 退出 0，只证明测试跑了。
正例：独立执行单元只看 stderr 就找到第 7 行，并复述要改的字段。
语义判定写判定者、观察协议与证据落点；命令退出码不代替它的结论。
验收判据不写比例、计数或零值；只能靠数数或比例判的不是验收。不设通过阈值、不写读数为零。
示例只示范能靠读材料判的判据段，不示范 `grep=0`、覆盖率或读数为零。
本节是写作指引，不是质量门；它不新增字段、枚举或校验器。

### 语义判定怎么写？

判定只能是语义判定时，判定方式写 `只能人读`，按下面四项写实。

- **判什么**：一条能判真假的效果陈述。
- **谁判**：判定者身份，以及与实现者的上下文差异；判定者是另一执行单元，不需要用户本人到场。
- **怎么观察**：看什么、怎么记、什么算过、什么算没过；写清环境与数据。
- **证据落点**：原件路径与该记的档位。

如果你的验收结论只能写成「命令退出 0」，那它证明的是实现存在，不是效果达成。
请补一条语义判定，或把档位记成 `incomplete`。
语义型验收的结论不由命令产生；机器合同仍要求每个 Phase 有可执行 `gate_cmd`。
两者靠人读规则调和，不改校验器；允许「无命令 Phase」属另一次决定。

## 每张任务卡怎么写？

每张卡先按 8 个问题写正文，再写机器字段；正文在机器块之前。
8 个问题按序：为什么做、交付什么、不做什么、前置、怎么做、怎么验收、证据、下游（含何时停）。
它们落到既有字段，不新增字段：

| 人读问题 | 落到哪些既有字段 |
| --- | --- |
| 为什么做 | 来源 / FR / AC |
| 交付什么 | 输出 / 失败 |
| 不做什么 | 边界 / 禁止改动 |
| 前置 | 输入、依赖 |
| 怎么做 | 动作、文件 / 符号 |
| 怎么验收 | 测试层级 / 技能、场景 / 夹具或服务、RED/GREEN 门禁命令、预期退出码、RED 目标失败、GREEN 判定器 |
| 证据 | 证据、覆盖上限 |
| 下游（含何时停） | 停止 / 恢复、完成 |

本节的放置位置按选节表里本节的放置规则，两种位置都合法。
机器字段从「任务编号」开始，集中在卡末，标「校验器用，人可跳过」。
任务卡必须放在文件末 `## 机器字段（校验器用，人可跳过）` 之前。
机器块之后只放附录或示例；把卡片放到机器块之后会被判为形状错误，卡片字段也可能被机器块吞掉。
机器字段按 `skills/material-writing/SKILL.md` 的「材料写作标准（唯一）」第 9 条写。
可以折行，续行缩进，校验器会合并；首行不得为空或占位，也不必为迁就校验器写成超长单行。
人读正文按同一标准第 5 条写。
卡里那行加粗的「校验器用，人可跳过」是固定标记，不能删，也不能换成普通文字。
标记上一行的 lint 例外注释只为让 markdownlint 放行 MD036；照抄这张卡时把注释一起带上。
8 问的正文每行以问题名开头、后接一句实答；不要写成字段行，机器块从「任务编号」开始。

### G-2 纯文档示例（既有字段，无新增运行行为）

每个 Task 都完整重复一张卡片。

覆盖上限：只证明本次文档复放与具名模块输入。
显式不覆盖：不证明真实用户长期使用，也不证明说明之外的模块行为。

## 验收 Phase 才能做的检查

本节是本小交付唯一末验收 Phase 的填写处，两个验收都在这里逐条收束。

1. **入口准则**：Phase 1 的 Done、写入集落地与两份就绪件的 status 各写一行，缺件写缺口。
2. **两份就绪件**：数据侧是模块当前字节，环境侧是 Node 可执行；同类别新增实例不算新文件类型。
3. **授权边界**：本例无外部账号、无副作用，写明可全自动复放，不设人工确认。
4. **逐条结论**：两条验收各一行，写编号、一个档位与一条具名证据路径；行数与条数相等。
5. **五类执行事实**：命令与参数、cwd 与执行者、exit code、原始输出落点、机器可读报告各记一处。
6. **效果评测**：本例不做指标比较，写清不做的理由与影响，不写成通过。
7. **复验四项**：复验者与修复者上下文不同；F2P 与 P2P 各自用例清单按测试资产治理规则逐条列，计数属测试资产事实，不作验收判据。
8. **变更批准**：本例不增删验收集合，写「无」加理由。
9. **分诊与关闭**：本例无失败需要分诊；`Disposition` 初值在真实任务里留 `Pending`。
10. **回写五项**：`spec.md` 场景卡与验收表、覆盖验收、`facts.jsonl` 既有字段、修复记录各一行。
11. **六项结论**：评估与局限、与计划的偏差、未充分测试的特性、未解决事件、残留风险、签核对象逐项写。
12. **防自证五禁令**：判定器必须要求显式通过元素，不用「无失败即通过」。
13. **失败修复复验闭环**：本例无失败项；真实任务按失败、分诊、根因、修复、换上下文复验、回写走。

# simplicity-guard

## 定位

这是一个可直接由 stage-owned dispatcher 调用的只读 advisory lens/skill，不产
stage-result，不修改被审材料。build-spec/build-plan 直接调用它并保存
invocation fact；后续 wh-review 只读取该事实，不重复调用或重复计数。
它也可以被其他明确声明的 review packet 复用，但不能被偷偷变成第二个
stage owner。

审查目标不是把缺口变成更多要求，而是找出能删除、复用或缩小的内容。
发现额外内容时必须明确建议删除；不得用“以后可能需要”替它保留位置。

## 四阶梯决策树

依次向下，遇到第一个"能用"就停，不继续往下问。

```
P0：这项能力需要存在吗？
    必须能对应原始需求、已批准方向、已发生故障或明确硬约束
    → 不需要（YAGNI）：跳过，不写任何代码
    → 需要：继续 P1

P1：已有覆盖？
    仓库里已有能直接用的 / 标准库能做 / 平台原生功能能做 / 已安装依赖能做
    → 任一为真：直接用，禁止重写
    → 全否：继续 P2

P2：复用+改造？
    已有的东西改一改能不能用（改造也算复用，不算重写）
    → 能：改造复用，只改必须改的部分
    → 不能：继续 P3

P3：最小新增
    前三层都不行，才写代码。
    写法纪律（三条必须全部遵守）：
    ① 先想后写：动手前说清楚为什么 P0-P2 都不行，不确定就停下问，不做静默假设
    ② 最小代码：只写解决问题所需的最少代码，不写投机功能
    ③ 手术式修改：只动必须动的地方，只清理自己改动产生的孤儿代码，每行改动可追溯到需求
```

## Provider 审查协议

逐项检查待审方案中的新增能力、抽象、模块、入口、状态、证据、迁移和发布
机制。每项必须停在第一个可用阶梯，并在 finding 中写明 `P0`、`P1`、
`P2` 或 `P3`：

- P0 不成立：要求删除该内容，并指出它缺少哪一种必要性证据。
- P1 成立但仍新增：要求改为直接复用，并指出已有能力。
- P2 成立但选择重写：要求缩为手术式改造，并指出复用点。
- 只有 P0-P2 均不成立时才允许 P3；P3 仍须是解决已证明问题的最小新增。

重点寻找：

- 未经原始需求或批准方向授权的 scope creep。
- 仓库、标准库、平台或已有依赖已经覆盖的重复已有能力。
- 仅因“长期理想架构”“以后可能需要”加入、但没有故障证据或硬约束的能力。
- 为执行或证明当前流程而新建第二套流程、证据、状态或发布系统。
- 只增不删：修订后旧抽象、兼容层、任务或文字仍被无理由保留。

审查 `build-code` 时只裁决当前 diff 中的范围扩张、重复路径、投机抽象、
兼容层、死代码和隐藏失败兜底。不得重开 accepted 产品范围，不得按 LOC
或个人风格裁决，也不得删除需求明确要求的测试、输入校验、错误处理、安全
或可访问性保护。

任一上述问题会实质扩大实现或维护面时，输出 `revise_required`。只报具体、
可执行的删除或缩减 finding；不得建议顺手建设通用框架。没有这类问题时，
不制造 finding。

## 例外（不适用四阶梯）

以下场景不得因追求少代码而删掉已证明必要的保护：

- 信任边界的输入校验
- 防丢数据的错误处理
- 安全措施
- 无障碍基础

## 配套禁止项

- 禁止投机性抽象（为"将来可能用到"而写的代码）
- 删除优于新增（能删就不要保留）
- bug 走根因，不打补丁
- 审查建议不能比问题本身更复杂

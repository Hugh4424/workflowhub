本文件写给 make-decision、build-plan 与 build-code 作者；读完要能定位需求、决定、写集、验收与原件。

### 答复登记：原话和语气怎样保留？

本节是答复来源分级、来源身份与语气词表的唯一权威；方法与其它材料只引用本节，不另立词表。
每条真实用户答复逐字进需求索引唯一原件，主文只引用编号。
索引列固定为 `编号|来源分级|答复原文|语气|原件ref与行位|时点|所属包`，七列都必填，不另建第二索引或增删列。
现行 v2 模板把这一列写作「原件位置」，与本模板的「原件ref与行位」是同一个位置列；`build-decision-baseline.mjs` 两种都读、空白不计，规范检查器只认逐字「原件ref与行位」。
索引顶部的「主干」与「最小切片」按「包清单怎样分层，主干与最小切片写在哪？」节写。
主干段不占这七列，也不新建第二个索引。

来源分级回答“谁写了这句、如何取得”，只有四类：

- 自由手写：用户自己写的原话。
- 明确选项采纳：用户选了给定选项；答复原文只写用户选中的那句逐字原文，题目、选项含义与真实所选保存在该条目 `原件ref与行位` 指向的问答批次原件，索引不为它增列；找不到含题目与选项的批次原件就写缺口，不凭记忆补题目。
- 保存转录：从聊天、录音或粘贴件转存；逐字回原件。
- 作者推断：作者根据上下文得出，明写“这是推断”，不得写成用户答复。

来源身份回答“谁对这条答复负责”，闭集只有两个值：用户答复、作者推断。
来源分级是作者推断时来源身份必须是作者推断；其余三类必须是用户答复。

语气回答“允许、要求、建议还是拒绝”，只有四档：permit、require、recommend、reject。
来源分级与语气是两个概念，不能互相替代，也不能用整体批准替代逐条答复。

原件 ref 与行位接受四种写法：`path#L7-L7`、`path#L7`、`path:7`、`path:7-9`。
相对 ref 先按任务根、再按 `quality/evidence/decision-log-refs/` 解析；两处都不可读或同时命中不同文件时按缺口处理。
答复原文必须是原件的完整答复载荷：去掉行首列表符或序号（`3.`、`3、`、`3)`、`3）`、`（3）`、`(3)`，只去一次）、反引号包裹与首尾空白后，与原行整句相等，或与其中一段反引号内容整段相等；在逗号或句号处截断的片段一律不是逐字原话，机检报 `ANSWER_SOURCE_UNVERIFIABLE` 并给出行位。

决策日志在四个内容字段（做什么／不做什么／风险／改动）之外，引用答复时另写三个来源字段：`source_id`、`modality`、`来源身份`；三者必须同时出现且非空，缺一即来源不可验证。
一个决定只引用一条答复；多条答复各写各的决定，不在一处重复声明三个来源字段。

验收引用必须带与原件相同的语气：允许不能被写成要求，建议不能被写成命令。

旧答复在每包收敛前先审，结论只有四态；落点是每包收敛台账同包的相邻行 `旧答复审计：<答复编号>｜<四态>｜<原因或去向>｜<ref>`，不占十列之一，也不另立第三份台账。四态值固定为：

| 四态 | 含义 | 同包相邻行还写 |
| --- | --- | --- |
| 可用 | 原话与语气仍成立 | 继续引用的答复编号 |
| 被推翻 | 用户后来否定了它 | 作废原因与替代答复编号 |
| 部分变化 | 范围或条件变了 | 变了哪一部分与受影响落点 |
| 需重排 | 顺序或所属包变了 | 原位置、新位置与 owner |

审计保留原话与作废原因，不自动摘要、不改写历史批次；未审不得直接复用旧答复。

填写示例（受控演示，不冒充真实用户）：
`| U-901 | 保存转录 | 允许升一次数据库结构，旧数据兼容。后果：迁移失败会读不回旧条目，先用隔离库验。 | permit | talk/2026-11-12-003-talk-batch-3.md#L7-L7 | 2026-11-12 | 1 |`
对应决定写 `source_id: U-901`、`modality: permit`、`来源身份: 用户答复`；把 permit 写成 require 时，机检报 `ANSWER_MODALITY_MISMATCH`。

跨任务回放原答时，检查器只读认证任务根与显式 `--source-root <绝对目录>` 授权的来源根（`--source-root` 必须与 `--file` 同时用）；未授权的外部 ref 按不可验证处理，不静默放行。

索引缺来源、缺原件行位或取不到逐字原文时写具体缺口与提供者，不冒已登记。
机检据同一索引核来源存在、原句行位与语气；旧形状没有声明新来源合同只标形状差异，不改写历史。

## 确认点：三问、可改项与叫停怎样记？

确认点先问三件事：问题对不对、最小切片对不对、什么情况叫停。
「可改项」指用户可当场改的四类东西：范围、最小切片、验收、风险；连带可改本包工作量胃口。
胃口写四个数：轮次（最多问几轮）、上下文（最多读多少材料）、成本（最多花多少）、返工（允许返工几次）。
越界叫停写成一条可执行规则：signal（看到什么）→ threshold（到什么程度）→ action（停哪一步）→ owner（谁处理）。
用户改了哪一条或选了哪个可改项，逐条登记为答复，不只写“已确认”。
确认展示与答复引用分别读本日志的展示记录与「答复登记」节，不互相替代。
包清单确认在骨架确认时一次完成；逐包收敛前的合并分诊另做，只决定先补调研还是直接收敛，不重新确认清单、不改排已确认次序、不新增确认轮。

## UI 范围与设计基准：页面与设计源是什么？

只有 UI 任务写本节；非 UI 任务不写、不留空壳。
UI 任务按第 1 步三源判定，在「原始需求」之后写五行卡。
三源是原始页面或交互要求、真实路由与组件与技术栈、已接受计划或实际前端变更。
三源任一命中即按 UI 处理；三源都缺记“未知”加负责人，不默认非 UI。

| 行 | 写什么 |
| --- | --- |
| 是不是 UI | 写“是；依据……”或“否；理由……”。 |
| 页面、路由与组件 | 涉及的页面、路由、组件与影响范围。 |
| 设计源、提供者与可用时间 | 四路中选哪路、来源、负责人、何时可用。 |

## 验收面

### 工作包 1 怎么验收？

判据只写本包能观察到的结果。

每条 AC 只判本包交付；判据禁计数/比例/零值（沿 `skills/material-writing/SKILL.md` 第 11 条），存在即通过不算判据。
已验前置供件是输入（写谁验的、验的原件或命令、恢复条件），不写成本包完成条件。
确实依赖别包尚未交付的物时，单列「外部依赖」：EXT 前缀编号、owner、恢复条件；EXT-NN 按本包出现顺序编号，跨包不复用；该依赖不作为本包完成条件，外置原件仍沿「外置事实索引」，不另建台账。
观察协议按本节「观察协议表」逐条填；字段定义只在表里一处。
除验收明确要求命令退出码的项外，命令只作辅助，必须写明它证明了哪个现象。
案例：任务库归档 `strategy-iteration-t09-data-freeze-20261115` 的 `decision-log.md:449`（AC6 原写法）与 `decision-log.md:812-826`（终末窄修正），路径按当前任务库解析；本条只引用，不复制正文。
不得以样例或写死字符串冒充真实值。

#### 每个包怎么验收

- **成功什么样**：下游拿到决定、文件与验收索引。
  - 三处编号互相对应。
- **失败什么样**：任一落点缺失、编号冲突。
  - 下游要回问作者才能继续也算失败。
- **谁判**：未参与本包写作与实现的具名独立观察者（人或角色），不写泛称。
- **何时判**：写具体时点或前置完成条件。
- **观察什么**：写可观察的交付行为或字节。
- **在哪看**：写原件、页面或命令的落点。
- **什么算过**：写通过/失败的观察结论。
- **正例**：写一个应通过的实例。
- **反例**：写一个应失败的实例。
- **这条不检查什么**：写清边界，防越界判。
- **外部依赖**：EXT 编号、owner、恢复条件；不作为本包完成条件。
- **环境与数据**：本任务当前材料与真实来源原件。
  - 缺失时记 incomplete（未完成）并写恢复条件。
- **成本**：决策作者本人执行，预计一小时。
- **资源来源**：复用本任务既有材料与原件，不新造样张。
- **为什么不能再简**：观察实际交付（编号只作定位）；抽检能判真伪时不再全量。
  - 全量复核不增加判别力。
- **承接**：结论写本包决定与验收面同号 AC（验收判据）。
  - 未执行写档位（证据强度的八值分级）。
  - 证据落点写证据保存在哪里。
- **落地 Phase**：写清本包由哪个 Phase 落地。
  - 写 Phase 编号与承载文件路径。
  - 不落地的包要写明为什么，并写明产出交给谁。

### 覆盖结论是什么？

覆盖结论（示例）：需求 1 与 变更 1 均有 决定 1 落点。

唯一覆盖原件复用现有三栏。
三栏是来源、事实与处置、落点或缺口。
每个需求与每个变更各一行。

缺口格式是“原编号／原来源／缺哪一落点”。
已读却未交的需求或变更，事实栏明写“已投递未执行”。
缺口栏写应落现哪节、缺哪一输出、owner 下一动作。
登记未处置的项必须以缺口出现一次。
finding（审查发现）、风险、OI（未决问题）各归原处置位置。
不属于需求或变更的项，也在原处置格写缺口或“已投递未执行”。
原 ref 与 owner 下一步也要写。
影响需求或变更时，覆盖原件的对应格引用原处置。
不复制全文，不另建未处置清单。
排除需求仍须真实用户选择的理由、影响与去向。

# 功能规格：需求名称

- **功能名**：写出面向用户的名称。
- **来源**：写出上游功能描述和 accepted decision 的精确引用。
- **状态**：草稿、已接受或已替换。

## 速读卡（30 秒）

- **一句话问题**：说明谁在什么情况下遇到什么问题。
- **核心变化**：说明用户最终能做成什么。
- **范围边界**：说明本期覆盖和不覆盖的业务范围。
- **最大风险**：指出最值得先确认的风险或未决项。
- **验收信号**：写出做对后能直接观察到的结果。

## 1. 问题与紧迫性

用短段落说明现状、现有方式为何不够、受影响的人或流程，以及现在处理的原因。只写问题和影响，不写代码或方案。

## 2. 背景、目标与范围

### 背景

说明与现有产品、流程和 accepted decision 的关系。

### 目标

- 每条写一个完成后可验证的用户结果。

### 范围内

- 列出本期必须交付的业务范围；不做事项只放在第 7 节。

## 3. 用户场景与状态覆盖

### SCN-001：场景名称

- **角色**：说明谁触发场景。
- **Given**：说明前置状态。
- **When**：说明用户动作或业务事件。
- **Then**：说明用户可观察结果。

### 状态覆盖

| 状态 | 结论 | 场景 | 理由 |
| --- | --- | --- | --- |
| 默认 | 写适用或 N/A | 写 SCN ID 或 N/A | 说明理由 |
| 空 | 写适用或 N/A | 写 SCN ID 或 N/A | 说明理由 |
| 错误 | 写适用或 N/A | 写 SCN ID 或 N/A | 说明理由 |
| 加载 | 写适用或 N/A | 写 SCN ID 或 N/A | 说明理由 |
| 取消 | 写适用或 N/A | 写 SCN ID 或 N/A | 说明理由 |
| 边界 | 写适用或 N/A | 写 SCN ID 或 N/A | 说明理由 |
| 权限 | 写适用或 N/A | 写 SCN ID 或 N/A | 说明理由 |
| 竞态 | 写适用或 N/A | 写 SCN ID 或 N/A | 说明理由 |

适用状态必须引用场景；不适用写 `N/A — 具体理由`。

## 4. 产品事实与假设（PFACT）

- **PFACT-01**：写一条产品或流程事实。
  - **status**：只选 `verified`、`inferred`、`unknown` 或 `not_applicable`。
  - **正式证据**：仅 `verified` 填 task-relative ref、hash 和 source ID。
  - **推断来源、限制**：仅 `inferred` 填来源和不能据此确定的内容；这里是该假设的唯一真相。
  - **owner、影响**：仅 `unknown` 填负责人、影响和关联 OPEN/RISK ID。
  - **不适用理由**：仅 `not_applicable` 填具体理由。
  - **影响**：列出受影响的 FR ID 和 AC ID。

每条只保留所选 status 的字段；未知 PFACT 必须关联 RISK 或 OPEN。

## 5. 功能需求

### 功能域名称（DOMAIN）

先用短段落说明该域解决的问题和用户体验，再列需求。

- **FR-DOMAIN-001**：写一个独立、可观察、可测试的行为。
  - **范围边界**：说明包含和不包含什么。
  - **依据**：列 decision ID 和 PFACT ID。
  - **场景**：列 SCN ID。
  - **验收**：列 AC ID。

新需求使用 `FR-DOMAIN-NNN`；`FR-NNN` 只用于读取 legacy 文档。

## 6. 条件式业务合同

每个子节要么写完整适用合同，要么只写 `N/A — 具体理由`。

### 6.1 模块职责

#### 模块名称

- **负责什么**：写业务职责。
- **提供什么**：写给上下游的业务结果。
- **依赖什么**：写需要的上游业务能力。
- **验收边界**：写可独立验收的结果。

### 6.2 关键实体

#### 实体名称

- **定义**：写实体代表什么。
- **字段**：写业务含义、允许值或约束。
- **关系**：写与其他实体的业务关系。

### 6.3 数据与生命周期

- **数据粒度**：一条数据代表什么。
- **更新与时效**：实时、批量或失效时间。
- **缺失或迟到处理**：是否补传，以及用户看到什么。
- **预览与正式**：用户看到哪一种状态。
- **当前与历史**：覆盖或累加，历史是否保留。
- **归属与保留**：谁持有，保留多久。
- **清理策略**：淘汰或归档规则。

### 6.4 兼容性

- **既有消费方**：已有用户或上下游行为如何保持。
- **命名预留**：产品命名如何不堵死后续版本。
- **容器预留**：用户可见结构如何容纳后续内容。
- **状态预留**：产品状态如何容纳后续取值。
- **扩展边界**：本期预留什么，不承诺什么。

## 7. 明确不做与默认必须成立

### 明确不做

1. 写不做事项、decision ID 和阶段性或永久性质。这里是唯一权威非目标列表。

### 默认必须成立

- 写产品约束，并关联 FR ID 与 AC ID。工程门禁和精确命令留给 plan/tasks。

## 8. 业务影响与回归范围

### 受影响功能

- **既有行为**：说明当前如何工作。
- **本需求影响**：说明用户可观察变化。
- **回归路径**：说明必须重新走通的业务流程。
- **验收**：列 AC ID。

- **可能受冲击的业务规则**：写必须保持的不变量。
- **明确无影响**：写已检查且不受影响的功能、数据或流程。

## 9. 验收标准

- [ ] **AC-01**：写一个可判真假的用户或业务结果。
  - **需求**：列 FR ID。
  - **验证方法**：写人工步骤、测试层级或证据观察方式。
  - **通过条件**：写出现什么结果算通过。
  - **失败条件**：写出现什么结果说明未通过。
  - **证据类型**：写 `test`、`evidence` 或 `manual`。

验证方法停留在产品层；精确命令和工程 oracle 留给 plan/tasks。

## 10. 风险、未决与交接

- **RISK-01**：写风险主题。
  - **受影响 ID**：列 PFACT、FR 或 AC ID。
  - **触发条件**：写何时发生。
  - **后果**：写用户可观察影响。
  - **缓解或 STOP**：写最小动作或停止条件。
  - **处理 Stage**：写 `make-decision`、`build-spec`、`build-plan`、`build-code` 或 `verify-code`。
  - **验证**：写如何证明已处理或仍存在。

- **OPEN-01**：写未决问题。
  - **受影响 ID**：列 PFACT、FR 或 AC ID。
  - **owner**：写负责作出决定的人或角色。
  - **影响**：写不解决会改变什么。
  - **处理 Stage**：写处理阶段。
  - **关闭条件或 STOP**：写什么事实可关闭，或何时必须停止。

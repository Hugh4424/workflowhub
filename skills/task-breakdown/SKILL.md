# Task Breakdown

读者：三个阶段（含轻档与三个子流程）开工时的执行者与独立审查者。
读完要能先找一手来源、把源条目当覆盖分母、逐条需求过五问再切包，并为每包交一张人话卡。

## 先读这张表

本节只给路径与节锚，不写判据；判据在对应文件与内核里，照指针去读。

- 方法正文九条与问句：本文件 `#breakdown-method`。
- 每包人话卡的八格与内核指针：本文件 `#package-cards`。
- 停止条件摘要：本文件 `#stop-conditions`。
- 问题陈述八格模板：`references/问题陈述模板.md`。
- 存在性三态判据：`references/存在性判据.md`。
- 根因、影响面与验收清单：`references/根因影响验收清单.md`。
- 逐需求五问审查表：`references/逐需求五问审查表.md`。
- 格的唯一完整定义：`skills/unit-kernel/SKILL.md` 第 R6 条（只引条号，不复制判据）。

<a id="breakdown-method"></a>

## 拆包方法九条

一条需求从出现到可交付，按下面九条顺序过。每条只写问句与判法，形状与字段一律指回上表，不在此重复判据。

### 第 1 条 问题陈述

这条需求是谁、在什么场景下、现在怎么坏？
找不到一手来源（谁说的、何时、什么情境）就写「来源不明」，不拿转述当原话。
并写清什么会让我改主意（什么新证据会推翻这条问题判断），缺了记未取得。
八格与填写顺序见 `references/问题陈述模板.md`。

### 第 2 条 存在性

这个问题真的存在，还是只是看起来做了？
最小复现当场试一次，给「待证／真实／不成立」三态之一，见 `references/存在性判据.md`。

### 第 3 条 根因假设

一条主因能不能解释所有症状？
写一条主因加一条排除解释，清单与读数对照见 `references/根因影响验收清单.md`。

### 第 4 条 影响面

改它会影响谁、动到哪些数据和调用方？
四格落点见 `references/根因影响验收清单.md`，不在这里抄判据。

### 第 5 条 修复选项

有哪几条路，被否的为什么否？
至少写一条被否替代与它的适用条件；方案与取舍指回决策卡的对应格。

### 第 6 条 问题消失验收

怎么算这个问题真的消失了？
写通过条件、失败条件、至少一个反例与证据路径；验收标准形状指回 `skills/spec-specify/SKILL.md` 的验收标准节。

### 第 7 条 逐需求五问

每条需求过不过「问题／存在／根因／影响／消失」五问？
一条需求一行，结论与反证同格；并主动找一条反证（哪条读数能推翻结论），写进同格；问句与合并／拆分／依赖判据见 `references/逐需求五问审查表.md`。

### 第 8 条 覆盖

把源条目当分母，删一条会不会被报未覆盖？
分母＝源条目清单；按「源清单 ID 集合 − 覆盖表 ID 集合」（源−覆盖）与
「覆盖表 ID 集合 − 源清单 ID 集合」（覆盖−源）两个方向都重算，
任一方向差集非空即判未覆盖、不得写「完整」，差集要具名报出，不靠把表填满。

### 第 9 条 停止条件

什么情况下停手、不硬切？
见本文件 `#stop-conditions`。

<a id="package-cards"></a>

## 每包人话卡

切完包，每包一张人话卡，一包一节。八格名称与顺序如下，格的完整人读定义只引内核 R6，不复制正文。

- 一句话结果
- 对应需求
- 现状缺口
- 方案与取舍
- 边界
- 验收
- 风险与回退
- 未决

八格的完整人读定义在 `skills/unit-kernel/SKILL.md` 第 R6 条；本技能只给格名与顺序。
每包一节，标题写成「包 N：一句人话名」，编号在卡内就地解释，不出现未解释的内部编号。

<a id="stop-conditions"></a>

## 停止条件

- 找不到一手来源、也拿不到逐字原件：记「来源不明」，停该条，不拿转述代原话。
- 某条需求连最小复现都做不出、判为「不成立」：停该条并写理由，不硬塞进包。
- 源条目与覆盖表的两个方向差集任一非空却仍写「完整」：停，回覆盖这一步补具名差集（删源条目时查「覆盖−源」方向）。
- 需要新增检查器、字段或阶段才拦得住的缺口：停，写缺口、owner 与恢复条件，不改验收。

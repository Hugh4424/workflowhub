## 消费边界

交互作者规定用户能感知的结果，不另建业务状态机。
控件内事件与参数引用组件公开合同。请求序列、取消机制与资源释放引用工程源。状态术语引用领域源，外观和措辞分别引用视觉与内容源。若业务取消能力未知，反馈必须保留未知，不能用关闭面板推断后台撤回。

## 必填项与填写指引

作者先写用户可见变化，再链接产生它的证据。

| 项 | 填写指引 | 反例及原因 |
| --- | --- | --- |
| 适用范围 | 写平台、场景与已确认的用途 | “所有交互通用”：读者可能把局部规则套到业务命令 |
| 稳定术语 | 一个反馈含义只用一个名称，引用领域词义 | 把“已设置”与“可用”混称成功：不同事实被合并 |
| 条件与结果 | 用“当…时，…执行…”写单一行为 | 只列loading/error：没有触发、变化或owner |
| 恢复与取消 | 引业务能力；写保留信息及安全下一方向 | “关闭即撤回”：UI操作不能证明服务端结果 |
| 键盘与焦点 | 引原控件合同，补跨控件顺序与观察 | “按标准无障碍”：没有可复放路径 |
| 可观察验收 | 给输入、反馈、事实来源与失败信号 | 动画结束即通过：外观完成不是业务完成 |

## 反例与核对

核对者必须能区分用户意图、UI反馈和真实执行结果。
错误写法：“用户点取消后系统会自动回滚并成功退出。”原因：它把本地退出、服务端撤回与成功合成无来源保证。
可照抄写法：“当 `<用户取消本地等待>` 时，`<页面>` 停止 `<本地观察>`。`<已发命令>` 的结果仍由 `<原读回入口>` 核实。”
读者实写一个正常路径和一个失败或取消路径，逐项指出焦点、反馈与原结果来源；尚未执行的运行验证明确留缺口。

## 缺口与下一步

作者把未定业务行为交回相应任务/API owner。
现在必需：触发、结果来源、跨控件顺序及适用辅助信息。可待补：范围外输入方式的验证记录；不能据此宣称已覆盖。确实不适用：无提交场景的取消提交，注明无该操作。
缺口句式：“缺 `<权限/取消/焦点原合同>`，因此 `<消费者>` 不能确定 `<动作后果>`；`<提供者>` 补 `<具体决定或可回读合同>`，以 `<可观察结果>` 完成。”
本件不为缺失能力生成默认业务状态，也不以准备清单代替独立验收。
